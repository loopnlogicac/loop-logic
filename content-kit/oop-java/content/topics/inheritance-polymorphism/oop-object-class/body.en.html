Give objects a meaningful value contract

Two separately entered course codes may both say CSE212. The program may need to treat them as the same course value even though they are different objects. Object supplies common operations for Java objects, and value classes can override several of them with a deliberate policy.

The important operations here are toString(), equals(Object), hashCode() and getClass(). They answer different questions: how to describe the object, whether another value is equal, which hash bucket may fit it, and what its exact runtime class is. Do not use one answer as a substitute for another.

Every ordinary class inherits from Object directly or indirectly. That gives callers a common root reference type. An Object variable can reach a Course object, but the available compile-time operations come from Object. Correctly overriding those operations makes the value usable through that broad view.

Override the Object signature exactly

@Override
public boolean equals(Object other) {
    if (this == other) { return true; }
    if (!(other instanceof Course course)) { return false; }
    return code.equals(course.code);
}
@Override
public int hashCode() {
    return code.hashCode();
}

The equals parameter is Object, not Course. A Course parameter would add an overload while leaving Object’s identity equality in place. The method is public because the inherited operation is public. @Override helps the compiler catch both signature and access mistakes.

The demonstrated Course class is final and stores a non-null immutable String code. Its constructor inputs are documented as non-null. The identity check handles the same object quickly. The type pattern rejects null and unrelated types before comparing the chosen value field.

Separate identity, value and hash

Identity asks whether two references reach the very same object. For references, == performs that comparison. Object.equals also uses identity by default. A class overrides equals when its domain needs a different definition, such as equal course codes.

first  --> Course { code = "CSE212" }
second --> Course { code = "CSE212" }

first == second        false
first.equals(second)   true
hashes must match      true

Value equality depends on a selected set of meaningful fields. For a Seat, row and column might identify the value. A display label or cached calculation should not accidentally join equality unless the domain requires it. Choose that policy before writing code.

A hash code is an int used to help organize values, especially in hash-based containers. Equal objects must have equal hash codes. Different values may share a hash code, called a collision. A hash is neither a unique identifier nor a memory address promise.

Keep equality an equivalence relation

The equals contract has several parts. Reflexive means a non-null value equals itself. Symmetric means a.equals(b) agrees with b.equals(a). Transitive means that if a equals b and b equals c, then a equals c.

Equality must also be consistent across repeated checks while the information used by equality stays unchanged. A non-null object must compare unequal to null. These rules let callers group and search values without results depending on comparison direction or arbitrary timing.

The hashCode contract requires stable repeated results during an execution while equality-relevant state remains unchanged. It does not require the same hash across separate executions. It also does not require unequal objects to have different hashes. A useful distribution improves performance but is not the equality definition.

When overriding equals, override hashCode using the same equality-relevant fields. For two int coordinates, 31 * row + column is a simple combination. Int overflow is defined in Java and is acceptable in such hash calculations. The equality method still compares both coordinates directly.

Avoid surprising equality across a hierarchy

Value equality becomes harder when subclasses add identity information. A base Point may compare coordinates while ColouredPoint also compares colour. If the base accepts the child but the child rejects the base, symmetry breaks. The compiler cannot diagnose this behavioural error.

Making a value class final is one straightforward policy. No subclass can add incompatible value state. Another design uses composition: a coloured value contains a Point instead of extending it. More flexible hierarchies need an explicitly shared equality policy and careful reasoning.

Some classes use an exact getClass comparison in equals to reject different runtime classes. Others use instanceof to accept an agreed family. Neither choice is universally correct. The final Course example makes the distinction harmless because Course has no subclasses.

Keep equality fields stable when using an object as a hash key. If a course code changes after insertion, later lookup may compute another bucket. The object can remain stored but become difficult to find. Prefer immutable keys, or remove and reinsert around a controlled change.

Describe objects without confusing text with identity

toString should give a useful concise description for people reading diagnostics. Course[CSE212] communicates more than the default class-and-hash style. Avoid sensitive data and enormous nested object graphs. Calling println on a non-null object uses its toString representation.

A readable description is not automatically a storage format. If code later parses that text, harmless formatting edits can break data loading. Define a separate documented serialization format when persistence is required. Equality should not depend on text formatting unless that is the domain’s explicit value definition.

getClass returns the exact runtime Class object and is final in Object. instanceof tests compatibility with a type and accepts subclasses. These questions differ: a Child is an instance of Parent, while child.getClass() is Child.class rather than Parent.class.

If you know C: Java hashCode does not promise a raw pointer value. Memory management may move objects without changing their logical identity. Compare references with == when identity is the question, and call a well-defined equals when value is the question.

Check both halves of value equality

Overloading equals by accident

equals(Course) is a different signature. An Object reference will still select equals(Object). Use the exact public Object parameter signature and annotate the intended override.

Comparing hashes instead of fields

A collision can occur for unequal values. Hash equality is only a possible match and never proves value equality. Compare the domain fields in equals.

Ignoring mutable equality state

A setter on an equality field can disrupt a hash container’s assumptions. A private field is not stable if methods still mutate it. Choose a stable key or explicitly manage its removal and reinsertion.

Patterns simplify the type guard

The instanceof variable used in Course.equals became permanent in Java 16 and is available on Java 17. The Object contracts are much older. Records also arrived permanently in Java 16, but this lesson shows the ordinary class implementation explicitly.
