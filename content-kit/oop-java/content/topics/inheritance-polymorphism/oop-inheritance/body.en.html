A more specific kind of student

A scholarship student still has a roll number and can register for courses. The scholarship adds information without removing those student abilities. Inheritance lets a class describe a more specific kind of an existing type. Java writes this relationship with extends.

Call the general class the superclass or parent. Call the more specific class the subclass or child. Student can be the superclass of Scholar. When you use a Scholar where Student is expected, the student promises must still hold.

Sharing a few lines is not enough reason to inherit. A library stores books, but a library cannot stand in for a book. That relationship needs references between objects. The useful question is whether every child can behave correctly wherever the parent is required.

If you know C: placing one struct inside another does not create Java’s subtype relationship. Java also selects overridden instance methods through the actual object. You do not manage a superclass object with a separate pointer or free its memory manually.

Declare the relationship and initialize its state

class Scholar extends Student {
    private final int award;
    Scholar(int roll, int award) {
        super(roll);
        this.award = award;
    }
}

The class name after extends is the direct superclass. Scholar adds its own award field. The superclass remains responsible for initializing its own roll field. super(roll) invokes a Student constructor with that argument.

Constructors are not inherited. You write the constructors a child needs and arrange the superclass call. Accessible methods may be inherited, but private parent fields cannot be named directly in a separate child class. The child can ask an accessible parent method to operate on that state.

Trace the constructor chain before the child body

A Scholar is one object containing the state required by its class hierarchy. There is no separately created Student object waiting inside it. A Student reference may refer to this same Scholar object. References with different declared types can therefore share one identity.

For ordinary construction, Java initializes fields to default values before constructor work begins. Constructor chaining reaches the superclass first. After the superclass constructor returns, the child’s instance field initializers and initializer blocks run in textual order. The rest of the child constructor body then executes.

If a Java 17 constructor has no explicit constructor invocation, Java supplies super(). This works only when an accessible no-argument superclass constructor exists. Defining Student(int) does not also create Student(). You must pass the needed argument yourself.

A constructor may delegate to another constructor in its own class through this(...). That chain must eventually reach a superclass constructor. You cannot write both this(...) and super(...) as separate first calls in one constructor. The chain supplies the parent initialization once.

Read three common hierarchy shapes

Single inheritance describes one child directly extending one parent. Scholar extending Student is the smallest picture. A class may have many ancestors indirectly, but it still has only one direct class superclass.

Multilevel inheritance forms a chain. A LabTutor may extend Student, which extends Person. Methods available from Person can remain available further down the chain, subject to access and overriding rules. Long chains make construction and behaviour harder to follow.

Hierarchical inheritance describes several children of the same parent. Bus and Bike are separate branches below Vehicle. Neither becomes a subtype of the other merely because they share an ancestor. A Bike reference cannot accept an arbitrary Bus.

Single:       Scholar --|> Student
Multilevel:   LabTutor --|> Student --|> Person
Hierarchical: Bus --|> Vehicle <|-- Bike

Most ordinary classes ultimately extend Object. If you omit extends from a normal class declaration, Object is its direct superclass. Object itself has no superclass. Useful Object operations, including equality and text descriptions, receive their own discussion later.

Why one class parent matters

Imagine two class parents both storing balance and both implementing withdraw. A child inheriting both would need rules for choosing state and behaviour. Java avoids this class inheritance ambiguity by allowing only one direct class superclass. The declaration cannot list two classes after extends.

A class can still offer several capabilities through interfaces. A campus terminal might be both Printable and Scannable. Interfaces describe contracts without creating a second class-state ancestry. The Interfaces lesson explains defaults and how explicit conflict resolution works.

The one-parent rule does not remove all design choices. A deep hierarchy can still expose unsuitable inherited methods or depend too closely on parent implementation details. Keep inheritance focused on stable behavioural relationships. Use a collaborator when you need a tool rather than a more general identity.

Keep extension boundaries explicit

Parent implementation changes can affect every child. If a parent method starts calling another overridable method, a child override may now run in an unexpected place. Review inherited workflows when changing shared code. A shallow hierarchy with clear extension points is easier to maintain than a chain built only for line reuse.

Java 17 also supports sealed classes, which restrict the permitted direct subclasses. This differs from final, which permits no subclasses at all. A sealed hierarchy needs explicit declarations for its permitted children and their extension policy. The examples use ordinary open hierarchies, so their constructor and method traces do not depend on sealed syntax. Choose an extension restriction to express a real model boundary rather than to alter constructor order.

Check the relationship before fixing the syntax

Assuming private means missing from the object

A private parent field still contributes state to a child object. The restriction concerns access to its declaration. Preserve the boundary by using an appropriate parent operation, rather than making every field protected.

Forgetting an argument-taking parent constructor

An empty child constructor tries super() implicitly. If the parent offers only an int constructor, compilation fails. Call super with the required value as the first constructor statement.

Using inheritance to borrow an unrelated utility

A Course should not extend Calculator merely to reuse multiplication. Course does not satisfy a calculator contract. A utility call or contained calculator expresses that use more clearly and avoids inheriting irrelevant operations.

Constructor ordering on Java 17

These programs target Java 17. An explicit this(...) or super(...) invocation must come first in the constructor. Newer Java constructor rules are outside this lesson’s baseline. No preview features are needed for the hierarchy shapes shown here.

Keep the parent promise

Inheritance gives a specific type a general contract and shared implementation. Initialize parent state through its constructor and choose hierarchy shapes that reflect real substitutability. Next, study the exact replacement rules in Method Overriding.
