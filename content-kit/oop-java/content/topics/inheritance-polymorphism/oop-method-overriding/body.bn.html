একই অনুরোধে কাজের ধরন বদলাও

ফি ডেস্ক প্রতিটি ফি অবজেক্টে amount() কল করে। সাধারণ ফি আর ল্যাব ফি আলাদাভাবে হিসাব হতে পারে। কল একই থাকে। মেথড ওভাররাইডিং দিয়ে সাবক্লাস ইনহেরিট করা ইনস্ট্যান্স মেথডের কাজ বদলায়, আগের চুক্তিও বজায় রাখে।

শুধু নাম মিললেই ওভাররাইড হয় না। প্যারামিটারের signature, অর্থাৎ নাম আর প্যারামিটার টাইপের কাঠামো, মিলতে হবে। রিটার্ন টাইপ, অ্যাক্সেস আর এক্সেপশনের নিয়মও মানতে হবে। তাই প্যারেন্টের কলার চাইল্ড দিয়েও কাজ করতে পারে।

ডিপার্টমেন্টের ঠিক করা নোটিশে ল্যাব নিজের রুমের খবর যোগ করতে পারে। কিন্তু চাওয়া নোটিশটি দিতেই হবে। একইভাবে শুধু সঠিক signature দিয়ে কাজের অর্থ ঠিক থাকে না; নতুন মেথডকেও আগের চুক্তি মানতে হবে।

ওভাররাইড করার ইচ্ছা স্পষ্ট করো

class LabFee extends Fee {
    @Override
    int amount() {
        return 750;
    }
}

@Override দেখে কম্পাইলার যাচাই করে মেথডটি supertype-এর মেথড ওভাররাইড বা ইমপ্লিমেন্ট করছে কি না। এই annotation ছাড়াও রানটাইমে ওভাররাইড চলে। এটি বানান বা প্যারামিটারের ভুল আগে ধরতে সাহায্য করে।

Fee-তে amount() থাকলেও চাইল্ডে amount(int count) লিখলে নতুন ওভারলোড হয়। amount() বদলায় না। @Override দিলে কম্পাইলার এই ভুল ধরে।

মেথড signature-এ নাম আর প্যারামিটার টাইপ থাকে; জেনেরিক মেথডে আরও কিছু নিয়ম আছে। শুধু রিটার্ন টাইপ বদলে ওভারলোড হয় না। এখানকার সাধারণ উদাহরণে আগে নাম আর প্যারামিটার মেলাও, তারপর বাকি বিধিনিষেধ দেখো।

কোন কল চলে আর কোন অবজেক্ট পায় আলাদা করো

Fee fee = new LabFee()-তে ঘোষিত টাইপ Fee, আসল অবজেক্টের ক্লাস LabFee। কম্পাইলার দেখে Fee-তে amount() আছে কি না। রানটাইমে এই ওভাররাইডযোগ্য ইনস্ট্যান্স কল LabFee-এর ইমপ্লিমেন্টেশন চালায়।

কোন অবজেক্ট কল পায়?new দিয়ে বানানো LabFee
কোন ওভাররাইড চলে?LabFee.amount()

দুই মেথডের বডি নিজে থেকে একসঙ্গে চলে না। ওভাররাইডের বডিই পুরো কাজ দেয়। প্যারেন্টের হিসাবও লাগলে চাইল্ড থেকে super.amount() কল করো।

amount()-এর ভেতর this.amount() লিখলে সাধারণত একই অবজেক্টের ওভাররাইড আবার চলে। থামার শর্ত না থাকলে রিকার্শন চলতে থাকে। প্যারেন্টের কাজ নিতে super.amount() লাগে।

C জানা থাকলে: একই নামের ফাংশন নিজে থেকে Java-র মতো অবজেক্ট দেখে বাছাই হয় না। Java আগে ঘোষিত রেফারেন্স টাইপ দিয়ে কল যাচাই করে, পরে যে অবজেক্ট কল পায় তার ওভাররাইড বেছে নেয়। রেফারেন্সের মান তবু কপি হয়েই প্যারামিটারে যায়।

আগের মেথড রেখেই ওভারলোড যোগ করো

String প্যারামিটার আলাদা label মেথড তৈরি করে। পূর্ণসংখ্যা পাঠালে আগের int signature-ই চলে।

কলার যে চুক্তির ওপর নির্ভর করে তা রাখো

ওভাররাইডে অ্যাক্সেস কমানো যায় না। public মেথড public-ই থাকবে। protected থেকে public করা যায়, private বা package-private করা যায় না। নইলে প্যারেন্টের মেথড কল করার অনুমতি থাকা কলার চাইল্ডে এসে আটকে যেত।

রেফারেন্স রিটার্ন প্যারেন্টের রিটার্ন টাইপের subtype হতে পারে। একে covariant return বলে। Object দেওয়ার কথা থাকলে String দেওয়া চলে। String দেওয়ার কথা বলে Object দেওয়া চলে না।

প্রিমিটিভ রিটার্নে এই ছাড় নেই। int-এর বদলে long দিয়ে ওভাররাইড করা যায় না। void-ও void থাকবে। সাধারণ অ্যাসাইনমেন্টে সংখ্যা বড় টাইপে গেলেও ওভাররাইডের নিয়ম বদলায় না।

Checked exception কলারকে সামলাতে বা ঘোষণা করতে হয়। ওভাররাইড প্যারেন্টের চুক্তির চেয়ে বড় checked exception যোগ করতে পারে না। বাদ দিতে বা আরও নির্দিষ্ট করতে পারে। Unchecked exception-এ একই বাধা নেই। বিস্তারিত এক্সেপশন পাঠে আসবে।

আলাদা সাবক্লাসের মেথড প্যারেন্টের private মেথড ওভাররাইড করে না। final ইনস্ট্যান্স মেথড ওভাররাইড করা যায় না। কনস্ট্রাক্টরও ইনহেরিট করে ওভাররাইড করা যায় না। static মেথড টাইপের; তাতে hiding-এর নিয়ম চলে।

ওভাররাইড আর ওভারলোডের সিদ্ধান্ত আলাদা

বিষয়ওভাররাইডিংওভারলোডিং
প্যারামিটারইনহেরিট করা signature মেলেটাইপ বা সংখ্যা আলাদা
ইনহেরিট্যান্স লাগে?supertype সম্পর্ক লাগেএক ক্লাসেও হতে পারে
মূল বাছাইরানটাইমের অবজেক্ট দিয়ে ইমপ্লিমেন্টেশনকম্পাইলের সময় আর্গুমেন্ট আর রেফারেন্সের টাইপ দিয়ে
রিটার্নএকই বা মানানসই covariant রেফারেন্সশুধু রিটার্ন বদলে আলাদা হয় না
সহায়ক annotation@Overrideনতুন ওভারলোডে @Override নয়

এক কলে দুটোই থাকতে পারে। আগে কম্পাইলার ওভারলোড থেকে signature বেছে নেয়। পরে রানটাইমে তার ওভাররাইড বেছে নেয়। পরের পাঠে ঘোষিত আর আসল টাইপ আলাদা রেখে এই ধাপ দেখবে।

চাইল্ডে অ্যাক্সেসযোগ্য প্যারেন্ট static মেথডের একই signature লিখলে static hiding হয়। কাঙ্ক্ষিত ক্লাসের নাম দিয়ে কল করো। অবজেক্ট দিয়ে লিখে রানটাইম বাছাই হবে এমন ধারণা দিও না।

ফিল্ডও মেথডের মতো ওভাররাইড হয় না। একই নামের দুটি ফিল্ড আলাদা ঘোষণা, একটি অন্যটি hide করতে পারে। private ফিল্ড আর স্পষ্ট অপারেশন রাখলে স্টেটের অ্যাক্সেসকে পলিমরফিক মেথডের কাজের সঙ্গে গুলিয়ে ফেলবে না।

প্যারেন্টের মেথড সত্যিই ইনহেরিট হয়েছে কি না দেখো

অন্য প্যাকেজের চাইল্ড অ্যাক্সেস করতে না পারা package-private মেথড ওভাররাইড করার জন্য ইনহেরিট করে না। একই নামের চাইল্ড মেথড তখন আলাদা অপারেশন হতে পারে। প্যাকেজের বাইরে এক্সটেন্ড করার চুক্তিতে protected বা public কাজে আসে। signature মেলানোর আগে অ্যাক্সেসও দেখো। @Override এই আসল সম্পর্কই যাচাই করে।

শুধু নাম মিলিয়ে থেমো না

একটি প্যারামিটারের টাইপ বদলে ফেলা

score(long), score(int)-কে ওভাররাইড করে না। int সংস্করণটি থেকে যায়। @Override দাও; কম্পাইলার আপত্তি করলে পুরো প্যারামিটার তালিকা দেখো।

অ্যাক্সেস কমিয়ে আগের চুক্তি লুকানো

চাইল্ড public মেথড private করতে পারে না। সেই কাজ চাইল্ডে থাকা উচিত না হলে hierarchy আবার ভাবো। প্যারেন্ট টাইপের কলার এখনও চুক্তিটি দেখতে পায়।

super দিয়ে চাইল্ডের কাজ চাওয়া

super প্যারেন্টের ইমপ্লিমেন্টেশন বেছে নেয়। রেফারেন্স ভেরিয়েবলের রানটাইম প্যারেন্ট বোঝায় না। অবজেক্ট একই থাকে। বেছে নেওয়া প্যারেন্ট বডি আবার অন্য ওভাররাইডযোগ্য মেথড কল করতে পারে।

Java-র স্থায়ী ফিচার ব্যবহার করো

Java 17-এ covariant রেফারেন্স রিটার্ন আর @Override চলে। এখানে record, pattern matching বা preview option লাগে না। একই সোর্স ফাইলে ক্লাস লিখলেও নিয়ম একই।

চুক্তি রেখেই মেথড বদলাও

ইনহেরিট করা signature মেলাও, অ্যাক্সেস আর রিটার্নের নিশ্চয়তা রাখো। @Override দিয়ে কম্পাইলারকে যাচাই করতে দাও। ফলাফলে প্যারেন্টের কাজ লাগলেই super কল করো। এবার পলিমরফিজমে ওভারলোড বাছাই, রানটাইম dispatch আর cast একসঙ্গে দেখো।
