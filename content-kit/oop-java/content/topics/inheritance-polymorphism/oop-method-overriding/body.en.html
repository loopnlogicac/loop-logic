Keep the request, change the response

A fee desk asks every fee object for amount(). Ordinary fees and lab fees may calculate different answers. The caller still makes the same request. Method overriding lets a subclass replace an inherited instance operation while keeping its usable contract.

The name alone does not identify an override. The parameter signature must match an inherited method under Java’s overriding rules. The return type, access and exception promises must also fit. These rules let existing parent callers continue to use the child safely.

Think of a notice format agreed by a department. A lab may add a specific room message, but it must still provide the requested notice. Replacing behaviour is useful only when the replacement honours the original meaning. A valid signature cannot guarantee sensible behaviour by itself.

Make the intended override visible

class LabFee extends Fee {
    @Override
    int amount() {
        return 750;
    }
}

@Override asks the compiler to verify that the declaration overrides or implements a supertype method. It does not enable runtime selection; the override works without the annotation. Using it catches accidental spelling changes and parameter mismatches early.

Suppose Fee declares amount() but the child writes amount(int count). That new parameter list creates another method. It does not replace amount(). With @Override, the compiler rejects the mistaken intention instead of silently accepting a separate overload.

A method signature includes its name and parameter types, with additional details for generic methods. Return type alone cannot distinguish overloads. For the ordinary non-generic examples here, compare the name and parameter list first, then verify the remaining override restrictions.

Separate the callable contract from the receiver

For Fee fee = new LabFee(), the variable’s declared type is Fee and the receiver object’s runtime class is LabFee. The compiler checks that Fee offers amount(). At runtime, the overridable instance call uses LabFee’s matching implementation.

QuestionAnswer for fee.amount()
What operation is available?Fee.amount()
What object receives the call?The LabFee created with new
Which override runs?LabFee.amount()
What value returns?750

The method does not run both bodies automatically. An override completely supplies the selected implementation. If you want the parent contribution too, explicitly call super.amount() inside the child. This is useful when a child extends a calculation rather than replacing every part.

Calling this.amount() from amount() normally calls the current object’s override again. Without a stopping condition, that creates recursion rather than reaching the parent. super.amount() deliberately selects parent behaviour and avoids that accidental self-call.

If you know C: a same-named function does not automatically acquire Java’s receiver-based selection. Java checks a method contract through the declared reference type, then chooses the overriding instance implementation from the receiver. The reference itself is still passed by value.

Preserve what callers were allowed to rely on

An override cannot reduce access. A public parent operation must stay public. A protected operation may become public, but cannot become private or package-private. Otherwise a caller allowed to invoke the parent method could lose that permission after substitution.

A reference return may become a subtype of the parent return. This is called a covariant return. Returning String where Object was promised is safe because every String is an Object. Returning Object where String was promised weakens the result and is invalid.

Primitive returns do not use this rule. An int-returning operation cannot be overridden with a long return. A void operation also remains void. Numeric widening during an ordinary assignment does not change overriding requirements.

Checked exceptions are failures callers must handle or declare. The exception lesson explains them fully. An override cannot add a broader checked exception than the inherited contract allows. It may omit checked exceptions or narrow them; unchecked exceptions are not restricted in that same way.

A private parent method is not overridden by a separate subclass declaration. A final instance method cannot be overridden at all. Constructors are not methods inherited for overriding. A static method belongs to a type rather than an instance and follows hiding rules.

Both mechanisms may appear in one call. First the compiler chooses a signature from the available overloads. Then runtime dispatch selects an override of that signature. The next lesson develops this two-stage trace with arguments whose declared and runtime types differ.

Static hiding is another distinction. A child may declare a static method with the same signature as an accessible parent static method. Call it through the intended class name. Do not use an object expression to suggest that runtime instance selection will occur.

Fields also do not override like methods. Two same-named fields occupy separate declarations and can hide one another. Prefer private fields with clear operations. This keeps state access from becoming confused with the polymorphic method behaviour you intend to teach or use.

Check whether the parent operation is actually inherited

Package-private methods need special care across package boundaries. A child in another package does not inherit an inaccessible package-private parent method for overriding. A same-named child declaration may therefore be a separate operation. Protected and public methods can provide intentional extension contracts across packages. Before comparing signatures, check access and inheritance together. This also explains why adding @Override is useful: the compiler verifies an actual supertype relationship rather than accepting a visually similar name.

Look beyond the matching name

Changing one parameter type

score(long) does not override score(int). The inherited int version remains available. Add @Override to intended replacements and inspect the full parameter list when the compiler rejects it.

Reducing visibility to hide an inherited promise

A child cannot make a public operation private. If the child should not offer the operation, reconsider the hierarchy rather than fighting access rules. The parent contract is still visible to parent-typed callers.

Using super to reach child behaviour

super selects a parent implementation explicitly. It does not mean the runtime parent of a reference variable. The receiver is still the current object, and the selected parent body can itself call other overridable methods.

Use stable Java language features

Covariant reference returns and @Override are supported on Java 17. None of these examples requires records, pattern matching or preview options. The method rules apply equally when the concrete class is declared in the same source file.
