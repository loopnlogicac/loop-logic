টিকিট নীতি ব্যবহার করে, নিজে নীতি হয়ে যায় না

টিকিটের ভাড়া হিসাব লাগে, কিন্তু টিকিট নিজে ভাড়ার নীতি নয়। নীতির অবজেক্ট রেখে সেটিকে হিসাব করতে বলতে পারে। Java ডিজাইনে কম্পোজিশন বলতে সাধারণভাবে সহযোগী অবজেক্ট দিয়ে কাজ গড়া বোঝায়। সব ইমপ্লিমেন্টেশন ইনহেরিট করতে হয় না।

এটি has-a সম্পর্ক: Ticket-এর একটি Rate আছে। ইনহেরিট্যান্সে is-a সম্পর্ক হয়, যেমন StudentRide, Ride-এর চুক্তি মানে। দুটোতেই কোড পুনরায় ব্যবহার হয়, তবে চুক্তি আর নির্ভরতা আলাদা।

বদলানো অংশ মালিক অবজেক্টের ব্যবহারের টুল বা নীতি হলে কম্পোজিশন ভাবো। প্যারেন্টের পুরো কাজের চুক্তি মানলে ইনহেরিট্যান্স রাখো। এটি সম্পর্ক যাচাই করার পরামর্শ; সব সুপারক্লাস সরানোর নিয়ম নয়।

সহযোগী রাখো, অনুরোধ তার কাছে পাঠাও

class Ticket {
    private final Rate rate;
    Ticket(Rate rate) {
        this.rate = rate;
    }
    int fare(int distance) {
        return rate.fare(distance);
    }
}

Ticket কনস্ট্রাক্টরে Rate পায়। এখানে সঠিক, null নয় এমন নীতি ধরা হয়েছে। private ফিল্ডে কলার সরাসরি অন্য রেফারেন্স বসাতে পারে না। final হওয়ায় তৈরির পরে রেফারেন্স স্থির থাকে। হিসাবের অপারেশন ইন্টারফেস বলে দেয়।

Delegation মানে কাজের অংশ সহযোগী অবজেক্টকে দেওয়া। Ticket.fare থেকে Rate.fare কল হয়। বাইরের ক্লাস যাচাই বা দরকারি সমন্বয় যোগ করতে পারে, তবে নীতির চুক্তি চুপিচুপি বদলাবে না। স্পষ্ট নামে কাজের দিক বোঝাও।

Ticket আর Rate সহযোগী আলাদা অবজেক্ট। ReducedRate-এর সব অপারেশন Ticket-এ ইনহেরিট হয় না। Ticket নিজের public সীমায় বেছে নেওয়া কাজ দেয়। ভেতরের নীতি বদলালেও কলার সহজ টিকিটের অপারেশন পায়।

Rate রেফারেন্সেও পলিমরফিজম চলে। আলাদা ইমপ্লিমেন্টেশন একই fare দেয়। Ticket শুধু সেই চুক্তি জানে। প্রতি ফর্মুলায় Ticket সাবক্লাস না বানিয়ে তৈরির সময় নীতি বেছে নিতে পারো।

কিছু সহযোগী পুরো সময় স্থির থাকে। Display-এর style-এর মতো কিছু নিয়ন্ত্রিত মেথডে বদলানো যায়। এতে পরের কাজ বদলায়, মালিকের রানটাইম ক্লাস বা পরিচয় বদলায় না। নতুন সহযোগী মালিকের শর্ত মানে কি না যাচাই করো।

C জানা থাকলে: সহযোগীর রেফারেন্স অন্য struct-এর পয়েন্টার ফিল্ডের মতো লাগতে পারে। Java নিজে মেমরি ফেরত নেওয়া সামলায়। তবু কে component শেয়ার বা বদলাতে পারবে সেই মালিকানার নীতি তোমাকেই ঠিক করতে হবে।

Java-র সাধারণ কম্পোজিশন আর UML-এর কড়া সম্পর্ক আলাদা

Java-তে has-a ডিজাইনকে অনেকেই কম্পোজিশন বলে। UML composition-এ আরও শর্ত আছে: একটি part এক সময়ে সর্বোচ্চ এক composite মালিকের। মডেলে part-এর lifetime-এর দায়িত্ব পুরো অবজেক্টের সঙ্গে যুক্ত। ভরাট diamond পুরো অবজেক্টের পাশে থাকে।

private ফিল্ডেই মালিকানা প্রমাণ হয় না। দুটি Department একই Printer আর্গুমেন্ট পেলে একই স্বাধীন অবজেক্ট শেয়ার করে। এটি স্বাভাবিকভাবে association; মডেল চাইলে shared aggregation বলা যায়। private বলে exclusive composition হয়ে যায় না।

Lamp-এর ভেতরে তৈরি SwitchState পরিষ্কার একক component। দেখানো API-তে শেয়ার বা প্রকাশ করা হয় না। পরে mutable component ফেরালে মালিকানার নীতি আবার দেখতে হবে। আসল রেফারেন্সের পথ দেখে এনক্যাপসুলেশন আর মালিকানা বোঝো।

garbage collection UML-এর lifetime নিয়ম চাপায় না। মালিকের রেফারেন্স ছাড়লেই component সঙ্গে সঙ্গে ধ্বংস হয় না; অন্য রেফারেন্স থাকলে তো নয়ই। ডোমেইনে লাগলে deletion, invalidation আর resource cleanup-এর কাজ আলাদা ঠিক করো।

ভেবে শেয়ার করো, দরকারি প্রবেশপথে যাচাই করো

এক নীতি অনেক টিকিটে শেয়ার করা যেতে পারে। immutable হলে বা শেয়ার করা স্টেট চুক্তির অংশ হলে ঠিক আছে। mutable counter নীতিতে একটি টিকিট অন্যটিকে অপ্রত্যাশিতভাবে প্রভাবিত করতে পারে। সহযোগী মান, সার্ভিস, না নিজের স্টেট তা ঠিক করো।

কনস্ট্রাক্টরে dependency দিলে কলার নির্ভরতা দেখে, নিয়ন্ত্রিত ইমপ্লিমেন্টেশন দেয়। এটুকুতে dependency inversion হয় না; প্যারামিটার concrete ক্লাসও হতে পারে। ReducedRate-এর বদলে Rate নিলে কাজের abstraction পাও।

Delegation-এ ব্যর্থতার নিয়মও রাখতে হবে। fare শুধু শূন্য বা বেশি দূরত্ব নিলে যাচাই কোথায় হয় লেখো। কয়েক স্তরে অমিল পরীক্ষা কোরো না। মালিকের ফলের চুক্তি আর সহযোগীর ইনপুটের শর্ত মেলাও।

কম্পোজিশনে টাইপ, আর্গুমেন্ট, রেফারেন্স আর forwarding মেথড বাড়ে। সীমা পরিষ্কার বা পরিবর্তন আলাদা করলে খরচ কাজে আসে। স্থির এক লাইনের হিসাবে অনেক অবজেক্টের চেয়ে সরাসরি ইউটিলিটি কল পরিষ্কার হতে পারে।
