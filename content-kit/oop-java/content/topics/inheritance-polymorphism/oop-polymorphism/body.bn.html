যাতায়াতের প্রোগ্রামে সাধারণ আর শিক্ষার্থীদের রাইডের ভাড়া যোগ করতে হবে। লুপ প্রতিটি রাইডের কাছে ভাড়া চাইবে; সব ধরন চেনা তার কাজ নয়। পলিমরফিজম-এ একই সাধারণ টাইপ দিয়ে কাজ করো, আলাদা অবজেক্ট নিজেদের মানানসই কাজ দেয়।

ওভাররাইড করা ইনস্ট্যান্স মেথড দিয়ে Java-তে রানটাইম পলিমরফিজম হয়। ওভারলোডিংকে প্রায়ই compile-time polymorphism বলে, কারণ কম্পাইলার প্যারামিটার signature বেছে নেয়। দুটো সিদ্ধান্ত আলাদা তথ্য ব্যবহার করে। ধাপ দুটি আলাদা রাখলে আউটপুট অনুসরণ সহজ হয়।

রেফারেন্সের ঘোষিত টাইপ সোর্সে লেখা থাকে। অবজেক্টের রানটাইম ক্লাস তৈরির সময় ঠিক হয়। Fee ভেরিয়েবলে LabFee রাখলে অবজেক্ট সাধারণ Fee হয়ে যায় না। একই অবজেক্টের কম অপারেশন তখন দেখা যায়।

সাধারণ রেফারেন্সে নির্দিষ্ট অবজেক্ট রাখো

int amount = fee.amount();

এই অ্যাসাইনমেন্ট upcast: subtype-এর রেফারেন্স supertype দিয়ে ব্যবহার হচ্ছে। আলাদা cast লিখতে হয় না। Fee আর তার supertype-এর অপারেশন পাওয়া যায়। শুধু LabFee-তে থাকা অপারেশন চাইলে আরও নির্দিষ্ট টাইপের রেফারেন্স দরকার।

Downcast সেই নির্দিষ্ট টাইপে ব্যবহারের অনুরোধ। এতে ফিল্ড যোগ হয় না, অবজেক্টের ক্লাসও বদলায় না। null ছাড়া ভুল cast হলে রানটাইমে ClassCastException হয়। অবজেক্টের ধরন নিশ্চিত না হলে আগে পরীক্ষা করো।

Java 16-এর এই type pattern টাইপ মেলে কি না দেখে। মিললে lab ভেরিয়েবল পাও। সেখানে তার টাইপ LabFee, তাই বিশেষ মেথডগুলো কল করা যায়। null হলে শর্ত false। LabFee-এর সাবক্লাস হলেও মেলে; হুবহু একই ক্লাস হতে হয় না।

আগে রেফারেন্স আর আর্গুমেন্টের ঘোষিত টাইপ লেখো। কম্পাইলের সময় এগুলো দিয়ে signature বেছে নাও। তারপর রানটাইমের অবজেক্ট দেখো। বেছে নেওয়া ইনস্ট্যান্স signature-এর সবচেয়ে নির্দিষ্ট ওভাররাইডটি চলে।

প্রথম ক্ষেত্রে value-তে String থাকলেও print(String) বাছাই হয় না। ওভারলোড বাছাইয়ে রানটাইমের আর্গুমেন্ট অবজেক্ট দেখা হয় না। দ্বিতীয় ক্ষেত্রে literal-এর টাইপ String, তাই String ওভারলোড বেছে নেওয়া হয়।

সাবক্লাস একটি signature ওভাররাইড করে অন্যটি ইনহেরিট করতে পারে। Dynamic dispatch, অর্থাৎ রানটাইমে মেথড বাছাই, print(Object) থেকে পাশের print(String)-এ যায় না। নির্বাচিত signature-এর ওভাররাইড খোঁজে। তাই একই অবজেক্টে দুই কলের লেবেল আলাদা হতে পারে।

শুধু LabPass-এ lab ভেরিয়েবল তৈরি হয়, রুম প্রিন্ট হয়। সাধারণ Pass আর null অন্য শাখায় যায়।

ফিল্ড পড়া আর মেথড কল তুলনা করো

Base রেফারেন্স Base-এর ফিল্ড পড়ে। ইনস্ট্যান্স মেথড Child-এ dispatch হয়ে Child-এর ফিল্ড পড়ে।

cast করলেও অবজেক্ট আগেরটিই থাকে

Pass pass-এ new LabPass(12) রাখলে Pass টাইপ দিয়ে room কল দেখা যায় না। সফল downcast-এ LabPass-এর অপারেশন ফিরে পাও। দুই রেফারেন্স একই অবজেক্ট আর একই room ফিল্ড শেয়ার করে।

pass-এ new Pass() থাকলে LabPass-এর চুক্তিই নেই। cast নতুন কাজ বসাতে পারে না। রানটাইমে ClassCastException হয়। কম্পাইলার cast করতে দিতে পারে, কারণ অন্য কোনো Pass রেফারেন্সে সত্যিই LabPass থাকতে পারে।

null-কে রেফারেন্স টাইপে cast করলে null-ই পাও; ClassCastException হয় না। সেই null দিয়ে ইনস্ট্যান্স মেথড কল করলে NullPointerException হয়। কারণ আলাদা বলে ঠেকানোর পরীক্ষাও আলাদা।

Pattern ভেরিয়েবলের scope কন্ট্রোল ফ্লো অনুযায়ী ঠিক হয়। দেখানো if-এর true শাখায় lab পাও, কারণ সেখানেই মিল নিশ্চিত। শর্তের আগে বা false শাখায় পাও ধরে নিও না। জটিল উল্টো শর্তে কোন পথে কাজ যাচ্ছে দেখো।

টাইপ পরীক্ষা বাড়ানোর আগে সাধারণ চুক্তিতে কাজ রাখো

প্রতি subtype-এর জন্য instanceof লেখার চেয়ে fare() কল যোগ করা সাধারণত সহজ। সব রাইডের কাজ সাধারণ abstraction-এ রাখো। নতুন রাইড নিজের হিসাব দিলে মোট করার লুপ বদলাতে হবে না।

টাইপ পরীক্ষাও দরকার হতে পারে। room হয়তো শুধু LabPass-এর কাজ, বা বাইরে থেকে মিশ্র অবজেক্ট আসে। সমস্যাতেই পার্থক্য থাকলে পরীক্ষা করে কল করো। প্রতিটি পলিমরফিক কাজকে সব সাবক্লাসের নামের তালিকা বানিয়ে ফেলো না।

সাধারণ supertype-এর রেফারেন্স অ্যারেতে রাখা যায়। আলাদা অ্যারে টাইপ অ্যাসাইন করার সময় Java-র array covariance-এর কারণে বাড়তি রানটাইম পরীক্ষা হয়। এটি মেথড dispatch থেকে আলাদা। এই অনুশীলনে কাঙ্ক্ষিত base type দিয়েই আসল অ্যারে বানাও।

static মেথড টাইপের তথ্য দিয়ে বাছাই হয়। ফিল্ডেও নির্বাচিত ঘোষণা ব্যবহার হয়। super.method() সরাসরি প্যারেন্টের ইমপ্লিমেন্টেশন চায়। এখানে dynamic dispatch বলতে ওভাররাইড করা ইনস্ট্যান্স মেথডের পথ বোঝাচ্ছি।

null দিয়ে ওভারলোড কল খেয়াল করো

null যেকোনো রেফারেন্স প্যারামিটারের সঙ্গে মেলে। Object আর String ওভারলোড থাকলে null-এর জন্য বেশি নির্দিষ্ট String বেছে নেয়। String আর Integer থাকলে কেউ অন্যটির চেয়ে নির্দিষ্ট নয়, তাই কল ambiguous হয়। cast দিয়ে কাঙ্ক্ষিত আর্গুমেন্ট টাইপ জানাতে পারো, অবজেক্ট বানাতে হয় না। সিদ্ধান্তটি কম্পাইলের সময় হয়। null instanceof String false হওয়ার নিয়মটি আলাদা।

Object text = "hi"-তে text-এর টাইপ Object-ই। ভেতরে String আছে বলে String ওভারলোড আসে না। প্রতিটি ওভারলোড কলে আর্গুমেন্টের ঘোষিত টাইপ লিখে নাও।

ভেরিয়েবলের নাম দেখে downcast করা

নাম labPass হলেও ঘোষিত টাইপ অনুমতি দিলে সাধারণ Pass থাকতে পারে। নাম টাইপের নিশ্চয়তা দেয় না। instanceof বা স্পষ্ট টাইপের চুক্তি ব্যবহার করো।

cast-কে অবজেক্ট কপি ভাবা

cast-এ ব্যবহারের টাইপ বদলায়, পরিচয় বদলায় না। দুই রেফারেন্স দিয়েই একই অবজেক্ট বদলানো গেলে দুটোতেই ফল দেখা যায়। আলাদা কপি চাইলে কপি করার কাজ আর ভেতরের রেফারেন্স কপি করার নীতি ঠিক করো।

Java 16 থেকে type pattern স্থায়ী

Java 17-এ instanceof type pattern-এর জন্য preview flag লাগে না। পুরোনো কোডে true শাখার ভেতর আলাদা cast লেখা হয়। নিরাপদে ব্যবহারের ধারণা একই। sealed hierarchy লাগে না।

অবজেক্টের আগে চুক্তি অনুসরণ করো

ঘোষিত টাইপ অ্যাক্সেসযোগ্য signature বেছে নেয়। রানটাইম অবজেক্ট তার ওভাররাইড বেছে নেয়। Upcast-এ পরিচয় থাকে, পরীক্ষা করে downcast করলে বিশেষ কাজ নিরাপদে পাও। এবার অ্যাবস্ট্রাক্ট ক্লাসে কিছু কাজ অসম্পূর্ণ রেখেই চুক্তি লেখো।
