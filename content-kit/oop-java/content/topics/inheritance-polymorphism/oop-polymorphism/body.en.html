One request can reach different implementations

A transport program totals fares for ordinary and student rides. The loop should ask each ride for its fare without knowing every category. Polymorphism means using a common type while different objects supply their own valid behaviour.

Java supports runtime polymorphism through overridden instance methods. Overloading is often called compile-time polymorphism because the compiler selects among parameter signatures. These mechanisms cooperate, but they use different information. Keeping the two decisions separate makes output questions much easier to trace.

A reference has a declared type visible in the source. The object it reaches has a runtime class established during construction. A Fee variable can hold a LabFee object without turning that object into an ordinary Fee. The broader variable offers a narrower view of the same identity.

Use a general reference and a specific object

Fee fee = new LabFee();
int amount = fee.amount();

The assignment is an upcast: a subtype reference is used through a supertype. No explicit cast is needed. The compiler allows operations declared by Fee and its supertypes. A LabFee-only operation is unavailable through this variable unless you establish a more specific view.

A downcast requests that more specific view. It does not add fields or change the object’s class. A wrong non-null cast throws ClassCastException at runtime. Use a type test when the reference may point to different kinds of objects.

if (fee instanceof LabFee lab) {
    System.out.println(lab.room());
}

This Java 16 type pattern tests compatibility and introduces lab on the successful path. The variable has type LabFee there, so its specialist methods are available. The condition is false for null. It also accepts subclasses of LabFee rather than requiring an exact runtime class.

Resolve the signature, then the instance implementation

Start a trace by writing down the declared receiver type and the argument types. Use them to select a method signature at compile time. Only after that choice should you inspect the runtime receiver class. Runtime dispatch chooses the most specific override of the already selected instance signature.

A subclass may override one signature and inherit another. Dynamic dispatch does not jump sideways from print(Object) to print(String). It searches for an override of the chosen operation. This is why the same receiver can print two different labels in the example.

Casts preserve the original object

Suppose Pass pass holds new LabPass(12). Upcasting to Pass hides the room operation from the declared view but keeps the same object. A successful downcast recovers a LabPass view. Both references still reach the same room field and share identity.

Now suppose pass holds new Pass(). That object never had the LabPass contract. A cast cannot install the missing behaviour. The runtime check rejects the request with ClassCastException. A compiler may allow the cast because some Pass references really can hold LabPass objects.

Casting null to a reference type yields null. The cast itself does not throw ClassCastException. Calling an instance method through the resulting null reference instead raises NullPointerException. These are distinct failures with different causes and different useful guards.

Pattern variables follow flow-sensitive scope rules. In the simple if shown here, lab is available in the true branch where the match is known. Do not assume it is usable before the condition or on the false branch. More complex negated conditions need careful control-flow reasoning.

Move behaviour into the contract before adding type checks

A sum of fare() calls is usually clearer than repeated instanceof checks for each fare subtype. Put behaviour that every ride should support on the common abstraction. Then a new ride implementation can supply its calculation without changing the total loop.

Type tests still have uses. A specialist room operation may genuinely apply only to LabPass, or an external boundary may deliver mixed objects. Use a guarded test when the distinction is part of the problem. Do not turn every polymorphic operation back into a central list of subclass names.

Arrays can store references of a common supertype, making small polymorphic examples convenient. Java array covariance introduces additional runtime checks when assigning different array types. Those checks are separate from method dispatch. Keep the actual array allocation at the intended base type in these exercises.

Static methods are selected through type information rather than runtime receiver overriding. Field access also uses the selected declaration. An explicit super.method() asks for parent implementation behaviour. Reserve the term dynamic dispatch here for the overridden instance method path.

Watch overloads involving null

The null literal is compatible with reference parameter types. If overloads accept Object and String, a null argument selects String because it is more specific. If the alternatives accept unrelated types such as String and Integer, neither is more specific, so the call is ambiguous. An explicit cast can state the intended argument type without constructing an object. This choice still happens at compile time, before any matching receiver override is selected. It is separate from the false result of null instanceof String.

Keep the two type questions separate

Reading the right side for overload selection

Object text = "hi" still declares text as Object. The compiler does not switch to a String overload because the current contents happen to be a String. Write the declared argument type beside every overloaded call before tracing it.

Downcasting because the variable name sounds specific

A variable named labPass can still hold a plain Pass if its declared type allows that assignment. Names do not establish runtime compatibility. Use instanceof or a contract that makes the type guarantee explicit.

Assuming a cast copies an object

A cast changes the permitted view, not identity. If two views permit mutation of the same target, changes remain visible through both. Creating an independent copy needs an actual copying operation and a clear policy for referenced state.

Pattern matching is permanent from Java 16

Java 17 supports instanceof type patterns without preview flags. Older Java code commonly writes a type test followed by an explicit cast inside its true branch. The safety idea is the same. No sealed hierarchy is required for these patterns.

Trace the contract before the object

Declared types select accessible signatures; runtime receivers select matching instance overrides. Upcasts preserve identity, while guarded downcasts recover specialist views safely. Continue with Abstract Classes to define contracts whose implementations are intentionally incomplete.
