এক ক্লাস পরিবারের বাইরে কাজের চুক্তি দাও

ক্যাম্পাস টার্মিনাল কার্ড পড়ে, রসিদও প্রিন্ট করে। দুই কাজের জন্য একই ক্লাস প্যারেন্ট লাগবে না। ইন্টারফেস এমন চুক্তি, যা আলাদা ক্লাস ইমপ্লিমেন্ট করতে পারে। একটি ক্লাস এক প্যারেন্টকে extends করেও কয়েকটি ইন্টারফেসের চুক্তি মানতে পারে।

প্রিন্ট দরকার হলে কলার Printable-এর ওপর নির্ভর করুক। print() কীভাবে হবে তা ইমপ্লিমেন্টেশন ঠিক করে। ডিভাইস বদলালেও অনুরোধ একই থাকে। তাই কলার আর ইমপ্লিমেন্টেশনের মাঝে ইন্টারফেস কাজে আসে।

ইন্টারফেস একটি রেফারেন্স টাইপও। Printable ভেরিয়েবলে ইমপ্লিমেন্ট করা অবজেক্ট রাখতে পারো। সরাসরি ইন্টারফেস বানানো যায় না। প্রতিটি ইন্টারফেস রেফারেন্স দিয়ে দেখলেও অবজেক্টের আসল ক্লাস আর পরিচয় একই থাকে।

দরকারি public অপারেশন পূরণ করো

interface Printable {
    void print();
}
class Terminal implements Printable {
    @Override
    public void print() {
        System.out.println("Receipt ready");
    }
}

সাধারণ abstract ইন্টারফেস মেথড নিজে থেকেই public আর abstract। ঘোষণায় শব্দ দুটি বাদ দিতে পারো। ক্লাসে print অবশ্যই public করতে হবে। package-private করলে আগের অ্যাক্সেস কমে যায়। @Override দিয়ে চুক্তি ঠিকমতো পূরণ হচ্ছে কি না যাচাই করাও।

একাধিক ইন্টারফেসে কমা দাও: implements Readable, Printable। এর আগে একটি ক্লাসকে extends করা যায়। একটি ইন্টারফেস নিজেও কয়েকটি ইন্টারফেসকে extends করতে পারে। চুক্তি যোগ হয়, একাধিক ক্লাসের স্টেটের চেইন হয় না।

ইন্টারফেসের ফিল্ড নিজে থেকেই public, static আর final। এগুলো শেয়ার করা কনস্ট্যান্ট; প্রতি অবজেক্টের বদলানো স্টেট নয়। ইন্টারফেসে ইনস্ট্যান্স ফিল্ড বসানোর কনস্ট্রাক্টর নেই। দরকারি স্টেট ইমপ্লিমেন্ট করা ক্লাসে রাখো।

Readable আর Printable রেফারেন্স একই Terminal দেখাতে পারে। প্রথমটি দিয়ে read(), দ্বিতীয়টি দিয়ে print() পাও। ঘোষিত টাইপ বদলালে টার্মিনাল কপি হয় না। মেথডগুলো একই স্টেট ব্যবহার করে।

ইন্টারফেসের কলেও dynamic dispatch চলে; রানটাইমের অবজেক্ট মেথড দেয়। কলার আসল ক্লাস আন্দাজ না করে কাজের চুক্তি মানুক। নির্দিষ্ট ক্রমে কয়েকটি কল লাগলে সেই ক্রমও চুক্তিতে লেখো।

ছোট ইন্টারফেসে অপ্রয়োজনীয় কাজ চাপাতে হয় না। স্ক্যানারকে শুধু অন্য ডিভাইস প্রিন্টও করে বলে নকল print লিখতে হবে কেন? কলার আলাদাভাবে ব্যবহার করলে চুক্তি আলাদা করো। সত্যি দুই কাজ জানা অবজেক্টে একসঙ্গে ইমপ্লিমেন্ট করো।

C জানা থাকলে: ইন্টারফেস টাইপহীন ফাংশন অ্যাড্রেসের তালিকা নয়। Java প্যারামিটার, রিটার্ন আর সব কাজ পূরণ হয়েছে কি না দেখে। ঘোষিত টাইপ যতটুকু অনুমতি দেয় ততটুকুই কল করা যায়; আসল অবজেক্টের মেথড রানটাইমে বাছাই হয়।

চুক্তি, default আর দ্বন্দ্ব মেটানো দেখো

দুটি কাজের চুক্তি মানো

Terminal, Readable আর Printable দুটোই মানে। আলাদা রেফারেন্স একই অবজেক্টে আলাদা public অপারেশন ডাকে।

default আর static helper ব্যবহার করো

ExamNotice ডিফল্ট text অপারেশন ইনহেরিট করে। তারিখের helper ইন্টারফেসের নিজের, তাই Notice.valid দিয়ে কল হয়।

দুটি default-এর মধ্যে সিদ্ধান্ত দাও

Left আর Right-এর সম্পর্কহীন name default পায় Joint। নিজের ওভাররাইডে দ্বন্দ্ব মিটিয়ে ফল এক করে।

এক অপারেশনের নীতি লেখো

FeePolicy একটি হিসাবের চুক্তি দেয়, HalfFee সেটি পূরণ করে। পরে একই চুক্তিতে lambda-ও বসানো যায়।

default কাজ দেয়, ইনস্ট্যান্স স্টেট দেয় না

Default method হলো বডিসহ ইন্টারফেস ইনস্ট্যান্স মেথড। ক্লাস এটি ইনহেরিট বা ওভাররাইড করতে পারে। শেয়ার করা কাজ পাওয়া যায়; বদলানো ইনস্ট্যান্স ফিল্ড বা কনস্ট্রাক্টর আসে না।

ইনহেরিট করা উপযুক্ত ক্লাস ইমপ্লিমেন্টেশন ইন্টারফেস default-এর আগে প্রাধান্য পায়। সম্পর্কহীন দুটি ইন্টারফেস একই signature-এর default দিলে ক্লাসকে ওভাররাইড করে মেটাতে হয়। লেখার ক্রম দেখে Java বেছে নেয় না।

সমাধানের ওভাররাইডে Left.super.name() দিয়ে যোগ্য সরাসরি superinterface-এর default চাও। সাধারণ super.name() ক্লাস প্যারেন্টের জন্য। qualified ইন্টারফেস কলের বিধিনিষেধ আছে; যেকোনো আগের ইন্টারফেসের বডিতে লাফ দেওয়া যায় না।

আরও নির্দিষ্ট subinterface আগের default বদলাতে পারে। তাই একই default বারবার এলেই দ্বন্দ্ব হয় না। এখানে সমস্যা হলো সম্পর্কহীন দুই প্রার্থী, কেউ বেশি নির্দিষ্ট নয়। ক্লাসেই সিদ্ধান্ত নিয়ে কলারকে নীতিটি জানাও।

helper আর এক অপারেশনের চুক্তি আলাদা রাখো

ইন্টারফেসের static মেথড তার নিজের। ইমপ্লিমেন্ট করা ক্লাসে ইনস্ট্যান্স বা static ক্লাস মেথড হিসেবে ইনহেরিট হয় না। ExamNotice অবজেক্ট দিয়ে নয়, Notice.valid(7) দিয়ে কল করো।

Functional interface-এ Java-র নিয়ম অনুযায়ী একটি abstract মেথডের চুক্তি থাকে। default আর static মেথড abstract কাজ বাড়ায় না। @FunctionalInterface দিয়ে কম্পাইলারকে যাচাই করতে বলো। ইমপ্লিমেন্টেশনে lambda লিখতেই হবে এমন নয়।

HalfFee নামের ক্লাস FeePolicy পূরণ করে। পরে lambda একই এক-অপারেশনের ভূমিকায় ছোট করে লেখার সুযোগ দেয়। হিসাব, predicate বা callback-এর মতো লাইব্রেরির অনেক নীতিতে এই ধরন পাবে।

শুধু annotation পাওয়ার জন্য সম্পর্কহীন দুই কাজকে flag দিয়ে এক মেথডে ঢুকিও না। কলারের দরকার বোঝায় এমন চুক্তি লেখো। কাজ পরিষ্কার হলে তবেই ছোট সিনট্যাক্স উপকারী।

Object-এর সঙ্গে default-এর নিয়ম মানো

ইন্টারফেসে toString-এর মতো Object-এর ইনস্ট্যান্স মেথডের default ইমপ্লিমেন্টেশন দেওয়া যায় না। সব অবজেক্টে আগে থেকেই থাকা ক্লাসভিত্তিক Object-এর কাজের সঙ্গে বাধত। সেটি ক্লাসে লেখো। Java 9 থেকে private ইন্টারফেস মেথড দিয়ে default-গুলোর সাধারণ কোড রাখা যায়। এগুলো ভেতরের helper; ক্লাসকে পূরণ করতে হয় না, ইনস্ট্যান্স ফিল্ডও যোগ হয় না।

প্রতি মেথডের অ্যাক্সেস আর মালিকানা দেখো

ইমপ্লিমেন্টেশন package-private রাখা

ক্লাস মেথডে access modifier বাদ দিলে ইন্টারফেসের public চুক্তি মেটে না। public যোগ করো। একই সোর্স ফাইলে থাকলেও নিয়ম বদলায় না।

তালিকার ক্রমে default বাছাই হবে ভাবা

implements Left, Right লিখলে Left আগে জেতে না। সম্পর্কহীন দ্বন্দ্বে নিজে ওভাররাইড করো। তার ভেতর সরাসরি default বেছে নাও বা একসঙ্গে ব্যবহার করো।

কনস্ট্যান্টকে অবজেক্টের স্টেট ভাবা

ইন্টারফেস ফিল্ড শেয়ার করা আর final। প্রতি অবজেক্টের আলাদা বদলানো count রাখতে পারে না। স্টেট ক্লাসে রেখে ইন্টারফেসে কাজের চুক্তি দাও।

কোন ফিচার কোন Java থেকে এসেছে

default, static ইন্টারফেস মেথড আর functional interface এসেছে Java 8-এ। private helper এসেছে Java 9-এ। Java 17-এ সবই চলে। এখানকার উদাহরণে private helper বা preview feature লাগে না।

কলারের দরকারি কাজের চুক্তি দাও

ইন্টারফেসে একাধিক চুক্তি, public ইমপ্লিমেন্টেশন আর বেছে নেওয়া default থাকে। সম্পর্কিত অবজেক্টে শেয়ার করা ইনস্ট্যান্স স্টেট লাগলে অ্যাবস্ট্রাক্ট ক্লাস ভাবো। এবার final কীওয়ার্ডে অ্যাসাইনমেন্ট আর এক্সটেন্ড করা নিয়ন্ত্রণ শেখো; সেগুলোকে immutability-এর সঙ্গে গুলিয়ো না।
