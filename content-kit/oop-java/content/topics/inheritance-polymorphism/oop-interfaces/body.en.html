Describe a capability without choosing a family

A campus terminal can read a card and print a receipt. Those capabilities need not share one class parent. An interface names a contract that different classes can implement. A class can promise several interface capabilities while extending only one class.

A caller that needs printing should depend on Printable rather than a particular terminal model. The caller asks for print(), and the implementation decides how to perform it. This keeps the request stable while devices differ. Interfaces are therefore useful boundaries between consumers and implementations.

An interface is also a reference type. You can declare a Printable variable and assign an implementing object to it. You cannot directly construct the interface itself. The object still belongs to its concrete class and keeps the same identity through each interface view.

Implement the required public operations

interface Printable {
    void print();
}
class Terminal implements Printable {
    @Override
    public void print() {
        System.out.println("Receipt ready");
    }
}

An ordinary abstract interface method is implicitly public and abstract. You may omit those words in its declaration. The implementing class must make print public; package-private access would reduce the promised visibility. @Override also checks that the method actually fulfils the interface operation.

Use commas to implement multiple interfaces: implements Readable, Printable. A class may extend one superclass before that implements list. An interface may itself extend multiple interfaces. This combines contracts without creating multiple class-state inheritance.

Interface fields are implicitly public, static and final. They represent shared constants rather than mutable per-object storage. An interface has no constructor that initializes instance fields. An implementing class stores the state needed to fulfil its operations.

Several views can reach one implementation

Readable <|.. Terminal ..|> Printable
                 |
                 v
            one object
         read() and print()

Readable reference --> Terminal object <-- Printable reference

The two interface references can point to the same Terminal object. A call through Readable exposes read(), while Printable exposes print(). Changing the declared view does not copy the terminal. Its instance methods use the same underlying state.

Interface calls participate in dynamic dispatch. The runtime receiver supplies the implementing method. Consumers should depend on the operation’s documented meaning, not guess the concrete class. If several methods must be called in a particular order, that order belongs in the contract too.

Small capability contracts can avoid irrelevant operations. A document scanner should not need a fake print method merely because another device combines scanning and printing. Split capabilities when clients use them independently. Combine them in one implementation when the real object supports both.

If you know C: an interface is not a collection of untyped function addresses. Java checks parameter types, return types and implementation completeness. The reference can reach only operations permitted by its declared type, with runtime selection of the concrete receiver’s methods.

Use contracts, defaults and explicit conflict resolution

Implement two capabilities

Terminal supports Readable and Printable together. Separate references call different public operations on the same terminal.

Use a default and a static helper

ExamNotice inherits the default text operation. The date helper is called with Notice.valid because it belongs to the interface itself.

Choose between competing defaults

Joint receives unrelated name defaults from Left and Right. Its override resolves the conflict and chooses how to combine the results.

Name a one-operation policy

FeePolicy states one calculation and HalfFee implements it. This contract can also support a lambda later, without changing its meaning.

A default supplies behaviour, not instance storage

A default method is an interface instance method with a body. An implementing class can inherit that body or override it. Defaults allow a contract to provide useful shared behaviour. They do not give the interface mutable instance fields or constructors.

An inherited suitable class implementation takes precedence over an interface default. If two unrelated interfaces provide competing defaults with the same signature, the class must resolve them explicitly. Java does not choose according to declaration order.

Inside the resolving override, Left.super.name() requests an eligible direct superinterface’s default. Ordinary super.name() refers to class ancestry instead. These qualified interface calls are restricted; they are not a general mechanism for jumping to any ancestor interface body.

A more specific subinterface can refine an inherited default, so not every repeated default creates ambiguity. The critical case here is two unrelated candidate defaults with neither more specific than the other. Resolve that case locally and explain the policy to callers.

Separate helpers from single-operation contracts

A static interface method belongs to the declaring interface. It is not inherited as an instance operation or as a static class method by implementors. Call Notice.valid(7), rather than trying to call it through an ExamNotice object. This makes the helper’s ownership clear.

A functional interface has one abstract method contract under Java’s interface rules. Default and static methods do not add abstract requirements. @FunctionalInterface asks the compiler to check this property. It does not require the implementation to use lambda syntax.

HalfFee is a named class implementing the functional FeePolicy contract. A lambda later offers shorter notation for the same one-operation role. The functional-interface preview matters because many Java library policies use this shape, including computations, predicates and callbacks.

Keep a functional contract meaningful. Two unrelated operations should not be squeezed into one method with a flag merely to obtain the annotation. Prefer the interface that describes the caller’s need. Concise syntax is a benefit only after the behaviour is clear.

You can use both approaches together. An abstract report class may implement Printable and share common formatting with its children. Other unrelated printable objects need not join that report hierarchy. The interface preserves the common capability while the class preserves family-specific implementation.

Keep default behaviour compatible with Object

An interface cannot provide a default implementation of an Object instance method such as toString. That would interfere with the class-based Object behaviour every implementing object already has. Put that implementation in a class instead. Private interface methods, available since Java 9, can help share code among defaults without becoming implementation obligations. They remain internal helpers and do not introduce interface instance fields.

Check visibility and ownership of each method

Leaving an implementation package-private

An omitted access modifier on a class method does not match the interface’s public promise. Add public to the implementing method. Being declared in the same source file does not relax the overriding rule.

Assuming defaults resolve by list order

implements Left, Right does not prefer Left. An unrelated conflict needs an explicit override. Choose or combine the direct defaults inside that override rather than relying on a guessed precedence.

Treating constants as object state

An interface field is shared and final. It cannot hold a separate mutable count for each implementation instance. Put changing state in the class and expose behaviour through the interface operation.

Interface bodies have explicit release boundaries

Default methods, static interface methods and functional-interface support arrived in Java 8. Private interface helper methods arrived in Java 9. All are available on Java 17, although the examples here need no private helpers or preview features.

Promise the capability the caller needs

Interfaces support multiple contracts, public implementations and carefully chosen shared defaults. Use abstract classes when related objects also need shared instance state. Continue to The final Keyword to control assignment and extension without confusing those controls with immutability.
