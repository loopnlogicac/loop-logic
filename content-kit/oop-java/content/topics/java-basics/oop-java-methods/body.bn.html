একই হিসাব বারবার লাগলে একটা নাম দাও

ধরো, তিনটি স্ক্রিনে একই ক্রেডিটের হিসাব লাগে। প্রতিটি স্ক্রিনে হিসাব কপি করলে পরে বদলানো কঠিন হয়। একটি মেথড দিয়ে কাজের নাম, ইনপুট আর ফল নির্দিষ্ট করো। একই দায়িত্ব যেখানে দরকার, সেখান থেকে মেথডটি কল করতে পারো।

Java-র মেথড কোনো ক্লাসের অংশ। static মেথড নির্দিষ্ট ইনস্ট্যান্সের বদলে ক্লাসের সঙ্গে যুক্ত। তাই static main থেকে অবজেক্ট বানানো ছাড়াই static সহায়ক মেথড কল করা যায়। কাজ যখন অবজেক্টের স্টেটের ওপর নির্ভর করবে, তখন ইনস্ট্যান্স মেথড শিখবে।

C-এর ফাংশন জানলে প্যারামিটার আর return পরিচিত লাগবে। Java-র জরুরি নিয়ম হলো, প্রতিটি আর্গুমেন্টের মান কপি করে পাঠানো হয়। সেই মান অবজেক্ট রেফারেন্স হলেও একই নিয়ম। কপি হওয়া মান আর শেয়ার করা অবজেক্ট আলাদা করে ভাবলে একটি পরিচিত ভুল এড়াতে পারবে।

মেথডের ঘোষণা পড়ে তার প্রতিশ্রুতি বোঝো

মেথডের ঘোষণায় থাকে, কল করার সময় কী দিতে পারবে আর কী ফল পাবে। প্যারামিটার তালিকার নামগুলো ওই কলের জন্য লোকাল নাম। মেথডের রিটার্ন টাইপ void না হলে স্বাভাবিকভাবে শেষ হওয়ার প্রতিটি পথে উপযুক্ত মান return করতে হবে।

static int totalCredits(int courses, int credit) {
    return courses * credit;
}
static void showHeading() {
    System.out.println("Result");
}

staticকল গ্রহণ করার ইনস্ট্যান্স লাগে না

বডিএকটি কলের কাজ করে

কোনো এক্সপ্রেশনে totalCredits(4, 3) থাকলে কলের জায়গায় তার ফেরত দেওয়া ফল বসে। void মেথডের কল ব্যবহার করো কাজ করানোর জন্য, মান পাওয়ার জন্য নয়। void মেথড থেকে আগেই বের হতে শুধু return লিখতে পারো; পরে কোনো এক্সপ্রেশন থাকবে না।

রেফারেন্সের কপিও কিন্তু কপিই

কল করার জায়গায় যে এক্সপ্রেশন দাও, সেটা আর্গুমেন্ট। তার মান যে লোকাল ভেরিয়েবল পায়, সেটা প্যারামিটার। int আর্গুমেন্টে সংখ্যাটা কপি হয়। প্যারামিটার বদলালে কল করা কোডের int ভেরিয়েবল বদলায় না। বদলানো সংখ্যা রাখতে চাইলে return করে নিয়ে অ্যাসাইন করো।

অ্যারে আর্গুমেন্টে একটি রেফারেন্সের মান পাঠানো হয়। প্যারামিটার একই অ্যারের আরেকটি রেফারেন্স পায়। সেটার মাধ্যমে এলিমেন্ট লিখলে শেয়ার করা অ্যারে অবজেক্ট বদলায়। কিন্তু প্যারামিটারে অন্য অ্যারে অ্যাসাইন করলে শুধু প্যারামিটার ভেরিয়েবল বদলায়।

একটি কাগজ থেকে রুম নম্বর আরেকটি কাগজে কপি করার কথা ভাবো। দুই কাগজ ধরেই একই রুমে পৌঁছাতে পারো। রুমের আসবাব বদলালে সবার চোখেই সেটা বদলাবে। কিন্তু এক কাগজে অন্য রুম নম্বর লিখলে দ্বিতীয় কাগজের লেখা বদলাবে না।

এই কারণেই Java-কে pass by reference বলা ঠিক নয়। সাধারণ প্যারামিটার দিয়ে কল করা কোডের ভেরিয়েবলে সরাসরি নতুন মান অ্যাসাইন করা যায় না। একই অবজেক্ট ব্যবহার করলে তার পরিবর্তন সবাই দেখতে পারে। তবে অবজেক্ট শেয়ার করা আর একই ভেরিয়েবল শেয়ার করা আলাদা ব্যবস্থা।

ইনপুট থেকে কল শেষে ফিরে আসা পর্যন্ত অনুসরণ করো

প্রথম মেথড একটি মান হিসাব করে। পরের দুটি দিয়ে প্রিমিটিভ মান কপি আর রেফারেন্স কপির পার্থক্য দেখবে। এরপর ওভারলোডিং আর রিকার্শনে মেথডের নাম ধরে হিসাব এগোনোর দুটি আলাদা ধরন দেখবে।

বারবার ব্যবহার করা যায় এমন ক্রেডিটের হিসাব

দুটি int আর্গুমেন্ট প্যারামিটারে কপি হয়। return দিয়ে 12 কল করা কোডে ফিরে যায়।

প্রিমিটিভ আর্গুমেন্টের মান কপি হয়

raise নিজের লোকাল মান 65 করে। কল করা কোডে মান তখনও 60।

অ্যারের মান বদলানো আর নতুন অ্যারে অ্যাসাইন করা

কপি হওয়া রেফারেন্স প্রথমে মূল অ্যারের 60-কে 70 করে। প্যারামিটারে নতুন মান অ্যাসাইন করে কল করা কোডের রেফারেন্স বদলানো যায় না।

একই নামের দুটি ওভারলোড

int আর্গুমেন্টে int ওভারলোড বাছা হয়, আউটপুট 6। double আর্গুমেন্টে double ওভারলোড বাছা হয়, আউটপুট 7.0।

রিকার্শন দিয়ে ফ্যাক্টরিয়াল

প্রতিটি কলে n কমতে কমতে 1 হয়। কলগুলো থেকে ফেরার সময় 2, 3, 4 আর 5 গুণ হয়ে 120 পাও।

ওভারলোডিং আর নিজের মেথডকে কল করা

ওভারলোডিং মানে প্যারামিটার তালিকা আলাদা রেখে একই নামে একাধিক মেথড ঘোষণা করা। আর্গুমেন্টের টাইপ দেখে কম্পাইলার উপযুক্ত ঘোষণা বেছে নেয়। int আর্গুমেন্ট int ওভারলোড-এর সঙ্গে মেলাতে পারে, আর double আর্গুমেন্ট double ওভারলোড-এর সঙ্গে। শুধু রিটার্ন টাইপ বদলে ওভারলোড আলাদা করা যায় না।

সম্পর্কিত কাজের জন্য ওভারলোডিং ব্যবহার সহজ করতে পারে। তবে সম্পর্কহীন কাজে আলাদা নাম দাও। maximum-এর সব ওভারলোড সর্বোচ্চ মান খুঁজবে, পাঠক এমনটাই আশা করবে। শুধু নামটা সুবিধার বলে আলাদা কাজ এক নামে রেখো না।

রিকার্শন মানে একটি মেথড নিজেকেই কল করে। প্রতিটি কলের নিজের প্যারামিটার আর লোকাল ভেরিয়েবল থাকে। base case হলো এমন ছোট সমস্যা, যার উত্তর দিতে আর নিজের মেথডকে কল লাগে না। recursive case-এ সমস্যাকে সেই base case-এর দিকে ছোট করতে হবে।

ফ্যাক্টরিয়ালে factorial(1) ফেরত দেয় 1। factorial(2) ওই ফলের জন্য অপেক্ষা করে, তারপর 2 দিয়ে গুণ করে। অপেক্ষায় থাকা পরের কলগুলো 3, 4 আর 5 দিয়ে গুণ করে। সব কল একই n ব্যবহার করে না। প্রতিটি কলে নিজস্ব n থাকে।

পরে আবার শুরু করার অপেক্ষায় থাকা কাজ কল স্ট্যাকে জমে। রিকার্শন বেশি গভীর হলে সেই জায়গা শেষ হয়ে StackOverflowError হতে পারে। Java tail-call optimisation-এর নিশ্চয়তা দেয় না। তাই বড় ইনপুটে লুপ বেশি নিরাপদ হতে পারে। সমস্যার গঠন পরিষ্কারভাবে মেলে আর গভীরতার সীমা জানা থাকলে রিকার্শন বেছে নাও।

ফ্যাক্টরিয়ালের সংখ্যারও সীমা আছে। long দিয়ে 20 পর্যন্ত ফ্যাক্টরিয়াল রাখা যায়, তার পরের সবগুলো নয়। base case ঠিক থাকলেই হিসাবের overflow আটকায় না। ইনপুটের বৈধ সীমা বলো। কলের গভীরতা আর সংখ্যার বৃদ্ধি দুটোই ভাবো।

ফেরত দেওয়া ফল আর অবজেক্ট বদলানো আলাদা করো

ফেরত আসা প্রিমিটিভ মান ফেলে দেওয়া

মেথড বাড়ানো নম্বর return করলেই মূল ভেরিয়েবল নিজে থেকে বদলায় না। কল করা কোডে ফল রাখতে চাইলে অ্যাসাইন করো। প্রিমিটিভ হিসাবের জন্য ফল return করার পরিষ্কার ডিজাইন প্রায়ই বোঝা সহজ করে।

কল করা কোডের অ্যারে বদলে দিতে চাওয়া

অ্যারে প্যারামিটারে নতুন রেফারেন্স দিলে কল করা কোডের রেফারেন্স ঘুরে যায় না। নতুন অ্যারে বসাতে চাইলে সেটা return করো। এলিমেন্ট বদলানো আর বাইরের ভেরিয়েবল বদলানোর জন্য আলাদা ধরনের ব্যবহারপথ লাগে।

রিকার্শনে ছোট সমস্যার দিকে না যাওয়া

কলগুলো base case-এর দিকে না গেলে base case রেখেও লাভ নেই। অঙ্কের যোগফলে অঋণাত্মক সংখ্যাকে দশ দিয়ে ভাগ করলে একটি অঙ্ক বাদ যায়। থামা যাচাই করতে শূন্য আর একাধিক অঙ্কের সংখ্যা দুটোই হাতে অনুসরণ করো।

মেথডের ভিত্তির নিয়ম একই থাকে

static সহায়ক মেথড, ওভারলোডিং আর রিকার্শন Java-র পুরোনো সুবিধা। এই পাতায় Java 17-এর পরের কিছু লাগছে না। পরে অবজেক্টের স্টেট বদলানো যায় এমন ইনস্ট্যান্স মেথডেও আর্গুমেন্ট কপি হওয়ার একই নিয়ম চলবে।

কাজের নাম দাও, কপি হওয়া মান অনুসরণ করো

ভালো মেথডের কাজ স্পষ্ট, ফলও বোঝা সহজ। প্যারামিটারের মান আর সেটা যে অবজেক্টকে দেখায়, দুটো আলাদা করে অনুসরণ করো। এবার উদাহরণে ব্যবহৃত অ্যারে অবজেক্টগুলো Java-র অ্যারে পাঠে শেখো।
