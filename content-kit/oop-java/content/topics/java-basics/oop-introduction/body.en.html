Think in terms of things and responsibilities

Imagine a library desk handling several loans. Each loan has a book, a borrower and a return date. You also need actions such as renew and return. Keeping these facts and actions together gives you a useful picture of object-oriented programming, or OOP.

An object is a particular thing represented inside a running program. Its state is the information it currently holds. Its behaviour is the work you can ask it to do. A loan changes state when a book is returned, but it remains the same loan.

If you know C, you already know how functions divide work into steps. OOP offers another way to organise that work. It does not replace conditions, loops or careful algorithms. Instead, it helps you decide which part of a larger program should own each rule.

From a procedure to a responsible object

A procedural marks program might keep an array of marks and pass it to several functions. One function reads marks, another changes them, and another prints a report. This can be an excellent design when the task is small and the data flow is clear.

As the program grows, several screens may update a result. If every screen writes the mark directly, each screen must remember the range rule. One missed check can store 140 as a mark. The difficulty is keeping the rule consistent wherever the state changes.

An object design puts a result and its update operation together. A Result object holds one mark. Its changeMark operation decides whether a proposed value is allowed. A display routine asks for the saved mark rather than changing storage behind the object's back.

The difference is about responsibility, not punctuation. A program containing many classes can still have confused ownership. Conversely, a short procedural solution may be clearer than an elaborate hierarchy. Ask where a rule belongs and which data it needs before deciding to introduce a class.

Classes, instances and the four pillars

A class describes the fields and operations that its objects will have. Think of a library form with named spaces. The form design is like a class; two completed forms represent two separate loans. An instance is an object created from that class.

loan A: book 12, roll 17, due 20
loan B: book 12, roll 24, due 25

The two loans can mention the same book code at different times. They still have separate identities and histories. Identity answers which particular object you mean. State answers what that object's values are now. Matching some fields does not automatically make two objects identical.

OOP is often explained through four pillars. Learn the problem each pillar addresses before memorising the name. These ideas connect, but they do different jobs.

PillarPlain meaningExample
EncapsulationKeep data and its rules togetherwithdraw checks the balance

PolymorphismUse one operation with different implementationsDifferent payment types implement pay

Encapsulation prevents uncontrolled changes to important state. Abstraction lets you use a useful operation without learning every internal step. A caller can ask whether a loan is overdue without knowing how dates are stored. These two ideas often help even when the program has no inheritance.

Inheritance describes an is-a relationship between related types. It should express a sound model rather than provide a shortcut for copying code. Polymorphism allows a request through a common type to reach behaviour appropriate to the actual object. Later lessons show the method calls and output traces behind this picture.

Now model a course registration. A Student holds a roll and credit limit. A Course holds a code and capacity. A Registration connects them and records enrollment state. Rejecting a repeated enrollment belongs near that connection, while changing course capacity belongs with the course.

This separation makes a later change easier to locate. If the credit limit changes, you should not need to inspect every report printer. The goal is to reduce the number of places that must agree about one rule.

Why use Java here?

Java makes classes and declared types central to ordinary programs. The compiler checks whether a method exists and whether arguments have suitable types. You receive useful feedback before the program runs. That makes object relationships visible while you are learning to design them.

Java also manages object memory through garbage collection. An object that can no longer be reached becomes eligible for reclamation. You do not call C's free on each object. This removes one memory-management task, although you must still think carefully about sharing and resource use.

Java is not purely made of objects. It also has primitive values such as int and boolean. A class can combine primitive state with references to other objects. You will learn that distinction before using object relationships in larger designs.

Avoid empty design slogans

Calling every noun a class

A noun is only a starting clue. A course title may be a String field rather than a separate class. Give a class a clear responsibility and meaningful rules. More boxes in a diagram do not automatically create a better design.

Confusing abstraction with secrecy

Abstraction presents the useful part of an idea. It is not about hiding information for its own sake. A small, clear operation helps callers understand what they may do while leaving storage choices inside the class.

Assuming OOP guarantees speed

OOP structures a solution. Its performance still depends on data structures, algorithms and implementation choices. First choose a correct model, then measure important costs when the application requires it.
