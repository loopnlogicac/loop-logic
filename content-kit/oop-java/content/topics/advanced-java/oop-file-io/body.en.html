Give data a life beyond one run

An in-memory marks list disappears when the program ends. A text file can preserve those marks for another run or another tool. File input and output converts between bytes stored at a filesystem location and values your application can use.

Text I/O needs three decisions: where the file is, how bytes represent characters, and what each line means. A correct read operation can still produce incorrect application data if the encoding or record format is wrong. Make all three choices explicit.

Files also fail for reasons outside the program’s control. A path may be missing, permissions may deny access, or storage may fill while writing. Use the exception-handling rules to distinguish a failed operation from a successful empty file.

If you know C

A Java reader manages characters rather than exposing a FILE pointer. You still own the lifetime of an open resource. Try-with-resources replaces many manual close paths, while a charset controls conversion between stored bytes and Java text.

Combine a path, charset and operation

Path path = Path.of("marks.txt");
String text = Files.readString(path, StandardCharsets.UTF_8);
Files.writeString(path, text, StandardCharsets.UTF_8);

Path describes a location; it does not open or create the file by itself. Files provides operations on that location. StandardCharsets.UTF_8 names a fixed encoding, avoiding dependence on a machine’s default charset. Use the same encoding when writing and reading a defined text format.

A relative path is resolved against the process working directory. That directory can differ between an IDE and a terminal launch. It is not automatically the folder containing the source file. Accept a deliberate path argument or document the launch directory for a real application.

The default writeString and newBufferedWriter behavior creates a missing file or truncates an existing file. Truncation removes previous contents. Appending requires explicit open options, such as CREATE and APPEND, and a format that makes appended records unambiguous.

Open, use, close and interpret

Path + UTF-8 bytes -- reader --> String lines -- parse --> marks
marks -- format --> String lines -- writer --> UTF-8 bytes at Path

A BufferedReader fetches characters in chunks and offers readLine. Each returned line excludes its line terminator. A real blank line produces an empty String. End of file produces null. Mixing those two cases can stop reading too soon or try to parse data that is not present.

A BufferedWriter collects small writes before passing them to the underlying destination. newLine writes the platform line separator. flush passes buffered characters onward, while close also releases the resource. A reader opened before buffered output is flushed may not see the latest text.

Close the writer before reopening its file for reading. Nested try-with-resources blocks make this order visible. If the body throws, closing still occurs during ordinary exception propagation. Cleanup can also fail, so preserve causes and suppressed exceptions when diagnosing I/O problems.

Reading and parsing are separate operations. IOException describes I/O failure. NumberFormatException describes a token that does not fit the numeric conversion rule. A valid integer can still violate a mark range. Handle each at the layer that owns that rule.

Define what one record means

A file format is a contract between a writer and a later reader. If one mark appears per line, state whether blank lines are allowed, whether spaces are trimmed and which numeric range is valid. Without that contract, a reader cannot decide whether to skip or reject an unexpected line.

Delimited records need escaping rules when fields can contain the delimiter or a newline. A small project can forbid those characters explicitly. A larger application should choose a well-defined format or implement matching escape and unescape operations. Splitting on a delimiter without considering the data is not a general parser.

Preserve trailing empty fields when they matter. String.split takes a regular expression, and its default behavior discards trailing empty results. A negative limit retains them. Validate the expected field count before indexing the resulting array.

String length is measured in UTF-16 code units. UTF-8 file byte length is a different quantity. Do not use a character count to assume a file’s byte size, especially for Bangla text. The same explicit UTF-8 policy handles both ASCII and Bangla content.

Protect live data during an import

Suppose an importer reads ninety valid marks and fails on the next line. If it already cleared and replaced the current list, the application may now expose partial state. Decide whether partial acceptance is intended. For an all-or-nothing import, build and validate a temporary collection first.

Only after the entire read succeeds should the application replace its current collection. This commit point is a design decision, independent of whether resources closed correctly. Closing a reader does not undo earlier mutations.

Saving has a related risk. Opening the destination for overwrite can erase old contents before all new data is written. Writing a sibling staging file and moving it into place can reduce exposure to partial writes. A normal move is not automatically crash-safe or atomic across all filesystems.

An exists check cannot guarantee that the following open will succeed. Another process may change the path or permissions between the check and operation. Attempt the real operation and handle its exception. Prechecks can improve a user message, but they are not a substitute for handling failure.

Choose whole-file or incremental reading

readString is convenient for a small configuration or message. It loads the complete text into memory. A BufferedReader loop is better when you can process records incrementally or the file may be large. Keeping every parsed record still requires memory for those records.

Files.lines returns a lazy stream backed by an open file. Its concise appearance does not remove the closing obligation. Use it in try-with-resources and remember that failures can occur while traversing, not only while creating the stream.

Passing an open reader into a helper also raises ownership questions. A helper should not unexpectedly close a reader that its caller still needs. State who opens and closes each resource. In these complete examples, the code that opens the resource also closes it.

Keep data absence distinct from failure

Using an empty line as EOF

An empty line is still data. Test for null to detect EOF, then apply the format’s blank-line policy. Calling trim before a null check would dereference null at the end.

Ignoring a failed save

A success message must follow successful completion and close. If writing or closing throws, report a failed save. Silent recovery can make a user believe data is durable when it is not.

Assuming an extension defines the encoding

A .txt suffix does not tell Java which charset was used. Specify and document the actual format. If you read a file written by another tool, confirm its encoding rather than guessing from the filename.

Make file boundaries explicit

  • State the charset and per-record grammar together.
  • Finish buffered writes before consuming their output.
  • Stage imports before changing live collections.
  • Use temporary paths for demonstrations that create their own data.
  • Keep diagnostic path information separate from a stable user-facing message.

Text APIs used by Java 17

Files.readString and writeString arrived in Java 11. The buffered reader and writer factories are available in the Java 17 baseline. These examples explicitly select UTF-8 and need no platform-default encoding assumption. They use no object serialization.
