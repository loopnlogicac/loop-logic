একবার চলার পরেও ডেটা রাখো

প্রোগ্রাম শেষ হলে মেমরির নম্বরের তালিকা হারায়। টেক্সট ফাইলে রাখলে পরের বার বা অন্য টুলে ব্যবহার করা যায়। ফাইল ইনপুট-আউটপুট ফাইলসিস্টেমের কোনো জায়গার বাইট আর অ্যাপের ব্যবহারযোগ্য মানের মধ্যে রূপ বদলায়।

টেক্সটে তিনটি সিদ্ধান্ত লাগে: ফাইল কোথায়, বাইট দিয়ে অক্ষর কীভাবে লেখা, আর প্রতি লাইনের অর্থ কী। পড়া সফল হলেও encoding বা record format ভুল হলে ডেটা ভুল হয়। তিনটিই স্পষ্ট করো।

ফাইল না থাকা, অনুমতি না পাওয়া বা লেখার সময় স্টোরেজ ভরে যাওয়ার মতো বাইরের কারণেও ব্যর্থতা হয়। এক্সেপশনের নিয়মে ব্যর্থ কাজ আর সফলভাবে পড়া খালি ফাইল আলাদা করো।

C জানা থাকলে

Java reader FILE pointer প্রকাশ না করে অক্ষর সামলায়। খোলা রিসোর্সের lifetime-এর দায়িত্ব তবু তোমার। try-with-resources অনেক manual close সামলায়। charset ঠিক করে বাইট আর Java টেক্সটের মধ্যে রূপ বদলানো।

path, charset আর কাজ একসঙ্গে দাও

Path path = Path.of("marks.txt");
String text = Files.readString(path, StandardCharsets.UTF_8);
Files.writeString(path, text, StandardCharsets.UTF_8);

Path জায়গা বোঝায়; নিজে ফাইল খোলে বা বানায় না। Files সেখানে অপারেশন দেয়। StandardCharsets.UTF_8 নির্দিষ্ট encoding নেয়; মেশিনের default-এর ওপর নির্ভর করে না। নির্দিষ্ট format পড়া আর লেখায় একই encoding রাখো।

relative path প্রক্রিয়ার working directory ধরে মেলে। IDE আর টার্মিনালে তা আলাদা হতে পারে। সোর্স ফাইলের ফোল্ডার নিজে থেকে নয়। অ্যাপে স্পষ্ট path argument নাও বা চালানোর ফোল্ডার বলো।

ডিফল্ট writeString আর newBufferedWriter ফাইল না থাকলে বানায়, থাকলে truncate করে, অর্থাৎ আগের লেখা মুছে দেয়। শেষে যোগ করতে CREATE আর APPEND-এর মতো explicit option লাগে। নতুন record কোথায় শুরু তা বোঝার format-ও চাই।

খোলো, ব্যবহার করো, বন্ধ করো, অর্থ বের করো

Path + UTF-8 bytes -- reader --> String lines -- parse --> marks
marks -- format --> String lines -- writer --> UTF-8 bytes at Path

BufferedReader একসঙ্গে কিছু অক্ষর আনে, readLine দেয়। ফলের লাইনে line terminator থাকে না। সত্যিকারের ফাঁকা লাইনে খালি String, ফাইল শেষে null। গুলিয়ে ফেললে আগে থেমে যেতে বা না থাকা ডেটা parse করতে পারো।

BufferedWriter ছোট লেখাগুলো জমিয়ে নিচে পাঠায়। newLine প্ল্যাটফর্মের line separator দেয়। flush buffer-এর অক্ষর এগিয়ে পাঠায়; close রিসোর্সও ছাড়ে। flush-এর আগে reader খুললে নতুন লেখা নাও দেখতে পারে।

একই ফাইল পড়ার আগে writer বন্ধ করো। আলাদা try-with-resources block-এ ক্রম পরিষ্কার থাকে। বডি throw করলেও স্বাভাবিক propagation-এ close চলে। cleanup-ও ব্যর্থ হতে পারে; ডায়াগনস্টিকে cause আর suppressed exception রাখো।

পড়া আর parse আলাদা। IOException I/O ব্যর্থতা, NumberFormatException সংখ্যায় বদলানোর অযোগ্য token বোঝায়। সঠিক পূর্ণসংখ্যাও নম্বরের সীমা ভাঙতে পারে। যে স্তরের নিয়ম, সেখানেই সামলাও।

নিজের ফাইলের আগে স্বয়ংসম্পূর্ণ উদাহরণ চালাও

ছোট টেক্সট লিখে ফেরত পড়ো

প্রথম প্রোগ্রাম নিজের temporary file বানিয়ে দুই নম্বরের লাইন লেখে, পড়ে প্রিন্ট করে। বদলাতে থাকা temporary নাম প্রিন্ট করে না। finally ফাইল মুছে দেয়, তাই বারবার চালালে জমে না।

buffer দিয়ে পড়ো আর লেখো

writer আলাদা লাইনে CSE 80 আর MAT 75 রাখে। সেটি বন্ধ হলে reader খোলে। লুপ readLine-এর null পরীক্ষা করে, তাই প্রতিটি সত্যিকারের লাইন একবার প্রিন্ট হয়। প্রতি লাইনে record এলে এই ধরন কাজে আসে।

না থাকা path সামলাও

নতুন temporary directory-তে absent.txt নেই তা নিশ্চিত। নির্দিষ্ট catch স্থির মেসেজ দেয়, তারপর মেনু চালানোর লাইন আসে। প্ল্যাটফর্মভেদে বদলানো এক্সেপশন লেখা না দেখিয়েও ব্যর্থতা আর খালি সফল রিড আলাদা থাকে।

এক record-এর অর্থ ঠিক করো

format লেখক আর পরের পাঠকের চুক্তি। প্রতি লাইনে নম্বর হলে ফাঁকা লাইন চলে কি না, space trim হয় কি না, সীমা কত বলো। নইলে অপ্রত্যাশিত লাইন বাদ দেবে না পুরো পড়া বাতিল করবে তা জানা যায় না।

field-এ delimiter বা newline থাকতে পারলে escaping-এর নিয়ম লাগে। ছোট প্রজেক্টে সেগুলো স্পষ্ট নিষেধ করতে পারো। বড় অ্যাপে নির্দিষ্ট format বা মেলা escape-unescape অপারেশন নাও। ডেটা না ভেবে delimiter-এ split করলেই সাধারণ parser হয় না।

শেষের খালি field দরকার হলে রাখো। String.split regular expression নেয়; ডিফল্টে শেষে খালি ফল বাদ দেয়। negative limit দিলে থাকে। অ্যারের index পড়ার আগে field count যাচাই করো।

String length UTF-16 code unit গোনে। UTF-8 ফাইলের byte length আলাদা। বিশেষ করে বাংলায় অক্ষর গুনে বাইটের আকার ধরো না। একই explicit UTF-8 নীতিতে ASCII আর বাংলা দুটোই চলে।

import-এ চলতি ডেটা রক্ষা করো

নব্বইটি সঠিক নম্বরের পরে পরের লাইনে ব্যর্থ হলে কী হবে? আগে চলতি list মুছে বসাতে থাকলে অর্ধেক স্টেট দেখা যাবে। আংশিক নেওয়া ইচ্ছাকৃত কি না ঠিক করো। সব একসঙ্গে নিতে আগে অস্থায়ী collection বানিয়ে যাচাই করো।

পুরো পড়া সফল হলেই চলতি collection বদলাও। এই commit point ডিজাইনের সিদ্ধান্ত; রিসোর্স ঠিকমতো বন্ধ হয়েছে কি না তা থেকে আলাদা। reader বন্ধ আগের mutation ফিরিয়ে দেয় না।

save-এও overwrite-এর জন্য খুললেই নতুন লেখা শেষের আগে পুরোনো ডেটা মুছে যেতে পারে। পাশের staging file-এ লিখে শেষে move করলে ঝুঁকি কমে। সাধারণ move সব filesystem-এ atomic বা crash-safe এমন নয়।

exists পরীক্ষা পরের open সফল হওয়ার নিশ্চয়তা নয়। মাঝখানে অন্য process path বা permission বদলাতে পারে। আসল অপারেশন করো, এক্সেপশন সামলাও। আগের পরীক্ষা ভালো মেসেজ দিতে পারে, ব্যর্থতা সামলানোর বিকল্প নয়।

পুরো ফাইল না ধাপে ধাপে পড়বে বাছো

ছোট configuration বা মেসেজে readString সুবিধার; পুরো টেক্সট মেমরিতে আনে। বড় ফাইল বা লাইন ধরে কাজের জন্য BufferedReader ভালো। সব parsed record জমালে অবশ্য সেগুলোর মেমরি লাগবেই।

Files.lines খোলা ফাইলের ওপর lazy stream দেয়। ছোট লেখা হলেও বন্ধ করতে হবে। try-with-resources নাও। শুধু বানানোর সময় নয়, traversal-এর সময়ও ব্যর্থতা আসতে পারে।

helper-এ খোলা reader দিলে কে বন্ধ করবে বলো। কলারের এখনও দরকার এমন reader helper হঠাৎ বন্ধ করবে না। এই পূর্ণ উদাহরণে যে খোলে সে-ই বন্ধ করে।

ডেটা না থাকা আর ব্যর্থতা আলাদা রাখো

ফাঁকা লাইনকে EOF ধরা

ফাঁকা লাইনও ডেটা। null দিয়ে EOF ধরো, তারপর format-এর ফাঁকা লাইনের নিয়ম লাগাও। null পরীক্ষার আগে trim করলে শেষে null dereference হবে।

save ব্যর্থতা উপেক্ষা

কাজ আর close সফল হওয়ার পরেই সফলতার মেসেজ। লেখা বা বন্ধে throw হলে failed save জানাও। চুপ থাকলে ব্যবহারকারী ডেটা স্থায়ী হয়েছে ভাবতে পারে।

extension থেকে encoding ধরা

.txt Java-কে charset বলে না। আসল format লিখে দাও। অন্য টুলের ফাইল পড়লে নাম দেখে আন্দাজ না করে encoding নিশ্চিত করো।

ফাইলের সীমার চুক্তি স্পষ্ট করো

  • charset আর প্রতি record-এর grammar একসঙ্গে বলো।
  • buffer-এর লেখা শেষ করে তারপর পড়ো।
  • চলতি collection বদলানোর আগে import stage করো।
  • নিজের ডেটা বানানো উদাহরণে temporary path নাও।
  • ডায়াগনস্টিক path আর ব্যবহারকারীর স্থির মেসেজ আলাদা রাখো।

Java 17-এর টেক্সট API

Files.readString আর writeString Java 11 থেকে। buffered reader-writer factory Java 17-এ আছে। এখানে UTF-8 স্পষ্ট দেওয়া, platform default ধরা হয়নি। object serialization নেই।

ফাইল খোলা সফল হলেই কাজ শেষ নয়

path, encoding, record-এর নিয়ম আর cleanup-এর দায়িত্ব ঠিক করো। পড়া বা parse ব্যর্থ হলেও বৈধ স্টেট রাখো। এবার মাল্টিথ্রেডিংয়ে আলাদাভাবে চলা কাজ সমন্বয় করো।
