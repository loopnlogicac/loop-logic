ব্যর্থতার জন্য আলাদা পথ রাখো

নম্বর লিখতে গিয়ে সংখ্যার বদলে absent লিখলে পরের শিক্ষার্থীর কাজ থেমে থাকা উচিত নয়। এক্সেপশন হলো ব্যর্থতা বোঝানো অবজেক্ট, যা চলতি স্টেটমেন্টের ক্রম থামায়। যেখানে পরের সিদ্ধান্ত নেওয়া যায়, সেখানে ব্যর্থতা সামলাও।

নম্বর বদলানোর মেথড জানে না আবার চাইবে, শিক্ষার্থী বাদ দেবে, না import বন্ধ করবে। সে ব্যর্থতা জানায়। কলার পরের নীতি ঠিক করে। ফলে সাধারণ হিসাব পরিষ্কার থাকে, প্রত্যাখ্যানও চোখে পড়ে।

false ফেরানো সাধারণ মেথডের পথেই ফেরে। এক্সেপশন বাইরে বাইরে মেলা handler খোঁজে। ব্যর্থ কাজের বাকি স্টেটমেন্ট চলে না। তখনও অবজেক্টের নিয়ম ঠিক রাখতে হবে।

C জানা থাকলে

C ফাংশনে প্রায়ই status code ফেরে, কলারকে পরীক্ষা করতে হয়। Java-র checked exception কিছু ব্যর্থতা সামলানো বা বাইরে পাঠানোর সিদ্ধান্ত কম্পাইলের সময় বাধ্যতামূলক করে। ডেটা যাচাই আর ব্যবহারকারীকে কারণ জানানো তবু দরকার।

চেষ্টা, সামলানো আর cleanup আলাদা করো

try {
    int mark = Integer.parseInt(text);
    accept(mark);
} catch (NumberFormatException failure) {
    showInputMessage();
} finally {
    finishAttempt();
}

try-তে ব্যর্থ হতে পারে এমন কাজ থাকে। catch প্যারামিটার মেলা এক্সেপশন অবজেক্ট পায়। স্বাভাবিকভাবে বা এক্সেপশনে বেরোনোর সময়ের কাজ finally-তে রাখো। এখানে helper-এর নাম ভূমিকা বোঝায়; লাইব্রেরির মেথড নয়।

লেখার ধরনকাজ
throw new InvalidMarkException(...)এখনই নির্দিষ্ট ব্যর্থতা জানানো
throws InvalidMarkExceptionমেথড checked ব্যর্থতা বাইরে পাঠাতে পারে বলা
catch (InvalidMarkException failure)এই টাইপ বা subtype সামলানো
try (Resource resource = ...)নিজে থেকে বন্ধ করার ব্যবস্থা

throws নিজে কিছু ছোড়ে না; মেথডের সীমার চুক্তি দেয়। throw স্বাভাবিক পথ থামিয়ে এক্সেপশন বাইরে পাঠানো শুরু করে।

ব্যর্থতা থেকে handler পর্যন্ত যাও

সবচেয়ে ভেতরের সক্রিয় try থেকে শুরু করো। Java লেখার ক্রমে catch দেখে। না মিললে মেথড ছেড়ে কলারের দিকে খোঁজে। স্বাভাবিক এই unwinding-এ মাঝের finally ব্লকগুলো চলে।

main calls importMark
  importMark calls parseInt
    parseInt raises NumberFormatException
  importMark has no matching catch
main catch reports the invalid token
main continues with the next request

catch-এ subtype-ও মেলে। NumberFormatException একটি RuntimeException, তাই তার catch-এও মেলে। নির্দিষ্ট টাইপ আগে রাখো। প্যারেন্ট catch-এর পরে চাইল্ড catch পৌঁছানো যায় না বলে কম্পাইল হয় না।

Throwable-এর নিচে Error আর Exception আলাদা। RuntimeException আর Error পরিবারের টাইপ unchecked। অন্য exception checked: কলারকে catch বা throws দিতে হয়। IOException পরিচিত উদাহরণ। নিজের ক্লাস Exception থেকে এলে checked, RuntimeException থেকে এলে unchecked।

Unchecked মানে ক্ষতিহীন নয়; কম্পাইলারের নিয়ম বোঝায়। ভুল আর্গুমেন্ট, null অ্যাক্সেস আর হিসাবের ব্যর্থতাতেও ভালো চুক্তি লাগে। সব Error ধরতে যেয়ো না; সেরে ওঠার মতো রিসোর্স বা সঠিক স্টেট নাও থাকতে পারে।

সেরে ওঠা আর রিসোর্সের দায়িত্ব দেখো

ভুল নম্বরের পরেও এগিয়ে যাও

absent থেকে নম্বর বানানো ব্যর্থ হয়। ইনপুটের মেসেজ, চেষ্টার cleanup, তারপর পরের শিক্ষার্থীর মেসেজ আসে। catch ব্যর্থ লাইনে ফিরে যায় না। আবার চেষ্টা করতে আলাদা লুপ লাগবে।

ডোমেইনের ব্যর্থতা লেখো

InvalidMarkException অ্যাপের নম্বরের নিয়ম বোঝায়। নেওয়ার আগে 0..100 যাচাই হয়। checked ঘোষণা কলারকে সিদ্ধান্ত নিতে বাধ্য করে। Exception থেকে আসা serialization-এর জন্য serialVersionUID সংস্করণ দেয়; এখানে serialization করা হয় না।

নেওয়ার উল্টো ক্রমে বন্ধ করো

দুই Desk ব্যবহার করে কাজ ব্যর্থ হয়। আগে B, পরে A বন্ধ হয়। তারপর বাইরের catch কাজের ব্যর্থতা প্রিন্ট করে। AutoCloseable সবার সাধারণ close অপারেশন দেয়।

দুটি ব্যর্থতার তথ্য রাখো

কাজে আর বন্ধ করার সময় দুবার ব্যর্থ হতে পারে। try-with-resources কাজের ব্যর্থতাকে প্রধান রাখে; close-এরটি suppressed তালিকায় যোগ করে। শুধু প্রধান মেসেজ দেখলে দরকারি তথ্য বাদ পড়ে।

কোথায় সেরে উঠবে ঠিক করো

কনসোল আবার নম্বর চাইতে পারে; importer পুরো ফাইল বাদ দিতে পারে। চুপচাপ অর্ধেক import করা বন্ধ করার চেয়েও খারাপ হতে পারে। সব একসঙ্গে বদলানোর চুক্তি থাকলে আগে অস্থায়ী স্টেটে যাচাই করো।

Scanner.nextInt ভুল টোকেন রেখে দিলে বারবার কলেও একই ব্যর্থতা হয়। আগে টোকেন পড়ে parseInt করলে এগোনোর পথ পরিষ্কার। অনুশীলনে সংখ্যা নয় এমন লেখা আর সীমার বাইরের পূর্ণসংখ্যা আলাদা করা হয়েছে।

বাস্তব প্রতিক্রিয়ার জন্য ছোট catch রাখো। পুরো অ্যাপ ধরে কিছু না বলা প্রোগ্রামিং ভুল লুকায়। এই স্তর সামলাতে না পারলে বাইরে পাঠাও বা আসল cause রেখে অর্থপূর্ণ এক্সেপশনে মোড়াও। আসল ব্যর্থতা ফেলে অপ্রাসঙ্গিক সাধারণ মেসেজ দিও না।

স্টেট অ্যাসাইনের আগে শর্ত দেখো। প্রত্যাখ্যাত withdrawal-এ balance আগের মতো থাকবে। টাকা কাটার পরে throw করলে catch ঠিক হলেও স্টেট ভাঙে। এক্সেপশন আর এনক্যাপসুলেশন একই নিয়ম রক্ষা করে।

সফলতার মতো প্রত্যাখ্যানও অনুসরণ করো

balance শূন্য, চাওয়া টাকা এক হলে কাটার আগেই পরীক্ষা ব্যর্থ। FundsException কলারে যায়, DENIED প্রিন্ট হয়; balance শূন্য থাকে। শূন্য থেকে শূন্য চাইলে পরীক্ষা সফল, ফল শূন্য, এক্সেপশন নেই।

এখানে checked exception ডোমেইনের প্রত্যাখ্যান স্বীকার করতে বলে। সব প্রত্যাখ্যানে এক্সেপশন লাগবে এমন নয়। API পরিষ্কার হলে boolean বা result object-ও ব্যবহার করা যায়।

মেসেজের সঙ্গে টাইপ আর cause দেখো। ব্যবহারকারীর মেসেজ স্থির আর বোঝার মতো হোক। ডায়াগনস্টিকে টেকনিক্যাল প্রসঙ্গ রাখো। ছোট মেসেজ করতে আসল এক্সেপশন ফেলো না। suppressed cleanup ব্যর্থতাও কারণ বুঝতে সাহায্য করে।

cleanup যেন ফল ঢেকে না দেয়

finally থেকে return

finally-এর return আগের return বা এক্সেপশন বদলে দিতে পারে। finally-তে cleanup রাখো, মূল কাজকে ফল ঠিক করতে দাও। closeable রিসোর্সে স্বয়ংক্রিয় ব্যবস্থাপনা নাও।

সব বন্ধ হওয়ায় finally চলবে ভাবা

সাধারণ return আর exception unwinding-এ finally চলে। জোর করে প্রক্রিয়া বন্ধ, JVM crash বা JVM exit-এ বাদ যেতে পারে। সব shutdown-এ নিশ্চয়তা বোলো না।

সামলানোকে সফলতা ভাবা

ভুল প্রিন্ট মানে কাজ শেষ নয়। নথিবদ্ধ ব্যর্থ ফল দাও, বুঝে আবার চেষ্টা করো বা অনুরোধ বন্ধ করো। সব Exception ধরে বাইরে সফলতার মেসেজ দিও না।

ব্যর্থতার পথ পরীক্ষা করার মতো রাখো

  • ভাঙা ডোমেইন নিয়ম অনুযায়ী এক্সেপশনের নাম দাও।
  • এক স্তর থেকে অন্য স্তরে বদলালে cause রাখো।
  • নিজের দায়িত্বের রিসোর্সে try-with-resources নাও।
  • স্টেট দেখার সময় সফল আর প্রত্যাখ্যাত পরিবর্তন দুটোই পরীক্ষা করো।

Java 17-এ রিসোর্স সামলানো

try-with-resources Java 7 থেকে আছে। Java 9 থেকে আগে থাকা final বা effectively final ভেরিয়েবলও header-এ চলে। এখানে header-এ ঘোষণা আছে, preview লাগে না। catch-এর ক্রম আর checked propagation-এর নিয়ম Java 17-এও চলে।

স্টেট ঠিক রেখে ব্যর্থতা সামলাও

এক্সেপশন মেথডের সীমা পেরিয়ে ব্যর্থতা জানায়। প্রতিক্রিয়া দিতে পারলে catch করো, আসল cause রাখো, রিসোর্সের lifetime স্পষ্ট করো। এবার জেনেরিকসে চলার আগেই কিছু ভুল আটকাও।
