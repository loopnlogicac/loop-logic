Recover where you can make a decision

When a student types a mark, the text may be wrong. A network connection may also fail while you save it. An exception is an object describing a problem that interrupts the normal path. You can handle that problem where enough information exists to choose another action. You should not hide it and pretend the operation succeeded.

Imagine a library clerk accepting a return. A damaged barcode needs a different response from an overdue book. Java lets you distinguish failures by type. A catch block can deal with one problem while an unrelated problem continues to its caller. This keeps the normal operation readable without losing the reason for failure.

If you know C

If you know C, you have probably checked return codes after a function call. Java still uses ordinary results for expected choices. Exceptions add a separate path for failures that prevent a method from fulfilling its promise. Start with the input and resource examples here before handling every possible failure in a larger application.

Separate protected work, recovery and cleanup

A try block encloses work that may fail. A catch parameter receives a matching exception object. The first compatible catch runs. Place specific exception types before broader types; otherwise the broad handler would make the specific one unreachable. A finally block performs cleanup when control leaves try or catch normally, through return, or through an exception.

The keyword throw actually raises one exception object. The declaration throws lists exception types a method may pass to its caller. A declaration does not create an exception or recover from one. Its purpose is to describe part of the method contract. Choose a message that states the failed condition without revealing private information.

try {
    int mark = Integer.parseInt(text);
    saveMark(mark);
} catch (NumberFormatException problem) {
    System.out.println("Enter a whole number");
} finally {
    System.out.println("Attempt finished");
}

Follow the first matching handler

Suppose parsing the text fails. Java stops evaluating the statements in try at that point. It does not call saveMark. It looks for a compatible catch in the current method, then in calling methods if necessary. This search is called stack unwinding. Local primitive values disappear with abandoned calls, but resource cleanup still needs an explicit policy.

If parsing succeeds and saveMark throws another exception, the NumberFormatException handler does not match it. The exception continues outward after finally runs. If every operation succeeds, catch is skipped and finally still runs. Use a small trace to distinguish these three paths before reading a nested example.

The exception hierarchy starts with Throwable. Most application handlers catch a suitable Exception subtype. Error represents serious conditions such as exhausted memory and is normally outside routine recovery. Avoid catch(Throwable): it can swallow failures your method cannot repair. Uncaught exceptions usually terminate that thread and print a diagnostic stack trace.

Know what the compiler requires

A checked exception is an Exception subtype outside RuntimeException and its descendants. IOException is a familiar example. A method must catch a checked exception or declare it. The compiler checks the possibility from declarations; it does not predict whether a disk will fail during this particular run.

Unchecked exceptions include RuntimeException and Error families. IllegalArgumentException describes an unacceptable argument; NumberFormatException is one subtype. You may catch unchecked exceptions when recovery is meaningful. Their unchecked status does not mean that they are harmless, nor that throwing them is always a good interface design.

Use a custom exception when callers need a distinct domain decision. InvalidMarkException can carry the rejected value or a clear message. Extending Exception makes it checked; extending RuntimeException makes it unchecked. Choose deliberately. An exception class is serializable through its parent, so these examples declare serialVersionUID to make that inherited contract explicit.

A custom checked exception fits a service whose caller can request another mark. A programming invariant broken deep inside a model often deserves an unchecked exception instead. Do not create a new type solely to rename an existing precise exception. Catching the precise standard type often makes the caller easier to understand.

Close resources even when an operation fails

A resource is something you acquire and must release, such as an open reader. Garbage collection manages ordinary object memory. It does not promise timely closure of file handles. A try-with-resources statement closes objects implementing AutoCloseable when its body exits. Resources close in the reverse order of their declarations.

If the body throws and close also throws, Java keeps the body exception as the main failure. The close failure becomes a suppressed exception available from getSuppressed(). If only close fails, its exception is the main one. This preserves the original reason for failure while retaining cleanup evidence.

Do not put a return in finally. It can replace a result or hide an exception that was already travelling outward. Finally also is not a guarantee against process termination or machine failure. Use it for predictable control flow inside the running JVM, and prefer try-with-resources for resources with an appropriate close method.

Decide whether retry can preserve state

A retry is useful only when the failed operation can safely be attempted again. Parsing another token is usually harmless. Repeating a payment after an uncertain network response may charge twice. Before offering retry, identify which side effects have already happened and whether the operation has an identity that prevents duplication.

Recover without losing the original cause

An empty catch block silently converts failure into apparent success. A later method may then use data that was never loaded. Either recover with a valid alternative, show a useful error, or propagate the failure. Printing a message and continuing is correct only if the remaining state still satisfies its rules.

Catching Exception around an entire menu hides which operation failed. Narrow the try block to parsing or saving, then choose a handler for that operation. Do not catch NullPointerException as routine validation. Check an optional reference deliberately, and repair unexpected null values at their source.

When translating a low-level failure into a domain exception, keep the cause with a constructor accepting Throwable. That lets a maintainer find the original IOException later. Avoid exposing an entire stack trace to a student using the application. Give the user a useful action and keep technical diagnostics at an appropriate boundary.

Use stable exception features in Java 17

Try-with-resources arrived in Java 7. Java 9 allowed an existing final or effectively final resource variable in its header. These examples create resources directly in the header and need no newer syntax. Multi-catch uses a vertical bar between unrelated exception types when their recovery code is identical.

InterruptedException needs special care in threaded code. If a method cannot propagate interruption, restoring the interrupt flag is usually appropriate. The thread lesson explains that cooperation. Here, checked declarations describe possible failure without claiming that every declaration must throw during every invocation.

Choose a meaningful recovery boundary

Exception handling keeps the normal path clear while preserving failure details. Match narrow types, validate domain rules, and close acquired resources automatically.
