Choose the shape of your data

A marks sheet needs positions, a room register needs unique names, and a result lookup needs roll-to-mark pairs. These are different jobs. The collections framework supplies reusable interfaces and implementations for storing groups of objects. Your choice should follow the questions the application asks most often.

List, Set and Map describe different promises. A List models a sequence. A Set models membership without duplicates. A Map connects keys to values. Map belongs to its own interface hierarchy; it is not a subtype of Collection, although its keys, values and entries have collection views.

You already know arrays. Collections add operations such as growing, removing and looking up values without requiring you to resize storage manually. They also introduce contracts about ordering, equality and mutation. A useful declaration makes those contracts visible to the reader.

Program to the needed interface

List<Integer> marks = new ArrayList<>();
Set<String> rooms = new HashSet<>();
Map<Integer, String> names = new HashMap<>();

The left side names the operations callers need. The right side chooses a representation. Use explicit imports for the types you use. A List variable can accept either ArrayList or LinkedList, but their performance characteristics differ.

Generic element types keep mixed values from entering by mistake. Integer is used rather than primitive int because collection type arguments must be reference types. Iterating with int unboxes each Integer, so null entries would cause trouble. Decide whether null belongs in your domain before choosing an implementation.

Compare operation costs and ordering rules

ImplementationUseful propertyCost or limitation
ArrayListO(1) indexed access; amortized O(1) appendMiddle insertions and removals shift elements, O(n)
LinkedListO(1) operations at either endIndexed access traverses links, O(n)
HashSet / HashMapExpected O(1) basic lookup with suitable hashesNo sorted or insertion iteration order guarantee
TreeSet / TreeMapSorted iteration and navigational operationsO(log n) basic lookup, insertion and removal

ArrayList stores references in a resizable backing array. Some appends must grow that array, so a single append can cost O(n). Amortized constant time describes a sequence of appends, distributing growth costs across them. It is not a promise that every append takes identical time.

LinkedList links nodes. Removing through an already positioned iterator can avoid a search, but locating an arbitrary index still takes traversal. Repeated get(i) calls in a loop can therefore turn a simple-looking linked-list traversal into quadratic work. Use an iterator or enhanced for loop instead.

Hash collections use hashCode to find candidate locations and equals to distinguish keys. Equal values must have equal hashes. Sorted collections use comparison, and comparison returning zero defines a duplicate key or element there. Keep ordering consistent with equals when you can.

Separate storage from presentation order

Keep duplicate marks and remove deliberately

The list begins as 60, 70, 60. Removing index one deletes 70. Appending 80 gives [60, 60, 80]. A later boxed removal deletes the first equal 60. This difference is an overload decision, so the argument type matters.

Report unique rooms in sorted order

Adding Lab a second time returns false. HashSet itself does not promise whether Hall or Lab appears first. Constructing a TreeSet for the display makes the output order explicit. The original membership set remains separate from this reporting choice.

Count each course code

A map stores one count per course. merge inserts one for an absent code or combines one with its current count. Integer::sum names the addition method. The example copies entries into a TreeMap before printing, so CSE reliably comes before MAT.

Treat LinkedList as a deque

A deque supports adding or removing at either end. The urgent entry goes to the front, ahead of A and B. Removing from the front until empty prints their processing order. No index search is needed for these end operations.

Traverse through the right view

Enhanced for is clear when you need every element without changing the structure. For a map report, entrySet exposes each key and value together. Iterating keys and looking up every value is legal, but the entry view states your intent more directly.

An Iterator supports a controlled traversal and, when implemented, removal of the last returned element. Call next before remove and follow its state rules. Calling list.remove directly during an ordinary for-each loop can invalidate traversal and raise ConcurrentModificationException.

For a filtering operation on a mutable collection, removeIf often expresses the goal better. Its predicate says which values to discard. Not every collection supports removal; an unmodifiable list rejects structural changes. Understand the collection’s mutation contract before applying a convenient method.

Fail-fast iterators are debugging aids with best-effort detection. They are not locks and do not make shared mutation safe. Multithreaded code needs an explicit concurrency policy. The later thread lesson explains why ordinary unsynchronized collections cannot be treated as shared counters or queues without care.

Plan for empty data and changing keys

An empty list has size zero, so get(0) fails. An empty report may print no rows, while an application menu may choose an explicit EMPTY message. Define this behavior in the surrounding operation instead of assuming that every collection contains at least one value.

Map.get returning null can mean an absent key or a present null value when the implementation permits nulls. containsKey distinguishes them. getOrDefault supplies a fallback but does not insert it. A map key is unique: put with an existing equal key replaces the associated value.

A mutable key can become impossible to find through ordinary lookup if its hash or equality fields change after insertion. The entry still exists in storage, but lookup may search somewhere else. Prefer immutable IDs, remove before changing identity fields, or redesign the key.

Revisit one reporting requirement

Suppose rolls arrive as 7, 2, 7, 1 and 2. A list preserves all five entries. A set stores three distinct values. A TreeSet additionally reports them as 1, 2 and 7. The requested output therefore determines both duplicate handling and ordering, before performance becomes the deciding factor.

Avoid convenient but misleading assumptions

Depending on hash order

One observed run of a HashMap is not an ordering contract. Another data set or JVM may reveal a different order. Use TreeMap for sorted keys or LinkedHashMap when insertion order is the requirement.

Assuming every List is mutable

List.of creates an unmodifiable list and rejects null elements. Arrays.asList has a fixed-size array-backed structure. new ArrayList makes a separately resizable list. These factories share an interface but deliberately offer different mutation policies.

Choosing a tree without an ordering contract

TreeSet and TreeMap need comparable keys or a supplied comparator. A comparison that uses only marks can collapse different students with tied marks. Include a suitable tie-breaker when their identities must remain distinct.

State the reason for your collection

  • Choose list positions, set membership or map association before selecting a class.
  • Use a stable ID for map keys.
  • Sort reports deliberately instead of depending on incidental iteration.
  • Document duplicate and empty-input behavior at the application boundary.

Collection factories and Java 17

List.of, Set.of and Map.of arrived in Java 9. These examples run on Java 17. They use ordinary generics and avoid later sequenced-collection APIs. The following ordering lesson briefly uses records, a feature finalized in Java 16, as small data holders.
