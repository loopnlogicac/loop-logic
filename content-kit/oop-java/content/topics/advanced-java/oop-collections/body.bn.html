ডেটার কাজ দেখে কাঠামো বেছে নাও

নম্বরের তালিকায় অবস্থান দরকার, রুমের রেজিস্টারে অনন্য নাম, আর ফল খুঁজতে রোলের সঙ্গে নম্বরের জোড়া। Collections framework অবজেক্টের দল রাখার ইন্টারফেস আর ইমপ্লিমেন্টেশন দেয়। অ্যাপকে কোন প্রশ্ন বেশি করতে হয় দেখে বাছো।

List ক্রম রাখে। Set ডুপ্লিকেট ছাড়া সদস্য রাখে। Map key-কে value-এর সঙ্গে যুক্ত করে। Map আলাদা ইন্টারফেস hierarchy-তে, Collection-এর subtype নয়। তবে key, value আর entry-এর collection view পাওয়া যায়।

অ্যারের সঙ্গে পরিচয় হয়েছে। কালেকশনে নিজে স্টোরেজ বড় না করে যোগ, বাদ আর খোঁজার কাজ পাও। সঙ্গে ক্রম, সমতা আর বদলানোর চুক্তিও আসে। ঘোষণায় সেই চুক্তি পরিষ্কার রাখো।

দরকারি ইন্টারফেস দিয়ে কাজ করো

List<Integer> marks = new ArrayList<>();
Set<String> rooms = new HashSet<>();
Map<Integer, String> names = new HashMap<>();

বামে কলারের দরকারি অপারেশন, ডানে স্টোরেজের ইমপ্লিমেন্টেশন। ব্যবহৃত টাইপের স্পষ্ট import দাও। List-এ ArrayList বা LinkedList রাখা যায়, কিন্তু পারফরম্যান্স আলাদা।

জেনেরিক টাইপ ভুল করে মিশ্র মান ঢোকানো আটকায়। আর্গুমেন্ট রেফারেন্স টাইপ বলে int-এর বদলে Integer লাগে। int দিয়ে লুপে পড়লে unbox হয়; null থাকলে সমস্যা হবে। ডোমেইনে null চলে কি না আগে ঠিক করো।

কাজের খরচ আর ক্রমের নিয়ম তুলনা করো

ইমপ্লিমেন্টেশনকাজের বৈশিষ্ট্যখরচ বা সীমা
ArrayListindex-এ O(1) অ্যাক্সেস; শেষে যোগে amortized O(1)মাঝে যোগ বা বাদে এলিমেন্ট সরাতে O(n)
LinkedListদুই প্রান্তে O(1) কাজindex-এ যেতে লিংক ধরে O(n)
HashSet / HashMapউপযুক্ত hash-এ সাধারণ খোঁজে expected O(1)সাজানো বা যোগ করার ক্রমে traversal-এর নিশ্চয়তা নেই
TreeSet / TreeMapসাজানো traversal, কাছের মান খোঁজার অপারেশনসাধারণ খোঁজ, যোগ আর বাদে O(log n)

ArrayList বড় করা যায় এমন ভেতরের অ্যারেতে রেফারেন্স রাখে। কোনো append-এ অ্যারে বাড়াতে O(n) লাগে। অনেক append-এর মোট খরচ ভাগ করলে গড়ে স্থির সময় হয়; একে amortized বলে। প্রতিটি append একই সময় নেবে এমন নয়।

LinkedList নোডের লিংক রাখে। ঠিক অবস্থানে থাকা iterator দিয়ে বাদ দিলে খোঁজা লাগে না। index খুঁজতে তবু হাঁটতে হয়। লুপে বারবার get(i) করলে মোট কাজ quadratic হতে পারে। iterator বা enhanced for নাও।

Hash কালেকশন সম্ভাব্য জায়গা পেতে hashCode, key আলাদা করতে equals ব্যবহার করে। সমান মানের hash সমান চাই। সাজানো কালেকশনে comparison শূন্য হলে একই key বা এলিমেন্ট ধরা হয়। সম্ভব হলে ordering আর equals মেলাও।

স্টোরেজ আর রিপোর্টের ক্রম আলাদা রাখো

ডুপ্লিকেট নম্বর রাখো, বুঝে বাদ দাও

60, 70, 60 তালিকার index এক বাদ দিলে 70 যায়। 80 যোগে [60, 60, 80] হয়। পরে boxed মান দিয়ে বাদ দিলে প্রথম সমান 60 যায়। ওভারলোড বাছাইয়ে আর্গুমেন্টের টাইপ জরুরি।

অনন্য রুম সাজিয়ে দেখাও

দ্বিতীয়বার Lab যোগে false ফেরে। HashSet-এ Hall না Lab আগে আসবে তার চুক্তি নেই। দেখানোর জন্য TreeSet বানালে ক্রম নির্দিষ্ট হয়। মূল membership set আলাদা থাকে।

কোর্স কোড গুনে রাখো

Map-এ প্রতি কোর্সে একটি count। merge না থাকলে এক বসায়, থাকলে আগের সঙ্গে এক যোগ করে। Integer::sum যোগের মেথড বোঝায়। প্রিন্টের আগে TreeMap-এ নিলে CSE নিশ্চিতভাবে MAT-এর আগে আসে।

LinkedList-কে deque হিসেবে নাও

Deque-তে দুই প্রান্তে যোগ বা বাদ চলে। জরুরি কাজ সামনে যায়, A আর B-এর আগে। সামনে থেকে খালি হওয়া পর্যন্ত নিলে কাজের ক্রম প্রিন্ট হয়। index খোঁজা লাগে না।

ঠিক view দিয়ে ঘুরে দেখো

কাঠামো না বদলে সব এলিমেন্ট চাইলে enhanced for পরিষ্কার। Map রিপোর্টে entrySet একসঙ্গে key আর value দেয়। key ঘুরে আলাদা lookup করা চলে, তবে entry view উদ্দেশ্য স্পষ্ট করে।

Iterator নিয়ন্ত্রিতভাবে ঘোরে; সমর্থন থাকলে শেষে ফেরানো এলিমেন্ট বাদ দেয়। remove-এর আগে next কল করো, স্টেটের নিয়ম মানো। সাধারণ for-each চলার সময় সরাসরি list.remove করলে traversal ভেঙে ConcurrentModificationException হতে পারে।

mutable collection থেকে শর্তমতো বাদ দিতে removeIf সহজ। predicate কোন মান বাদ যাবে বলে। সব collection removal সমর্থন করে না; unmodifiable list পরিবর্তন নেয় না। আগে mutation-এর চুক্তি বোঝো।

Fail-fast iterator যতটা পারে ভুল শনাক্ত করে; এটি debugging-এর সাহায্য, lock নয়। শেয়ার করা পরিবর্তন নিরাপদ করে না। একাধিক থ্রেডে স্পষ্ট নীতি লাগে। থ্রেডের পাঠে সাধারণ unsynchronized collection শেয়ার করার সমস্যা দেখবে।

খালি ডেটা আর বদলানো key ভাবো

খালি list-এর size শূন্য, তাই get(0) ব্যর্থ। রিপোর্টে কোনো লাইন নাও আসতে পারে; মেনুতে EMPTY দেখাতে পারো। বাইরের অপারেশনে নিয়ম ঠিক করো। সবসময় মান আছে ধরে নিও না।

null অনুমতি দিলে Map.get-এর null মানে key নেই বা তার মান null। containsKey পার্থক্য করে। getOrDefault বিকল্প ফেরায়, সেটি insert করে না। সমান পুরোনো key-তে put করলে মান বদলে যায়।

রাখার পরে key-এর hash বা সমতার ফিল্ড বদলালে lookup-এ আর নাও পাও। entry স্টোরেজে থাকে, কিন্তু খোঁজ অন্য জায়গায় যায়। immutable ID নাও, বদলানোর আগে সরাও বা key নতুন করে ভাবো।

একটি রিপোর্টের চাহিদা আবার দেখো

রোল 7, 2, 7, 1, 2 এলে List পাঁচটিই রাখে। Set তিনটি আলাদা মান রাখে। TreeSet সেগুলো 1, 2, 7 ক্রমে দেয়। পারফরম্যান্সের আগেই চাওয়া আউটপুট ডুপ্লিকেট আর ক্রমের সিদ্ধান্ত দেয়।

সহজ কিন্তু ভুল ধারণা এড়াও

hash-এর ক্রমে ভরসা

একবারের HashMap আউটপুট ক্রমের চুক্তি নয়। ডেটা বা JVM বদলালে ক্রম বদলাতে পারে। সাজানো key-তে TreeMap, যোগ করার ক্রমে LinkedHashMap নাও।

সব List বদলানো যায় ভাবা

List.of unmodifiable আর null নেয় না। Arrays.asList অ্যারেভিত্তিক fixed-size list। new ArrayList আলাদাভাবে বড় করা যায়। একই ইন্টারফেস হলেও নীতি আলাদা।

ordering না ভেবে tree নেওয়া

TreeSet আর TreeMap-এ Comparable key বা Comparator লাগে। শুধু নম্বর তুললে সমান নম্বরের আলাদা শিক্ষার্থী এক হয়ে যেতে পারে। পরিচয় আলাদা রাখতে tie-breaker যোগ করো।

কালেকশন বেছে নেওয়ার কারণ বলো

  • আগে List-এর অবস্থান, Set-এর সদস্য, না Map-এর সম্পর্ক দরকার ঠিক করো।
  • Map key-তে স্থির ID নাও।
  • ঘটনাচক্রের ক্রম না ধরে রিপোর্ট বুঝে সাজাও।
  • ডুপ্লিকেট আর খালি ইনপুটের আচরণ নথিবদ্ধ করো।

Java 17-এ collection factory

List.of, Set.of, Map.of Java 9-এ এসেছে। এখানে Java 17-এর সাধারণ জেনেরিকস আছে, পরের sequenced-collection API নেই। পরের ordering পাঠে ছোট ডেটা রাখতে Java 16 থেকে স্থায়ী record ব্যবহার হয়েছে।

কাজের সঙ্গে স্টোরেজ মেলাও

ক্রমে List, অনন্য মানে Set, key দিয়ে খোঁজায় Map নাও। ক্রম, সমতা আর পরিবর্তনের নিয়ম দেখো। এবার Comparable আর Comparator দিয়ে নির্দিষ্ট ordering লেখো।
