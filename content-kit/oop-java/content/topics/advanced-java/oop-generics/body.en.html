Reuse a shape while preserving its type

A box can hold a room name or a seat count. You want one box implementation, yet a room name should still behave as a String. Generics let a class or method use a type parameter that its caller supplies. The compiler then follows that type through the operations.

Without generics, a box might return Object. Every caller would need a cast before using String methods. A mistaken cast might compile and fail only during execution. Box<String> moves the element promise into the declaration so incompatible uses are rejected earlier.

A type parameter is a relationship, not a request to accept anything everywhere. If one method accepts T and returns T, its result follows the type selected for that call. A different invocation may select a different reference type without rewriting the method.

If you know C

A void pointer can carry different address values, but it does not preserve the original type relationship for callers. Java generics add source-level checking around such relationships. They do not require manual memory allocation or a separate generated class for every element type.

Declare a class parameter or a method parameter

class Box<T> {
    private final T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
}
static <T> T first(List<T> values) {
    return values.get(0);
}

The class parameter T is available in its instance fields, constructor and instance methods. The method parameter belongs to that method invocation. Place a method’s type parameter before its return type, even when the method is static. A static member cannot use the enclosing class’s T as though every instance shared one element type.

The diamond in new Box<>(...) asks the compiler to infer suitable arguments from the surrounding context. Inference still performs checks; it is not a switch to dynamic typing. Use clear declarations when a more elaborate inferred type would make the code hard to understand.

Type arguments are reference types. Box<int> is illegal, while Box<Integer> can hold boxed integer values. Null remains possible unless the class validates against it. Generics by themselves do not promise non-null values.

Follow one parameter through its uses

For Box<String>, the constructor accepts a String and get returns a String to source callers. For Box<Integer>, those positions use Integer. Mixing these boxes cannot silently turn a String into an Integer. The compiler checks each declared relationship.

A bound states the minimum capability a parameter must have. T extends Number makes Number methods available inside the generic code. The word extends is also used when the bound is an interface. A bound can combine a class and interfaces with an ampersand, with the class bound first.

Bounded code can use only the promised operations. Number exposes doubleValue but not a general plus operator for arbitrary T values. Convert to a chosen arithmetic representation and explain its limits. A double total can round large integers or decimal values; it is not an exact financial sum.

The larger method uses T extends Comparable<? super T>. A T can then be compared through an ordering that accepts T or one of its supertypes. This handles more useful types than requiring only Comparable<T>, while still keeping the comparison safe.

Read types through complete calls

Typed boxes remove caller casts

The name box yields a String with length three. The seats box yields an Integer, which is unboxed before adding two. The resulting lines are 3 and 32. No cast is needed to recover either source-level type.

A Number bound supports numeric reads

The total method accepts lists whose element types extend Number. Integer and Double calls choose different type arguments, but both use doubleValue internally. The totals are 5.0 and 4.0. The bound grants an operation rather than a particular stored numeric representation.

Copy from a narrow source to a wider destination

Integers can be stored in a Number list. The copy method expresses that direction using two wildcards tied to T. It reads each element safely and appends it without changing its object type or order.

Return one of two comparable arguments

The bounded larger method works with both String and Integer. It returns an existing argument, retaining T instead of returning Object. A comparison result of zero selects the left argument by the method’s documented choice.

Unknown types need different read and write rules

List<Integer> is not a subtype of List<Number>. If that assignment were permitted, a caller could add a Double through the Number reference. The original Integer list would then contain a value that violates its declaration. Generic types are ordinarily invariant in their arguments.

List<? extends Number> means a list of some unknown type at or below Number. Reading an element as Number is safe. Adding an arbitrary Integer is unsafe because the real list might be List<Double>. The only generally safe new reference value to add through that view is null, when the collection allows it.

List<? super Integer> means the element type is Integer or a supertype. Adding an Integer is safe. Reading an element gives only Object without further information, because the actual list might also hold unrelated Object values. This is why the useful reminder is producer extends, consumer super.

These restrictions describe operations through the declared view. They do not make the underlying list immutable. Another reference may still permit mutation. If a method needs to read and replace T values, a named type parameter may express its relationship better than unrelated wildcards.

Understand what remains at runtime

Type erasure translates type parameters into their bounds, often Object, while the compiler inserts necessary casts and bridge methods. Box<String> and Box<Integer> do not become two separately specialized JVM classes. The source checks are still valuable even though type arguments are not generally available as runtime tags.

Erasure explains several restrictions. You cannot overload only on List<String> versus List<Integer>, because the signatures erase to the same List parameter. You cannot write new T() without a supplied construction strategy. You also cannot test instanceof List<String>; List<?> is suitable when you need to test only the runtime list shape.

Arrays remember their component class at runtime, unlike most parameterized types. Generic array creation such as new T[10] is therefore unavailable. Prefer a typed collection rather than forcing an unchecked array cast. Mixing raw collections with parameterized code can undermine the compiler’s guarantees and create heap pollution.

Choose between a named parameter and a wildcard

Suppose a helper only prints the size of a list. List<?> is enough because it never needs an element-specific operation. A method that returns the last element should use <T> T last(List<T> values), preserving the input-to-result relationship. Returning Object would throw away useful information that the caller already has.

Now consider exchanging two positions inside one list. A helper with a named T can read a T and write it back safely. Two unrelated wildcard lists do not prove that their unknown element types match. This distinction is about relationships, rather than a rule that wildcards are always more flexible or always less useful.

Check the empty case before implementing last. The exercise requires at least one element, so size minus one is valid. A general-purpose API should either reject empty input with a documented exception or return a representation of absence. Generics do not decide that behavior. They describe the result type only when a result exists.

A useful declaration should help a caller predict operations without reading the method body. Prefer that clarity over the shortest possible arrangement of angle brackets.

Keep the type promise intact

Using raw types to silence a difficult declaration

A raw Box discards useful checks. It can lead to unchecked warnings and later ClassCastException. Fix the parameter relationship rather than suppressing the warning. A short explicit type argument is easier to maintain than an unexplained cast.

Expecting bounds to construct values

T extends SomeClass does not promise a no-argument constructor. If code must make T objects, pass a factory such as Supplier<T>. Keep that creation dependency explicit.

Confusing wildcard views with ownership

An extends wildcard limits writes through one reference. It does not copy the collection, transfer ownership or freeze its contents. Return a defensive copy or a documented unmodifiable view when representation protection is the actual goal.

Describe relationships with the smallest useful promise

  • Use familiar T, E and K/V names for short generic roles.
  • Choose bounds that expose only operations the method actually needs.
  • Prefer wildcards at flexible input boundaries and concrete return types for callers.
  • State whether empty inputs and null values are accepted.

Generics on Java 17

Generics arrived in Java 5 and diamond inference in Java 7. Java 17 retains erasure and invariant generic arguments. These examples need no unchecked conversions. The Java language does not provide primitive type arguments or automatic specialization for Box<Integer>.
