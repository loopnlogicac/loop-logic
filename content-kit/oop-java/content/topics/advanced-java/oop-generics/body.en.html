Give containers a type promise

A library shelf labelled Books should not accept an unrelated payment receipt. A generic type gives a Java container a similar promise. With Box<String>, you can store text and read it as String. You no longer need a cast at every retrieval. The compiler checks the promise before the program runs.

Generics reuse one implementation for many reference types. Box<Integer> and Box<String> share the same class definition, but their callers see different element types. This is useful for lists, pairs, repositories and small utility methods. It removes repeated code while keeping mistakes near the place where they are made.

If you know C

If you know C, this is different from putting void pointers into a container and remembering the real type yourself. Java checks generic uses statically. Generics do not add pointer arithmetic or manual memory release. They describe relationships among types, while references still identify objects managed by the JVM.

Read type parameters as placeholders

A type parameter appears in angle brackets after a class name. T is a conventional short name, not a keyword. Inside that declaration, T can describe fields, parameters and results. At a use site, replace it with a reference type. Primitive int cannot be a type argument; use Integer, with boxing when needed.

A generic method declares its own type parameters before the return type. A static method cannot use the enclosing class's T without declaring an independent parameter. This restriction makes sense because one static member belongs to the class rather than a particular Box<String> instance.

The diamond <> lets the compiler infer constructor type arguments from context. Inference does not mean that a container can change its declared type later. After assigning new Box<>() to Box<String>, adding an Integer remains illegal. Write a meaningful bound when your implementation needs operations beyond Object methods.

class Box<T> {
    private T value;
    void set(T value) { this.value = value; }
    T get() { return value; }
}
// A generic method has its own parameter:
static <T> T first(java.util.List<T> items) {
    return items.get(0);
}

Separate declared type from object identity

Suppose you create Box<String>, store CSE, and call get(). The compiler knows that the returned value is String. It can allow length() without a visible cast. Storing a numeric value is rejected at the call, rather than becoming an unexpected ClassCastException much later.

Generic classes are invariant. List<Integer> is not a subtype of List<Number>, even though Integer extends Number. If that assignment were allowed, a caller could add a Double through the Number view. The original Integer list would then contain an incompatible element. Java prevents that contradiction.

You can still assign an ArrayList<Integer> to List<Integer>. The inheritance relationship between the container classes is preserved when the argument matches. Do not confuse this ordinary interface substitution with changing the element argument. Draw the two dimensions separately: the container implementation and the element type.

A bound such as T extends Number lets a method call doubleValue(). The word extends is also used for interface bounds. Multiple bounds use an ampersand; a class bound, when present, comes first. Bounds describe available operations. They do not make arithmetic operators work on arbitrary T values.

Accept producers and consumers without unsafe casts

A wildcard describes an unknown argument. List<? extends Number> accepts a list whose element type is Number or some subtype. Reading an element gives at least Number. Adding an Integer is unsafe because the actual list might be List<Double>. Apart from null, you cannot add a chosen Number value through that view.

List<? super Integer> accepts Integer lists and suitable supertype lists, such as Number or Object lists. Adding an Integer is safe for each possibility. Reading through that view gives only Object, because an Object list may contain text as well. The lower bound protects writes without promising a narrow read type.

The memory aid is producer extends, consumer super. Ask which direction values travel through the parameter. A source produces values you read. A destination consumes values you add. A method that copies integers can therefore accept an extends source and a super destination. The actual list objects are unchanged; only the allowed view differs.

List<?> is useful when you only need size, iteration as Object, or clearing. It is not List<Object>. A List<Object> allows adding arbitrary objects; an unknown list does not. Choose a type parameter rather than a wildcard when two positions must have the same unknown type, such as a result tied to an input.

Understand what survives at runtime

Java implements most generics through type erasure. The compiler replaces unbounded type parameters with Object, or with their first bound, and inserts necessary casts. It also checks your uses before erasure. This preserves compatibility with older bytecode, while source code retains a strong generic contract.

Box<String> and Box<Integer> do not become different runtime classes. Their getClass results identify the same Box class. Consequently, instanceof List<String> is not legal: the JVM cannot verify each element argument that way. instanceof List<?> can check the raw container family without making an element-type promise.

Erasure also explains why new T() and new T[10] are not allowed. A constructor call or array allocation needs a runtime type that the parameter does not provide. Supply a factory when construction is required, or use a suitable List<T>. Do not replace the problem with unchecked casts and then suppress the warning.

Two overloads taking List<String> and List<Integer> have the same erased parameter type. They cannot coexist with the same method name and remaining signature. Use different operation names or a meaningful additional parameter. A raw List loses generic checking and can pollute otherwise typed code, so avoid it even when old examples use it.

Connect two arguments with one parameter

Consider a method that returns one element from a supplied list. A declaration using List<?> can read only Object, losing the relationship to the caller's element type. A generic method <T> T first(List<T> values) preserves that relationship. It also needs a nonempty-input contract, because generic safety does not prevent index errors.

Now consider copying Number values into a destination. A signature with one T, an extends source and a super target connects both positions. The compiler finds a T compatible with the source and destination. Two unrelated unbounded wildcards would not express the same connection, even though both look flexible at first.

Wildcards also have capture: the compiler treats one unknown argument as a consistent hidden type during an operation. A small private generic helper can sometimes give that captured type a name. This is preferable to a raw type or unchecked cast when rearranging elements inside one unknown list.

Type inference uses the invocation context as well as arguments. An explicit local result type can make a complex expression easier for both the reader and compiler. When an overloaded print call and a collector make inference confusing, store the collected List<String> in a variable first. Clarity is a better goal than compressing the entire operation into one line.

Keep the contract precise

An unchecked cast does not prove that every element is of the requested type. It transfers responsibility to you, and failure may surface at a later read. Prefer declarations that preserve the element type throughout the operation. When connecting to an old API, isolate conversion and validate values before exposing a typed collection.

Using extends for a destination is a common wildcard mistake. Rephrase the operation: the method must add Integer values, so the destination consumes Integer. A super bound expresses that requirement. Conversely, a producer can return a subtype value as its upper bound, but cannot accept arbitrary new values of the upper type.

Do not put unrelated responsibilities behind an enormous type parameter list. A generic Pair<K,V> explains a relationship. Six parameters with no shared operations may obscure a small concrete class. Start from a repeated operation and introduce only the type variability it actually needs. Document whether null elements are supported separately from generic type safety.

Use Java 17 without relying on reified type arguments

Generics arrived in Java 5, and diamond inference in Java 7. These examples use both within the Java 17 baseline. Local var inference, introduced in Java 10, can infer a generic variable type but does not change erasure. Explicit target types often make empty collection construction clearer for beginners.

The java.util collection APIs use generics throughout. Read wildcard signatures slowly and identify which parameter produces or consumes data. At runtime, generic declarations may be visible through reflection metadata, but ordinary objects do not carry a fully checked element argument for every operation. Avoid treating that metadata as automatic validation of contents.

Use types to connect inputs and results

Generics express reusable relationships without giving up static checking. Bounds provide operations, and wildcards make carefully limited views possible. Trace reads and writes before choosing extends or super. In collections, these rules explain why one interface can support many safe container implementations.
