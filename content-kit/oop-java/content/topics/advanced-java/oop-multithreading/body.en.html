Separate work from its execution schedule

A program may need to calculate a report while another task handles a request. A thread is an independent path of execution within one process. Threads can share objects, which makes communication convenient and shared-state mistakes possible.

Concurrency means tasks can make progress during overlapping periods. Parallelism means tasks actually execute at the same time on different processing resources. Creating two threads does not guarantee parallel execution or a faster result. The scheduler chooses when each runnable thread gets processor time.

A correct concurrent program must not depend on one lucky schedule. Separate task logic from coordination. Decide when the caller must wait, which data is shared and which rule protects updates. These decisions matter more than the number of threads created.

If you know C

Java manages object memory, but it does not make shared updates automatically safe. A reference copied into two threads can still designate one mutable object. Garbage collection and synchronization solve different problems.

Describe a task and start a thread

Runnable task = () -> calculate();
Thread worker = new Thread(task);
worker.start();
worker.join();

Runnable has a void run operation with no arguments. It describes work. Constructing Thread does not start that work. start schedules execution on a new thread; calling run directly is an ordinary method call on the current thread.

A Thread can be started only once. Create a new Thread for another execution, or use an executor that manages reusable workers. Do not call start again after join and expect the same thread object to restart.

join blocks the caller until the chosen thread terminates, unless waiting is interrupted. It does not wait for every thread in the application. Put the join after start and avoid holding a lock the worker needs while waiting for it.

Separate completion, visibility and atomicity

Completion asks whether work has finished. Visibility asks whether one thread can observe another thread’s writes. Atomicity asks whether an operation can be interleaved with another operation. A safe design needs the relevant guarantees for all three.

A successful join establishes visibility of the joined thread’s actions to the waiting caller. Locking has visibility rules too: releasing and later acquiring the same monitor connects writes and reads. These guarantees replace guesses about timing.

A synchronized instance method acquires the receiver’s monitor. Only one thread at a time can hold that monitor. Protect the entire increment with the same monitor for every worker. Synchronizing two different Counter instances would not coordinate one shared value.

Treat cancellation as cooperation

Thread.sleep pauses the current thread for approximately a requested duration, subject to scheduling and interruption. It does not release monitors the thread already owns. A sleeping thread inside synchronized code can therefore keep other workers blocked.

interrupt requests cooperation. If a thread is sleeping or joining, it may receive InterruptedException and have its interrupt status cleared as part of that delivery. If the current method cannot propagate the checked exception, restoring the flag with Thread.currentThread().interrupt() lets outer code observe cancellation.

Restoring the flag is not a reason to continue normal work indefinitely. Choose an appropriate return or termination path. A CPU-bound task should check cancellation at suitable points. Some blocking I/O operations have their own cancellation behavior; do not assume every method reacts exactly like sleep.

Never use deprecated Thread.stop to force a worker to vanish. Abrupt stopping can expose partially updated objects. Design tasks to reach safe cancellation boundaries and leave shared state valid.

Waiting for completion while holding a needed lock can deadlock. For example, main holds the Counter monitor and joins a worker whose next operation needs that monitor. Main waits for the worker; the worker waits for main. Keep waiting and lock ownership small and deliberate.

Separate task submission from worker management

ExecutorService accepts tasks and manages their execution. Runnable is useful for work without a return value. Callable<T> returns a T and may throw checked exceptions. submit wraps either form in a Future whose completion can be inspected or awaited.

Future.get can throw ExecutionException if the task failed, carrying the task’s cause. It can also be interrupted while waiting. A failed task does not automatically print a useful user message. The submitting layer needs a policy for reporting or propagating the failure.

shutdown stops accepting new tasks and allows accepted tasks to finish. It does not itself wait until termination. Use awaitTermination with a timeout when later code must know all work is done. shutdownNow requests interruption and returns queued work that did not start; it cannot guarantee immediate termination of uncooperative tasks.

Bounded task sizes and explicit cleanup are especially useful in a console program. An executor’s ordinary worker threads can keep the process alive. A missing shutdown may therefore look like a program that printed the right answer but never exited.

In Java 17, ExecutorService does not implement AutoCloseable. Use a finally block rather than copying a try-with-resources pattern from newer Java documentation. Later releases have different APIs, so match examples to the release you compile against.

Protect rules rather than individual lines

A bank account transfer needs more than separately synchronized getters and setters. Checking the balance and subtracting funds must belong to one protected operation, or another thread can change the state between them. Identify the invariant and make its complete update atomic.

Static synchronized methods lock the Class object, while instance synchronized methods lock a receiver. Those are different monitors. Two methods with the synchronized keyword do not automatically protect each other when their lock objects differ.

Prefer reducing shared mutable state when possible. A worker can compute a local result and return it through a Future. That often makes reasoning easier than having every worker update one large shared report. Synchronization is necessary when sharing is intentional, but less sharing means fewer interleavings to inspect.

Coordinate even an empty task

With n equal to zero, both counter workers start and immediately finish without incrementing. Main still joins them before reading. The result is zero under the same protocol as a larger input. Avoid a separate timing-based shortcut for empty work; one consistent completion rule is easier to verify.

The executor square-sum exercise also returns zero for no terms, using a task-local accumulator. No shared counter is needed because only the final value crosses the Future boundary.

Replace schedule guesses with protocols

Sleeping before printing a shared result

A long delay might pass on your laptop and fail on a busy machine. Use join, a Future or another documented completion mechanism. Time passing does not establish visibility or completion.

Locking a fresh object on every call

Each fresh lock is independent, so competing workers never exclude one another. Keep one stable lock associated with the shared state. Document which fields it protects.

Ignoring interruption

An empty interruption catch can make cancellation ineffective. Propagate it when the signature allows, or restore the status and leave through a safe path. Do not convert a cancellation request into an unexplained success.

Keep coordination small

  • Give each task a bounded responsibility and clear result.
  • Join every worker whose completion the next action depends on.
  • Protect an invariant with one consistent locking policy.
  • Avoid slow operations while holding a monitor.
  • Shut down executors and explain cancellation behavior.

Concurrency within the Java 17 baseline

Thread, Runnable, synchronized and ExecutorService are available in Java 17. Virtual threads belong to later releases and are outside this lesson. The executor example explicitly calls shutdown because Java 17 lacks the later AutoCloseable executor contract.

Correctness must survive a different schedule

Tasks describe work; joins and futures coordinate completion; shared monitors protect compound updates. Treat interruption and cleanup as part of the contract. Apply that discipline to the single event thread in Swing basics.
