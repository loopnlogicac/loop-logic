Separate one class counter from many student records

A department may want a count of all student records created, while each record needs its own identifier. Copying the department count into every student would mix two responsibilities. A static member belongs to a loaded class rather than each individual instance.

Think of a shared classroom notice board beside separate student notebooks. Updating the board changes one shared place. Updating a notebook changes only one student's record. Static state resembles the board; instance state resembles the notebooks.

This distinction explains why main is static. The launcher can call it without selecting a particular Main object. A static method has no current this reference. It can use its arguments and class state, or work through an explicitly supplied object.

Mark shared members explicitly

Place static on a field or method declaration when its meaning belongs to the class. Call static methods through the class name to make that ownership visible. A method being static does not automatically make it pure, constant or safe for concurrent access.

class Student {
    private static int created;
    private final int id;
    Student() {
        created++;
        id = created;
    }
    static int count() {
        return created;
    }
}

created is shared; id is copied into each object during construction. Adding final to id prevents reassignment of that instance field. The two modifiers answer different questions: static concerns ownership, while final concerns assignment.

Before any Student is constructed, created starts at zero. The first constructor increments it to one and saves one in that object's id. The second increments it to two and saves two elsewhere. The first object's id remains one.

The static count method can read created without an instance. It cannot read an arbitrary unqualified id because no particular Student is selected. A static helper receiving a Student argument can access permitted instance state through that explicit reference. Static does not forbid object use; it removes the implicit receiver.

Static state belongs to a class as loaded by a class loader. In advanced applications, distinct class loaders can load distinct copies of a class. For these ordinary console programs, one loaded copy is the useful model. Do not turn the phrase shared by the class into a claim about every JVM in the world.

A static counter is not automatically the number of currently live objects. The example counts constructions and never decrements. Garbage collection does not update that counter for you. Name such fields according to what they actually measure.

When class initialization happens

A static initializer is a static block or static field initializer that prepares class state. Relevant active uses trigger class initialization, including creating an instance, invoking a static method, or using a nonconstant static field. Java performs that initialization once for the loaded class.

Static field initializers and static blocks run in textual order. A field has its default value before those assignments execute. If one initializer depends on another, read the declaration order carefully. Complicated cross-class initialization dependencies can be difficult to reason about.

Compile-time constants are an important exception to a casual first-use rule. A static final primitive or String initialized with a constant expression may be inlined into caller code. Reading such a constant does not necessarily initialize its declaring class. Not every static final field is a compile-time constant.

A static final field computed by a method call is still final, but its value is not a constant expression in that sense. Its initialization follows the class initialization process. This distinction matters when you predict whether a static block prints during an output question.

Do not put interactive input in a static initializer for a normal teaching model. Initialization timing would become tied to class use rather than an explicit user action. Keep initialization small, predictable and focused on preparing the class.

Use static methods when no receiver is needed

A utility class groups related stateless operations. Math is a familiar library example. A MarkMath.clamp method can depend only on a proposed mark and need no MarkMath object. Its name tells callers what calculation is performed.

A private constructor prevents ordinary outside callers from instantiating the utility class. Marking the class final can make its non-inheritance intent explicit as well. The private constructor, rather than static methods alone, is what blocks direct construction.

Avoid turning every method into a static utility by habit. A wallet withdrawal depends on one wallet's state and belongs naturally to that receiver. A pure conversion from poisha to whole taka can be a static calculation. Ownership follows the meaning of the work.

A utility should also stay focused. A class collecting every unrelated helper in an application becomes hard to navigate. Group methods that share a coherent responsibility, and choose names that communicate the inputs and result without hidden mutable dependencies.

Understand the cost of sharing

Mutable static state means callers can influence one another. If a shared fee rate changes, bills computed for existing Enrollment objects may change too. That can be correct if the model promises the current rate, or wrong if each enrollment should preserve its original rate.

Decide whether a value is a live shared policy or a historical snapshot. Save an instance value when the event should remember the rate at creation. Use a shared field only when all relevant calculations should observe later changes. This is a design decision, not merely a syntax choice.

Tests and repeated runs also need to account for static state. Within one JVM, a counter can retain changes between method calls. Starting a fresh JVM starts a fresh class initialization context. A reset method should not be added casually if it would break the class contract.

Concurrent updates require additional coordination. Incrementing an int is not made atomic or safely shared merely by declaring it static. Multithreading later covers coordination. Here, the examples deliberately use one thread and bounded counts.

Calling a static method through an instance

Java may permit some instance-style static accesses, but the spelling misleads readers about the receiver. Use the class name. It also avoids compiler lint warnings in code checked strictly.

Trying to use this in static code

A static call has no implicit object. Pass an object explicitly when its state is needed, or make the operation an instance method when that is its true responsibility.

Expecting a static block for each object

A static block prepares the loaded class once. An instance initializer or constructor runs for each new object. Keep two separate counts in an initialization trace.

The ownership rules stay the same

The static member and initializer rules used here are supported under Java 17 without a new feature. Static imports, taught with packages, only shorten member names. They do not change when the declaring class is initialized or who owns its fields.
