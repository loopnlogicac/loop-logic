ক্লাসের একটি কাউন্টার আর অনেক শিক্ষার্থীর রেকর্ড আলাদা করো

বিভাগ জানতে চাইতে পারে মোট কয়টি শিক্ষার্থীর রেকর্ড তৈরি হয়েছে। আবার প্রতিটি রেকর্ডের নিজের পরিচয় নম্বর লাগবে। মোট সংখ্যা প্রতিটি শিক্ষার্থীর মধ্যে কপি করলে দুই দায়িত্ব মিশে যায়। static মেম্বার প্রতিটি ইনস্ট্যান্সের বদলে লোড হওয়া ক্লাসের অংশ।

শিক্ষার্থীদের আলাদা খাতার পাশে ক্লাসের সবার জন্য একটি নোটিশ বোর্ড ভাবো। বোর্ড বদলালে একটি শেয়ার করা জায়গা বদলায়। খাতা বদলালে একজনের রেকর্ড বদলায়। static স্টেট বোর্ডের মতো, ইনস্ট্যান্স স্টেট খাতার মতো।

main কেন static, এই পার্থক্য থেকেই বোঝা যায়। নির্দিষ্ট Main অবজেক্ট না বেছেই লঞ্চার সেটি কল করতে পারে। static মেথডে বর্তমান অবজেক্টের this রেফারেন্স নেই। আর্গুমেন্ট, ক্লাসের স্টেট বা স্পষ্ট করে দেওয়া অবজেক্ট দিয়ে কাজ করতে পারে।

শেয়ার করা মেম্বার স্পষ্ট করে চিহ্নিত করো

ফিল্ড বা মেথডের অর্থ ক্লাসের সঙ্গে যুক্ত হলে ঘোষণায় static দাও। মালিকানা বোঝাতে static মেথড ক্লাসের নাম দিয়ে কল করো। static হলেই মেথড বাইরের স্টেট বদলাবে না, মান স্থির হবে বা একই সঙ্গে কয়েকটি থ্রেডে নিরাপদে চলবে—এমন নয়।

class Student {
    private static int created;
    private final int id;
    Student() {
        created++;
        id = created;
    }
    static int count() {
        return created;
    }
}

created সবার শেয়ার করা। তৈরির সময় প্রতিটি অবজেক্টের id-তে আলাদা করে মান বসে। id-তে final থাকায় ইনস্ট্যান্স ফিল্ডটি আবার অ্যাসাইন করা যায় না। মডিফায়ার দুটি আলাদা প্রশ্নের উত্তর দেয়। static মালিকানা বোঝায়, final অ্যাসাইন করার নিয়ম বোঝায়।

কোনো Student তৈরির আগে created শূন্য। প্রথম কনস্ট্রাক্টর সেটি এক বাড়িয়ে নিজের অবজেক্টের id-তে এক রাখে। দ্বিতীয়টি বাড়িয়ে দুই করে, নিজের id-তে দুই রাখে। প্রথম অবজেক্টের id এক-ই থাকে।

static count মেথড ইনস্ট্যান্স ছাড়াই created পড়তে পারে। কিন্তু নির্দিষ্ট Student বাছা হয়নি বলে শুধু id লিখে কোনো অবজেক্টের মান পড়তে পারে না। static সহায়ক মেথডে Student আর্গুমেন্ট নিলে ওই রেফারেন্স দিয়ে অনুমোদিত ইনস্ট্যান্স স্টেট পড়তে পারে। static অবজেক্ট ব্যবহার নিষেধ করে না; নিজে থেকে পাওয়া অবজেক্ট রেফারেন্স সরিয়ে দেয়।

class loader যে ক্লাস লোড করেছে, static স্টেট তার। উন্নত অ্যাপ্লিকেশনে আলাদা class loader একই ক্লাসের আলাদা কপি লোড করতে পারে। এখানকার সাধারণ কনসোল প্রোগ্রামে একটি লোড হওয়া কপিই যথেষ্ট মডেল। ক্লাসের শেয়ার করা মানে পৃথিবীর সব JVM-এর জন্য একটি, এমন দাবি কোরো না।

static কাউন্টার নিজে থেকে বর্তমানে মেমরিতে থাকা অবজেক্টের সংখ্যা নয়। এখানে কতবার তৈরি হয়েছে গোনে, কখনো কমায় না। garbage collection তোমার হয়ে কাউন্টার আপডেট করে না। ফিল্ড আসলে যা মাপে, সেই অনুযায়ী নাম দাও।

মালিকানা আর মান বসানোর সময় আলাদা করে দেখো

Student-এ শেয়ার করা নম্বর তৈরির ব্যবস্থা আর আলাদা সেভ করা id আছে। Settings একবারের ক্লাস initialization দেখায়। Lab তার সঙ্গে প্রতি অবজেক্টের initialization তুলনা করে। MarkMath-এ স্থায়ী ইনস্ট্যান্স স্টেট ছাড়া হিসাব দেখবে।

শেয়ার করা মোট সংখ্যা, আলাদা id

দুটি অবজেক্টের id হলো 1 আর 2। একটি static কাউন্টারে দুইবার তৈরি হওয়ার হিসাব থাকে।

ক্লাসে একবার initialization

প্রথম সক্রিয় ব্যবহারে Settings-এর initialization হয়। init একবার প্রিন্ট করে। তারপর দুটি মেথড কলেই 30 পড়া হয়।

ছোট utility ক্লাস

স্টেটবিহীন কাজের জন্য অবজেক্ট লাগে না। private কনস্ট্রাক্টর অর্থহীন utility ইনস্ট্যান্স তৈরি করতে দেয় না।

static আর ইনস্ট্যান্স initialization

static ব্লক একবার চলে। দুটি অবজেক্টের প্রতিটির জন্য ইনস্ট্যান্স ব্লক একবার করে চলে।

ক্লাসের initialization কখন হয়

static initializer হলো static ব্লক বা static ফিল্ডের initializer, যা ক্লাসের স্টেট তৈরি করে। প্রাসঙ্গিক সক্রিয় ব্যবহার থেকে ক্লাসের initialization শুরু হয়। যেমন ইনস্ট্যান্স তৈরি, static মেথড কল বা কনস্ট্যান্ট নয় এমন static ফিল্ড ব্যবহার। লোড হওয়া ক্লাসের জন্য কাজটি একবার হয়।

static ফিল্ডের initializer আর static ব্লক লেখার ক্রমে চলে। এসব অ্যাসাইনমেন্টের আগে ফিল্ডে ডিফল্ট মান থাকে। একটি initializer অন্যটির ওপর নির্ভর করলে ঘোষণার ক্রম মন দিয়ে পড়ো। আলাদা ক্লাসের মধ্যে জটিল initialization-এর নির্ভরতা বুঝতে অসুবিধা হতে পারে।

কম্পাইলের সময় জানা কনস্ট্যান্টের ক্ষেত্রে প্রথম ব্যবহার নিয়ে সাধারণ নিয়মে ব্যতিক্রম আছে। constant expression দিয়ে মান বসানো static final প্রিমিটিভ বা String কল করা কোডে সরাসরি বসে যেতে পারে। এমন কনস্ট্যান্ট পড়লে তার ক্লাসের initialization হবেই, তা নয়। সব static final ফিল্ড কম্পাইলের সময়ের কনস্ট্যান্ট নয়।

মেথড কলের ফল থেকে মান পাওয়া static final ফিল্ড final-ই থাকে। কিন্তু ওই অর্থে constant expression নয়। তার মান বসানো ক্লাস initialization-এর প্রক্রিয়াতেই হয়। আউটপুটের প্রশ্নে static ব্লক প্রিন্ট করবে কি না বুঝতে এই পার্থক্য দরকার।

সাধারণ শেখার মডেলে static initializer-এর মধ্যে ব্যবহারকারীর ইনপুট রেখো না। তাহলে ইনপুটের সময় স্পষ্ট কাজের বদলে ক্লাস ব্যবহারের সঙ্গে জড়িয়ে যাবে। initialization ছোট, অনুমান করা যায় এমন আর ক্লাস প্রস্তুত করার কাজে সীমিত রাখো।

নির্দিষ্ট অবজেক্ট না লাগলে static মেথড নাও

Utility class সম্পর্কিত স্টেটবিহীন কাজ একসঙ্গে রাখে। লাইব্রেরির Math পরিচিত উদাহরণ। MarkMath.clamp শুধু প্রস্তাবিত নম্বর নিয়ে কাজ করতে পারে। MarkMath অবজেক্ট লাগে না। নাম দেখে কোন হিসাব হচ্ছে বোঝা যায়।

private কনস্ট্রাক্টর বাইরের সাধারণ কোডকে utility ক্লাসের ইনস্ট্যান্স বানাতে বাধা দেয়। ক্লাস final করলে ইনহেরিট্যান্সের জন্য নয়, সেটাও বোঝানো যায়। সরাসরি অবজেক্ট বানানো আটকায় private কনস্ট্রাক্টর। শুধু static মেথড থাকলেই তা আটকায় না।

অভ্যাস করে সব মেথড static utility বানাবে না। ওয়ালেট থেকে টাকা তোলা নির্দিষ্ট ওয়ালেটের স্টেটের কাজ। সেটার ইনস্ট্যান্স মেথড মানায়। পয়সা থেকে পূর্ণ টাকা বের করার হিসাব static হতে পারে। কাজের অর্থ অনুযায়ী মালিকানা ঠিক হয়।

utility-র দায়িত্বও নির্দিষ্ট থাকুক। অ্যাপ্লিকেশনের সব সম্পর্কহীন সহায়ক কাজ এক ক্লাসে রাখলে খুঁজে পাওয়া কঠিন হয়। একই ধরনের দায়িত্বের মেথড একসঙ্গে রাখো। নাম থেকে ইনপুট আর ফল বোঝা যাক, আড়ালে পরিবর্তনযোগ্য স্টেটের নির্ভরতা না থাকুক।

শেয়ার করার প্রভাব বোঝো

বদলানো যায় এমন static স্টেটে এক অংশ অন্য অংশকে প্রভাবিত করতে পারে। শেয়ার করা ফি-র হার বদলালে আগের Enrollment অবজেক্টের হিসাব করা বিলও বদলাতে পারে। বর্তমান হার দেওয়ার প্রতিশ্রুতি থাকলে এটি ঠিক। শুরুর হার মনে রাখার কথা থাকলে ভুল।

মানটি বর্তমান শেয়ার করা নীতি, নাকি আগের ঘটনার স্থির ছবি, ঠিক করো। তৈরির সময়ের হার মনে রাখতে হলে ইনস্ট্যান্স মান সেভ করো। সব হিসাবেই পরের পরিবর্তন দেখার কথা থাকলে শেয়ার করা ফিল্ড নাও। এটি ডিজাইনের সিদ্ধান্ত, শুধু কোড লেখার ধরন নয়।

টেস্ট আর বারবার চালানোর সময়ও static স্টেট ধরতে হবে। একটি JVM-এর মধ্যে মেথড কলের মাঝে কাউন্টারের পরিবর্তন থেকে যায়। নতুন JVM-এ নতুন করে ক্লাসের initialization হয়। ক্লাসের প্রতিশ্রুতি ভাঙতে পারে এমন reset মেথড হঠাৎ যোগ করবে না।

একই সময়ের আপডেটে বাড়তি সমন্বয় লাগে। int বাড়ানোর কাজ static লিখলেই এক ধাপে নিরাপদে শেষ হয় না বা থ্রেডে নিরাপদে শেয়ার হয় না। পরে মাল্টিথ্রেডিংয়ে শিখবে। এখানে ইচ্ছা করেই একটি থ্রেড আর সীমার মধ্যে গণনা ব্যবহার করা হয়েছে।

ইনস্ট্যান্স দিয়ে static মেথড কল

Java কিছু ক্ষেত্রে এমন লেখা মেনে নিতে পারে। তবে পাঠক ভুলভাবে ভাবতে পারে নির্দিষ্ট অবজেক্টের কাজ চলছে। ক্লাসের নাম নাও। এতে কঠোর lint চেকে কম্পাইলারের সতর্কতাও এড়ানো যায়।

static কোডে this ব্যবহার

static কলে নিজে থেকে কোনো অবজেক্ট থাকে না। স্টেট দরকার হলে স্পষ্ট করে অবজেক্ট পাঠাও। অথবা কাজের দায়িত্ব সেখানেই হলে ইনস্ট্যান্স মেথড করো।

প্রতি অবজেক্টে static ব্লক চলবে আশা করা

static ব্লক লোড হওয়া ক্লাস একবার প্রস্তুত করে। প্রতিটি নতুন অবজেক্টে ইনস্ট্যান্স initializer বা কনস্ট্রাক্টর চলে। ট্রেসে দুই ধরনের গণনা আলাদা রাখো।

মালিকানার নিয়ম একই থাকে

এখানকার static মেম্বার আর initializer Java 17-তেই চলে। নতুন ফিচার লাগে না। প্যাকেজের সঙ্গে static import শিখবে। সেটি শুধু মেম্বারের নাম ছোট করে। ক্লাস কখন initialization করবে বা ফিল্ডের মালিক কে, বদলায় না।

মডেলে যা সত্যিই শেয়ার করা, সেটুকুই শেয়ার করো

ইনস্ট্যান্স মেম্বার আলাদা অবজেক্টের। static মেম্বার লোড হওয়া ক্লাসের বা নির্দিষ্ট অবজেক্ট ছাড়া হিসাবের। মালিকানা থেকে initialization-এর সময় আলাদা করে দেখো। এরপর সাধারণ রেফারেন্স দিয়ে শেয়ার করা বুঝতে অবজেক্ট রেফারেন্স আর সমতা শেখো।
