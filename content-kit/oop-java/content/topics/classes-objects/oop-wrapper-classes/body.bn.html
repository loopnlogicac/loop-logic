প্রিমিটিভ মানকে অবজেক্ট টাইপে রাখো

অ্যারেতে সরাসরি int রাখা যায়। কিন্তু কিছু API অবজেক্ট চায়। র‍্যাপার ক্লাস প্রিমিটিভ মানকে অবজেক্ট টাইপ দিয়ে প্রকাশ করে। Integer হলো int-এর র‍্যাপার, আর Double হলো double-এর। এতে দরকারি অপারেশন পাও। পাশাপাশি রেফারেন্সের কিছু ফাঁদও আসে।

কার্ডে সংখ্যা লেখার কথা ভাবো। সংখ্যার মান আর যে কার্ডে লেখা আছে, দুটি আলাদা ধারণা। আলাদা দুটি কার্ডে একই সংখ্যা থাকতে পারে। কার্ড না থাকা আর শূন্য লেখা কার্ড থাকা এক নয়।

পরে generic collection-এ র‍্যাপার কাজে লাগবে। সেখানে টাইপ আর্গুমেন্ট হিসেবে রেফারেন্স টাইপ লাগে। এখনই collection ব্যবহার না করেও boxing আর সমতা বুঝতে পারো। প্রতিটি ট্রেসে প্রিমিটিভ মান, অবজেক্টের পরিচয় আর সম্ভাব্য null রেফারেন্স আলাদা রাখো।

প্রতিটি প্রিমিটিভের র‍্যাপার চিনে নাও

প্রিমিটিভ আর র‍্যাপার-এর জোড়া
প্রিমিটিভর‍্যাপারসাধারণ কাজ
byteByteছোট চিহ্নসহ পূর্ণসংখ্যা
shortShortকম সীমার চিহ্নসহ পূর্ণসংখ্যা

র‍্যাপার নামগুলো java.lang-এর ক্লাস, তাই আলাদা ইমপোর্ট লাগে না। সব নাম শুধু প্রিমিটিভের প্রথম অক্ষর বড় করলেই হয় না। int-এর জন্য Integer, char-এর জন্য Character। সংখ্যার র‍্যাপার ক্লাসগুলোর সাধারণ superclass হলো Number। এটি নবম প্রিমিটিভ র‍্যাপার নয়।

int mark = 80;
Integer boxed = mark;
int restored = boxed;
Integer parsed = Integer.valueOf("80");

Autoboxing হলো প্রিমিটিভ থেকে তার র‍্যাপার-এ স্বয়ংক্রিয় রূপান্তর। Unboxing দিয়ে প্রিমিটিভ মান বের করা হয়। অনুমোদিত প্রসঙ্গে কম্পাইলার এসব রূপান্তর বসিয়ে দেয়। তবুও চালানোর সময় ফল কী হবে, তা ভাবতে হয়।

হিসাবের আগে-পরে রূপান্তর অনুসরণ করো

int মান 80-কে Integer-এ অ্যাসাইন করলে boxed রূপ চাওয়া হয়। null নয় এমন Integer-কে int-এ রাখলে সংখ্যার মান বের হয়। boxed + 5-এর মতো হিসাবেও আগে unboxing হয়। ফল সংখ্যার যোগ, String জোড়া লাগানো নয়।

র‍্যাপার অবজেক্ট অপরিবর্তনীয় মান। boxed++ লিখলে আগের Integer-এর ভেতরের সংখ্যা বদলায় না। আগে unboxing, প্রিমিটিভ মান বাড়ানো, আবার boxing আর ভেরিয়েবলে অ্যাসাইন করা হয়। পুরোনো Integer-এর অন্য রেফারেন্স আগের মানই দেখে।

প্রিমিটিভ int কখনো null হয় না। Integer হতে পারে। null রেফারেন্স unbox করতে গেলে NullPointerException হয়। দেখতে সাধারণ হিসাব মনে হওয়ায় ভুলের জায়গা অপ্রত্যাশিত লাগতে পারে। সংখ্যার এক্সপ্রেশন হঠাৎ ব্যর্থ হলে রেফারেন্স কোথা থেকে এসেছে দেখো।

নতুন Integer অ্যারেতে null রেফারেন্স থাকে, নিজে থেকে boxed শূন্য নয়। হিসাবের আগে প্রতিটি এলিমেন্টে মান দাও। অথবা অনুপস্থিত মানের স্পষ্ট নিয়ম করো। অন্যদিকে নতুন int অ্যারেতে প্রিমিটিভ শূন্য থাকে। এলিমেন্টের টাইপ বাছলে ডেটার অর্থ আর ব্যর্থতার সম্ভাবনাও বদলায়।

final Integer রেফারেন্স আবার অ্যাসাইন করা যায় না। র‍্যাপার অবজেক্টও নিজের সংখ্যার মান বদলাতে পারে না। final int[] আলাদা; সেখানে অ্যারের এলিমেন্ট পরিবর্তনযোগ্য। সব final রেফারেন্স একই ভাবার বদলে সাধারণ অবজেক্টের নিয়মে ফিরে যাও।

Boxing, পার্সিং আর নিরাপদ তুলনা দেখো

প্রথম উদাহরণে নম্বর box করে আবার হিসাবের জন্য বের করা হয়। পরের দুটি ছোট মানের নিশ্চিত পরিচয় আর বড় মানের তুলনা আলাদা করে। পার্সিং সংখ্যার টেক্সট বদলায়। শেষের চেক সত্যিই অনুপস্থিত র‍্যাপার সামলায়।

নম্বর box আর unbox করা

প্রথম অ্যাসাইনমেন্টে 80 box হয়। দ্বিতীয়টিতে হিসাবের আগে unbox হয়। ফলে 85 পাও।

ছোট মানে নিশ্চিত একই পরিচয়

-128 থেকে 127-এর মধ্যে কনস্ট্যান্ট int box করলে নিয়ম অনুযায়ী একই পরিচয় শেয়ার হয়। মানের সমতাও থাকে।

বড় boxed মান নিরাপদে তুলনা

1000-এর ক্ষেত্রে মানের তুলনা নির্ভরযোগ্য। রেফারেন্স ক্যাশ করা আছে কি না, কিছু ধরে নেওয়া হয়নি।

সংখ্যার টেক্সট পার্স করা

পার্সিং টেক্সট থেকে সংখ্যার মান বের করে। পার্স করা রোলের সঙ্গে 1 যোগ করলে 18 হয়।

অনুপস্থিত র‍্যাপার সামলানো

শর্ত দিয়ে null রেফারেন্স unbox করা এড়িয়ে ডিফল্ট শূন্য বেছে নেওয়া হয়।

ছোট মানের পরিচয় মিলে যাওয়ার ফাঁদ

বাছা কিছু মানের জন্য Java আগের র‍্যাপার অবজেক্ট আবার ব্যবহার করতে পারে। -128 থেকে 127-এর মধ্যে কনস্ট্যান্ট int boxing-এ একই পরিচয় ভাষার নিয়মে নিশ্চিত। তাই উদাহরণে কনস্ট্যান্ট 127 থেকে পাওয়া দুটি Integer রেফারেন্স == দিয়ে true দেয়।

সেখান থেকে সব পূর্ণসংখ্যার নিয়ম বানাবে না। বাস্তবায়ন চাইলে বাধ্যতামূলক সীমার বাইরেও ক্যাশ করতে পারে। তাই 1000-এর মতো বড় মানে রেফারেন্সের পরিচয়কে সব রানটাইমে চলার সংখ্যার তুলনা ধরা যাবে না। এক রানটাইমে ঠিক মনে হওয়া প্রোগ্রাম অন্য জায়গায় ভুল ধারণা দিতে পারে।

Integer.valueOf-এর বর্ণনাতেও অন্তত ছোট সীমার ক্যাশের কথা আছে। কাজে লাগানোর শিক্ষা একই: সংখ্যার সমতা চাইলে মান তুলনা করো। ক্যাশ অবজেক্ট বরাদ্দের খুঁটিনাটি। ব্যবহারকারী কোড সেটাকে কাজের নিয়ম বানাবে না।

Integer.equals একই int মানের অন্য Integer গ্রহণ করে। শুধু গাণিতিক মান মিললেই Long-কে সমান ধরে না। র‍্যাপার-এ টাইপ অনুযায়ী সমতার নিজস্ব নিয়ম থাকে। সংখ্যার রূপান্তর চাইলে তুলনার আগে সেটা স্পষ্ট করে করো।

একটি অপারেন্ড প্রিমিটিভ হলে ==-এর কাজও বদলাতে পারে। Integer আর int তুলনায় র‍্যাপার unbox হয়ে প্রিমিটিভ মান তুলনা হতে পারে। র‍্যাপার null হলে ব্যর্থ হতে পারে। == পরিচয় দেখবে নাকি সংখ্যা তুলনা করবে বলার আগে অপারেন্ডের টাইপ পড়ো।

ক্রম ঠিক করতে Integer.compare ঋণাত্মক সংখ্যা, শূন্য বা ধনাত্মক সংখ্যা দেয়। বিয়োগ করে ক্রম বোঝার শর্টকাটে চরম int মানে overflow হতে পারে। compare-এ সেই সমস্যা এড়ানো যায়। বাস্তবায়নের ঘটনায় ভর না করে কাঙ্ক্ষিত সম্পর্ক বোঝায় এমন অপারেশন নাও।

টেক্সট বদলানো আর boxing আলাদা

Integer.parseInt পূর্ণসংখ্যার টেক্সট পড়ে প্রিমিটিভ int দেয়। Integer.valueOf(String) একই ধরনের টেক্সট পড়ে Integer দেয়। boxing টেক্সট নয়, আগেই থাকা প্রিমিটিভ মান দিয়ে শুরু হয়। কাজগুলো কাছাকাছি দেখা গেলেও আলাদা রূপান্তরের সমস্যা সমাধান করে।

পার্সিংয়ে নির্দিষ্ট টাইপের সীমার মধ্যে বৈধ লেখা লাগে। 3.5-এর মতো দশমিক টেক্সট বৈধ int টোকেন নয়। কোর্সের লেবেল থাকা টেক্সট বা সীমার বাইরের সংখ্যাও অবৈধ। এসব ক্ষেত্রে Integer.parseInt, NumberFormatException দেয়। রাউন্ড করে বা null দেয় না।

শুরুতে যোগ বা বিয়োগের চিহ্ন পূর্ণসংখ্যার টেক্সটের অংশ হতে পারে। সাধারণ দশমিক parseInt-এ সামনে শূন্য থাকলেই অক্টাল হয় না। পার্স করা সংখ্যা আগের লেখার দৈর্ঘ্য মনে রাখে না। তাই 0017 পার্স করলে সতেরো পাও। শূন্য দিয়ে পূরণ করা লেবেল চাইলে পরে ফরম্যাট করো।

Double.parseDouble দিয়ে 3.75-এর মতো floating-point টেক্সট পড়া যায়। ফল তখনও double-এর আনুমানিক হিসাব মানে। টেক্সট পার্স করলেই বাইনারি floating-point টাকার নিখুঁত দশমিক টাইপ হয় না। ইনপুট বোঝা আর সংখ্যার মডেল বাছা আলাদা রাখো।

এখানকার অনুশীলনে বৈধ ইনপুটের সীমা বলা আছে, যাতে রূপান্তরে মন দিতে পারো। নিয়ন্ত্রণহীন ব্যবহারকারীর ইনপুটে অবৈধ পার্সিং কীভাবে সামলাবে, ঠিক করতে হবে। এক্সেপশনের পাঠে সমস্যা জানানো আর সামলে এগোনো শিখবে।

মডেলে অনুপস্থিত মান দরকার কি না ঠিক করো

অনুপস্থিত আর শূন্য আলাদা রাখতে হলে র‍্যাপার উপকারী। যেমন, নম্বর নেই মানে এখনও মূল্যায়ন হয়নি। শূন্য মানে মূল্যায়ন হয়েছে, ফল শূন্য। দুটোতেই শূন্য বসালে অর্থ হারায়। null রেফারেন্স দিয়ে একভাবে অনুপস্থিতি বোঝাতে পারো। তবে ব্যবহারপথে তা বলতে হবে।

null বৈধ হলে unboxing-এর আগে চেক করো। শর্ত দিয়ে বলা ডিফল্ট নাও বা অনুপস্থিত মান বাদ দাও। শুধু বাছা শাখাটিই মান বের করার চেষ্টা করছে নিশ্চিত করো। স্পষ্ট intValue মেথড কলেও আসল র‍্যাপার অবজেক্ট লাগে, স্বয়ংক্রিয় unboxing-এর মতোই।

ডেটা সব সময় আছে আর হিসাবে লাগে, এমন হলে API বাধ্য না করলে প্রিমিটিভ নাও। এতে null থাকার অবস্থা আর অপ্রয়োজনীয় অবজেক্টের হিসাব এড়াও। নির্দিষ্ট মডেল বা API-র দরকারে র‍্যাপার নাও। ক্লাসের নাম দেখতে বেশি অবজেক্ট ওরিয়েন্টেড বলে নয়।

অবজেক্ট নিয়ে অযাচিত ধারণা এড়াও

ছোট পরীক্ষায় মিলেছে বলে == নেওয়া

ক্যাশের boxed মান রেফারেন্স শেয়ার করতে পারে। Integer-এর নিয়ম অনুযায়ী boxed মান তুলনা করতে equals নাও। রেফারেন্স না থাকতে পারলে ইনস্ট্যান্স মেথড কলের আগে null সামলাও।

বাদ দেওয়ার পরামর্শ থাকা পুরোনো কনস্ট্রাক্টরে র‍্যাপার বানানো

new Integer-এর বদলে valueOf বা autoboxing পছন্দ করো। পুরোনো কনস্ট্রাক্টর deprecated; এখানে বাড়তি কোনো সুবিধা দেয় না। তার সতর্কতাও নতুন API বেছে নেওয়ার পরামর্শ জানায়।

পার্সিং দশমিকের ভগ্নাংশ বাদ দেয় ভাবা

Integer.parseInt আগে থেকেই সংখ্যা হওয়া double-কে কাস্ট করার মতো নয়। এটি পূর্ণসংখ্যার টেক্সট বৈধ কি না দেখে। বলা ইনপুট ফরম্যাটের জন্য সঠিক পার্সার নাও। অবৈধ টেক্সটের সমস্যা ভেবেচিন্তে জানাও।

Boxing পুরোনো, কনস্ট্রাক্টরের পরামর্শও জরুরি

autoboxing আর unboxing এসেছে Java 5-এ। এখানকার রূপান্তর আর factory মেথড Java 17 সমর্থন করে। deprecated র‍্যাপার কনস্ট্রাক্টর এড়ানো হয়েছে। কোনো ফল নির্দিষ্ট রানটাইমের বাড়তি ক্যাশের ওপর নির্ভর করে না।

ভেবে মান তুলনা করো, অনুপস্থিত রেফারেন্স যাচাই করো

র‍্যাপার প্রিমিটিভের হিসাবকে অবজেক্টভিত্তিক API-র সঙ্গে যুক্ত করে। boxing, unboxing আর পার্সিং আলাদা ধাপ। ব্যর্থতার কারণও আলাদা। সমতায় টাইপ খেয়াল করো, null সামলানো স্পষ্ট রাখো। ক্লাসের সম্পর্ক আর বিস্তার শেখার জন্য প্রস্তুত হলে ইনহেরিট্যান্সে যাও।
