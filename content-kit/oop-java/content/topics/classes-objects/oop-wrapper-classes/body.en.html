Put a primitive value inside an object type

An array can store int values directly, but some APIs require objects. A wrapper class represents a primitive value through an object type. Integer is the wrapper for int, while Double wraps double. The distinction adds useful operations and also introduces reference-related pitfalls.

Think of a number written on a card. The numeric value and the card carrying it are different ideas. Two cards may carry the same number while being separate objects. A missing card is not the same as a card carrying zero.

Wrappers matter for future generic collections, which use reference types as type arguments. You can understand boxing and equality now without using those collections yet. Keep the primitive value, object identity and possible null reference separate in every trace.

Autoboxing is the automatic conversion from a primitive to its wrapper. Unboxing extracts the primitive value. The compiler inserts these conversions in permitted contexts, but the runtime consequences still matter.

Follow the conversion around arithmetic

Assigning int 80 to Integer requests a boxed representation. Assigning that nonnull Integer to int extracts its numeric value. Arithmetic such as boxed + 5 also unboxes before adding. The result is numeric addition rather than String concatenation.

Wrapper objects are immutable values. Writing boxed++ does not edit an existing Integer's internal number. It unboxes, increments the primitive value, boxes the result and reassigns the variable. Another reference to the old Integer still observes its original value.

Primitive int cannot be null, but Integer can. Attempting to unbox a null reference throws NullPointerException. The expression may look like ordinary arithmetic, so the failure location can surprise you. Inspect the reference's origin when a numeric expression unexpectedly fails.

A new Integer array contains null references, not automatically boxed zeros. Fill each element before arithmetic, or define an explicit missing-value policy. A new int array, by contrast, contains primitive zeros. Choosing the element type changes both storage meaning and possible failure cases.

A final Integer reference cannot be reassigned, and the wrapper object itself cannot change its numeric value. That combination differs from final int[], whose referenced elements remain mutable. Return to the general object rule rather than assuming all final references behave alike.

The small-value identity trap

Java can reuse wrapper objects for selected values. For boxing constant int values from -128 through 127, shared identity is guaranteed by the language rules. That is why two Integer references initialized from the constant 127 compare true with == in the example.

Do not extend that observation to every integer. Implementations may cache values beyond the required range. Identity for a larger value such as 1000 must therefore not be used as a portable numeric comparison rule. A program that seems to work on one runtime can mislead you elsewhere.

Integer.valueOf also documents caching for at least its small range. The practical lesson remains to use value comparison when you mean numeric equality. Caching is an allocation detail that callers should not turn into a business rule.

Integer.equals accepts another Integer with the same int value. It does not treat a Long as equal merely because the mathematical magnitude matches. The wrappers preserve their type-specific equality contracts. If you intend a numeric conversion, make that conversion explicit before comparing.

The == operator also behaves differently when one operand is primitive. A comparison between Integer and int can unbox the wrapper and compare primitive values. If that wrapper is null, it can fail. Read operand types before predicting whether == performs identity comparison or numeric comparison.

For ordering, Integer.compare returns a negative number, zero or a positive number. It avoids using subtraction as an ordering shortcut, which can overflow for extreme int values. Choose an operation that states the intended relation instead of relying on implementation accidents.

Text conversion is different from boxing

Integer.parseInt reads integer text and returns primitive int. Integer.valueOf(String) reads integer text and returns Integer. Boxing starts with an existing primitive value instead of text. These operations can appear near each other, but they solve different conversion problems.

Parsing accepts a valid representation within the target range. Decimal text such as 3.5 is not a valid int token. Text containing a course label or an out-of-range number is also invalid. Integer.parseInt reports these cases with NumberFormatException rather than rounding or returning null.

A leading sign can be part of integer text. Leading zeros in ordinary decimal parseInt do not request octal notation. The parsed number no longer remembers display width, so parsing 0017 gives seventeen. Use formatting later if you need a padded label.

Double.parseDouble can read decimal floating-point text such as 3.75. Its result still follows double's approximate arithmetic. Parsing text does not make binary floating-point an exact decimal money type. Keep input interpretation separate from the numeric model you choose.

Choose whether missing values belong in the model

A wrapper is useful when missing and zero must remain distinct. For example, a missing mark could mean not yet assessed, while zero is an assessed result. Replacing both with zero loses that meaning. A null reference is one representation, but the interface must describe it.

Check for null before unboxing when it is allowed. A conditional can choose a documented default or skip a missing value. Ensure only the chosen branch attempts extraction. A method called intValue still needs a real wrapper object, just like implicit unboxing.

For data that is always present and used in arithmetic, prefer a primitive unless an API requires a wrapper. It avoids nullable state and unnecessary object-level reasoning. Use wrappers for a concrete modeling or API need rather than because the class name looks more object-oriented.

Using == because a small experiment succeeded

Cached boxed values can share references. Use equals when comparing boxed values by their Integer contract. Handle null before calling an instance method through a possibly missing reference.

Constructing wrappers with deprecated constructors

Prefer valueOf or autoboxing instead of new Integer. The old constructors are deprecated and add no useful value here. Their warnings also signal that a newer API choice is expected.

Assuming parsing truncates decimal text

Integer.parseInt does not behave like casting an already numeric double. It validates integer text. Choose the parser for the promised input format and report invalid text deliberately.

Boxing is old; constructor advice still matters

Autoboxing and unboxing were introduced in Java 5. The Java 17 baseline supports the conversions and factories used here. Deprecated wrapper constructors are avoided, and no result depends on a runtime-specific extension to caching.
