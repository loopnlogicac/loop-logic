দুটি তীর একই বদলানো যায় এমন অবজেক্টে পৌঁছাতে পারে

দুই শিক্ষার্থীকে একই রুম নম্বর দিলে তারা একই রুমে যাবে। ওই রুমের আসবাব বদলালে দুজনই পরিবর্তন দেখবে। একজনের কাগজের রুম নম্বর বদলালে অন্যজনের কাগজ বদলাবে না। Java-র রেফারেন্সও এমন: কপি হওয়া রেফারেন্সের মান একই শেয়ার করা অবজেক্টে পৌঁছাতে পারে।

Aliasing মানে দুই বা ততোধিক রেফারেন্স একই অবজেক্টকে দেখায়। প্রোগ্রামের অংশগুলো ইচ্ছা করে স্টেট শেয়ার করলে এটি কাজে লাগে। স্বাধীন কপি আশা করলে চমক লাগে। প্রথমেই ভেরিয়েবল আর অবজেক্ট আলাদা করে আঁকো।

এই পাঠে মেমরির ছবির সঙ্গে null আর সমতা দেখবে। অবজেক্টের ফিল্ড বদলানো আর রেফারেন্স অন্যদিকে নেওয়া আলাদা করবে। দুটি রেফারেন্স একই অবজেক্টে যায় কি না, আর দুটি অবজেক্টের মান সমান কি না—এই প্রশ্ন দুটোও আলাদা করবে।

রেফারেন্স ঘোষণা করো, তারপর কোথায় যাবে ঠিক করো

রেফারেন্স ভেরিয়েবলে new থেকে পাওয়া রেফারেন্স, অন্য ভেরিয়েবলের কপি বা null থাকতে পারে। null বিশেষ মান, যার অর্থ কোনো অবজেক্ট নেই। লোকাল রেফারেন্স পড়ার আগেও নিশ্চিতভাবে মান অ্যাসাইন করতে হয়।

Cell first = new Cell(5);
Cell alias = first;
Cell missing = null;
boolean identical = first == alias;

প্রথম লাইনে Cell তৈরি হয়। দ্বিতীয় লাইন আরেক Cell না বানিয়ে তার রেফারেন্স কপি করে। তৃতীয় লাইনে কোনো Cell হয় না। কত অবজেক্ট হয়েছে দেখতে ঘোষণা না গুনে অবজেক্ট তৈরি গুনো।

C জানা থাকলে রেফারেন্সকে শেয়ার করা স্টেটে পৌঁছানোর উপায় ভাবতে পারো। কিন্তু সরাসরি মেমরির হিসাব করা যাবে না। Cell রেফারেন্সে এক যোগ করে পাশেরটি খোঁজা যায় না। রেফারেন্স দিয়ে অবজেক্ট নিজে মুক্ত করার সুযোগও Java দেয় না।

ফিল্ড বদলালে মান বদলায়, অ্যাসাইন করলে তীর সরে

first ----------> Cell A { value = 8 }

ফিল্ডে অ্যাসাইন করলে যে অবজেক্টে পৌঁছেছ, তার ভেতরের জায়গা বদলায়। একই অবজেক্টের সব রেফারেন্স তা দেখতে পারে। রেফারেন্স অ্যাসাইন করলে বাঁ পাশের ভেরিয়েবল বদলায়, অন্যগুলো থাকে। এগুলো স্টেট বদলানোর আলাদা ধরন।

মেথডের প্যারামিটারেও একই পার্থক্য। Java প্যারামিটারে রেফারেন্সের মান কপি করে। অনুমতি থাকা ব্যবহারপথ দিয়ে মেথড ওই অবজেক্ট বদলাতে পারে। প্যারামিটারে নতুন মান দিলে শুধু লোকাল রেফারেন্স বদলায়। কল করা কোডের ভেরিয়েবল বদলায় না।

পুরোনোর বদলে নতুন অবজেক্ট নেওয়ার একটি উপায় হলো নতুনটি return করা। কল করা কোড স্পষ্ট করে সেই রেফারেন্স অ্যাসাইন করবে। এতে বদলানোটা চোখে পড়ে। প্যারামিটারকে বাইরের একই ভেরিয়েবল বলে ভুল ধারণা দিতে হয় না।

চলমান প্রোগ্রাম থেকে কোনো পথেই অবজেক্টে পৌঁছানো না গেলে garbage collection তার মেমরি নিতে পারে। একটি রেফারেন্স null করলেই অবজেক্ট নাগালের বাইরে যায় না। অন্য সক্রিয় পথ থাকতে পারে। কখন মেমরি নেওয়া হবে নিশ্চিত নয়। তাই সাধারণ কন্ট্রোল ফ্লোর ঘটনা হিসেবে সেটা ধরবে না।

একই অবজেক্টের রেফারেন্স, অনুপস্থিত মান আর তুলনা দেখো

প্রথম দুটি উদাহরণে একটি শেয়ার করা Cell আর একই রকম মানের দুটি Cell আলাদা হবে। null চেক দিয়ে ব্যবহারের আগে অবজেক্ট আছে কি না দেখা হয়। মেথডের ট্রেসে প্যারামিটার সরানোর আগে মূল অবজেক্ট বদলায়। Objects.equals দিয়ে অনুপস্থিত রেফারেন্সের মাঝেও নিরাপদ তুলনা দেখবে।

একই অবজেক্টের অন্য রেফারেন্স দিয়ে পরিবর্তন

দুটি রেফারেন্স এক Cell-এ পৌঁছায়। মান 8 হয়, আর পরিচয়ের তুলনা true দেয়।

একই ফিল্ডের মান নিয়ে আলাদা অবজেক্ট

দুটি new আলাদা পরিচয়ের অবজেক্ট বানায়। Cell, Object.equals পায়। এখানে সেটিও পরিচয় তুলনা করে।

null থেকে বাঁচার চেক

রেফারেন্স কোনো অবজেক্ট দেখায় না। ফিল্ড পড়ার আগে পরীক্ষা করায় NullPointerException এড়ানো যায়।

আগে অবজেক্ট বদলানো, পরে প্যারামিটার সরানো

প্রথম অ্যাসাইনমেন্ট মূল Cell বদলায়। দ্বিতীয়টি শুধু প্যারামিটারের কপি সরায়। তাই কল করা কোড এখনও 7 দেখে।

null থাকলেও নিরাপদ মানের তুলনা

প্রথম রেফারেন্স null হলে Objects.equals তার মাধ্যমে মেথড কল না করেই সামলায়।

অনুপস্থিত মানের অর্থ স্পষ্ট করো

null দিয়ে ইনস্ট্যান্স মেথড কল বা ইনস্ট্যান্স ফিল্ড পড়লে NullPointerException হয়। রানটাইম কল গ্রহণ করার অবজেক্ট পায় না। null-এর সঙ্গে রেফারেন্স তুলনা করা নিরাপদ। ওই তুলনায় অবজেক্টের ফিল্ড ব্যবহার হয় না।

তোমার ডিজাইনে null বৈধ কি না দেখো। খোঁজার ঐচ্ছিক ফল সত্যিই না থাকতে পারে। কিন্তু বাধ্যতামূলক Student নির্ভরতা না থাকলে তৈরির সময় প্রত্যাখ্যান করাই ভালো হতে পারে। অর্থ না বুঝে সর্বত্র null চেক দিলে মডেলের গভীর ভুল চাপা পড়তে পারে।

short-circuit শর্ত দিয়ে নিরাপদ চেক করা যায়। cell != null && cell.value > 0-তে প্রথম তুলনা true হলেই ডান পাশ চলে। উল্টো ক্রমে লিখলে চেক সাহায্য করার আগেই ফিল্ড পড়তে যাবে। নিরাপদ হওয়ার যুক্তিতে এই ক্রমও জরুরি।

চেকের পরে নির্দিষ্ট বিকল্প থাকতে হবে। Missing প্রিন্ট, বলা কোনো ফল return বা কাজ প্রত্যাখ্যান—প্রতিটিই মানাতে পারে। চুপ করে শূন্য বসানো সব সময় ঠিক নয়। বৈধ শূন্য আর অনুপস্থিত মানের অর্থ আলাদা হতে পারে।

টেক্সটের মান তুলনা করতে নিশ্চিতভাবে null নয় এমন লিটারালের মাধ্যমে equals কল করতে পারো। Objects.equals আরও সাধারণভাবে দুটি রেফারেন্স null-সহ নিরাপদে তুলনা করে। দুটো null হলে true, শুধু একটি null হলে false দেয়। অন্য ক্ষেত্রে প্রথম অবজেক্টের equals কল করে।

পরিচয় আর মান আলাদা প্রশ্ন

রেফারেন্সে == পরিচয় তুলনা করে। দুটি রেফারেন্স একই অবজেক্ট দেখালে বা দুটোই null হলে true। ফিল্ড পরীক্ষা করে না। তাই 5 মানের নতুন দুটি Cell-এর দৃশ্যমান সংখ্যা মিললেও পরিচয় আলাদা।

নিজে override না করলে সাধারণ ক্লাস Object থেকে equals পায়। Object.equals-ও পরিচয় তুলনা করে। Java সাধারণ ক্লাসে নিজে থেকে প্রতিটি ফিল্ড মিলিয়ে সমতা বানায় না। Cell-এর উদাহরণে ইচ্ছা করেই পাওয়া সেই নিয়ম রাখা হয়েছে।

String টেক্সটের মান তুলনা করতে equals override করে। Integer-এর মতো র‍্যাপার ক্লাসেও মানের নিজস্ব নিয়ম আছে। তাই a.equals(b) মানে a-এর ক্লাসের সমতার নিয়ম ব্যবহার করা। সব সময় সব ফিল্ড মেলানো নয়। নির্ভর করার আগে নিয়ম পড়ো বা নিজে নির্ধারণ করো।

পরে মানভিত্তিক সমতা লিখলে hashCode-এর নিয়মও মানতে হবে। hash-ভিত্তিক কনটেইনার ঠিক চলতে সমান অবজেক্টের hash code সমান লাগবে। Object ক্লাসের পাঠে পূর্ণ বাস্তবায়ন শিখবে। এখানে অসম্পূর্ণ equals লিখলে রেফারেন্সের মূল ছবি থেকে মন সরে যাবে।

অ্যাপ্লিকেশনের ডিজাইনেও পরিচয়ের এই পার্থক্য কাজে লাগে। একই মানের দুটি রেকর্ড আলাদা ঘটনা বোঝাতে পারে। দুটি অপরিবর্তনীয় স্থানাঙ্ককে স্থানাঙ্কের মানে সমান ধরতে পারো। পরিচয় বা মানের সমতাকে সব কাজে শ্রেষ্ঠ না ধরে কোন প্রশ্ন দরকার ঠিক করো।

শেয়ার করা ব্যবহারপথের সিদ্ধান্ত

মেথড ভেতরের পরিবর্তনযোগ্য অবজেক্ট দিলে বাইরের কোড স্টেটের একই অবজেক্টের রেফারেন্স পায়। public অপারেশন দিয়ে সেটি বদলাতে পারে। এটি ইচ্ছাকৃত সহযোগিতা বা এনক্যাপসুলেশনের অনাকাঙ্ক্ষিত ফাঁক হতে পারে। মেথডের প্রতিশ্রুতিতে মালিকানার নীতি বোঝাও।

বাইরের অ্যারে কপি করলেই সব অবজেক্ট কপি হয় না। shallow copy-তে নতুন কনটেইনারের জায়গা হয়, এলিমেন্টের রেফারেন্সের মান থাকে। স্বাধীন পরিবর্তনযোগ্য অবজেক্টের সম্পর্ক চাইলে গভীর কপি লাগতে পারে। সেটা ডিজাইন অনুযায়ী কাজ, সাধারণ অ্যাসাইনমেন্ট নয়।

অপরিবর্তনীয় অবজেক্টে শেয়ার করার ঝুঁকি কমে। অন্য রেফারেন্স স্টেট বদলাতে পারে না। প্রোগ্রামের কয়েকটি অংশের বর্তমান একই অবস্থা দেখা দরকার হলে পরিবর্তনযোগ্য অবজেক্টও দরকারি। শেয়ার বা কপি কোনোটিই সব সময় ভালো নয়। মডেল আর প্রত্যাশিত পরিবর্তন দেখে বেছে নাও।

এতে মনে হয় মেথড বাইরের ভেরিয়েবলে নতুন মান বসাতে পারবে। Java আসলে রেফারেন্সের মান কপি করে। পার্থক্য বোঝাতে ফিল্ড বদলানো আর প্যারামিটারে নতুন রেফারেন্স দেওয়া দুটোই দেখো।

== দিয়ে ভেতরের মান তুলনা

শেয়ার করা লিটারাল বা ক্যাশের মানে পরিচয়ের তুলনা মিলে যেতে পারে। তাতে সেটা মান তুলনার নিয়ম হয় না। উপযুক্ত equals নাও। মেথড কলের রেফারেন্স অনুপস্থিত হতে পারলে null সামলাও।

লোকাল ভেরিয়েবল ছাড়লেই অবজেক্ট শেষ ভাবা

অন্য ফিল্ড, অ্যারের এলিমেন্ট বা লোকাল থেকে অবজেক্টে পৌঁছানো যেতে পারে। অবজেক্ট কতক্ষণ থাকবে, তা একটি ভেরিয়েবলের scope দিয়ে ঠিক হয় না। বন্ধ ব্রেস এলেই Java সঙ্গে সঙ্গে অবজেক্ট ধ্বংস করবে, এমন নিশ্চয়তা নেই।

রেফারেন্সের নিয়মে নতুন কাঠামো লাগে না

Java 17-তেও এখানকার pass-by-value আর পরিচয়ের নিয়ম একই। Objects.equals Java 7 থেকে আছে। পরে আসা pattern matching কপি করা রেফারেন্স আর তার অবজেক্টের পার্থক্য বদলায় না।

ভেরিয়েবল, অবজেক্ট আর প্রতিশ্রুতি আলাদা রাখো

প্রতিটি রেফারেন্সের জন্য তীর আঁকো। স্টেটমেন্ট তীর সরাচ্ছে, নাকি অবজেক্ট বদলাচ্ছে ঠিক করো। null ভেবে সামলাও। ক্লাসের নিয়ম অনুযায়ী সমতা বেছে নাও। এবার টাইপের নাম সাজাতে প্যাকেজ আর ইমপোর্ট শেখো।
