Two arrows can reach one changing object

Imagine two students receiving the same room number. Changing the furniture in that room affects what both visitors see. Changing one student's written room number does not rewrite the other's. Java references behave similarly: copied reference values can reach one shared object.

Aliasing means two or more references identify the same object. It is useful when parts of a program intentionally share state. It becomes surprising when a caller expects an independent copy. The first step is to draw variables and objects as different things.

This lesson combines that memory picture with null and equality. You will distinguish changing an object's field from redirecting a reference. You will also distinguish asking whether two references reach one object from asking whether two objects have equal values.

Declare a reference, then decide its target

A reference variable can hold a reference returned by new, a copy from another variable, or null. null is the special value meaning no object. A local reference still needs definite assignment before it is read.

Cell first = new Cell(5);
Cell alias = first;
Cell missing = null;
boolean identical = first == alias;

The first line creates a Cell. The second copies its reference without constructing another Cell. The third creates no Cell at all. Count allocations rather than declarations when you trace the number of objects.

If you know C, a reference gives you a way to reach shared state, but not raw memory arithmetic. You cannot add one to a Cell reference to find a neighbour. Java also prevents direct manual freeing of an object through its reference.

Mutation moves a value; reassignment moves an arrow

After Cell alias = first:

first -----+
           +----> Cell A { value = 5 }
alias -----+

After alias.value = 8:

first -----+
           +----> Cell A { value = 8 }
alias -----+

After alias = new Cell(9):

first ----------> Cell A { value = 8 }
alias ----------> Cell B { value = 9 }

A field assignment changes storage inside the reached object. Every alias can observe that changed field. Reference assignment changes the variable on the left side, leaving other variables untouched. These are two different kinds of state change.

The same distinction applies to method parameters. Java copies the reference value into the parameter. The callee can mutate the reached object if its interface permits it. Reassigning the parameter changes only that local reference, not the caller variable.

Returning a new object is one way to ask the caller to adopt a replacement. The caller then assigns the returned reference explicitly. That interface makes the rebinding visible instead of pretending a parameter is the caller's variable.

An object without any reachable path from the running program becomes eligible for garbage collection. Setting one alias to null does not make an object unreachable while another live path remains. Collection timing is not guaranteed, so do not use it as an ordinary control-flow event.

Give missing values an explicit meaning

Calling an instance method through null, or reading an instance field through it, throws NullPointerException. The runtime cannot find a receiver object. Comparing a reference with null is safe because the comparison does not access an object's fields.

Check whether null is an allowed state in your design. An optional search result may legitimately be missing. A required Student dependency might be better rejected at construction. Adding checks everywhere without deciding the meaning can hide a deeper modeling error.

Short-circuit conditions are useful guards. In cell != null && cell.value > 0, the right side runs only when the first comparison is true. Reversing the order attempts the field access before the guard can help. The order is part of the safety argument.

A guard should lead to a defined alternative. Printing Missing, returning a documented result or rejecting the operation may all be appropriate. Silently substituting zero is not always correct, because a legitimate zero and a missing value can mean different things.

For content comparisons, a known nonnull literal can be the receiver of equals. Objects.equals offers a more general null-safe comparison of two references. It returns true for two null values, false when exactly one is null, and otherwise delegates to the first object's equals.

Identity and value are different questions

Reference == compares identity: it is true when both references identify the same object, or both are null. It does not inspect fields. Two fresh Cell objects with value 5 therefore have different identities even though their visible numbers match.

Every ordinary class inherits equals from Object unless it overrides the method. The inherited Object.equals also compares identity. Java does not automatically invent field-by-field equality for an ordinary class. The Cell examples deliberately keep that inherited rule visible.

String overrides equals to compare text content. Wrapper classes such as Integer define their own value rules too. Thus a.equals(b) means apply the equality contract of a's class, rather than always compare all fields. Read or define that contract before relying on it.

When you later implement value equality, you must also respect the hashCode contract. Equal objects need equal hash codes for hash-based containers to work correctly. The Object Class teaches a complete implementation. An incomplete custom equals here would distract from the reference model.

The same identity distinction can guide application design. Two records can represent separate events with identical values. Two immutable coordinates may be considered equal by coordinates. Decide which question matters instead of assuming identity or value equality is universally preferable.

Sharing is an interface decision

A method returning a mutable internal object gives the caller an alias into its state. The caller may then mutate that state through public operations. That can be intentional collaboration, or an unwanted hole in encapsulation. Explain the ownership policy in the method contract.

Copying an outer array does not automatically copy all its referenced objects. A shallow copy creates new container storage while preserving element reference values. Independent mutable object graphs may require deeper copying, which is a design-specific operation rather than ordinary assignment.

Immutable objects reduce sharing risks because aliases cannot change their state. Mutable objects remain useful when multiple parts of a program need a common live view. Neither sharing nor copying is always best; the right choice follows the model and expected updates.

Avoid misleading reference explanations

Saying objects are passed by reference

That wording suggests the callee can reassign the caller variable. Java copies reference values instead. Show both a field mutation and a parameter reassignment to distinguish the mechanisms.

Comparing content with ==

Identity comparison can succeed for shared literals or cached values without becoming a content rule. Use the appropriate equals contract for values. Add null handling when the receiver may be missing.

Assuming an abandoned local destroys the object

Another field, array element or local may still reach it. Object lifetime follows reachability, not only the scope of one variable. Java does not guarantee immediate destruction at a closing brace.

Reference rules do not need new syntax

Java 17 uses the same pass-by-value and identity rules illustrated here. Objects.equals has been available since Java 7. Later pattern-matching syntax does not change the distinction between a copied reference and its target object.

Keep variables, targets and contracts separate
