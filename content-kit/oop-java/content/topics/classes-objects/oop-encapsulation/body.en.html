Keep a rule with the state it protects

A marks register should never hold a mark outside its allowed range. Checking the range only on one input screen is fragile. Another caller might update the same data through a different path. Encapsulation keeps state and the operations that protect its rules together.

Imagine a desk accepting correction requests. Callers can ask for a change, but cannot quietly overwrite the official register. The desk checks each request before changing the record. A class can follow the same idea through private state and carefully selected methods.

An invariant is a condition that should remain true for a usable object. For Result, the mark stays between zero and one hundred. Encapsulation helps preserve that invariant after construction and after each permitted operation. Merely placing fields in a class does not preserve anything by itself.

A setter is an operation with a policy

A getter exposes a value or view. A setter requests a state change. Neither should be added automatically to every field. A good interface offers the operations callers need and rejects changes the model does not allow.

public boolean setMark(int proposed) {
    if (proposed < 0 || proposed > 100) {
        return false;
    }
    mark = proposed;
    return true;
}

This setter validates before assignment. A failed request returns false and leaves the old state intact. That is a clear failure policy. Another design might throw an exception, but the caller must understand whichever policy the interface chooses.

The getter may return the mark as a primitive int. A caller receives a copied number, so changing its local variable cannot rewrite the private field. Returning mutable objects requires more care because the copied reference may still reach internal state.

old valid state remains on the rejected path

An operation changes an object from one valid state to another. Check everything needed before committing the change. If you partly update several fields and then discover an error, the object can be left inconsistent. Small interfaces make these transitions easier to reason about.

For a seat pool, reserve is more meaningful than setRemaining. A reservation reduces available seats by one only when a seat exists. Callers cannot arbitrarily increase or make the count negative. The operation expresses the domain action rather than a storage assignment.

For a wallet, withdraw checks a positive amount and sufficient balance before subtracting. The old balance remains after rejection. A public setBalance method would allow callers to bypass the meaning of deposit and withdrawal. Encapsulation is strongest when operations describe legitimate actions.

Sometimes the safest update is no update

An immutable object exposes no way to change its observable state after construction. A coordinate or course code can often be a stable value. To represent another coordinate, create another object instead of changing the old one. Sharing the old value then becomes easier to reason about.

For a simple immutable Point, make the class final, keep primitive fields private and final, set them in the constructor, and provide read operations only. final on the class prevents a subclass from adding surprising mutable behaviour. It does not alone prove that the class itself is immutable.

final on a field prevents assigning that field again after its permitted initialization. For primitive fields, that fixes the stored value. For a reference field, it fixes the reference while the target may still change. A final int array can still have its elements edited.

Immutability therefore requires thinking through the entire reachable state. String fields are useful because String objects are already immutable. A field holding a mutable list, array or object needs a different policy. You must avoid both direct mutation and outside aliases that can mutate it.

An immutable design can make failed updates irrelevant: no operation attempts to update existing state. That is valuable for values shared across calculations. Mutable objects remain appropriate when their identity represents something that changes over time, such as a live seat pool.

Protect mutable boundaries with copies

A defensive copy prevents an outside reference from reaching storage that should remain private. If a constructor receives an int array and stores it directly, the caller still holds an alias. The caller can then edit the class state without any setter.

Copy the incoming array before storing it. An int array clone gives a new array with the same primitive values. Later edits to the caller array do not reach that new array. Copying on construction protects only the incoming boundary, however.

A getter returning the stored array would create a new outside alias. Return another copy when callers need a snapshot of the values. Alternatively, expose individual derived results such as first or total rather than the full container. Choose the smallest useful view.

For an array of object references, cloning copies references rather than the referenced objects. Mutable elements may therefore remain shared. The correct copying depth depends on the element types and the promised interface. Never claim deep immutability merely because the outer array was cloned.

Copying has a cost proportional to the number of elements copied. That cost may be reasonable when it preserves an important contract. Avoid unnecessary snapshots in a tight loop by choosing a better interface, while keeping ownership and mutation rules explicit.

Hide representation so the implementation can evolve

Information hiding means callers depend on useful behaviour rather than storage choices. A seat pool might later compute availability from several internal counters. If callers only use reserve and remaining, that internal change can preserve the public contract. A getter named getArray returning the live storage creates a strong dependence on representation. A method named totalMarks gives a result with meaning and more implementation freedom. This does not mean all getters are bad. It means their promises should be chosen consciously. Encapsulation also improves testing and review. You can list the state transitions exposed by the interface and check each invariant around them. If callers can mutate every field, there may be too many uncontrolled routes to inspect reliably.

Avoid holes in the boundary

Saving before checking

If setMark writes first and rejects later without restoring state, the invalid mark remains. Check the proposed value before assignment. A false return should match the documented state guarantee.

Generating setters for immutable identity

A roll or record identifier may be fixed for the life of an object. Adding a setter only because a field exists can create unwanted transitions. Decide what changing that identity would mean.

Returning a private array directly

Private controls access to the field name, not edits through a reference already returned. A caller holding that array can write elements. Return a safe copy or a narrower observation instead.

Immutability does not require a record

The designs here use ordinary Java 17 classes with explicit constructors. Records became permanent in Java 16 and appear later in the track. Their concise syntax also does not automatically make mutable component objects deeply immutable.
