Decide which doors a class should open

A classroom register may be readable by several staff members, while corrections follow a smaller set of permitted actions. A class also needs different levels of access. An access modifier controls where a declaration can be used in source code.

Think of a class interface as a set of doors. Public operations are doors intended for callers. Private fields sit behind them so the class can control changes. Opening every door makes a short demonstration convenient, but makes a growing system harder to protect.

Java provides public, protected and private keywords. Omitting an access modifier gives package-private access. These choices describe source-level visibility, not encryption or a complete security boundary. Choose them to express a design that callers can understand and maintain.

Put visibility on the declaration

An access modifier comes before the field, constructor or method declaration. The same spelling can have different consequences depending on the member and its enclosing type. A package groups related types under a shared name; Packages and Imports explains its folders and compilation.

class Account {
    private int balance;
    public int getBalance() {
        return balance;
    }
    public boolean deposit(int amount) {
        // Validate before changing balance.
        return false;
    }
}

The separate top-level Main class cannot directly name Account's private balance field. Main can call an accessible getter instead. A private member is also accessible within the enclosing top-level class's nest, including its nested classes. Nested-class rules are explained later; private does not mean only one method can read the field.

Package-private has no keyword. A declaration such as int room; can be used by eligible code in the same package. Do not write default before an ordinary field as an access modifier. The default keyword has other Java uses.

The table assumes the declaring type is itself accessible. A public method does not make a package-private top-level class globally accessible. Public access is also subject to module accessibility in modular applications, which are beyond this package-level introduction.

A top-level class can be public or package-private. It cannot be private or protected. A nested type is a member and has additional choices. Keep these two declaration positions separate when answering a visibility question.

Constructors also have access levels. A public class with a private constructor cannot be directly constructed by arbitrary outside code. This can be deliberate, as with a utility class whose useful work is static. Access to the type and access to constructing it are separate questions.

Protected is not a synonym for public

A subclass is a class derived from another class, introduced fully in Inheritance. protected members are accessible to types in the same package. Across packages, access is permitted through subclass code under more specific rules.

For a protected instance member accessed from a subclass in another package, the receiver must meet the subclass-type restriction. Suppose Child extends Parent. Inside Child, using this.value can be legal, and access through a Child reference can be legal. Access through an arbitrary Parent reference is not generally allowed there.

That restriction prevents a subclass from becoming a universal doorway into every Parent instance. Being a subclass gives access for implementing that subclass, rather than permission to inspect unrelated parent objects everywhere. Static protected members have no instance receiver but still require the right access context.

A folder diagram can clarify the situation. Put Parent in campus.base and Child in campus.special. A third unrelated type in campus.other does not gain access by importing Parent. An import resolves a name; it never grants permission to a member.

Why a field should usually be private

A public balance field allows every caller to store a negative value. You cannot later guarantee that deposits and withdrawals pass through validation if some callers write directly. Private state gives operations a chance to enforce one consistent rule.

A getter is not required for every private field. Some values are implementation details that callers should never see. A method such as reserve may answer a caller's need without exposing the internal counter. Start from the actions the class supports, then choose the data it must reveal.

Smaller visibility also limits the number of callers that depend on a declaration. A private helper can be renamed or reorganised with fewer outside consequences. A public API creates a stronger promise to other code, so make that promise deliberately.

Visibility does not replace validation. A public method can still store an invalid value if its implementation permits it. Private fields create the boundary; carefully designed operations protect the state inside that boundary.

Check names, types and context separately

Assuming an import opens private members

An import only lets you use a shorter type or static member name. The compiler still performs access checks. Use a permitted operation rather than trying another import spelling.

Making fields protected to prepare for every future subclass

Protected state exposes representation to subclass implementations. Those subclasses can then depend on details you hoped to change. Prefer private state and focused methods unless a concrete inheritance design needs wider access.

Calling all omitted modifiers public

For an ordinary class member, omission means package-private. Some declaration contexts, such as interface members, have special implicit rules. Read the declaration's context rather than relying on one memorised default.

Using access as a password mechanism

Source access checks help structure programs. They are not a substitute for user authentication, permissions or data protection in an application. Keep the purpose of the language feature clear.

Visibility under the Java 17 model

The access levels described here apply to ordinary Java 17 classes. Modern private access includes nested types in one top-level nest. Named modules add another layer for public package accessibility, but do not turn private fields into public state.
