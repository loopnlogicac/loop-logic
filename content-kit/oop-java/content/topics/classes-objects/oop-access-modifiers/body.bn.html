ক্লাসের কোন দরজা খোলা থাকবে ঠিক করো

ক্লাসের রেজিস্টার কয়েকজন কর্মী পড়তে পারেন। কিন্তু সংশোধন করতে হলে নির্দিষ্ট কিছু কাজের অনুমতি লাগে। ক্লাসের ডেটা ব্যবহারেরও এমন আলাদা স্তর দরকার। সোর্স কোডের কোথা থেকে কোনো ঘোষণা ব্যবহার করা যাবে, অ্যাক্সেস মডিফায়ার তা ঠিক করে।

ক্লাসের ব্যবহারপথকে কয়েকটি দরজা ভাবো। public অপারেশন হলো অন্য কোডের জন্য খোলা দরজা। private ফিল্ড ভেতরে থাকে, যাতে ক্লাস পরিবর্তন নিয়ন্ত্রণ করতে পারে। ছোট উদাহরণে সব দরজা খুলে রাখা সুবিধার। কিন্তু সিস্টেম বড় হলে নিয়ম রক্ষা করা কঠিন হয়।

Java-তে public, protected আর private কিওয়ার্ড আছে। অ্যাক্সেস মডিফায়ার না লিখলে package-private অ্যাক্সেস হয়। এগুলো সোর্স কোডে ব্যবহারের সীমা বোঝায়। এনক্রিপশন বা নিরাপত্তার পুরো ব্যবস্থা নয়। অন্য কোড যেন ডিজাইন বুঝতে আর ধরে রাখতে পারে, সে অনুযায়ী বেছে নাও।

ঘোষণার সঙ্গে অ্যাক্সেস লিখো

ফিল্ড, কনস্ট্রাক্টর বা মেথডের ঘোষণার আগে অ্যাক্সেস মডিফায়ার থাকে। কোন মেম্বার আর কোন টাইপের ভেতরে আছে, তার ওপর একই মডিফায়ারের ফল আলাদা হতে পারে। প্যাকেজ সম্পর্কিত টাইপগুলোকে একটি নামে রাখে। প্যাকেজ আর ইমপোর্টে ফোল্ডার আর কম্পাইলের নিয়ম শিখবে।

class Account {
    private int balance;
    public int getBalance() {
        return balance;
    }
    public boolean deposit(int amount) {
        // Validate before changing balance.
        return false;
    }
}

আলাদা top-level Main ক্লাস Account-এর private balance ফিল্ড সরাসরি ব্যবহার করতে পারবে না। অনুমতি থাকা গেটার কল করতে পারবে। যে top-level ক্লাসের ভেতরে private মেম্বার, তার একই nest-এর nested ক্লাস থেকেও সেটি ব্যবহার করা যায়। nested ক্লাস পরে শিখবে। private মানে শুধু একটি মেথডই পড়তে পারবে, তা নয়।

package-private-এর কোনো কিওয়ার্ড নেই। int room;-এর মতো ঘোষণা একই প্যাকেজের উপযুক্ত কোড ব্যবহার করতে পারে। সাধারণ ফিল্ডের আগে অ্যাক্সেস বোঝাতে default লিখবে না। Java-তে default-এর অন্য কাজ আছে।

অ্যাক্সেসের টেবিল শর্তসহ পড়ো

সাধারণ মেম্বার কোথা থেকে ব্যবহার করা যায়
অ্যাক্সেসএকই top-level nestএকই প্যাকেজের অন্য টাইপঅন্য প্যাকেজের সাবক্লাসঅন্য প্যাকেজের সম্পর্কহীন টাইপ
privateহ্যাঁনানানা
package-privateহ্যাঁহ্যাঁনানা
protectedহ্যাঁহ্যাঁহ্যাঁ, কিছু শর্তেনা
publicহ্যাঁহ্যাঁহ্যাঁহ্যাঁ

টেবিলে ধরা হয়েছে, মেম্বার যে টাইপে ঘোষণা করা আছে, সেই টাইপও ব্যবহার করা যাচ্ছে। package-private top-level ক্লাসে public মেথড দিলেই ক্লাস সবার জন্য খুলে যায় না। মডিউলভিত্তিক অ্যাপ্লিকেশনে public অ্যাক্সেসের ওপর মডিউলের শর্তও থাকে। প্যাকেজের এই শুরুর পাঠে সেটার বিস্তারিত নেই।

top-level ক্লাস public বা package-private হতে পারে। private বা protected হতে পারে না। nested টাইপ নিজে একটি মেম্বার, তাই তার বাড়তি সুযোগ আছে। অ্যাক্সেসের প্রশ্নে এই দুই অবস্থানের ঘোষণা আলাদা রাখো।

কনস্ট্রাক্টরেরও অ্যাক্সেসের স্তর আছে। public ক্লাসের কনস্ট্রাক্টর private হলে ইচ্ছেমতো বাইরের কোড সেটি দিয়ে অবজেক্ট বানাতে পারবে না। এটি ইচ্ছাকৃত হতে পারে। যেমন, static কাজ করা utility ক্লাস। টাইপ ব্যবহার করা আর সেটি দিয়ে অবজেক্ট বানানোর অনুমতি আলাদা প্রশ্ন।

+--------------------------+
| Account                  |
+--------------------------+
| - balance: int           |
+--------------------------+
| + deposit(amount): boolean  |
| + getBalance(): int      |
+--------------------------+
কল করা কোড --> public অপারেশন --> private স্টেট

UML-এর ক্লাস বাক্সে প্লাস public, মাইনাস private, হ্যাশ protected আর টিল্ডা প্যাকেজ অ্যাক্সেস বোঝায়। মেথডের বডি না দেখিয়েও ডায়াগ্রামে ব্যবহারপথ দেখা যায়। প্রতিটি প্রস্তাবিত দরজা অন্য কোডের আসলেই দরকার কি না, এটা দিয়ে যাচাই করো।

অনুমতি থাকা কাজগুলো ব্যবহারযোগ্য রাখো

Account-এর উদাহরণে public অপারেশন দিয়ে private স্টেট পড়া আর অবৈধ পরিবর্তন ফেরানো আছে। Lab-এ একই নামহীন প্যাকেজের অ্যাক্সেস দেখবে। Counter নিজের স্টেট আড়াল করে দরকারি কাজের ছোট ব্যবহারপথ দেয়।

মেথড দিয়ে private স্টেট পড়া

আলাদা top-level Account-এর private balance ফিল্ড Main সরাসরি ব্যবহার করতে পারে না। getBalance অনুমোদিতভাবে মান পড়ে দেয়।

অবৈধ জমা প্রত্যাখ্যান

public অপারেশন private স্টেট বদলানোর আগেই false দেয়। তাই balance শূন্য থাকে।

একই নামহীন প্যাকেজে অ্যাক্সেস

কোনো ক্লাসেই package ঘোষণা নেই। দুটি টাইপ একই নামহীন প্যাকেজে থাকায় package-private ফিল্ড ব্যবহার করা যায়।

package-private ক্লাসে public মেথড

গণনার মান আড়াল করা আছে। ক্লাসের প্যাকেজ অ্যাক্সেস আছে। ক্লাস ব্যবহার করতে পারে এমন কোডের জন্য মেথডগুলো ব্যবহারপথ তৈরি করে।

protected আর public এক কথা নয়

অন্য ক্লাস থেকে তৈরি ক্লাস হলো সাবক্লাস। ইনহেরিট্যান্সে পুরোটা শিখবে। একই প্যাকেজের টাইপগুলো protected মেম্বার ব্যবহার করতে পারে। অন্য প্যাকেজে সাবক্লাসের কোড থেকে আরও নির্দিষ্ট শর্তে ব্যবহার করা যায়।

অন্য প্যাকেজের সাবক্লাস থেকে protected ইনস্ট্যান্স মেম্বার ব্যবহার করলে যে রেফারেন্স দিয়ে ব্যবহার করছ, তার টাইপেও সাবক্লাসের শর্ত মানতে হয়। ধরো, Child, Parent-কে extend করে। Child-এর ভেতরে this.value বৈধ হতে পারে। Child রেফারেন্স দিয়েও বৈধ হতে পারে। কিন্তু যেকোনো Parent রেফারেন্স দিয়ে সাধারণভাবে সেই অনুমতি নেই।

এই শর্তে সাবক্লাস সব Parent ইনস্ট্যান্সের ভেতরে ঢোকার দরজা হয়ে যায় না। সাবক্লাস হওয়ার অনুমতি তার নিজের বাস্তবায়নের জন্য। সম্পর্কহীন সব প্যারেন্ট অবজেক্ট পরীক্ষা করার ছাড়পত্র নয়। static protected মেম্বারে ইনস্ট্যান্স রেফারেন্স লাগে না। তবুও সঠিক অ্যাক্সেসের প্রসঙ্গ লাগবে।

ফোল্ডারের ছবি দিয়ে ভাবতে পারো। Parent রাখো campus.base-এ, Child রাখো campus.special-এ। campus.other-এর সম্পর্কহীন তৃতীয় টাইপ Parent ইমপোর্ট করলেই অ্যাক্সেস পায় না। ইমপোর্ট নাম চিনতে সাহায্য করে; মেম্বারের অনুমতি দেয় না।

এখানকার চলমান উদাহরণে ক্লাসগুলো একই নামহীন প্যাকেজে আছে। একাধিক সোর্স ফাইল ছাড়াই private, public আর প্যাকেজ অ্যাক্সেস দেখায়। প্যাকেজের বাইরে protected বুঝতে টেবিল আর আলাদা প্যাকেজের চিন্তার উদাহরণ ব্যবহার করো।

ফিল্ড সাধারণত private কেন রাখবে

balance public হলে যেকোনো কোড ঋণাত্মক মান রাখতে পারে। কেউ সরাসরি লিখলে জমা আর উত্তোলন সব সময় যাচাইয়ের ভেতর দিয়ে যাবে, এমন নিশ্চয়তা দিতে পারবে না। private স্টেট থাকলে অপারেশন একটি নির্দিষ্ট নিয়ম মানানোর সুযোগ পায়।

প্রতিটি private ফিল্ডের গেটার লাগবে না। কিছু মান ভেতরের বাস্তবায়নের অংশ; অন্য কোডের দেখা দরকার নেই। reserve-এর মতো মেথড ভেতরের কাউন্টার না দেখিয়েও চাহিদা মেটাতে পারে। আগে ক্লাস কী কাজ দেবে ভাবো, তারপর কোন ডেটা দেখাতে হবে ঠিক করো।

অ্যাক্সেস ছোট রাখলে ওই ঘোষণার ওপর নির্ভর করা কোডও কমে। private সহায়ক মেথডের নাম বা গঠন বদলালে বাইরের প্রভাব কম হয়। public API অন্য কোডের কাছে বড় প্রতিশ্রুতি। তাই ভেবেই সেটা দাও।

অ্যাক্সেস দিয়ে যাচাইয়ের কাজ হয় না। public মেথডের কোড চাইলে অবৈধ মানও রাখতে পারে। private ফিল্ড সীমানা তৈরি করে। ভালোভাবে ডিজাইন করা অপারেশন সেই সীমানার ভেতরের স্টেট রক্ষা করে।

নাম, টাইপ আর ব্যবহারের জায়গা আলাদা করে দেখো

ইমপোর্ট করলে private মেম্বার খুলবে ভাবা

ইমপোর্ট শুধু টাইপ বা static মেম্বারের ছোট নাম লিখতে দেয়। কম্পাইলার অ্যাক্সেস ঠিকই চেক করে। ইমপোর্টের বানান পাল্টানোর বদলে অনুমোদিত অপারেশন নাও।

ভবিষ্যতের সব সাবক্লাসের জন্য ফিল্ড protected করা

protected স্টেট দিয়ে সাবক্লাসকে ডেটা রাখার খুঁটিনাটি দেখিয়ে দাও। পরে বদলাতে চাওয়া তথ্যের ওপর সাবক্লাস নির্ভর করতে পারে। নির্দিষ্ট ইনহেরিট্যান্স ডিজাইনে দরকার না হলে private স্টেট আর নির্দিষ্ট কাজের মেথড পছন্দ করো।

মডিফায়ার না থাকলেই public বলা

সাধারণ ক্লাস মেম্বারে না লিখলে package-private হয়। কিছু প্রসঙ্গে, যেমন interface মেম্বারে, নিজস্ব অন্তর্নিহিত নিয়ম আছে। একটি ডিফল্ট মুখস্থ না করে কোথায় ঘোষণা আছে পড়ো।

অ্যাক্সেসকে পাসওয়ার্ডের ব্যবস্থা ভাবা

সোর্সের অ্যাক্সেস চেক প্রোগ্রামের গঠন ঠিক রাখতে সাহায্য করে। অ্যাপ্লিকেশনে ব্যবহারকারীর পরিচয় যাচাই, অনুমতি বা ডেটা সুরক্ষার বিকল্প নয়। ভাষার ফিচারটি কী কাজে এসেছে, পরিষ্কার রাখো।

এখানকার স্তরগুলো Java 17-এর সাধারণ ক্লাসে প্রযোজ্য। আধুনিক private অ্যাক্সেসে একই top-level nest-এর nested টাইপও পড়ে। named module public প্যাকেজ ব্যবহারে আরেক স্তর যোগ করে। তাতে private ফিল্ড public হয় না।

দরকারি সবচেয়ে ছোট ব্যবহারপথ খোলো

কোন কোডকে সাহায্য করতে ঘোষণা দিয়েছ, সেই অনুযায়ী অ্যাক্সেস নাও। মেম্বারের অনুমতি বোঝার আগে তার টাইপ, প্যাকেজ আর সাবক্লাসের প্রসঙ্গ দেখো। এরপর এই সীমানায় অর্থপূর্ণ নিয়ম রক্ষা করতে এনক্যাপসুলেশন শেখো।
