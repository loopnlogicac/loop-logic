Turn an action into a model request

A calculator button does not calculate by itself. It announces an action to registered listeners. A listener is an object whose callback receives that notification. The callback translates the action into a request and decides how to display the result.

A button can be activated by more than a mouse click, including keyboard interaction. ActionListener represents the button’s action meaning rather than raw mouse movement. Choose the highest-level event that matches what the user intends.

A useful calculator separates three roles. The view holds fields, buttons and labels. The model owns arithmetic rules. The controller reads field text, calls the model and chooses a message. Small applications may put controller code in a setup helper, but the responsibilities can still stay distinct.

Keeping numeric rules outside the view makes them usable in a console program and easier to inspect. It also keeps Swing event-thread requirements away from arithmetic code that needs no graphical display.

Register a named listener or a lambda

button.addActionListener(listener);
button.addActionListener(event -> performRequest());

The first form supplies an object implementing ActionListener. Its required operation is public void actionPerformed(ActionEvent event). The second form supplies the same functional contract with a lambda. Registration stores the listener for later notification; it does not invoke the application action immediately.

ActionEvent describes the event and its source. A controller can inspect it when several sources share one listener. For a small calculator, separate callbacks or a captured operation name can be clearer than a long chain of source comparisons.

Named listener classes are useful for reusable behavior, explicit state and several helper methods. Lambdas work well for short actions close to their setup. Both approaches run under the event source’s invocation rules; a lambda does not automatically start a background thread.

Follow a request across three boundaries

JTextField text --> controller parse --> int values
int values --> Calculator operation --> result or failure
result or failure --> controller message --> JLabel

The controller first reads both fields and trims surrounding spaces according to this calculator’s input rule. Integer.parseInt converts each String to int. A conversion failure means the model never receives a valid numeric request.

The model then applies the operation. add uses Math.addExact so overflow becomes a visible failure rather than silent wraparound. divide rejects zero and the MIN_VALUE divided by minus one overflow case. Ordinary integer division truncates toward zero.

Finally, the controller maps an accepted result or expected failure into status text. NumberFormatException is distinct from ArithmeticException, so bad input and an impossible calculation can have different messages. Neither failure should fall through into a success message.

All short field reads and label changes happen in the event callback on the EDT. The model contains no Swing imports and has no need to know which thread owns the interface. If arithmetic becomes a long-running task, move its execution to a worker and return the result to the EDT.

Give every rule one home

The model should not decide button positions, label colors or dialog wording. Those are presentation choices. The controller should not duplicate arithmetic checks already owned by the model; otherwise a console client could accidentally follow different rules.

The model can throw a meaningful domain failure or return a structured result. The controller translates that outcome into a user message. For this small application, existing numeric exception types are enough. A larger application may prefer named result types for expected validation failures.

A view can expose getters for user input and methods for displaying a result, keeping Swing fields private. A separate controller can then depend on those operations rather than knowing every layout detail. Avoid exposing every component publicly just to connect classes.

Not every three-role design requires three large classes. A small view-building helper and a numeric model can be clear. Split further when the responsibilities become hard to navigate or need reuse. The goal is to make dependencies explainable, not to maximize file count.

Register once and define an end

Listener registration and listener invocation are different moments. Adding another listener inside every click usually accumulates callbacks. One later action can then update the count several times. Register stable callbacks during setup and change explicit controller state when behavior changes.

When replacing a listener, retain the old listener reference so removeActionListener can remove the intended object. Two newly created lambdas are not a reliable way to identify the same registration. Store a handle when the lifecycle requires later unregistration.

A long-lived publisher may retain its listeners and any objects they capture. Closing a view does not automatically unregister it from every external publisher. The owner of the subscription should release it when the view no longer needs events.

When an action starts background work, decide what repeated activation means. You may disable the button, cancel an earlier task or allow multiple independent requests. Also decide what happens if the window closes before the result arrives. Lifecycle rules prevent stale updates and hidden retained objects.

Keep callbacks short without losing correctness

The event thread processes events sequentially. A slow listener delays repainting and later input. Thread.sleep inside a listener does not create a pause that leaves the rest of the interface active. It blocks that same event thread.

SwingWorker offers a background doInBackground operation and an event-thread done completion callback. A completion handler can retrieve a result, handle failure and update the view. Ordinary worker threads can instead queue a small UI change through SwingUtilities.invokeLater.

Moving work to a background thread introduces shared-state concerns. Copy the request values before starting the worker rather than repeatedly reading fields from it. Return an immutable result where possible. The user may edit the fields while work is running, so the request needs a defined snapshot.

Keep rejected requests visibly rejected

Catching every exception as bad input

A broad catch can disguise a programming error as a user typo. Catch expected conversion and arithmetic failures narrowly. Preserve unexpected causes for diagnosis rather than treating every failure as ordinary validation.

Allowing silent numeric wraparound

Plain int addition can overflow. Math.addExact reports that situation so the controller can display a useful message. An int calculator must also state that it performs integer division, not decimal division.

Putting components inside the model

A Calculator method that reads JTextField cannot be used independently of Swing. Accept numeric arguments and return numeric results. Let the controller own text conversion and the view own display.

Test the request path and inspect the view

  • Exercise valid, blank, malformed, zero-divisor and overflow inputs.
  • Register each intended callback once.
  • Keep arithmetic rules free of view dependencies.
  • Use background work for slow operations and return UI updates to the EDT.
  • Define subscription and window-close lifetimes explicitly.

Callbacks and Java 17

ActionListener predates lambdas, so a named implementation works across older Java versions. Lambdas need Java 8 or later. Math.addExact is also available from Java 8. The examples use Java 17 and require no preview features or deprecated event APIs.

Make the action boundary clear

Listeners receive actions, controllers translate requests, and models enforce numeric rules. Keep callbacks short and make failures visible. Apply these ideas in the library project and review method behavior in the exam questions.
