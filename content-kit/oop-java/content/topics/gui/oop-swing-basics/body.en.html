Build a window from cooperating components

A console asks for one line at a time. A graphical form keeps labels, fields and buttons visible together. Swing is Java’s desktop GUI toolkit. It lets you describe components and their relationships while the window system handles drawing and user input.

A course-entry form needs a window, a place to group controls, a label, a text field and a button. These are separate objects with separate responsibilities. Building the interface means composing those objects into a hierarchy, then arranging them with layout rules.

A graphical program also has a different execution rhythm. Main schedules setup and returns. The application then responds to events such as button actions and window closing. Avoid treating the interface as a loop that repeatedly asks every button whether it was clicked.

Swing needs a graphical desktop to display windows. The window examples are intended for a local desktop JDK. Their behavior is described visually because typing and clicking determine the results; there is no fixed console printout.

This call queues setup on the event dispatch thread, often called the EDT. show is a static helper in these programs. It creates the frame and controls, installs the component hierarchy, packs it and makes it visible. invokeLater does not block main until the user closes the window.

Import each used Swing and AWT class explicitly. Swing components live in javax.swing, while layout managers such as BorderLayout live in java.awt. Similar names in different packages can otherwise become confusing.

A container owns a hierarchy of child components. Its layout manager determines their positions and sizes. Instead of choosing fixed pixel coordinates for every control, you describe a policy that can respond to window resizing and different font metrics.

pack computes a suitable initial window size from the preferred sizes of the component hierarchy. A text field’s column count contributes to preferred width; it is not a maximum input length. Input-length validation is a separate application rule.

Set the close policy before showing the frame. DISPOSE_ON_CLOSE releases that frame’s native resources when it closes. EXIT_ON_CLOSE requests application termination, which may be inappropriate in an application with other windows or background work. HIDE_ON_CLOSE hides a frame without disposing it.

A component normally has one parent container at a time. Adding the same label to another panel moves it rather than duplicating it. Create separate label instances when the same text must appear in two places.

The search window uses BorderLayout for heading, form and button. Its form panel uses GridLayout with two rows and two columns. Nested panels let each container solve one arrangement problem. Resize the window and observe how the form cells share space.

Make one short UI update

The greeting example installs a lambda action listener. Clicking Greet reads the field and sets the label text. That callback is short and runs on the event thread. It previews the event-handling model without introducing slow work or arithmetic validation.

Choose a policy instead of coordinates

FlowLayout works well for a small group of buttons or compact controls. It keeps preferred sizes and lays out a row, wrapping when needed. It is a JPanel’s default layout, but specifying it can make the design intent clearer.

BorderLayout divides a container into NORTH, SOUTH, EAST, WEST and CENTER. Each region holds one direct component, often another panel. The center takes remaining space. Adding several unrelated components to the same region does not create the multi-control region you intended; nest a panel there.

GridLayout makes equal-sized cells. It is useful when uniform sizing is acceptable. A label and a long field may not deserve equal width in a polished form, so more flexible managers such as GridBagLayout can be considered later. Choose the simplest policy that expresses the actual design.

A null layout requires manual bounds for every component. Fixed coordinates often fail when fonts, screen scaling, window size or translated text change. Layout managers adapt to those conditions. A window that looks acceptable at one resolution is not enough evidence for a coordinate-based design.

When rows is nonzero, GridLayout derives its effective columns from the number of components and rows. The grid-capacity exercise models a planned fully populated rectangle; it does not claim that any arbitrary component count will preserve both configured dimensions.

Keep the event queue moving

The event thread handles ordinary Swing component work, including callbacks and repaint requests. Create and update those components there unless the API explicitly documents an operation as thread-safe. Main is a different thread; invokeLater transfers setup to the correct place.

A callback that sleeps or reads a large file blocks the event queue. The window may stop repainting and appear frozen even though the program is still working. Use a background mechanism such as SwingWorker for slow tasks, then update the interface from its event-thread completion path.

Queue order is not a reason to put expensive calculations into invokeLater. That method selects a thread; it does not make the task cheap. Keep queued UI operations focused on creating, reading or updating the visible state.

Share model results rather than letting background code reach into arbitrary controls. This makes ownership clearer and avoids race-prone component access. The next lesson separates a calculator’s numeric rules from its fields and buttons.

Separate text rules from display setup

A text field supplies a String, which may be blank or contain unexpected spaces. Decide whether trimming is appropriate for each field. A room code may ignore surrounding spaces, while a password or exact text entry may preserve them. The visual component does not decide that policy.

The console practice exercises isolate small rules from the graphical display. They check planned cell capacity and a required room label. Those rules can be called from a listener later, and they can be tried without opening a window. They do not replace visual inspection of resizing, focus and label readability.

When a label changes to longer text, layout may need to accommodate the result. A real interface can reserve space or update its layout deliberately. Do not respond by repeatedly packing the frame after every keystroke without considering how that affects the user’s window size.

Avoid hidden lifecycle assumptions

Showing the frame before adding controls

Build the initial hierarchy first, then pack and show it. Adding controls afterward can require revalidation and repainting. Clear setup order makes the first visible frame consistent.

Assuming every close should exit the JVM

A child window may close while the rest of the application continues. Choose dispose, hide or exit according to ownership. Disposing a window does not automatically cancel unrelated worker tasks.

Extending JFrame without a design need

Often a helper method that constructs a JFrame is enough. Composition keeps application state separate from a framework superclass. Subclass only when specialization is useful, not merely because an example needs a window.

Review the interface by using it

  • Launch setup through the event dispatch thread.
  • Resize each form and inspect long labels.
  • Use nested panels for independent layout regions.
  • Choose a close policy that fits the application lifetime.
  • Keep business rules callable without Swing components.

Desktop requirements for Java 17

Swing is provided by the java.desktop module in Java 17. These unnamed-package examples need no module declaration. A full desktop JDK and graphical session are required to show their windows; a headless process can compile the source but cannot display a JFrame.
