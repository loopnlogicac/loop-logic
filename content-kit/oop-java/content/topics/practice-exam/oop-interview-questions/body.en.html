Answer with a rule and a small example

An interview asks whether you can explain a choice, not only repeat a definition. Start with one plain distinction, then give a tiny example. If asked about final, separate variable reassignment from object mutation. If asked about polymorphism, name the selected method and the runtime receiver.

The fifty short answers cover the OOP pillars, Java-specific rules and practical design decisions. Read one question, answer aloud, and then compare the contract in your answer with the worked answer. Add a counterexample when it helps expose an assumption.

Make claims narrow enough to defend

Avoid absolute claims such as HashMap is ordered or final means immutable. Identify the exact promise. HashMap has no fixed iteration-order contract; a final reference cannot be rebound. These statements remain true even when a small demonstration happens to suggest something else.

For equality, distinguish identity, value equality and hashing. Give a pair of equal value objects and explain their matching hashes. Then mention that unequal values may collide. For inheritance, explain why a subtype can replace a parent for valid calls. Shared fields alone do not prove that relationship.

When a question asks about performance, specify the operation and assumptions. ArrayList indexed reads are constant time; inserting at the front shifts references. Hash lookup is typically efficient with suitable keys, while ordered trees give logarithmic operations and sorted traversal. A class name by itself is not a performance argument.

Connect the answer to a changing requirement

For a library model, compare an interface that expresses borrowing with a superclass that shares id and title. A reference-only item should not promise borrowing merely to reuse fields. A TextStore should own file parsing, while a Library owns lending rules. This gives you concrete reasons for boundaries.

For dependency inversion, identify the policy, the detail and the abstraction. A notification policy can depend on a Sink interface and receive an implementation. Explain the cost too: an interface adds a type and indirection. Use it where changing destinations or isolating behaviour makes that cost worthwhile.

For concurrency, describe shared state and the completion protocol before proposing threads. For Swing, name the EDT ownership rule and keep the model independent. For file loading, say when validation commits. These details show that a design remains correct outside the happy path.

Use the traces as follow-up questions

After each short answer, try an output trace that challenges it. Does a parameter assignment change the caller? Does final stop a list addition? Does a record compare by components while reference identity remains different? Predict before running, and explain the exact rule behind the result.

If you do not know a version-specific feature, say which baseline you are using. Records are standard from Java 16, sealed classes from Java 17, and virtual threads come later. A precise boundary is more useful than claiming that every feature in a current tutorial works on Java 17.

Explain behaviour and tradeoffs in your own words

Keep each answer short enough to say clearly, but include the condition that makes it correct. Use a diagram or two-line trace when prose becomes vague. Revisit the library project and defend one design choice at a time using these questions.
