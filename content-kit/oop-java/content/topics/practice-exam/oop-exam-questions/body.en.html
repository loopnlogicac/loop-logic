Practise reasoning under a time limit

An OOP exam often combines definitions, output tracing and a small design or program. Each asks for a different kind of evidence. A definition needs a precise distinction. A trace needs ordered decisions. A design needs responsibilities and rules that survive operations.

Use this bank in two passes. First answer without executing code. Then compare your reasoning with the worked answer and run the executable quiz traces. A correct guess is less useful than a clear explanation of why another plausible output cannot occur.

The short and long questions fit midterm topics such as objects, constructors and encapsulation. Later questions combine dispatch, collections, exceptions and concurrency for final preparation. Marks indicate the expected depth, not a rule that every answer needs the same number of sentences.

Resolve a call in a fixed order

  1. Check whether names, access and argument types make the code legal.
  2. Record the declared type of each reference expression.
  3. Record the actual class of each constructed object.
  4. Choose the overloaded signature using compile-time information.
  5. For an overridable instance method, follow the runtime receiver to its implementation.
  6. Execute that body and record each printed character or line.

Fields and static methods do not follow instance-method dispatch. A cast may change the compile-time view without changing the object. Assigning one reference to another creates an alias, not an independent object. Keep these facts separate in the trace.

For constructor questions, separate superclass construction, subclass field initialization and subclass constructor body. In Java 17 an explicit this or super constructor invocation must come first. A superclass constructor calling an overridable method adds another hazard: subclass fields may still have default values.

Build a complete explanation

For a four-mark class/object question, define the type, identify one instance, name state and name behavior. A course registration gives a concrete example. Avoid using class and object as interchangeable words.

For encapsulation, include a rejected operation. A private mark field is insufficient if its setter accepts 200. Explain validation before assignment and show that a failed update leaves the earlier valid mark unchanged. That connects access control to a useful invariant.

For a code-writing answer, state accepted input and output before the algorithm. Include constructor requirements, required method signatures and boundary behavior. A method fragment can answer a method question, but do not present it as a complete runnable program if main and supporting declarations are missing.

Explain the contract behind the mechanism

For equals and hashCode, identify the equality fields and explain why they stay stable. Equal hash codes alone do not prove equality. A correct answer must address symmetry and null as well as a successful pair of equal objects.

For collection selection, name both the required behavior and its cost. TreeSet fits sorted unique rolls. ArrayList fits indexed marks. HashMap fits key-based counting when sorted iteration is unnecessary. If a report needs order, show how you establish it.

For exceptions and files, say where recovery happens and whether partial state is allowed. For threads, show an interleaving that violates the rule before proposing a repair. Writing synchronized without identifying the shared lock does not explain the repair.

Show a request moving through the design

A useful design answer gives each class one clear responsibility, names relationships and states multiplicities where relevant. Then walk through one request. Which object checks a borrowing limit? Which object changes a loan state? What remains unchanged after rejection?

Use inheritance for a genuine substitution contract and composition for collaborators. An interface can name a capability across unrelated classes. Avoid making every noun a subclass without explaining what clients may safely assume about it.

The worked answers below include a validated Course, a member policy, a registration report and a shared-counter repair. Review them as reasoning patterns, then adapt the names and rules to a fresh problem. Memorized class diagrams cannot replace a new problem’s constraints.

Give evidence for each conclusion

  • Do not invent output for code that cannot compile.
  • Do not let a Child runtime object alter compile-time overload selection.
  • Do not treat a final reference as a deep immutable object.
  • Do not call a sleep delay a completion guarantee.
  • Do not claim a design is good only because it names a pattern.

Review the decision that caused the mistake

After each attempt, identify whether the error came from typing, dispatch, state, ordering or ownership. Revisit that specific lesson before trying another question. Continue with the library project for integrated implementation and the interview bank for concise explanations.
