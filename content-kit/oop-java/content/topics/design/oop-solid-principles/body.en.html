Find the change that makes a design difficult

A marks application may calculate grades correctly and still be painful to change. Editing message delivery might disturb grading. Adding a fee type might require editing many callers. SOLID names five principles for examining these design pressures and choosing clearer boundaries.

The letters stand for Single Responsibility, Open-Closed, Liskov Substitution, Interface Segregation and Dependency Inversion. Learn the problem each principle addresses before memorizing its name. A useful explanation identifies a concrete failing interaction, then shows how a design change removes that difficulty.

These principles are guidance rather than a demand for the largest possible class hierarchy. A tiny stable calculation may need no new interface. Extra types and indirection have costs. Apply a boundary when it separates real responsibilities, protects a contract or isolates useful variation.

Express dependencies through narrow contracts

interface Sink {
    void send(String text);
}
class Notifier {
    private final Sink sink;
    Notifier(Sink sink) { this.sink = sink; }
    void notifyMark(int mark) {
        sink.send("Mark " + mark);
    }
}

This small fragment demonstrates several design choices. Notifier coordinates the reporting policy. Sink describes the destination capability. A caller supplies a suitable implementation. The constructor assumes a non-null sink, and the operation’s text format is independent of how the destination stores or displays it.

An interface by itself does not prove good design. If Sink exposed every detail of a particular mail server, the policy would still depend on that server’s representation. Choose operations around what the consumer needs, then let details fulfil that contract.

Compare a specific design problem with its repair

SRP: separate arithmetic from presentation

MixedBill owns both multiplication and receipt wording. Changing the currency label and changing the billing calculation are different requests. Bill and ReceiptText put those decisions in separate places while keeping the same displayed result.

Single responsibility means a coherent reason to change, not exactly one method. A class can have several methods maintaining one billing policy. Splitting every helper into a new class would add navigation cost without necessarily separating a real responsibility.

OCP: extend the policy family

BranchFare contains a central student decision. Another category would require editing that calculation. Fare gives consumers a stable operation while StudentFare provides one implementation. Object creation still chooses which policy to use.

Open-closed means open for useful extension while an established boundary stays stable. It does not ban all edits forever. The boundary itself may need revision when requirements change fundamentally. Choose the variation you actually expect instead of predicting every possible future feature.

LSP: preserve the promised capability

Box promises writable storage, while FixedBox removes that ability. Its write method rejects a request that the parent meaning allows. Archive instead implements Reader and offers only the capability it can honestly fulfil.

Liskov substitution asks whether a subtype can replace its supertype without breaking the supertype’s behavioural promises. A matching Java signature is necessary but insufficient. The deliberate bad write body shows the broken promise; the main operation observes the mismatch without attempting the rejected write.

A subtype must not demand stronger preconditions. If Account accepts any positive withdrawal within balance, a child cannot suddenly require at least 500. A subtype also must not weaken postconditions. Returning null where a non-null result was promised breaks callers even when compilation succeeds.

ISP: remove irrelevant capabilities from the client contract

WideDevice asks a scan-only class to acknowledge printing. ScannerDevice removes that unrelated requirement. A combined machine can implement a separate printing capability too, without forcing all scanning clients to depend on it.

Interface segregation groups operations around client needs. It does not require every interface to contain exactly one method. A cohesive reader contract may legitimately need open, read and close together. Split when clients otherwise acquire dependencies or obligations they do not use.

DIP: let the caller supply a destination

FixedNotifier constructs ConsoleSink internally. Notifier instead depends on Sink and receives MemorySink. Both produce the same mark text, but the policy can now work with another destination without naming that concrete implementation.

Dependency inversion makes higher-level policy and lower-level details depend on an abstraction. The abstraction should describe the policy’s need rather than expose one detail’s internal API. Constructor injection makes the dependency visible and supplied from outside.

Describe inputs, results and side effects

Contracts make SOLID reasoning concrete. For a grade calculation, state the accepted mark range and the permitted grade labels. For a sink, state whether send returns only after recording, whether ordering matters and how failure is reported. Consumers can then depend on something more precise than a method name.

Consider a FeePolicy whose apply operation accepts nonnegative prices and returns a nonnegative amount no greater than the input. A new implementation returning a negative amount violates that contract. Moving it behind an interface does not make it a valid extension.

State side effects as well. A read operation promised to leave data unchanged should not remove an item in one subtype. A storage operation promised to retain earlier records should not silently replace them. Substitution concerns observable behaviour, including state transitions, not only the immediate return value.

Keep validation responsibility clear. If the boundary promises that all inputs are already valid, internal implementations may rely on that promise. If public callers can send arbitrary marks, reject invalid values at an appropriate entry point. Inconsistent assumptions across layers create avoidable surprises.

Avoid replacing one difficulty with unnecessary machinery

Dependency injection and dependency inversion are related but distinct. Passing a concrete ConsoleSink through a constructor is injection. The consumer still depends on ConsoleSink. Accepting the Sink contract supports inversion when both the policy and adapter depend on that useful abstraction.

OCP also does not require replacing every if statement. Selecting a policy from a menu naturally involves a choice. The useful goal is to keep that choice out of stable consumers that only need the resulting behaviour. A factory or construction method can own selection.

Interfaces can become too narrow as well as too broad. Ten nearly identical contracts may make a straightforward workflow harder to understand. Group operations that naturally belong together for the same client. Separate them when different consumers need genuinely different capabilities.

Measure success through understandable change. Can you add a destination without editing grading? Can a client use any subtype under the same legal inputs? Can a scan-only device implement its contract without fake methods? These questions expose practical value more clearly than counting classes.

If you know C: you may already separate calculation functions from input and output functions. SOLID extends that separation to object contracts, subtype promises and dependency direction. Java interfaces make the boundaries explicit, but the reasoning still starts with the program’s responsibilities.

Build an answer around evidence

In a university design question, first identify the consumer and its expectation. Next show a legal input or requested change that the design handles badly. Name the relevant principle, draw the repaired relation, and explain which classes now change independently.

For LSP, a single counterexample is powerful. State that Account permits withdrawing 100, then show a child rejecting that amount despite sufficient balance. The answer demonstrates a stronger precondition. Merely writing “inheritance is wrong” does not explain the broken promise.

In an interview, also mention the cost. An injected sink adds a constructor dependency and another type but allows isolated policy checks and alternate destinations. If no variation or isolation is useful, a direct stable dependency can be a reasonable smaller design.

Avoid turning principles into slogans

Equating SRP with one method per class

Several methods may maintain one coherent policy. Split according to independent change reasons, then keep related operations together. Method count alone does not identify a responsibility.

Claiming any subclass satisfies LSP

The compiler checks structural rules, not every business promise. Check accepted inputs, returned results and state effects. A child may compile and still break a legal parent interaction.

Adding abstractions without a consumer

An interface copied mechanically from one class may preserve all the original coupling. Begin with a real caller need and a useful substitution boundary. Keep the result understandable enough for the next programmer to follow.

Principles do not depend on a new Java feature

The SOLID guidance applies across language versions. These Java 17 implementations use ordinary classes, interfaces and constructors. Runtime exception handling and larger collection designs appear elsewhere; the design examples keep their inputs and collaborations bounded.

Choose the smallest boundary that solves the observed problem
