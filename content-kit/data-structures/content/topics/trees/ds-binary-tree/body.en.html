Choose where the child links live

Imagine the seats in a small tournament chart. Each box has a left and right position below it. You can number every possible box, or give each occupied box two arrows. These become the array and linked representations of a binary tree.

A representation is the way you arrange a logical structure in memory. The stored keys do not determine that arrangement by themselves. You also need rules describing which keys are children of which parents. Two programs can receive identical keys and build different shapes if their input conventions differ.

This lesson builds a complete tree from keys supplied in level order. It also shows sparse array positions explicitly. Neither builder compares keys to impose search ordering. For the naming of root, leaf and height, revisit tree terminology.

Implicit positions and explicit pointers

In a zero-based array representation, the root occupies position zero. For an occupied index i, its potential left child is 2*i+1 and its potential right child is 2*i+2. A non-root node's parent is (i-1)/2 using integer division. The root needs a separate no-parent case.

For a complete tree with n keys, every index from zero through n-1 is occupied. A child exists exactly when its computed index is less than n. Append uses the next index and takes O(1) work when spare capacity exists. Array growth can require O(n) copying, as in the dynamic array.

typedef struct Node {
    int key;
    struct Node *left, *right;
} Node;

A linked node stores the key and two pointers. A NULL child pointer means that position is empty. The pointer named root identifies the first record, or is NULL for an empty tree. Records may live anywhere in allocated memory; their addresses need not follow key order.

The array formulas change for one-based numbering: children become 2*i and 2*i+1, and parent becomes i/2. Both conventions work, but mixing them loses nodes. Write the root index beside any diagram before translating relationships into arithmetic.

Build the shape from level-order input

The complete-tree builder reads n in the range zero through twelve, then n keys from -99 through 99. It first saves those values in a temporary array. Reading everything before allocating nodes avoids a partly built tree when a key is missing. Only after successful reading does build begin.

The build function receives the current array index i. If i lies outside the active range, it returns NULL. Otherwise it allocates one Node, writes the key, then builds the two child positions recursively. Returning that record publishes the completed local subtree to its caller.

Allocation can fail. The ok flag remembers failure without discarding records already returned by earlier calls. Remaining calls stop creating nodes. The main function still receives the partial root and passes it to destroy, which releases every reachable record before returning failure.

Building n linked records takes O(n) time and O(n) node storage. The recursive calls add O(log n) space for this complete shape. A general arbitrary-shape builder can instead need O(h+1) call space. Allocation time is a library cost beyond the pointer assignments described here.

To represent a sparse shape in an array, keep a separate present flag for each possible position. The value zero cannot identify a hole if zero is legal data. Example three therefore stores occupancy independently from keys. It also rejects a child whose parent position is absent.

Sparse input may name child positions before their parents. Validate relationships after all pairs have been read. An occupied node with an absent parent is an orphan, so those pairs do not describe a rooted tree. With the fixed fifteen-position bound, checking every position costs O(15), or O(capacity) in general.

An explicit child-index table is another array-based option. Each record stores indices for its left and right children, with a special missing index. This preserves sparse shapes without enormous gaps. Its links behave like pointers, but indices refer to records inside the same array.

Choose storage for the expected shape

A complete array packs keys tightly and avoids two pointers per key. Neighboring positions can also share cache lines. Moving the array does not change implicit child indices. However, code holding raw pointers into its old storage must not keep using them after a resize.

A right-only chain occupies implicit indices 0, 2, 6, 14 and 30. Five records already demand positions through thirty. Adding more nodes makes the highest position grow exponentially with chain length. Linked nodes use one record per occupied position, so they are a better fit for this sparse shape.

Neither representation makes every operation constant time. Following a known child link is O(1), but locating an arbitrary unsorted key can visit all n nodes. Mirroring a linked tree swaps both pointers at each record and takes O(n) time. Its recursion adds O(h+1) space, while the existing records stay allocated.

Deleting a general binary-tree node needs a stated policy about its children. Removing an arbitrary occupied array position leaves a hole unless you repair the shape. Removing a linked record without saving its subtrees loses access to them. The later BST lesson supplies one specific deletion policy based on key ordering.

When an exam supplies a byte address and key width, array location is base plus index times width. Those widths are assumptions for that question. A linked node needs a separately supplied record layout before you can calculate its member addresses; the key-array formula does not describe pointer-based records.

Assuming input order means search-tree insertion

The keys 8, 10, 3 place 10 on the left in a complete level-order build. That is valid for a binary tree. A BST insertion routine would choose different links, so always state the input interpretation.

Following a computed child beyond the active array

The formula gives a position, not proof that a child exists. Check that position against n for complete storage. For sparse storage, check capacity and occupancy before reading its key.

Releasing a parent first

Once you free a linked record, you cannot read its child pointers. Release its left and right subtrees before freeing the record. Destroying the whole tree costs O(n) time and leaves no live records.

Portable C17 node storage

The Node type and builders use standard C17 allocation. Allocate with sizeof *p so the requested size follows the pointed-to type. Structure padding and pointer width vary by machine; no output assumes a fixed record size or prints real addresses.

Representation defines the available moves
