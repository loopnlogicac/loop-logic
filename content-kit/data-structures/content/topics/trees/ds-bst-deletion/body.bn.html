পাশের নোড না হারিয়ে record সরাও

Registry থেকে roll number বাদ দিতে হতে পারে, অথচ তার ট্রি নোডের নিচে অন্য record আছে। সঙ্গে সঙ্গে ঘর মুছলে child link হারাবে। BST deletion আগে ঠিক করে ঘরটার জায়গা কে নেবে, তারপর incoming link ঠিক করে, শেষে অদরকারি record ছাড়ে।

মূল প্রশ্ন ownership। Parent বা caller-এর root ভেরিয়েবল একটা subtree-তে ঢোকার পয়েন্টার-এর মালিক। Deletion routine-কে subtree-র নতুন root ফেরাতে হবে। সেই পয়েন্টার আগের root, বেঁচে থাকা child বা NULL হতে পারে।

তুমি BST-র ক্রম, search আর minimum জানো। Deletion একই তুলনা দিয়ে target-এ পৌঁছায়, তারপর শূন্য, এক আর দুই child আলাদা সামলায়। এখানেও unique key-র নিয়ম, তাই প্রতিটি সফল অনুরোধে ঠিক একটা রাখা key সরে।

free-এর আগে link ভাবো। মেমরি ছাড়লে অন্য পয়েন্টার নিজে ঠিক হয় না। Parent পুরোনো address দেখালে বিপদ। নিচের ছবিতে প্রতিটি deletion case-এর আগে আর পরে কাঙ্ক্ষিত অবস্থা দেখানো আছে।

বদলি subtree root ফেরাও

erase(root, key):
    if root is missing: return NULL
    if key is smaller: root.left = erase(root.left, key)
    if key is larger: root.right = erase(root.right, key)
    if equal and at most one child: save child, free root, return child
    if equal and two children:
        next = minimum(root.right)
        root.key = next.key
        root.right = erase(root.right, next.key)
    return root

Caller লেখে root = erase(root,key)। ফাংশনের ভেতরে child-এর owner-ও ফেরত পাওয়া পয়েন্টার left বা right field-এ বসায়। বেশিরভাগ অনুরোধে root record টিকে গেলেও নিয়মটা দরকার। Root deletion অন্য কোথাও লুকানো বিশেষ ব্যতিক্রম নয়।

দুই child সরানোর ক্ষেত্রে দুটি আলাদা ঘটনা: key-র অবস্থান বদলায়, আর আসল একটা record বাদ যায়। Trace-এ আলাদা রাখো। সাধারণত প্রথম target record successor key নিয়ে টিকে যায়। আগে successor key রাখা record-টাই শেষে free হয়।

Child সংখ্যার তিন case

প্রথম case: child নেই

আগে: parent.left ---> [3 | NULL | NULL]
পরে: parent.left ---> NULL
ছাড়া হলো: 3 রাখা record

Leaf-এর নিজের কোনো child subtree নেই। বদলি হিসেবে NULL রেখে leaf record ছাড়ো, NULL ফেরাও। Parent-এর assignment incoming link সরায়। Leaf-ই পুরো ট্রি হলে caller NULL পায়, ট্রি ফাঁকা হয়।

সরানোর স্থানীয় পয়েন্টার কাজ O(1)। কিন্তু leaf খুঁজতে root থেকে leaf পর্যন্ত পুরো search লাগতে পারে। স্থানীয় edit আর পুরো কাজের খরচ এক কোরো না। Target না থাকলে search হয়, কিন্তু এই release case আসে না।

দ্বিতীয় case: ঠিক এক child

আগে: root ---> [8 | left ---> 3 | right=NULL]
                     [3 | left ---> 1 | right ---> 6]
রাখা হলো: child ---> 3
পরে: root ---> [3 | left ---> 1 | right ---> 6]
ছাড়া হলো: শুধু পুরোনো 8 record; subtree 3 বেঁচে আছে

free-এর আগে non-NULL child পয়েন্টার রাখো। Child আগেই deleted node-এর ancestor-দের সব সীমা মানে। তাই তাকে ওপরে তুললেও BST-র নিয়ম থাকে। রাখা পয়েন্টার ফেরাও, যাতে আসল owner মুছে ফেলা record পাশ কাটাতে পারে।

এখানে মুছতে যাওয়া নোডে destroy চালানো ভুল। Destroy পুরো নিজের subtree ছাড়ে, যে child বাঁচাতে হবে তাকেও। শুধু আলাদা করা record-এ free চালাও। বদলি link দায় নেওয়ার পরে তার আগের child field আর record-গুলোর মালিক নয়।

তৃতীয় case: দুই child

আগে:             [8]
                 /   \
               [3]   [10]
                     /  \
                   [9]  [14]
Successor copy: record 8-এর key হয় 9
পুরোনো 9 বাদ:   10.left ---> NULL
পরে:              [9]

               [3]   [10]

Right subtree-র minimum নোড বেছে নাও। তার key left subtree-র সব key-র বড় এবং right subtree-র অন্য কোনো key-র বড় নয়। সেই key target-এ copy করে পুরোনো successor record সরালে ক্রম থাকে।

Successor-এর left child থাকতে পারে না, থাকলে right subtree-তেই আরও ছোট key পাওয়া যেত। Right child থাকতে পারে। তাই তাকে সরানো শূন্য বা এক child-এর case-এ নামে। এই successor-এর রিকার্সিভ erase-এ আর দুই child বদলাতে হবে না।

Copy-র পরে সাময়িকভাবে দুই record-এ একই key থাকে। এটা কাজের মাঝের অবস্থা। সেখানে থামবে না বা সম্পূর্ণ বৈধ set হিসেবে দেখাবে না। পরের erase পুরোনো successor সরায়।

Lab প্রথম উদাহরণের একই insertion-order BST থেকে শুরু। তুলনা, successor ধরে হাঁটা, key বদল, owner-link মেরামত আর আসল deletion আলাদা action দেখায়। কোনো root বা child link record-টি না দেখালেই delete হয়। ফলে dangling reference-কে সরাসরি link-এর সমস্যা হিসেবে বোঝা যায়।

Successor নিজেই right child হলে রিকার্সিভ removal সরাসরি target-এর right link বদলায়। Successor আরও কয়েক level বামে হলে আর তার right child থাকলে তার parent left link দিয়ে সেই child নেয়; বাকি right subtree অক্ষত থাকে।

কোন record সরল trace করো

প্রথম উদাহরণ দুই child-এর root সরায়, দ্বিতীয়টি root-এর একমাত্র child ওপরে তোলে। Drain উদাহরণ root না থাকা পর্যন্ত বারবার minimum সরায়। চালানোর আগে ভাবো কোন আসল record free হবে, তার বদলি কোন পয়েন্টার পাবে।

Key সরিয়ে root link ঠিক করো

Root-এর দুই child। তার key 9 হয়, তারপর আগের 9 রাখা নোডের link কেটে free করা হয়।

এক child-সহ root মুছো

Root link আগে রাখা child পয়েন্টার পায়। নোড 8 free হলেও নোড 3 বেঁচে থাকে।

বারবার minimum সরিয়ে ট্রি ফাঁকা করো

প্রতিটি minimum-এর left child নেই, তাই শূন্য বা এক child case-এ সরে। শেষ root NULL।

খরচ, ব্যর্থতা আর একই অনুরোধ বারবার

Deletion search সর্বোচ্চ h+1 দৈর্ঘ্যের এক পথ ধরে। Successor search right subtree-র মধ্যে থাকে, পুরো ট্রি ঘাঁটে না। মোট সময় O(h+1), রিকার্সিভ call space-ও O(h+1); deletion নতুন node record allocate করে না।

Balanced ট্রি-তে সীমা O(log n), কিন্তু সাধারণ BST-র height n-1 হতে পারে। চেইনে তাই O(n) deletion সময় আর call depth হতে পারে। নোড সরালেই ancestor-রা rebalanced হয় না। পরের AVL পাঠে সেই আলাদা কাজ আসবে।

ফাঁকা ট্রি থেকে মুছলে free ছাড়াই NULL ফেরে। একমাত্র নোড মুছলেও NULL ফেরে, তবে আগে একটা record free হয়। না থাকা key মুছলে সব নোড আর link আগের মতো। তাই সফল deletion আবার চাইলে দ্বিতীয়বার আর কিছু সরে না।

Linked BST deletion-এ capacity-full case নেই; এখানে storage নেওয়া নয়, ছাড়া হয়। Trace ছোট রাখতে ইনপুট প্রোগ্রামে তবু বারো key-র সীমা। পরের query পড়া না গেলে failure path বাকি ট্রি destroy করে।

বাইরের কোডের রাখা পয়েন্টার deletion-এ অবৈধ হতে পারে। Target record-এর পয়েন্টার রাখলে দুই child deletion-এ address টিকে গেলেও key বদলাতে পারে। Successor record-এর পয়েন্টার release-এর পরে অবৈধ। এই পাঠে key দিয়ে query করা হয়, record identity স্থির থাকার প্রতিশ্রুতি নেই।

আসল নোডে integer key ছাড়া আরও ডেটা থাকলে replacement নিয়ে ভাবতে হবে। পুরো logical record copy করো বা তার payload-এর ownership বুঝে সরাও। শুধু key copy করে অন্য ডেটা রেখে দিলে এক roll number-এ অন্য শিক্ষার্থীর marks জুড়ে যেতে পারে। Shared বা হিপ-owned payload-এরও স্পষ্ট ownership rule দরকার।

পুরো ট্রি cleanup এখনও postorder: আগে left destroy, তারপর right, শেষে current free। সাধারণ deletion-এ ওপরে তোলা child-এর ওপর সেই cleanup চলবে না। উদাহরণে শেষে বেঁচে থাকা root-এই শুধু destroy চলে। এক record সরানো আর প্রোগ্রাম শেষে সব ownership ছাড়া আলাদা থাকে।

Practice-এর pruning সমস্যা শুধু আগের গঠনের leaf সরায়। রিকার্শন-এর আগে leaf পরীক্ষা করে বলে নতুন প্রকাশিত leaf টিকে যায়। Trimming সমস্যা child trim করার পরে interval-এর বাইরের সব key সরায়। শুধু ফাংশন-এর নাম চেনার মতোই এই নিয়ম পড়া জরুরি।

Subtree-র owner পয়েন্টার ঠিক করো

ফেরত পাওয়া root না নেওয়া

Assignment ছাড়া erase(root,key) লিখলে ওপরে ওঠা root হারাবে বা free হওয়া address রেখে দেবে। বর্তমান owner-এ ফেরত পয়েন্টার জুড়ো। Recursively দুই child field-এও একই নিয়ম।

free-এর পরে child পড়া

free(root) record-এর lifetime শেষ করে। পুরোনো bit একই দেখালেও পরে root.left পড়া undefined behavior। আগে live child পয়েন্টার রাখো, তারপর record ছেড়ে রাখা মান ফেরাও।

যেকোনো বড় key দিয়ে বদলানো

Right subtree-র maximum বসালে নতুন root-এর ডানে ছোট key থেকে যেতে পারে। Right minimum বিশেষ, কারণ বাকি right key সব তার বড়। এলোমেলো right descendant নয়, minimum(root.right) নাও।

পুরোনো successor ভুলে যাওয়া

Key copy deletion নয়। দ্বিতীয় erase না হলে node count বদলায় না, duplicate থেকে যায়। সঠিক দুই child অনুরোধে size ঠিক এক কমবে।

হাতে erase যাচাই করো

প্রতিটি allocated record-এর child field-সহ ঘর আঁকো। Free হবে যেটি, গোল করো। সেটি কাটার আগে বদলি owner link আঁকো। তারপর দেখো root ছাড়া প্রতিটি বেঁচে থাকা record-এর ঠিক একটা incoming ট্রি link আছে কি না।

Right child-সহ গভীর successor পরীক্ষা করো; যেমন key 8,3,12,10,14,9,11 নিয়ে 8 মুছো। সরাসরি right successor, এক নোড আর না থাকা key-ও পরীক্ষা করো। প্রতিবার record গুনে inorder-কে আগের set থেকে target বাদ দেওয়া ফলের সঙ্গে মেলাও। পরীক্ষাগুলো আলাদা ভুল ধরে।

Successor-এর right child পরীক্ষা করতে 8,3,15,10,20,12 insert করে 8 মুছো। Successor 10-এর right child 12 আছে। পুরোনো root-এ 10 copy করো, 15.left-কে 12 দেখাও, তারপর পুরোনো 10 record ছাড়ো। Inorder হবে 3,10,12,15,20। আগের leaf-successor উদাহরণ থেকে এটা আলাদা: এখানে পুরোনো successor-এর জায়গায় NULL দিলে দরকারি নোড 12 হারাবে।

C17 lifetime-এর নিয়ম

C17-এ free(NULL) চলে, কিন্তু free হওয়া non-NULL পয়েন্টার পড়া বা আবার free করা নিরাপদ হয় না। উদাহরণে প্রতিটি আসল record একবার ছাড়া হয়। আগের address আর পরের কোনো allocation-এর সম্পর্ক থাকার বাধ্যবাধকতা নেই।

বদলি বসানো আর ছাড়া আলাদা রাখো
