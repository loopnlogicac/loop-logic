Remove a record without losing its neighbors

A roll number can leave a registry even when several other records hang below its tree node. Erasing the box immediately would lose those child links. BST deletion first decides who should take the box's place, then repairs the incoming link, and finally releases the unwanted record.

The key problem is ownership. The parent, or the caller's root variable, owns the incoming pointer to a subtree. A deletion routine must return the subtree's new root. That returned pointer may equal the old root, refer to a surviving child, or be NULL.

You already know BST ordering, search and minimum. Deletion uses those same comparisons to reach a target. It then handles zero, one or two children separately. This lesson retains the unique-key policy, so each successful request removes exactly one stored key.

Think about links before thinking about free. Freeing memory does not automatically repair other pointers. A parent that still points to the old address becomes unsafe. The diagrams below show the intended before and after state for every deletion case.

Return the replacement subtree root

erase(root, key):
    if root is missing: return NULL
    if key is smaller: root.left = erase(root.left, key)
    if key is larger: root.right = erase(root.right, key)
    if equal and at most one child: save child, free root, return child
    if equal and two children:
        next = minimum(root.right)
        root.key = next.key
        root.right = erase(root.right, next.key)
    return root

The caller writes root = erase(root,key). Inside the function, child owners similarly assign the returned pointer to their left or right field. This rule is needed even when most requests preserve the root record. Root deletion is not a special exception hidden elsewhere.

There are two independent events in a two-child removal: a key changes location, and a physical record disappears. Keep them separate in your trace. The original target record usually survives with its successor key. The record that previously held that successor key is the one eventually freed.

The three child-count cases

Case one: no children

Before: parent.left ---> [3 | NULL | NULL]
After:  parent.left ---> NULL
Released: the record that held 3

A leaf owns no child subtrees. Save NULL as its replacement, release the leaf record, and return NULL. The parent assignment removes its incoming link. If this leaf was the whole tree, the caller receives NULL and the tree becomes empty.

The removal itself uses O(1) pointer work. Finding the leaf can still require a full root-to-leaf search. Do not confuse the local edit with the cost of the whole operation. A missing target performs the search but never enters this release case.

Case two: exactly one child

Before: root ---> [8 | left ---> 3 | right=NULL]
                     [3 | left ---> 1 | right ---> 6]
Saved:  child ---> 3
After:  root ---> [3 | left ---> 1 | right ---> 6]
Released: only the old 8 record; subtree 3 stays alive

Save the non-NULL child pointer before free. The child already satisfies all bounds imposed by the deleted node's ancestors. Promoting it therefore preserves the BST property. Return that saved pointer so the actual owner can bypass the deleted record.

Calling destroy on the deleted node would be wrong here. Destroy releases an entire owned subtree, including the child that must survive. Use free on the single detached record. Its former child fields do not own records after the replacement link has taken over that responsibility.

Case three: two children

Before:           [8]
                 /   \
               [3]   [10]
                     /  \
                   [9]  [14]
Copy successor: record 8 changes key to 9
Unlink old 9:    10.left ---> NULL
After:            [9]
                 /   \
               [3]   [10]
                         \
                         [14]

Choose the minimum node in the right subtree. Its key is greater than every key in the left subtree. It is no greater than any other right-subtree key. Copying that key into the target preserves the order once the old successor record is removed.

The successor cannot have a left child, because that child would contain a smaller right-subtree key. It can have a right child. Its own removal therefore reduces to the zero-child or one-child case. That is why the recursive erase call will not require another two-child replacement for this successor.

After the copy, the key briefly exists in two records. This is a temporary intermediate state inside the operation. Do not stop the algorithm there or expose it as a completed valid set. The next erase removes the old successor occurrence.

The lab starts from the same insertion-order BST as example one. It displays comparisons, successor walking, key replacement, owner-link repair and physical deletion as separate actions. The delete action occurs only after no root or child link points to that record. This makes dangling references visible as a concrete link problem.

Suppose the successor is the right child itself. Then the recursive removal updates the target's right link directly. Suppose the successor lies several levels farther left and owns a right child. Its parent must adopt that child through its left link; the rest of the right subtree remains intact.

Costs, failure cases and repeated requests

A deletion search follows one path of length at most h+1. The successor search stays within the right subtree and does not introduce a whole-tree scan. Total time is O(h+1). Recursive call space is also O(h+1); deletion allocates no new node records.

On a balanced tree those bounds become O(log n), but an ordinary BST can have height n-1. A chain therefore permits O(n) deletion time and call depth. Removing a node does not automatically rebalance its ancestors. The upcoming AVL lesson introduces that separate responsibility.

Deleting from an empty tree returns NULL without calling free. Deleting the only node also returns NULL, but frees one record first. Deleting an absent key leaves every node and link unchanged. Repeating a successful deletion request therefore reports no further removal the second time.

The linked BST has no capacity-full case in deletion. A request releases storage rather than acquiring it. The input programs still enforce their twelve-key limit to keep traces manageable. Their failure paths destroy the remaining tree if a later query cannot be read.

Deletion can invalidate pointers held by outside code. If a caller saved a pointer to the target record, two-child deletion may keep that address but change its key. A saved pointer to the successor record becomes invalid after release. This lesson exposes keys as queries and avoids promising stable record identities.

If a real node holds more than an integer key, replacement needs more thought. Copy the complete logical record, or deliberately move ownership of its payload. Copying only a key while leaving unrelated data can attach one student's marks to another roll number. Shared or heap-owned payloads also need an explicit ownership policy.

Whole-tree cleanup remains postorder: destroy left, destroy right, free current. Ordinary deletion must not run that cleanup on the promoted child. The example programs call destroy only on the final surviving root. That separates single-record removal from end-of-program ownership release.

The practice pruning problem removes only leaves from the original shape. It tests leaf status before recursing, so newly exposed leaves survive. The trimming problem instead removes every key outside an interval after trimming children. Reading those policies carefully matters as much as recognizing the function name.

Repair the pointer that owns the subtree

Ignoring the returned root

Writing erase(root,key) without assignment loses a promoted root or keeps an address that has been freed. Always reconnect the returned pointer at the current owner. Apply that rule recursively to both child fields.

Reading the child after free

The expression free(root) ends the record's lifetime. A later root.left access has undefined behavior, even if the old bits look unchanged. Save the live child pointer first, then release the record and return the saved value.

Replacing with any larger key

The maximum in the right subtree may leave smaller keys below the new root's right side. The right minimum is special because all other right keys remain greater. Use minimum(root.right), rather than a random right descendant.

Forgetting the old successor

Copying a key is not a deletion. Without the second erase call, the node count stays unchanged and a duplicate remains. A correct two-child request decreases size by exactly one.

Audit an erase operation by hand

Draw a small box for each allocated record, including its child fields. Circle the record that will be freed. Draw the replacement owner link before crossing out that record. Then check that every surviving record has one incoming tree link, except the root.

Test a deep successor with a right child, such as keys 8,3,12,10,14,9,11 and deletion 8. Also test a direct-right successor, a singleton and a missing key. After each request, count records and compare inorder keys with the original set minus the target. These checks expose different failure modes.

To exercise a successor with a right child, insert 8,3,15,10,20,12 and delete 8. The successor is 10, which owns right child 12. Copy 10 to the old root record, repair 15.left to point at 12, then release the old 10 record. The resulting inorder is 3,10,12,15,20. This differs from the earlier leaf-successor example: replacing the old successor with NULL here would lose the still-needed node 12.

C17 lifetime rules

C17 permits free(NULL), but that does not make a freed non-NULL pointer safe to read or free again. The examples release each physical record once. There is no required relationship between its former address and any later allocation.

Separate replacement from release

Zero-child and one-child cases replace an owner link directly. Two-child deletion copies a carefully chosen successor and removes its old record. Next, AVL trees preserve short search paths through height checks and rotations.
