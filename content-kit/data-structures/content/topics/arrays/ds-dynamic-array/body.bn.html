শুরু করা যাক

কম্পিউটারে আরও মেমরি থাকলেও নির্দিষ্ট অ্যারের ঘর ফুরিয়ে যেতে পারে। ডাইনামিক অ্যারে অ্যারের মতো ইনডেক্স দিয়ে পড়তে দেয়, তবে বেশি জায়গা লাগলে বরাদ্দ ব্লক বদলায়। ভাবো, ক্লাস বড় হলে আগের সব নম্বর ঠিক রেখে খাতাটা আরও বড় খাতায় তুলছ।

কালেকশনের যৌক্তিক সিকোয়েন্স একটাই থাকে। আসল মেমরির ব্লক সরতে পারে, আর ফাঁকা ক্যাপাসিটি হঠাৎ বেড়ে যেতে পারে। এখানে ছোট ভেক্টর বানাবে: struct-এ মালিক পয়েন্টার, ব্যবহৃত সাইজ আর বরাদ্দ ক্যাপাসিটি থাকবে। দ্বিগুণ করে বাড়াবে, আর ছোট করার জন্য আলাদা সীমা রাখবে।

Resize-এ সাবধান হতে হয়, কারণ মেমরি নেওয়া ব্যর্থ হতে পারে। এখান থেকে খরচের একটা দরকারি ফলও বোঝা যায়: এক append-এ বেশি খরচ হলেও অনেক append মিলিয়ে প্রতি অপারেশনের amortized খরচ ধ্রুব হতে পারে। মেমরির ছবি আর খরচের যুক্তি একই কাজকে দুই দিক থেকে দেখায়।

কীভাবে রাখবে, কী নিয়ম মানবে

Vector-এর ফিল্ড values, size আর capacity। size <= capacity রাখো। capacity শূন্য হলে values শুরুতে NULL। প্রথম append-এ এক ঘর চায়। এরপর size ক্যাপাসিটির নিচে থাকলে সরাসরি values[size]-এ লেখা যায়।

ভরে গেলে পুরোনোর দ্বিগুণ ক্যাপাসিটি নাও। এই ছোট লাইব্রেরিতে সর্বোচ্চ 1024 ঘর রাখা যায়। তাই সমর্থিত সাইজে দ্বিগুণ করা আর sizeof দিয়ে গুণ দুইটাই নিরাপদ সীমায় থাকে। সীমাহীন সাধারণ লাইব্রেরিতে বাইট চাওয়ার আগে size_t-এর সর্বোচ্চ মান অনুযায়ী overflow, অর্থাৎ সংখ্যার সীমা ছাড়িয়ে যাচ্ছে কি না, স্পষ্টভাবে দেখতে হতো।

int *values = realloc(vector->values, capacity * sizeof *values);
if (values == NULL) {
    return 0;
}
vector->values = values;
vector->capacity = capacity;

realloc একই জায়গায় ব্লক বাড়াতে পারে বা মান অন্য ব্লকে সরাতে পারে। ব্যর্থ হলে NULL দেয়, কিন্তু পুরোনো মেমরি বৈধ থাকে। ফলটা অস্থায়ী পয়েন্টারে রাখো, সফল হলেই মালিক পয়েন্টার বদলাও। Resize-এ মেমরি সরে যেতে পারলে আগে রাখা এলিমেন্ট পয়েন্টার আর ব্যবহার করবে না।

pop শেষের ব্যবহৃত এলিমেন্ট বাদ দিতে size কমায়। size শূন্য হলে ব্যর্থতা জানায়। চাইলে ছোট করার নিয়মে size ক্যাপাসিটির সর্বোচ্চ এক-চতুর্থাংশ হলেই ক্যাপাসিটি অর্ধেক হয়। একবার মেমরি নেওয়া হলে ক্যাপাসিটি একের নিচে নামে না। শুরুতে খালি ভেক্টরের ক্যাপাসিটি অবশ্য শূন্য হতে পারে।

মেমরিতে কী হচ্ছে দেখো

1 থেকে 5 যোগ করো। প্রথম append এক ঘর নেয়। দ্বিতীয়বার তা ভরা পেয়ে দুই ঘর নেয়। তৃতীয়বার চার ঘর লাগে। চতুর্থবার আগের ফাঁকা ঘরেই বসে। পঞ্চমবার আট ঘর লাগে। নিয়মটা দেখে রান করার আগেই পরের resize কোথায় হবে বলতে পারো।

মান 1 যোগের পরে: [1]                         size=1 capacity=1
মান 2 যোগের পরে: [1][2]                      size=2 capacity=2
মান 3 যোগের পরে: [1][2][3][ফাঁকা]             size=3 capacity=4
মান 4 যোগের পরে: [1][2][3][4]                 size=4 capacity=4
মান 5 যোগের পরে: [1][2][3][4][5][ ][ ][ ]      size=5 capacity=8

Growth ল্যাব মেমরি সরিয়ে নেওয়া মডেল করে, যাতে কপির সম্ভাব্য খরচ দেখা যায়। বড় ব্লক তৈরির সময় old-values প্যানেলে বর্তমান ব্যবহৃত সিকোয়েন্স থাকে। নতুন মান যোগের আগে পুরোনো প্রতিটি মান আবার বসে। আসল realloc একই জায়গায় বাড়িয়ে কপি এড়াতে পারে; যৌক্তিক ফল আর ক্যাপাসিটির নিয়ম একই থাকে।

সি-এর append ফাংশন স্টোরেজ তৈরি হওয়ার পর নতুন মান লেখে, তারপর size বাড়ায়। বড় করা ব্যর্থ হলে শূন্য দেয়; পুরোনো সাইজ আর মান ঠিক থাকে। কলার ফল দেখে ব্যর্থতা ফেরত দেওয়ার আগে বর্তমান মালিকের মেমরি ছেড়ে দেয়।

এবার ক্যাপাসিটি আটে আট এলিমেন্ট নিয়ে শেষে থেকে বাদ দাও। সাইজ সাত থেকে তিন পর্যন্ত ক্যাপাসিটি আট থাকে। সাইজ দুই হলে চার হয়। এক হলে দুই হয়। শূন্য হলে এক ঘরে নামতে পারে।

ছোট করার আগে: [1][2][ ][ ][ ][ ][ ][ ] size=2 capacity=8
ছোট করার পরে:  [1][2][ ][ ]             size=2 capacity=4
পরের append:      [1][2][3][ ]             size=3 capacity=4

বড় আর ছোট করার সীমার ফারাক জরুরি। এক-চতুর্থাংশ ভরা অবস্থায় ছোট করার পর নতুন ব্লক প্রায় অর্ধেক ভরা থাকে। তাই পরের একটি append-এই আবার বড় করতে হয় না। একই সীমার কাছে যোগ-বিয়োগ পালা করে হলে এভাবে বারবার resize এড়ানো যায়।

ধাপে ধাপে কাজটা দেখো

start with values = NULL, size = 0, capacity = 0
for each value in input order
    if size == capacity: choose capacity = max(1, 2 * capacity)
        allocate new cells and preserve all size live values
    write value at values[size]; increase size
finish; release the allocation after using it

উদাহরণ

দুই ক্যাপাসিটির সীমা পার করে append করো

ক্যাপাসিটি হয় 1, 2, 4, 4 আর 8। শুধু ব্যবহৃত মান প্রিন্ট হয়। বাড়তি ঘর পরে append করার জায়গা রাখে।

যথেষ্ট বাদ দেওয়ার পরেই ছোট করো

প্রথম কয়েকটা মান বাদ দিলেও ক্যাপাসিটি আট থাকে। এক-চতুর্থাংশ ভরা হলে তা অর্ধেক হয়, তাই প্রতি pop-এ resize লাগে না।

খালি ভেক্টর ব্যবহার করে মেমরি আবার কাজে লাগাও

খালি ভেক্টরে pop ব্যর্থ হয়, size বদলায় না। 72 বাদ দেওয়ার পর সেই বরাদ্দ ঘরে নতুন মেমরি না নিয়েই 85 রাখা যায়।

ইনপুট থেকে ভেক্টর বানাও

পাঁচটা ইনপুট নম্বরের জন্য ক্যাপাসিটি আট লাগে। realloc ব্লক সরাতে পারে, তাই নতুন মান লেখার আগে append মালিক পয়েন্টার আপডেট করে।

খরচ আর বিশেষ অবস্থাগুলো

append-এর খরচ দুই রকম। ফাঁকা ক্যাপাসিটি থাকলে O(1)। Resize-এ ব্লক সরলে nটি পুরোনো মান রাখতে হতে পারে, তাই ওই append-এর worst case O(n)। অনেক append জুড়ে কপি হওয়া দৈর্ঘ্য 1+2+4+8 করে বাড়ে। n-তম append শেষ হওয়ার আগে যোগফল 2n-এর নিচে থাকে। নতুন মানের n বার লেখা ধরলেও মোট O(n)।

এই সিকোয়েন্সের সীমা থেকেই O(1) amortized append সময় আসে; random ইনপুট ধরতে হয় না। প্রতি কল সমান দ্রুত হবে, এমন নিশ্চয়তা নেই। ইনডেক্স দিয়ে পড়া O(1), কিন্তু মাঝখানে ঢোকাতে এখনো O(n) সরানো লাগে। স্টোরেজ বড় করা ক্যাপাসিটির সমস্যার সমাধান; সিকোয়েন্সের সব কাজের খরচের নয়।

সাধারণ দ্বিগুণ বৃদ্ধির পর ভেক্টর O(n) মেমরি রাখে; ফাঁকা জায়গা সর্বোচ্চ ধ্রুব গুণক পরিমাণ। মেমরি সরানোর সময় সাময়িকভাবে পুরোনো আর নতুন দুই ব্লকই লাগতে পারে। ছোট করা ব্যর্থ হলেও pop যৌক্তিকভাবে সফল হয়; কমে যাওয়া সিকোয়েন্স পুরোনো বড় মেমরিতে বৈধ থাকে।

খালি pop ব্যর্থ হয়। এক এলিমেন্টে pop করলে কোনো ব্যবহৃত মান থাকে না। খালি হওয়ার পর ভেক্টর আবার ব্যবহার করা যায়। মালিকের কাজ শেষ হলে vector.values ঠিক একবার ছাড়ো, পয়েন্টারটা NULL থাকলেও।

যেসব ভুল প্রায়ই হয়

realloc-এর ফল সরাসরি মালিক পয়েন্টারে রাখা

বড় করা ব্যর্থ হলে vector->values=realloc(...) পুরোনো একমাত্র অ্যাড্রেসের ওপর NULL লিখে দেয়। মেমরি থাকে, কিন্তু তাতে আর পৌঁছানো যায় না। অস্থায়ী ফলের পয়েন্টার এই ক্ষতি ঠেকায়।

ক্যাপাসিটির সব ঘর প্রিন্ট করা

অব্যবহৃত ঘরে নম্বরের নির্দিষ্ট মান থাকবে, এমন নিশ্চয়তা নেই। pop-এর পরে সীমার বাইরে পুরোনো ডেটা থাকলেও show শুধু size-এর নিচের ইনডেক্স প্রিন্ট করে।

প্রতি বাদ দেওয়ার পরেই ছোট করা

capacity সবসময় size-এর সমান রাখলে বারবার append-এ বারবার কপি লাগতে পারে। বাড়ানো আর ছোট করার সীমা একই হলেও পালা করে যোগ-বিয়োগ ব্যয়বহুল হতে পারে। সীমা আলাদা রাখো।

বড় করার পরে পুরোনো এলিমেন্ট পয়েন্টার ব্যবহার করা

realloc মেমরি সরালে &vector.values[2]-এর মতো অ্যাড্রেস ছেড়ে দেওয়া ব্লকের হতে পারে। ইনডেক্স রাখো, দরকার হলে বর্তমান মালিক থেকে নতুন পয়েন্টার নাও।

ভেক্টরের ইন্টারফেস মেমরি নেওয়ার নিয়ম না জানিয়েও ইনডেক্স দিয়ে পড়তে দিতে পারে। কলার শুধু i < size হলে এলিমেন্ট i চাইবে। ভেতরে বড় করার সময় values আর capacity বদলালেও যৌক্তিক পজিশন একই থাকে। দীর্ঘ সময় এলিমেন্টের অ্যাড্রেস রাখার বদলে ইনডেক্স ফেরত দিলে এই সীমা মানা সহজ হয়। তবু কোন কাজে ধার নেওয়া পয়েন্টার অকার্যকর হতে পারে, তা ইন্টারফেসে বলো।

কাজের অভ্যাস

append-কে পুরো একটা লেনদেন হিসেবে ভাবো: সমর্থিত ক্যাপাসিটি হিসাব করো, মেমরি চাও, সফল কি না দেখো, মালিকানা আপডেট করো, তারপর মান লেখো। ব্যর্থতার রিটার্ন মান অর্থপূর্ণ রাখো, যাতে কলার মান সেভ হয়েছে ধরে না নিয়ে ঠিক সিদ্ধান্ত নিতে পারে।

Amortized খরচ বোঝাতে resize-এর সীমা আর মোট কপি দুটোই দেখাও। ছোট করার নিয়ম বোঝাতে সীমার কাছে পালা করে যোগ-বিয়োগ দেখাও। দুইভাবে দেখলে দুই ধরনের ভুল ধরা পড়ে। 1024 ঘরের সীমা এই ছোট লাইব্রেরির সিদ্ধান্ত; সব ডাইনামিক অ্যারের বৈশিষ্ট্য নয়।

সি ভার্সন নিয়ে কথা

ভেক্টরে C17-এর মেমরি নেওয়ার ফাংশন আছে। realloc(NULL, positive_size) প্রথম মেমরি নিতে পারে। এখানে শূন্য সাইজে realloc কল করা হয় না, তাই শূন্য সাইজ নিয়ে ভার্সনভেদে আচরণের সমস্যা এড়ানো যায়। size_t-এর জন্য %zu দিয়ে প্রিন্ট করা হয়; এটি C99 থেকে আছে।

সারকথা

ভেক্টরে সরাসরি ইনডেক্স দিয়ে পড়ার সঙ্গে বদলানো যায় এমন স্টোরেজ থাকে। ব্যর্থতায় মালিকানা বাঁচাও, আর resize-এর কাজ পুরো সিকোয়েন্স জুড়ে হিসাব করো। এবার সিঙ্গলি লিংকড লিস্ট-এ আলাদা মেমরির নোড দেখো।
