Finish a branch before trying its sibling

Imagine exploring a corridor until no new room remains, then returning to the most recent junction. You remember which doorway to try next. Depth-first search, or DFS, uses this pattern to explore a graph through nested calls or explicit stack frames.

DFS gives two useful events for each reached vertex. Discovery happens when exploration enters it for the first time. Finishing happens after all its neighbors have been inspected and every recursive child has returned. The two orders differ because a parent cannot finish before its active descendants.

A visited array prevents a cycle from causing endless recursion. Mark a vertex at entry, before exploring a neighbor. Our examples examine ascending neighbor IDs, matching the BFS lesson's graph choices. The traversal reaches the same component as BFS from that source, but the route and visit order usually differ.

A frame must remember where to resume

Recursive DFS stores the current vertex and the loop's next neighbor position in each active call frame. The recursive example prints enter U before its neighbor loop and leave U afterward. When a child returns, the parent's loop continues where it stopped, rather than restarting from its first neighbor.

The iterative example recreates that state with stack[top] and next[top]. The top index identifies the active frame. If the frame still has a neighbor, advance its saved next index before deciding whether to descend. On an unseen neighbor, mark it and push a fresh frame whose next index begins at zero.

mark start; enter[start] = ++clock; push frame(start,0)
while frames remain
    u = top; advance its next neighbor index
    if neighbor v is unseen: mark v; enter[v] = ++clock
        push frame(v,0)
    if no neighbors remain: leave[u] = ++clock
        pop the exhausted frame and resume its parent
report discovery order, finish order and times

The integer clock begins at zero and increases on every entry and exit. Enter and leave arrays begin at zero, so an unreached vertex is distinguishable from any recorded event. Our seven-vertex graph uses at most seven active frames and fourteen event times. The explicit stack stores suspended calls, not arbitrary future visits.

Read the information DFS provides

A DFS interval [enter[u],leave[u]] contains every descendant's interval. Two completed vertices have either nested or disjoint intervals in the DFS forest. For example, vertex two's interval 6..7 sits inside vertex four's 5..8. This is a relation in the traversal tree, not a claim that the original graph had only tree edges.

The discovery edges form a tree within one reached component. Other inspected edges can connect vertices already seen. In an undirected cycle, the reverse parent edge must be distinguished from another visited neighbor if you are detecting cycles. In a directed graph, cycle detection needs active-versus-finished states, not only a single visited boolean.

DFS is a foundation for connected components, topological ordering and cycle analysis. For a DAG, reversing finish order gives a topological order when all vertices are explored. A graph with a directed cycle cannot receive a valid topological ordering, so cycle checks must accompany that use.

A DFS path does not guarantee the fewest edges. In graph zero, it reaches two through 0,1,3,5,4,2 even though the original graph has edge 0-2. BFS would discover two at distance one. Use DFS for exploration structure and finishing information, and BFS for minimum-hop routes in an unweighted graph.

A simpler iterative DFS may push vertices in reverse neighbor order and skip them when already visited. That can produce a useful discovery order, but it does not directly reproduce recursive return events. The frame method is necessary when you want exact matching entry/exit times and parent resumption.

Bound active calls and include other components

Adjacency-list DFS takes O(V+E) time over a complete forest: each vertex is entered once and every adjacency entry is inspected once. Visited flags, event arrays and the worst-case active stack use O(V) auxiliary storage. A path can require V simultaneous calls, so recursive depth is not always logarithmic.

Our fixed graph builder first uses a matrix, with O(V squared) construction work and rectangular storage. Traversal uses active neighbor counts afterward. For a large sparse graph, build compact lists directly and choose an explicit frame stack when the language call stack could overflow.

A no-edge graph from one source has one entry and one exit. A singleton behaves the same way. A complete graph still marks every vertex once, although it examines many already-seen neighbors. The explicit stack capacity is sufficient because only unseen vertices create new frames.

To cover disconnected graphs, keep seen across searches and scan vertices in ID order. The first unseen vertex becomes a new forest root. Example three does this and counts components: graph zero gives two, while the empty-edge seven-vertex graph gives seven. Resetting seen between roots would repeat old components and overcount them.

Remember suspended work

Restarting the neighbor loop after every pop

A parent would repeatedly inspect earlier edges and might descend incorrectly. Store its next index in the frame and advance before pushing a child.

Assigning finish time at discovery

The child calls have not happened yet. Record finish only when the active frame has no neighbors left to inspect.

Calling a traversal forest the original graph

Tree edges record first discoveries. The original graph may also contain cycles and extra connections that the forest does not retain.

Discovery and finish timestamps are often useful when checking an implementation. Every reached vertex must have enter less than leave. Every event number should occur once, and a descendant interval should fit inside its active ancestor. Those facts expose incorrect early pops even when a printed discovery order looks reasonable.

To reproduce a particular recursive trace, match both neighbor order and marking time. Pushing all unvisited neighbors at once can choose a different parent for a vertex reached from several directions. Saving one active frame and descending one child at a time keeps the iterative program's behavior aligned with the recursive explanation.

C17 calls and explicit frames

C17 supports recursive function calls but promises no portable maximum recursion depth. The explicit DFS frame array avoids that dependency for the bounded graph and makes each saved neighbor index visible.
