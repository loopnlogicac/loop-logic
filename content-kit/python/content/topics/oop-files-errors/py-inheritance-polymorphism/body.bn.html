এক অনুরোধ, কয়েক রকম উত্তর

ক্যাম্পাসে regular আর evening course-এর charge আলাদা, caller তবু fee() চায়। পলিমরফিজম মানে এক interface-এ ভিন্ন আচরণের অবজেক্ট ব্যবহার। প্রতি report-এ type check-এর বদলে course-কে fee জিজ্ঞেস করো।

ইনহেরিট্যান্স existing ক্লাস থেকে নতুন ক্লাস সংজ্ঞা দেয়। আগেরটি parent/base, নতুনটি child/subclass। আচরণ ভাগ হয়, তবে শুধু code share করতেই family নয়।

Parent চাওয়া জায়গায় subclass মানাতে হবে। Report fee method চায় মানে সব subtype-এ একই অর্থের operation। fee অপ্রাসঙ্গিক list দিলে Python সংজ্ঞা নিলেও caller ভাঙে।

ক্লাস বাড়িয়ে তার অংশ initialize

Subclass নামের পরে বন্ধনীতে parent। নিজের নেই এমন attribute-method ancestor-এ পাওয়া যায়। একই নামে method দিলে inherited আচরণ override হয়। Receiver-এর lookup প্রথম implementation বাছে।

class Course:
    def __init__(self, credits):
        self.credits = credits

    def fee(self):
        return self.credits * 1000

class LabCourse(Course):
    def __init__(self, credits, lab_fee):
        super().__init__(credits)
        self.lab_fee = lab_fee

    def fee(self):
        return super().fee() + self.lab_fee

super().__init__ parent-এর initialization রাখে। এটি explicit কল, নতুন initializer-এ automatic extra কাজ নয়। Subclass initializer না দিলে parent-এরটি inherit হতে পারে। দুই case আলাদা, আসলে কোন __init__ মিলছে দেখো।

অঙ্কের আগে method lookup trace

LabCourse(3, 500) subclass initializer পায়। সেটি parent-কে 3 দেয়, একই LabCourse-এ credits থাকে। ফিরে lab_fee-ও ওই অবজেক্টে। ভেতরে আলাদা parent অবজেক্ট হয় না।

course.fee() LabCourse থেকে override পায়। super().fee() তার পর থেকে Course.fee খোঁজে। Base 3000, override 500 যোগে 3500। দুটোতেই self একই instance।

Method resolution order বা MRO ক্লাস খোঁজার sequence। এখানে single inheritance-এ child আগে parent। super() এই ক্রম ধরে, সব hierarchy-তে fixed parent-এ নিঃশর্ত লাফ নয়।

LabCourse.fee(self)
    |
    +-- super().fee() --> Course.fee(self) --> 3000
    |
    +-- self.lab_fee যোগ ------------------> 3500

C জানা থাকলে

C ফাংশন পয়েন্টার আর explicit structure দিয়ে আচরণ বদলাতে পারে। Python object.fee()-তে ordinary method lookup। নিজে virtual table বাছতে হয় না, একই call দিতে declared base-ও বাধ্যতামূলক নয়।

Caller না লিখে contract আবার ব্যবহার

উদাহরণ caller-এর request আর বাছা implementation আলাদা করে। Override super ডাকলে আউটপুট order দেখো। শেষটিতে student wallet রাখে, student-কে wallet-এর ধরন করে না।

Base fee-তে lab charge যোগ

একই fee call Course-এ 3000, LabCourse-এ 3500। Override base calculation-এ নিজের charge যোগ করে।

বাড়ানো method call দেখো

Override আগে base ডাকে বলে base-এর পরে urgent। দুটো এক Urgent instance-এ কাজ করে।

সম্পর্কহীন লেবেল provider নাও

Room আর Team-এর custom shared parent নেই। show_label শুধু লেবেল operation চায়, প্রতিটির string প্রিন্ট করে।

Student-এর সঙ্গে wallet composition

Student attribute-এ Wallet রাখে। Helper দিয়ে balance পায়, isinstance দেখায় Student Wallet subtype নয়।

অবজেক্ট কী করতে পারে জিজ্ঞেস

Duck typing-এ named family না চেয়ে supported operation ধরে কোড। send_report(target) target.send(message) ডাকতে পারে। EmailSender আর ScreenSender unrelated হলেও agreed send behavior দিলে দুটোই চলে।

একই method নাম contract-এর শুরু। Caller argument, return আর effect-ও চায়। Message উপেক্ষা করা send শুধু call সফল বলেই উপযুক্ত নয়। Contract document করে implementation-জুড়ে behavior টেস্ট করো।

সত্যিই family membership চাইলে isinstance। সাধারণ subclass instance-এ isinstance(child, Parent) true। Subclass নিতে চাইলে type(value) is Parent এড়াও, সেটি exact type। কোনোটিই business meaning প্রমাণ করে না।

Has-a সম্পর্কে Composition নাও। Student-এর Wallet আছে, Student Wallet নয়। Attribute-এ রেখে দরকারে method ডাকো। সব public operation inherit না করেই helper পাল্টানো যায়।

Subclass parent-এর সব promise রাখে কি না ভাবো। Special account charge যোগ করলেও caller নির্ভরযোগ্য balance চায়। Child-এর rule-এ parent-এর স্বাভাবিক কাজ invalid হলে family আবার ভাবো বা helper নাও।

Inherited code-এ receiver ধরো

Inherited method self-এ আরেক method ডাকতে পারে। Child সেটি override করলে parent-এ সংজ্ঞা দেওয়া caller থেকেও child implementation চলে। Receiver আসল child-ই থাকে; inheritance ভেতরের সব call parent-এ freeze করে না।

যেমন Course.summary self.fee() ডাকে। LabCourse summary অপরিবর্তিত inherit করে fee override। LabCourse(...).summary তখন specialized fee নেয়। Shared format স্থির, এক হিসাব আলাদা হলে কাজে লাগে। দুই call-এ self trace করো।

প্রতি ভবিষ্যৎ subtype-এর জন্য shared summary-তে type branch যোগ কোরো না। fee interface-এ caller formula না জেনেও operation চায়। Formula উপযুক্ত ক্লাস-এ, result type consistent রাখো।

প্রতিটি supported type বানিয়ে একই reporting ফাংশন-এ দেওয়া সহজ টেস্ট। Call আর অর্থ মেলে দেখো। শুধু একই base inherit হয়েছে দেখার চেয়ে সরাসরি contract টেস্ট।

Initialization আর interface-এর promise

Parent initializer বাদ

নিজের __init__ inherited-টি বদলায়। credits initialize না হলে পরে AttributeError। Parent state ধরার আগে তার argument-সহ super().__init__।

বাড়ানোর বদলে আবার নিজেকে কল

fee override-এর self.fee() একই override আবার পায়। অন্য stop না থাকলে RecursionError। MRO-র পরের implementation চাইলে super().fee()।

চাওয়া call shape বদল

Parent fee() extra argument না নিলে child-এ day required করা caller ভাঙে। Compatible signature আর অর্থ রাখো। Optional পার্থক্য construction বা documented parameter-এ।

লম্বা inheritance chain

গভীর family-তে আচরণের উৎস বোঝা কঠিন। Shared meaning-সহ ছোট hierarchy ভালো। শুধু একই operation লাগলে artificial parent-এর চেয়ে duck-typed ফাংশন পরিষ্কার।

Single inheritance দিয়ে শুরু

Zero-argument super(), override আর duck typing Python 3.10–3.12-তে চলে। Multiple inheritance-ও আছে, Class.__mro__ দিয়ে ক্রম দেখা যায়। Cooperative multiple inheritance-এ সাবধান compatible method লাগে, এই পরিচয়ের বাইরে। super সবসময় immediate textual parent, উদাহরণ তা বলে না।

Implementation বদলালেও operation স্থির

ইনহেরিট্যান্স অর্থপূর্ণ parent interface নেয়, override বিশেষ আচরণ, super lookup চালায়। Duck typing unrelated ক্লাস-কে একই contract দেয়। পরের special method print, len, comparison আর operator-এ অবজেক্ট জোড়ে।
