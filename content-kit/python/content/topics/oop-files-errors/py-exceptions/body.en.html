Give failures a route back to the caller

A student types seventy where your program expects an integer. int cannot convert that text. Instead of returning an unrelated number, it raises ValueError. An exception is an object describing a failure that interrupts the current path of execution. A suitable handler can recover or explain the problem.

Exceptions separate successful results from failures. A mark of zero can be valid, so returning zero for invalid input would lose information. Raising an exception preserves that distinction. The caller can decide whether to ask again, skip a record or stop the operation.

You do not need to catch every possible exception everywhere. Handle a failure where the program has enough information to respond usefully. A calculation function can reject an invalid argument while the user-interface function explains it. Unexpected programming mistakes should remain visible during development.

Match specific exception types

Place a risky operation in try and follow it with an except clause naming the failure you expect. The name after as receives the exception object. Printing its message can help a user, but avoid depending on exact interpreter-generated wording for your program's logic.

try:
    marks = int(text)
except ValueError:
    print("Enter a whole number")
else:
    print(f"Read {marks}")
finally:
    print("Input attempt finished")

The else block runs when try completes normally, without an exception, return, break or continue. Put successful follow-up work there when you do not want its errors caught by the same except. The finally block runs when control leaves the statement through normal Python mechanisms, including a handled or unhandled exception.

Multiple except clauses are considered in order. Put a more specific subclass before a broader parent. A tuple such as except (ValueError, TypeError) handles several named categories with one response. Do not write except ValueError or TypeError, because that expression does not form the intended tuple.

Follow the stack until a handler matches

When an operation raises, Python stops executing the remaining statements in that try path. It checks nearby handlers and, if none matches, propagates the failure to the caller. The search can continue through several function calls. Without a matching handler, the program ends with an error report and traceback.

A traceback lists the active calls leading to the error. Start by reading the final exception type and message, then inspect the relevant lines above it. The deepest line often shows where the operation failed, while earlier frames explain how that value arrived.

An except clause catches instances of the named class and its subclasses. ZeroDivisionError, ValueError, TypeError and KeyError describe different problems. Broadly catching Exception can hide a wrong variable or missing attribute alongside the input failure you meant to handle.

Name domain failures clearly

Use raise ValueError("marks must be from 0 to 100") when the argument has a supported type but an invalid value. TypeError is appropriate when the type itself is unsupported. Choose the category so callers can distinguish failures without searching the message text.

A custom exception class gives a domain-specific category. For example, InsufficientFunds(Exception) identifies a rejected withdrawal. An empty class body with pass is enough to create the type. Add attributes only when callers need structured details such as the requested and available amounts.

Raise the custom error at the point where the rule fails. Catch it where the program can choose another action. Do not print an error and then return a normal-looking success value. A caller could accidentally continue as if the operation succeeded.

Inside a handler, bare raise re-raises the current exception and preserves its traceback context. Use this when a layer logs or cleans up but cannot recover. To translate a low-level failure into a domain explanation, raise NewError(...) from original. The explicit cause preserves the diagnostic relationship.

Avoid inheriting ordinary domain errors directly from BaseException. Exception is the usual parent. KeyboardInterrupt and SystemExit belong to a broader control category, and a routine recovery handler should not swallow them by accident. A bare except catches even those exits.

Keep cleanup separate from the result

Use finally for actions that must happen when leaving an operation, such as releasing a resource acquired earlier. A return from inside try still passes through finally. This makes cleanup reliable under ordinary Python control flow, but does not promise execution after abrupt process termination or a power failure.

Do not return from finally. That can replace a pending return value or suppress an active exception, making a real failure disappear. Cleanup should finish its work and let the original result or error continue. A cleanup action can itself fail, so keep it simple and understand the resource's API.

For files, the with statement usually expresses cleanup more clearly than writing manual close calls. The file lesson uses that form, and context managers later explain the protocol behind it. Try/finally remains useful when no suitable context manager exists.

Catching every error around a long function

A broad try can confuse bad input with a bug in later arithmetic or display code. Limit the try to the conversion or operation you intend to recover from. Use else for the successful next stage.

Silencing errors with pass

An empty handler can leave partially updated state with no explanation. Ignore only an explicitly harmless case. Otherwise report the failure or let it propagate.

Use ordinary exception handling first

The exception classes and try/except/else/finally patterns shown work on Python 3.10–3.12. Exception groups and except* arrived in Python 3.11 and are outside this lesson. User-facing programs should provide their own stable explanations rather than assume error wording is identical on every Python release.
