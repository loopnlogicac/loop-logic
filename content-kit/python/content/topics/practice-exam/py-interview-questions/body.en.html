Make a short answer precise enough to trust

A Python interview answer should help another person predict behavior. Start with the rule, give a small example and state a useful limit. The fifty numbered short questions below cover objects, collections, functions, iteration and practical design. Their worked answers provide a starting explanation rather than a script to memorize.

Try saying each answer in your own words before reading it. If a claim sounds absolute, look for the condition that makes it true. Python guarantees dictionary insertion order, while reference counting describes common CPython behavior. Knowing that difference prevents a confident answer from becoming an inaccurate one.

Questions 1–20: explain what is shared

The first ten answers concern names, identity, copying, hashing and lifetime. Draw references when explaining mutation. A tuple can contain a mutable list, so immutable outer structure does not promise deep immutability. A shallow copy creates one new container while retaining nested references.

Questions eleven through twenty compare practical collection choices. Discuss the information each structure preserves: a list keeps order and duplicates, a set keeps unique hashable values, and a dictionary links unique keys to values. Expected lookup costs help explain choices, but construction time and memory also matter.

When describing an idiom such as dict.fromkeys, mention the hashability requirement. When discussing zip, distinguish its default shortest-input behavior from strict checking. A concise answer becomes more useful when it includes the assumption that the idiom needs.

Questions 21–40: follow definitions and calls

The next group follows scope, arguments, closures and decoration. Ask when a value is evaluated: at definition, at call or during later iteration. That timeline explains both shared default lists and closures that observe a loop's later binding.

Iteration questions separate an iterable from its iterator and a generator definition from actual advancement. Calling a generator function creates a suspended object. Consuming it changes its state. A second list conversion cannot recreate values that have already been consumed.

Object-design answers cover duck typing, composition and dataclasses. Prefer a small behavioral contract over an unnecessary hierarchy. A generated initializer saves repetitive code, but it does not supply every validation rule. Frozen fields likewise do not recursively freeze referenced objects.

Questions 41–50: state the operating assumptions

The final ten answers connect exceptions, files, annotations, tests, concurrency and data tools. Explain which failures a handler anticipates. Describe what cleanup guarantees and what it does not guarantee. Successful parsing is only one step toward a valid application record.

For concurrency, name the implementation and build assumptions. Ordinary GIL-enabled CPython threads can help waiting-heavy work while limiting simultaneous execution of Python bytecode. Extensions and optional free-threaded builds change that picture. Avoid turning one implementation detail into a universal rule about every Python program.

For library choice, begin with the work: numerical arrays, labeled tables or figures. A familiar dependency is not automatically the right dependency. Explain what capability the application needs, and keep a standard-library solution when it expresses the task more clearly.

Defend an answer with an observable example

The fifteen quiz questions include five runnable traces. Predict each result before executing it, then explain why a tempting alternative is wrong. If you confuse list.sort with sorted, demonstrate both return values. If you confuse shallow and deep independence, mutate a nested list.

For a longer practice session, ask a partner to change one assumption after each answer. What if a value is unhashable, an input is empty or a generator is already exhausted? Those follow-ups test whether you understand the contract beyond a memorized phrase.
