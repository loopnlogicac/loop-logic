একই প্রশ্নের ছোট রূপ সমাধান

চার factorial পেতে চারকে তিন factorial দিয়ে গুণ করা যায়। ছোট প্রশ্নের গঠন একই। রিকার্শন ছোট বা সহজ সংস্করণে ফাংশন কল করে, তারপর উত্তর মেলায়।

থামার জায়গা চাই। Factorial zero factorial-এ পৌঁছায়, যার মান এক। ছোট পরিচিত উত্তর না থাকলে কল আরও কাজ চেয়েই যাবে। ভালো design থামার নিয়ম আর সেদিকে অগ্রগতি দুটো বোঝায়।

ট্রি, nested structure আর divide-and-conquer search-এ রিকার্শন স্বাভাবিক। লম্বা সোজা sequence-এ লুপ পরিষ্কার, call মেমরি কম। সমস্যার গঠন স্পষ্ট করে এমন পদ্ধতি নাও।

রিকার্সিভ step-এর আগে base case

def factorial(number):
if number == 0:
    return 1
return number * factorial(number - 1)

Base case আর কল ছাড়াই উত্তর দেয়। রিকার্সিভ step সমস্যা ছোট করে ফেরত ফল মেলায়। ফাংশন nonnegative integer ধরে; negative-এ এক কমালে zero-র দিকে যায় না।

ইনপুট bound contract-এর অংশ, শুধু টেস্ট-এর সুবিধা নয়। কেন reduction বৈধ, call depth সামলানো যায় বোঝায়। ভুল মান reject করো বা caller বৈধ মান দেবে বলো।

রিকার্সিভ result ফেরানো জরুরি। শুধু factorial(number - 1) কল ছোট উত্তর হিসাব করে ফেলে দেয়। পরের গুণে expression value দরকার, তাই return-এ মেলাবে।

প্রতি অপেক্ষার কলে নিজস্ব local state

Call স্ট্যাক active কল আর থামানো কাজ রাখে। factorial(3) অপেক্ষা করে factorial(2), সেটি factorial(1), সেটি factorial(0)-এর। সবার আলাদা number binding।

factorial(3) থেকে ফেরা
কলফেরার হিসাবফল
factorial(0)Base মান1

factorial(2)2 * 12

নামার সময় অপেক্ষার কাজ জমে। ফেরার পথ unwinding: সবচেয়ে গভীর অপেক্ষার কল থেকে বাইরে কাজ চলে। রিকার্সিভ call-এর আগে প্রিন্ট descent order, পরে প্রিন্ট unwind order।

Depth আর total call count এক নয়। Branching recurrence অনেক কল করলেও একসঙ্গে ছোট chain active হতে পারে। Time আর স্ট্যাক মেমরি বোঝাতে দুটো বিশ্লেষণ করো।

C জানা থাকলে

C-র মতো প্রতিটি active রিকার্সিভ call-এর local state আলাদা। Python interpreter রিকার্শন limit-ও মানে, tail রিকার্শন বাদ দিয়ে optimize করে না। Big integer fixed-width factorial overflow এড়ায়, কিন্তু বাড়তে থাকা মানে সময়-মেমরি লাগে।

Linear descent আর repeated subproblem তুলনা

Factorial আর GCD-তে কলপ্রতি এক child। Fibonacci-তে দুই, একই ছোট argument বারবার। Cache উদাহরণ সেই request রেখে আবার হিসাব এড়ায়।

Factorial কল খুলে ফেরো

কল 4 থেকে 0-তে নামে। Base 1 ফেরায়, অপেক্ষার কল 1,2,3,4 দিয়ে গুণ করে। Zero factorial রিকার্সিভ call ছাড়া empty-product মান 1 দেয়।

নামা আর ফেরার trace

ঢোকা প্রতিটি কল রিকার্সিভ call-এ থামে। enter 0 আর base-এর পরে leave 1,2,3। Call-এর পরের কাজ unwinding-এ।

কমতে থাকা remainder-এ GCD

Pair (48,18), (18,12), (12,6), শেষে (6,0)। দ্বিতীয় অংশ zero-তে থামে। বলা gcd(0,0)=0 নিয়ম একই base case সামলায়।

Repeated Fibonacci subproblem cache

Decorator argument ধরে উত্তর রাখে। 10-এ প্রথম কলে এগারো distinct miss, আট repeated hit। Clear saved result সরায়। এটি memoisation, এখানে standard-library decorator দিয়ে পরিচয়।

Linear call depth-এর বদলে লুপ

লুপ accumulated product আর next factor রেখে একই recurrence করে। Factor-প্রতি Python call এড়ায়। লম্বা সোজা sequence-এ প্রায়ই ভালো implementation।

Repeated কাজ কমাও, depth ভুলো না

Python রিকার্শন-depth limit রাখে। বেশি nesting-এ সাধারণত RecursionError। পরিবেশ আর আশপাশের কলে available depth নির্ভর করে, তাই default limit থেকে নির্দিষ্ট safe count বলবে না।

sys-এর getrecursionlimit আর setrecursionlimit আছে, কিন্তু limit বাড়ানো সাধারণ সমাধান নয়। খুব বেশি হলে native স্ট্যাক শেষ হয়। শেষ কাজ রিকার্সিভ call হলেও Python tail call বাদ দেয় না।

Memoisation আগে সমাধান করা subproblem-এর উত্তর রাখে। functools-এ lru_cache আছে। @-এর line পরের ফাংশন caching দিয়ে wrap করে; decorator পাঠে syntax বিস্তারিত।

Cache ছাড়া Fibonacci একই মান বারবার করে exponential কাজ। শুরুতে empty unbounded cache থাকলে zero থেকে n প্রতিটি argument একবার। Subproblem count linear, cache storage linear, রিকার্সিভ depth-ও linear থাকে।

এই খরচে arithmetic operation unit ধরা। Fibonacci মান n-এর সঙ্গে বাড়ে, big-integer addition সত্যিই constant নয়। তুলনার উদ্দেশ্য repeated কাজ চেনা, যেকোনো বড় সংখ্যা বিনা খরচে বলা নয়।

lru_cache hashable argument চায়। Argument-নির্ভর deterministic হিসাবে নাও। Hidden changing state, current time বা returned mutable অবজেক্ট edit cache বিভ্রান্তিকর করে। দরকার ফুরালে cache_clear saved answer ছাড়ে।

Finite maxsize-এ lru_cache সীমিত recent argument combination রাখে। Eviction-এ পরের request আগে করা ফল আবার হিসাব করতে পারে। মেমরি আর repeated কাজের trade-off। Unbounded-এ eviction নেই, বেশি অবজেক্ট থাকে।

Cache argument আর return value-র reference-ও ধরে। একই mutable list আলাদা caller পেলে shared edit দেখা যায়। Immutable ফল ভালো, বা copy দেওয়ার design স্পষ্ট করো। Mathematical ফাংশন-এর মতো call হলে cache বোঝা সহজ।

Binary search-এ প্রতি ধাপে interval অন্তত অর্ধেক, depth logarithmic। Factorial-এর linear depth থেকে আলাদা। শুধু রিকার্সিভ বললে খরচ বোঝা যায় না, call ট্রি-র গঠন বলে।

থামা, ফল মেলানো আর resource দেখো

কল পৌঁছায় না এমন base case

Negative থেকে এক কমালে zero-only case থামায় না। প্রতি বৈধ পথে কমতে থাকা nonnegative মাপ দেখাও। GCD-তে positive remainder, binary search-এ interval ছোট।

Slice করে সুবিধা হারানো

রিকার্সিভ binary search-এ slice copy নয়, index boundary পাঠাও। Slice comparison-এর বাইরে সময় আর storage বাড়ায়। Half-open interval-এ low, high-এর সমান বা বড় হলেই empty বোঝা সহজ।

সীমাহীন linear depth-এ রিকার্শন

লুপ factor-প্রতি frame ছাড়াই factorial জমায়। Memoisation অতিরিক্ত গভীর linear chain সারায় না। বড় depth-এ ইটারেটিভ dynamic প্রোগ্রামিং বা explicit স্ট্যাক ভাবো।

আগে ছোট trace: zero, one, normal, তারপর বলা সবচেয়ে বড় ইনপুট। ভুল identity, off-by-one reduction আর available depth-এর ধারণা ধরা পড়ে।

Cache tool, থামার নিয়ম নয়

functools.lru_cache, cache_info আর cache_clear Python 3.10–3.12-তে আছে। রিকার্শন limit runtime setting, ঠিক এত depth সফল হবে portable প্রতিশ্রুতি নয়।

Call optimize-এর আগে অগ্রগতি প্রমাণ

রিকার্শনে ছোট direct answer আর বৈধ shrinking step চাই। Cache repeated subproblem, লুপ অদরকারি depth এড়ায়। পরের higher-order ফাংশন ফাংশনকেই reusable value ধরে।
