উত্তর যাচাই করার মতো ধাপ দেখাও

সম্পূর্ণ DBMS উত্তরে আগে অনুমান থাকবে, মাঝের যুক্তি দেখা যাবে এবং শেষে সমর্থিত সিদ্ধান্ত থাকবে। এই বারোটি সমাধানসহ প্রশ্নে ডেটাবেস ডিজাইন, SQL, normalization ও transaction analysis একসঙ্গে আছে। সমাধান না দেখে চেষ্টা করো, তারপর নিজের বাদ পড়া যুক্তির ধাপ মেলাও।

নম্বর দেখে কতটা বিস্তারিত চাই বোঝো। ডিজাইনে cardinality ও key, গণনার প্রশ্নে closure, graph edge বা পুনর্গঠিত tuple দেখাতে হবে। SQL-এ প্রতি row-এর অর্থ ও সীমার ঘটনাগুলো পরীক্ষা করো। শেষের ছোট quiz বড় উত্তরের আলাদা সিদ্ধান্ত যাচাই করে।

ডিজাইন ও relational query

১. Student, section ও একই কোর্সের বারবার offering-এর Chen ER model আঁকো; enrollment ও result টেবিলে বসাও।

নম্বর: ১০।

[Student] M --- <Enrolls> --- N [Section]
                   |               | N
             (enrolled_on)      <Offers>
                                   | 1
                                [Course]

Student-এর student_id, Course-এর course_id এবং Section-এর section_id দাগ দিয়ে key দেখাও। প্রতি section ঠিক একটি course পড়ায়; একটি course-এর একাধিক section হতে পারে। Student ও section—কারও enrollment থাকা বাধ্যতামূলক নয়। enrolled_on-কে Enrolls সম্পর্কে বসাও। পূর্ণ Chen চিত্রে entity আয়তক্ষেত্র, relationship diamond এবং attribute oval হবে।

Student ও Course-এর আলাদা টেবিল করো। Section-এ course_id non-NULL foreign key। M:N সম্পর্ক থেকে Enrollment(student_id,section_id,enrolled_on) করো; identifier জোড়াটি key এবং parent-এর foreign key। Result(student_id,section_id,marks)-এ একই primary key ও Enrollment-এর দিকে composite foreign key রাখো। Enrollment-এর result নাও থাকতে পারে। এতে একই কোর্সের অন্য offering-এর registration আলাদা চেনা যায়।

২. Room number শুধু নিজের building-এর ভেতর unique হলে পরিচয় ও relational mapping দেখাও।

নম্বর: ৬।

[Building] 1 === <<Contains>> === N [[Room]]
 building_id                       room_number
 (underlined)                      (partial key)

Room weak: শুধু room_number দিয়ে ভিন্ন building-এর 101 নম্বর কক্ষ আলাদা করা যায় না। Room-এ double rectangle, identifying সম্পর্কে double diamond এবং Room-এর total participation দেখাও। পরিচয় হলো building_id ও room_number জোড়া। Room-এ PRIMARY KEY(building_id,room_number), non-NULL building_id foreign key এবং capacity-এর মতো সাধারণ attribute রাখো। পূর্ণ Chen চিত্রে partial key-এর নিচে সাধারণত ভাঙা দাগ হয়।

৩. Section 31-এ ভর্তি শিক্ষার্থীর নামের relational algebra ও SQL লেখো, প্রকৃত ফল দেখাও।

নম্বর: ৮।

আগে প্রয়োজনীয় registration বাছো, student_id দিয়ে students-এর সঙ্গে join করো, তারপর নাম project করো। Expression: πstudent_name(Students ⋈Students.student_id=Enrollment.student_id σsection_id=31(Enrollment))। নিচের SQL-এ student identity-ও আছে, যাতে একই নামের আলাদা মানুষ চেনা যায়। কেবল নামের set projection চাইলে SELECT DISTINCT student_name নেবে।

SELECT s.student_id, s.student_name FROM students AS s
JOIN enrollments AS e ON e.student_id=s.student_id
WHERE e.section_id=31 ORDER BY s.student_id;

| student_id | student_name  |

|        101 | Ayesha Rahman |
|        102 | Tanvir Hasan  |

৪. খালি section-সহ সব section-এর enrollment count দেখাও। COUNT কেন বেছেছ বোঝাও।

নম্বর: ৮।

sections থেকে শুরু করে LEFT JOIN দিয়ে সব রাখো। Section key দিয়ে group করো। প্রকৃত enrollment-এ child key NULL হতে পারে না, তাই COUNT(e.student_id) আসল matching registration গোনে। Section 36-এর outer join NULL-সহ একটি row বানালেও child count শূন্য হয়। COUNT(*) নিলে সেটিই এক গুনত।

SELECT se.section_id, COUNT(e.student_id) AS registrations
FROM sections AS se LEFT JOIN enrollments AS e ON e.section_id=se.section_id
GROUP BY se.section_id ORDER BY se.section_id;

Dependency ও normal form

৫. R(S,C,N,T,M), F={S → N,C → T,SC → M}-এর সব candidate key বের করো এবং 1NF থেকে 3NF-এ ভাঙো।

নম্বর: ১০।

কোনো FD-এর ডান পাশে S বা C নেই, তাই সব key-তে দুটোই লাগবে। SC+ শুরুতে SC; S → N দিয়ে N, C → T দিয়ে T এবং SC → M দিয়ে M পাওয়া যায়। তাই SC একমাত্র candidate key। N, T, M nonprime। প্রতি cell-এ একটি scalar মান ধরলে শুরুতে relation 1NF।

S → N ও C → T, SC-এর proper subset-এর ওপর নির্ভর করে, তাই 2NF ভাঙে। Student(S,N), Course(C,T), Registration(S,C,M) করো; key যথাক্রমে S, C, SC। প্রতিটি nontrivial projected determinant key, তাই তিনটিই BCNF এবং 3NF। Student split-এর common S থেকে SN, Course split-এর common C থেকে CT নির্ধারিত হয়; দুটো ধাপই lossless। প্রতিটি মূল FD একটি component-এ স্থানীয়, তাই dependency-ও থাকে।

৬. R(A,B,C)-তে শুধু A → B। AB,BC split পরীক্ষা করো; lossy হলে counterexample দাও।

নম্বর: ৮।

Common attribute B। তার closure শুধু B; AB বা BC কোনোটিই নির্ধারণ করে না। তাই binary lossless criterion মেলে না। r={(a1,b,c1),(a2,b,c2)} নাও; এটি A → B মানে। AB projection-এ (a1,b),(a2,b), BC-তে (b,c1),(b,c2)। Join করলে মূল দুটির সঙ্গে (a1,b,c2),(a2,b,c1) যোগ হয়। বাড়তি tuple প্রমাণ করে A ও C-এর মূল যোগসূত্র হারিয়েছে।

৭. R(S,C,I), SC → I,I → C-এর 3NF ও BCNF তুলনা করো; IC,SI split আলোচনা করো।

নম্বর: ১০।

প্রতি key-তে S লাগে; C বা I যোগ করলে পূর্ণ হয়। Key SC ও SI, তাই তিন attribute-ই prime। SC → I-এর বাম পাশে superkey; I → C-এর ডান পাশে prime। দুটোই 3NF মানে। I+ হলো IC, যেখানে S নেই; তাই I → C BCNF ভাঙে।

I → C দিয়ে IC ও SI করো। Common I থেকে IC নির্ধারিত, তাই lossless। Projected nontrivial FD মিলিয়ে শুধু I → C পাওয়া যায়। তার অধীনে SC+ থেকে I আসে না; তাই SC → I স্থানীয়ভাবে রক্ষা হয়নি। বাস্তবায়নে ওই নিয়ম আলাদাভাবে প্রয়োগ করো অথবা dependency-preserving 3NF ডিজাইন নাও।

Schedule, recovery ও নিরাপদ access

৮. r1(X),r2(Y),w1(X),r2(X),w2(Y)-এর conflict serializability নির্ধারণ করে graph আঁকো।

নম্বর: ৬।

T1 ----> T2

X-এর r1(X),r2(X) জোড়া read-read, তাই edge নেই। w1(X)-এর পরে r2(X) হওয়ায় T1 → T2 হয়। T1 কখনো Y ছোঁয় না, তাই Y থেকে উল্টো edge নেই। Graph acyclic; T1,T2 একটি topological order ও সমতুল্য serial order। Conflict-serializable হতে interleaving-টি নিজে serial হওয়া লাগে না।

৯. A account 1, B account 2 লক করে, তারপর একে অন্যের account চায়। Detection, retry ও prevention বোঝাও।

নম্বর: ৮।

A --waits for--> B
A <--waits for-- B

চক্রাকারে অপেক্ষা deadlock। InnoDB detection চালু থাকলে engine একটি transaction-কে victim বেছে rollback করে error 1213 দেয়। অ্যাপ idempotent request identity রেখে সীমিত চেষ্টায় সম্পূর্ণ ব্যবসার কাজটি আবার চালায়। সর্বশেষ requester-ই victim হবে এমন নিশ্চয়তা নেই। একই identifier order-এ দুই lock চাইলে এই cycle কমে। Lock timeout-এর rollback boundary আলাদা; সেটিও স্পষ্টভাবে সামলাতে হবে।

১০. Committed transfer-এ wallet 1000/500 থেকে 900/600। পরে uncommitted edit প্রথম wallet 1 করে, তারপর crash। Recovery ও শেষ অবস্থা বোঝাও।

নম্বর: ৮।

Transfer commit হয়েছে, তাই configured durability guarantee অনুযায়ী টিকতে হবে। পরের edit uncommitted; committed data হিসেবে থাকা চলবে না। Recovery প্রয়োজনীয় logged page change replay করে, তারপর engine-এর নিয়মে uncommitted পরিবর্তন undo করতে পারে। শেষ logical অবস্থা 900/600। Checkpoint redo কাজ কমাতে পারে, দ্বিতীয় transaction commit করে না। ফাইল বা media হারালে এখনও আলাদা backup লাগে।

১১. Student search quoted input SQL-এ জুড়ে দেয়। ভুল বোঝাও এবং bound value দিয়ে বিকল্প দেখাও।

নম্বর: ৮।

সাজানো input literal শেষ করে operator বা comment ঢুকিয়ে predicate-এর অর্থ বদলাতে পারে। স্থির statement-এ value placeholder prepare করো, নাম bind করো, execute করে statement deallocate করো। Text তখন মান হিসেবেই থাকে। অ্যাপে connector-এর parameter API নাও, least privilege রাখো এবং কলার কোন student record দেখতে পারবে আলাদা যাচাই করো।

PREPARE search FROM 'SELECT COUNT(*) AS matches FROM students WHERE student_name=?';
SET @name='Ayesha Rahman';
EXECUTE search USING @name;
DEALLOCATE PREPARE search;

১২. InnoDB REPEATABLE READ কেন সব multi-row invariant serial হয়—তার সাধারণ প্রমাণ নয়?

নম্বর: ৮।

Consistent read প্রতিষ্ঠিত snapshot নেয়; write ও locking read বর্তমান version ও lock নেয়। দুই transaction একই invariant পড়েও আলাদা row বদলাতে পারে। শর্তটি রক্ষা না করলে write skew হতে পারে। স্থির snapshot সব workload-এ serial order-এর সমতুল্যতার প্রমাণ নয়। Invariant চিহ্নিত করে উপযুক্ত shared locking, constraint বা serializable execution নাও এবং প্রতিযোগী transaction পরীক্ষা করো।

সিদ্ধান্তের পেছনের যুক্তি যাচাই করো

জমা দেওয়ার আগে অনুমানগুলো দাগাও; শেষ key, query identity বা graph-এর সিদ্ধান্ত চিহ্নিত করো। প্রতিটি দাবির দৃশ্যমান ধাপ আছে কি না দেখো। একই ধারণা অল্প কথায় বোঝানোর অনুশীলনে ইন্টারভিউ প্রশ্ন নাও।
