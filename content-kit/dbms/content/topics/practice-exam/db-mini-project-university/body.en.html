Deliver a small registration service

Build a university service that registers students without exceeding section capacity, records marks for valid enrollments and reports pending results. The project extends the familiar university schema with a transaction-owning registration procedure, a reporting view and two audit triggers.

Keep the scope narrow: one seeded Spring 2026 dataset, one fixed registration date and one result per student-section enrollment. Payment, prerequisites, timetable conflicts and repeated-course replacement are separate requirements. The existing constraints remain active, so a result cannot reference a nonexistent enrollment and marks must stay from 0 through 100.

A capacity check performed outside a transaction can race. Two clients may both see one free seat. The protocol here locks the section row before counting enrollments. All enrollment insertions and capacity reductions must follow a compatible section-lock protocol. A direct privileged INSERT can bypass this rule, so deploy a restricted account with EXECUTE authority rather than unrestricted enrollment DML.

The procedure owns START TRANSACTION, COMMIT and rollback. Call it only when the connection has no active caller transaction. START TRANSACTION can end an existing transaction boundary in MySQL; it does not create a nested transaction. The fixed date is a teaching parameter choice, and a production interface should validate an explicit registration date against its academic policy.

Rectangles name entities and angle brackets stand for relationship diamonds in this compact Chen sketch. Student and Section participate optionally in Enrolls: either may currently have no registration. Every Enrollment has exactly one Student and one Section. A Result is optional for an Enrollment but cannot exist without it.

Department names depend on department_id, course descriptions depend on course_id, and marks depend on the enrollment pair. The existing separate tables respect those dependencies. Store no student name or course title inside results. The audit table intentionally retains old values as history; its rows describe change events rather than current result facts.

Read a section report without multiplied children

Independent per-section counts are joined after aggregation. Section 35 has one pending result; section 36 is empty and has a NULL mean, not a fabricated zero.

The routine’s exception handler rolls back and rethrows SQL exceptions. Duplicate enrollment, absent student and full section failures must leave no new registration. The section SELECT is a current locking read, and the count is the first consistent read after that lock. With no earlier snapshot, a waiting caller counts the registrations committed before it acquired the section lock.

The audit records omit timestamps and human actor identity to keep this small model explicit. They do not claim tamper resistance. Administrators can modify tables, cascaded result deletion does not invoke child DELETE triggers, and rollback removes audit evidence. A production audit design needs authenticated identity, retention, access restrictions and a policy for failed attempts.

Exercise failures and concurrent callers

Try a valid first enrollment, its duplicate, an absent student, an absent section and a full section. For capacity concurrency, set section 36 capacity to one in a fresh schema and start two registration calls for different students on separate connections. Exactly one may commit under this protocol. The waiting caller must either report full or handle a transaction failure; the count must never exceed one.

For result integrity, attempt marks below zero, above 100 and a result with no enrollment. All must be rejected by existing constraints. Also test 79 then 80 to cross the A to A+ boundary. Confirm the generated grade and audit old/new values together, rather than trusting the number of trigger rows alone.

The supplied reports preserve all six sections. Validate one empty section, one with pending results and one with several recorded results. The average should use only recorded marks. Keep student, enrollment and result privileges separate according to staff duties, and bind every application-supplied value through the connector API.

Protect the protocol as well as the SQL

Leaving a bypass route to enrollment

A section lock works only when competing enrollment changes use the same protocol. Restrict direct DML for the application identity, and make administrative capacity edits acquire the corresponding lock before validating the new limit.

Calling a transaction-owning routine inside another unit

The routine cannot be safely composed as a nested transaction. Choose a clear owner for each transaction. A larger workflow should use a redesigned caller-owned routine rather than assuming its savepoint survives an inner START TRANSACTION.

Presenting the audit as a security boundary

These triggers provide transactional change history for inserts and real updates. They neither authenticate a human nor record every destructive operation. Design those missing controls before calling it a production audit system.

Connect design to observable behaviour

The project joins ER mapping, normalisation, constraints, views, procedures, triggers and locking into one bounded workflow. Explain each invariant and its failure test before adding features. Use the exam bank to practise defending these design choices.
