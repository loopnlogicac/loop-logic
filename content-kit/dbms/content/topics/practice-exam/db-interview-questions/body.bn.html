সংক্ষেপে উত্তর দাও, তারপর শর্ত বোঝাও

এই পঞ্চাশটি প্রশ্ন পরিষ্কারভাবে মুখে বোঝানোর অনুশীলন। আগে মূল উত্তর বলো, তারপর কোন শর্তে সেটি ঠিক তা যোগ করো। ইন্টারভিউয়ার বড় দাবি নিয়ে প্রশ্ন তুললে মুখস্থ সংজ্ঞা আবার না বলে ছোট উদাহরণ দাও।

প্রশ্নগুলোতে ডিজাইন, SQL, dependency, ট্রানজ্যাকশন ও বাস্তব storage বেছে নেওয়া আছে। প্রতিটি প্রশ্নে থেমে নিজের উত্তর মুখে বলো। কোনো কথা কেন সত্য বোঝাতে না পারলে সংশ্লিষ্ট বড় পাঠটি পড়ো।

ডিজাইন ও পরিচয়

১. বিচ্ছিন্ন ডেটা ফাইলের চেয়ে DBMS কী বেশি দেয়?

এটি query, একসঙ্গে update, integrity, অনুমতি ও recovery সমন্বয় করে। এতে অ্যাপের পুনরাবৃত্ত কাজ কমে; তবে স্কিমা ও ব্যবসার নিয়ম এখনও ডিজাইন করতে হয়।

২. Logical ও physical data independence কীভাবে আলাদা?

Logical independence-এ বাইরের view অকারণে না বদলে conceptual structure বদলানো যায়। Physical independence-এ logical interface না বদলে storage ও access পদ্ধতি বদলানো যায়।

৩. যেকোনো SQL টেবিল কি একটি relation?

গণিতের relation নির্দিষ্ট domain-এর tuple-এর সেট। Constraint ছাড়া SQL টেবিলে duplicate ও NULL থাকতে পারে। তাই দুটো মেলাতে শর্ত স্পষ্ট করতে হবে।

৪. Candidate key ও superkey-এর পার্থক্য কী?

Candidate key থেকে কোনো attribute বাদ দিলে আর tuple চেনা যায় না। Superkey-তে পরিচয়ের জন্য অপ্রয়োজনীয় অতিরিক্ত attribute থাকতে পারে।

৫. Foreign key-তে একই মান বারবার থাকতে পারে কেন?

একই parent-কে একাধিক child row উল্লেখ করতে পারে। Foreign key সঠিক reference নিশ্চিত করে; প্রতিটি child reference অনন্য করে না।

৬. Entity কখন weak হয়?

তার পরিচয়ে মালিকের key এবং নিজের partial key দুটোই লাগে। আলাদা ভবনে একই room number থাকা পরিচিত উদাহরণ।

৭. ER সম্পর্কে total participation কী?

ওই পাশের প্রতিটি entity instance-কে সম্পর্কে অংশ নিতেই হবে। এটি সর্বনিম্ন অংশগ্রহণের শর্ত; সর্বোচ্চ কত partner হবে তা আলাদা বিষয়।

৮. M:N সম্পর্ক টেবিলে কীভাবে বসাবে?

দুই অংশগ্রহণকারীর reference নিয়ে একটি bridge relation বানাও। সম্পর্কের ঘটনার পরিচয় অনুযায়ী key দাও। সম্পর্কের নিজস্ব attribute ওই bridge-এ রাখো।

৯. Enrollment-এ শুধু course না রেখে section লাগে কেন?

একই কোর্স বারবার পড়ানো হতে পারে। শিক্ষার্থী কোন নির্দিষ্ট offering-এ ভর্তি হয়ে ফল পাচ্ছে তা section আলাদা করে।

১০. Surrogate identifier যোগ করলেই কি redundancy চলে যায়?

না। পুরোনো determinant-গুলো এখনও ব্যবসার তথ্য বর্ণনা করে। প্রয়োজনীয় uniqueness রাখো এবং dependency বিশ্লেষণ করো; নতুন id-কে normalization ধরে নিও না।

SQL-এর অর্থ ও ফলের গঠন

১১. NULL = NULL সাধারণ equality-এর মতো হয় না কেন?

SQL-এ NULL অনুপস্থিত বা অজানা তথ্য বোঝায়। এই তুলনায় UNKNOWN হয়। অনুপস্থিত মান পরীক্ষা করতে IS NULL নাও।

১২. COUNT(*) ও COUNT(column) কীভাবে আলাদা?

প্রথমটি ইনপুট row গোনে। দ্বিতীয়টি expression non-NULL এমন row গোনে। Outer join-এর পরে এই পার্থক্য খুব দরকার।

১৩. WHERE ও HAVING-এর পার্থক্য কী?

WHERE grouping-এর আগে ইনপুট row ছাঁকে। HAVING তৈরি হওয়া group ছাঁকে। অবস্থান বদলালে count ও কোন group থাকবে দুটোই বদলাতে পারে।

১৪. LEFT JOIN-এর unmatched parent হারিয়ে যেতে পারে কেন?

পরের WHERE শর্ত NULL-দিয়ে বাড়ানো child মান প্রত্যাখ্যান করতে পারে। Match না হলেও parent রাখতে চাইলে child মেলানোর শর্ত ON-এ দাও।

১৫. Raw child join করার চেয়ে EXISTS কখন ভালো?

অন্তত একটি child আছে কি না জানতে চাইলে EXISTS সরাসরি membership বোঝায়। প্রতিটি matching child-এর জন্য parent row বাড়ায় না।

১৬. Nullable subquery-এর সঙ্গে NOT IN ঝুঁকিপূর্ণ কেন?

তুলনার সেটে NULL থাকলে না-মেলা মানের predicate-ও UNKNOWN হতে পারে। NOT EXISTS দিয়ে উদ্দেশ্যের অনুপস্থিতি প্রায়ই আরও সরাসরি বলা যায়।

১৭. UNION যা সরায়, UNION ALL কী রাখে?

UNION ALL দুই ইনপুটের duplicate occurrence রাখে। UNION distinct set-এর মতো মিলিত ফল দেয়। একই ঘটনা বারবার ঘটার অর্থ আছে কি না দেখে বেছে নাও।

১৮. Window aggregate ও GROUP BY আলাদা কেন?

Window প্রতিটি ইনপুট row রেখে তার সঙ্গে group-সম্পর্কিত মান জুড়তে পারে। GROUP BY প্রতি group-এ একটি আউটপুট row বানায়।

১৯. RANK ও DENSE_RANK tie কীভাবে সামলায়?

সমান ordering value-তে দুটোই সমান position দেয়। Tie-এর পরে RANK ফাঁক রাখে; DENSE_RANK আলাদা level-গুলোকে টানা নম্বর দেয়।

২০. একই limited subset পেতে সম্পূর্ণ ordering লাগে কেন?

Ordering value সমান হলে tie-এর কোন row নেওয়া হবে অস্পষ্ট থাকে। একই subset আবার চাইলে একটি unique tie-breaker যোগ করো।

Dependency ও decomposition

২১. কয়েকটি আলাদা sample row কি functional dependency প্রমাণ করে?

না। Dependency সব অনুমোদিত অবস্থার নিয়ম। Sample দিয়ে নিয়ম ভুল দেখানো যায়; সবসময় সত্য হওয়ার নিশ্চয়তা requirements থেকে আসতে হবে।

২২. Attribute closure-এর কাজ কী?

দেওয়া FD অনুযায়ী শুরুর সেট থেকে নির্ধারিত সব attribute সংগ্রহ করে। এটি দিয়ে implication ও superkey কি না পরীক্ষা করা যায়।

২৩. 2NF কখন ভাঙে?

কোনো nonprime attribute candidate key-এর proper subset-এর ওপর নির্ভর করলে। শুধু নির্বাচিত primary key নয়, সব candidate key পরীক্ষা করো।

২৪. X → A-এর জন্য 3NF-এর আনুষ্ঠানিক শর্ত কী?

Nontrivial dependency হলে X superkey অথবা A prime হতে হবে। Candidate key-গুলো overlap করলে ডান পাশে prime থাকার ছাড়টি গুরুত্বপূর্ণ।

২৫. BCNF আরও কঠোর কী শর্ত দেয়?

প্রতি nontrivial functional determinant-কে superkey হতে হবে। 3NF-এ ডান পাশ prime হলে যে ছাড় ছিল, BCNF-এ তা নেই।

২৬. MVD কী তথ্য প্রকাশ করে?

নির্দিষ্ট determinant-এর জন্য একটি attribute set বাকি attribute থেকে স্বাধীনভাবে বদলায়। ফলে tuple-এর সংশ্লিষ্ট সব cross combination থাকা লাগে।

২৭. Decomposition lossless হয়েও dependency না রাখতে পারে কীভাবে?

Projection join করে প্রতিটি বৈধ মূল relation ফেরত পাওয়া যেতে পারে, কিন্তু আলাদা component-এ একটি পুরোনো FD স্থানীয়ভাবে পরীক্ষা করা নাও যেতে পারে। তথ্য ফেরত পাওয়া ও নিয়ম প্রয়োগ আলাদা পরীক্ষা।

২৮. Spurious tuple কী?

মূল relation-এ একসঙ্গে ছিল না এমন অংশ projection join-এ মিলে যে বাড়তি row বানায়।

২৯. 3NF synthesis-এ কখনো key relation যোগ হয় কেন?

FD-ভিত্তিক component সব নিয়ম মানিয়েও group-এর যোগসূত্র হারাতে পারে। Candidate key-সহ relation যোগ করলে synthesis-এর lossless নিশ্চয়তা পূর্ণ হয়।

৩০. Denormalization কি সবসময় ডিজাইনের ভুল?

না। পড়া দ্রুত করতে বা ঐতিহাসিক snapshot রাখতে ইচ্ছা করে তথ্য নকল হতে পারে। Update, পুরোনো হয়ে যাওয়া এবং পুনর্গঠনের পরিষ্কার নীতি চাই।

ট্রানজ্যাকশনের সীমা ও concurrency

৩১. Atomicity কোন একক রক্ষা করে?

নির্ধারিত ট্রানজ্যাকশন সীমা। ব্যবসার একটি কাজ দুই ট্রানজ্যাকশন বা বাইরের সার্ভিসে ছড়ালে একটি local transaction নিজে থেকে সব atomic করতে পারে না।

৩২. Atomic transaction কি consistency ভাঙতে পারে?

পারে। ভুল debit ও credit একসঙ্গে commit করলে সব হবে বা কিছুই হবে না শর্ত মানে, কিন্তু মোট balance-এর নিয়ম ভাঙতে পারে।

৩৩. Dirty read কী?

এক ট্রানজ্যাকশন অন্যটির uncommitted পরিবর্তন পড়ে। লেখক পরে abort করলে পাঠক এমন মান ব্যবহার করেছে যা committed history-তেই আসেনি।

৩৪. Nonrepeatable read কী?

এক ট্রানজ্যাকশন একই row আবার পড়ে ভিন্ন committed মান দেখে। READ COMMITTED-এ consistent read নতুন snapshot নেওয়ায় এমন হতে পারে।

৩৫. Phantom কী?

একই predicate query আবার চালিয়ে matching row set বদলানো দেখা, যেমন নতুন row পাওয়া। এটি হবে কি না isolation ও access আচরণের ওপর নির্ভর করে।

৩৬. Precedence ও wait-for graph কীভাবে আলাদা?

Precedence edge conflicting data operation-এর ক্রম দিয়ে serializability বোঝায়। Wait-for edge কোন আটকে থাকা transaction কোন lock holder-এর অপেক্ষায় আছে দেখিয়ে deadlock বিশ্লেষণ করে।

৩৭. Basic 2PL কি deadlock দূর করে?

না। উল্টো ক্রমে lock নিয়ে ট্রানজ্যাকশনগুলো চক্রাকারে অপেক্ষা করতে পারে। একই ক্রমে lock নেওয়া এই ঝুঁকি কমায়।

৩৮. Deadlock retry-তে কী আবার চালাবে?

বর্তমান ডেটা নিয়ে পুরো abort হওয়া transaction, সীমিত retry-সহ। Request identity রাখো, যাতে আগের অনিশ্চিত ফল একই ব্যবসার কাজ দুবার না ঘটায়।

৩৯. Savepoint nested transaction নয় কেন?

এটি একটি ট্রানজ্যাকশনের ভেতরে ফেরত যাওয়ার জায়গা চিহ্নিত করে। Release করলে স্বাধীন commit হয় না; পুরো rollback করলে চারপাশের কাজও সরে যায়।

৪০. MySQL-এ সাধারণ DDL কি আগের DML-এর সঙ্গে rollback হয়?

অনেক DDL implicit commit ঘটায়। Atomic DDL ওই DDL operation-টিকেই রক্ষা করে; সাধারণ user rollback group-এর অংশ করে না।

Recovery, storage ও security

৪১. Crash-এর পরে redo কী সাহায্য করে?

চূড়ান্ত ডেটা page-এ নিরাপদে না-পৌঁছানো logged পরিবর্তন পুনর্গঠন করতে পারে। Uncommitted logical পরিবর্তনের জন্য এখনও rollback সামলাতে হয়।

৪২. Rollback ছাড়া undo আর কী করে?

Consistent read-এর জন্য পুরোনো row version দেয়। তাই কতদিন রাখা হবে তা transaction শেষ হওয়ার পাশাপাশি সক্রিয় snapshot-এর প্রয়োজনের ওপরও নির্ভর করে।

৪৩. Checkpoint backup নয় কেন?

এটি চলমান storage system-এর ভেতরে recovery-এর অগ্রগতি ধরে। Media হারানো বা committed ভুলের পরে আলাদা ঐতিহাসিক কপি দেয় না।

৪৪. পূর্ণ row খুঁজতে InnoDB secondary index কী ব্যবহার করে?

নিজের entry-তে রাখা clustered primary-key মান। তাই noncovering lookup-এ secondary ও clustered দুই tree-ই লাগতে পারে।

৪৫. Range query-তে B+ tree-এর leaf সুবিধা দেয় কেন?

শুরুর leaf পাওয়ার পর key-এর ক্রম ও পাশের leaf-এর link ধরে কাছাকাছি মান পড়া যায়। Hash layout-এ স্বাভাবিক interval order নেই।

৪৬. EXPLAIN-এর rows কী বোঝায়?

Plan operation কত ইনপুট row পরীক্ষা করবে তার estimate। এটি চূড়ান্ত ফলের সঠিক count বা চলার সময় মাপা মান হওয়া বাধ্যতামূলক নয়।

৪৭. Prepared statement authorization-এর বদলি নয় কেন?

এটি SQL syntax-এ মান কীভাবে ঢোকে তা রক্ষা করে। নির্দিষ্ট বৈধ identifier-এর তথ্য এই কলার পড়তে পারবে কি না অ্যাপকেই ঠিক করতে হবে।

৪৮. Stored procedure-এ কি injection flaw থাকতে পারে?

পারে। অবিশ্বস্ত text জুড়ে বানানো dynamic SQL procedure-এর ভেতরেও অনিরাপদ। মান bind করো এবং অনিবার্য structural choice সীমিত করো।

৪৯. NoSQL কি schema নেই বোঝায়?

না। অ্যাপ এখনও নির্দিষ্ট field name, type ও সম্পর্ক আশা করে। কঠোর table definition না থাকলেও validation, versioning ও migration লাগবে।

৫০. Network partition হলে CAP কোন সিদ্ধান্ত চায়?

ক্ষতিগ্রস্ত operation-এ linearizable response নাকি availability ছাড়বে তা ঠিক করতে হয়। সম্পর্কহীন যেকোনো দুটি product feature চিরকাল বেছে নেওয়ার নির্দেশ নয়।

স্লোগানের বদলে একটি বাস্তব উদাহরণ দাও

প্রতিটি উত্তরের জন্য একটি উদাহরণ ও একটি সীমাবদ্ধতা বলার অভ্যাস করো। এতে ছোট সংজ্ঞা কাজের ব্যাখ্যা হয়। চলমান SQL-এর সঙ্গে এই পার্থক্যগুলো মেলাতে বিশ্ববিদ্যালয় সার্ভিস বানাও।
