Give each diagram rule a table rule

An ER diagram says that students enroll in sections. MySQL needs concrete tables and constraints that preserve that meaning. Mapping connects the conceptual picture to a relational design you can create and query.

You do not convert every shape into the same kind of table. Strong entities normally become tables. Some relationships become foreign keys. Others need bridge tables. Attribute kinds also matter: a name can be one column, while several phone numbers usually require several child rows.

Use the university’s assumptions throughout the mapping. Each student belongs to one department. A course can have several semester sections. An enrollment connects one student to one section. A result depends on an existing enrollment. The SQL examples show these choices through shared university records.

The small set of building blocks

A primary key identifies a row. A foreign key references a parent row. UNIQUE prevents repeated known values, and NOT NULL requires a value. These constraints express different parts of the diagram. A foreign key alone cannot say that one parent has at most one child.

CREATE TABLE child_entity (
    child_id INT PRIMARY KEY,
    parent_id INT NOT NULL,
    FOREIGN KEY (parent_id) REFERENCES parent_entity(parent_id)
);

This definition pattern represents a required parent on the child side. It assumes the parent table already exists. The foreign-key values must use compatible column types. Create parent tables before dependent tables so each reference has a valid target.

Map identity, relationships and attributes

Begin with independent entities

Create Department with department_id as primary key and its code as a separate unique value. Then create Student with student_id as primary key. Keep student_name as a description. A key must remain unique under the declared rules, rather than merely appearing unique in today’s data.

A composite address can become street, city and postcode columns when those parts are useful separately. Do not preserve a conceptual composite oval by forcing a comma-separated string. Conversely, avoid splitting a name into arbitrary pieces when the application does not need or reliably know those pieces.

Put a 1:N reference on the many side

Department 1:N Student means each student row stores its department_id. Several students can repeat the same department value. NOT NULL requires every student to name a department. The foreign key ensures that the named department exists.

This does not require every department to have a student. A parent row can exist without a child. ER total participation on the parent side therefore needs additional enforcement when required. Ordinary child foreign keys express a narrower direction of the rule.

Turn M:N into rows of pairs

Student and Section each connect to many partners. Create Enrollments with student_id and section_id as references. Their pair is the primary key under the rule of one enrollment per student-section combination. Place enrolled_on there because it describes that connection.

Neither component is unique alone. Ayesha repeats across three enrollment rows, and section 33 repeats across three students. The complete pair cannot repeat. If repeat events within the same section are allowed, extend the identity with an attempt or event identifier.

Make 1:1 unique on the reference

A student card has card_id as its own key and student_id as a foreign key. Add UNIQUE to student_id so one student cannot own two cards. NOT NULL on that reference makes every card belong to a student. A student with no card is still allowed.

Choose the foreign-key side carefully when participation differs. Storing the reference on a total side can avoid unnecessary NULL values. If both entities must always exist together, combining tables may be reasonable. Separate lifecycles or access needs may still justify separate tables.

Preserve owner-dependent identity

A weak Room uses building_id together with room_number as its primary key. building_id also references Buildings. Room number 101 can appear in two buildings because the complete keys differ. A multivalued phone property similarly moves into child rows rather than a list inside Students.

The phone design uses a label unique within each student, such as home or mobile. It therefore limits one phone per student-label pair. If several mobile numbers are permitted, choose another distinguishing value. Mapping must preserve the intended multiplicity, not accidentally narrow it.

Map relationship attributes at the right level

A 1:N relationship attribute can often be stored beside the many-side reference. A M:N relationship attribute belongs on its bridge row. For a ternary relationship, retain references to all three participating entities and derive the key from its cardinality rules. Do not assume that three separate binary tables preserve the original triple or its attributes.

Inspect the mapped university structures

One department number per student

Read the student keys and their department references. The repeated department values show the many side without duplicating department descriptions.

One row per enrollment pair

Section 33 has three students. Inspect the bridge rows and notice that enrolled_on belongs to each particular pairing.

Several phone values for one owner

Create a child table with a composite identity. Both phone records refer to student 101 while retaining separate labels.

An optional card with a unique owner

The card mapping adds a unique reference. Without that uniqueness, a valid foreign key would still permit several cards for one student.

Room numbers scoped by a building

The weak-entity mapping permits the same room number under different owners. Building identity is part of every room identity.

Map subtypes without losing shared identity

Extended ER can use a Person table and separate Student and Teacher subtype tables. Each subtype’s person_id is both primary key and foreign key to Person. Shared contact fields stay on Person; role-specific fields stay on their subtypes. Overlap is possible because the same person can appear in both subtype tables.

Separate subtype tables do not automatically enforce disjointness or total coverage. A single-table alternative can use a discriminator for disjoint roles, though many optional fields may result. Choose a mapping that fits the role rules and document any extra constraints needed across tables.

Mapping errors that change the rules

Putting lists inside a reference column

Writing section IDs as one comma-separated value makes each individual reference hard to constrain and query. Create one enrollment row per section instead. The bridge then supports foreign keys, uniqueness and ordinary joins without parsing strings.

Dropping the owner from a weak key

Using room_number alone would reject a valid second room 101. Using a separate room identifier can be convenient, but preserve UNIQUE(building_id, room_number) as well. The natural business rule remains important even when the physical key choice changes.

Assuming a foreign key enforces every diagram line

A foreign key checks references from existing child rows. It does not create a child for each parent or prove that a head teacher belongs to the headed department. Identify those stronger rules and provide additional logic rather than claiming the mapping enforces them already.

MySQL enforcement details

These definitions use InnoDB foreign keys and work on MySQL 8.0.16 or later. CHECK constraints need that version for enforcement. Generated grade columns in the university schema follow marks automatically; students enter marks rather than maintaining several inconsistent grade fields.

Preserve the meaning of each connection

Map entity identity first, then place references according to cardinality and participation. Use bridge tables for M:N, unique references for 1:1 and owner keys for weak identities. Next, study why those keys work in Relations, Keys and Constraints.
