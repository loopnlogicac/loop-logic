যে রেকর্ড বদলাতে চাও সেটিই বদলাও

দোকানে তিনটি desk lamp এসেছে; একটি stock বাড়াতে হবে। সব পণ্য বদলে দিলে বড় ভুল। SQL রো change-এ পরিষ্কার target ও ফল যাচাইয়ের উপায় চাই।

INSERT নতুন রো যোগ করে, UPDATE আগের রো বদলায়, DELETE matching রো সরায়। টেবিলের স্ট্রাকচার-এর ভেতর কাজ হয়। কনস্ট্রেইন্ট চালু থাকে, তাই নিয়ম ভাঙা ইনসার্ট বা আপডেট প্রত্যাখ্যাত হতে পারে।

Shop রেকর্ড-এ customer, catalogue পণ্য, অর্ডার, item line ও পেমেন্ট আলাদা করো। কোন তথ্য বদলাবে তা টেবিল ঠিক করে। পরে catalogue price বদলালেই পুরোনো অর্ডার-এর সম্মত দাম বদলাবে না।

কলাম আর target স্পষ্ট করে লেখো

INSERT INTO table_name (column_a, column_b)
VALUES (value_a, value_b);

UPDATE table_name
SET column_b = replacement
WHERE key_column = wanted_key;

DELETE FROM table_name
WHERE key_column = wanted_key;

কলাম list মানের অর্থ মিলিয়ে দেয়। UPDATE assignment-এ SET নেয়। DELETE পুরো রো সরায় বলে কলাম list নেই। WHERE সাজানোর জিনিস নয়; কোন আগের রো বদলানোর প্রার্থী তা ঠিক করে।

একাধিক রো-তে VALUES-এর পরে একাধিক parenthesized গ্রুপ দাও; প্রতিটি কলাম list মেলাবে। IGNORE ছাড়া সাধারণ InnoDB INSERT-এ কনস্ট্রেইন্ট failure হলে ওই স্টেটমেন্ট ব্যর্থ হয়, শুধু বৈধ নতুন রো commit হয় না। আগের স্টেটমেন্ট-এর জন্য এখনও explicit rollback লাগতে পারে।

আগে দেখো, বদলাও, আবার যাচাই

স্থির পরিচয় দিয়ে target ধরো

পণ্য 4 desk lamp। “Study products”-এর মতো একাধিক রো মেলানো বর্ণনার চেয়ে identifier ভালো target। আগে একই শর্তে পরিচয় ও stock পড়ো। তারপর stored value-তে পাওয়া quantity যোগের মতো arithmetic করো।

মনে রাখা মোট বসালে অন্যের বৈধ adjustment মুছে যেতে পারে। Arithmetic আপডেট ওই stale-value ভুল এড়ায়, যদিও পুরো inventory-তে concurrency rule চাই। Preview উপকারী, কিন্তু lock নয়; অন্য session বদলাবে না তার প্রমাণও নয়।

Rollback কোথায় কাজ করে বোঝো

START TRANSACTION পরিবর্তনের দল শুরু করে; COMMIT স্থায়ী করে; ROLLBACK uncommitted InnoDB change বাতিল করে। Correction-এ আগে target দেখো, ট্রানজ্যাকশন-এর ভেতর বদলাও, ফল দেখে তারপর commit করো।

Autocommit সাধারণত চালু। ট্রানজ্যাকশন না খুললে সফল standalone change সঙ্গে সঙ্গে commit হতে পারে। পরে rollback তা ফেরায় না। Correction-এর মাঝে স্ট্রাকচার কমান্ড দেবে না; অনেক DDL implicit commit করে।

না থাকা target আর নির্ভরশীল রেকর্ড

অনুপস্থিত customer ডিলিট করা বৈধ, শূন্য রো সরে। অনুপস্থিত পণ্য আপডেট-ও শূন্য বদলায়। স্টেটমেন্ট সফল মানেই চাওয়া object পেয়েছে নয়। Target আবার পড়ো এবং ক্লায়েন্ট দিলে affected-রো তথ্য দেখো।

Foreign কী ডিলিট আটকাতে বা dependent change ঘটাতে পারে। Shop-এ অর্ডার ডিলিট হলে order_items cascade; পেমেন্ট history রক্ষায় অর্ডার deletion restrict। তাই cancel প্রায়ই status change ও নির্দিষ্ট refund process, physical ডিলিট নয়।

Safe-আপডেট mode একটি সহায়ক রক্ষাকবচ

MySQL SQL_SAFE_UPDATES উপযুক্ত কী restriction বা limit ছাড়া broad UPDATE/DELETE আটকাতে পারে। শেখার সময় কাজে লাগে, তোমার উদ্দেশ্য বিচার করতে পারে না। ভুল পণ্য-এ ঠিক কী দিয়ে আপডেট হলেও guard পার হয়।

স্টেটমেন্ট ব্যর্থ হলেই safe mode বন্ধ করবে না। আগে কী শর্ত ও প্ল্যান দেখো। Limit-ও কোন business object বদলাবে তা চেনে না; শুধু সংখ্যা বাঁধে। Targeting শুরু object পরিচয় থেকে।

সহজে ভুল বোঝা পরিবর্তন

UPDATE-এ WHERE বাদ

শর্ত ছাড়া প্রতিটি রো প্রার্থী। একটি পণ্য চাইলে চালানোর আগে থেমে কী দাও। একই শর্তের preview অতিরিক্ত category বা spelling comparison-এর ভুল ধরতে সাহায্য করে।

ছোট DELETE ভেবে TRUNCATE

TRUNCATE হলো DDL: টেবিল খালি, generated numbering reset ও implicit commit হয়। WHERE নেই; পরে সাধারণ rollback ফেরায় না। নির্বাচিত transactional রো সরাতে DELETE নাও। Reference কনস্ট্রেইন্ট আরও সীমা দিতে পারে।

বাদ দেওয়া কলামের ডিফল্ট না জানা

Nullable phone বাদ দিলে NULL হওয়া ঠিক হতে পারে। Amount-এ zero ডিফল্ট missing business information লুকাতে পারে। নির্ভর করার আগে ডিফল্ট বোঝো। সিনট্যাক্স ঠিক ইনসার্ট-ও ভুল ঘটনা বলতে পারে।

ট্রানজ্যাকশন আচরণ engine-নির্ভর

Shared টেবিল MySQL 8.0.16 বা নতুনে InnoDB। Rollback উদাহরণ InnoDB ট্রানজ্যাকশন-এর ওপর নির্ভর করে। Nontransactional engine বা implicit-commit স্ট্রাকচার কমান্ড-এ একই আচরণ ধরে নিও না।

বদলানোর সময় উদ্দেশ্য দৃশ্যমান

Explicit কলাম addition পরিষ্কার করে, কী শর্ত change চেনে, ট্রানজ্যাকশন যাচাইয়ের সীমা দেয়। Dependent history রেখো, DELETE ও TRUNCATE আলাদা করো। এরপর SELECT-এর শুরু-তে নির্ভুল পড়া শেখো।
