যে রেকর্ড বদলাতে চাও সেটিই বদলাও

দোকানে তিনটি desk lamp এসেছে, তাই এক পণ্যের stock বাড়াতে হবে। সব পণ্য আপডেট হয়ে গেলে বড় ভুল। SQL-এ রো বদলাতে স্পষ্ট target আর ফল যাচাইয়ের উপায় চাই।

INSERT নতুন রো যোগ করে, UPDATE পুরোনো রো বদলায়, DELETE মেলা রো সরায়। টেবিলের কাঠামোর মধ্যেই কাজগুলো হয়। কনস্ট্রেইন্ট সক্রিয় থাকে, তাই নিয়ম ভাঙলে ইনসার্ট বা আপডেট বাদ পড়তে পারে।

Shop-এর রেকর্ডে customer পরিচয়, পণ্য catalogue, অর্ডার, item line আর পেমেন্ট আলাদা দেখো। কোন তথ্য বদলাবে তা থেকেই টেবিল বেছে নাও। পরে catalogue price বদলালে পুরোনো অর্ডার-এ ঠিক হওয়া দাম লেখা যাবে না।

কলাম আর target স্পষ্ট করে লেখো

INSERT INTO table_name (column_a, column_b)
VALUES (value_a, value_b);

UPDATE table_name
SET column_b = replacement
WHERE key_column = wanted_key;

DELETE FROM table_name
WHERE key_column = wanted_key;

কলাম list প্রতিটি মানের অর্থ মিলিয়ে দেয়। UPDATE-তে SET assignment করে। DELETE পুরো রো সরায় বলে কলাম list নেই। WHERE সাজানোর জন্য নয়, কোন পুরোনো রো পরিবর্তনের প্রার্থী তা ঠিক করে।

কয়েক রো ঢোকাতে VALUES-এর পরে কয়েকটি বন্ধনী-ঘেরা দল দাও। প্রতিটি কলাম list মেলাবে। InnoDB-তে সাধারণ INSERT-এ IGNORE না থাকলে কনস্ট্রেইন্ট failure পুরো স্টেটমেন্ট ব্যর্থ করে, শুধু বৈধ নতুন রো commit করে না। তবে ট্রানজ্যাকশন-এর আগের স্টেটমেন্ট ফেরাতে explicit rollback লাগতে পারে।

আগে দেখো, বদলাও, আবার যাচাই

স্থির পরিচয় দিয়ে target ধরো

পণ্য 4 হলো desk lamp। “Study products”-এর মতো কয়েক রো মেলা বর্ণনার চেয়ে ID শক্ত target। একই শর্তে আগে ID আর stock পড়ো। তারপর রাখা মানে আসা পরিমাণ যোগের মতো arithmetic চালাও।

মনে রাখা মোট সরাসরি বসালে অন্য বৈধ adjustment মুছে যেতে পারে। Arithmetic আপডেট এই stale-value ভুল এড়ায়, যদিও পুরো inventory-তে concurrency rule-ও চাই। Preview সাহায্য করে, lock নয়; অন্য session বদলাবে না তার প্রমাণও নয়।

Rollback কোথায় কাজ করে বোঝো

START TRANSACTION পরিবর্তনের দল শুরু করে, COMMIT স্থায়ী করে। ROLLBACK uncommitted InnoDB রো change বাতিল করে। সংশোধনের সময় target দেখে ট্রানজ্যাকশন-এ বদলাও, ফল দেখে নিশ্চিত হলেই commit।

সাধারণত autocommit চালু, তাই ট্রানজ্যাকশন না খুললে সফল আলাদা change সঙ্গে সঙ্গে commit হতে পারে। এরপর rollback আগের commit ফেরায় না। মাঝখানে structural কমান্ড এড়াও, কারণ অনেক DDL implicit commit করে।

না থাকা target আর নির্ভরশীল রেকর্ড

না থাকা customer ডিলিট বা পণ্য আপডেট বৈধ, কিন্তু কোনো রো বদলায় না। স্টেটমেন্ট সফল মানেই চাওয়া object পেয়েছে নয়। আবার পড়ে দেখো, ক্লায়েন্ট দিলে affected-রো তথ্যও দেখো।

Foreign কী deletion আটকাতে বা dependent change করতে পারে। অর্ডার মুছলে shop-এর order_items cascade হয়, কিন্তু পেমেন্ট ইতিহাস বাঁচাতে deletion আটকায়। তাই পেমেন্টের পরে cancel প্রায়ই নির্দিষ্ট refund-সহ status change, physical ডিলিট নয়।

Safe-আপডেট mode একটি সহায়ক রক্ষাকবচ

SQL_SAFE_UPDATES উপযুক্ত কী restriction বা limit ছাড়া broad UPDATE-DELETE ঠেকাতে পারে। শেখায় ভালো, কিন্তু তোমার উদ্দেশ্য জানে না। সঠিক কী দিয়েও ভুল পণ্য বদলালে পার হয়ে যায়।

ব্যর্থ হলেই safe mode বন্ধ কোরো না। আগে কী শর্ত আর প্ল্যান দেখো। Limit-ও কোন business object বদলাবে বলে না, শুধু সংখ্যা বাঁধে। ভালো targeting শুরু হয় object-এর পরিচয় থেকে।

ছোট DELETE ভেবে TRUNCATE

TRUNCATE DDL হিসেবে টেবিল ফাঁকা করে, numbering reset আর implicit commit করে। WHERE নেই, পরে সাধারণ rollback ফেরায় না। বাছা transactional রো সরাতে DELETE। Reference rule-এ আরও restriction থাকতে পারে।
