Turn several rows into a useful summary

A department office asks how many students belong to each department. Listing every student answers a different question. Aggregate functions combine rows into counts, totals and other summaries.

An aggregate function computes a value from several input rows. COUNT counts, SUM adds, AVG calculates a mean, and MIN and MAX find the smallest and largest known values. GROUP BY divides rows into groups so each group receives its own summary.

Before writing an aggregate query, say what one output row represents. It might describe the entire university, one department or one section. Also state which records enter the calculation. An average of passing results differs from an average of all completed results.

Separate rows, groups and result order

SELECT grouping_column, COUNT(*) AS row_count
FROM source_table
WHERE row_condition
GROUP BY grouping_column
HAVING COUNT(*) >= required_count
ORDER BY grouping_column;

WHERE tests individual rows before grouping. GROUP BY forms groups using the named expressions. Aggregate functions summarise each group. HAVING tests the completed groups. ORDER BY arranges the groups that remain. The server can choose its physical execution method while preserving this logical result.

Count the right things

Rows are different from known values

Students contains eight rows. COUNT(*) therefore returns eight. Two students have unknown hometowns, so COUNT(hometown) returns six. Repeated Dhaka values count separately in that expression. COUNT(DISTINCT hometown) instead counts five different known towns.

Most aggregate functions ignore NULL arguments. This does not mean an unknown mark should be replaced automatically with zero. Zero is a real value that changes the numerator and denominator. Keep the missing-result policy explicit when presenting an average.

An ungrouped aggregate over an empty input still returns one summary row. COUNT is zero, but SUM and AVG are NULL. A grouped query over no input rows has no groups and normally returns no rows. These cases explain why an unpaid order may disappear from a payment-only grouped report.

Form groups with a defined meaning

Grouping Students by department_id creates three groups. Their sizes are four, two and two. Each output row describes a department represented in Students. A newly created department with no students would not appear in this query because there is no student row to form its group.

To include empty departments, begin with Departments and use an outer join to Students. Then count a non-NULL student identifier rather than COUNT(*), which would count the preserved parent row. You will examine that join pattern in Joins. The difference follows from what each joined row represents.

Grouping by several columns creates groups for their complete combinations. Department and hometown together describe a different grouping from department alone. Two NULL hometowns belong to the same hometown group under SQL grouping rules, even though ordinary equality with NULL does not yield TRUE.

Apply WHERE and HAVING at different stages

Suppose you want sections with at least two passing results. First use WHERE to keep marks of at least 40. Then group by section_id. Finally use HAVING to keep groups whose count is at least two. The resulting average describes passes only.

If instead you group all results and keep sections whose average is at least 40, failures still contribute to that average. Moving a condition between WHERE and HAVING can therefore change the question. Name a column mean_pass when it excludes failures, rather than calling it an unrestricted mean.

Respect ONLY_FULL_GROUP_BY

MySQL normally enables ONLY_FULL_GROUP_BY. A grouped SELECT cannot request an arbitrary nonaggregate value from each group. For example, a department group contains several student names. There is no single student_name that describes the entire group.

Return the grouping key and aggregates, or choose a grouping that makes the selected fact meaningful. MySQL also recognises some functional dependencies, such as other columns determined by a grouped primary key. That does not justify choosing an arbitrary name from a department containing several students.

Disabling the mode can allow a misleading query to run without defining which name belongs in the answer. The repair is to clarify what one row means. Do not use a convenient aggregate such as MIN(name) unless the question actually asks for that defined representative.

Use weights when courses have different credits

A grade point summarises one course result on the documented 4.00 scale. CGPA combines completed course results with credit weights. Multiply each grade point by its course credits, sum those products and divide by the sum of the same completed credits.

The report excludes pending results and assumes no repeated-course replacement rule. Real universities may replace grades or apply special retake policies. State those policies before calling a calculation an official CGPA. Round the final displayed value rather than rounding each intermediate contribution unnecessarily.

A plausible number can answer the wrong question

Averaging already averaged groups

Two sections can have different numbers of results. Averaging their means gives each section equal weight, rather than each result equal weight. Recompute from the underlying rows or combine each mean with its contributing count when an overall student-result mean is required.

Summing after a one-to-many join without checking multiplicity

An order can have several items and several payments. Joining both directly can repeat each payment for every item. A later SUM then overstates receipts. Check what one joined row represents and summarise each relationship at the intended level before combining totals.

Assuming GROUP BY also sorts

Grouping defines which rows share a summary. It does not promise the order of those summaries. Add ORDER BY when displaying departments or sections. A report should not depend on an accidental grouping implementation.

Keep grouping mode enabled

These aggregates work on MySQL 8.0.16 and 8.4. ONLY_FULL_GROUP_BY is normally enabled in both. Functional-dependency recognition can permit some nonaggregate expressions, but every selected value still needs a clear meaning for its group.

State the population behind the summary

Aggregates summarise input rows, so counts, NULL policies, filters and weights determine their meaning. WHERE selects rows and HAVING selects groups. Keep grouping unambiguous and order reports explicitly. Continue with Joins to build careful summaries across related tables.
