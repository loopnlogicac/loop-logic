Invalid রেকর্ড রাখা কঠিন করো

100-এর scale-এ 101 নীরবে নয়। ফল nonexistent enrollment-এর নয়। টেবিল definition রো বদলালে MySQL-কে promise check করতে দেয়।

CREATE TABLE কলাম,type,কনস্ট্রেইন্ট বলে। কনস্ট্রেইন্ট stored ডেটা-তে enforced rule। Requirement বোঝার বদলি নয়, তবে accidental invalid state অনেক ঠেকায়।

কোন তথ্য রাখবে তার স্পষ্ট নাম। Attendance রো এক শিক্ষার্থী এক তারিখ, পরিচয়-reference-presence লাগে। এই policy-তে একই শিক্ষার্থী-day দুই রেকর্ড চলবে না।

সংজ্ঞা promise হিসেবে পড়ো

CREATE TABLE table_name (
    id INT AUTO_INCREMENT PRIMARY KEY,
    required_value INT NOT NULL,
    status_code INT NOT NULL DEFAULT 1,
    UNIQUE (required_value),
    CHECK (status_code IN (0, 1))
);

প্রতি line design-এর অংশ। ID বাদ দিলে generated, required value NULL নয়, omitted status ডিফল্ট। UNIQUE known value repeat ঠেকায়, CHECK রো শর্ত। Pattern থেকে actual fact-এর নাম-reference বাছো।

কনস্ট্রেইন্ট সম্পর্কিত, বিনিময়যোগ্য নয়
Ruleকী নিশ্চিতকী নিশ্চিত নয়
NOT NULLমান চাইটেক্সট nonblank বা সত্যি
UNIQUEKnown কী repeat নয়Nullable-এ NULL নেই
PRIMARY KEYUnique required পরিচয়Business number gapless
DEFAULTবাদ দিলে মানদেওয়া অন্য মান বৈধ
CHECKশর্ত FALSE নয়UNKNOWN বাদ
FOREIGN KEYReference-এর valid parentসব parent-এর child আছে

অর্থপূর্ণ domain-এ rule মেলাও

Required আর valid value

NOT NULL unknown mark ঠেকায়। 0..100 CHECK invalid known ঠেকায়। Real mark চাইলে দুটোই। CHECK TRUE বা UNKNOWN নেয়, FALSE বাদ; রেঞ্জ একা NULL বাদ নয়।

NOT NULL নাম empty স্ট্রিং হতে পারে। Blank নিষিদ্ধ হলে rule আর ইনপুট validation। Whitespace-only অর্থপূর্ণ কি না-সহ policy মানো। Type একা সব business rule নয়।

কী,reference,ডিফল্ট

Primary কী এক/কয়েক কলাম। student_id-attended_on unique pair একদিন এক attendance, component আলাদা repeat পারে। FK existing Students রো নিশ্চিত।

কলাম বাদ বা explicit DEFAULT-এ ডিফল্ট। Supplied value check-এর বদলি নয়। উপস্থিত ধরে entry হলে ডিফল্ট 1 ভালো, অন্য workflow explicit চাইতে পারে।

AUTO_INCREMENT omitted ID দেয়, gapless নয়। Failure,ডিলিট,rollback gap রাখতে পারে। Highest ID রো সংখ্যা বা legal receipt সংখ্যা নয়।

স্ট্রাকচার বুঝে বদলাও

ALTER কলাম/কনস্ট্রেইন্ট যোগের মতো change। NOT NULL/UNIQUE-এর আগে old রো দেখো; NULL বা duplicate ভাঙতে পারে। বানানো placeholder নয়, verified তথ্য দিয়ে ঠিক করো।

DROP definition-রো সরায়। TRUNCATE definition রেখে empty, সাধারণত AUTO_INCREMENT reset। DELETE DML, WHERE থাকতে পারে। ট্রানজ্যাকশন-reference আচরণ আলাদা।

অনেক structural কমান্ড implicit commit। TRUNCATE-এর পরে ROLLBACK টেবিল ফেরায় না। Referenced টেবিল truncate-এ InnoDB restriction-ও। Destructive explore-এ private scratch টেবিল।

Definition তৈরি, alter, test

Constrained attendance

Generated ID,শিক্ষার্থী FK,unique day,ডিফল্ট,রেঞ্জ একসঙ্গে। ইনসার্ট-এ MySQL কোন মান দেয় দেখো।

ALTER-এ capacity

Study-গ্রুপ টেবিল capacity পায়। Inserted গ্রুপ নতুন ডিফল্ট ten seat নেয়।

Empty, তারপর definition সরাও

Private লেবেল টেবিলে TRUNCATE-DROP আলাদা। Metadata সংখ্যা-এ DROP-এর পরে নেই।

রেঞ্জ-এর বাইরে mark reject

ইচ্ছা করে 101 আপডেট। CHECK violation reject করে আগের valid ফল রাখে।

দেখতে বেশি শক্ত কনস্ট্রেইন্ট

UNIQUE মানেই required

Nullable unique-এ MySQL বহু NULL নেয়। Optional email-এ ভালো, required candidate ID নয়। Known unique চাইলে NOT NULL।

অসংগত নাম

Lowercase টেবিল, descriptive student_id/enrolled_on। কারণ ছাড়া একই অর্থে StudentID,sid,student_number বদল নয়। OS-এ টেবিল-নাম case আলাদা হতে পারে, lowercase consistency ভালো।

Rejection না বুঝে rule off

FK এরর ভুল parent বা operation অর্ডার জানায়। আগে রো-সম্পর্ক দেখো। Check off-এ orphan থাকে। Rejection ডেটা-design তদন্তের evidence।

CHECK enforcement-এর ভার্সন

MySQL 8.0.16 থেকে CHECK enforced। আগে কিছু সিনট্যাক্স নিলেও শর্ত মানাত না। এখানে 8.0.16+ আর FK-transactional রো change-এ InnoDB।

পুরো rule বলো

Type,required,কী,ডিফল্ট,check আলাদা সমস্যা মেটায়। বুঝে মেলাও, রো আর structural change আলাদা। পরের INSERT, UPDATE আর DELETE-এ এগুলো ব্যবহার।
