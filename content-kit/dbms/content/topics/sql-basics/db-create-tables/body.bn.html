অবৈধ রেকর্ড রাখা কঠিন করো

স্কেল 100-এ শেষ হলে 101 নম্বর নীরবে ঢোকা চলবে না। Enrollment নেই এমন কারও ফলও রাখা যাবে না। টেবিল definition দিয়ে রো বদলানোর সময়ই MySQL-কে নিয়ম পরীক্ষা করাতে পারো।

CREATE TABLE কলাম, type ও কনস্ট্রেইন্ট সংজ্ঞা দেয়। কনস্ট্রেইন্ট stored ডেটা-তে ডেটাবেস-এর প্রয়োগ করা নিয়ম। ভালো কনস্ট্রেইন্ট বাস্তব requirement মানায়। Requirement বোঝার বিকল্প নয়, তবে অনেক অবৈধ অবস্থা আটকায়।

কোন ঘটনা রাখছ পরিষ্কার করো। Attendance রো এক তারিখে এক শিক্ষার্থী-এর কথা বলে। পরিচয়, শিক্ষার্থী reference ও presence value লাগে। এই নীতিতে একই দিন একই শিক্ষার্থী-এর দুই attendance হতে পারবে না।

Definition-কে প্রতিশ্রুতি হিসেবে পড়ো

CREATE TABLE table_name (
    id INT AUTO_INCREMENT PRIMARY KEY,
    required_value INT NOT NULL,
    status_code INT NOT NULL DEFAULT 1,
    UNIQUE (required_value),
    CHECK (status_code IN (0, 1))
);

প্রতি line ডিজাইনের অংশ। Identifier বাদ দিলে তৈরি হবে; required value NULL নয়; status বাদ দিলে ডিফল্ট। UNIQUE জানা মানের পুনরাবৃত্তি আটকায়, CHECK রো-এর শর্ত দেখে। এটি definition pattern; নিজের ঘটনার আসল নাম ও reference নাও।

কনস্ট্রেইন্ট সম্পর্কিত, বিনিময়যোগ্য নয়
Ruleকী নিশ্চিতকী নিশ্চিত নয়
NOT NULLমান চাইটেক্সট nonblank বা সত্যি
UNIQUEKnown কী repeat নয়Nullable-এ NULL নেই
PRIMARY KEYUnique required পরিচয়Business number gapless
DEFAULTবাদ দিলে মানদেওয়া অন্য মান বৈধ
CHECKশর্ত FALSE নয়UNKNOWN বাদ
FOREIGN KEYReference-এর valid parentসব parent-এর child আছে

অর্থপূর্ণ domain-এ rule মেলাও

Required আর valid value

NOT NULL অজানা mark আটকায়; zero-to-100 CHECK অবৈধ জানা mark আটকায়। রেকর্ড করা ফলে প্রকৃত mark চাইলে দুটোই নাও। SQL CHECK TRUE বা UNKNOWN মেনে FALSE আটকায়, তাই রেঞ্জ একা NULL সরায় না।

NOT NULL নামও empty স্ট্রিং হতে পারে। Blank নিষিদ্ধ হলে উপযুক্ত nonblank rule ও ইনপুট validation দাও। শুধু whitespace বৈধ কি না-সহ আসল নীতি কনস্ট্রেইন্ট-এ আনো। Type একা সব business requirement বলে না।

কী,reference,ডিফল্ট

Primary কী এক বা একাধিক কলামের হয়। student_id ও attended_on unique pair একদিনে এক attendance বলে। আলাদা component বারবার আসতে পারে। Foreign কী শিক্ষার্থী number-কে existing Students রো-তে মেলায়।

কলাম বাদ দিলে বা স্পষ্ট DEFAULT চাইলে ডিফল্ট লাগে। দেওয়া মান যাচাইয়ের বিকল্প নয়। Attendance entry-তে সত্যিই উপস্থিতি ধরা হলে ডিফল্ট 1 মানায়; অন্য workflow-তে explicit ইনপুট লাগতে পারে।

Identifier বাদ দিলে AUTO_INCREMENT সুবিধামতো দেয়। ফাঁকহীন numbering-এর নিশ্চয়তা নয়। Failure, ডিলিট ও rollback-এ gap হতে পারে। সর্বোচ্চ ID-কে বর্তমান রো সংখ্যা বা আইনমাফিক receipt সংখ্যা ভাববে না।

স্ট্রাকচার বুঝে বদলাও

ALTER TABLE আগের definition বদলায়, যেমন কলাম বা কনস্ট্রেইন্ট যোগ করে। NOT NULL বা UNIQUE-এর আগে পুরোনো রো দেখো। NULL বা repeated known value নতুন rule ভাঙতে পারে। বানানো placeholder নয়, যাচাই করা তথ্য দিয়ে ঠিক করো।

DROP TABLE definition ও রো সরায়। TRUNCATE TABLE definition রেখে খালি করে, সাধারণত AUTO_INCREMENT reset করে। DELETE হলো DML; WHERE দিয়ে matching রো সরায়। ট্রানজ্যাকশন ও reference আচরণে এরা আলাদা।

MySQL-এর অনেক structural কমান্ড implicit commit ঘটায়। পরে ROLLBACK দিলেও TRUNCATE করা টেবিল ফেরে না। অন্য টেবিলের foreign কী reference থাকলে InnoDB truncate সীমিত করে। ধ্বংসাত্মক স্ট্রাকচার change শেখার জন্য নিজের scratch টেবিল নাও।

Definition তৈরি, বদল ও পরীক্ষা করো

কনস্ট্রেইন্ট-সহ attendance

Attendance উদাহরণে generated পরিচয়, শিক্ষার্থী reference, unique day, ডিফল্ট ও রেঞ্জ check একসঙ্গে আছে। একটি ইনসার্ট-এ MySQL কোন মান নিজে দেয় দেখো।

ALTER-এ capacity

ছোট study-গ্রুপ টেবিলে capacity কলাম যোগ হয়। ইনসার্ট করা গ্রুপ নতুন ডিফল্ট দশ আসন নেয়।

Empty, তারপর definition সরাও

Private লেবেল টেবিলে TRUNCATE ও DROP আলাদা দেখা যায়। DROP-এর পরে metadata সংখ্যা বলে টেবিল আর নেই।

রেঞ্জ-এর বাইরে mark reject

আপডেট-এ ইচ্ছা করে 101 চাওয়া হয়েছে। MySQL CHECK violation প্রত্যাখ্যান করে আগের বৈধ ফল রাখে।

শক্ত মনে হলেও অসম্পূর্ণ কনস্ট্রেইন্ট

UNIQUE মানেই required

Nullable unique কলাম-এ MySQL একাধিক NULL মানে। Optional email-এ মানতে পারে, কিন্তু required candidate identifier দেয় না। সবার জানা unique মান চাইলে NOT NULL-ও দাও।

অসংগত নাম

টেবিল lowercase ও কলাম descriptive রাখো, যেমন student_id, enrolled_on। একই অর্থে অকারণে StudentID, sid, student_number বদলাবে না। OS অনুযায়ী টেবিল-নাম case আচরণ বদলায়; consistent lowercase কাজে লাগে।

Rejection না বুঝে rule off

Foreign-কী এরর প্রায়ই ভুল parent বা operation অর্ডার বোঝায়। আগে reference রো ও সম্পর্ক দেখো। Check বন্ধ করলে orphan রেকর্ড থাকতে পারে। Rejection-কে ডেটা ও design খোঁজার প্রমাণ ধরো।

CHECK enforcement-এর ভার্সন জানো

MySQL 8.0.16 থেকে CHECK enforce হয়। আগের ভার্সন কিছু সিনট্যাক্স নিলেও শর্ত মানাত না। এখানে 8.0.16 বা নতুন এবং foreign কী ও transactional change-এর জন্য InnoDB ধরা।

পুরো নিয়মটি বলো

Type, required value, কী, ডিফল্ট ও check আলাদা কাজ করে। ভেবে একসঙ্গে নাও; রো change ও স্ট্রাকচার change আলাদা করো। এরপর INSERT, UPDATE ও DELETE-এ definition ব্যবহার করো।
