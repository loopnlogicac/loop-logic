Make invalid records harder to store

A mark of 101 should not quietly enter a system whose scale ends at 100. A result should not belong to a nonexistent enrollment. Table definitions let MySQL check these promises whenever rows change.

CREATE TABLE defines columns, types and constraints. A constraint is a rule the database enforces on stored data. Good constraints support the real requirements. They cannot replace understanding those requirements, but they prevent many accidental invalid states.

Start with a clear name for the fact being stored. An attendance row describes one student on one date. It needs an identity, a student reference and a presence value. It should not allow two attendance records for the same student and day under this particular policy.

Read a definition as a set of promises

CREATE TABLE table_name (
    id INT AUTO_INCREMENT PRIMARY KEY,
    required_value INT NOT NULL,
    status_code INT NOT NULL DEFAULT 1,
    UNIQUE (required_value),
    CHECK (status_code IN (0, 1))
);

Each line expresses one part of the design. The identifier is generated when omitted. A required value cannot be NULL. A default supplies an omitted status. UNIQUE forbids repeated known values. CHECK tests a condition on a row. This is a definition pattern; choose actual names and references from the fact you are modelling.

Combine rules for meaningful domains

Required values and valid values

NOT NULL prevents an unknown mark. CHECK with a zero-to-100 range prevents invalid known marks. Use both when a recorded result must have a real mark. SQL CHECK accepts TRUE or UNKNOWN and rejects FALSE, so the range condition alone does not exclude NULL.

A name declared NOT NULL may still be an empty string. If blank names are forbidden, add a suitable nonblank rule and validate input carefully. Constraints should follow the actual policy, including whether whitespace-only values are meaningful. A type declaration alone cannot describe every business requirement.

Keys, references and defaults

A primary key can have one column or several. A unique pair such as student_id with attended_on expresses one attendance event per day. Its components can repeat individually. Foreign keys ensure those student numbers refer to existing Students rows.

A DEFAULT value applies when the statement omits the column or explicitly requests DEFAULT. It is not a substitute for checking a supplied value. A default present value of 1 is suitable only if attendance entry really assumes presence; another workflow may need explicit entry instead.

AUTO_INCREMENT provides a convenient identifier when one is omitted. It does not promise gapless numbers. Failed work, deletions and rollbacks may leave gaps. Do not interpret the highest generated ID as the current number of rows or as a legally controlled receipt count.

Change structure deliberately

ALTER TABLE changes an existing definition, for example by adding a column or constraint. Before adding NOT NULL or UNIQUE, inspect existing rows. Old NULL values or repeated known values can violate the proposed rule. Correct them using verified information rather than invented placeholders.

DROP TABLE removes the table definition and its rows. TRUNCATE TABLE empties a table while keeping its definition and normally resets AUTO_INCREMENT. DELETE removes rows through DML and can have a WHERE condition. These commands have different transaction and reference behaviour.

Many MySQL structural commands cause an implicit commit. A later ROLLBACK does not restore a table emptied by TRUNCATE. InnoDB also restricts truncating a table referenced by another table’s foreign key. Use a private scratch table when exploring destructive structural changes.

Constraints that look stronger than they are

Assuming UNIQUE also requires a value

MySQL allows several NULL values in a nullable unique column. That can suit an optional email, but it does not provide a required candidate identifier. Add NOT NULL when every row must have a known unique value.

Using inconsistent names

Choose lowercase table names and descriptive column names, such as student_id and enrolled_on. Avoid switching between StudentID, sid and student_number for the same meaning without a reason. Table-name case behaviour can differ across operating systems, making consistent lowercase naming especially useful.

Disabling rules instead of understanding a rejection

A foreign-key error often identifies an incorrect parent or operation order. Check the referenced row and intended relationship first. Disabling foreign-key checks can leave orphaned records. Treat a rejection as evidence to investigate the data and design.

CHECK enforcement has a version boundary

MySQL 8.0.16 began enforcing CHECK constraints. Earlier versions accepted some CHECK syntax without enforcing its condition. The definitions here target 8.0.16 or newer and use InnoDB for foreign keys and transactional row changes.
