Ask what one value fixes

Imagine two students assigned to the same department number. If that number names one department, both rows must agree on the department name. A functional dependency, or FD, describes this promise. You use it to decide which facts belong together before splitting a large table.

Write X → Y to say that equal X values require equal Y values. X and Y are sets of attributes. Formally, any two tuples agreeing on every attribute in X must agree on every attribute in Y. Different X values may still share the same Y. A student number determines a name, but a name need not identify one student.

Dependencies come from requirements. Eight students with different hometowns do not prove that hometown determines student_id. Tomorrow another student may arrive from Dhaka. A small relation can disprove a proposed FD with two conflicting rows, but cannot establish a rule for all future data. Ask the registrar what must always hold.

Classical FD reasoning uses relations with ordinary values and set semantics. SQL permits NULL and duplicates in many places, so map the design carefully. Use primary keys, NOT NULL, uniqueness and foreign keys where those express the intended rules. A nullable UNIQUE column is not automatically a classical candidate key.

Build implications with Armstrong’s axioms

The three basic inference rules are sound: they never produce a dependency that violates the original promises. They are also complete for FDs: repeated application can derive every implied FD. You do not have to list all implications to use them. Attribute closure packages the same reasoning into a short calculation.

RuleGivenConcludeMeaning
ReflexivityY ⊆ XX → YKnowing a set includes knowing its parts
AugmentationX → YXZ → YZCarry the same extra attributes on both sides
TransitivityX → Y and Y → ZX → ZFollow a chain of determination

Union and decomposition are useful derived rules. From X → Y and X → Z, infer X → YZ. From X → YZ, infer each part separately. Pseudotransitivity gives XW → Z from X → Y and YW → Z. The W must be carried along; knowing X alone may not supply it.

To calculate X+, start with the attributes in X. Scan the FDs. Whenever a left side is contained in the current set, add its right side. Repeat the scan because an addition may unlock an earlier rule. Stop only at a fixed point. Then X → Y follows exactly when Y is contained in X+.

Find keys and simplify a cover

A registration key, line by line

Let R(S,C,N,T,D,H) mean student, course, student name, course title, department and department name. Assume F = {S → ND, D → H, C → T}. The teaching model allows at most one registration per student-course pair. Neither S nor C appears on a right side, so neither can be obtained from other attributes. Every candidate key must contain both.

Closure stageKnown attributesReason
0S,CStart with SC
1S,C,N,DApply S → ND
2S,C,N,D,HApply D → H
3S,C,N,D,H,TApply C → T

Thus SC is a superkey. S+ = SNDH lacks C and T; C+ = CT lacks S, N, D and H. Dropping either member fails, so SC is minimal and is the only candidate key under these rules. SCN is a superkey but is not a candidate key. The added name contributes nothing.

Keys can have different sizes

For R(A,B,C) with A → BC and BC → A, A+ contains ABC. BC+ also contains ABC. Neither B+ nor C+ grows beyond its starting attribute. Candidate keys are A and BC. Do not search only for keys with the smallest number of columns; minimal means no proper subset is a superkey, not globally shortest.

Reduce a canonical cover

Take F = {A → BC, B → C, A → B, AB → D, D → E}. First split every right side: A → B, A → C, B → C, A → B, AB → D, D → E. Remove the duplicate A → B. Test whether B is extraneous in AB → D by computing A+ with the current dependencies. A gives B, then AB gives D. Therefore replace AB → D with A → D. A itself is not removable because B+ does not reach D.

Now test A → C for redundancy. Temporarily remove it. A still gives B, and B gives C, so the dependency is redundant. The remaining singleton cover is G = {A → B, B → C, A → D, D → E}. Every dependency of G follows from F. Conversely, G derives A → BC and AB → D by union and augmentation, so F and G are equivalent.

Check each remaining rule by removing it and recalculating its left closure. Without A → B, A reaches D and E but not B. Without B → C, B cannot reach C. Without A → D, A reaches B and C but not D. Without D → E, D cannot reach E. All left sides are singleton and nonempty, so no further left attribute can be removed. This is a minimal cover. Some books combine the A rules as A → BD and call that the canonical cover; state which convention you use.

Use the cover to prepare a decomposition

Create AB, BC, AD and DE from G. A+ under G is ABCDE, so A is a key and AB already contains it. Each listed FD can be checked inside one component. Joining AB with BC on B is lossless because B determines BC. Joining that result with AD on A, then DE on D, is also lossless. The full preservation argument is developed in decomposition.

A different minimal cover may exist because simplifications can be chosen in different orders. Equivalence matters more than matching a particular printed list. Compare closures, and keep the original business meaning visible beside abbreviated letters. An unexplained A → B can conceal a mistaken assumption about the real registration process.

Find optional attributes systematically

Candidate-key enumeration can start with attributes absent from every right side. Treat that set as mandatory, then add combinations of the remaining attributes and calculate closures. Once a combination is a key, skip its supersets because they cannot be minimal. This prunes the search without assuming that every key has the same size.

For R(A,B,C,D) with A → B and C → D, A and C are mandatory. AC+ immediately reaches ABCD, so AC is the only candidate key. Neither B nor D can replace a mandatory attribute, and adding either to AC only creates a larger superkey.

Separate evidence from rules

Reversing the arrow

A department number determines a department name under the stated policy. That does not mean a name determines a department number unless names are also unique. Write a two-row counterexample with different numbers and the same name to test the reversal.

Stopping a closure scan too soon

If the list places D → H before S → D, the first scan may skip D → H. Scan again after adding D. The order of the written rules cannot change the mathematical closure.

Removing a rule during its own proof

For a redundant-FD test, remove that FD before calculating closure. Otherwise the rule proves itself. For an extraneous left attribute test, use the standard reduced-left closure test, then verify that the old and new covers imply each other. These are different questions.

Carry the promises into table design

You can now turn informal uniqueness promises into exact arrows, derive closures, enumerate minimal keys and simplify dependencies. Keep both the full relation heading and the FD set in every solution. Next, apply those rules to 1NF, 2NF and 3NF.
