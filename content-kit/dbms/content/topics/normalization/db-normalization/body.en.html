Repair a registration sheet

A spreadsheet can look convenient while copying the same department name into hundreds of rows. When that name changes, you must find every copy. Normalisation reorganises facts so one change has one clear home. The goal is a dependable design, not the largest possible number of tables.

Start with a sheet Student(S, Name, D, DeptName, Courses). Ayesha has Courses = {CSE 212, MAT 101}. The course collection is a repeating group for a system that must query registrations individually. Write the requirements before splitting anything: S → Name,D; D → DeptName; C → Title,Credits; and SC → Mark. Here C identifies a course and the example allows one attempt per student-course pair.

The shared university design uses section_id to distinguish offerings and stores results against a student-section pair. Our shorter SC model is a design exercise, not a replacement for that richer schema. Real requirements with retakes need an attempt or offering identifier. A normal form cannot repair a key that describes the wrong event.

Write the relation and its dependencies

-- Design notation, not SQL statements:
-- R(S, Name, D, DeptName, C, Title, Credits, Mark)
-- Key: (S,C)
-- S -> Name,D; D -> DeptName; C -> Title,Credits; SC -> Mark

A prime attribute belongs to at least one candidate key. A nonprime attribute belongs to none. In this example only S and C are prime. Candidate keys, rather than only the selected primary key, decide the formal normal-form tests. Work through every relevant dependency and all alternative keys.

Walk from 1NF to 3NF

For 1NF, make each registration a separate row and each cell a value from its chosen domain. Replace the Courses collection with C, Title, Credits and Mark columns. A string containing commas is not automatically a violation: an address can be one value if the application treats it as indivisible. A list pretending to be several course identifiers is different because membership, keys and constraints must work on each course.

SC is the key because S alone repeats for Ayesha and C repeats across students. Its closure includes the entire heading using the stated FDs. This flat relation is 1NF, but it repeats both student facts and course facts. Those repeated facts explain the next three problems.

An update anomaly appears when you change only one copy of Ayesha’s department name. An insertion anomaly prevents recording a new course without inventing a student registration or allowing fake key values. A deletion anomaly removes the last course description when you delete its last registration. These problems follow from where facts are stored, not from a missing screen validation.

A relation is in 2NF when it is in 1NF and no nonprime attribute depends on a proper subset of any candidate key. S → Name,D is partial on SC. C → Title,Credits is another partial dependency. DeptName also follows from S through D, so it belongs with the student-side facts at this stage.

The first split shares S between Student2 and the remaining registration facts. S determines all of Student2, so the split is lossless. The course split shares C, which determines Course. You can reconstruct exactly the original registrations by joining on S and C. Each partial dependency now has its own home. Registration retains the mark because neither S nor C alone determines it.

For 3NF, require every nontrivial FD X → A to have X as a superkey or A as a prime attribute. Student2 still violates this: D → DeptName has a nonkey determinant and a nonprime result. Split it into Student(S,Name,D) and Department(D,DeptName). The common D determines Department, establishing another lossless binary split. Course and Registration need no further changes under the given dependencies.

The final four relations preserve the original FD set locally. S determines student facts in Student; D determines its name in Department; C determines course facts in Course; SC determines marks in Registration. Add foreign keys from Student to Department and from Registration to Student and Course. Foreign keys enforce references; they do not replace the uniqueness and FD arguments.

A one-column candidate key rules out partial dependence on that key, but it does not guarantee 3NF. Student2 demonstrates why: its single-column key still determines a nonkey D that determines another nonkey fact. If there are alternative composite keys, inspect them too. Normalisation is about every candidate key rather than a shortcut based on the chosen PRIMARY KEY.

Observe the anomaly and its repair

Expose a partial update

One row says CSE renamed while two other rows retain the old department name. A partial update breaks the intended department rule without violating the flat table’s structure.

Update the authoritative department

The department name changes once. All three joined registrations show the same new value, and rollback restores the teaching data.

Keep course facts after the last registration

The course remains even when section 31 has no registrations. Separate course storage removes the deletion anomaly; the transaction restores enrollments and cascaded results.

The examples use the existing Department, Student, Course and enrollment relationships. Their section-based key keeps multiple offerings distinct. Compare the flat update with the joined update before changing more rows: the disagreement is a design symptom, while the joined result reads a single authoritative value.

Plan the change from duplicated rows

A real migration must resolve disagreements before adding constraints. Suppose two flat registrations for the same department_id contain different department names. SELECT DISTINCT does not decide which name is authoritative; it merely exposes two values. Confirm the correct value with the business owner, repair the source and then populate Department with one row per department key.

After copying the decomposed components, join them back on their keys and compare every original fact, not only the row count. Check missing parent references, duplicate business keys and marks that no longer map to one registration. Introduce primary keys and foreign keys only after these checks succeed. A transaction or controlled migration window must also prevent new inconsistent writes during the switch. The final reader queries can then use joins or a view while each write targets the authoritative fact.

Avoid mechanical splitting

Adding an id and declaring success

A surrogate row_id can identify the flat row but leaves S → Name and D → DeptName untouched. It does not remove duplication or those dependencies. Retain the real business key as a uniqueness rule, then decompose the facts that depend on parts of it.

Calling every indirect FD a 3NF violation

The formal 3NF exception for a prime right side matters when candidate keys overlap. Use the definition rather than “no transitive dependencies” without qualification. BCNF examines the stricter determinant rule.

Forgetting reconstruction

Splitting R into arbitrary small headings can manufacture rows when you join them. Show the common attributes and why they determine one side at each binary step. Also check which FDs remain enforceable without cross-table queries.

Map mathematical rules to MySQL

Normal-form definitions do not depend on a MySQL release. The SQL demonstrations use InnoDB and enforced foreign keys. CHECK enforcement requires MySQL 8.0.16 or newer. A production migration would copy data, resolve inconsistent duplicates, validate references and switch readers only after checking reconstructed values.

Give each changing fact one home

Move repeating course groups into rows, separate partial dependencies for 2NF, then separate the nonkey department dependency for 3NF. Prove that joins recover the original information. Continue with lossless decomposition and dependency preservation.
