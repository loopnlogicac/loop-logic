Registration sheet ঠিক করো

Spreadsheet সুবিধাজনক মনে হলেও একই বিভাগের নাম শত row-তে নকল হতে পারে। নাম বদলালে প্রতিটি কপি খুঁজতে হয়। Normalization তথ্য এমনভাবে সাজায়, যেন একটি পরিবর্তনের পরিষ্কার একটি জায়গা থাকে। লক্ষ্য নির্ভরযোগ্য ডিজাইন, যত বেশি সম্ভব টেবিল নয়।

Student(S, Name, D, DeptName, Courses) sheet ধরো। Ayesha-র Courses = {CSE 212, MAT 101}। আলাদা registration query করতে হলে এই collection repeating group। ভাঙার আগে নিয়ম লেখো: S → Name,D; D → DeptName; C → Title,Credits; SC → Mark। C কোর্সের পরিচয়; এখানে প্রতি student-course জোড়ায় এক attempt অনুমোদিত।

Shared university ডিজাইনে section_id offering আলাদা করে; ফল student-section জোড়ায় থাকে। ছোট SC মডেলটি ডিজাইন অনুশীলন, সমৃদ্ধ স্কিমার বিকল্প নয়। Retake থাকলে attempt বা offering identifier লাগে। ভুল ঘটনার পরিচয় দেওয়া key কোনো normal form সারাতে পারে না।

Relation আর dependency লেখো

-- Design notation, not SQL statements:
-- R(S, Name, D, DeptName, C, Title, Credits, Mark)
-- Key: (S,C)
-- S -> Name,D; D -> DeptName; C -> Title,Credits; SC -> Mark

Prime attribute অন্তত একটি candidate key-তে থাকে; nonprime কোনো key-তেই নেই। এখানে শুধু S ও C prime। শুধু নির্বাচিত primary key নয়, সব candidate key formal normal-form test ঠিক করে। সব প্রাসঙ্গিক dependency ও alternative key দেখো।

1NF থেকে3NF

1NF-এ প্রতি registration আলাদা row, প্রতি cell নিজ domain-এর একটি মান। Courses collection-এর বদলে C, Title, Credits, Mark কলাম করো। কমাযুক্ত string নিজে violation নয়: অ্যাপ ভাগ না করলে address একটি মান হতে পারে। কিন্তু একাধিক course identifier-এর list আলাদা; প্রতিটি course-এ membership, key ও constraint কাজ করতে হবে।

Ayesha-র জন্য S বারবার আসে, আর আলাদা student-এ C আসে, তাই একা কেউ key নয়; SC key। দেওয়া FD-তে তার closure পুরো heading পায়। Flat relation 1NF হলেও student ও course-এর তথ্য নকল করে। এখান থেকেই পরের তিন সমস্যা।

Ayesha-র department name-এর একটি কপি বদলালে update anomaly। ভুয়া registration বা key ছাড়া নতুন course রাখা না গেলে insertion anomaly। শেষ registration মুছতে গিয়ে course description-ও হারালে deletion anomaly। সমস্যা তথ্যের অবস্থানে; শুধু screen validation না থাকায় নয়।

Relation 1NF এবং কোনো nonprime attribute কোনো candidate key-এর proper subset-এর ওপর নির্ভর না করলে 2NF। S → Name,D হলো SC-এর partial dependency; C → Title,Credits-ও তাই। D হয়ে S থেকে DeptName আসে, তাই এই ধাপে student-side তথ্যের সঙ্গেই থাকবে।

2NF componentCandidate কীরাখা FD
Student2(S,নাম,D,DeptName)SS → নাম,D আর D → DeptName
Course(C,Title,Credits)CC → Title,Credits
Registration(S,C,Mark)SCSC → Mark

প্রথম split-এ Student2 ও বাকি registration-এর common S, যা পুরো Student2 নির্ধারণ করে; তাই lossless। Course split-এর common C পুরো Course নির্ধারণ করে। S ও C-তে join করে ঠিক পুরোনো registration ফেরে। Partial dependency আলাদা জায়গা পেয়েছে। Mark Registration-এ থাকে, কারণ শুধু S বা C সেটি ঠিক করে না।

3NF-এ প্রতি nontrivial X → A-তে X superkey অথবা A prime চাই। Student2-তে D → DeptName-এর determinant nonkey এবং ফল nonprime, তাই ভাঙে। Student(S,Name,D) ও Department(D,DeptName) করো। Common D Department নির্ধারণ করায় split lossless। দেওয়া FD-তে Course ও Registration আর বদলাতে হয় না।

শেষ চার relation-এ মূল FD স্থানীয়ভাবে থাকে। Student-এ S, Department-এ D, Course-এ C এবং Registration-এ SC সংশ্লিষ্ট তথ্য ঠিক করে। Student থেকে Department, Registration থেকে Student ও Course foreign key দাও। Foreign key reference মানায়; uniqueness ও FD যুক্তির বিকল্প নয়।

এক-column candidate key-তে partial dependency হয় না; তাই বলে 3NF নিশ্চিত নয়। Student2-র এক-column key থেকে nonkey D, তারপর আরেক nonkey fact আসে। Alternative composite key থাকলে সেগুলোও দেখো। Normalization সব candidate key নিয়ে, নির্বাচিত PRIMARY KEY-এর shortcut নয়।

Anomaly আর repair দেখো

Partial আপডেট প্রকাশ

এক row-তে CSE-এর নতুন নাম, অন্য দুইটিতে পুরোনো। Flat table-এর structure না ভেঙেও partial update বিভাগের নিয়ম ভাঙে।

Authoritative বিভাগ বদল

বিভাগের নাম একবার বদলায়। তিনটি joined registration একই নতুন মান দেখায়; rollback-এ আগের ডেটা ফেরে।

শেষ registration গেলেও কোর্স

Section 31-এর registration না থাকলেও course থাকে। আলাদা course storage deletion anomaly সরায়। Transaction enrollment ও cascaded result ফেরায়।

উদাহরণে আগের Department, Student, Course ও enrollment সম্পর্কই নেওয়া হয়েছে। Section-based key একাধিক offering আলাদা রাখে। আরও row বদলানোর আগে flat ও joined update তুলনা করো। অমিল ডিজাইনের লক্ষণ; joined ফলে একটি authoritative মান পড়া হয়।

Duplicated রো থেকে migration

বাস্তব migration-এ constraint দেওয়ার আগে অমিল মেটাতে হয়। একই department_id-এর দুই flat registration-এ দুই নাম থাকলে SELECT DISTINCT কোনটি সঠিক বলে না, শুধু দুটো দেখায়। দায়িত্বশীল ব্যক্তির সঙ্গে মান নিশ্চিত করে source ঠিক করো, তারপর Department-এ key-প্রতি এক row রাখো।

Component copy-এর পরে key-তে join করে প্রতিটি মূল তথ্য মেলাও, শুধু count নয়। Missing parent, duplicate business key ও registration-হীন mark খোঁজো। তারপর primary ও foreign key দাও। বদলের সময় transaction বা controlled migration window দিয়ে নতুন inconsistent write আটকাতে হবে। পরে reader join বা view নিতে পারে; writer তথ্যের authoritative জায়গায় লিখবে।

যান্ত্রিক split এড়াও

ID যোগেই সফল বলা

Surrogate row_id flat row চেনে, কিন্তু S → Name ও D → DeptName বদলায় না। Duplicate বা dependency দূর হয় না। আসল business key unique রেখেই তার অংশের ওপর নির্ভর করা তথ্য আলাদা করো।

সব indirect FD-কে3NF violation

Candidate key overlap করলে 3NF-এর prime-right-side ছাড় দরকার। শর্ত ছাড়া “transitive dependency নেই” বলার বদলে formal সংজ্ঞা নাও। BCNF আরও কঠোর determinant rule দেখে।

Reconstruction ভুলে যাওয়া

ইচ্ছেমতো ছোট heading-এ ভাঙলে join-এ নতুন row তৈরি হতে পারে। প্রতি binary ধাপে common attribute ও কেন এক পাশ নির্ধারণ করে দেখাও। কোন FD cross-table query ছাড়া মানানো যায় তাও দেখো।

গাণিতিক rule MySQL-এ

Normal-form সংজ্ঞা MySQL release-নির্ভর নয়। SQL-এ InnoDB ও enforced foreign key আছে। CHECK enforcement-এর জন্য MySQL 8.0.16 বা নতুন লাগে। বাস্তব migration-এ data copy, অমিল duplicate repair, reference validation ও reconstructed value মিলিয়ে তারপর reader বদলাতে হবে।

বদলানো fact-এর এক বাড়ি

Repeating course group-কে row করো, 2NF-এ partial dependency আলাদা করো, 3NF-এ nonkey department dependency সরাও। Join-এ মূল তথ্য ফেরে প্রমাণ করো। এরপর lossless decomposition ও dependency preservation পড়ো।
