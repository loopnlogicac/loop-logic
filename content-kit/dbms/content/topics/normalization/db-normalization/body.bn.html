Registration sheet ঠিক করো

শত রো-তে একই বিভাগ নাম রাখলে দেখতে সুবিধা,নাম বদলাতে সব copy খুঁজতে হয়। Normalization fact গুছিয়ে এক পরিবর্তনের এক বাড়ি দেয়। লক্ষ্য নির্ভরযোগ্য design,সর্বোচ্চ টেবিল সংখ্যা নয়।

Student(S,নাম,D,DeptName,Courses)-এ Ayesha-র Courses={CSE212,MAT101}। আলাদা registration কোয়েরি-তে collection repeating গ্রুপ। আগে rule:S→নাম,D;D→DeptName;C→Title,Credits;SC→Mark। এখানে কোর্স C আর pair-পিছু এক attempt।

Shared schema section_id-তে offering আলাদা,শিক্ষার্থী-সেকশন-এ ফল। ছোট SC শুধু design exercise,সমৃদ্ধ schema-র বদলি নয়। Retake-এ attempt/offering ID চাই। ভুল event কী normal form সারায় না।

Relation আর dependency লেখো

-- Design notation, not SQL statements:
-- R(S, Name, D, DeptName, C, Title, Credits, Mark)
-- Key: (S,C)
-- S -> Name,D; D -> DeptName; C -> Title,Credits; SC -> Mark

Prime attribute অন্তত এক candidate কী-তে,nonprime কোনোটিতে নয়। এখানে S-C prime। শুধু selected primary নয়,সব candidate কী formal test ঠিক করে। Relevant FD আর alternative কী দেখো।

1NF থেকে3NF

1NF-এ registration-পিছু রো,প্রতি cell chosen domain-এর মান। Courses বদলে C,Title,Credits,Mark। Comma স্ট্রিং নিজে violation নয়,address indivisible হলে এক মান। বহু কোর্স ID-র list আলাদা,কারণ membership,কী,কনস্ট্রেইন্ট কোর্স-পিছু চাই।

Ayesha-তে S repeat,C শিক্ষার্থী-জুড়ে repeat,SC কী। FD-তে closure পুরো heading। Flat1NF হলেও শিক্ষার্থী-কোর্স fact repeat,পরের তিন সমস্যা তাই।

এক copy-তে বিভাগ নাম বদল আপডেট anomaly। Registration বানানো বা fake কী ছাড়া নতুন কোর্স রাখা যায় না,insertion anomaly। শেষ registration মুছে কোর্স description হারানো deletion anomaly। Fact কোথায় রাখা তার সমস্যা,screen validation নয়।

2NF মানে1NF আর কোনো candidate কী-র proper subset-এ nonprime dependent নয়। SC-তে S→নাম,D আর C→Title,Credits partial। S→D→DeptName,তাই এই ধাপে শিক্ষার্থী-পক্ষে যায়।

2NF componentCandidate কীরাখা FD
Student2(S,নাম,D,DeptName)SS → নাম,D আর D → DeptName
Course(C,Title,Credits)CC → Title,Credits
Registration(S,C,Mark)SCSC → Mark

প্রথম split-এর common S পুরো Student2 ঠিক করে,lossless। Course split-এ common C পুরো Course। S-C জয়েন-এ ঠিক original registration ফেরে। Partial FD নিজস্ব জায়গা পায়;Mark registration-এ,কোনো এক অংশ যথেষ্ট নয়।

3NF-এ সব nontrivial X→A-তে X superkey বা A prime চাই। Student2-এ D→DeptName nonkey determinant-nonprime ফল,ভাঙে। Student(S,নাম,D),Department(D,DeptName) করো। Common D বিভাগ ঠিক করে,lossless। Given FD-তে Course-Registration আর বদল নয়।

চার relation-এ সব FD locally:Student-এS,Department-এD,Course-এC,Registration-এSC। Student→Department আর Registration→Student,Course FK দাও। FK reference মানায়,uniqueness-FD proof-এর বদলি নয়।

One-কলাম কী-তে ওই কী-র partial নেই,3NF নিশ্চিত নয়। Student2-এ এক-কলাম কী থেকেও nonkey D আরেক fact ঠিক করে। Alternative composite থাকলে সেগুলোও দেখো,chosen PRIMARY KEY-ভিত্তিক shortcut নয়।

Anomaly আর repair দেখো

Partial আপডেট প্রকাশ

এক রো CSE renamed,অন্য দুই old। Flat স্ট্রাকচার না ভেঙেও intended বিভাগ rule ভাঙে।

Authoritative বিভাগ বদল

নাম একবার বদলে তিন joined registration-এ একই। Rollback teaching ডেটা ফেরায়।

শেষ registration গেলেও কোর্স

Section31 empty হলেও কোর্স থাকে। আলাদা স্টোরেজ deletion anomaly সরায়;ট্রানজ্যাকশন enrollment আর cascaded ফল ফেরায়।

উদাহরণ existing Department,Student,Course,enrollment সম্পর্ক। Section কী বহু offering আলাদা রাখে। Flat disagreement design symptom,জয়েন এক authoritative মান পড়ে—আরও রো বদলানোর আগে তুলনা।

Duplicated রো থেকে migration

কনস্ট্রেইন্ট-এর আগে disagreement মেটাও। একই department_id-তে দুই নাম হলে DISTINCT দুটো দেখায়,কোনটি সত্য বাছে না। Business owner-এ নিশ্চিত হয়ে source repair,তারপর কী-পিছু Department।

Component copy করে কী-তে জয়েন,শুধু সংখ্যা নয় প্রতিটি fact মিলাও। Missing parent,duplicate business কী,এক registration-এ না মেলা mark দেখো। সফল হলেই PK-FK। Switch-এ নতুন inconsistent write আটকাতে ট্রানজ্যাকশন/controlled window। Reader জয়েন/ভিউ নেবে,write authoritative fact-এ।

যান্ত্রিক split এড়াও

ID যোগেই সফল বলা

Surrogate row_id flat রো চেনালেও S→নাম,D→DeptName থাকে। Duplication-FD যায় না। Business কী unique রেখে অংশের fact decompose।

সব indirect FD-কে3NF violation

Overlap কী-তে prime right-side exception জরুরি। Unqualified “no transitive dependency” নয়,formal definition। BCNF stricter determinant দেখে।

Reconstruction ভুলে যাওয়া

Arbitrary ছোট heading জয়েন-এ ভুয়ো রো। প্রতি binary step-এর common attribute কেন এক side ঠিক করে বলো। Cross-টেবিল কোয়েরি ছাড়া কোন FD check হয় তাও দেখো।

গাণিতিক rule MySQL-এ

Normal form release-নির্ভর নয়। SQL InnoDB-FK,CHECK8.0.16+। বাস্তব migration-এ copy,duplicate repair,reference validate,reconstructed value check-এর পর reader switch।

বদলানো fact-এর এক বাড়ি

Repeating কোর্স রো-তে,2NF-এ partial আলাদা,3NF-এ nonkey বিভাগ। জয়েন original ফেরায় proof দাও। পরের lossless আর dependency preservation।
