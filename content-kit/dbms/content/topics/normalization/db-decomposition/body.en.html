Prove that the split keeps its promises

You can cut a registration table into smaller pieces and still join them into the wrong answer. Two tests protect different promises. Losslessness protects the information in valid rows. Dependency preservation protects the ability to enforce the original rules inside individual components.

For a decomposition D = {R1,…,Rn}, lossless means that joining the projections of every legal relation r on R returns exactly r. Projection removes duplicate tuples in relational theory. The join always contains the original tuples, because each original tuple contributes to every projection. The risk is extra, spurious tuples created by matching parts from different originals.

An SQL SELECT without DISTINCT uses bag semantics. When comparing a mathematical decomposition with SQL, account for duplicates and define keys. A query that happens to return the same row count today is not a proof over all legal states. Write the FD set, headings and assumptions beside every calculation.

Apply two different tests

For a binary decomposition into R1 and R2 whose union is R, the FD-based lossless criterion is (R1 ∩ R2) → R1 or (R1 ∩ R2) → R2 in F+. Calculate the intersection’s closure under F and ask whether it includes an entire component. This criterion is both necessary and sufficient for losslessness with respect to FDs.

For preservation, project F+ onto each Ri. Let G be the union of those projected FD sets. The decomposition preserves F when G implies every original FD. Because projected rules already follow from F, the reverse implication is automatic. Check each X → Y in F by finding X+ under G. If Y is missing, local enforcement is insufficient.

A projection can include derived rules. Suppose F = {A → B, B → C}, and one component is AC. Although no printed FD uses only A and C, A → C is implied and belongs to the projection. Looking only for the original arrows in the components can wrongly declare preservation lost.

Reconstruct, challenge and chase

A binary lossless split

Let R(A,B,C,D), F = {A → B, B → C, C → D}, and split into AB and BCD. Their intersection is B. Starting B+ = {B}, B → C adds C, then C → D adds D. Thus B+ contains BCD, and the split is lossless. A need not be determined by B: determining one side is sufficient.

The projected rules include A → B in AB, and B → C plus C → D in BCD. Their union contains all original rules, so preservation holds too. A+ = ABCD establishes A as a candidate key. Reconstructing by B is safe because there is only one C,D combination per B in a valid original relation.

A lossy split with a concrete witness

Now take R(A,B,C), F = {A → B}, and decompose into AB and BC. The intersection is B; B+ = {B}, which contains neither AB nor BC. The test fails. To show what that means, choose a legal original r with just two tuples.

AB projects to {(a1,b1),(a2,b1)}. BC projects to {(b1,c1),(b1,c2)}. Joining on B yields four tuples: the original two plus (a1,b1,c2) and (a2,b1,c1). A → B still holds in the original and in the reconstruction. That FD does not say which C belongs with which A, so the decomposition discards precisely that association.

If the business rule B → C were also valid, the two-row witness would be illegal and the closure test would succeed. This is why a lossless judgment is always relative to a stated dependency set. You cannot silently add a convenient FD after seeing a bad join.

A lossless split that loses enforcement

Use SCI with F = {SC → I, I → C}, decomposed as SI and IC. Their intersection I determines IC, proving losslessness. The projected nontrivial rules contribute I → C, but none supplies I from SC. Under their union, SC+ stays SC. Therefore SC → I is not preserved.

A witness for the enforcement problem is SI = {(101,Nusrat),(101,Arif)} and IC = {(Nusrat,DBMS),(Arif,DBMS)}. The components satisfy their local FDs. Their join violates SC → I. These component states need not be projections of a valid original relation; they demonstrate the danger of independent updates after decomposition.

Chase a three-way decomposition

For ABCD and the chain A → B, B → C, C → D, take AB, BC and CD. A chase tableau has one row per component. Put the distinguished symbol aA in a column when that component includes A; otherwise put a fresh symbol unique to that cell. Use analogous symbols for the other columns.

Rows AB and BC agree on B = aB. Apply B → C to equate their C symbols; replace b13 with aC, because a distinguished symbol takes priority. Now all three rows agree on C = aC. Apply C → D and replace b14 and b24 with aD. The AB row becomes (aA,aB,aC,aD), an all-distinguished row. The chase therefore proves the decomposition lossless.

A → B causes no additional useful merge here, since no two starting rows share A. That is fine: not every FD must fire. The presence of one all-distinguished row is the success condition. If no further merges are possible and no such row exists, the FD chase does not establish a lossless decomposition; for this standard tableau procedure the saturated failure witnesses lossiness under the FDs.

You can also prove this example by safe binary steps. First split ABCD into ABC and CD on C → D; then split ABC into AB and BC on B → C. Both intersections determine their separated side. This sequence is often easier to explain than a full chase, but it must really yield the given components. Arbitrarily checking selected component pairs is not a valid general multiway test.

Synthesise a preserving 3NF design

Begin with a singleton minimal cover G. For each determinant X, make a relation containing X and its right-side attributes. Remove a relation contained in another relation. If no component contains a candidate key for the original R, add a relation containing a candidate key. This is the standard 3NF synthesis construction; the minimal-cover assumptions are part of its guarantee.

For R(A,B,C,D,E), G = {A → B, B → C, C → A, D → E}, synthesis initially gives AB, BC, CA and DE. No component contains a key for all five attributes. D is mandatory, and A, B or C can determine the three-cycle. Candidate keys are AD, BD and CD. Add AD. Each original FD has a component, and adding a key relation provides the lossless guarantee.

The initial four components are not lossless: their join can combine every ABC group with every DE group, forgetting which D originally accompanied which A. AD restores that association. Do not omit the key step merely because every dependency already appears somewhere. This example separates preservation from losslessness in the opposite direction to the instructor example.

When you write an exam answer, end with two separate conclusions and their evidence. “Lossless because I determines IC; not preserving because SC+ under the projections lacks I” is a complete argument. Saying only “BCNF decomposition” hides both the reconstruction reason and the enforcement cost.

Distinguish an A-based split from a preserving split

For R(A,B,C) and F = {A → B, B → C}, consider AB and AC. The intersection A has closure ABC, so this binary decomposition is lossless. The AC projection includes the derived A → C. Its union with A → B cannot derive B → C, since B+ under those local rules remains B. Thus the design loses dependency preservation despite retaining the candidate key in both components.

A concrete enforcement witness uses AB = {(a1,b),(a2,b)} and AC = {(a1,c1),(a2,c2)}. Each component obeys its A-based FD. Their join associates the same b with both c1 and c2, violating the original B → C rule. In contrast, AB and BC preserve that dependency locally and are also lossless because B determines BC. Compare the projected closures before selecting either design for implementation.

For either decomposition, record the relation headings before calculating closures. The same attribute set can be a key for a component while failing to identify rows of the original relation.

Use the correct heading at each step

Checking whether the intersection is a key for all of R

The binary criterion needs the intersection to determine one component, not the whole original heading. B in the AB,BCD example is enough even though B does not determine A.

Inferring preservation from foreign keys

A foreign key keeps references valid. It does not derive SC → I across SI and IC. Referential integrity and local FD preservation protect different invariants, so list both when implementing the schema.

Reusing undistinguished symbols in a chase

Each missing cell starts with a fresh b symbol. Reusing one can create an agreement that the dependencies never justified. Only merge symbols when a stated FD allows it, and replace consistently across the tableau.

Finish with two explicit conclusions

Use intersection closure for a binary split, projected-rule closures for preservation, and a chase or valid sequence for several components. The same design can pass one test and fail the other. Return to normalisation to connect these proofs with SQL keys and foreign keys.
