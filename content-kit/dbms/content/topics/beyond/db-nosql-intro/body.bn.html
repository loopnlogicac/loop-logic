কোন কাজ বারবার হবে তা দিয়ে শুরু করো

Shopping cart,social কানেকশন ও university transcript ভিন্ন প্রশ্ন করে। Relational model সব বোঝাতে পারে; অন্য model কোনো access সহজে প্রকাশ বা scale করতে পারে। NoSQL অনেক system-এর পরিবার, এক engine বা consistency promise নয়।

নামটি প্রায়ই “not only SQL” বলা হয়। Nonrelational system-এ SQL-like ভাষা, relational-এ JSON-ও আছে। পণ্য নাম নয়, ডেটা shape,operation,invariant,failure দেখে বাছো। Flexible representation-এও required ফিল্ড ও valid value-এর নিয়ম লাগে।

এক request কী পড়ে-লেখে, কোন fact একসঙ্গে atomic বদলাবে ও কোন রিপোর্ট গ্রুপ পেরিয়ে জয়েন করবে ভাবো। Distribution-এ replication,partition placement,network failure আসে। Relational deployment-এও এগুলো আছে; শুধু NoSQL-এর নয়।

Document store related ফিল্ড,array,nested object একটি retrievable unit-এ রাখে। Cart document-এ customer পরিচয় ও item থাকতে পারে। Embed-এ এক-cart read সহজ। পণ্য reference-এ সব attribute copy লাগে না; agreed price copy purchase history ঠিক রাখে।

কী-value store get(session_id),put(session_id,value)-এর মতো কাজ করে। কী মূল পথ। Cache expiry দিতে পারে; নামটি নিজে persistence,eviction বা ট্রানজ্যাকশন guarantee নয়। নির্দিষ্ট system-এর ফিচার দেখো।

Wide-কলাম store বা কলাম-family store partition ও clustering choice ঘিরে ডেটা গুছায়। বড় scan-এর compressed analytical columnar engine আলাদা। Attendance সেকশন-month partition ও তারিখ-শিক্ষার্থী অর্ডার-এ হতে পারে। ভুল partition কী অধিকাংশ traffic এক node-এ ফেলতে পারে।

Graph store relationship-কে সরাসরি edge হিসেবে রাখে। Course prerequisite path traversal-এ বলা যায়। Relational recursion-ও path পারে; সম্পর্ক আছে বলেই graph store বাধ্যতামূলক নয়। Traversal-এর depth,frequency,selectivity দেখো।

Global stock আপডেট এখনও অর্ডার ও inventory পেরোয়। Document boundary overselling নিজে সারায় না। কিছু system multi-document ট্রানজ্যাকশন দেয়; scope-cost বোঝো। Reservation বা compensation workflow business process বদলায়, explicit failure handling চাই।

Event partition বাছো

Common request যদি “সেকশন 31-এর March 2026 attendance”, সেকশন-month partition bounded রেঞ্জ এক রাখে। তারিখ-শিক্ষার্থী clustering অর্ডার পড়া সাহায্য করে। এক শিক্ষার্থী কোন কোন সেকশন-এ গেছে জানতে অন্য টেবিল/path লাগতে পারে। কোয়েরি-specific duplication ইচ্ছাকৃত হতে পারে, তবে আপডেট process app-এর দরকারি consistency রাখবে।

সব university event-এর এক permanent partition করবে না; সীমাহীন বাড়ে ও hotspot হয়। শুধু current-day partition-ও সব write এক জায়গায় নিতে পারে। মোট স্টোরেজ নয়, peak partition size ও throughput মাপো। পরে repartition-এ ডেটা movement ও app coordination লাগতে পারে।

Network partition-এর সময় CAP

CAP theorem asynchronous distributed model-এ node-গুলোর যোগাযোগ বিচ্ছিন্ন হওয়া দেখে। Consistency সাধারণত linearizability: completed operation real-time অর্ডার মেনে এক current copy-এর মতো। Availability-তে nonfailed node-এর প্রতিটি request সফল response পাবে; partition-এর জন্য reject বা অনন্ত wait নয়।

Network partition-এ সব relevant operation-এ দুটি guarantee একসঙ্গে হয় না। এটি “চিরকাল যেকোনো দুই ফিচার বাছো” নয়। Partition tolerance model-এর failure শর্ত। Partition না থাকলেও latency,replication,consistency গুরুত্বপূর্ণ, কিন্তু theorem-এর impossibility সাধারণ পারফরম্যান্স benchmark নয়।

A-তে write শেষের পরে B যদি linearizability ভেঙে v1 দেয়, ওই operation-এ availability নেওয়া হলো। Latest state নিশ্চিত করতে না পেরে B refuse/wait করলে CAP availability ছাড়া হলো। Public catalogue ও balance change-এ পছন্দ আলাদা হতে পারে।

Eventual consistency বলে আপডেট থামলে ও যোগাযোগ ফিরলে conflict-resolution assumption অনুযায়ী replica converge করবে। প্রতিটি read current বা conflicting পেমেন্ট ব্যবসায় ঠিক হবে বলে না। Read-your-writes,causal অর্ডার,strong ট্রানজ্যাকশন আলাদা guarantee, পণ্য নির্দিষ্ট scope-এ দিতে পারে।

University-র জন্য বাছাই

Transcript-এ strong কী,reference,mark কনস্ট্রেইন্ট ও শিক্ষার্থী-offering-ফল জয়েন চাই। আগের relational schema ভালো শুরু। কী-based session cache পাশে, prerequisite explorer-এ graph operation থাকতে পারে। অনেক model একসঙ্গে চললেও প্রতিটিতে backup,monitoring,synchronization কাজ বাড়ে।

Failed আপডেট-এর পরে duplicate fact কীভাবে সারবে জিজ্ঞেস করো। অনেক document-এ নাম থাকলে multi-document আপডেট বা asynchronous propagation লাগে। Display লেবেল-এ মানলেও authoritative grade-এ নাও মানতে পারে। Denormalization read সহজ করে write ও staleness-এর দায় বাড়ায়।

শেষে operational evidence দেখো: ট্রানজ্যাকশন boundary,ইনডেক্স,কোয়েরি limit,replica placement,recovery ও team experience। “Schema-less” মানে arbitrary type নিরাপদ নয়। Document shape ভার্সন করো, required ফিল্ড validate, migration পরিকল্পনা করো। Model কনস্ট্রেইন্ট কোথায় থাকে বদলায়; সংজ্ঞার প্রয়োজন সরায় না।

শুধু মডেলের নাম দেখে সিদ্ধান্ত নিও না

সব NoSQL-কে eventually consistent বলা

System ও operation mode অনুযায়ী strong read বা ট্রানজ্যাকশন-সহ guarantee আলাদা। Consistency দাবি করার আগে exact operation ও configuration বলো।

Wide-কলাম আর analytical কলাম মেশানো

কলাম-family distributed রো partition ও কোয়েরি pattern ঘিরে সাজানো। Analytical columnar compressed কলাম scan করে। একই “কলাম” শব্দ workload এক করে না।

Foreign কী আছে বলেই graph বাছা

বেশিরভাগ কাজের ডেটা-তেই সম্পর্ক আছে। Graph-এর লাভ traversal workload ও access need থেকে, শুধু connected রেকর্ড থেকে নয়।

মডেল ও নিশ্চয়তা একসঙ্গে বাছো

Document aggregate,known-কী access,partition event ও relationship traversal তুলনা করো। Partition-এ কোন operation-এর কী response-consistency চাই বলো। Concrete requirement থেকে model বোঝাতে বিশ্ববিদ্যালয় প্রজেক্ট নাও।
