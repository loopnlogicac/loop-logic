Access pattern দিয়ে শুরু

Cart,social কানেকশন,transcript আলাদা প্রশ্ন। Relational-এ সব হয়,তবে বিশেষ access অন্য model-এscale/express সহজ হতে পারে। NoSQL broad family,এক engine বা consistency promise নয়।

“Not only SQL” বলা হয়। Nonrelational SQL-like দিতে পারে,relational JSON রাখে। নাম নয়,shape,operation,invariant,failure দিয়ে বাছো। Flexible-তেও required ফিল্ড-valid value rule চাই।

এক request কী read-write,কোন fact atomic,কোন রিপোর্ট cross-গ্রুপ জয়েন জানতে হবে। Distribution replica,partition,networkfailure আনে;relational-এও আছে,NoSQL-only নয়।

Event partition বাছো

সাধারণ প্রশ্ন যদি “সেকশন 31-এর March 2026-এর attendance” হয়, সেকশন আর month দিয়ে partition করলে নির্দিষ্ট রেঞ্জ একসঙ্গে থাকে। তারিখ আর শিক্ষার্থী-এর clustering অর্ডার ভেতরের পড়া সাজায়। এক শিক্ষার্থী কোন কোন সেকশন-এ ছিল জানতে অন্য টেবিল বা access path লাগতে পারে। কোয়েরি অনুযায়ী duplication সচেতন হতে পারে, তবে আপডেট যথেষ্ট consistent রাখতে হবে।

সব university event এক permanent partition-এ রেখো না। সেটি সীমাহীন বড় হয়ে hotspot হতে পারে। শুধু বর্তমান দিনকেও কী করলে সব write এক জায়গায় যায়। শুধু মোট স্টোরেজ নয়, peak partition size আর throughput হিসাব করো। পরে repartition করতে ডেটা movement আর app-এর সমন্বয় লাগতে পারে।

Network partition-এর সময় CAP

CAP theorem এমন asynchronous distributed model নিয়ে কথা বলে যেখানে node-এর যোগাযোগ বিচ্ছিন্ন হতে পারে। এখানে consistency সাধারণত linearizability: completed operation যেন এক বর্তমান copy-তে real-time মেনে সাজানো হয়েছে। Availability মানে nonfailed node-এ প্রতিটি request সফল response পাবে, partition-এর জন্য reject বা অনির্দিষ্ট অপেক্ষা নয়।

Network partition-এর সময় সব প্রাসঙ্গিক operation-এ দুটোই নিশ্চিত করা যায় না। এটি “চিরকাল যেকোনো দুই ফিচার বেছে নাও” ধরনের menu নয়। Partition tolerance model-এর failure শর্ত। যোগাযোগ ঠিক থাকলেও latency, replication আর consistency-এর পছন্দ আছে, কিন্তু সেগুলো theorem-এর নির্দিষ্ট impossibility proof-এর সমান নয়।

A-তে write সম্পূর্ণ হওয়ার পরে B যদি linearizability ভেঙে v1 দেয়, ওই operation-এ সে availability বেছে নেয়। সর্বশেষ অবস্থা নিশ্চিত করতে না পেরে B অপেক্ষা বা প্রত্যাখ্যান করলে CAP-এর সংজ্ঞায় availability ছাড়ে। Public catalogue আর balance বদলানোর কাজের উপযুক্ত পছন্দ আলাদা হতে পারে।

Eventual consistency বলে, আপডেট থামলে আর যোগাযোগ ফিরলে নির্দিষ্ট conflict-resolution assumption-এ replica এক হবে। প্রতিটি read বর্তমান, বা conflicting পেমেন্ট business-এর জন্য ঠিক মিটবে—এমন প্রতিশ্রুতি নয়। Read-your-writes, causal ordering আর শক্ত ট্রানজ্যাকশন mode আলাদা নিশ্চয়তা, যা পণ্য নির্দিষ্ট scope-এ দিতে পারে।

University-র জন্য বাছাই

Transcript-এ শক্ত কী, reference, mark কনস্ট্রেইন্ট আর শিক্ষার্থী-offering-ফল জয়েন দরকার। Existing relational schema তাই ভালো শুরু। Session cache কী-based access যোগ করতে পারে, prerequisite explorer graph operation নিতে পারে। একাধিক model পাশাপাশি চলে, তবে প্রতিটি system-এ backup, monitoring আর synchronization-এর কাজ বাড়ে।

আপডেট ব্যর্থ হলে duplicate fact কীভাবে ঠিক হবে জিজ্ঞেস করো। বহু document-এ নাম থাকলে multi-document change বা asynchronous propagation লাগতে পারে। Display লেবেল-এ চললেও authoritative grade-এ তা নাও মানাতে পারে। Denormalization সহজ read-এর বিনিময়ে write আর stale value সামলানোর দায় বাড়ায়।

শেষে ট্রানজ্যাকশন boundary, supported ইনডেক্স, কোয়েরি limit, replica placement, recovery আর দলের অভিজ্ঞতার evidence দেখো। “Schema-less” মানে app যেকোনো type নিরাপদে নেয় না। Document shape-এর ভার্সন রাখো, required ফিল্ড যাচাই আর migration প্ল্যান করো। Model বদলালে কনস্ট্রেইন্ট কোথায় থাকে বদলায়, সংজ্ঞা দেওয়ার প্রয়োজন যায় না।
