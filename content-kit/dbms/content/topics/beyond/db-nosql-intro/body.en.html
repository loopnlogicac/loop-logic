Start from access patterns

A shopping cart, a social connection and a university transcript ask different questions. A relational model can represent all three, but another model may make a particular access pattern easier to scale or express. NoSQL is a broad family of systems rather than one storage engine or one consistency promise.

The name is often read as “not only SQL.” Some nonrelational systems provide SQL-like query languages, and relational systems support JSON documents. Decide using the data shape, operations, invariants and failure requirements, rather than whether the product’s name contains SQL. A flexible representation still needs rules about required fields and valid values.

A useful comparison asks what one request reads or writes, which facts must change atomically and which reports must join information across groups. Distribution introduces replication, partition placement and network failures. These concerns exist in relational deployments too; they are not exclusive to NoSQL.

A document store keeps related fields, arrays and nested objects in one retrievable unit. For a cart, the document can include customer identity and line items. Embedding makes one-cart reads convenient. Referencing separate product documents avoids copying every product attribute, while copying the agreed price can correctly preserve purchase history.

A key-value store answers requests such as get(session_id) and put(session_id,value). The key is the main route to the value. A cache may add an expiration policy, but “key-value” does not itself guarantee persistence, eviction behaviour or transaction support. Verify those features for the selected system.

A wide-column store, sometimes called a column-family store, groups data around partition and clustering choices. This is different from an analytical columnar engine that compresses each column for large scans. A query-oriented table might partition attendance by section and month, then order events by date and student. A bad partition key can put most traffic on one node.

A graph store represents relationships as first-class edges. A prerequisite path from one course to another can be expressed as a traversal. Relational recursive queries can also solve paths, so graph storage is not required merely because the data contains relationships. Evaluate the depth, frequency and selectivity of the traversals.

Choose a boundary and test a failure

Design an order aggregate

Order document 206
customer_id: 105
ordered_on: 2026-03-02
items:
  product_id: 1, quantity: 2, agreed_price_bdt: 60.00
  product_id: 3, quantity: 1, agreed_price_bdt: 120.00

The order and its items are often read together, so embedding the items can fit one aggregate. Store the agreed item price because later catalogue price changes must not rewrite purchase history. Keep customer identity as a reference when its details are maintained elsewhere. Decide whether the customer address is a live reference or a historical delivery snapshot; those are different facts.

Updating global stock still spans the order and product inventory. A document boundary does not automatically solve overselling. Some document databases support multi-document transactions, with scope and cost limits that must be understood. Alternatives such as reservations and compensating workflows change the business process and require explicit failure handling.

Choose an event partition

Suppose the common request is “show attendance events for section 31 during March 2026.” A partition key based on section and month keeps that bounded range together. A clustering order by event date and student can support ordered reading within it. A request for every section attended by one student may require another table or access path. Query-specific duplication can be deliberate, but its update process must stay consistent enough for the application.

Avoid one permanent partition for all university events. It can grow without bound and become a hotspot. Likewise, a partition for the current day alone can direct every write to one place. Estimate peak partition size and throughput, not just total storage. Repartitioning later is an operational change that may need data movement and application coordination.

Understand CAP during a partition

The CAP theorem addresses an asynchronous distributed setting where communication between nodes can be interrupted. Its consistency is typically linearizability: completed operations behave as if there were one current copy with a real-time-respecting order. Its availability requires every request to a nonfailed node to receive a successful response, rather than being rejected or waiting indefinitely because of the partition.

During a network partition, a system cannot guarantee both those properties for all relevant operations. This is not a general “pick any two features forever” menu. Partition tolerance concerns the failure condition in the model. When there is no partition, latency, replication and consistency choices still matter, but the theorem’s specific impossibility argument is not the same as an everyday performance benchmark.

EventNode ANode BDecision
Before partitionBalance version v1Balance version v1Replicas agree
Link failsAccepts change to v2Cannot receive v2Communication is unavailable
Read arrives at BStill separatedOnly has v1Return potentially stale data or refuse/wait

If B returns v1 after a completed write to A in a way that violates linearizability, the system chooses availability over that consistency guarantee for the operation. If B refuses or waits because it cannot establish the latest state, availability as defined by CAP is sacrificed. The appropriate choice can differ between a public catalogue page and a balance-changing operation.

An eventual-consistency promise says replicas converge when updates stop and communication recovers, under the system’s conflict-resolution assumptions. It does not specify that every read is current, nor that conflicting payments are resolved correctly for the business. Read-your-writes, causal ordering and stronger transaction modes are separate guarantees that products may provide in particular scopes.

Make a university choice

A transcript system needs strong keys, references, mark constraints and joins among students, offerings and results. The existing relational schema is a sensible starting point. A session cache can complement it with key-based access, and a prerequisite explorer may benefit from graph-oriented operations. Multiple models can coexist, but each added system introduces backup, monitoring and synchronisation work.

Ask how duplicate facts are repaired after a failed update. If a name appears in many documents, changing it may be a multi-document operation or an asynchronous propagation process. That can be acceptable for a display label while unsuitable for an authoritative grade. Denormalisation trades simpler reads for more responsibility over writes and staleness.

Finally, examine operational evidence: transaction boundaries, supported indexes, query limits, replica placement, recovery procedures and team experience. “Schema-less” does not mean that an application accepts arbitrary types safely. Version document shapes, validate required fields and plan migrations. A different model changes where constraints live; it does not remove the need to define them.

Avoid model-name shortcuts

Calling all NoSQL eventually consistent

Different systems and operation modes provide different guarantees, including strong reads or transactions. State the exact operation and configuration before making a consistency claim.

Confusing wide-column with analytical column storage

Column-family access is organised around distributed row partitions and query patterns. Analytical columnar storage focuses on scanning compressed columns. The shared word “column” does not make their workloads identical.

Choosing a graph because foreign keys exist

Most useful data has relationships. Graph-specific value comes from the traversal workload and its access needs, not merely the presence of connected records.

Choose a model and its guarantees together

Compare document aggregates, known-key access, partition-oriented events and relationship traversals. During partitions, define which consistency and response guarantees each operation needs. Use the university project to justify a model from concrete requirements.
