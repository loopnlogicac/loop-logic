Let two cashiers work at once

Two cashiers can sell the last notebook at the same moment. If both read stock 1 and later write stock 0, the database may record only one deduction for two sales. Concurrency control makes overlapping transactions follow rules that protect the intended result.

A schedule lists operations from transactions while preserving each transaction’s own order. A serial schedule finishes one transaction before starting another. A serialisable schedule may interleave operations but has an effect equivalent to a serial order under a specified equivalence definition. Interleaving is useful because one transaction can progress while another waits for disk or a lock.

We use r1(X) for transaction 1 reading X and w1(X) for writing X. Commit and abort events matter for recovery, but the basic conflict-serialisability test looks at read/write ordering. Serialisability and recoverability are separate properties; an acyclic graph alone does not guarantee safe dirty-read behaviour.

Build a precedence graph before guessing

Two operations conflict when they belong to different transactions, access the same data item and at least one writes it. Read-read pairs do not conflict. For each ordered conflicting pair from Ti to Tj, draw an edge Ti → Tj. If the resulting precedence graph is acyclic, the schedule is conflict-serialisable. Any topological ordering gives an equivalent serial transaction order.

The graph has one edge, so the interleaving is conflict-equivalent to T1 then T2. Operations on different items can move past each other without changing relevant conflicts. Graph nodes are transactions, not individual SQL statements or accounts.

Now consider r1(X), r2(X), w1(X), w2(X). r1(X) before w2(X) gives T1 → T2. r2(X) before w1(X) gives T2 → T1. The cycle means no serial ordering preserves all conflicts. If both transactions computed a new balance from their old read, the last write can erase the other change. Cycle: not conflict-serialisable

A recoverable schedule commits a reader only after the transaction whose value it read has committed. A cascadeless schedule avoids reading uncommitted writes altogether. A strict schedule also prevents overwriting uncommitted writes. These strengthen recovery behaviour; they are not replacements for the graph test.

Move from schedules to actual locks

Two phases of locking

A shared lock allows compatible readers; an exclusive lock protects a writer against incompatible access. In basic two-phase locking, or 2PL, a transaction first grows by acquiring locks. Once it releases any lock, it enters a shrinking phase and may acquire no new locks. This rule guarantees conflict serialisability for the lock-based model, but it can deadlock.

Strict 2PL retains exclusive locks until commit or abort, preventing other transactions from reading or overwriting uncommitted writes. Rigorous 2PL retains shared locks too. Some textbooks use slightly different terminology, so state which locks are held. InnoDB combines locking with multiversion concurrency control; its ordinary consistent SELECT reads are not a literal shared-lock implementation of textbook 2PL.

The wait-for graph has a cycle, so neither transaction can finish unless one is rolled back or otherwise interrupted. With deadlock detection enabled, InnoDB selects a victim and returns error 1213. Victim choice depends on work done and timing; do not build application logic around which session loses. Retry the whole transaction from its start, with bounded attempts and backoff.

Acquiring account locks in the same identifier order reduces this common cycle. Keep transactions short, index selective predicates and avoid waiting for user input while holding locks. A lock wait timeout is different: error 1205 usually rolls back the waiting statement by default, whereas an InnoDB deadlock rolls back the victim transaction. Explicitly roll back the business operation before retrying after a timeout.

Observe snapshot visibility

The following results were observed on two real MySQL 8.4.7 connections. Account 1 starts at 1000 for each visibility experiment. A selects once, B changes it to 900, and A selects again. For the first two rows B commits before A’s second SELECT. For READ UNCOMMITTED B has not committed, and later rolls back.

At InnoDB REPEATABLE READ, the first ordinary consistent read establishes the transaction’s snapshot. Later consistent reads use that snapshot and can still see 1000 after B commits 900. START TRANSACTION alone does not necessarily establish the snapshot; START TRANSACTION WITH CONSISTENT SNAPSHOT can request it explicitly at the supported isolation level. You also see your own writes, which can make mixed reads surprising.

At READ COMMITTED, each consistent read obtains a fresh snapshot, so A’s second read sees B’s committed 900. At READ UNCOMMITTED, the observed 900 is dirty because B later rolls it back. A report using that value could make a decision based on a state that never commits. These differences are about visibility, not about whether B’s UPDATE needs a write lock.

Distinguish consistent and locking reads

An ordinary InnoDB SELECT usually uses MVCC versions without locking the selected rows. SELECT … FOR UPDATE requests current data and exclusive locks for a later change. In the observed locking experiment, A holds account 1 with FOR UPDATE. B’s UPDATE waits and ends with error 1205 after a deliberately short session lock-wait timeout. A’s COMMIT releases the blocking lock.

A locking read can therefore see a different version from an earlier consistent snapshot read in the same REPEATABLE READ transaction. Avoid mixing them casually when an invariant depends on one view. Use an explicit transaction; in autocommit mode a locking read’s protection ends when its statement transaction finishes. Lock the rows you intend to validate and change within the same transaction boundary.

For range searches, InnoDB can use next-key locks, combining record and gap protection, at REPEATABLE READ. A unique-key equality search for an existing record normally needs only its record lock. At READ COMMITTED, most search gap locking is reduced, with exceptions such as foreign-key and duplicate-key checks. The access path affects which records and gaps are examined and locked.

At SERIALIZABLE with an explicit transaction, a plain SELECT can block writers. In autocommit read-only cases, InnoDB may use a consistent read because that one statement is its own transaction. Do not generalise from a one-statement client experiment to a multi-statement business operation. Check transaction boundaries as well as the isolation setting.

REPEATABLE READ is MySQL’s default, but configuration may change it. Read @@transaction_isolation on the actual connection. Stronger-looking labels do not repair missing predicates, unchecked affected rows or constraints outside the transaction. The correct isolation choice follows from the invariant and the access pattern, then must be checked with competing sessions.

Recoverability needs commit order too

Consider w1(X), r2(X), c2, a1: T2 reads an uncommitted value from T1, commits, and T1 then aborts. The read/write precedence graph has only T1 → T2, so it is acyclic. Yet the schedule is not recoverable because the dependent reader committed before its source transaction committed.

If T2 instead waits to commit until T1 commits, that dependency can be recoverable. If reads never consume another transaction’s uncommitted writes, cascading aborts from dirty reads are avoided. This example shows why a serialisability answer must not be used as the entire recovery argument. Graphs about conflicting operation order and rules about commit dependencies protect different properties.

Avoid false conclusions from one connection

Drawing edges for two reads

Two reads do not change each other’s values. Include only read-write, write-read and write-write conflicts on the same item. A spurious edge can create a false cycle.

Expecting a savepoint to resolve every deadlock

The deadlock victim transaction has been rolled back, so earlier savepoints are gone. Restart the complete business transaction. After other errors, inspect the documented transaction effect rather than guessing from the SQLSTATE alone.

Calling a snapshot a serial execution proof

A stable snapshot can still allow write skew when transactions read overlapping conditions but update different rows. Protect the shared invariant with suitable locking, constraints or serialisable execution. Stable repeated reads alone are insufficient.

Check graphs, boundaries and observations

A precedence graph tests conflict order; a wait-for graph explains blocking cycles. InnoDB adds snapshot visibility and locking reads with different behaviours. Use the captured two-session schedule to reason about the operation, then connect failures to undo, redo and recovery.
