দুই cashier একসঙ্গে

দুই cashier একই সময়ে শেষ খাতাটি বিক্রি করতে পারে। দুজন stock 1 পড়ে পরে 0 লিখলে দুই বিক্রির জন্য একবারই কমতে পারে। Concurrency control একসঙ্গে চলা transaction-কে কাঙ্ক্ষিত ফল রক্ষার নিয়ম মানায়।

Schedule-এ প্রতিটি transaction-এর নিজের ক্রম রেখে সব operation সাজানো হয়। Serial schedule একটির পরে অন্যটি চালায়। Serializable schedule-এ কাজ মিশলেও নির্দিষ্ট equivalence অনুযায়ী ফল কোনো serial order-এর সমতুল্য। একজন disk বা lock-এর অপেক্ষায় থাকলে অন্যজন এগোতে পারে বলে interleaving কাজে লাগে।

r1(X) মানে transaction 1-এর X পড়া, w1(X) লেখা। Recovery-তে commit-abort গুরুত্বপূর্ণ; basic conflict-serializability read/write order দেখে। Serializability ও recoverability আলাদা; acyclic graph একাই dirty read নিরাপদ করে না।

আন্দাজের আগে precedence graph

ভিন্ন transaction-এর operation একই item ছুঁলে এবং অন্তত একটি write হলে conflict। Read-read conflict নয়। Ti থেকে Tj-এর প্রতিটি ordered conflicting pair-এ Ti → Tj edge দাও। Precedence graph acyclic হলে schedule conflict-serializable। যেকোনো topological order সমতুল্য serial order দেয়।

Cycle: conflict-serializable নয়

Recoverable schedule-এ reader তার পড়া মানের লেখক commit করার পরে commit করে। Cascadeless-এ uncommitted write পড়াই হয় না। Strict schedule-এ uncommitted write-এর ওপর লেখাও আটকে থাকে। এগুলো recovery ভালো করে; graph test-এর বিকল্প নয়।

Schedule থেকে actual lock

Locking-এর দুই phase

Shared lock compatible reader-দের থাকতে দেয়; exclusive lock writer-কে incompatible access থেকে রক্ষা করে। Basic two-phase locking বা 2PL-এ আগে lock নেওয়ার growing phase। একটি ছাড়লেই shrinking phase; নতুন lock নেওয়া যায় না। Lock-based model-এ এটি conflict serializability দেয়, কিন্তু deadlock হতে পারে।

Strict 2PL-এ commit বা abort পর্যন্ত exclusive lock থাকে; অন্যরা uncommitted write পড়তে বা overwrite করতে পারে না। Rigorous 2PL shared lock-ও রাখে। বইভেদে নাম বদলায়, তাই কোন lock থাকবে বলো। InnoDB locking ও MVCC মেলায়; ordinary consistent SELECT বইয়ের shared-lock 2PL-এর হুবহু বাস্তবায়ন নয়।

Wait-for graph:
A ----অপেক্ষা----> B
A <---অপেক্ষা----- B

Wait-for graph-এ cycle, তাই কাউকে rollback বা interrupt না করলে কেউ শেষ করতে পারে না। Detection চালু থাকলে InnoDB victim বেছে error 1213 দেয়। কাজের পরিমাণ ও timing-এ victim বদলায়; কে হারবে ধরে app logic বানাবে না। সীমিত retry ও backoff দিয়ে পুরো transaction শুরু করো।

একই identifier order-এ account lock নিলে পরিচিত cycle কমে। Transaction ছোট রাখো, selective predicate index করো, lock ধরে user input-এর অপেক্ষা করবে না। Error 1205 timeout-এ default-এ সাধারণত waiting statement rollback হয়; deadlock-এ victim transaction পুরো যায়। Timeout-এর পরে retry-এর আগে business operation স্পষ্ট rollback করো।

Snapshot visibility দেখো

নিচের ফল আসল দুটি MySQL 8.4.7 connection-এ দেখা। প্রতি visibility পরীক্ষায় account 1 শুরুতে 1000। A একবার পড়ে, B 900 করে, A আবার পড়ে। প্রথম দুই ক্ষেত্রে দ্বিতীয় SELECT-এর আগে B commit করে। READ UNCOMMITTED-এ B commit করেনি, পরে rollback করে।

A levelপ্রথম readপরে Bদ্বিতীয় read
REPEATABLE READ1000900 commit1000
READ COMMITTED1000900 commit900
READ UNCOMMITTED1000900 pending900

InnoDB REPEATABLE READ-এ প্রথম ordinary consistent read snapshot তৈরি করে। পরের read একই snapshot-এ B-এর 900 commit-এর পরেও 1000 দেখতে পারে। শুধু START TRANSACTION-এ snapshot তৈরি হবেই নয়। Supported level-এ WITH CONSISTENT SNAPSHOT স্পষ্টভাবে চাইতে পারে। নিজের write-ও দেখা যায়, তাই mixed read অবাক করতে পারে।

READ COMMITTED-এ প্রতি consistent read নতুন snapshot নেয়, তাই A দ্বিতীয়বার committed 900 দেখে। READ UNCOMMITTED-এর 900 dirty, কারণ B পরে rollback করে। সেই মানের report কখনো commit না হওয়া অবস্থায় সিদ্ধান্ত নিতে পারে। পার্থক্য visibility-তে; B-এর UPDATE write lock নেবে কি না তাতে নয়।

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT balance FROM accounts WHERE id = 1 ORDER BY id;
-- B updates account 1 and commits before A repeats this SELECT.
SELECT balance FROM accounts WHERE id = 1 ORDER BY id;
COMMIT;

Consistent আর locking read

সাধারণ InnoDB SELECT প্রায়ই row lock না নিয়ে MVCC version পড়ে। SELECT … FOR UPDATE পরের পরিবর্তনের জন্য current data ও exclusive lock চায়। পরীক্ষায় A account 1 ধরে রাখলে B-এর UPDATE অপেক্ষা করে, ছোট session timeout-এ error 1205 পায়। A COMMIT করলে blocking lock ছাড়ে।

একই REPEATABLE READ transaction-এ locking read আগের snapshot থেকে অন্য version দেখতে পারে। Invariant এক view-এর ওপর নির্ভর করলে অসাবধানে মেশাবে না। Explicit transaction নাও; autocommit-এ statement শেষেই locking read-এর সুরক্ষা শেষ। যে row যাচাই ও বদলাবে একই transaction-এ lock করো।

REPEATABLE READ range search-এ InnoDB next-key lock দিয়ে record ও gap একসঙ্গে রক্ষা করতে পারে। Existing unique-key equality search-এ সাধারণত শুধু record lock লাগে। READ COMMITTED-এ অধিকাংশ search gap lock কমে, তবে foreign-key ও duplicate-key check-এ ব্যতিক্রম আছে। Access path কোন record-gap দেখা ও lock হবে বদলায়।

Explicit SERIALIZABLE transaction-এ plain SELECT writer আটকাতে পারে। Autocommit read-only ক্ষেত্রে একটি statement-ই transaction বলে InnoDB consistent read নিতে পারে। এক-statement client পরীক্ষা থেকে multi-statement ব্যবসার কাজ নিয়ে সাধারণ সিদ্ধান্ত দেবে না। Isolation-এর সঙ্গে transaction boundary-ও দেখো।

MySQL-এর default REPEATABLE READ, তবে configuration বদলাতে পারে। নিজের connection-এ @@transaction_isolation পড়ো। শক্ত নাম ভুল predicate, unchecked affected row বা transaction-এর বাইরের constraint সারায় না। Invariant ও access pattern থেকে level বেছে competing session-এ যাচাই করো।

Recoverability-তে commit অর্ডার-ও

w1(X), r2(X), c2, a1 ধরো: T2, T1-এর uncommitted মান পড়ে commit করে; পরে T1 abort। Read/write graph-এ শুধু T1 → T2, তাই acyclic। তবু recoverable নয়, কারণ source commit-এর আগে dependent reader commit করেছে।

T1 commit পর্যন্ত T2 অপেক্ষা করলে dependency recoverable হতে পারে। অন্যের uncommitted write না পড়লে dirty read থেকে cascading abort এড়ায়। তাই serializability-এর উত্তর পুরো recovery argument নয়। Conflict order ও commit dependency আলাদা বৈশিষ্ট্য রক্ষা করে।

এক কানেকশন থেকে ভুল সিদ্ধান্ত নয়

দুই read-এ edge

দুটি read পরস্পরের মান বদলায় না। একই item-এ শুধু read-write, write-read ও write-write conflict নাও। বাড়তি edge মিথ্যা cycle বানাতে পারে।

Savepoint সব deadlock সারাবে

Deadlock victim-এর পুরো transaction rollback হয়েছে, তাই আগের savepoint নেই। সম্পূর্ণ business transaction শুরু করো। অন্য error-এ শুধু SQLSTATE দেখে আন্দাজ না করে documented transaction effect দেখো।

Snapshot-কে serial proof

Stable snapshot-এও overlapping condition পড়ে আলাদা row লিখলে write skew হতে পারে। Shared invariant উপযুক্ত lock, constraint বা serializable execution দিয়ে রক্ষা করো। শুধু repeated read স্থির হওয়া যথেষ্ট নয়।

Graph,boundary,observation মিলাও

Precedence graph conflict order পরীক্ষা করে; wait-for graph blocking cycle বোঝায়। InnoDB-তে snapshot ও locking read-এর আচরণ আলাদা। দুই-session schedule দিয়ে কাজটি বোঝো, তারপর failure-কে undo, redo ও recovery-এর সঙ্গে মেলাও।
