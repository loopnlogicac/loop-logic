Recover the last valid history

A server can stop between the debit and credit of a transfer. Some changed pages may already be on disk, while other committed pages may still be in memory. Recovery rebuilds a valid database state from persistent information instead of trusting the last contents of memory.

Different failures require different responses. A constraint rejection affects a statement or transaction. A process crash loses volatile server memory but may leave storage intact. A media failure loses files or devices. A committed mistaken DELETE is a logical error: the engine correctly remembers an action that the user did not intend. A single recovery mechanism does not solve all four.

Separate the database’s internal recovery logs from application audit logs. An audit row may help explain who changed a mark, but it does not replace the engine’s redo or undo structures. Similarly, a successful COMMIT is meaningful only within the configured persistence and storage guarantees.

Understand the buffer, undo and redo

A buffer pool keeps frequently used pages in memory. A changed page is dirty until its new contents have been written to the data file. A commit does not require every changed page to be written to its final location immediately. This saves random disk writes, but it means the engine needs a durable way to reconstruct committed changes.

A redo log records information needed to reapply changes to pages. An undo log records information needed to reverse uncommitted modifications and support older row versions. InnoDB uses both. Undo is also important to MVCC reads, so it is not merely a temporary file deleted as soon as each statement ends.

Write-ahead logging, or WAL, orders persistence: required log records must reach durable storage before a data page depending on them is flushed. Before acknowledging a durable commit, the required commit-related redo must also be persisted according to the configuration. Otherwise a page could contain a change whose recovery information vanished during the crash.

Two buffer-management choices explain why both directions are needed. With a steal policy, a dirty page containing uncommitted changes may reach disk, so recovery needs undo. With a no-force policy, commit need not flush every changed page, so recovery needs redo. These are conceptual policies; a real engine implements them with page latches, log sequence numbers and detailed recovery protocols.

Use accounts A = 1000 and B = 500. The following teaching log records logical old and new values; it is not the byte format of InnoDB’s physical redo records. T1 transfers 100, then commits. T2 later changes A to 1 but has not committed when the server stops.

The required final state is A = 900 and B = 600. Redo restores necessary logged page changes that were not safely present. Undo removes T2’s uncommitted effect, restoring A from 1 to 900 if necessary. T1’s committed transfer remains. The engine uses page and log metadata to avoid reapplying changes incorrectly.

Do not describe every real recovery algorithm as “redo winners only.” A repeat-history approach may redo logged changes from transactions that will later be undone, then roll those transactions back. InnoDB redo concerns pages and log sequence positions; transaction rollback concerns uncommitted logical effects. The teaching log explains the desired outcome without claiming to reproduce every internal record operation.

A checkpoint is a progress marker

A checkpoint records a safe recovery progress position. Flushing dirty pages advances the point before which redo is no longer needed for crash reconstruction. A fuzzy checkpoint allows normal transactions to continue while page flushing and checkpoint advancement happen. It does not require every active transaction to finish at once.

Suppose the oldest page still requiring redo has modifications beginning near LSN 200. A later log record at 500 does not mean recovery can ignore 200–499. Checkpoint advancement depends on the page and log conditions the engine tracks. A transaction that began before a checkpoint can still be active after it, so its rollback needs cannot be inferred from a simple time line alone.

Checkpointing limits restart work and frees redo capacity for reuse. It is not a backup, does not commit transactions and does not let you restore a deleted table by choosing a prior checkpoint. A checkpoint stored with lost data files cannot replace independently retained recovery material. The relevant retention rules for undo and binary logs are also different from redo checkpoint reuse.

Restore after media loss

If the data device is lost, ordinary restart cannot reconstruct unavailable base files from a small circular redo area. Restore a valid backup to replacement storage, then use retained binary logs for point-in-time recovery when that recovery path was configured. Protect encryption keys and backup metadata too; encrypted files without the required keys may be unusable.

A consistent logical backup of InnoDB data can use a snapshot, subject to the tool’s rules and restrictions on concurrent DDL. Physical backup tools have their own preparation and consistency steps. Copying live data files with an ordinary file copy is not automatically a consistent backup. Use a supported procedure and practise the complete restore into a separate environment.

Define a recovery point objective, or RPO, as the acceptable amount of lost recent data. Define a recovery time objective, or RTO, as the acceptable time to resume service. A nightly backup without retained changes may expose nearly a day of loss. Frequent log retention can reduce the recovery point gap, but restoration time and operational complexity still need measurement.

Undo a committed human mistake

Suppose an operator commits DELETE FROM results without the intended WHERE. A clean restart will keep the deletion because it is committed history. One response is restoring a backup to an isolated server, replaying binary logs only up to the verified boundary before the deletion, extracting the lost rows and reconciling later valid changes. The exact procedure depends on log format, positions and application requirements.

Do not guess a timestamp and overwrite the current database immediately. Establish the affected transaction, preserve current recovery material and validate the recovered records before replacing anything. A compensating INSERT can be appropriate when the lost facts are known and constraints are understood, but it is an explicit repair transaction, not an automatic rollback of an old commit.

Recovery logs, binary logs and replicas have different roles. InnoDB redo supports engine crash recovery. The server binary log supports replication and point-in-time replay with a backup. A replica can faithfully repeat a mistaken deletion, so replication is not itself a historical backup. Retention and separation are design choices, not properties obtained by naming a second server.

Avoid three recovery shortcuts

Stopping at the last COMMIT word in a sample log

A real engine uses durable log positions and recovery metadata. A client-side printed command is not proof that the server durably acknowledged it. Keep the teaching trace separate from the persistence protocol.

Lowering flush settings without changing the promise

Less frequent redo flushes can improve throughput while exposing acknowledged work to loss under some failures. State the durability tradeoff explicitly and assess the underlying storage guarantees. The default-looking value alone is not a power-loss test.

Keeping the only backup beside the data files

One device failure or credential compromise can destroy both. Retain protected copies separately and test restoration, including accounts, routines, triggers and encryption requirements. A backup job reporting success is only the start of recovery evidence.

Match the recovery tool to the failure

Undo protects against uncommitted effects, redo supports restart, and checkpoints limit repeated log work. Backups and retained logs address wider losses and committed mistakes. Connect the persistence story with pages, files and indexes.
