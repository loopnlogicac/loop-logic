A query describes a result, not a route

You ask for the names of students taking Database Management Systems. SQL states which rows you want. The server still has to decide which table to read first, which index to use and how to match registrations. Query processing turns that request into work the engine can perform.

Two equivalent SQL expressions can use the same execution plan. Conversely, one query text can get a different plan when the data, statistics or server version changes. The optimiser’s goal is to choose a promising route from the available alternatives. Its choice is based on estimates, so the chosen plan is not guaranteed to be the fastest possible plan.

Optimisation should preserve meaning. Rewriting a LEFT JOIN as an INNER JOIN changes which students survive. Removing duplicates can change a required count. First establish the intended rows and duplicate policy, then compare routes that produce that same answer. A quick wrong result is not a useful optimisation.

Ask the server to explain a plan

EXPLAIN SELECT student_id, student_name
FROM students WHERE student_id = 101 ORDER BY student_id;

Traditional EXPLAIN returns one or more rows describing plan operations. EXPLAIN FORMAT=TREE presents a tree on supported MySQL versions. EXPLAIN ANALYZE, introduced in MySQL 8.0.18, actually executes the query and adds timing and row observations in a tree-style presentation. Avoid treating ANALYZE as a harmless estimate when the query is expensive.

Follow the processing pipeline

SQL text
   |
parse and resolve names
   |
logical transformations and access alternatives
   |
cost estimates -> chosen physical plan
   |
execution operators -> result rows

Parsing checks that the SQL has a valid grammatical shape. Name resolution binds columns to tables and detects ambiguous or unknown names. The server also checks relevant privileges and types. A prepared statement can separate preparation from parameter binding, but preparation does not freeze every cost decision forever; engines may reprepare when metadata changes.

Logical transformations can simplify predicates, merge or materialise derived results and move filters where they remain equivalent. Pushing a selective filter closer to a scan can reduce rows passed to later operators. Outer joins, aggregation, LIMIT and window functions create boundaries where a naive movement can change the answer. The legality of a rewrite comes before its cost.

Physical alternatives include full table scans, index lookups, range scans, different join orders and different join methods. For an inner join among several tables, starting with a selective relation can reduce later work. The optimiser does not have unlimited time to enumerate every possible plan, so practical search strategies and engine capabilities constrain the alternatives considered.

A cost model estimates work such as page access and CPU processing. It uses statistics describing table size, index distribution and value selectivity. Selectivity is the fraction expected to pass a condition. A unique-key equality usually has a strong one-row bound, while a hometown filter may match many students. Skew means not all hometown values are equally frequent.

Statistics can be stale or too coarse. Correlated predicates may be estimated poorly if each condition is treated too independently. For example, department and course selections are often related. ANALYZE TABLE refreshes supported statistics, but it is an administrative operation with its own cost; do not run it on every application request as a substitute for understanding the plan.

Execution follows the selected operators. A join may repeatedly probe an index on its inner input, or use a hash join where MySQL’s version and plan support it. Sorting and grouping can require temporary storage. Some operations stream rows while others must consume many input rows before returning a result. LIMIT helps most when the access path can stop early.

For a rough reasoning exercise, suppose a plan estimates 1000 scanned rows and filtered = 10. About 100 rows are expected to pass that input’s conditions. A nested loop probing five inner rows for each of those can perform about 500 inner-row visits. If the first estimate is wrong by a factor of ten, later work estimates can be wrong by much more than one row.

The numbers in the committed plan examples were produced by MySQL 8.4.7 on the small shared data. Other releases or refreshed statistics can change key choices, row estimates and Extra text. Read the logic of the route rather than memorising every printed cell. The accompanying SELECT establishes which answer the plan must preserve.

A sargable condition can be used directly to locate entries in a suitable search index. A direct date interval is a common example. Wrapping the indexed column in YEAR can prevent use of that ordinary index as a simple range route, although a matching functional index or a supported transformation may change the situation. “Avoid all functions” is too broad a rule.

Composite index order also matters. With an index on (department_id, admitted_on), a department equality can narrow the leading prefix, then a date interval can narrow the following part. A condition on admitted_on alone does not provide the same straightforward prefix route. Indexes can still be scanned for coverage or other strategies, so distinguish efficient lookup from merely appearing in a plan.

When tuning a real workload, save the intended result definition and a representative dataset. Compare estimated rows with observed rows using a suitable execution measurement. Check whether parameters have skewed distributions, whether filters are applied late and whether joins multiply rows before aggregation. Measure under realistic caching and concurrency rather than extrapolating from eight student rows.

Do not add an index for every column mentioned in WHERE. One carefully ordered composite index may serve the important predicate combination, while several weak indexes add write costs without helping. Likewise, an index hint can make one parameter fast and another slow. Use hints only with evidence, version awareness and a plan for rechecking as data changes.

Estimate the cost of repeated probes

Suppose one plan scans 10,000 enrollment rows and probes a student key for every row. Another plan first identifies 20 students, then uses a suitable enrollment index to find five registrations each. The second route may examine far fewer joined records, but only if its selectivity and per-student estimates are reasonable. Index existence alone does not establish those counts.

If the selected department actually contains 5,000 students rather than 20, the repeated probes can become expensive. This is a cardinality-estimation problem, not a syntax error. Compare representative parameter values, inspect the estimated and observed input rows and ask whether distribution statistics describe the workload. Preserve a correct zero-registration case while experimenting with alternate query shapes.

Keep result correctness in the tuning loop

Reading rows as final output count

Traditional EXPLAIN rows is an estimate of examined input rows for that operation. Filters and joins can change the number reaching the result. Compare it with actual observations when the distinction matters.

Removing an outer join to force a shorter plan

A student with no enrollment must still appear in a student-preserving report. An inner join removes that student. Preserve the report’s semantics before judging the operator count.

Assuming filesort always spills to disk

The historical name covers a sorting operation outside index order. The work may fit in memory. Inspect the actual workload and resource behaviour before concluding that storage I/O is the bottleneck.

Read version-specific plan formats

The point and covering EXPLAIN examples use the traditional table format. The joined plan uses FORMAT=TREE to show nested operators without a schema-dependent ref field. FORMAT=TREE arrived in 8.0.16 and EXPLAIN ANALYZE in 8.0.18. Join implementations and cost behaviour have evolved across releases. Record the version when comparing plans and retain the actual result checks.

Explain the route before changing it

Parsing establishes meaning, optimisation compares legal routes, and execution performs the chosen work. EXPLAIN gives estimates and access choices; observation tests those estimates. Revisit storage and indexing whenever a plan’s page and row costs are unclear.
