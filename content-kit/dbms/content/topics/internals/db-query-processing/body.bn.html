কোয়েরি ফল বলে,পথ নয়

ডেটাবেস Management Systems নেওয়া শিক্ষার্থী-এর নাম চাও। SQL কোন রো চাই বলে। কিন্তু কোন টেবিল আগে, কোন ইনডেক্স ও enrollment match কীভাবে হবে সার্ভার বাছে। কোয়েরি processing অনুরোধকে engine-এর করার মতো কাজে বদলায়।

সমতুল্য দুই SQL একই প্ল্যান নিতে পারে। আবার একই টেক্সট ডেটা,statistics,ভার্সন বদলালে অন্য প্ল্যান পায়। Optimizer available পথের মধ্যে সম্ভাবনাময়টি বাছে। Estimate-ভিত্তিক বলে সবচেয়ে দ্রুত হবেই নয়।

Optimization-এ অর্থ রাখতে হবে। LEFT-কে INNER JOIN করলে কোন শিক্ষার্থী থাকে বদলায়। Duplicate সরালে দরকারি সংখ্যা বদলাতে পারে। আগে intended রো ও repetition নীতি, তারপর একই উত্তর দেওয়া পথ তুলনা। দ্রুত ভুল উত্তর কাজে লাগে না।

প্ল্যান ব্যাখ্যা চাও

EXPLAIN SELECT student_id, student_name
FROM students WHERE student_id = 101 ORDER BY student_id;

Traditional EXPLAIN প্ল্যান operation-এর রো দেয়; supported ভার্সন-এ FORMAT=TREE tree দেখায়। MySQL 8.0.18-এর ANALYZE আসল কোয়েরি চালিয়ে timing ও রো observation যোগ করে। Expensive কোয়েরি-তে একে harmless estimate ভাববে না।

Processing pipeline ধরো

   |

   |

   |

   |

Parsing সিনট্যাক্স ঠিক দেখে। নাম resolution কলাম-টেবিল মেলায়, ambiguous বা unknown নাম ধরে। Privilege ও type-ও পরীক্ষা হয়। Prepare ও binding আলাদা করা যায়, কিন্তু সব cost decision চিরতরে স্থির নয়; metadata বদলালে reprepare হতে পারে।

Legal transformation predicate সরল, derived ফল merge/materialize, equivalent জায়গায় ফিল্টার সরাতে পারে। Selective ফিল্টার scan-এর কাছে নিলে পরে কম রো। Outer জয়েন,aggregate,LIMIT,window-এ সরল movement অর্থ বদলাতে পারে। আগে বৈধতা, পরে cost।

Physical বিকল্প scan,ইনডেক্স lookup,রেঞ্জ,জয়েন অর্ডার ও method। Inner জয়েন-এ selective relation আগে নিলে পরে কাজ কমে। সব প্ল্যান খোঁজার অসীম সময় নেই; practical search ও engine capability বিবেচিত বিকল্প বাঁধে।

Cost model page access ও CPU কাজের estimate করে। টেবিল size,ইনডেক্স distribution,selectivity-এর statistics নেয়। Selectivity শর্তে টেকার সম্ভাব্য fraction। Unique equality-তে সাধারণত এক-রো bound; hometown-এ অনেক। Skew-তে সব town সমান frequent নয়।

Statistics পুরোনো বা বেশি coarse হতে পারে। Correlated predicate আলাদা ধরে estimate খারাপ হয়; বিভাগ ও কোর্স selection সম্পর্কিত হতে পারে। ANALYZE TABLE supported statistics refresh করে, নিজেও admin cost আছে। প্ল্যান না বুঝে প্রতি request-এ চালাবে না।

Execution নির্বাচিত অপারেটর চালায়। জয়েন inner ইনডেক্স বারবার probe বা ভার্সন-প্ল্যান অনুযায়ী hash জয়েন নিতে পারে। সর্ট-গ্রুপ temporary স্টোরেজ নিতে পারে। কেউ stream করে, কেউ আগে অনেক ইনপুট নেয়। Access path আগে থামতে পারলেই LIMIT বেশি সাহায্য করে।

প্ল্যান আর actual ফল

Unique-কী lookup explain

Primary equality-র one-রো bound। Actual Ayesha রো-এর পাশে কী ও access type পড়ো। এটি প্ল্যান পড়া, speed benchmark নয়।

Selective joined রিপোর্ট

রিপোর্ট-এ 101,102। Tree-তে covering enrollment lookup, পরে শিক্ষার্থী primary-কী probe। Traditional ref-এর কানেকশন-specific schema এড়াতে TREE। ছোট ডেটা প্ল্যান shape দেখায়, speed নয়।

কলাম না ঢেকে তারিখ interval

দুই form একই পাঁচ admission দেয়। Half-open রেঞ্জ expression ইনডেক্স ছাড়া suitable তারিখ ইনডেক্সের সুযোগ রাখে। ছোট টেবিল runtime advantage প্রমাণ করে না।

Covering access দেখো

InnoDB secondary entry-তে primary কী থাকে। Hometown ইনডেক্স requested কলাম cover করতে পারে। Using ইনডেক্স coverage বলে, zero physical I/O নিশ্চয়তা নয়।

ধরো estimated scanned রো 1000, filtered 10। প্রায় 100 শর্ত পেরোবে। প্রত্যেকটির জন্য পাঁচ inner রো probe-এ প্রায় 500 visit। প্রথম estimate দশ গুণ ভুল হলে পরের estimate-ও অনেক ভুল হতে পারে।

প্ল্যান-এর সংখ্যা ছোট shared ডেটা-তে MySQL 8.4.7-এর। Release বা refreshed statistic-এ কী,রো,Extra বদলায়। Cell মুখস্থ নয়, পথের যুক্তি পড়ো। পাশে SELECT কোন উত্তর রাখতে হবে দেখায়।

Sargable শর্ত উপযুক্ত search ইনডেক্স-এ সরাসরি entry খুঁজতে পারে। তারিখ interval উদাহরণ। YEAR-এ কলাম মুড়লে ordinary রেঞ্জ path বন্ধ হতে পারে; matching functional ইনডেক্স বা supported transformation-এ বদলায়। “সব ফাংশন এড়াও” অতিরিক্ত বড় নিয়ম।

Composite অর্ডার-ও জরুরি। (department_id,admitted_on)-এ বিভাগ equality, তারপর তারিখ interval পথ ছোট করে। শুধু admitted_on-এ একই prefix নেই। Coverage বা অন্য strategy-তে ইনডেক্স scan-ও হতে পারে; প্ল্যান-এ থাকা ও efficient lookup আলাদা।

Real tuning-এ intended ফল ও representative dataset রাখো। উপযুক্ত execution measurement-এ estimate ও observed রো তুলনা করো। Parameter skew,late ফিল্টার,aggregate-এর আগে জয়েন multiplication দেখো। আট শিক্ষার্থী থেকে নয়, realistic cache ও concurrency-তে মাপো।

WHERE-এর প্রতিটি কলাম-এ ইনডেক্স নয়। Ordered composite গুরুত্বপূর্ণ combination ধরতে পারে; weak অনেক ইনডেক্স write cost বাড়ায়। Hint এক parameter দ্রুত, অন্যটি ধীর করতে পারে। Evidence,ভার্সন awareness ও recheck প্ল্যান নিয়ে নাও।

বারবার probe-এর খরচ হিসাব করো

এক প্ল্যান 10,000 enrollment scan করে প্রতি রো-তে শিক্ষার্থী probe করে। অন্যটি আগে 20 শিক্ষার্থী, পরে ইনডেক্স-এ পাঁচ registration করে পায়। Estimate সঠিক হলে দ্বিতীয়টি কম joined রেকর্ড পড়তে পারে। শুধু ইনডেক্স থাকাই ওই সংখ্যা প্রমাণ নয়।

বাস্তবে বিভাগ-এ 20 নয় 5,000 শিক্ষার্থী হলে repeated probe ব্যয়বহুল। এটি cardinality estimation, সিনট্যাক্স এরর নয়। Representative parameter,estimated-observed ইনপুট ও distribution statistics দেখো। কোয়েরি বদলাতে zero-registration case সঠিক রেখো।

Tuning-এর সময়ও সঠিক ফল যাচাই করো

রো-কে final আউটপুট সংখ্যা ভাবা

Traditional রো ওই operation-এর examined ইনপুট estimate। ফিল্টার ও জয়েন final সংখ্যা বদলায়। দরকার হলে actual observation-এর সঙ্গে মেলাও।

ছোট প্ল্যান পেতে outer জয়েন সরানো

Student-preserving রিপোর্ট-এ enrollment-হীন শিক্ষার্থী-ও চাই। Inner জয়েন সরায়। অপারেটর সংখ্যা-এর আগে semantics রাখো।

filesort মানেই disk-এ লেখা ভাবা

Filesort-এর ঐতিহাসিক নাম ইনডেক্স অর্ডার-এর বাইরে সর্ট বোঝায়। মেমরি-তেই ধরতে পারে। স্টোরেজ I/O bottleneck বলার আগে workload ও resource behavior দেখো।

ভার্সন অনুযায়ী প্ল্যান format পড়ো

Point-covering example traditional format, joined প্ল্যান TREE—schema-dependent ref ছাড়া nested অপারেটর। TREE 8.0.16, ANALYZE 8.0.18 থেকে। জয়েন ও cost ভার্সন-এ বদলায়। প্ল্যান তুলনায় ভার্সন লিখে actual ফল check রাখো।

পথ বদলানোর আগে ব্যাখ্যা করো

Parsing অর্থ স্থাপন, optimization legal পথ তুলনা, execution কাজ করে। EXPLAIN estimate ও access choice, observation সেগুলো পরীক্ষা। Page-রো cost অস্পষ্ট হলে স্টোরেজ ও indexing-এ ফেরো।
