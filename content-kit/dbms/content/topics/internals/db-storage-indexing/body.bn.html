শুধু comparison নয়,page visit

প্রতি book number খুঁজতে সব তাক খুললে লাইব্রেরির catalogue ধীর হতো। Storage organization প্রয়োজনীয় page-এ যাওয়ার পথ দেয়। Page পড়া-লেখার জন্য record একত্র করে। তাই মেমরির অনেক তুলনার চেয়ে একটি দরকারি page visit বেশি গুরুত্বপূর্ণ হতে পারে।

File organization বলে record কোথায় থাকে। Index অতিরিক্ত search structure, যদিও কিছু engine index-এর ভেতরেই record রাখে। সম্পর্কিত এই পছন্দগুলোর খরচ আলাদা। খরচ বলতে page read, record comparison, memory নাকি maintenance গুনছ তা বলো।

MySQL-এ একাধিক storage engine আছে। এখানে সাধারণ ধারণা InnoDB-এর সঙ্গে মেলানো হয়েছে। এটি clustered B-tree-family structure-এ table data রাখে; ordered index access-এ সাধারণত B+ tree-এর আচরণ দেখা যায়। বইয়ের heap-file চিত্র তুলনার মডেল; shared InnoDB table-কে heap file বলা নয়।

Heap file free-space map দেখে খালি জায়গার page-এ নতুন row রাখতে পারে। Cold disk model-এ b data page পুরো scan করতে প্রায় b page read লাগে। বাস্তবে sequential throughput, prefetch ও cache সময় বদলায়। তাই b যুক্তি বোঝায়, stopwatch-এর সময় নয়।

Sorted file প্রথম page খুঁজে range-এর পরপর page পড়তে পারে। b page-এ ideal binary search প্রায় log2(b) probe নেয়। ঘন ঘন insert-এ ক্রম রাখা ব্যয়বহুল: record সরাতে, overflow area বাড়াতে বা file সাজাতে হয়। Ordered tree ছোট local change-এ maintenance ছড়িয়ে দেয়।

পাঠ্যবইয়ের primary index প্রায়ই primary key-তে সাজানো file-এর index; কখনো প্রতি data block-এ একটি sparse entry থাকে। Secondary index অন্য search key নেয়, সাধারণত dense entry বা matching record reference-এর list লাগে। Clustered index row placement নিয়ন্ত্রণ করে। System-ভেদে নাম বদলায়; শুধু নাম না বলে physical organization বোঝাও।

Tree আর reference হাঁটো

ছোট B+ tree

                 root: [30 | 60]
                 /      |      \
leaves:     [10,20] -> [30,40,50] -> [60,70,80]
               ordered leaf link

Internal separator key search-এর পথ দেখায়। চিত্রে 30-এর নিচে বামে, 30 থেকে 60-এর নিচে মাঝখানে, অন্তত 60 ডানে যায়। 40 খুঁজতে root পড়ে মাঝের pointer ধরে leaf দেখো। 35 থেকে 70 পড়তে সম্ভাব্য প্রথম key-এর leaf থেকে শুরু করে range শেষ হওয়া পর্যন্ত leaf link ধরো।

B+ tree-এর leaf-এ record বা record reference থাকে; internal entry পথ দেখায়। সব leaf একই depth-এ, তাই point search-এ level-এর সংখ্যা নির্দিষ্ট থাকে। প্রতি page-এ অনেক entry বলে fanout—internal node-এর child pointer সংখ্যা—বড় হয়। এতে বড় relation-ও অল্প level-এ থাকে।

Insert লক্ষ্য leaf খুঁজে ক্রমে entry বসায়; page পূর্ণ হলে split হতে পারে। Split-এর separator parent-এ যায়; parent পূর্ণ হলে ওপরেও split ছড়ায়। Root split-এ এক level বাড়ে। Delete-এ implementation অনুযায়ী redistribution বা merge হতে পারে। Local change হলেও log, lock বা latch এবং পরে page write লাগে।

Teaching tree height

ধরো সরল মডেলে internal page-এ সর্বোচ্চ 100 child pointer, leaf-এ 80 record। 800,000 record-এ 800000/80 = 10,000 পূর্ণ leaf লাগে। 100 internal node এগুলো ধরতে পারে। একটি root ওই 100 node ধরে। তাই root, internal, leaf—তিন page level।

Cache না থাকলে এই মডেলে point lookup প্রায় তিন tree page পড়ে। Root ও internal page cached থাকলে একটি leaf-এর physical read-ই যথেষ্ট হতে পারে। বাস্তবে page পুরো ভরে না, record-এর মাপ আলাদা এবং বড় value অতিরিক্ত page নিতে পারে। এটি fanout বোঝায়; row count থেকেই MySQL-এর সঠিক height বলে না।

Range-এ পরপর 200 record ধরো। Leaf-প্রতি 80 হলে সুবিধাজনক alignment-এ অন্তত ceil(200/80) = 3 leaf লাগে। Page-এর শেষদিকে শুরু হলে চারটিও লাগতে পারে। প্রথম root-to-leaf পথের পরে leaf ধরে পরপর পড়া হয়। তাই B+ tree point lookup ও interval দুটোতেই কাজে লাগে।

InnoDB clustered mapping

University students টেবিলে PRIMARY KEY(student_id) clustered index ঠিক করে। Leaf record-এ row-এর column থাকে; আলাদা heap row-এর pointer শুধু নয়। একটি table-এর clustering order একটিই। Guaranteed display order চাইলে এখনও ORDER BY লাগে; physical organization SQL ordering contract নয়।

Explicit primary key না থাকলে InnoDB প্রথম উপযুক্ত UNIQUE index নেয় যার সব key column NOT NULL। সেটিও না থাকলে hidden clustered row identifier বানায়। স্থির primary key নিজে বাছো, যাতে ডিজাইন ও অ্যাপ row identity বলতে পারে। Hidden identifier অঘোষিত business uniqueness মানায় না।

Hometown-এর secondary index-এ hometown ও clustered row খোঁজার primary-key মান থাকে। পুরো student পেতে আগে secondary, তারপর প্রতি match-এ clustered index লাগতে পারে। শুধু hometown ও student_id লাগলে secondary leaf query cover করতে পারে; বাড়তি row lookup বাঁচে।

লম্বা primary key secondary entry-ও বড় করে, কারণ তার মান সঙ্গে থাকে। Entry বড় হলে page-এ কম ধরে, বেশি page লাগতে পারে। ছোট, স্থির key একসঙ্গে কয়েকটি index ছোট করতে পারে। তবে surrogate key নিলেও অ্যাপের প্রয়োজনীয় unique business identifier আলাদা মানাতে হবে।

Hash bucket

Hash function equality search key-কে bucket-এ মেলায়। শেখানোর h(id) = id mod 4 মডেলে 101 ও 105 দুটোই bucket 1। এটি collision; row সমান হওয়ার প্রমাণ নয়। Bucket-এ original key তুলনা এবং overflow, chaining বা অন্য collision strategy চাই।

ভালো distribution ও নিয়ন্ত্রিত load-এ equality lookup অল্প expected bucket access নেয়। Skew-তে লম্বা overflow chain এই প্রত্যাশা ভাঙে। id 101 থেকে 110 range hash-bucket order-এ পাশাপাশি নয়। Hash সংখ্যার কাজে লাগা ক্রম নষ্ট করায় অনেক bucket দেখতে হতে পারে।

Static hashing bucket layout স্থির রাখে; extendible বা linear hashing-এর মতো dynamic পদ্ধতি ধীরে বাড়ে। Rehash বা split-এ maintenance লাগে। এগুলো সাধারণ indexing ধারণা। Shared InnoDB table-এ normal B-tree index-এর মতো ইচ্ছেমতো সাধারণ HASH index বাছা যায় না।

InnoDB adaptive hash index ঘন ঘন ব্যবহৃত B-tree page-এর internal optimization। দরকারি index ঘোষণা করার বিকল্প নয়; version ও configuration অনুযায়ী পাওয়া এবং default বদলায়। MEMORY engine explicit hash index দেয়, কিন্তু persistence ও transaction আচরণ InnoDB থেকে আলাদা। শুধু একটি lookup সুবিধা দেখে নয়, পুরো workload দেখে engine নাও।

Read লাভ বনাম write

Index insert, delete বা key update-এ clustered structure-এর পাশাপাশি index page-ও বদলায়। বেশি index মানে বেশি space, buffer-pool capacity ও log work। Primary key update-এ secondary entry-র identity-ও বদলাতে পারে। তাই খুব কম ব্যবহৃত index কোনো query না নিলেও write-heavy কাজ ধীর করতে পারে।

ছোট table বা বেশিরভাগ row দরকার হলে full scan যুক্তিযুক্ত। Secondary access-এ ছড়ানো অনেক clustered lookup লাগতে পারে; scan leaf page দক্ষভাবে পড়ে। Selectivity, row width, coverage, cache ও cost model অনুযায়ী ভালো পথ বদলায়। Query optimization বিকল্প থেকে plan বেছে নেয়।

Logical-physical অর্ডার আলাদা

Clustering-এ SELECT অর্ডার

SQL অন্য access path বা execution strategy নিতে পারে। শেষে ORDER BY দাও, দরকার হলে unique tie-breaker-সহ। Physical tree একটি কাজ করার পথ; ফলের ক্রমের প্রতিশ্রুতি নয়।

Expected hash-কে worst constant

Collision ও skew-তে overflow কাজ লাগে। Expected cost বলার সময় load ও distribution-এর অনুমান বলো। Worst-case bucket অনেক খারাপ হতে পারে।

Secondary-তে PK ভুলে যাওয়া

InnoDB secondary index clustered identity রাখে। মাপের হিসাব করতে secondary column-এর সঙ্গে ওই identity ধরো। চওড়া primary key প্রতিটি secondary index বড় করতে পারে।

Workload-এর route বাছো

Heap, sorted, tree ও hash organization record বসানো ও search-এর খরচে ভিন্ন সমঝোতা করে। InnoDB নির্বাচিত key-তে row cluster করে, secondary entry দিয়ে সেগুলো পায়। এরপর EXPLAIN ও optimizer-এর access choice পড়ো।
