শুধু comparison নয়,page visit

প্রতি book number খুঁজতে সব তাক খুললে লাইব্রেরির catalogue ধীর হতো। স্টোরেজ organization প্রয়োজনীয় page-এ যাওয়ার পথ দেয়। Page পড়া-লেখার জন্য রেকর্ড একত্র করে। তাই মেমরির অনেক তুলনার চেয়ে একটি দরকারি page visit বেশি গুরুত্বপূর্ণ হতে পারে।

ফাইল organization বলে রেকর্ড কোথায় থাকে। ইনডেক্স অতিরিক্ত search স্ট্রাকচার, যদিও কিছু engine ইনডেক্সের ভেতরেই রেকর্ড রাখে। সম্পর্কিত এই পছন্দগুলোর খরচ আলাদা। খরচ বলতে page read, রেকর্ড comparison, মেমরি নাকি maintenance গুনছ তা বলো।

MySQL-এ একাধিক স্টোরেজ engine আছে। এখানে সাধারণ ধারণা InnoDB-এর সঙ্গে মেলানো হয়েছে। এটি clustered B-tree-family স্ট্রাকচার-এ টেবিল ডেটা রাখে; ordered ইনডেক্স access-এ সাধারণত B+ tree-এর আচরণ দেখা যায়। বইয়ের heap-ফাইল চিত্র তুলনার মডেল; shared InnoDB টেবিল-কে heap ফাইল বলা নয়।

Heap ফাইল free-space map দেখে খালি জায়গার page-এ নতুন রো রাখতে পারে। Cold disk model-এ b ডেটা page পুরো scan করতে প্রায় b page read লাগে। বাস্তবে sequential throughput, prefetch ও cache সময় বদলায়। তাই b যুক্তি বোঝায়, stopwatch-এর সময় নয়।

Sorted ফাইল প্রথম page খুঁজে রেঞ্জ-এর পরপর page পড়তে পারে। b page-এ ideal binary search প্রায় log2(b) probe নেয়। ঘন ঘন ইনসার্ট-এ ক্রম রাখা ব্যয়বহুল: রেকর্ড সরাতে, overflow area বাড়াতে বা ফাইল সাজাতে হয়। Ordered tree ছোট local change-এ maintenance ছড়িয়ে দেয়।

পাঠ্যবইয়ের primary ইনডেক্স প্রায়ই primary কী-তে সাজানো ফাইল-এর ইনডেক্স; কখনো প্রতি ডেটা block-এ একটি sparse entry থাকে। Secondary ইনডেক্স অন্য search কী নেয়, সাধারণত dense entry বা matching রেকর্ড reference-এর list লাগে। Clustered ইনডেক্স রো placement নিয়ন্ত্রণ করে। System-ভেদে নাম বদলায়; শুধু নাম না বলে physical organization বোঝাও।

Tree আর reference হাঁটো

ছোট B+ tree

                 root: [30 | 60]
                 /      |      \
leaves:     [10,20] -> [30,40,50] -> [60,70,80]
               ordered leaf link

Internal separator কী search-এর পথ দেখায়। চিত্রে 30-এর নিচে বামে, 30 থেকে 60-এর নিচে মাঝখানে, অন্তত 60 ডানে যায়। 40 খুঁজতে root পড়ে মাঝের pointer ধরে leaf দেখো। 35 থেকে 70 পড়তে সম্ভাব্য প্রথম কী-এর leaf থেকে শুরু করে রেঞ্জ শেষ হওয়া পর্যন্ত leaf link ধরো।

B+ tree-এর leaf-এ রেকর্ড বা রেকর্ড reference থাকে; internal entry পথ দেখায়। সব leaf একই depth-এ, তাই point search-এ level-এর সংখ্যা নির্দিষ্ট থাকে। প্রতি page-এ অনেক entry বলে fanout—internal node-এর child pointer সংখ্যা—বড় হয়। এতে বড় relation-ও অল্প level-এ থাকে।

ইনসার্ট লক্ষ্য leaf খুঁজে ক্রমে entry বসায়; page পূর্ণ হলে split হতে পারে। Split-এর separator parent-এ যায়; parent পূর্ণ হলে ওপরেও split ছড়ায়। Root split-এ এক level বাড়ে। ডিলিট-এ implementation অনুযায়ী redistribution বা merge হতে পারে। Local change হলেও log, lock বা latch এবং পরে page write লাগে।

Teaching tree height

ধরো সরল মডেলে internal page-এ সর্বোচ্চ 100 child pointer, leaf-এ 80 রেকর্ড। 800,000 রেকর্ড-এ 800000/80 = 10,000 পূর্ণ leaf লাগে। 100 internal node এগুলো ধরতে পারে। একটি root ওই 100 node ধরে। তাই root, internal, leaf—তিন page level।

Cache না থাকলে এই মডেলে point lookup প্রায় তিন tree page পড়ে। Root ও internal page cached থাকলে একটি leaf-এর physical read-ই যথেষ্ট হতে পারে। বাস্তবে page পুরো ভরে না, রেকর্ড-এর মাপ আলাদা এবং বড় value অতিরিক্ত page নিতে পারে। এটি fanout বোঝায়; রো সংখ্যা থেকেই MySQL-এর সঠিক height বলে না।

রেঞ্জ-এ পরপর 200 রেকর্ড ধরো। Leaf-প্রতি 80 হলে সুবিধাজনক alignment-এ অন্তত ceil(200/80) = 3 leaf লাগে। Page-এর শেষদিকে শুরু হলে চারটিও লাগতে পারে। প্রথম root-to-leaf পথের পরে leaf ধরে পরপর পড়া হয়। তাই B+ tree point lookup ও interval দুটোতেই কাজে লাগে।

InnoDB clustered mapping

University students টেবিলে PRIMARY KEY(student_id) clustered ইনডেক্স ঠিক করে। Leaf রেকর্ড-এ রো-এর কলাম থাকে; আলাদা heap রো-এর pointer শুধু নয়। একটি টেবিলের clustering অর্ডার একটিই। Guaranteed display অর্ডার চাইলে এখনও ORDER BY লাগে; physical organization SQL ordering contract নয়।

Explicit primary কী না থাকলে InnoDB প্রথম উপযুক্ত UNIQUE ইনডেক্স নেয় যার সব কী কলাম NOT NULL। সেটিও না থাকলে hidden clustered রো identifier বানায়। স্থির primary কী নিজে বাছো, যাতে ডিজাইন ও অ্যাপ রো পরিচয় বলতে পারে। Hidden identifier অঘোষিত business uniqueness মানায় না।

Hometown-এর secondary ইনডেক্স-এ hometown ও clustered রো খোঁজার primary-কী মান থাকে। পুরো শিক্ষার্থী পেতে আগে secondary, তারপর প্রতি match-এ clustered ইনডেক্স লাগতে পারে। শুধু hometown ও student_id লাগলে secondary leaf কোয়েরি cover করতে পারে; বাড়তি রো lookup বাঁচে।

লম্বা primary কী secondary entry-ও বড় করে, কারণ তার মান সঙ্গে থাকে। Entry বড় হলে page-এ কম ধরে, বেশি page লাগতে পারে। ছোট, স্থির কী একসঙ্গে কয়েকটি ইনডেক্স ছোট করতে পারে। তবে surrogate কী নিলেও অ্যাপের প্রয়োজনীয় unique business identifier আলাদা মানাতে হবে।

Hash bucket

Hash ফাংশন equality search কী-কে bucket-এ মেলায়। শেখানোর h(id) = id mod 4 মডেলে 101 ও 105 দুটোই bucket 1। এটি collision; রো সমান হওয়ার প্রমাণ নয়। Bucket-এ original কী তুলনা এবং overflow, chaining বা অন্য collision strategy চাই।

ভালো distribution ও নিয়ন্ত্রিত load-এ equality lookup অল্প expected bucket access নেয়। Skew-তে লম্বা overflow chain এই প্রত্যাশা ভাঙে। id 101 থেকে 110 রেঞ্জ hash-bucket অর্ডার-এ পাশাপাশি নয়। Hash সংখ্যার কাজে লাগা ক্রম নষ্ট করায় অনেক bucket দেখতে হতে পারে।

Static hashing bucket layout স্থির রাখে; extendible বা linear hashing-এর মতো dynamic পদ্ধতি ধীরে বাড়ে। Rehash বা split-এ maintenance লাগে। এগুলো সাধারণ indexing ধারণা। Shared InnoDB টেবিলে normal B-tree ইনডেক্সের মতো ইচ্ছেমতো সাধারণ HASH ইনডেক্স বাছা যায় না।

InnoDB adaptive hash ইনডেক্স ঘন ঘন ব্যবহৃত B-tree page-এর internal optimization। দরকারি ইনডেক্স ঘোষণা করার বিকল্প নয়; ভার্সন ও configuration অনুযায়ী পাওয়া এবং ডিফল্ট বদলায়। MEMORY engine explicit hash ইনডেক্স দেয়, কিন্তু persistence ও ট্রানজ্যাকশন আচরণ InnoDB থেকে আলাদা। শুধু একটি lookup সুবিধা দেখে নয়, পুরো workload দেখে engine নাও।

Read লাভ বনাম write

ইনডেক্স ইনসার্ট, ডিলিট বা কী আপডেট-এ clustered স্ট্রাকচার-এর পাশাপাশি ইনডেক্স page-ও বদলায়। বেশি ইনডেক্স মানে বেশি space, buffer-pool capacity ও log work। Primary কী আপডেট-এ secondary entry-র পরিচয়-ও বদলাতে পারে। তাই খুব কম ব্যবহৃত ইনডেক্স কোনো কোয়েরি না নিলেও write-heavy কাজ ধীর করতে পারে।

ছোট টেবিল বা বেশিরভাগ রো দরকার হলে full scan যুক্তিযুক্ত। Secondary access-এ ছড়ানো অনেক clustered lookup লাগতে পারে; scan leaf page দক্ষভাবে পড়ে। Selectivity, রো width, coverage, cache ও cost model অনুযায়ী ভালো পথ বদলায়। কোয়েরি optimization বিকল্প থেকে প্ল্যান বেছে নেয়।

Logical-physical অর্ডার আলাদা

Clustering-এ SELECT অর্ডার

SQL অন্য access path বা execution strategy নিতে পারে। শেষে ORDER BY দাও, দরকার হলে unique tie-breaker-সহ। Physical tree একটি কাজ করার পথ; ফলের ক্রমের প্রতিশ্রুতি নয়।

Expected hash-কে worst constant

Collision ও skew-তে overflow কাজ লাগে। Expected cost বলার সময় load ও distribution-এর অনুমান বলো। Worst-case bucket অনেক খারাপ হতে পারে।

Secondary-তে PK ভুলে যাওয়া

InnoDB secondary ইনডেক্স clustered পরিচয় রাখে। মাপের হিসাব করতে secondary কলামের সঙ্গে ওই পরিচয় ধরো। চওড়া primary কী প্রতিটি secondary ইনডেক্স বড় করতে পারে।

Workload-এর route বাছো

Heap, sorted, tree ও hash organization রেকর্ড বসানো ও search-এর খরচে ভিন্ন সমঝোতা করে। InnoDB নির্বাচিত কী-তে রো cluster করে, secondary entry দিয়ে সেগুলো পায়। এরপর EXPLAIN ও optimizer-এর access choice পড়ো।
