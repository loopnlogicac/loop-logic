Count page visits, not only comparisons

A library catalogue would be slow if you opened every shelf for each book number. Storage organisation provides routes to the relevant pages. A page groups records for reading and writing, so one useful page visit can matter more than many comparisons already in memory.

A file organisation describes where records are placed. An index is an additional search structure, although some engines store the records inside an index itself. These are related choices with different costs. Always state whether a cost counts page reads, record comparisons, memory use or maintenance work.

MySQL supports several storage engines. This lesson maps the general concepts to InnoDB, which stores table data in a clustered B-tree-family structure and normally uses B+ tree behaviour for ordered index access. A textbook heap-file diagram is a comparison model, not a claim that the shared InnoDB tables are heap files.

A heap file can place a new row into a page with free space using a free-space map. A full scan of b data pages costs roughly b page reads in a cold disk model. Actual sequential throughput, prefetching and caching change elapsed time, so b is a reasoning tool rather than a stopwatch prediction.

A sorted file can first locate the starting page and then scan consecutive pages for a range. For b pages, ideal binary search takes about log2(b) page probes. Keeping the order during frequent inserts is expensive: records may move, overflow areas may grow, or periodic reorganisation may be needed. An ordered tree spreads that maintenance across smaller local changes.

Textbook primary indexes often index a file ordered by its primary key, sometimes sparsely with one entry per data block. A secondary index uses a different search key and usually needs dense entries or lists of matching record references. A clustered index controls the table’s row placement. Terminology varies across systems, so explain the physical organisation rather than relying only on the name.

Walk the tree and its references

Read a small B+ tree

                 root: [30 | 60]
                 /      |      \
leaves:     [10,20] -> [30,40,50] -> [60,70,80]
               ordered leaf links

Internal separator keys guide searches. In this drawing, values below 30 go left; values from 30 up to but below 60 go to the middle; values at least 60 go right. To find 40, read the root, choose the middle pointer, then inspect that leaf. To read 35 through 70, begin at the leaf containing the first possible key, then follow leaf links until the range ends.

B+ trees keep records or record references at leaves; internal entries guide routing. Leaves share the same depth, so a point search has a predictable number of tree levels. Each page holds many entries, producing high fanout, the number of child pointers per internal node. High fanout makes the tree shallow even for large relations.

Insertion finds the target leaf, adds the entry in order and may split a full page. A split introduces a separator into the parent; parent overflow can propagate upwards. A root split adds one level. Deletion may redistribute entries or merge pages according to the implementation. These are local structural changes, but they still require logging, locking or latching and eventual page writes.

Estimate a teaching tree height

Assume a simplified internal page has room for at most 100 child pointers, and a leaf holds 80 records. For 800,000 records, you need 800000/80 = 10,000 full leaves. One internal level with 100 nodes can reference those leaves. One root can reference those 100 internal nodes. The tree therefore has three page levels: root, internal and leaf.

Leaf10,000800,000 records

An uncached point lookup visits about three tree pages in this model. If root and internal pages stay cached, physical reads may drop to one leaf page. Real occupancy is below full capacity, records vary in width and large values can use extra pages. This calculation illustrates fanout; it does not predict the exact height of a MySQL table from its row count alone.

Suppose a range covers 200 consecutive records. At 80 records per leaf, it needs at least ceil(200/80) = 3 leaf pages when favourably aligned, and possibly four when it starts near a page end. The initial root-to-leaf route is followed by sequential leaf traversal. This is why B+ trees are useful for both point lookups and intervals.

Map the clustered index to InnoDB

For the university students table, PRIMARY KEY(student_id) defines the clustered index. The leaf record contains the row’s columns, not merely a pointer to a separate heap row. There can be only one clustering order for one table. A query still needs ORDER BY for a guaranteed display order; physical organisation is not an SQL ordering contract.

When an InnoDB table has no explicit primary key, it uses the first suitable UNIQUE index with all key columns NOT NULL. If none exists, InnoDB creates a hidden clustered row identifier. Choose a deliberate, stable primary key so the design and application can name row identity. A hidden engine identifier does not enforce an unstated business uniqueness rule.

A secondary index on hometown stores hometown values and the primary-key values used to locate clustered rows. Finding a full student by hometown may first traverse the secondary index, then traverse the clustered index for each match. If the query needs only hometown and student_id, the secondary leaf can cover it, avoiding that additional row lookup.

A long primary key enlarges secondary index entries because its value accompanies them. More bytes per entry mean fewer entries per page and potentially more pages. A stable compact key can therefore reduce several indexes at once. However, choosing a surrogate key still requires enforcing a unique business identifier when the application depends on it.

Understand hash buckets

A hash function maps an equality search key to a bucket. In a teaching model h(id) = id mod 4, keys 101 and 105 both map to bucket 1. This is a collision, not proof that the rows are equal. The bucket must compare the original keys and handle overflow, chaining or another collision strategy.

With a good distribution and controlled load, equality lookup can use a small expected number of bucket accesses. Skew can create long overflow chains and defeat that expectation. A range such as id between 101 and 110 is not contiguous in hash-bucket order. You may need to inspect many buckets because the hash destroys the useful numeric ordering.

Static hashing fixes the bucket layout, while dynamic approaches such as extendible or linear hashing grow more gradually. Rehashing or splitting buckets has a maintenance cost. These are general database indexing ideas. InnoDB users do not choose an ordinary HASH index for the shared tables in the same way they choose a normal B-tree index.

InnoDB’s adaptive hash index is an internal optimisation over frequently accessed B-tree pages. It is not a substitute for declaring useful indexes, and its availability and default setting depend on the server version and configuration. The MEMORY engine supports explicit hash indexes, but its persistence and transaction behaviour differ from InnoDB. Choose an engine for the whole workload, not for one attractive lookup claim.

Balance read savings against writes

An index insert, delete or key update changes index pages as well as the table’s clustered structure. More indexes consume space, buffer-pool capacity and log work. Updating a primary key can also change the identity stored in secondary entries. A rarely used index can therefore slow a write-heavy workload even when no query chooses it.

A full scan can be sensible for a small table or a query that needs most rows. Secondary access may require many scattered clustered-row lookups, while a scan reads leaf pages efficiently. The best route depends on selectivity, row width, coverage, caching and the cost model. Query optimisation turns those alternatives into a chosen plan.

Do not confuse logical and physical order

Expecting SELECT order from clustering

SQL can choose another access path or execution strategy. Request a final ORDER BY, including a unique tie-breaker when necessary. The physical tree is an implementation route, not a promised result order.

Calling expected hash lookup worst-case constant

Collisions and skew can force overflow work. State the load and distribution assumptions behind an expected cost. Worst-case bucket behaviour can be much worse.

Ignoring the primary key inside secondary entries

InnoDB secondary indexes carry clustered identity. Estimate their size using that identity as well as the declared secondary columns. Adding a wide primary key can enlarge every secondary index.
