Treat a transfer as one decision

Ayesha sends Tanvir 100 BDT. Subtracting from Ayesha and adding to Tanvir are two statements, but together they represent one transfer. A transaction groups those related changes. If only the first statement survives, money disappears from the model.

The four ACID properties explain what a transactional system promises. Atomicity concerns all-or-nothing effects. Consistency concerns the rules that define valid states. Isolation concerns concurrent activity. Durability concerns committed effects after failure. The letters name separate responsibilities; a COMMIT statement alone cannot prove all four.

We use two InnoDB accounts attached to the familiar students. Initially Ayesha has 1000 BDT and Tanvir has 500 BDT. The intended invariant is a total of 1500 BDT, with neither balance negative. Account identifiers are fixed, money uses DECIMAL, and the example excludes fees and external payment systems. Those assumptions make the expected state precise.

The partially committed state is a conceptual recovery boundary. It is not a MySQL status word you should expect from a SELECT. The server may still fail after the final UPDATE and before commit persistence. Only successful commit acknowledgment establishes the client-visible commit boundary under the configured durability policy.

Atomicity means a crash or chosen rollback must not leave half of this transactional operation committed. InnoDB undo supports this promise. However, many SQL statement errors undo only the failing statement. If a credit fails after a debit, your application must roll back the surrounding transfer. Do not continue to COMMIT merely because the connection is still alive.

Consistency means the transaction takes a valid starting state to a valid ending state. A CHECK can reject a negative balance, but it does not guarantee preservation of the total across two rows. Your code must debit and credit the same amount and handle missing accounts. Constraints support correct logic; they cannot infer every business invariant.

Isolation means concurrent transfers cannot interfere in ways forbidden by the chosen level and access pattern. A plain SELECT followed later by an unconditional UPDATE can lose a concurrent change. Use conditional updates or locking reads, verify affected rows, and acquire locks in a consistent order. Stronger isolation may trade concurrency for a simpler correctness argument.

Durability means committed changes survive failures within the system’s promise. InnoDB normally uses redo so a dirty page need not reach its final disk location before commit. The redo must be persisted appropriately. On MySQL, innodb_flush_log_at_trx_commit=1 is the usual durable setting; binary logging adds sync_binlog considerations. Storage devices must honour flushes. A backup remains necessary for disk loss.

The consistency letter in ACID is different from consistency in the CAP theorem. ACID consistency concerns application invariants. CAP’s consistency concerns a single-copy view across distributed replicas. The vocabulary overlaps, but the claims should not be substituted for each other.

The intermediate total of 1400 is acceptable inside this carefully controlled transaction. Other sessions must not rely on it as a completed transfer. A separate report using an unsuitable isolation level could observe intermediate data, which explains why atomic writes and suitable read isolation must work together.

For a missing destination account, a direct UPDATE affects zero rows. Treat that as failure of the whole transfer, then roll back the debit. An application should check both expected account rows before changing them and still handle later errors. Network loss during COMMIT adds another challenge: the client may not know whether commit happened. Use a unique transfer identifier and reconciliation rather than blindly sending the debit again.

A retry should represent the complete transaction, using current data and the same idempotency key for the business request. A deadlock retry is not permission to repeat a payment to an external service. Database rollback cannot undo an already sent email or an independently accepted payment. Coordinate those side effects with an appropriate delivery and reconciliation design.

Name the business request before retrying

Consider a client that sends COMMIT, then loses its connection before receiving the server response. Two outcomes are possible from the client’s view: the server committed and the response was lost, or commit did not finish. Automatically replaying an unlabelled transfer can debit the sender twice in the first case. Automatically declaring failure can hide a successful transfer.

Give each transfer request a unique business identifier and store its completed outcome with the balance changes in the same transaction. On reconnect, a caller can look up that identifier and reconcile the request. A uniqueness rule prevents two committed records for the same request. The recorded amount and account identities must also be checked, so reusing an identifier with a different payload cannot silently become a different transfer.

This pattern supports idempotent handling: repeating the same logical request returns the established outcome rather than creating a second payment. It still needs a concurrency-safe implementation and a policy for requests whose first transaction is active. A timeout does not prove that the server performed no work. These boundaries explain why durable database commits and reliable business responses are related but separate design concerns.

Locate the failed promise

Calling any correct SQL consistent

Two valid UPDATE statements can subtract different amounts and still satisfy each row’s CHECK. Compare the invariant before and after the transfer. Arithmetic correctness and affected-row checks belong in the transaction design.

Assuming a statement error aborts every prior change

A check violation commonly leaves the transaction active with earlier statements pending. Handle the error and issue full ROLLBACK when the business operation cannot finish. A deadlock may abort the entire transaction, so classify errors before retrying.

Equating rollback with recovery from every disaster

ROLLBACK addresses uncommitted transactional changes. It cannot restore yesterday’s committed accidental deletion or a destroyed storage device. Recovery logs and tested backups cover additional failure classes.

Connect logic, isolation and persistence

A safe transfer has an explicit invariant, checked account matches, one commit boundary and a clear error path. ACID describes the combined behaviour of your transaction logic and the storage engine. Study concurrency control next to see what happens when two transfers overlap.
