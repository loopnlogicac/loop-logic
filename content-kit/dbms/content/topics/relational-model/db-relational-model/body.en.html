Rows need identities and rules

Two students can share a name, but they should not share a student identifier. A result should refer to a real enrollment. The relational model gives you precise language for these everyday requirements.

A relation is a set of tuples described by named attributes. You can picture it as a table, with some cautions about SQL’s duplicates and NULL values. A tuple is one row. An attribute is a named column with an allowed domain of values.

A domain describes permissible values for an attribute. Marks might be whole numbers from zero through 100. A name uses text, while admitted_on uses a date. A SQL type captures part of a domain; further constraints may be needed to express the complete rule.

Write distinct constraints for distinct jobs

student_id INT PRIMARY KEY,
email VARCHAR(120) NOT NULL UNIQUE,
department_id INT NOT NULL,
FOREIGN KEY (department_id) REFERENCES departments(department_id)

The pattern above names three different responsibilities. The primary key identifies the student row. Email provides another guaranteed identifier in this design. The department reference connects the student to an existing parent. None of these rules says that a name must be unique.

Choose minimal identifiers

A superkey is any attribute set that uniquely identifies tuples under the schema’s rules. If student_id is unique, then student_id together with student_name is also unique. Adding extra attributes does not destroy uniqueness, but those attributes may be unnecessary.

A candidate key is a minimal superkey: remove any attribute and the remaining set no longer guarantees uniqueness. Minimal means no unnecessary attributes. It does not mean shortest spelling, smallest number or fastest index.

The primary key is the candidate selected as the main row identifier. Other candidate keys are alternate keys. In Students, student_id is primary and email is alternate because both are declared unique and required. A nullable UNIQUE column alone is not a classical candidate key.

A foreign key is a set of child attributes that references an eligible parent key. It may repeat across child rows. Many students can reference department 1. Its purpose is a valid connection, not unique identification of the child.

Entity integrity requires the primary-key attributes to be known and unique. A composite primary key excludes NULL in every component. Referential integrity requires each non-NULL foreign-key reference to match a valid parent. NOT NULL adds a requirement that an optional reference alone would not provide.

Result references the whole enrollment pair. Two separate references to Student and Section would only prove that both parents exist independently. They would not prove that this student actually enrolled in this section. The composite reference preserves that stronger relationship.

Choose parent-change actions deliberately

ON DELETE RESTRICT prevents deletion while a child still refers to the parent. ON DELETE CASCADE removes dependent child rows. ON DELETE SET NULL keeps child rows but clears their nullable references. Choose the action from the meaning of the relationship, not from a preference for shorter cleanup code.

ON UPDATE actions govern changes to referenced key values. CASCADE copies the new parent key into child references. RESTRICT blocks an incompatible change. SET NULL requires nullable child columns. In InnoDB, NO ACTION behaves like immediate RESTRICT rather than a deferred end-of-transaction check.

Test a key against permitted future rows

Imagine admitting another student named Ayesha Rahman. The name may repeat without breaking any stated rule. Now imagine admitting another student with identifier 101. That must fail because the schema guarantees unique identifiers. Candidate-key reasoning uses these permitted and forbidden future situations, rather than a coincidence in today’s short list.

Do not infer keys from small samples

Declaring a name unique because it happens to be unique today

The current eight names differ, but the university may admit another student with the same name. A key claim must follow the permitted future data. Ask which rule guarantees identity before declaring a candidate key.

Using cascades for all historical records

An enrollment’s result may reasonably depend on that enrollment. A payment often has a different lifecycle and may need to survive profile closure. The shop design restricts deletion through financial references. Changing all references to CASCADE would change that policy, not merely save typing.

Expecting rollback to undo every command

The cascade examples use InnoDB row changes inside an open transaction. Many structural commands commit implicitly. Creating or dropping a table inside the same workflow changes the rollback boundary. Keep structural operations out of a row-change experiment unless their effects are understood.

Relational ideas and MySQL details

Classical relations are sets without NULL. SQL tables can contain duplicate rows unless constrained, and nullable fields use three-valued logic. These examples use MySQL 8.0.16 or later with InnoDB, primary keys and explicitly declared reference actions.

Let constraints express promises

Candidate keys provide minimal guaranteed identity. Primary keys enforce entity integrity, while foreign keys preserve valid references. Parent-change actions decide what dependent facts should do. Next, combine relations as queries in Relational Algebra.
