Join relationships, not merely tables

Imagine a department noticeboard beside a student register. One lists department codes; the other lists each student's department identifier. A join lets you read those records together without storing the department name in every student row. You decide which pairs belong together and what to do when one side has no match.

A join combines rows according to a condition. The most familiar condition compares a foreign key with its referenced key. That gives each student the correct department. However, a join can compare other columns too. SQL does not automatically choose a relationship because two columns have similar names.

Before writing a join, say what one output row means. It might mean one student, one enrollment, or one payment. This decision is called the result's grain. A report can have correct syntax and still answer the wrong question when its grain changes unexpectedly.

The university data contains eight students and twelve enrollments. Fahim, student 108, has no enrollment. Sadia, student 107, has an enrollment without a result. These two cases help you see the difference between preserving people and preserving recorded activity.

Choose the pair rule and the preserved side

An INNER JOIN returns pairs whose ON condition is true. A LEFT JOIN also keeps each left row that finds no partner. For that unmatched row, columns from the right side become NULL. A RIGHT JOIN gives the same protection to the right input instead.

Read students AS s LEFT JOIN enrollments AS e ON e.student_id = s.student_id from left to right. Students is the population you promise to retain. Enrollments supplies optional matches. The ON condition identifies registrations belonging to the current student. Short aliases make column ownership visible without repeatedly writing long table names.

A CROSS JOIN creates every possible pair. Eight students crossed with six sections produce 48 choices, including registrations that never happened. A self join reads one table under two aliases. The aliases represent separate roles, such as the first and second classmate.

MySQL has no native FULL OUTER JOIN. Combine a left join with a second branch containing only unmatched right rows. Use UNION ALL so legitimate duplicate rows survive. The second branch must test a non-null key from the left input. Testing an optional descriptive column could incorrectly classify a matched row as missing.

SELECT <columns>
FROM <left_table> AS l
LEFT JOIN <right_table> AS r ON <matching_condition>
WHERE <result_filter>
ORDER BY <display_keys>;

Trace pairs before counting them

Start with Ayesha, student 101. She matches three enrollment rows, so a student-enrollment join emits three pairs. Tanvir also emits three. Nabila emits two, and students 104 through 107 emit one each. An inner join stops there, producing twelve rows.

Now apply the left-join rule to Fahim. His match list is empty, so SQL emits one padded row with NULL enrollment columns. The left join therefore contains thirteen rows. It has eight distinct student identifiers, but thirteen student-enrollment rows. Neither count is automatically the number your report needs.

When you group by student, COUNT(e.section_id) counts actual registrations because section_id cannot be NULL in enrollments. COUNT(*) counts the padded row too. For Fahim those expressions return zero and one respectively. Always connect an aggregate to the object it is supposed to count.

The relationship between enrollments and results uses two columns. Student 101 has several results, and section 31 has several students. Joining on student_id alone mixes sections; joining on section_id alone mixes students. Compare both student_id and section_id to preserve the composite enrollment identity.

A three-table join follows a chain. An enrollment names a section, and that section names a course. Department membership cannot replace this path. A CSE student can take MAT 101, so matching student and course departments would lose real registrations and invent others.

For self joins, decide whether pair direction matters. If Ayesha and Tanvir are one unordered classmate pair, require the first identifier to be smaller. Equality would pair each student with themselves. Inequality alone would include both Ayesha-Tanvir and Tanvir-Ayesha.

Locate filters at the right stage

An outer filter can remove preserved rows

A condition in ON decides whether two rows match. A condition in WHERE filters the joined rows afterward. For an inner join, moving an ordinary filter between these locations often preserves the result. For an outer join, it can remove the very rows you meant to protect.

Suppose you need every student, with any marks of at least 80 beside their name. Put the marks condition in ON. Students with no such result receive NULL result columns. If you put r.marks >= 80 in WHERE, those padded rows fail because the comparison is unknown. The report then lists only students with high marks.

Joining two child lists multiplies amounts

Another common error is multiplying money. Order 202 has two items and two payments. Joining both child tables directly to orders makes four combinations. Each item amount and each payment amount appears twice. Adding those repeated amounts doubles both totals even though the join conditions are individually correct.

Repair that report by summarising each child separately to one row per order. Then join the summaries. Do not use SUM(DISTINCT amount) as a general repair: two genuine payments may have the same amount and both should count. The issue is repeated row identity, not repeated numeric value.

Make relationship assumptions visible

Write explicit ON conditions and qualify shared column names. Prefer ordinary JOIN syntax over NATURAL JOIN, which can silently gain new matching columns after schema changes. Select only the columns your report promises so students and reviewers can inspect its grain.

Estimate the expected count before running a complicated report. Ask whether each new relationship is one-to-one, one-to-many or optional. If adding a table unexpectedly increases the row count, examine its matches before adding DISTINCT. Deduplication can hide a wrong condition instead of fixing it.

MySQL outer-join limits

These joins work on MySQL 8.0 and 8.4. FULL OUTER JOIN still needs an emulation. The shared tables additionally rely on CHECK enforcement from MySQL 8.0.16. An ORDER BY on the complete result controls display order; index order or branch order is not a substitute.

Keep the report population explicit

Choose the preserved population, define the matching key, and track the number of partners per row. That makes missing data and duplicate totals easier to explain. Next, use subqueries when your question asks for a comparison, membership decision or existence test rather than every matching pair.
