সম্পর্কিত change একসঙ্গে

Shop অর্ডার বানিয়ে item যোগ করে। অর্ডার বেঁচে item হারালে কাজ অসম্পূর্ণ। ট্রানজ্যাকশন দিয়ে সম্পর্কিত change এক unit করে সফল হলে রাখা, ব্যর্থ হলে ফেরানো যায়।

ট্রানজ্যাকশন commit বা rollback boundary-তে নিয়ন্ত্রিত ডেটাবেস কাজের দল। COMMIT সফল change স্থায়ী, ROLLBACK এখনও uncommitted transactional change বাতিল করে। কোন স্টেটমেন্ট ও engine boundary-তে আছে জানতে হবে।

Shared টেবিল InnoDB: transactional রো change,রো lock,foreign কী দেয়। একই SQL চলে বলেই nontransactional টেবিলের rollback এক ধরে নিও না। Engine কী ফেরানো যাবে ঠিক করে।

এখানে এক কানেকশন-এর control দেখব। অন্য কানেকশন-এর visibility,level,deadlock concurrency control-এ আছে। Boundary unit রক্ষা করে, কিন্তু অন্যরা কী দেখবে তার সব উত্তর নয়।

শুরু,শেষ আর partial progress

START TRANSACTION-এর পরে related DML চালাও, ফল যাচাই করো; সফল হলে COMMIT, ব্যর্থ হলে ROLLBACK। মানুষ screen পড়া বা unrelated ইনপুট দেওয়ার সময় lock ধরে ট্রানজ্যাকশন খোলা রাখবে না।

Savepoint active ট্রানজ্যাকশন-এর named marker। SAVEPOINT first_item অবস্থান রাখে। ROLLBACK TO ওই marker-এর পরের কাজ ফেরায়, আগেরটি pending রাখে। ট্রানজ্যাকশন শেষ নয়; শেষে COMMIT বা full ROLLBACK চাই।

RELEASE SAVEPOINT marker সরায়, change ফেরায় বা commit করে না। Full COMMIT/ROLLBACK সব savepoint শেষ করে। নতুন ট্রানজ্যাকশন শুরু MySQL-এ nested ট্রানজ্যাকশন নয়। এক unit-এর আংশিক rollback চাইলে savepoint নাও।

Autocommit session variable সাধারণ boundary ঠিক করে। One এবং explicit ট্রানজ্যাকশন না থাকলে সফল standalone স্টেটমেন্ট সাধারণত commit। START TRANSACTION variable স্থায়ী না বদলে কাজ জড়ো করে; শেষে configured আচরণ ফেরে।

START TRANSACTION;
<first_related_change>;
SAVEPOINT <marker>;
<later_related_change>;
ROLLBACK TO SAVEPOINT <marker>;
COMMIT;

Pending আর permanent মান trace

শুরুতে 100 exercise book। Conditional UPDATE অন্তত দুই থাকলেই দুই কমায়। Explicit ট্রানজ্যাকশন-এ COMMIT পর্যন্ত pending; পরে 98। Predicate numeric rule রক্ষা করে, ট্রানজ্যাকশন permanence।

Conditional আপডেট zero রো বদলিয়েও এরর না দিতে পারে: পণ্য নেই বা stock কম। App-কে affected রো দেখে business success বলতে হবে। COMMIT সফল মানেই সব চাওয়া রো মিলেছে নয়।

Student 106-এর mark সাময়িক 40→100। একই ট্রানজ্যাকশন 100 ও generated A+ দেখে। ROLLBACK-এ 40,D ফেরে। Generated কলাম base value অনুসরণ করে; আলাদা repair লাগে না।

আগে book 100→99, তারপর savepoint, পরে pen 200→198। ROLLBACK TO শুধু pen ফেরায়। COMMIT আগের book রাখে। দুই final stock marker-এর দুই পাশ বোঝায়।

Autocommit off-এ implicit ট্রানজ্যাকশন চলতে থাকে। COMMIT/ROLLBACK-এর পরের transactional স্টেটমেন্ট নতুনটি শুরু করে। Zero থেকে one করলে outstanding কাজ commit হতে পারে। Pooled কানেকশন সেটিং ফেরানোর আগে স্পষ্টভাবে কাজ শেষ করো।

খালি ট্রানজ্যাকশন rollback ক্ষতি করে না। আগে commit হওয়া change rollback ফেরায় না। ওই কানেকশন আগে লিখেছে কি না নয়, এখনও pending কি না boundary। Commit-এর পরে compensating change বা restoration লাগে।

Boundary-র দুইপাশে পড়ো

উদাহরণে full commit,full rollback,partial rollback ও সেটিং change আছে। Boundary-র আগে-পরে মান মেলাও। নিজের pending edit SELECT-এ দেখা যায়; নতুন মান দেখাই commit প্রমাণ নয়।

Practice অর্ডার-এ parent ও এক child item। Foreign কী-তে parent আগে ইনসার্ট চাই। Rollback দুটো pending রো সরায়। Referential integrity ও atomic workflow একসঙ্গে লাগে, এরর check-এর বদলি নয়।

স্টেটমেন্ট এরর সবসময় full rollback নয়

Failure explicit সামলাও

অর্ডার ইনসার্ট সফল, item CHECK-এ ব্যর্থ ধরো। অনেক এরর শুধু ব্যর্থ স্টেটমেন্ট ফেরায়, আগেরটি pending। Ignore করে commit করলে অসম্পূর্ণ অর্ডার থাকবে। এরর ধরে intended unit rollback করো।

InnoDB deadlock victim-এর মতো এরর পুরো ট্রানজ্যাকশন ফেরাতে পারে। পুরো কাজ retry লাগবে কি না জানো এবং external effect duplicate এড়াও। ডেটাবেস ROLLBACK পাঠানো message বা আলাদা সার্ভিস-এর charge ফেরায় না।

DDL আর savepoint আলাদা boundary

CREATE TABLE,ALTER TABLE,CREATE INDEX implicit commit করতে পারে। Stock আপডেট-এর মাঝে ঢোকালে পরের rollback-এর আগেই stock স্থায়ী। Atomic DDL নিজের crash-safe আচরণ; user-controlled rollback গ্রুপের অংশ নয়।

Savepoint স্বাধীন commit নয়। ROLLBACK TO-এর পরে আগের change pending; full rollback-এ সেটিও যায়। সব lock ছাড়ে ধরবে না; engine-specific detail আছে। এটি ডেটা rollback position, complete resource reset নয়।

ট্রানজ্যাকশন owner স্পষ্ট

কোন layer boundary চালায় ঠিক করে লিখে দাও। Procedure হঠাৎ commit করলে বড় caller operation ভাঙে। Ordinary CALL নিজে atomic ধরে caller-ও ভুল করতে পারে। Routine ও trigger workflow review-তে ধরো।

Schema migration সাধারণ business ট্রানজ্যাকশন-এর বাইরে রাখো। সম্ভব হলে lock-এর আগে ইনপুট validate, কাজের মাঝে affected রো ও প্রতিটি এরর path দেখো। Pool-এ ফেরানোর আগে সেটিং ফেরাও, যেন পরের user অপ্রত্যাশিত mode না পায়।

InnoDB আর implicit commit জরুরি

ট্রানজ্যাকশন-savepoint MySQL 8.0/8.4-এ আছে। Shared CHECK 8.0.16 চায়। স্টেটমেন্ট অনুযায়ী implicit-commit rule বদলায়। Admin SQL ও DML মেশানোর আগে manual দেখো; BEGIN সব কমান্ড রক্ষা করে ধরে নিও না।
