Ask a small question inside a larger one

A teacher wants results above the class average. First you need the average; then you need the marks that exceed it. A subquery expresses that smaller question inside the larger report. The connection between those questions matters more than how deeply you indent the SQL.

A subquery is a SELECT used inside another SQL statement. It can supply one value, a row of values, a set of candidates or a temporary relation. Choose the form that matches your question. Comparing a mark with one mean is different from asking whether a student has any registration.

You already know how joins return matching pairs. A membership test usually needs only one yes-or-no decision for each outer row. That difference explains why replacing a subquery with a join can unexpectedly repeat people. Neither form is universally better; each expresses a different shape of work.

The examples reuse university results and shop prices. Their empty cases are deliberate. No enrollment, no recorded mark and no product in a category are different situations. A good query should explain which of those situations it handles and what answer it chooses.

Match the subquery shape to the comparison

A scalar subquery supplies one column from at most one row. Put it in parentheses where one value is expected. AVG without GROUP BY is a common choice because it returns exactly one aggregate row. If there are no input marks, that row contains NULL.

A scalar subquery returning no rows also supplies NULL. Returning two rows causes an error, even if both rows contain the same value. A LIMIT 1 can hide this error while choosing an arbitrary row. Use a unique predicate or a meaningful ordered selection when the requirement truly asks for one row.

A row subquery supplies several columns for a tuple comparison. The enrollment identity is the pair student_id and section_id. The left tuple and the subquery result must have the same number of columns in matching positions. Testing separate IN lists would allow unintended combinations across different enrollments.

A table subquery appears in FROM and needs an alias in MySQL. It behaves like a temporary relation for the surrounding statement. A grouped payment subquery can provide one total per order, ready for a join without multiplying the original payment rows.

SELECT <outer_columns>
FROM <outer_table> AS o
WHERE EXISTS (
    SELECT 1 FROM <inner_table> AS i WHERE <correlation>
)
ORDER BY <outer_keys>;

Distinguish membership, witnesses and universal tests

Use IN when a value or tuple must belong to the subquery result. Repeated copies inside the result do not create additional outer rows. Ayesha's identifier may occur in several enrollment rows, but a membership test on students still returns her once.

Use EXISTS when any qualifying inner row is enough. The selected expression is irrelevant to existence. SELECT 1 is a readable convention, not a request to count ones. A returned row containing NULL still makes EXISTS true. An empty result makes EXISTS false.

A correlated subquery refers to a value from its outer query. In the missing-enrollment report, the inner WHERE compares enrollment.student_id with the current student identifier. Think of evaluating that question for each student. The optimizer may transform the work internally, so this mental model does not promise a particular execution strategy.

The correlated average example compares each result with its own section mean. For section 31 the marks are 85 and 65, giving mean 75. Only 85 qualifies. Comparing both marks with the overall mean would answer a different question and could select different students.

ANY needs at least one true comparison. A price above ANY study price need only exceed the cheaper study item. ALL needs every comparison to be true. A price above ALL study prices must exceed even the largest one. Equality with the largest price is insufficient for a strict greater-than comparison.

Empty sets reveal the logic clearly. A greater-than ANY comparison is false when there is no candidate to witness success. A greater-than ALL comparison is true because there is no candidate that violates it. This universal empty-set rule is called vacuous truth. Decide whether that matches the business question before relying on it.

Protect meaning around NULL

Nullable exclusions need a policy

NOT IN is tempting for exclusion, but nullable values make it dangerous. Consider 101 NOT IN (102, NULL). The first inequality is true; the comparison with NULL is unknown. The combined condition is unknown, so WHERE removes the row rather than treating it as a confirmed non-member.

NOT EXISTS is usually clearer for missing-related-row questions. Match the relevant identity inside the subquery and negate the existence decision. An outer NULL key still needs an explicit policy: ordinary equality finds no match for it. If NULL should match NULL, use a null-safe comparison deliberately.

Correlate the intended columns

The same warning applies to ANY and ALL when their candidate results contain NULL. A true comparison can establish ANY; a false comparison can disprove ALL. Otherwise unknown comparisons may leave the result unknown. The empty-set rules apply to an actually empty result, not a one-row result containing NULL.

Avoid unqualified correlation. A condition such as student_id = student_id may compare the inner column with itself. Give each table an alias and write both owners explicitly. A syntactically valid self-comparison can make EXISTS true for every student as soon as one inner row exists.

Choose a readable equivalent before tuning

When considering a join rewrite, check uniqueness. A join to a unique department key has one match per student. A join to enrollments can have several. If only existence matters, keep EXISTS or make the deduplication requirement explicit. Compare semantics before comparing plans.

Inspect a small group by hand, including a missing match and a repeated match. Then try an empty inner result. Those cases distinguish queries that look equivalent on ordinary data. Use indexes and EXPLAIN later to investigate performance without changing the question being asked.

Keep the result shape portable

The scalar, row, derived-table and quantified comparisons shown here are available in MySQL 8.0 and 8.4. The shared schema requires MySQL 8.0.16 for enforced CHECK constraints. Optimizer improvements can change how a subquery runs, while its required cardinality and NULL rules remain part of the SQL meaning.

State the inner question precisely

Decide whether you need one value, a membership set or an existence decision. Correlate with complete keys, and reason separately about empty results and NULL values. Continue with set operations to combine entire compatible query results rather than testing each outer row against an inner answer.
