Give repeated database work a callable interface

Several reports may need to count a student's registrations or assign the same pass label. Copying the logic into every caller makes changes harder to coordinate. A stored routine gives that behaviour a name inside the database and accepts values through parameters.

A stored procedure is a database routine invoked with CALL. It can perform several statements, return result sets and pass values back through parameters. A stored function returns one declared scalar value and can be used in an expression. Choose by the required interface, rather than by which syntax looks shorter.

Storing logic in the database does not automatically make it faster or safer. The routine still needs clear privileges, sensible transaction boundaries and understandable error handling. A complicated routine can hide expensive queries just as easily as an application function can.

The examples use registration counts, result labels and a bounded arithmetic loop. The count works with the shared enrollment table. The label reflects the teaching pass boundary already used by results. The small loop isolates control flow without claiming that row-by-row processing is the best way to summarise a table.

Send a complete definition through the client

A routine body often contains BEGIN and END with several semicolon-terminated statements between them. The mysql command-line client normally treats a semicolon as the end of the submission. DELIMITER temporarily changes that client terminator so the whole routine definition can be sent together.

DELIMITER is not server SQL. In the examples, DELIMITER // tells the client to wait for //. Semicolons inside the body remain ordinary SQL statement separators. After the definition ends with END//, DELIMITER ; restores normal client behaviour. Many application drivers send the complete definition directly and do not understand a DELIMITER command.

CREATE PROCEDURE declares the routine name and parameters. IN supplies a value to the procedure. OUT sends a value back to the caller. INOUT does both. The caller commonly supplies session variables such as @registrations as writable receivers for OUT and INOUT arguments.

CREATE FUNCTION also declares a RETURNS type. Its RETURN statements must provide a compatible value. A stored function has no OUT parameter list like a procedure; it returns its scalar result through the function expression. The pass_label function therefore fits naturally beside marks in a SELECT list.

The examples declare SQL SECURITY INVOKER. This uses the caller's privileges rather than lending the routine owner's privileges. Callers still need EXECUTE access as well as any underlying rights required by invoker execution. A production design should review both the routine interface and its effective security context.

Follow values through parameters and local state

When you call count_registrations for student 101, IN p_student_id receives 101. SELECT COUNT(*) computes three and assigns it into the OUT parameter. When CALL finishes, the caller's @registrations variable receives that value. A separate SELECT displays it without needing the procedure to emit a result set itself.

Student 108 has no enrollment. COUNT without GROUP BY still returns one row containing zero, so the OUT parameter becomes zero. This is different from SELECT INTO returning no ordinary row, which needs careful handling because a variable may retain a previous value. Aggregate shape can simplify a routine's contract.

A local variable exists within its BEGIN-END block. DECLARE statements appear before executable statements in that block. DEFAULT can initialise a value, and SET changes it later. Local variables such as v_count differ from @session_variables, which belong to the connection and can remain after the routine returns.

Distinct prefixes help prevent ambiguous names. p_student_id is an input, v_count is local state and student_id is a table column. Without that separation, a predicate like student_id = student_id may compare the wrong objects and count every row. Qualifying columns with aliases gives another useful layer of clarity.

IF checks conditions in order. The result_status procedure first counts recorded results. A zero count produces no results; otherwise it produces recorded. That message describes presence, not academic success. A student with a fail grade still has a recorded result and must not be classified as pending.

The function checks NULL before comparing a mark with 40. SQL comparisons with NULL are unknown, so handling it explicitly makes the chosen pending label visible. For known marks, 40 and above return pass and lower values return fail. The function is a teaching label, not a replacement for validating marks against the table constraint.

The WHILE procedure starts v_step at one and p_total at zero. Every iteration adds the current step and then increments it. A limit of four produces totals one, three, six and ten. A limit of zero performs no iterations because the first condition is already false.

Validation rejects a NULL limit, negative limit or limit above 100 before the loop starts. This bounds both the work and the integer result for the example. SIGNAL with SQLSTATE 45000 reports an application-defined failure. Clear validation is better than allowing an unreasonable loop to run until a timeout.

Inspect both ordinary and boundary calls

The registration procedure is called for a student with several enrollments and one with none. The IF example then distinguishes pending results from recorded ones. These are related questions with different source tables and should not be collapsed into one vague status.

The arithmetic loop demonstrates local state and progress. The scalar function demonstrates expression use and a NULL boundary. INOUT finally shows a parameter that begins with a caller value and returns a changed value. Reading the initial and final values is the easiest way to understand that direction.

For SQL data work, prefer set-based statements when they express the task clearly. SUM over rows is usually better than fetching every row into a procedural loop. Control flow is useful for decisions and workflows; learning a loop does not make loops the default reporting tool.

Keep routine and transaction boundaries separate

CALL does not define atomicity

CALL does not automatically wrap every statement of an ordinary procedure into one transaction. With autocommit enabled and no explicit transaction, several updates may commit separately. If the operation must succeed as one unit, establish a clear transaction contract between caller and procedure.

Do not let a procedure unexpectedly COMMIT a transaction owned by its caller. Conversely, do not assume a caller knows that the procedure starts or ends a transaction. Document who controls the boundary. Stored functions and triggers have additional restrictions and cannot perform ordinary transaction control in the same way as a procedure.

Loop progress and function declarations are promises

A loop that never changes its condition variable can run indefinitely. Draw the condition, body and update as separate steps. Check that every path through the body eventually reaches progress or exits deliberately. Validation and a bounded limit make that reasoning easier, but they do not repair a missing increment.

DETERMINISTIC claims that the same inputs give the same result. MySQL does not prove that claim by inspecting every possible execution. The pass-label function genuinely depends only on its parameter and declares NO SQL because it reads no table data. Do not copy those characteristics onto a function that reads changing rows.

Stored-function creation may require extra authority or server configuration when binary logging is enabled. A failure there is an administrative policy issue, not evidence that changing the function's declared behaviour dishonestly is acceptable. Describe its actual data access and determinism, then resolve the required privileges with the database administrator.

Make routine contracts small and explicit

Choose parameter types that match the domain and validate unsupported inputs early. Return labels or counts with clear meanings, including the empty case. Keep routine names and output names specific enough that a caller can understand them without reading every statement in the body.

Use a small number of purposeful routines instead of moving all application code into the server. Review their dependencies when changing tables or permissions. A routine definition can remain stored while an underlying assumption becomes false, so versioned schema changes should include the routines that depend on those assumptions.

Client syntax and server features differ

The routine features shown here are supported by MySQL 8.0 and 8.4. DELIMITER belongs to the mysql client and must be adapted when definitions are submitted through another tool. The shared datasets require MySQL 8.0.16 for enforced CHECK constraints. Function-creation permissions can also depend on binary-logging settings.

Choose the interface and trace every value

Use procedures for callable multi-step work and functions for scalar expressions. Separate local state from session variables, bound loops and state who controls transactions. Continue with triggers to see database behaviour that runs automatically in response to row changes.
