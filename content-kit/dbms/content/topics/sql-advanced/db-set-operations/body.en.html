Combine answers with the same shape

Two offices hand you lists of department identifiers. One list comes from students; the other comes from teachers. You may want every occurrence, one copy of each identifier, only shared identifiers, or identifiers missing from the second list. Those are four different questions about the same inputs.

A set operation combines complete query results by matching columns in corresponding positions. Unlike a join, it does not place related records side by side. It adds, intersects or subtracts rows with the same shape. Think of stacking compatible lists before deciding how repeated entries should behave.

SQL results normally allow repeated rows. This repeated-row collection is often called a bag or multiset. Mathematical sets contain each value only once. The choice between these models is essential when counting people, merging attendance lists or combining financial activity.

The university data makes the difference visible. Eight students and four teachers contribute twelve department occurrences. Only three distinct departments appear. Both twelve and three are meaningful answers, provided you state whether you are counting records or department identities.

Align columns before choosing an operator

The paired queries must return the same number of columns. MySQL also needs compatible types in each position. Column names do not control matching. If the first result returns student_id then section_id, the second must return those meanings in the same order.

The combined result takes its output column names from the first query block. Give useful aliases there and use them in the final ORDER BY. A final sort applies to the complete combined answer. Sorting an input block does not promise the order of the final result.

UNION means UNION DISTINCT unless you specify ALL. It removes duplicate complete rows across both inputs. UNION ALL keeps every occurrence. If the same department appears four times among students and twice among teachers, UNION keeps one occurrence while UNION ALL keeps six.

INTERSECT keeps rows present on both sides. EXCEPT keeps rows from the left side that have no right-side match. These operators also use DISTINCT by default. Their ALL forms preserve multiplicity according to count rules, rather than retaining arbitrary duplicate copies.

When you mix operators, use parentheses to show your intended grouping. INTERSECT has higher precedence than UNION and EXCEPT in MySQL. A reader should not need to remember precedence to understand an important eligibility rule. Explicit grouping also helps when moving the query between SQL products.

Count complete rows and their occurrences

For INTERSECT DISTINCT, write one copy of each complete row that appears in both inputs. A registered student with a recorded result belongs to both identifier lists. Several result rows for that student still produce one identifier after the distinct intersection.

For EXCEPT DISTINCT, begin with the distinct left candidates and remove those appearing on the right. Enrolled identifiers minus result identifiers leaves Sadia, 107. Fahim is missing from enrollments entirely, so he is not a candidate for that subtraction. Students minus enrollments answers a different question and finds Fahim.

INTERSECT ALL keeps the smaller occurrence count from each side. Department 1 appears four times in students and twice in teachers, so two copies survive. Departments 2 and 3 each appear twice in students and once in teachers, leaving one copy each. The intersection therefore has four rows.

EXCEPT ALL subtracts right occurrence counts from left counts, with a minimum of zero. If the left side has three CSE entries and the right has two, one remains. Reversing the sides leaves none. Difference is directional, while union and intersection have symmetric membership rules for compatible inputs.

Duplicate comparison treats two NULLs as equal for these set operations. That does not change the meaning of NULL = NULL in an ordinary predicate, which remains unknown. The hometown example uses both missing hometowns and Dhaka values to show that a shared NULL can survive an intersection once.

Set matching compares all projected columns. Adding student_name beside department_id changes the identity being deduplicated. Two students in CSE are different complete rows when their names differ. Decide the projection first; then choose the operation. DISTINCT on a wider row cannot answer a narrower identity question automatically.

Do not confuse membership with row pairing

Pair counts differ from set counts

An inner join can emulate an intersection only with the right projection and duplicate handling. If each side contains repeated values, joining creates every matching pair. Three left copies and two right copies make six joined rows, while INTERSECT ALL would keep two. The algorithms answer different multiplicity questions.

An anti-join can emulate distinct difference when the matched-side key cannot be NULL. NOT EXISTS is often easier to reason about for nullable projections. Use MySQL's <=> null-safe equality if two NULL values should count as a match. Ordinary equality would incorrectly retain a missing value in some difference rewrites.

Duplicate removal is a semantic choice

Do not replace UNION ALL with UNION merely to make an unexpectedly large output shorter. Two genuine transactions with identical displayed fields may both need to remain. Conversely, UNION ALL is wrong for a directory that promises one copy of each town. Choose according to meaning before considering deduplication cost.

Avoid using unrelated values merely because their types line up. Combining a marks column with a product stock column produces a syntactically compatible number list with no useful interpretation. Column compatibility is a technical requirement, not evidence that the combined report makes sense.

Make population and repetition explicit

Describe each input in a short sentence, including its filters and projection. Then describe whether repetitions matter. For eligibility, membership often matters; for event accounting, every occurrence usually matters. This habit exposes mistakes before you inspect a long combined result.

Parenthesize mixed operations and place one final ORDER BY after the whole expression. Include enough ordering columns to distinguish displayed rows. Equal duplicate rows need no additional tie breaker because exchanging identical rows cannot change their displayed sequence.

Respect the native syntax boundary

UNION and UNION ALL are available in older MySQL releases. Native INTERSECT and EXCEPT, including their ALL forms, require MySQL 8.0.31 or later. This lesson's native examples therefore need that version. On earlier 8.0 servers use the demonstrated DISTINCT plus EXISTS or NOT EXISTS rewrites with appropriate NULL matching.
