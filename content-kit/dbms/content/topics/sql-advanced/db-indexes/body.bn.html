দরকারি রো-তে যাওয়ার পথ খোঁজো

মোটা register-এ শিক্ষার্থী খুঁজতে সব page পড়া যায়, কিন্তু নাম directory সঠিক page-এর কাছে নিয়ে যায়। ডেটাবেস ইনডেক্স একই ধরনের পথ দেয়। তবে প্রতিটি lookup দ্রুত হবেই এমন প্রতিশ্রুতি নয়।

ইনডেক্স টেবিল ডেটা-র সঙ্গে বজায় রাখা সহায়ক ডেটা স্ট্রাকচার। B-tree কী ক্রমে রাখে; সার্ভার equality বা রেঞ্জ-এ যেতে পারে। বাঁচা search work traversal, স্টোরেজ ও রো fetch-এর খরচের চেয়ে বেশি চাই।

Shared dataset হাতে দেখার মতো ছোট। এর timing দিয়ে production speedup প্রমাণ হয় না। Declaration ও প্ল্যান-এর শব্দ শেখো। আসল মাপ, realistic কোয়েরি, write ও concurrent কাজ দিয়ে পারফরম্যান্স বিচার করো।

Correctness ও access path আলাদা। Normal secondary ইনডেক্স যোগ-বিয়োগে ফল membership বদলানোর কথা নয়। ORDER BY না থাকলে printed অর্ডার বদলাতে পারে; সেটি কোয়েরি ordering-এর ত্রুটি, ইনডেক্স predicate-এর অর্থ বদলানো নয়।

কাজের ক্রমে কী সাজাও

CREATE INDEX নাম ও ordered কী কলাম নেয়। Composite index-এ একাধিক কী part। (department_id, student_name)-এ আগে বিভাগ, ভেতরে নাম। ক্রম উল্টালে অন্য access path।

সাধারণ B-tree lookup leftmost prefix থেকে শুরু। department_id equality প্রথম part, নাম-সহ equality দুটো নেয়। শুধু নাম-এ leading বিভাগ interval নেই; তবে MySQL scan, প্রযোজ্য skip-scan বা অন্য ইনডেক্স ভাবতে পারে।

রেঞ্জ-এর পরে কী use বদলায়। (department_id, admitted_on, student_id)-এ বিভাগ equality ও তারিখ রেঞ্জ স্পষ্ট interval। পরের কলাম ফিল্টারিং, coverage বা অর্ডার-এ সাহায্য করলেও আরেক leading equality-এর মতো interval ছোট করবেই নয়।

DROP INDEX named secondary স্ট্রাকচার সরায়, টেবিল রো নয়। Primary, unique ও foreign-কী-support ইনডেক্সের বাড়তি দায় আছে। একটি SELECT নেয় না বলেই কনস্ট্রেইন্ট-এর কী ফেলবে না।

সময়ের বদলে প্ল্যান choice পড়ো

InnoDB clustered primary-কী স্ট্রাকচার-এ রো রাখে। Secondary entry-তে রো খোঁজার primary কী থাকে। তাই secondary tree-এর পরে clustered রো fetch লাগতে পারে। ইনডেক্স-এ সব requested value থাকলে বাড়তি fetch বাঁচে।

Covering index নির্দিষ্ট কোয়েরির সব দরকারি মান রাখে। Covering ইনডেক্স-কোয়েরি সম্পর্ক, universal গুণ নয়। আরেক unindexed কলাম নিলে সুবিধা হারায়। Wide ইনডেক্স-এ স্টোরেজ ও maintenance-ও বাড়ে।

EXPLAIN optimizer-এর প্রস্তাবিত প্ল্যান। Traditional আউটপুট-এ type,possible_keys,কী,key_len,ref,রো,filtered,Extra থাকে। Fixed primary ID উদাহরণ const access নেয়। পরের SELECT actual রো দেখায়; EXPLAIN planning তথ্য।

Type-এ const,ref,রেঞ্জ,ইনডেক্স,ALL-এর মতো access বোঝায়। ALL টেবিল scan; ইনডেক্স পুরো ইনডেক্স scan-ও হতে পারে। একা লেবেল খারাপ প্ল্যান প্রমাণ নয়। ছয়-রো products scan কয়েক secondary lookup-এর চেয়ে সস্তা হতে পারে।

Possible_keys দরকারি candidate, কী নির্বাচিত ইনডেক্স। রো examined রো-এর estimate, exact আউটপুট সংখ্যা নয়। Filtered শর্তের পরে থাকা percentage-এর estimate। Statistics ও ভার্সন এগুলো বদলাতে পারে।

Extra-তে Using where,ইনডেক্স,filesort-এর মতো clue। Using ইনডেক্স সাধারণত covering access। Using filesort সর্টিং method-এর নাম; disk ফাইল লেখা হয়েছে তার প্রমাণ নয়। Predicate,projection,অর্ডার-এর সঙ্গে লেবেল মেলাও।

কম selectivity আর write খরচ

Low-selectivity কলাম অনেক রো ফেরাতে পারে। Selectivity শর্ত কতটা candidate কমায় বলে। কয়েক common status-ও composite কী-তে কাজে লাগতে পারে; একা ইনডেক্স করলেই lookup সার্থক নয়।

অতিরিক্ত ইনডেক্স write ব্যয় বাড়ায়। INSERT entry যোগ, DELETE সরায়, UPDATE কী বদলাতে পারে। CPU,buffer,log ও স্টোরেজ লাগে। শুধু রিপোর্ট পরীক্ষা করলে প্রতিটি অর্ডার entry-র খরচ চোখ এড়ায়।

Expression আর display অর্ডার

Indexed কলামের ওপর ফাংশন সাধারণ lookup আটকাতে পারে। YEAR(admitted_on) = 2026-এর বদলে 2026-01-01 থেকে 2027-01-01-এর আগে half-open রেঞ্জ ভাবো; stored তারিখ-এ contiguous interval। Functional ইনডেক্স আলাদা option, নিজস্ব rule আছে।

ইনডেক্স scan দেখে অর্ডার ধরে নেওয়াও ভুল। কাল optimizer অন্য path নিতে পারে। Sequence চাইলে SELECT-এ ORDER BY। Incidental primary-কী suffix নয়, রিপোর্ট অনুযায়ী tie-breaker নাও।

কাজ দেখে ডিজাইন করো, তারপর মাপো

গুরুত্বপূর্ণ predicate ও জয়েন থেকে শুরু। Equality,রেঞ্জ,অর্ডার,projection একসঙ্গে ভাবো। প্রতিটি কলাম আলাদা ইনডেক্স করবে না। Overlapping ইনডেক্স খরচ নকল করেও দরকারি composite অর্ডার মিস করতে পারে।

Representative ডেটা-তে আগে-পরে প্ল্যান তুলনা করো। Read benefit ও write cost রাখো। EXPLAIN ANALYZE actual execution তথ্য দেয়, কিন্তু কোয়েরি চালায়। কোয়েরি ও distribution বদলালে ইনডেক্স আবার দেখো।
