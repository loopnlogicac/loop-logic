Add a route to the rows you need

Imagine finding a student in a thick register. Reading every page works, but a name directory can take you close to the right page. A database index plays a similar role. It gives the server another way to locate rows without promising that every lookup will be faster.

An index is an auxiliary data structure maintained alongside table data. A B-tree index keeps searchable key values in order. The server can follow that structure to an equality match or a range. The saved search work must outweigh traversal, storage and row-fetching costs.

The shared datasets are deliberately small enough to inspect by hand. Their timings cannot demonstrate production-scale speedups. Use them to learn index declarations and plan vocabulary. Judge performance on representative data sizes and realistic query patterns, including writes and concurrent work.

Keep correctness separate from access paths. Adding or removing a normal secondary index should leave the result membership unchanged. A missing ORDER BY can make the printed order change, but that is an ordering defect in the query rather than an index changing the meaning of its predicate.

Build the key in a useful order

CREATE INDEX names an index and lists its key columns in order. A composite index contains more than one key part. For (department_id, student_name), entries are ordered first by department, then by student name within each department. Reversing those columns creates a different access path.

The ordinary B-tree lookup rule begins with the leftmost prefix. An equality on department_id can use the first key part. Equality on department_id and student_name can use both. A name-only condition does not provide that leading department interval, although MySQL may consider scanning, skip-scan access where applicable, or another index.

Range conditions affect later key use. With (department_id, admitted_on, student_id), one department equality followed by an admission-date range describes a clear interval. Later columns may help filtering, covering or ordering, but they do not necessarily narrow that interval like another leading equality.

DROP INDEX removes the named secondary structure. It does not erase table rows. Be careful around indexes required for constraints: primary keys, unique keys and foreign-key support have additional responsibilities. Do not drop a key merely because one SELECT does not appear to use it.

CREATE INDEX <index_name>
ON <table_name> (<leading_equality_column>, <range_column>);

Read a plan as a choice, not a stopwatch

InnoDB stores table rows in the clustered primary-key structure. A secondary-index entry includes the primary key needed to locate its row. A lookup may therefore visit a secondary tree and then fetch the clustered row. If the index already supplies every requested value, the server may avoid that extra row fetch.

A covering index is an index containing the values needed by a particular query. Covering is a relationship between an index and a query, not a universal property of the index. Selecting an additional unindexed column can remove that benefit. Wider indexes also take more space and maintenance work.

EXPLAIN shows the optimizer's proposed execution plan. Traditional output includes type, possible_keys, key, key_len, ref, rows, filtered and Extra. The primary-key example has one fixed identifier and uses const access. The following SELECT confirms the actual row, while EXPLAIN itself reports planning information.

The type column describes access, such as const, ref, range, index or ALL. ALL means a table scan; index can mean a full index scan. Neither label alone proves a bad plan. A six-row products table may be cheaper to scan than to access through several secondary lookups.

possible_keys lists candidate indexes considered useful for locating rows. key names the chosen index, which can differ from what you expected. rows is an estimate of examined rows, not the exact output count. filtered estimates the percentage remaining after conditions. Statistics and server versions can change these estimates.

Extra adds clues about work such as Using where, Using index or Using filesort. Using index commonly indicates covering access. Using filesort names a sorting method, not proof that a disk file was written. A useful explanation connects each label to the query's predicates, projection and order.

Avoid indexes that cost more than they save

Low selectivity and write costs

An index on a low-selectivity column may return much of the table. Selectivity describes how strongly a condition narrows candidates. A status with only a few common values can still be useful in a suitable composite key, but indexing it alone does not guarantee a worthwhile lookup.

Extra indexes make writes more expensive. An INSERT adds entries to applicable indexes. DELETE removes them. UPDATE may change index keys as well as row data. These actions consume CPU, buffer space, logging and storage. A report-only experiment can miss the cost paid by every order entry.

Expressions and display order need care

Functions around indexed columns can prevent a straightforward lookup using an ordinary index. Instead of YEAR(admitted_on) = 2026, consider a half-open date range from 2026-01-01 through before 2027-01-01. That expresses a contiguous interval on the stored date values. Functional indexes are a separate design option with their own rules.

Another trap is inferring sort order from a successful index scan. The optimizer can choose another path tomorrow. Put ORDER BY in the SELECT when the application needs a sequence. Match tie breakers to the report's meaning, rather than relying on an incidental primary-key suffix.

Design for a workload, then measure

Start with the most important query predicates and joins. Consider equality columns, range columns, ordering requirements and the returned projection together. Avoid building one index for every column in isolation. Several overlapping indexes can duplicate costs while still missing the useful composite order.

Compare plans before and after a proposed change on representative data. Record the read benefit and the write cost. EXPLAIN ANALYZE can provide actual execution information, but it runs the query, so use it with appropriate care. Revisit indexes when application queries and data distributions change.

Expect plan details to vary

CREATE INDEX, composite B-tree access and traditional EXPLAIN are available throughout MySQL 8.0 and 8.4. EXPLAIN ANALYZE arrived in 8.0.18. The shared tables additionally need CHECK enforcement from 8.0.16. Cost estimates and newer optimizer strategies are version-sensitive, even when the logical answer is unchanged.
