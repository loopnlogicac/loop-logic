কাজের যতটুকু access লাগে ততটুকু

ফল clerk নাম-মার্ক পড়বে,grade বদলাবে না। Shop app অর্ডার করবে,সার্ভার অ্যাকাউন্ট নয়। আলাদা অ্যাকাউন্ট-এ আলাদা job বলা যায়,এক component-এর ভুলের ক্ষতি কমে।

Authentication কে connect করে দেখে। Authorization তার কী করা চলে দেখে। Login সফল মানেই সব টেবিল নয়। আলাদা বুঝলে admin ক্ষমতা না দিয়েই access এরর বোঝা যায়।

Least privilege-এ দরকারি action-ডেটা-ই দাও। Operation,object scope,কলাম,delegation,lifetime সব ধরো। প্রথম রিপোর্ট চালাতে read-only-কে global admin নয়।

Isolated teaching সার্ভার-এ admin exercise temporary named অ্যাকাউন্ট বানিয়ে narrow grant দেখে সরায়। Sample পাসওয়ার্ড শুধু local। Real credential protected runtime secret-এ,rotation-সহ।

অ্যাকাউন্ট-এ host-ও আছে

MySQL user+host-এ পরিচয়,যেমন 'report_reader'@'localhost'। অন্য host আলাদা অ্যাকাউন্ট,credential,privilege হতে পারে। শুধু visible নাম পুরো পরিচয় নয়।

CREATE USER অ্যাকাউন্ট-auth তৈরি,selected ডেটাবেস access নিজে নয়। GRANT ভিউ SELECT বা নির্দিষ্ট কলাম UPDATE দেয়। REVOKE grant সরায়,DROP USER অ্যাকাউন্ট।

Global,ডেটাবেস,টেবিল,কলাম scope আছে। সব ডেটাবেস-এর grant এক students টেবিলের চেয়ে অনেক বড়। UPDATE(hometown)-এ edit সীমিত হলেও predicate-expression পড়ার privilege-ও ভাবো।

Exercise schema generated নাম। DATABASE() আর prepared SQL GRANT-REVOKE-তে বসায়। Identifier value placeholder নয়,তাই identifier quote। এখানে শুধু trusted generated নাম।

Untrusted ইনপুট concat করে privilege স্টেটমেন্ট নয়। Value-identifier handling আলাদা,admin SQL narrow interface চাই। App-এ অ্যাকাউন্ট management সাধারণত admin-এর,ordinary user ফিচার নয়।

CREATE USER '<user>'@'<host>' IDENTIFIED BY '<local_secret>';
GRANT <needed_privileges> ON <schema>.<object> TO '<user>'@'<host>';
REVOKE <removed_privileges> ON <schema>.<object> FROM '<user>'@'<host>';
DROP USER '<user>'@'<host>';

তৈরি থেকে সরানো পর্যন্ত grant

CREATE USER-এর পরে current schema টেবিল grant নেই,প্রথম metadata সংখ্যা তা দেখায়। অ্যাকাউন্ট বানানো আর useful রিপোর্ট login করা আলাদা,পারমিশন সচেতন যোগ।

students SELECT grant-এ টেবিল-level authorization। table_privileges current schema-টেবিল SELECT দেখায়। একই scope revoke-এ empty,তবু DROP না হওয়া পর্যন্ত অ্যাকাউন্ট আছে।

SELECT-UPDATE দিয়ে শুধু UPDATE revoke করলে SELECT থাকে। Revoke পুরো reset নয়। আবার টেবিল grant সরানো broader grant override করা deny rule নয়।

Applicable scope আর active role-এর পারমিশন additive। টেবিল SELECT সরিয়েও ডেটাবেস SELECT পড়া দেয়,role-ও পারে। পুরো effective design না দেখে capability গেছে বলবে না।

DEFINER নাম-only ভিউ approved interface দেয়,underlying check owner context-এ। Reader ভিউ SELECT পায়,students direct নয়। Deployment-এ narrow owner,অদরকারি admin নয়।

Fresh exercise-এ admin definition করেছে,এটি production owner recommendation নয়। Caller ভিউ privilege বনাম definer base privilege আলাদা আর alternate route বন্ধ রাখাই শিক্ষা।

UPDATE(hometown)-এর metadata column_privileges-এ,full টেবিল grant নয়। Target অ্যাকাউন্ট-এ actual operation,WHERE-তে পড়া কলাম-সহ test। Grant list একা compatibility proof নয়।

Exact operation-scope দেখো

প্রথমে access নেই,তারপর এক operation দিয়ে revoke,পরে restricted ভিউ। Temporary reader-কে ALL,global বা GRANT OPTION কোনোটিই নয়।

Metadata admin কানেকশন-এ consistent দেখা। Target user-এ login,allowed-denied test-এর বদলি নয়। Deployment review-এ তার কানেকশন-এ approved read আর rejected write যাচাই।

টেবিল access ছাড়া অ্যাকাউন্ট

নতুনটিতে grant নেই,দেখে teaching অ্যাকাউন্ট সরায়।

Student read grant,পরে revoke

প্রথম রিপোর্ট SELECT,দ্বিতীয় empty। Dynamic SQL current exercise schema নেয়,fixed নয়।

Narrow ভিউতে নাম

শুধু public_students SELECT। এখানে owner exercise admin,বাস্তবে narrow owner চাই।

Narrow revoke-এর পরেও broad access

সব authority source দেখো

ডেটাবেস-global grant বা role থাকলে টেবিল revoke-এর পরেও পড়ে। SHOW GRANTS আর role দেখে actual broad source সরাও। General টেবিল-level deny system নয়।

Access এরর-এ ALL ON *.* দিও না। অ্যাকাউন্ট management-write power রিপোর্ট-এর চেয়ে অনেক বেশি। Denied operation,object,effective অ্যাকাউন্ট জেনে সত্যিই দরকারি missing capability দাও।

Context দেখে reconnect

USER()-CURRENT_USER() কানেকশন আর authenticated context আলাদা বোঝায়। Host matching-সেটিং-এ local ধারণা ভুল হতে পারে। Definer object-এ আরও context,তাই relevant জায়গায় দেখো,এক মান universal নয়।

Grant change scope-session অনুযায়ী আলাদা সময়ে লাগতে পারে। Clean test-এ target reconnect। System grant টেবিল হাতে edit স্বাভাবিক workflow নয়;CREATE USER,GRANT,REVOKE-তে routine FLUSH PRIVILEGES লাগে না।

Allowed আর rejected দুই কাজ

App-admin অ্যাকাউন্ট আলাদা। রিপোর্ট reader-এ role না চাইলে write নয়। Controlled delegation না থাকলে GRANT OPTION নয়। Host,পাসওয়ার্ড,lifetime-ও review।

Fresh target কানেকশন-এ actual রিপোর্ট। Approved ভিউ read চলে,sensitive direct read-write না চলে দেখো। Broad grant-role দেখো;narrow example সফল মানেই alternate source নেই নয়।

MySQL8-এ অ্যাকাউন্ট explicit

8.0/8.4-তে GRANT-এর আগে CREATE USER,implicit shortcut নয়। Auth ডিফল্ট release-এ বদলায়,obsolete plugin নির্দেশ যাচাই ছাড়া নয়। Dataset8.0.16,এই admin action-এ যথাযথ ক্ষমতা চাই।

এক grant নয়,effective authority

অ্যাকাউন্ট পরিচয়,auth সেটিং,additive privilege source মিলে। Smallest useful interface,extra access সরিয়ে target কানেকশন-এ যাচাই। পরের functional dependency-তে access থেকে টেবিল-design rule ভাববে।
