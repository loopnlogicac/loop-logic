Give each job only the access it needs

A results clerk may need to read names and marks without changing grades. A shop application may need to create orders without managing server accounts. Separate database accounts let you express those different jobs and reduce the consequences of a mistake in one component.

Authentication checks who is connecting. Authorization checks what that account may do. A successful login does not imply permission to read every table. Keeping these checks separate makes an access-denied error easier to diagnose without handing out unnecessary administrator rights.

The least privilege principle means granting only the actions and data a job actually needs. It applies to operation type, object scope, visible columns, delegation and account lifetime. A read-only reporting account should not receive global administration merely because that makes the first query succeed.

The exercises run as an administrator inside an isolated teaching server. They create a specifically named temporary account, inspect narrow grants and remove it afterward. The sample password exists only for these local exercises. Real application credentials belong in protected runtime secret configuration, with an appropriate rotation process.

An account includes its host

MySQL identifies an account by both user name and host, such as 'report_reader'@'localhost'. Another host part can identify a different account with different credentials and privileges. Do not treat the visible user name alone as the complete identity when diagnosing access.

CREATE USER creates the account and its authentication configuration. It does not automatically grant table access to the database selected in the current connection. GRANT supplies specific privileges, such as SELECT on one view or UPDATE on a chosen column. REVOKE removes a granted privilege; DROP USER removes the account.

Privilege scopes include global, database, table and column levels. A grant on every database is much broader than a grant on students in one schema. Column-level grants can restrict edits such as UPDATE(hometown), but you must also consider read privileges needed by the actual update predicates and expressions.

The current exercise database has a generated name. The examples use DATABASE() and prepared SQL to insert that name into the GRANT or REVOKE statement. Identifiers cannot be supplied through ordinary value placeholders, so the schema name is quoted as an identifier. This code uses only the trusted database name created for the exercise.

Do not build privilege statements by concatenating untrusted user input. Values and identifiers need different handling, and administrative SQL deserves a narrow interface. In an application, account management is usually an administrative responsibility rather than a feature exposed to ordinary end users.

CREATE USER '<user>'@'<host>' IDENTIFIED BY '<local_secret>';
GRANT <needed_privileges> ON <schema>.<object> TO '<user>'@'<host>';
REVOKE <removed_privileges> ON <schema>.<object> FROM '<user>'@'<host>';
DROP USER '<user>'@'<host>';

Trace grants from creation to removal

Immediately after CREATE USER, the account has no table grants in the current schema. The first example counts metadata rows to demonstrate that absence. Creating an account is therefore not the same action as making a reporting login useful; the relevant data permissions must be added deliberately.

Granting SELECT on students creates a table-level authorization for that account. The information_schema.table_privileges report shows SELECT for the current schema and table. After REVOKE SELECT on that same scope, the report becomes empty. The account still exists until DROP USER executes.

The two-operation practice grants SELECT and UPDATE, then revokes UPDATE. SELECT remains. REVOKE is selective: it removes the specified grant rather than resetting the entire account. Conversely, revoking one table-level grant is not a deny rule that overrides all possible broader grants.

MySQL permissions are additive across applicable scopes and active roles. A database-level SELECT can still authorize a read after a table-level SELECT is removed. An active role can also supply access. Inspect the full effective grant design before concluding that a narrow revoke successfully removed the capability.

A name-only view can provide an approved reporting interface. With SQL SECURITY DEFINER, underlying access is checked using the definer context. The reader needs SELECT on the view but need not receive direct SELECT on students. In a real deployment, choose a narrowly privileged view owner instead of an unnecessarily powerful administrator.

The example definition is created by the exercise administrator so it can be executed in the fresh database. That convenience is not a recommended production owner policy. The security lesson is the separation between a caller's view privilege and the definer's underlying privileges, plus the need to close alternate base-table access.

Column-level UPDATE(hometown) authorizes an even narrower kind of edit. Its metadata appears in column_privileges rather than as a complete table UPDATE grant. When designing a real statement, test the whole operation under the target account, including any columns read in WHERE. An isolated grant listing does not prove application compatibility.

Inspect exact operations and scopes

The first account receives no table access. The next receives one table operation and loses it again. The view example grants a read on a restricted interface. None of these exercises grants ALL, global access or GRANT OPTION to the temporary reader.

The metadata queries run through the administrative connection so you can inspect the grants consistently. They are not a substitute for testing login and allowed or denied statements as the target user. A complete deployment review should use that user's connection and verify both successful reads and rejected writes.

Broad access can survive a narrow revoke

Inspect every source of authority

A user may still read students after a table-level SELECT revoke because a broader database or global privilege remains. Roles can supply another source. Review SHOW GRANTS and the relevant role configuration, then remove the actual broad source if policy requires it. MySQL privileges do not work as a general table-level deny system.

Do not respond to an access error by granting ALL ON *.*. That can add account-management and data-changing powers far beyond one failed report. Identify the denied operation, object and effective account first. Grant the narrow missing capability only when the job should genuinely have it.

Verify account context and reconnect

USER() and CURRENT_USER() can help distinguish the connection identity from the authenticated account context. Host matching and server configuration can make assumptions about local connections misleading. Inside definer objects, security context adds another distinction, so inspect these functions in the relevant calling context rather than reading one value as a universal identity.

Grant changes can take effect at different times depending on privilege scope and active sessions. For a clean verification, reconnect as the target account after the administrative change. Directly editing mysql system grant tables is not the normal management workflow. CREATE USER, GRANT and REVOKE maintain privileges without a routine FLUSH PRIVILEGES step.

Verify allowed work and rejected work

Maintain separate application and administrator accounts. Give report readers no data-changing privileges unless their role requires them. Avoid GRANT OPTION unless controlled delegation is part of the job. Review host restrictions, password management and account removal alongside object grants.

Test the actual report using a fresh connection as the intended account. Confirm that approved view reads succeed and direct sensitive-table reads or writes fail as designed. Also inspect broad grants and active roles. A successful narrow example cannot prove that no alternate authorization source exists.

Account management is explicit in MySQL 8

MySQL 8.0 and 8.4 use explicit CREATE USER before GRANT; GRANT is not an implicit account-creation shortcut. Authentication defaults differ across releases, so avoid copying obsolete plugin instructions without checking the server. The dataset baseline remains 8.0.16, while the account-management actions here require suitable administrative privileges.

Review effective authority, not only one grant

An account has an identity, authentication settings and additive privilege sources. Grant the smallest useful interface, remove unnecessary access and verify through a target-user connection.
