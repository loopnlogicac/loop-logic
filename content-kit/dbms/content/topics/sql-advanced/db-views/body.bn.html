দরকারি কোয়েরির স্থির নাম

Librarian বারবার member ID ও নাম চান, email নয়। একই projection না লিখে নাম দিয়ে টেবিলের মতো কোয়েরি করতে পারো। ভিউ এই interface দেয়; মূল member রেকর্ড নিজের টেবিলেই থাকে।

ভিউ stored কোয়েরি definition। সাধারণ MySQL ভিউ ফলের private snapshot রাখে না। কোয়েরি করলে definition ধরে ডেটা আনে। Base টেবিলে member নাম বদলালে পরের ভিউ কোয়েরি-তেও দেখা যেতে পারে।

ভিউ রিপোর্ট সহজ ও sensitive কলাম আলাদা করতে পারে। নিয়ন্ত্রিত আপডেট পথও দিতে পারে। কিন্তু readable কোয়েরি সবসময় updatable নয়; ভিউ-তে কলাম লুকালেই অন্য পথের grant বাতিল হয় না।

একই রেকর্ড দেখার নাম দেওয়া জানালা ভাবো। কী দেখায় বদলালে দ্বিতীয় শিক্ষার্থী রো set হয় না। Visible কলাম, population, operation ও security context নির্দিষ্ট করো।

Interface স্পষ্ট define

CREATE VIEW নামের সঙ্গে SELECT definition জোড়ে। Explicit কলাম ও অর্থপূর্ণ alias নাও। student_directory-তে student_id,নাম,বিভাগ রেখে email বাদ দিতে পারো। Consumer তখন পুরো students টেবিলের বদলে উদ্দেশ্যের shape পায়।

Controlled security interface দেখানো ছাড়া উদাহরণে SQL SECURITY INVOKER। এটি underlying access-এ caller privilege দেখে। DEFINER ভিউ owner-এর privilege নেয়। কোনো mode-এই ভিউ access-এর নিজের grant বাদ যায় না।

Simple filtered ভিউ-তে WITH CHECK OPTION দিলে ওই পথের write রো-কে ফিল্টার-এর ভেতর রাখবে। CSE-only ভিউ-তে বিভাগ 1 থেকে 2 করলে রো বেরোত; CHECK OPTION ওই আপডেট আটকায়।

CASCADED ডিফল্ট; underlying ভিউতের applicable শর্ত-ও দেখে। LOCAL নিজের শর্ত দেখে, underlying declared check option-ও মানে। স্তরে ভিউ করলে প্রতিটি definition দেখো; একটি visible ফিল্টার সব write path রক্ষা করে ধরে নিও না।

CREATE SQL SECURITY INVOKER VIEW <view_name> AS
SELECT <visible_columns> FROM <base_table>
WHERE <visible_population>
WITH CASCADED CHECK OPTION;

Live ফল আর আপডেট mapping আলাদা

Simple projection-এর প্রতি রো সরাসরি base রো-তে মেলে। ভিউ দিয়ে student_name আপডেট হলে students-এর একই কলাম বদলায়। Primary কী visible রাখলে target পরিষ্কার, কিন্তু তা একাই updatability নিশ্চিত নয়।

Aggregate-এ mapping ভাঙে। Enrollment মোট তিন registration বোঝাতে পারে; সংখ্যা চার লিখলে কোন নতুন registration চাই জানা যায় না। তাই GROUP BY ও aggregate ভিউ MySQL-এ non-updatable। DISTINCT-সহ আরও restriction আছে।

MySQL rule অনুযায়ী কিছু joined ভিউ-তে সীমিত আপডেট চলে; সব জয়েন writable নয়। অনুমোদিত base টেবিলে mapping ঠিক চাই। শুরুতে complex multi-টেবিল পথের চেয়ে স্পষ্ট single-টেবিল ভিউ review সহজ।

Updatable মানেই সব ইনসার্ট সম্ভব নয়। Required base কলাম ডিফল্ট ছাড়া বাদ থাকলে রো পূর্ণ হয় না। ইনসার্ট interface দেওয়ার আগে NOT NULL, ডিফল্ট, generated কলাম ও কনস্ট্রেইন্ট দেখো।

Available-products-এ live evaluation দেখো। Stock zero হলে পণ্য 1 হারায়; rollback-এ ফেরে। REFRESH লাগে না, কারণ ordinary ভিউ আলাদা ফল টেবিল নয়, কোয়েরি definition রাখে।

CHECK OPTION base টেবিলের সব change আটকায় না। অনুমতিপ্রাপ্ত direct আপডেট শিক্ষার্থী-কে CSE থেকে সরাতে পারে। Workflow boundary চাইলে inappropriate direct write grant সরাতে হবে।

Direct-টেবিল route বন্ধ

Clerk নাম-only ভিউতের সঙ্গে students-এও SELECT পেলে email এখনও পড়তে পারে। ভিউ সুবিধার exposure কমালেও broad grant boundary ভাঙে। টেবিল,ভিউ,ডেটাবেস ও active role জুড়ে effective পারমিশন দেখো।

Definer ভিউ direct base grant ছাড়াই approved ডেটা দেখাতে পারে। Owner-এর শুধু দরকারি base privilege চাই। অতিরিক্ত শক্ত owner ভুল definition-এর ক্ষতি বাড়ায়। Ownership ও অ্যাকাউন্ট removal পরিকল্পনা করো; missing definer interface ভাঙতে পারে।

কোয়েরি-কে history ভেবো না

ভিউতের ভেতরের ORDER BY-কে consumer-এর অর্ডার ভাববে না। Outer কোয়েরি ও optimizer বদলাতে পারে। Display sequence চাইলে final SELECT-এ ORDER BY। ভিউ relation বোঝায়, printed রিপোর্ট layout নয়।

ভিউ পুরোনো semester জমিয়ে রাখে ভাবাও ভুল। তারিখ ফিল্টার বর্তমান qualifying রো বাছে, আগের মান copy নয়। History চাইলে যথাযথ snapshot/history স্টোরেজ করো। কোয়েরির নাম old_results দিলেই history হয় না।

Definition interface contract

Public রিপোর্ট-এ stable নাম ও explicit কলাম নাও। Creation-এর সময় star expand হয়; পরে টেবিল change expectation গুলিয়ে দিতে পারে। Explicit projection exposure ও migration review পরিষ্কার করে।

Maintenance বোঝার সময় IS_UPDATABLE metadata দেখো, তারপর actual operation test করো। Insertability required base value ও কনস্ট্রেইন্ট-ও মানে। DROP VIEW definition সরায়, base রো রাখে; DELETE থেকে আলাদা।

MySQL security-আপডেট rule

এই ফিচার MySQL 8.0/8.4-এ আছে; shared CHECK 8.0.16 চায়। Ordinary MySQL ভিউ native materialized ভিউ নয়। Convenience, ট্রানজ্যাকশন visibility, আপডেট পারমিশন ও owner আলাদা বিষয়, ফল টেবিলের মতো হলেও।

কোয়েরির নাম আর authority দেখো

ভালো ভিউ-তে explicit projection, clear population ও আপডেট policy থাকে। SQL SECURITY-এর সঙ্গে boundary মানানো grant মেলাও। Logical ফল না বদলে access দ্রুত করতে ইনডেক্স পড়ো।
