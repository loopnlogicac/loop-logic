নম্বর বদলালেই office একটি রেকর্ড চায়। প্রতিটি screen-কে আলাদা ইনসার্ট মনে রাখতে বললে ভুল হয়। Trigger টেবিল operation-এর সঙ্গে প্রতিক্রিয়া জুড়ে দেয়; অনুমতিপ্রাপ্ত direct আপডেট-এও একই আচরণ চলে।

Trigger টেবিল event ও timing-এর stored প্রোগ্রাম। INSERT,UPDATE,DELETE-এর প্রতি affected রো-তে MySQL চালায়। CALL লাগে না; ডেটা-change স্টেটমেন্ট নিজে চালু করে।

সীমিত validation,normalization ও transactional audit-এ উপকারী। তবে শুধু original UPDATE পড়লে effect বোঝা যায় না। Trigger ছোট রাখো, dependency বোঝাও। অনেক hidden action-এ diagnosis কঠিন।

উদাহরণে inserted member নাম trim, mark change log, loan ইনসার্ট-ডিলিট history ও rollback আছে। Audit টেবিল সাধারণ InnoDB, তাই মূল change-এর একই ট্রানজ্যাকশন outcome মানে।

Event ও timing বাছো

CREATE TRIGGER-এ নাম,timing,event,টেবিল,FOR EACH ROW body। BEFORE রো stored হওয়ার আগে, AFTER operation সফল হওয়ার পরে। তিন event-এ দুই timing, মোট ছয় combination।

INSERT-এ proposed NEW, OLD নেই। DELETE-এ OLD, replacement NEW নেই। UPDATE-এ আগের OLD ও প্রস্তাবিত NEW দুটো। Trigger-এ এই prefix দিয়ে কলাম নাও।

OLD read-only। BEFORE INSERT/UPDATE-এ উপযুক্ত writable NEW কলাম বদলানো যায়; AFTER-এ নয়। Generated কলামের extra restriction আছে। Grade expression-কে কাজ করতে দাও, হাতে assign করবে না।

এক স্টেটমেন্ট body হতে পারে। একাধিক হলে BEGIN-END, তখন ক্লায়েন্ট-এর temporary DELIMITER লাগে procedure-এর মতো। এটি submission নিয়ন্ত্রণ করে, সার্ভার event timing নয়।

Mark audit-এ শিক্ষার্থী কী,সেকশন কী,old,new mark। Auto-increment audit_id stable display sequence, timestamp বা gapless counter নয়। Rollback-এ numbering gap হতে পারে।

Multi-রো স্টেটমেন্ট-এ প্রতি affected রো-তে আলাদা trigger। এগারো mark এক বাড়ালে এগারো audit হতে পারে। প্রতিবার নিজের OLD-NEW। MySQL-এ পুরো set একবারে পাওয়া স্টেটমেন্ট-level trigger নেই।

এক ফল আপডেট করে rollback করলে audit ইনসার্ট-ও rollback। আগে সংখ্যা এক, পরে zero; পুরোনো mark ফেরে। মূল change ও log দুটো transactional।

Trigger এরর স্টেটমেন্ট ব্যর্থ করতে পারে। InnoDB ওই স্টেটমেন্ট ও trigger effect rollback করে। চারপাশের ট্রানজ্যাকশন-এর সব আগের সফল স্টেটমেন্ট সবসময় ফেরে না। পুরো কাজের এরর policy চাই।

Audit coverage-এর সীমা জানো

Cascade আর TRUNCATE আলাদা

MySQL foreign-কী cascade child trigger চালায় না। Student ডিলিট-এ results cascade হলে results AFTER DELETE ওই child deletion লেখে না। Complete history দাবিতে বড় gap। Parent audit বা explicit deletion workflow-তে দরকারি তথ্য রাখো।

TRUNCATE-ও রো-প্রতি DELETE trigger চালায় না। এটি implicit-commit schema operation। প্রতি removed রো রেকর্ড চাইলে access নিয়ন্ত্রণ ও আলাদা administrative audit route বানাও। রো trigger একা complete security audit নয়।

Transactional log autonomous নয়

Trigger COMMIT/ROLLBACK দিয়ে স্বাধীন ট্রানজ্যাকশন বানাতে পারে না। সাধারণ InnoDB audit caller-এর ট্রানজ্যাকশন-এ বাঁধা। Rolled-back attempt-এর durable evidence চাইলে স্পষ্ট trust boundary-সহ external বা সার্ভার audit mechanism নাও।

নিজের trigger থেকে একই টেবিল আবার আপডেট করে NEW assignment-এর বদলি করবে না। Triggering স্টেটমেন্ট-এ ব্যবহৃত টেবিল modify-তে MySQL restriction আছে। Writable normalization-এ BEFORE ও SET NEW নাও। জটিল workflow recursive side effect না করে স্পষ্ট design করো।

Audit ownership-ও জরুরি। Edit-ডিলিট ক্ষমতা থাকলে ordinary history বদলানো যায়। Trust model অনুযায়ী grant, trigger definition ও definer রক্ষা করো। Automatic INSERT টেবিল-কে tamper-proof করে না।

Automatic effect খুঁজে পাওয়া সহজ করো

Event ও purpose দিয়ে trigger নাম দাও, body focused রাখো। UPDATE review-তে associated trigger ও target টেবিল দেখো। Hidden write lock,পারফরম্যান্স,failure analysis-এ ধরো। রো-প্রতি extra কোয়েরি ছোট operation-ও ব্যয়বহুল করে।

Real change,no-op,multi-রো,rollback test করো। Cascade ও TRUNCATE-এর মতো bypass-ও দেখো। এই case-ই audit coverage ঠিক করে। আশ্বাসদায়ক নাম নয়, observed scope অনুযায়ী history দাবি করো।

Audit ফিল্ড-এর অর্থ পরিষ্কার চাই। Timestamp দিলে স্টেটমেন্ট time,ট্রানজ্যাকশন time নাকি অন্য event ঠিক করো। এখানে explicit transition ও ID আছে, তাই wall clock-নির্ভর আউটপুট নয়।
