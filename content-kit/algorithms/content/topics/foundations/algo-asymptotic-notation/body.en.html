Introduction

A queue of students grows from ten people to ten thousand. A method that checks every pair grows much faster than a method that checks each person once. Asymptotic analysis compares this long-term growth. You keep the input size n visible and set aside machine-dependent timing details.

Think of a growth bound as a fence around a function, after some starting point. An upper fence says the work cannot grow faster than a chosen multiple. A lower fence says it cannot grow slower. Neither fence by itself says whether you are studying the best input or the worst input.

Pseudocode and conventions

choose the input-size parameter n
define a nonnegative cost f(n)
choose a positive comparison function g(n)
state the required inequality and its quantifiers
give constants and a threshold; prove the inequality

Asymptotic Notation step by step

Define upper, lower and tight bounds

Let f(n) be a nonnegative cost and let g(n) be positive for sufficiently large integer n. We write f(n) in O(g(n)) if positive constants c and n0 exist such that f(n) ≤ c g(n) for every n ≥ n0. The letter O describes an upper bound. A loose bound is still a bound: n is in O(n²).

We write f(n) in Ω(g(n)) if positive c and n0 exist with f(n) ≥ c g(n) for all n ≥ n0. This is a lower bound. Finally, f(n) is in Θ(g(n)) if positive c1, c2 and n0 give c1 g(n) ≤ f(n) ≤ c2 g(n) beyond n0. A tight bound combines both fences around the same growth rate.

For f(n) = 3n + 7, take n0 = 1. Since 7 ≤ 7n there, 3n + 7 ≤ 10n, establishing O(n). Also 3n + 7 ≥ 3n, establishing Ω(n). Together these witnesses prove Θ(n). You must provide constants that work for the entire tail, rather than only for one chosen input size.

Define strictly smaller and strictly larger growth

Little-o makes a stronger claim than big-O. Formally f(n) is in o(g(n)) when, for every c greater than zero, some n0 exists such that 0 ≤ f(n) < c g(n) for all n ≥ n0. The chosen threshold may depend on c. No single positive fraction of g eventually remains below f.

Little-omega reverses this strict comparison. We write f(n) in ω(g(n)) when every positive c has some n0 with f(n) > c g(n) for all n ≥ n0. For positive g, the ratio f/g tending to zero proves little-o; a ratio tending to infinity proves little-omega. A constant nonzero ratio proves neither strict relation.

Thus n is in o(n²), because n/n² = 1/n tends to zero. Conversely n² is in ω(n). However, 3n is in Θ(n), not o(n) or ω(n). A common trap is to read the small symbol as a more precise spelling of the large one. Their quantifiers are different: big-O needs one constant, while little-o must accommodate every positive constant.

Put common functions in order

For sufficiently large n, the usual ladder is 1, log n, n, n log n, n², n³, 2^n, then n!. Each step eventually dominates the one before it. Small values can mislead you: a complicated constant factor may delay the crossover. Asymptotic notation does not promise that the faster-growing method loses on every tiny input.

Changing the base of a logarithm multiplies it by a constant: log_b n = log_a n / log_a b for fixed valid bases. Therefore base two and base ten give the same Θ(log n) class. The base still matters when counting the exact number of halvings. Do not discard it when the question asks for an exact count.

Exponential growth differs from a large polynomial. Doubling n multiplies n³ by eight, but changes 2^n to the square of its previous value. Factorial growth is even faster. These comparisons explain why an algorithm that examines all subsets may stop being practical while a cubic method still handles moderate inputs.

Choose the function before bounding it

For a linear search, the best-case comparison count is 1 on a nonempty array with an immediate match. The worst-case count is n when the match is last or absent. Both functions have upper and lower bounds. Calling Ω the best case confuses the kind of input with the direction of an inequality.

Suppose a measured program takes 5n² + 2n + 9 counted operations. For n ≥ 1, it is at least 5n² and at most 16n². You have a tight quadratic bound with explicit constants. Lower-order terms matter for exact counts, but do not change the eventual growth class. Write the exact function first if the question provides enough information.

When combining sequential phases, add their costs. A scan followed by a quadratic comparison phase costs Θ(n + n²), which is Θ(n²). For independent nested loops, multiply iteration counts when each pair executes the body. For dependent loops, form a sum first; a triangular loop provides the classic example.

Check a strict-bound claim with a ratio

To show n log n is o(n²), divide by n². The ratio becomes log n divided by n, which tends to zero. This proves more than the loose upper bound O(n²). In contrast, dividing 5n² + 2n + 9 by n² tends to five, so that expression is Theta(n²) and is not o(n²). A positive finite limiting ratio describes matching growth rather than strictly smaller growth.

Why the method is correct

For an upper-bound proof, begin with arbitrary n beyond your threshold. Replace smaller terms by multiples of the proposed dominant term. For 5n² + 2n + 9, use n ≤ n² and 1 ≤ n² when n ≥ 1. This gives the upper coefficient 16. Dropping the positive smaller terms gives the lower coefficient 5.

To disprove O(n) for n², assume a fixed positive c could work. Choose an integer n larger than both c and the proposed n0. Then n² > cn, contradicting the required upper inequality. This argument defeats every possible constant rather than one unlucky candidate.

Time and space reasoning

The three programs count a scan, a triangular loop and repeated halving. Their main body counts are 8, 36 and 4 for the chosen sizes. In general these patterns grow as Θ(n), Θ(n²) and Θ(log n). The counts are mathematical operation counts, not milliseconds. Each counter uses constant auxiliary space, so different time classes need not imply different space classes.

Common mistakes

Writing an equality without its meaning

The common notation f = O(g) means membership in a class of bounded functions. It does not make O(g) a single numerical expression you can subtract freely.

Using a threshold that depends on n

A witness such as c = n does not prove an asymptotic bound. The constants must stay fixed as n grows.

Dropping logarithms from a product

n log n grows faster than n. The logarithmic factor is not a constant, even if it grows slowly.

C17 details

C17 optimisers may remove work whose result is unused. These programs print their counters, but the counters describe source-level operations rather than a promise about executed machine instructions.
