Try a choice, then return

Imagine filling a lab timetable one slot at a time. A choice that looks reasonable now may block the last course. You need a way to return to an earlier slot and try something else. Backtracking does exactly that: make a choice, explore its consequences, then undo the choice.

A state-space tree is a picture of these decisions. The root has no choices yet. An edge adds one choice. A node holds a partial candidate, and a leaf represents a complete candidate. You normally explore this tree with depth-first recursion rather than storing the entire tree.

Consider a length-four binary string with exactly two ones. You may put zero or one at every position. There are sixteen complete strings before filtering. Only six satisfy the requirement. This small problem lets you see the difference between generating candidates and rejecting impossible prefixes.

Backtracking is useful when choices interact and you need a valid arrangement or every arrangement. It does not promise fast execution for large inputs. Before using it, estimate the decision depth and branching factor. A small search can be clearer than a complicated table.

Describe the recursive contract

Our function explore(pos, used) assumes positions before pos already contain a chosen prefix. The value used counts its ones. Positions from pos onward remain undecided. The global n and ones stay fixed during the search.

At each call, first decide whether any completion is possible. Then handle a complete prefix. Otherwise, choose the next bit, recurse with one fewer undecided position, and restore that slot before trying another bit. Passing used by value means the child's counter cannot change the parent's counter.

The array slot is restored explicitly so you can see the undo step. A freshly overwritten slot would also work here, but that shortcut does not generalise to shared sets, occupancy flags or running totals. Write down every piece of mutable state before relying on overwriting.

explore(pos, used):
    if used > ones: return
    if used + n - pos < ones: return
    if pos == n: report path; return
    for bit in [0, 1]:
        path[pos] = bit
        explore(pos + 1, used + bit)
        path[pos] = 0

Reject a prefix for a reason

The first pruning test rejects too many ones. If used is already three but the requirement is two, adding more bits cannot help. The second test checks whether enough positions remain. With one open slot and zero ones so far, a requirement of two is unreachable.

These are proofs about every continuation of a prefix. They are stronger than saying a choice seems unhelpful. A guess-based rejection might remove the only answer. Always explain why no allowed completion can repair the state.

For n=4 and ones=2, try bits in the order zero then one. The first valid leaf is 0011. After printing it, return to its parent, undo the last bit and continue. The output order is lexicographic because every zero-prefixed subtree finishes before its corresponding one-prefixed subtree.

Keep siblings independent

The invariant is that the chosen prefix contains exactly used ones when a call starts. Choosing bit b extends the prefix by one and changes that count to used+b. Thus the child receives a truthful state. Returning and undoing restores the parent's prefix before a sibling starts.

For completeness, take any valid full string. Its prefixes never exceed the required ones, and each has enough remaining positions to finish. Neither pruning test rejects them. The search tries both bits at every surviving position, so it eventually follows that whole string.

For uniqueness, two different paths first differ at some bit. They cannot produce the same full binary string. A complete surviving prefix has exactly the required count, so every reported string is valid. These arguments establish validity, completeness and no duplicate reports separately.

Depth is smaller than the whole tree

Without pruning, depth n gives 2^n leaves and 2^(n+1)-1 nodes. Visiting nodes alone takes O(2^n) time. Printing each length-n answer adds O(n) per answer, so O(n*2^n) is a safe overall bound.

The active recursion stack has only one root-to-leaf path, not every node. It needs O(n) space together with the path array. If you store every answer instead of printing immediately, retained output can require O(n*2^n) memory.

Pruning often makes individual instances much smaller. It does not turn every combinatorial search into a polynomial algorithm. Counting required-one strings can also use a binomial formula, but that formula does not list their actual contents.

First answer, all answers, and no answers

Length zero has one empty candidate. A zero-one requirement yields the all-zero string; a requirement equal to n yields the all-one string. The program rejects a requirement outside zero through n instead of searching an impossible input.

If the task asks whether any answer exists, return a Boolean success flag at the first valid leaf. If it asks for all answers or their count, continue after every valid leaf. Mixing these stopping rules can silently undercount a correct search.

An early return can leave damage

A common bug sets a shared flag and returns before clearing it. Later siblings then inherit a choice they never made. Put cleanup on every unsuccessful return path, or design the state so the child owns a separate copy.

Another mistake tests the final condition at a partial prefix and treats it as complete. A prefix with two ones may still need more zero positions. Report only after every required position has a decision.

Do not draw every rejected subtree and claim the algorithm explored it. Pruning means those descendants were never visited. Distinguish visited nodes from logically possible candidates when explaining a speedup.

Name the state before coding

Write the recursive meaning in one sentence. Identify immutable parameters, copied counters and shared mutable containers. Mark the base case and the cleanup point before adding pruning.

For a new search, temporarily disable the prune on tiny inputs. Compare its answer set with the pruned version. Equal results are useful evidence; the pruning proof explains why equality continues beyond those examples.

Bound the recursion in C17

The demonstration allows at most twelve bit positions, so its path array and recursion depth are bounded. The tree-count example allows depth twenty, safely within its unsigned long long counter. General inputs need an overflow policy and a practical stack limit. C17 adds no automatic recursion-depth protection.
