Use a fingerprint to filter windows

Suppose you compare many same-length text windows with a pattern. Most windows are different, so a short numeric fingerprint can reject them quickly. Rabin-Karp computes a rolling hash and performs full character checks only when the fingerprint agrees.

A hash maps many strings into a limited set of numbers. Equal strings always have equal hashes under the same formula. Different strings can also have equal hashes; that event is a collision. A hash hit is therefore a candidate, not proof of an occurrence.

Our verified version compares characters after every hash equality. This makes its reported answers exact even with collisions. It can still be slow when there are many candidates, so correctness and expected speed need separate explanations.

The teaching hash treats lowercase letters as digits a=0 through z=25, uses base twenty-six, and reduces modulo 101. The small modulus makes arithmetic easy to follow and collisions easy to demonstrate. It is not a recommended defence against adversarial input.

Give every digit a place value

For a length-m window with digit values d0 through d(m-1), use the polynomial hash d0*base^(m-1)+d1*base^(m-2)+...+d(m-1), reduced modulo q. Left-to-right construction repeatedly multiplies the accumulated hash by base and adds the next digit.

Precompute high=base^(m-1) mod q. The outgoing first digit contributes outgoing*high. Subtract it, multiply by base to shift the remaining digits left, and add the incoming last digit. Each arithmetic stage reduces modulo q.

C remainder can be negative. Our code subtracts an already-reduced outgoing contribution from a hash in zero through q-1, then adds q before reducing. This bounded expression needs only one addition of q to become nonnegative.

The main program checks m>n before building the initial text-window hash. A longer pattern cannot fit, and reading its length from the shorter text would access invalid positions. Handling that case early protects both the algorithm and the array.

if m > n: report no matches; stop
high = base^(m - 1) mod q
hash pattern and first m text characters
for start = 0 to n - m:
    if window == wanted:
        compare all m characters; report only if equal
    if another window exists:
        remove outgoing digit times high, modulo q
        window = (window * base + incoming digit) mod q

Roll rather than rebuild

For pattern aba, digit values are zero, one and zero. Its integer polynomial value is 26, so its hash is 26 modulo 101. The first window aba agrees and passes verification.

The next window bab has polynomial value 677 and hash 71. Starting from 26, remove the leading a contribution zero, multiply by 26 and append b=1. The modular result is 71. Rebuilding all three positions is unnecessary.

Moving from bab back to aba removes b times high. Here high=26^2 mod 101=70. Subtracting seventy from seventy-one leaves one; shifting and appending a gives twenty-six again. The second true occurrence starts at two.

A collision example uses aa and dx. Their digit polynomials are zero and 3*26+23=101. Both reduce to zero. When searching for aa inside dx, the hash test succeeds but the first character comparison fails. The candidate is a spurious hit and must not increase the match count.

Follow hashes and verification separately

The rolling value and the match count describe different events. A hash mismatch rejects a window without a character scan. A hash equality starts verification, which may accept or reject the candidate.

Hash updates preserve the polynomial

The hash invariant states that window equals the polynomial of text[start..start+m), reduced modulo q. Initial construction establishes it for start zero. Removing the highest-power outgoing digit leaves the suffix polynomial. Multiplication by base shifts its exponents up, and appending the incoming digit constructs the next window. Modular arithmetic preserves each equality of residues.

If a text window equals the pattern, their digit sequences and polynomial values agree, so their hashes agree. The hash filter therefore never rejects a true occurrence. When hashes agree, direct comparison accepts exactly the equal windows. Together those facts prove both completeness and soundness of the reported matches.

Collisions do not invalidate the invariant. They mean the polynomial map is many-to-one. The exactness of this version comes from verification, not from assuming a sufficiently large prime eliminates all collisions.

A double hash makes accidental collisions less likely under suitable assumptions, but two fixed hashes still do not prove equality for arbitrary strings. If an application omits verification, it must accept a probabilistic or collision-dependent correctness policy. That is a different design from the exact matcher shown here.

Count candidate verification work

Constructing the pattern hash, first window and highest power takes O(m). Rolling through legal starts takes O(n). If H windows have equal hashes, verifying them adds up to O(H*m). A precise bound is therefore O(n+m+H*m).

Under a suitable randomised hash choice and a nonadversarial model, spurious hits can be rare, giving near-linear expected filtering work. Real matches still need verification in this implementation. A text of repeated a letters and a pattern of repeated a letters creates many true hits, each scanning m positions.

Thus verified Rabin-Karp has O(nm) worst-case time when m<=n. A fixed small modulus does not supply a universal near-linear guarantee. Always state the hash assumptions behind an expected-time claim.

The working hash values and counters require O(1) auxiliary space beyond input strings. Retaining all match positions adds O(z) output storage. The examples print positions immediately. Their fixed buffers are bounded teaching storage rather than a different mathematical space claim.

For matching many patterns of the same length, hash buckets can filter against several candidates together. Every equal-hash candidate still needs verification. Different pattern lengths require separate window lengths or another indexing strategy; one rolling value cannot represent every length at once.

A window exists only when it fits

A one-character pattern has high=1. Rolling removes that sole old digit before appending the new one, which is still the same formula. Equal text and pattern lengths yield exactly one candidate window.

If m>n, the main program prints zero hits and zero matches. Empty patterns are outside the token interface; a boundary-match policy would need handling before computing m-1.

Leading a digits contribute zero. This can make different-length strings share a polynomial value even without modular reduction. Our comparison always uses equal-length windows, so length remains part of the matching context rather than being inferred from the hash.

Embedded zero bytes and spaces are also outside these lowercase-token inputs. A binary-data search would pass explicit lengths and compare bytes directly. C string termination is an input representation choice, not a property of rolling hashes.

A hash hit must not increment the answer alone

Counting every equal hash as a match fails immediately on dx versus aa. Increase the hit counter at hash equality, but increase the occurrence counter only after all pattern bytes agree.

Using base^m instead of base^(m-1) subtracts the wrong outgoing contribution. Write a two-character window by hand to see that its first digit is weighted by one power of base.

Applying the final roll after the last legal window can read text[n] as if it were a new data character, or go further in a careless implementation. Guard the update with start+m<n, which means a genuine incoming byte exists.

Allowing large bases and moduli in int can overflow before the remainder reduces the result. Taking modulo after an overflowing multiplication does not repair undefined signed arithmetic. Choose a wider type or a safe modular multiplication routine and prove its bounds.

Keep hash conventions visible

Record the alphabet mapping, base, modulus and window length beside any trace. Compare reported starts with the naive implementation on repeated strings and deliberately colliding strings.

If you choose randomised hash parameters in production, separate that engineering choice from deterministic examples. For a classroom demonstration, fixed parameters make traces reproducible. The verifier preserves exact answers even when those parameters collide.

Small modular products fit C17 int

With base twenty-six, modulus 101 and digits at most twenty-five, each shown product is only a few thousand. The code reduces outgoing*high before subtraction, so one added modulus suffices. These particular bounds justify int arithmetic. Wider general parameters need a fresh overflow analysis.

Filter quickly, verify exactly

Rabin-Karp rolls a polynomial fingerprint across text windows. Hash disagreement proves inequality, while hash agreement only invites a direct check. Verification preserves exact answers; the number of candidate checks determines whether the run is near-linear or quadratic.
