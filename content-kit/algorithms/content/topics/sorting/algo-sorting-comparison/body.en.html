Introduction

You would not carry one paper and a thousand papers with the same plan. Sorting methods also suit different workloads. A nearly ordered short array, a strict memory limit, a bounded mark range, and a need to preserve tie order can each point to a different choice.

Choosing an algorithm means matching its guarantees to your contract. Start with the number of records, key representation, available workspace and stability requirement. Then compare the relevant time costs. A single slogan such as fastest sort hides the assumptions that make a method useful.

Pseudocode and conventions

return (x > y) - (x < y)

Choosing a Sorting Algorithm step by step

Read a comparison table carefully

Best, average and worst time describe different input or probability assumptions. For bubble sort, the listed linear best case assumes an early-exit flag. For insertion sort, it assumes already ascending input. Selection sort still scans every suffix regardless of order. Merge sort here always divides and merges, without a boundary-skip optimisation.

Quick sort's expected n log n statement assumes random pivot ranks for distinct keys. Final-element deterministic pivots can have quadratic time on ascending input. Heap sort instead offers a worst-case n log n upper guarantee. The names alone do not tell you whether an implementation has changed pivot selection, duplicate handling or recursion strategy.

Space entries refer to auxiliary memory beyond the input. Merge and stable counting sorts use output buffers. Iterative heap sort uses a few variables. The simple recursive quick sort can need a linear stack in its worst case, even though partition itself uses constant storage. Under our strict constant-workspace convention, that recursive version is not guaranteed in-place.

Stability depends on record movement

Suppose you first order student records by roll number, then order them by mark. A stable mark sort retains increasing rolls within equal marks. An unstable mark sort can scramble that useful earlier order. If the contract specifies only ascending marks, both outputs may be correct; if it requires roll tie order, only the stable behaviour is sufficient.

A numeric output with repeated 3 values cannot demonstrate which equal record came first. Attach labels or inspect a second record field. Bubble and insertion sorts preserve ties with strict movement tests; merge sort chooses left on equality. Standard selection, quick and heap sorts allow distant exchanges that can cross equal records.

You can make a total ordering by comparing mark first and original position second. This gives deterministic tie order even with an unstable underlying sort. However, the extra position field and comparison rule become part of the representation. Do not claim the library algorithm itself became stable.

Why comparisons need n log n in the worst case

For n distinct keys, there are n! possible input orders. A comparison-based sorter must learn enough information to distinguish them. Represent its decisions as a binary tree when each comparison has two possible outcomes for distinct keys. A leaf corresponds to one ordering outcome that the algorithm can correctly identify.

A binary tree of height h has at most 2^h leaves. Therefore a correct comparison sort requires 2^h ≥ n!, giving h ≥ log2(n!). For sufficiently large n, at least half the factors in n! are at least n/2, so log2(n!) ≥ (n/2)log2(n/2). This proves an Ω(n log n) worst-case comparison lower bound.

The bound concerns arbitrary distinct-key permutations and comparison-only information. It does not say every input needs n log n comparisons. An already ordered input can be verified in linear work by an adaptive method. It also does not cover counting or radix operations that use a structured bounded representation directly.

The decision tree argument is about the worst path, not measured seconds on a specific processor. A comparison may itself be expensive if it examines long strings or several record fields. When key comparison cost is nonconstant, multiply or otherwise include that cost rather than treating it as one machine instruction.

Use the C library qsort contract

The function qsort is declared in stdlib.h. Pass the base address, number of elements, element size, and a comparator function. The comparator receives pointers to two elements as const void pointers. Convert each to the correct element-pointer type and inspect its value without modifying either element.

Return a negative integer when the first key belongs earlier, zero when they compare equal, and a positive integer when it belongs later. The safe integer pattern is (x > y) - (x < y). Returning x - y can overflow for extreme signed integers, producing undefined behaviour or the wrong ordering sign.

Use sizeof a[0] for element size when a is the actual element array in the calling scope. Do not use sizeof a pointer as the record size. For a structure, cast to the structure type and compare its fields. All comparisons must agree with one consistent ordering; a comparator that changes its mind can invalidate the sort's contract.

The C standard does not require qsort to use quick sort, promise stability, or specify a universal asymptotic complexity. Its name is historical. A particular library can use another algorithm internally. When stability or strict worst-case resource guarantees are essential, choose an implementation whose documented guarantees meet them.

Make a choice from constraints

For thirty nearly ordered marks, insertion sort is a reasonable transparent choice. Its work follows the inversion count and it uses constant extra space. For a large arbitrary array with a strict constant-workspace requirement, iterative heap sort offers a useful worst-case bound. These choices depend on requirements rather than fashion.

For many student records where equal-mark roll order must survive, stable merge sort is appropriate if a linear buffer is available. For integers in a small range, compare n + k with n log n before selecting counting sort. If key width is small and digit extraction is well-defined, radix passes may also fit.

For ordinary application code without special stability or resource guarantees, a library sort can reduce implementation mistakes. You still own the comparator and must test its ordering rules, including equal and extreme keys. A reliable API cannot repair an inconsistent or overflowing comparator.

Write down the rejected alternatives when solving an exam design question. For example, choosing counting sort for ten sparse keys spread over a huge interval may waste memory. Choosing bubble sort solely because it is stable ignores its quadratic worst case. A good answer connects each constraint to an algorithm property.

Why the method is correct

To justify the comparator, consider the three integer relations. If x < y, its expression gives 0 - 1 = -1. If x equals y, it gives zero. If x > y, it gives 1 - 0 = 1. Only boolean results are subtracted, so extreme key differences cannot overflow. The comparison defines the usual consistent integer order.

For algorithm selection, prove the required properties rather than a universal winner. The decision tree establishes a worst-case comparison lower bound. A stable tie rule establishes record-order preservation. A workspace argument counts simultaneously live buffers and frames. Each claim answers a different requirement in the contract.

Common mistakes

Subtracting arbitrary signed keys in a comparator

x - y may overflow. Use relational comparisons and subtract their boolean results.

Assuming qsort must implement quick sort

The API promises ordering according to the comparator, not one internal algorithm or stability.

Ignoring key-domain size

Linear-time counting claims require controlling k. A sparse huge interval can make counting slower and larger than comparison sorting.

C17 details

qsort is a standard library interface available before C17. Its comparator contract and lack of a stability guarantee still apply in C17.
