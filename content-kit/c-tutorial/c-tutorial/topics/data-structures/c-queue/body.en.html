Serve the earliest waiting item

Students waiting at a help desk expect the earliest arrival to be served first. A queue represents that order. Enqueue adds at the rear, dequeue removes at the front and peek observes the next item without serving it. A queue does not choose the smallest roll number or the newest request.

Compare that with the stack from the previous lesson. A stack uses one end for both insertion and removal. A queue separates those ends so older items stay ahead of later arrivals. The same values can therefore produce different removal orders depending on the chosen abstraction.

You will implement a queue in a fixed circular array and with linked nodes. Both need a clear empty state and a failure result. The array also has a known full state, while the linked version can fail allocation. Neither should silently overwrite an existing arrival.

Count live elements and wrap physical positions

The circular representation stores a four-slot array, a front index and a count. Initially both numbers are zero. Front names the first live element when count is positive. Count ranges from zero through capacity, and the next insertion position is (front + count) modulo capacity when the queue is not full.

Modulo keeps indices within the buffer. After removing the element at physical index three, front becomes zero. Logical order can cross the physical end of the array. That is not a broken queue or a reason to sort its storage; it is how released slots are reused without shifting every remaining element.

enqueue returns failure when count equals capacity, before writing. dequeue and peek return failure when count is zero, leaving their output unchanged. The functions require valid pointers and a representation whose invariant already holds. They do not reserve any int value as an empty marker.

Physical indices:  0    1    2    3
After wraparound: [50] [60] [30] [40]
front = 2, count = 4
Logical order: 30 → 40 → 50 → 60

Update a boundary instead of moving every value

A naive array queue can shift all remaining values after each removal. That preserves order but costs linear work per dequeue. The circular design instead reads values[front], advances front modulo capacity and decrements count. Old bytes remain in unused slots, but count and front define which slots are live.

After enqueuing ten, twenty, thirty and forty, the array is full. Removing twice advances front to two and leaves two live values. Enqueuing fifty writes at zero, and enqueuing sixty writes at one. Reading from physical index zero would now misrepresent arrival order; traverse from front for count positions when displaying the queue.

Using count also resolves a common ambiguity. Designs that store only front and rear need another convention to distinguish full from empty when the indices coincide, often an unused slot or a flag. This implementation stores count and can use all four slots. Do not mix formulas from a different convention without updating its invariant.

Preserve arrival order through wraparound and empty transitions

Reuse released array slots after circular wraparound

After removing ten and twenty, front is two. New values occupy physical slots zero and one, but logical service order remains thirty, forty, fifty, sixty. A full rejection leaves the previous sequence untouched.

Reset both linked endpoints when removing the only node

A stale rear pointer after singleton removal would name freed storage. Resetting both endpoints allows the next enqueue to start a new chain safely. Subsequent removals preserve arrival order.

Give each unfinished job one round-robin time unit

Each job enters the queue once. After one unit, unfinished jobs return at the rear and finished jobs leave. The queue stores job indices; remaining stores their separate state. Three active jobs fit the four-slot capacity throughout.

Maintain both endpoints as one invariant

The linked representation owns front and rear pointers. An empty queue has both null. In a nonempty queue, front names the oldest node, rear names the newest node and rear.next is null. Those statements should stay true after every successful operation and after every rejected request.

Enqueue allocates a node before changing the chain. Set its value and null next first. If the queue is empty, set front to the node. Otherwise set the old rear's next to the node. Finally set rear to the node. If allocation fails, return with the old queue unchanged.

Dequeue saves the front node and its value, advances front to the successor and frees the old node. If front becomes null, rear must also become null. Leaving rear at the freed node creates a dangling pointer that a later enqueue could write through. The singleton case therefore tests more than ordinary head movement in a longer chain.

Before last removal: front ─┐
                            ├─→ [101 | NULL]
                       rear ─┘
After: front = NULL, rear = NULL; former node is freed.

Whole-queue cleanup repeatedly removes nodes until empty. A failed later allocation must not leak earlier nodes if the caller abandons construction. Borrowed pointers to removed nodes become invalid; resetting endpoints does not repair outside aliases. This design has one owner and no concurrent readers or writers.

Order is a tool, not the entire service policy

A queue is useful for task arrivals, buffered producer-consumer workflows and breadth-first exploration. The data structure preserves the order of accepted items. The application still decides which items are admitted, whether capacity rejection means retry or drop, and how much work each service turn performs.

The round-robin example stores job indices in the queue and remaining units in a separate array. Each dequeue consumes one unit. An unfinished job returns to the rear; a completed job disappears. This gives each currently queued job a turn before the same unfinished job cycles back.

For jobs needing two, one and three units, the service order is one, two, three, one, three, three. The final repeated turns belong to job three because the others have finished. This is a small deterministic simulation, not a claim about operating-system preemption, arrival timing or priority fairness.

Separating identity from state prevents unnecessary copies. If the queue stored a copied remaining count and the application also changed an array count, the two versions could disagree. Pick one authoritative place for mutable job state and let the queue carry the reference or index needed to find it.

Measure the transitions that can break order

Circular enqueue, dequeue and peek perform constant structural work. Linked enqueue and dequeue also change a constant number of links, aside from allocation behavior. A circular buffer reserves its full capacity in advance. A linked queue grows with its length but pays allocation and pointer overhead for each node.

Test empty dequeue and peek first. Then enqueue one item, peek without removal and dequeue it. For linked storage, confirm both endpoints become null and then enqueue again. That second construction exposes a dangling rear that a one-time run might miss.

For the circular queue, fill it, reject one extra arrival, remove two items, enqueue two more and drain it. Verify logical order rather than the physical array printout. A full rejection must preserve the previous four arrivals. An empty rejection must preserve the caller's prior output value.

Use duplicate and zero values in additional experiments. Status must distinguish an empty queue from a valid stored zero, and equal values must still occupy separate arrival positions. A sequence of operations tests the representation more effectively than calling enqueue once and assuming every later transition is similar.

Do not lose the distinction between storage and order

Printing physical slots as service order

After wraparound, index zero need not be the oldest live element. Start at front and visit count positions modulo capacity. Ignore unused slots even if they contain old-looking data.

Using a stale linked rear

When the final front node is removed, reset rear. A nonnull rear must always name a live final node. Merely checking front in dequeue does not protect a later enqueue from a dangling write.

Overwriting when full

This queue rejects a full insertion. Some ring buffers deliberately overwrite old data, but that is a different policy with different consequences. Do not introduce silent data loss by borrowing an overwrite formula into a rejecting queue.

Mixing queue and stack removal

Removing from the most recently filled slot gives stack-like order. Use front for dequeue and the calculated rear slot for enqueue. Draw accepted arrivals in a line when checking a command trace.

State what a rejected arrival means

A full queue tells the caller that this arrival was not stored. The caller may retry later, reject the request visibly or choose a different buffer, according to the application. It must not announce acceptance merely because earlier arrivals remain safe. Keep that admission result separate from later service completion: successfully enqueued work has joined the waiting sequence, but has not necessarily been processed.

This distinction is useful in a menu or a service simulation. Print accepted only after enqueue succeeds, and print a completion result only after the requested work finishes.

Single-threaded C17 queues

The implementations use standard C17 with bounded array indices and checked allocation. They are not concurrent queues. Sharing them between threads requires a separate synchronisation design. The local module examples make ownership explicit; the circular arithmetic itself does not need platform-specific facilities.
