Join separately allocated boxes into an ordered chain

An array stores neighbouring elements together. A linked list stores each value in a node that also points to the next node. Imagine a trail of cards: each card tells you where to find the following card. The cards need not occupy adjacent places, but you must preserve their directions to keep the trail reachable.

The owning head pointer names the first node. A null head means an empty list, and the final node has a null next pointer. Every allocated node must eventually be released exactly once. The value zero is ordinary data; it is not a special marker for an empty list.

This lesson builds a small reusable module and clients that exercise its operations. The module source and header are provided together, following the earlier multi-file lesson. Run the examples locally because they compile that module alongside each client. Focus on which link changes and which node owns live storage at each step.

Represent a node and identify the incoming link

The structure contains an int value and a pointer to another struct Node. A structure may contain a pointer to its own type because the pointer has a known representation; it cannot contain a complete instance of itself recursively by value. malloc(sizeof *node) allocates one node without repeating the type name.

insert_at and remove_at receive a pointer to the caller's head pointer. This lets them replace head when the first position changes. A local variable named link points to whichever pointer leads into the current position: initially the head pointer, and later a predecessor's next member. Updating *link changes the right incoming edge in either case.

The module requires valid owner and output pointers where its interface expects them. Positions use size_t and are zero-based. For a list of length n, insertion permits zero through n; removal permits zero through n minus one. Validate signed user positions before converting them to size_t, so a negative request does not become a huge positive index.

Insert without losing the suffix

To insert at the head, allocate and initialise a new node, set its next to the old head, then replace head. The old list remains reachable through the new node. If allocation fails, return failure without changing any existing link. Ownership of the new allocation begins only after a successful allocation.

Before: head ──> [20 | next] ──> [30 | NULL]
Prepare: new = [10 | old head]
After:  head ──> [10] ──> [20] ──> [30] ──> NULL

For a middle insertion, find the incoming link of the desired position. Set new.next to the old successor before redirecting that incoming link. Reversing those assignments without preserving the successor can lose the rest of the list. The pointer-to-link approach avoids a separate special-case assignment for the head.

Before: [20] ──> [30]
Prepare: new = [25 | address of 30]
After:  [20] ──> [25] ──> [30]

At the tail position, the incoming link currently contains null. The same assignments make the new node the final node with a null successor. Finding that position is linear without a stored tail pointer. A separate tail pointer can speed repeated appends, but then every deletion must also preserve its invariant.

Before: head ──> [10] ──> [20 | NULL]
After:  head ──> [10] ──> [20] ──> [30 | NULL]

Exercise normal changes and boundary rejections

Insert at the head, tail and a middle link

Each successful insertion redirects one incoming link. Positions are zero-based: inserting at the current length appends. The search reports the first matching position without modifying the list, and cleanup releases all four allocated nodes.

Delete the middle, head and final node safely

The predecessor link is redirected before the removed node is freed. Removing the only remaining node updates head to null. A later removal returns failure without dereferencing null or changing ownership.

Reject a position beyond the end without losing the existing list

A one-node list permits insertion at zero or one, not two. Validation finishes before allocation and mutation. The failed search leaves its output parameter unchanged. clear_list also resets the owning head, making repeated cleanup safe for that owner.

Unlink a node before releasing it

Removal first locates a nonnull incoming link. Save the node it names, replace the incoming link with that node's successor, then free the removed node. No later operation may read members from the freed node. The list now owns one fewer allocation, and the remaining chain is still connected.

Before: [10] ──> [20] ──> [30]
Save removed = address of 20
Redirect: 10.next = 20.next
After:  [10] ────────────> [30]     free(removed)

Deleting the head redirects the owning head pointer. Deleting the final node makes its incoming link null. Deleting the only node therefore leaves head null. An empty-list removal must return failure before dereferencing anything. The same pointer-to-link code expresses these cases without pretending that every node has a predecessor node.

Only node: head ──> [10 | NULL]
After removal: head = NULL
The former node is released; there is no readable node left.

If another part of the program borrowed a pointer to the removed node, that alias is now dangling. Setting head to null does not rewrite other pointers. Keep borrowing lifetimes short, or design an ownership policy that prevents deletion while borrowers need the node. This introductory list has one owner and no concurrent mutation.

Read the chain and release the entire chain

Search and printing walk from head while the current pointer is nonnull. Search returns the first matching position and leaves its output unchanged when no match exists. Printing displays each value before advancing. Neither operation changes the links, so a const-qualified node view communicates the read-only role.

Search for 30:
[10] index 0: no ──> [20] index 1: no ──> [30] index 2: yes
Search for 99 reaches NULL: missing, not an extra node.

Whole-list cleanup saves the successor while the current node is still alive, frees the current node, then advances the owner. Reading current.next after free would be a use-after-free. Repeating until head is null releases each allocation exactly once and leaves a safe empty owner for subsequent cleanup.

Save next ──> free current ──> head = next
Repeat until head == NULL.

Cleanup is needed on abandoned construction too. If the third input token is invalid after two successful appends, those two nodes still belong to the program. Release them before returning. A failed allocation similarly requires releasing the already-built prefix unless the caller explicitly takes ownership of that partial result.

Choose the structure for its operations

A singly linked list does not support direct indexed access. Reaching position k follows k links. Searching a missing value can visit all n nodes, and appending through this position-based interface also traverses the chain. Repeated appends therefore take quadratic total traversal work unless the design retains a tail or incoming-tail link.

Head insertion and removal use constant link work after any allocation. Nodes need extra pointer storage and separate allocations, and their scattered layout can reduce cache locality compared with arrays. A list is useful when its update pattern fits the task; it is not automatically a faster replacement for an array of marks.

The examples remain intentionally small so every link can be drawn. For a growing application, decide whether you need a length, a tail, duplicate-value rules or stronger failure detail. Every extra cached field creates another invariant to update on head, tail, empty and singleton transitions.

Keep reachability and lifetime separate

Overwriting the only route to a suffix

Save the old successor in the new node before redirecting the incoming link. Draw the arrows after each assignment rather than treating insertion as one mysterious pointer expression.

Freeing before saving next

A released node is not valid storage from which to recover its successor. Read next first. The fact that an allocator has not yet reused the bytes does not make a later access legal.

Assuming a valid index on every request

A position larger than the length has no corresponding incoming link. Reject it without allocating or changing the list. Removal also needs an actual node at the selected position; the tail's null link is an insertion boundary, not a removable element.

Losing allocations on an error return

Input and allocation failures can occur after a prefix has been built. Clear that owned prefix before abandoning the operation. A leak may not change the displayed list, but repeated failures can exhaust the program's resources.

Test transitions rather than only long lists

Start with an empty owner and try removal, search and printing. Then insert one node, remove it and verify that the owner becomes null again. These transitions exercise the absence of a predecessor and successor. A five-node middle deletion cannot replace the singleton test because its neighbouring links hide those boundaries.

For insertion, test position zero, the current length and one beyond the length. For removal, test zero, the last valid index and the current length. Confirm that rejected requests leave the printed chain unchanged. Use duplicate values to verify that search returns the first position, and search a missing value to verify that its output parameter is preserved.

Finally build several nodes and abandon construction after an invalid token. Review that every successfully allocated prefix node reaches cleanup. Dynamic memory diagnostics can help observe leaks and invalid accesses on executed paths; the ownership argument explains why the unexecuted failure paths must release the same resources.

Pointers and allocation under C17

The list uses standard C17 structures, pointers and dynamic allocation. It assumes a single owner and no concurrent access. The examples check allocation results, but ordinary successful runs cannot force every allocator failure. The unchanged-on-failure link ordering is therefore also part of the reasoning you should review.

Change one edge while preserving the rest

Track the incoming link, initialise before insertion, unlink before free and save successors before cleanup. Empty and singleton cases are real operations, not afterthoughts. Next, a stack restricts updates to one end of a sequence.
