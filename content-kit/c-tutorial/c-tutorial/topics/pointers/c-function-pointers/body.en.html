Function Pointers

A calculator chooses an operation after reading a menu option. One design repeats a long decision chain every time an operation is needed. Another stores the addresses of compatible functions in a table and selects one entry. A function pointer makes that second design possible.

A function pointer identifies callable code rather than an int or character object. Its type describes the result and argument types required for a valid call. That signature is part of the safety contract, just as the pointed-to type matters for ordinary object pointers.

You will first select an addition function, then build a small calculator table. Finally, you will pass a comparison function to qsort. That comparison function is a callback: another routine receives it and calls it when it needs your decision.

Declarations and call rules

Read int (*operation)(int,int) from the name outward. operation is a pointer, and the selected function takes two ints and returns int. The parentheses are essential. int *operation(int,int) instead declares a function that returns int *.

Initialize with a compatible function designator, such as operation = add_values. C converts the function designator to its function pointer for this use. Writing &add_values is also permitted, but the shorter spelling is common.

Call the selected function with operation(a,b) or (*operation)(a,b). Both forms use the same function type. The pointer must identify a compatible function before the call; a null function pointer is not callable.

An array declaration such as int (*operations[])(int,int) groups several compatible function pointers. Each entry must agree on parameter types and result type. Validate a menu index before indexing this table, then call the selected entry with suitable arguments.

A typedef can make repeated signatures easier to read: typedef int (*BinaryOp)(int,int);. Then BinaryOp names that pointer type, and BinaryOp operations[3] declares a three-entry table. The typedef does not relax call compatibility.

int (*operation)(int, int) = add_values;
int result = operation(4, 5);
int (*operations[])(int, int) = {add_values, subtract_values};

Follow the storage and operations

The first example initializes operation with the addition function. A call with four and five returns nine. Explicitly dereferencing operation before a second call produces five from two and three. The two spellings differ visually without changing which function is selected.

The calculator table contains addition, subtraction and multiplication in that order. With inputs six and two, entries zero through two produce eight, four and twelve. The table changes control flow by selecting code; it does not store the results in advance.

Every binary calculator function has the same signature, even though their bodies differ. A function that takes one int cannot be inserted safely by casting it to that binary type. The cast can silence a diagnostic while leaving an incompatible call with undefined behavior.

A function pointer can be passed as a parameter. The apply helper receives an int array, a count and a transformation function. It calls transform on each element and stores the returned value. Passing twice separates the array traversal from the choice of transformation.

The unary transformation must also obey its numeric bounds. A correctly typed callback can still overflow if it squares an arbitrary large int. The practice task bounds inputs to minus one hundred through one hundred so both doubling and squaring remain representable.

Function pointers do not support object-pointer arithmetic. There is no portable expression that advances from one function's address to the next function. A dispatch table is an ordinary array of pointer entries; arithmetic may traverse that table, not the selected function code.

The memory diagram draws function targets as code labels rather than writable value boxes. Standard C does not let you dereference a function pointer and assign new instructions as though you were changing an int. The useful operation is a compatible call.

Choose the right behavior

qsort sorts an array without knowing the meaning of its element values. You provide the array beginning, element count, element size and a comparator. The comparator has the required type int compare(const void *,const void *).

For an int array, the two callback arguments point at int elements. Convert them to const int * before reading. They are addresses, not integers already converted to pointer form. The void-pointer parameters provide a generic object-address interface, explained further in the next topic.

The comparator returns negative when the first element belongs before the second, zero when they compare equal, and positive when the first belongs after the second. qsort needs a consistent ordering. Returning true for greater-than alone loses the distinction between less-than and equality.

Avoid return *a - *b for unrestricted ints. The mathematical difference might exceed int range, causing signed overflow and undefined behavior. The expression (*a > *b) - (*a < *b) uses comparison results zero or one, so its result is always minus one, zero or one.

Do not change the compared objects inside the comparator. Repeated comparisons must agree for the values being sorted. A comparator that depends on a changing counter or random choice cannot define a stable ordering relation for qsort to follow.

The qsort example sorts 90, 40, 70 and 40 into 40, 40, 70 and 90. Equal keys remain in the result, but their relative identity is not guaranteed. The C standard does not promise a stable sorting algorithm or require one particular algorithm for qsort.

The caller supplies sizeof values[0] as the element size. Passing sizeof a pointer would give the wrong stride when pointer and element sizes differ. The compiler cannot discover the intended element type from the void * array argument alone.

Function pointers and object pointers occupy different semantic categories. The portable void * round-trip guarantee applies to object pointers, not every function pointer. Do not store callbacks in a void * table and assume ordinary object conversions preserve their calls.

A callback can be selected at runtime without losing type checking. Keep its declaration visible before use, match the signature, and avoid casts that hide disagreements. If different operations genuinely need different argument lists, design an explicit common wrapper or separate interfaces rather than pretending their signatures match.

A comparison routine should define a total ordering for the input values it receives. For integer keys, ordinary numeric order satisfies that need. With records, compare a primary key first and use a secondary key only when the first compares equal. Avoid contradictory answers for the same pair.

A callback can also carry policy without global variables. Standard qsort's comparator has no extra context parameter, so a design requiring caller-specific context needs another documented interface or a different sorting routine. Do not silently depend on mutable global state when teaching a reusable comparator.

The dispatch table itself is data storage and can be local, static or const-qualified according to the desired lifetime and mutability. The selected functions continue to exist as callable program code. A local table ending its lifetime does not end the functions; it only ends that collection of saved function addresses.

A menu wrapper should also specify division-by-zero and overflow behavior if division or unrestricted arithmetic is added. Selecting a valid function pointer proves call compatibility, while arithmetic preconditions remain the selected function's separate responsibility.

Mistakes and repairs

A missing pair of parentheses changes a function-pointer declaration into a pointer-returning function declaration. Start reading at the identifier and check what the next binding operation means. A typedef is useful after you understand that underlying declaration.

An out-of-range menu index reads beyond the dispatch table. Validate it before selecting an entry. A valid index may still select a null entry in a partially filled table, so either initialize every entry or check the chosen pointer before calling.

A qsort comparator must not subtract arbitrary ints. Tests with small marks can conceal the overflow problem. Use a comparison-sign expression that also handles minimum and maximum int values safely.

Do not infer qsort's stability from one observed output. With plain equal ints you cannot see which original equal entry came first. Records with equal keys require a documented stability policy or an explicit secondary ordering key.

Calling through an incompatible converted function pointer has undefined behavior. Correct return and argument types are not optional metadata. The intentional mistake example shows why a cast is not an argument adapter.

Call through an incompatible function type

The result is undefined: the call uses a type incompatible with the actual two-argument function. A cast cannot repair a signature mismatch.

Working habits

Keep dispatch tables small and signatures visible. Bound operands independently of pointer validity. Use callback parameters to separate traversal from policy, and write comparators around signs and consistent ordering rather than arithmetic shortcuts.

Standard and portability notes

Function pointers and qsort are available in C89 and later. The examples target C17 with C99-style loops. C23 does not make incompatible callback casts safe or require qsort to use a stable algorithm.
