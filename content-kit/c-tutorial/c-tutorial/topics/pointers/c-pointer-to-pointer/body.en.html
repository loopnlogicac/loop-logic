Pointer to Pointer

A pointer can select another pointer object, just as an int pointer selects an int object. This extra address level is useful when a helper must change which object its caller pointer selects. It also appears in tables of separately stored rows.

Imagine a desk index that identifies another index card. The second card identifies a room. Replacing the room number on that second card changes the final destination while the first card still selects the same card. A double pointer gives your program that two-level route.

Draw every level before writing code. The number of stars describes how many pointer objects you follow, not how many dimensions an arbitrary matrix must have. A fixed two-dimensional array and a table of row pointers have different layouts.

Declarations and call rules

Start with int score=45; int *p=&score; int **pp=&p;. The object pp stores the address of p. *pp accesses p and therefore has type int *. **pp follows p's stored address and accesses score, an int.

The assignment *pp = &other redirects p. The assignment **pp = 60 changes the currently selected int. The assignment pp = &another_pointer changes which pointer object pp selects. Keep these three write levels separate.

A helper declared void select_value(int **out, int *target) can assign *out=target. Calling select_value(&p,&b) gives it the address of p itself. Its contract requires a valid writable int * object at out; target may represent a live selected int or an agreed null state.

The table declaration int *rows[] = {a,b} stores one int pointer per row. In many expressions, rows converts to int ** because its first element has type int *. This is an actual intermediate pointer table, unlike a fixed int matrix.

int *p = &score;
int **pp = &p;

Follow the storage and operations

Follow pp to p in the first diagram, then follow p to score. Writing **pp changes score from forty-five to sixty. Neither pointer address needs to move. A later write to *pp could select a different int while pp remains aimed at p.

The redirection helper changes p in main because out points at that exact pointer object. It does not need to return the new address as a function result. The caller may inspect or dereference p afterward if the newly selected target is live and valid.

Passing p instead of &p loses the level needed for redirection. An int * value selects an int, not the int * object p. The compiler's incompatible-pointer diagnostic is evidence of a mismatched object level, rather than an obstacle to bypass with a cast.

The fixed pointer-table example uses a two-int row a and a three-int row b. rows[0] and rows[1] store separate addresses. A view named grid points at the first pointer entry. grid[1][2] first selects the second pointer, then advances two ints within its target row.

Each selected row needs a separate usable length. int ** contains no column count. If all rows happen to have three elements, that is an interface agreement, not information automatically retained by the pointer type.

The outer table and inner rows also have separate lifetimes. Local rows can be selected by a local table while all remain alive. Returning that local table or selecting an expired local row would break the route. Trace the lifetime of each box in the diagram independently.

Programs to inspect and trace

Two dereferences reach one int

pp selects the pointer p. Dereferencing p then selects score, which becomes sixty.

Redirect a pointer belonging to main

The helper receives the address of p and writes a new target address into that caller-owned pointer.

Two rows allocated independently

The outer allocation stores row pointers. Each inner allocation stores three ints. Both success and partial-failure paths release owned memory.

A fixed pointer table needs no allocation

The two rows have different lengths. rows owns the pointer entries; a and b own the actual elements.

Choose the right behavior

A dynamic row table obtains those boxes during execution. malloc requests a number of bytes and returns a pointer to allocated storage, or NULL on failure. free releases a successful allocation. Both are declared by stdlib.h; the next module teaches their full contracts.

The small dynamic example first allocates an outer table large enough for two int * entries. It then allocates three ints for each row. sizeof *grid describes one pointer entry, while sizeof *grid[r] describes one int element. These expressions keep the allocation sizes matched to their target levels.

The fixed dimensions are deliberately tiny, so their size products are representable. A general matrix allocator must additionally check multiplication overflow before requesting rows times pointer-size or columns times element-size bytes. Bounds on logical dimensions are part of an allocation design.

Every allocation result is checked before use. If a row fails, only the earlier completed row allocations belong to the program. The cleanup loop frees those earlier rows, then frees the outer table. It does not access uninitialized later pointer entries.

The example uses calloc for the outer table but never relies on its zero bytes representing null pointers. It assigns each entry before use and tracks completed rows by the loop index. This distinction keeps the cleanup reasoning portable.

After all rows succeed, assignments fill the ints with values based on their coordinates. The printed positions demonstrate that grid[0][2] and grid[1][2] belong to different row targets. Their numeric values do not depend on whether the allocator placed the rows near each other.

Successful cleanup frees each row while the outer table still contains the addresses needed to locate them. It then frees the table once. Freeing the outer table first would lose the only stored routes to the rows, causing leaks or invalid later accesses.

Independent row allocation permits different row lengths and convenient row-pointer swaps. It also creates several allocations and cleanup paths. A single contiguous block can improve locality and simplify ownership, but needs a different indexing or row-pointer setup. The dynamic-array topic compares these alternatives in detail.

A fixed int matrix[2][3] stores six ints in row order. It has no int * objects between the rows. Casting matrix to int ** does not insert those missing pointer objects. Dereferencing the cast would interpret int data as though it were pointer storage, producing undefined behavior.

Use int (*row)[3] for a pointer to a fixed three-int row. Use int ** only when the selected objects really are int pointers. Similar indexing syntax is not proof of equivalent representation.

Row swaps illustrate the benefit of the intermediate table. Exchanging grid[0] and grid[1] swaps two pointer values, so later indexing visits the rows in a different order. The allocated row blocks remain at their original locations. Each allocation must still be freed exactly once after the reordering.

If rows can repeat the same address, a loop that frees every entry would release the same allocation twice. The independent-row allocator avoids that ownership ambiguity by creating a different successful allocation for each row. A borrowed table that intentionally repeats rows needs a different cleanup contract.

For changing a caller pointer, a return-value design can sometimes be clearer than an output parameter: p = choose_target(...). The double-pointer form is especially useful when a function returns a status separately or must update several locations. Choose based on the interface, while preserving the same target-lifetime obligations.

After partial failure, do not publish a half-built grid as a usable result unless the interface explicitly describes partial construction. A common contract leaves the caller output null until construction succeeds completely, then transfers the completed table.

Mistakes and repairs

Do not count stars by the number of bracket pairs in an expression. matrix[r][c] can work through a pointer-to-array or through a real pointer table, with different intermediate types. Read the actual declaration at each level.

A null pp must not be dereferenced, even if the intended final target exists elsewhere. Likewise, a valid pp may select a null p, so **pp still requires another validity check. Each arrow must lead to a suitable live object.

When an allocation fails halfway through construction, freeing all requested rows is unsafe because some were never created. Track successful rows and unwind that prefix only. Do not read uninitialized table entries to guess whether allocation occurred.

Clearing grid after cleanup changes only that owner variable. Other aliases do not become valid or null automatically. End all borrowed row and element uses before releasing their storage.

A double-pointer cast does not create a row table

The result is undefined. The matrix holds ints, not int pointer objects; a cast cannot create those objects.

Working habits

Annotate pp as pointer to pointer, *pp as pointer, and **pp as value while tracing. Keep row counts and lengths outside the pointer type. Separate construction from cleanup, and make every allocation-failure exit release exactly the storage already owned.

Standard and portability notes

Double pointers and pointer tables are standard C features across C89 through C23. These programs target C17 and use C99 declarations. Allocation is explained as a small forward preview and linked to malloc and calloc for a fuller treatment.
