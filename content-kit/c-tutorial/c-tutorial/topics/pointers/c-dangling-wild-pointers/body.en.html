Dangling and Wild Pointers

A pointer can look plausible in a debugger and still be unusable. Its target may never have been selected, or the selected object may already have disappeared. These are different causes of invalid access, and they need different prevention habits.

An uninitialized pointer is often called a wild pointer. A pointer whose former target no longer exists is called a dangling pointer. These are common teaching terms rather than separate C pointer types. The declaration alone cannot reveal whether a particular runtime value is usable.

Think of an address written on a blank card versus a real room address after the building has closed. The first never identified a usable destination. The second once did, but its history is no guarantee that access remains valid.

Declarations and call rules

An automatic local declaration int *p; leaves p with an indeterminate value. Assign NULL or a live target address before reading it. Comparing the uninitialized value with NULL does not turn it into a valid absence marker.

A block variable exists only during its specified lifetime. A pointer saved from that block cannot keep the object alive. After the block ends, do not dereference the expired address or use it as though a non-null test established validity.

Allocated storage has a different lifetime. malloc requests storage and returns an owner pointer or NULL. free(owner) ends that allocated object's lifetime. The pointer variable owner is a separate object and can be assigned NULL afterward.

Only free valid allocated storage according to its ownership contract. An address of a local int, an interior element address or an already released block is not a new owner to release. The dynamic-memory module develops these allocation rules fully.

int *owner = malloc(sizeof *owner);
if (owner == NULL) {
    return 1;
}
*owner = 45;
free(owner);
owner = NULL;

Follow the storage and operations

The safe initialization example creates p as NULL, then assigns the address of a live score. The dereference occurs while score exists. Initializing at declaration makes the pointer's initial state explicit and prevents an accidental early read.

The scope example creates local inside a nested block. A view reads it while the block is active, and the scalar value is copied into saved. After the block, saved remains usable because it owns an independent int value, not an expired location.

If instead you copied &local into an outer pointer, that pointer would not provide a live object after the block. C may reuse the storage for something else or optimize away the original memory entirely. Seeing the old value once does not make future access valid.

The allocation example checks malloc before storing forty-five. It prints the value while the object is alive, releases the allocation once, then writes NULL to owner. The final status check reads that new null assignment rather than the stale allocated address.

Assigning owner=NULL is a local bookkeeping action. If alias was copied from owner before release, alias occupies a separate pointer object. It does not change when owner changes. Once the allocation is freed, both former access paths have lost their target.

The alias mistake demonstrates this point: clearing owner does not make *alias valid. The right repair is to end all alias use before release, copy any needed values while storage is live, and discard borrowed addresses when their owner ends the lifetime.

Programs to inspect and trace

Initialize before selecting a target

The pointer is initialized immediately and only dereferenced after a live target is assigned.

Copy a value before a block ends

The int value is copied while local is alive. No expired pointer is read after leaving the block.

Release allocated storage once

Allocation failure is checked. The value is read before free, then the owner is cleared and not reused.

Choose the right behavior

Ownership answers who is responsible for ending an allocation's lifetime. A borrowed pointer allows temporary access without that responsibility. Several borrowers can share one owner, but every borrower must finish before the owner releases the object.

One practical pattern places temporary aliases inside a block whose end precedes free. This makes their intended use window visible. It is still your responsibility not to return or save those aliases somewhere that outlives the window.

A helper that returns a pointer needs a documented result lifetime. Returning a pointer to the caller's own array is a borrow. Returning an allocated object transfers or shares ownership according to the interface. Returning a static object preserves lifetime but shares data across calls.

Returning an automatic local object address is invalid.

Freeing the same allocation twice is undefined behavior. Clearing one owner after release can prevent that exact variable from being used for a second free, because free(NULL) is harmless. It does not solve duplicated owners or stale aliases elsewhere in the program.

Do not use a stale pointer comparison to ask whether storage still exists. A pointer value associated with an object whose lifetime ended can become indeterminate under C's lifetime rules. Track a separate explicit state or clear controlled pointer variables without reading their former values.

AddressSanitizer can detect many use-after-free, use-after-scope and bounds mistakes during execution. UndefinedBehaviorSanitizer catches additional invalid operations. Compile a standalone practice program with -fsanitize=address,undefined and debug information when investigating memory access. A clean run covers only the paths exercised.

Compiler warnings can identify uninitialized pointers and returned local addresses. Treat those diagnostics as design feedback. Adding a cast or moving code into another helper may hide a warning without fixing lifetime. Follow the storage owner rather than judging whether the program happens to crash.

Avoid returning dynamic storage only to sidestep a local lifetime problem when a scalar result or caller-owned output would suffice. Allocation adds failure handling and release responsibility. Choose the simplest storage model that genuinely matches the required lifetime.

Mistakes and repairs

A null check on an uninitialized pointer is already a read of an indeterminate value. Initialize first. The wild-pointer mistake must be repaired at the address-selection step, not by checking whether its accidental bits look nonzero.

Using memory after free is undefined even if the old bytes appear unchanged. The allocator may retain, recycle or protect that memory. No observed output can establish a permitted post-release read.

Setting one pointer to NULL does not walk through the program clearing aliases. Draw each copied address separately so ownership and borrowing are visible. Ensure no old route remains in use when the target lifetime ends.

Do not free each interior element of one array allocation. The complete allocation has one owner address and one release. Interior pointers borrow positions in that object and cannot independently end their portions.

An uninitialized pointer is not a destination

The result is undefined: p was never assigned a valid target address. Initialize a real int and point to it.

An alias still expires after free

The result is undefined: alias still refers to the object whose lifetime ended. Clearing owner does not revive or clear alias.

Working habits

Initialize pointers immediately. Keep borrowed access shorter than owner lifetime. Copy ordinary values when locations are no longer needed. Release each owned allocation once, and end temporary aliases before that release.

Standard and portability notes

Uninitialized reads and expired-object access remain invalid across the C standards in this course. The examples target C17. Sanitizers are compiler tools rather than language guarantees, so their usefulness complements lifetime reasoning instead of replacing it.
