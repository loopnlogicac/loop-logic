const with Pointers

A function that reads exam marks should not accidentally change them. A pointer that must always select one result slot should not accidentally move elsewhere. Both intentions involve const, but they restrict different levels of a pointer declaration.

Think of a fixed bookmark and a read-only page. Fixing the bookmark prevents changing the selected page. Making access to the page read-only prevents edits through that route. You may apply either restriction or both, and the declaration must show which one you mean.

The goal is to communicate permitted actions in types. const helps the compiler catch unintended writes and helps a reader understand a function's role. It does not replace lifetime or bounds checks, and it does not automatically freeze every alias of a mutable object.

Declarations and call rules

Start reading at the identifier, moving outward according to parentheses and declaration binding. In const int *p, p is a pointer to const int. The pointer can receive another address, but an assignment to *p is prohibited through that access path.

The spelling int const *p means the same thing. const next to int qualifies the pointed-to int type. Read it as a read-only view of an int, without assuming that the underlying object was necessarily defined as const.

In int *const p = &score, p itself is a const pointer object. Its address value must be initialized and cannot be reassigned. The selected int is mutable, so *p=50 is permitted when score is a live writable int.

In const int *const p = &score, the pointer is fixed and writes through its target access are prohibited. Reading is permitted. The two const positions describe two distinct levels and answer different mutation questions.

For more complicated declarations, parentheses can change what binds first. int (*row)[3] is a pointer to a row array, while int *rows[3] is an array of pointers. The next topic develops that difference; the same outward-reading habit helps with both.

Follow the storage and operations

The movable read-only example starts p at a, then redirects it to b. That address assignment is allowed because p itself is not const. A later write through the variable name b changes the selected value to ten, which p can read.

This does not violate const. The underlying b was declared as an ordinary mutable int. const on the pointer's target type restricts writes through p, not every possible access route to b. A mutable alias can still update b under the usual validity rules.

The fixed-pointer example starts p at score and assigns fifty through *p. The pointer value stays unchanged. Attempting p=&other would instead assign the const pointer object and receive a diagnostic.

The fixed read-only view combines both restrictions. Neither view=&other nor *view=... is allowed. Yet changing the original mutable score by name remains valid and visible through view. Read-only access is not a snapshot or an independent copy.

For a function that sums input marks, const int *scores expresses that the helper does not write through its input pointer. Both mutable arrays and truly const arrays can provide input with appropriate type compatibility. The helper still needs an explicit count.

A const pointer parameter has a different role. Writing int *const values fixes only the local parameter object during that call. The caller's pointer was passed by value, so the caller's pointer variable is not made const. The pointed-to ints also remain writable through values.

Top-level const on a by-value parameter does not distinguish the external function type for compatibility. It can be useful inside the definition to prevent local reassignment, but it is not a promise that target elements will remain unchanged. Place const on the pointed-to type for that input-access promise.

Choose the right behavior

Adding a read-only view at one pointer level is safe: int * can convert to const int *. The conversion removes a write capability from that access path. The original mutable object remains available through other permitted routes.

Removing const is different. A cast can produce a mutable-looking pointer expression, but writing is valid only if the actual object was originally mutable and all other access rules hold. Writing an object defined as const has undefined behavior. Prefer an interface that preserves const rather than requiring casts.

Nested pointers introduce a less obvious restriction. C does not generally permit converting int ** to const int **. That conversion would not merely restrict access to one int; it would allow new pointer values to be stored into an intermediate pointer object with the wrong promise.

To see the hazard, imagine an ordinary int *p and a pointer pp selecting p. If pp could become const int **, code could store the address of a truly const int into p through that converted route. The original p would still have type int *, apparently permitting a later write into const storage.

The language rejects that implicit nested conversion. Use separately designed interfaces instead of forcing it with a cast. A table of read-only character pointers should be declared with its actual intended element type from the start.

A function that reads a string list without changing entries can use an appropriate pointer-table interface such as const char *const *names. Starting at names, the first dereference accesses a const pointer entry, and the next reaches const characters. The parameter variable names itself is still a by-value local pointer.

Const-correctness is about the allowed path, while ownership is about who controls storage lifetime. A const int * may borrow allocated storage that later gets freed by its owner. const does not keep it alive. Likewise, a fixed pointer can still become dangling when its target lifetime ends.

Concurrency also requires separate rules. A const view does not synchronize changes from another thread or promise the value cannot change between reads. The examples stay within single-threaded, valid mutable access so that the qualification lesson remains focused.

For an output buffer, const on the source and mutable qualification on the destination communicate opposite roles. The reverse-copy exercise follows this pattern. Its source and destination are distinct arrays, and the helper knows their usable count. const alone would not make overlapping reverse-copy correct.

The declaration table lets you test each permitted action directly. Ask whether assigning the pointer name is permitted, then ask whether assigning the dereferenced expression is permitted. This two-question method is more dependable than memorizing the phrase const pointer without identifying its level.

Mistakes and repairs

Placing const after the star restricts the pointer object. Placing it next to int restricts the int access path. If the compiler rejects the operation you intended, first check the level rather than deleting every qualifier.

Do not assume that a pointer-to-const makes its mutable target globally immutable. A valid writable alias can still change that object. If you need a saved result, copy the value or define genuinely immutable owned storage.

Do not use a cast to force int ** into const int **. The mismatch protects the intermediate pointer object from receiving a pointer with an incompatible write promise. Redesign the input representation when a read-only table is required.

A fixed pointer needs a valid initializer and a target lifetime long enough for its uses. Preventing reassignment does not prove that the original target survives. Keep permission, location and lifetime as separate checks.

Casting away const from a string literal does not make its characters writable. The literal rule holds independently of which pointer expression you use. Create a writable character-array copy for edits.

Writing through a pointer to const

This write violates the pointed-to const qualification. Use a mutable pointer only when the interface permits updates.

Redirecting a const pointer

The pointer object is const and cannot receive a second address. A pointer to const would restrict the other level.

Working habits

Read declarations from the identifier and label every star level. Put const on read-only input targets, keep outputs writable and preserve qualifiers through helper calls. Use separate objects when you need independent snapshots or different lifetimes.

Standard and portability notes

const became part of standard C in C89, and these pointer-qualification rules apply to the C17 examples. C23 has additional qualification details for arrays, so the examples avoid relying on nested array conversions that differ across standards. Ordinary pointer constness remains a separate question from ownership.
