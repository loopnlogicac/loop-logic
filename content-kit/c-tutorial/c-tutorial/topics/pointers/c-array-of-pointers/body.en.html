Array of Pointers

A row of addresses is different from an address of a row. The declarations look similar enough to confuse beginners, yet they describe different storage and different pointer steps. This lesson separates those two designs.

An array of pointers owns several pointer entries. Each entry may select a separate variable, string or numeric row. A pointer to an array owns one address selecting an entire fixed-width array object. Its target type records the width of that row.

Think of a list of room locations versus one location identifying a complete row of lockers. The list can select unrelated places. The row location describes a fixed-size group. Indexing syntax can hide the distinction, so begin with the declarations and memory picture.

Declarations and call rules

The declaration int *items[3] creates an array with three entries, each of type int *. Read items as array first because the brackets bind before the unparenthesized star. Every entry needs initialization before its pointer value is read.

The declaration int (*row)[3] creates a pointer to an array of three ints. Parentheses group the star with row before the array suffix. A compatible target is one row of an int matrix with three columns.

For a string table, const char *names[3] creates three pointers to read-only char access paths. The entries can be reassigned, while their literal targets must not be edited. char *const names[3] would instead fix the pointer entries while permitting writes through them only when their targets are truly writable.

Keep an outer entry count separately from each target's usable range. A pointer table does not encode the length of every row. Strings use their terminators for readable length; numeric jagged rows need explicit lengths.

int *items[3] = {&a, &b, &c};
int matrix[2][3] = {{1, 2, 3}, {4, 5, 6}};
int (*row)[3] = matrix;

Follow the storage and operations

The first example stores addresses of c, a and b in that order. Selecting items[1] retrieves &a, so *items[1]=15 changes a. The table order is independent of the variables' declaration order or physical placement.

Reassigning an entry changes its selected target without changing the target's address. Swapping two entries similarly changes a view over the objects. This can cheaply reorder strings while leaving the actual characters in their original storage.

The matrix example uses a pointer-to-array. row initially selects matrix[0]. Incrementing row advances one complete three-int array, reaching matrix[1]. Dereferencing row accesses that whole row, and then an index selects one of its ints.

The expression row[0][2] reads the third int in the currently selected row. Its meaning is consistent with (*row)[2]. The row width in the type supplies the correct stride; you do not manually multiply the pointer increment by three.

A table expression items usually converts to int ** because its first element is an int * object. A matrix expression converts to a pointer to its first row instead. Their intermediate objects differ, even when both permit two bracket pairs during access.

A table may select the same target twice. Writes through either entry then affect the same object. That aliasing can be intentional, but any operation promising independent rows must account for it. The array of addresses alone does not imply distinct owned targets.

Choose the right behavior

The literal-name table selects A, Campus and Lab. These target strings have visible lengths one, six and three. Each target has its own terminator. Equal pointer entry sizes do not imply equal target string capacities or lengths.

A numeric jagged array uses rows with different element counts. The example selects {2,4} and {6}. The accompanying lengths table stores two and one, preventing a traversal from reading a nonexistent second element of the shorter row.

For a selected prefix, validate the row index before reading its length entry. Then validate the requested count against that row's count. The final exercise uses short-circuit evaluation so an invalid row is rejected before lengths[row] is evaluated.

An empty logical prefix can have count zero while its underlying row storage still exists. The sum loop performs no reads and returns zero. This is different from inventing an accessible row element when a pointer entry is null.

Optional null rows require a deliberate contract. You might allow NULL only with length zero, and avoid arithmetic or dereference through that entry. Initializing all table entries to NULL provides a defined initial state, but it does not allocate any rows.

Ownership is separate for the table and targets. A local pointer table selecting local arrays needs no free. A table selecting literals also needs no free for those literals. An allocated table selecting independently allocated rows requires release rules for both levels, as the double-pointer lesson demonstrated.

If a table contains borrowed pointers into caller storage, its validity cannot exceed those targets' lifetimes. Returning the table does not extend an automatic row lifetime. Track each borrowed target, especially when some entries select nested-block arrays.

The total sizeof a real pointer array measures its entries. Dividing by sizeof its first entry gives the outer count in the declaring scope. That says nothing about the count of ints or chars reached through any one entry. Likewise, sizeof *row for a row pointer measures one full fixed-width row.

A cast cannot interchange these designs. Treating a matrix as int ** asks the program to read int data as pointer objects. Treating a table as a flat int matrix similarly reads address representations as values. Keep declarations compatible with the objects actually present.

Choose a fixed matrix when rows share a known width and adjacent storage is useful. Choose a pointer table when targets differ in length or location, or when address-only reordering matters. The representation should follow the data, not the superficial convenience of bracket syntax.

Mistakes and repairs

Missing parentheses change one pointer-to-array into an array-of-pointers declaration. Read the name outward and draw the first selected object. If that object is a pointer entry, another indirection is required before reaching ints.

Do not traverse every numeric row using the longest row's count. A shorter target does not gain storage because another row is larger. Pair each row with its own valid length.

An initialized outer table does not imply initialized targets. Conversely, valid target arrays do not initialize an unassigned pointer entry. Every arrow needs an actual stored address before use, and every target needs its own valid contents.

A table of const char * entries protects character access, while a table of char *const entries fixes addresses. Do not substitute one qualification for the other when storing literals. Both const levels may be appropriate for a fully read-only view.

Working habits

Write parentheses before filling initializers. Keep row lengths beside jagged targets and review aliases explicitly. Use entry swaps for address reordering, row-pointer increments for fixed-width matrix traversal, and storage-specific ownership rules for cleanup.

Standard and portability notes

Both declaration forms are available throughout standard C. The examples use C17 and C99-style loops. No newer standard makes a row-pointer type equivalent to a table-of-pointers type merely because their access expressions use similar brackets.
