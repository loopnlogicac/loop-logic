Prepare the source before compiling C

When you compile a C program, the compiler does not immediately translate every source character into machine instructions. It first performs preprocessing work such as including header contents and expanding macros. The preprocessor handles this source preparation before ordinary declarations and expressions are compiled.

Think of preparing a lab handout before printing it. You can insert a shared page, replace a short label with its full text, or choose one of two exercise sections. The final handout is what the printer receives. Likewise, the compiler sees the resulting C tokens after preprocessing has selected and expanded the source.

A preprocessor directive begins with # at the start of a logical line, allowing whitespace before it. The familiar #include line is one such directive. It makes declarations from a header available before the compiler checks calls such as printf. A #define can give a replacement token sequence a short name.

Preprocessing is not a runtime function call. An inactive #if branch does not wait for execution to choose it. The source selection happens while translating the program. A macro name inside a C expression is replaced before that expression's types and operators are analyzed. Understanding this timing explains both useful patterns and common surprises.

Read the C notation

An object-like macro gives a name to replacement tokens. The definition #define LAB_CAPACITY 24 makes later uses of LAB_CAPACITY expand to 24. Do not add a semicolon unless that token is intentionally part of the replacement. A macro is not an ordinary C variable declaration.

Directives generally occupy their own logical lines. A backslash immediately followed by a newline continues a logical line. Ordinary statements in main still need their C semicolons after expansion. Keep directive spelling and the resulting C syntax separate when diagnosing an error.

#define LAB_CAPACITY 24
#if LAB_CAPACITY > 20
#define ROOM_LABEL "large"
#endif

Observe the compiler input with gcc -E

The preprocessing phase works with tokens and directives. Included headers can themselves contain more includes, declarations, and macros. Comments are removed during earlier translation processing, with whitespace preserving token separation. Macros expand where their names occur as preprocessing tokens, not as arbitrary substrings inside larger identifiers.

The capacity example begins with a definition and a later printf call. Before the expression is compiled, LAB_CAPACITY becomes 24. The resulting call prints Capacity: 24. Nothing assigns a variable named LAB_CAPACITY at runtime; the compiler instead sees the numeric token where the name appeared.

To inspect this stage with GCC, run gcc -std=c17 -E examples/ex-1.c -o preprocessed.c from the topic directory. The -E option stops after preprocessing. The result is not an executable. It includes expanded header content and line markers, so it may be much longer than the short program you wrote.

Search near main in that result to see the replacement. GCC's -P option suppresses line markers when you want a cleaner text view: gcc -std=c17 -E -P examples/ex-1.c. Use this output as a diagnostic view rather than a file you manually maintain. Your original source and headers remain the intended editing locations.

The conditional example defines GROUP_SIZE as three. The preprocessor evaluates the #if condition, retains the matching puts line, and removes the alternative branch. The C compiler then compiles one call. A runtime if would instead compile both valid branches and choose one during execution.

A #define is active from its position onward until #undef or the end of the translation unit. It does not obey C block scope. A definition written visually inside a function can affect later source outside that function. Keep reusable definitions near headers or configuration sections to avoid this misleading appearance of locality.

PASS_MARK appears in both initialization and comparison. Each occurrence supplies the same numeric replacement. The surrounding C expressions still follow ordinary arithmetic and relational rules. The output is 45 1. Macro expansion is source preparation; it does not create a special integer type or change the comparison's meaning.

GROUP_SIZE expands to three in the #if condition. That condition is true, so the alternative puts line is excluded before compilation. The executable prints three-person group once. This choice is fixed for that build. To choose a group based on a student's runtime input, write an ordinary if instead.

Preprocessing versus ordinary C execution

An ordinary C const object has a type and follows C scope rules. An object-like macro has replacement tokens and follows preprocessing definition rules. A macro can stand for an integer, a string literal, a type fragment, or more complicated text. That flexibility also means type checking happens only after the replacement is inserted.

Preprocessor conditions cannot read a student's entered mark or call a runtime function. They work with permitted preprocessing integer expressions and macro definitions. An unrecognized identifier in #if is replaced with zero after macro processing, which can hide a misspelled configuration name. Compiler options such as -Wundef can help reveal that mistake.

The include directive does not itself link a library implementation. It provides declarations and related source definitions for compilation. Linking is a later stage. Including math.h can make a function declaration visible while a platform still requires a separate linker option for its implementation. Keep header inclusion and library linking as distinct steps.

Not every directive is portable in meaning. A recognized #pragma may control implementation-specific behavior. #pragma once is common but not guaranteed by C17. Standard macro-based include guards, taught in Header Files and Include Guards, express repeated-inclusion protection using portable directives.

Mistakes and repairs

Adding a statement semicolon to a numeric macro

#define PASS_MARK 40; expands inside an expression as extra punctuation. A later comparison can become syntactically invalid. Define the replacement as 40 and leave semicolons at the ends of ordinary C statements. Inspect -E output when the error points at an apparently harmless macro use.

Expecting a runtime value in #if

#if mark>=40 cannot select source based on a value read by scanf. mark is not a macro carrying that runtime value. Use an ordinary if inside the function for student input. Use #if for build configuration that is known during translation.

Habits to use in your programs

Keep configuration macros few, clearly named, and easy to locate. Prefer ordinary typed values or functions when preprocessing does not add a needed capability. Use -E to inspect confusing expansion rather than guessing from the macro's name. Keep generated intermediate text outside your maintained source files.

Document any required build flags near the interface they configure. If several files depend on the same macro, ensure they use a consistent configuration. A mismatch can create incompatible declarations or layouts even when each file compiles separately. Source preparation is part of the program's design, not decorative syntax.

C versions and portability

The core include, define, undef, and conditional directives are present in C89 and later. All programs here run as C17. GCC's -E and -P options are compiler tools rather than C syntax. C23 adds preprocessing facilities such as #embed; they are not part of this C17 lesson's executable examples.
