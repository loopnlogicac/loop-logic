Give a program its instructions before it starts

Suppose you want the same program to add a different set of marks each time. A menu can ask for numbers after launch. A command-line utility takes its instructions in the launch command instead: sum 20 -8 3. This makes it easy to repeat an operation, combine it with scripts and record exactly which operands were used.

The program receives strings, not automatically converted integers. The shell prepares those strings before C begins. Spaces normally separate arguments; shell quoting can keep spaces inside one argument. For example, a quoted college name reaches the program as one string. Quote syntax belongs to the shell, so it may differ between operating systems. C works with the already-separated strings.

You will walk that argument list, convert complete decimal operands and add them without signed overflow. Each stage answers a different question: is the right number of operands present, is this text a valid integer, and can the intended calculation fit the chosen type? Keeping those questions separate makes an invalid launch much easier to explain.

Read the count and the string array

A hosted entry point can be written int main(int argc, char *argv[]). argc is a nonnegative count. argv is an array-like collection of pointers to null-terminated strings. The usual invocation includes the program-name string at index zero, followed by the user arguments. A loop from one while the index is less than argc visits only the user arguments.

The pointer at argv[argc] is null. That is not an empty string. An empty argument has a valid pointer whose first character is the string terminator. Do not dereference the sentinel or pass it to %s. Check the count before accessing argv[1], and do not assume that argv[0] has a useful, portable spelling.

Arguments remain strings even when they look numeric. long value = strtol(text, &end, 10) requests base-ten conversion and stores the first unconverted position in end. The declaration needs stdlib.h; errno and ERANGE need errno.h. limits.h provides LONG_MIN and LONG_MAX for arithmetic guards. No header guesses the application's acceptable mark or operand range for you.

Ask three questions about each conversion

First ask whether any digits were read. strtol accepts an optional sign and leading whitespace. A string containing only a sign still has no digits, so end equals the original pointer. The returned zero alone cannot distinguish this case from the valid operand zero. An empty string fails the same no-digit test.

Second ask whether unwanted text remains. For this utility, *end must be the terminator. Thus 12kg and 12 followed by a space are rejected, even though their numeric prefixes convert. Accepting leading whitespace but rejecting trailing whitespace is a deliberate policy, inherited from strtol at the front and our whole-string check at the end. A different tool may trim both ends, but it must state that choice.

Third ask whether conversion overflowed. Set errno to zero immediately before strtol, then reject ERANGE. A successful conversion need not reset an old error value. The result can equal LONG_MIN or LONG_MAX legitimately, so a boundary value by itself does not prove failure. Use the documented error indication together with the conversion result.

Only after these checks should the helper assign through its result pointer. This preserves the caller's previous value on rejection. The surrounding program can then apply a narrower rule, such as marks from zero through one hundred. General numeric syntax, the long type's range and the application's range are three distinct layers.

Inspect, reject and safely accumulate arguments

Walk the arguments without assuming a nonempty program name

The shell supplies two arguments, although the first contains a space. The program starts at index one and checks the null pointer sentinel without passing it to %s. It does not print the host-specific spelling of argv[0].

Reject a numeric prefix that leaves trailing characters

The supplied argument is 12kg. strtol can convert its prefix, but end points at k. The helper rejects the whole argument rather than silently treating a measurement as the integer 12. It leaves the caller destination untouched on failure.

Check each addition before summing signed arguments

The three signed values produce 15. Parsing and addition have separate range checks: each argument may fit long while their total does not. The subtraction bounds are evaluated only in the sign branch where they are representable.

Treat an empty argument as missing digits

A shell can pass an empty string as an argument. No conversion happens, so end equals the original pointer. The output also confirms that rejection does not overwrite a previously valid caller value.

Guard arithmetic before performing it

Three individually valid long operands do not guarantee a valid long total. Imagine that total already equals LONG_MAX and the next operand is one. Computing the addition first invokes undefined behavior; inspecting a wrapped result afterwards cannot repair that operation. A correct guard must run before the addition.

When value is positive, compare total with LONG_MAX minus value. When value is negative, compare total with LONG_MIN minus value. These subtractions are representable in their respective sign branches. If the bound is crossed, report failure without adding. Zero changes nothing and needs no special range calculation.

The example rejects the first overflowing prefix. That policy is stronger than asking whether the final mathematical sum would fit after all later operands. For instance, a positive overflow followed by a compensating negative operand still fails. Supporting arbitrary intermediate totals would require a different representation or algorithm, rather than temporarily overflowing a signed long.

Do not let convenience hide an invalid launch

atoi is tempting because its call is short. It offers no end pointer to expose a suffix and no suitable conversion-range report for this validator. Treating atoi's zero as an error also rejects a legitimate zero. Use strtol when callers deserve a clear distinction between invalid text and a valid numeric value.

Another mistake starts an argv loop at zero and tries to convert the program name. Start ordinary operand loops at one. A missing operand is a usage problem, while an empty operand is a present but invalid value. Both should produce a nonzero exit status here, but their explanations can differ.

A negative integer such as -8 is not automatically an unknown option. If a later version accepts --help, recognise its documented spelling and define how -- ends option parsing. Do not strip every leading dash before conversion; doing so changes the numeric value. Likewise, do not invent quote-removal logic inside the number parser after the shell has already handled quoting.

Finally, printing a friendly error and returning zero misleads scripts that rely on the exit status. The examples return failure for bad usage, malformed operands and out-of-range totals. Successful output is printed only after all operands pass. This prevents a partially processed sum from looking like a completed answer.

Choose cases that separate the contracts

Test a single zero, a positive value, a negative value and a mixed-sign sum. Then test no operands, a quoted empty string, a sign without digits, a valid prefix with junk and a decimal outside the long range. Add a representable boundary followed by an operand that would overflow the total. These cases exercise different decisions rather than repeating one ordinary addition.

The line-based practice tasks model one argument at a time so that you can focus on validation independently of launching a process. Their input-size bounds are stated explicitly. When turning a line-based helper into an unrestricted file importer, add an overlong-line policy from file error handling; do not silently accept a truncated prefix.

Strings become operands only after validation

  • Check argc before indexing user arguments.
  • Keep the null sentinel distinct from an empty argument.
  • Use strtol to check digits, trailing text and conversion range.
  • Check each signed addition before changing the running total.
  • Return failure when usage or numeric validation fails.
