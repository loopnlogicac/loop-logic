A successful compile is not a promise about every execution

An array has four marks, but a program asks for mark number five. The compiler may still produce an executable. C does not automatically turn that access into a friendly bounds exception. The program has stepped outside the rules that make its behavior meaningful. A familiar-looking result on one machine cannot make the access valid.

Undefined behavior means that the C standard imposes no requirements on the affected execution. This is stronger than “the answer may vary.” The program may crash, appear to work, produce misleading output or be transformed by optimisation in ways that defeat a guessed machine-level trace. Your job is to remove the invalid operation, not memorise the output of one compiler run.

Some variation is permitted and still well-defined within stated choices. Distinguishing those categories helps you answer exam questions honestly. Before tracing a tricky expression, ask whether its accesses, arithmetic and lifetimes are valid at all. A valid trace starts with the language rules, not with an observed accident.

Three categories with different obligations

CategoryMeaningExample
UndefinedNo requirements on the affected executionSigned overflow
UnspecifiedOne of the permitted choicesOrder of independent argument evaluations
Implementation-definedA permitted choice documented by the implementationWhether plain char is signed

An unspecified choice need not be stable between calls. If two argument expressions are independent, either permitted order can produce a valid execution. If they conflict through unsequenced modifications of the same scalar object, the issue can instead be undefined behavior. The word order alone is not enough to classify the expression.

Implementation-defined does not mean that every compiler must choose the same answer. It means you can consult the implementation's documentation and use that choice when targeting that implementation. Portable code either avoids depending on the choice or explicitly states and checks its environmental assumptions.

A constraint violation is another useful distinction: the implementation must issue a diagnostic for violations such as assigning through a const-qualified lvalue. Runtime undefined behavior may require no such diagnostic. Keeping compiler warnings clean is valuable, but silence does not certify the validity of every possible input.

Check the assumptions behind each operation

Start with storage. A pointer must identify a suitable live object before you dereference it. Null, dangling and arbitrary pointers do not become valid because their numeric-looking representations seem plausible. Returning the address of an automatic local leaves a pointer to an object whose lifetime has ended. Reading it later is not a delayed copy of the former value.

Next check array boundaries. The valid element indices of a three-element array are zero, one and two. A pointer one past the array may be formed as a stop marker, but cannot be dereferenced. Forming a pointer farther beyond the array already violates the pointer-arithmetic rules; waiting until dereference is not a general repair.

Then check arithmetic. Signed addition, subtraction and multiplication must stay within the result type's range. Division needs a nonzero divisor, and INT_MIN divided by -1 is also invalid when that quotient is not representable. Shift counts must be nonnegative and smaller than the width of the promoted left operand. Unsigned types provide defined modular arithmetic, but do not legalise an invalid shift count.

Finally check sequencing. In C17, i = i++ contains conflicting unsequenced modifications. Choosing a supposed left-to-right order does not give it a portable answer. Separate the desired read, increment and assignment into full expressions so that the intended relationship is explicit. Different valid repairs may express different intentions, so identify the intended algorithm first.

Valid repairs beside one explicitly invalid operation

Guard an addition before signed overflow can occur

The first addition is rejected without evaluating INT_MAX + 1. The caller value remains 99. The valid addition then stores twelve. This is a precondition check, not an attempt to detect overflow after it has already happened.

Form a one-past pointer without dereferencing it

The end pointer is a valid loop boundary for this array. The loop never dereferences it. Forming arbitrary pointers beyond one past, or subtracting pointers to unrelated arrays, does not inherit this guarantee.

Replace an unsequenced update with explicit statements

Separate full expressions establish the intended order. The program deliberately does not use i = i++, whose competing unsequenced modifications have undefined behavior in C17. The repair states which value should be kept rather than guessing a compiler order.

Compile an intentional signed-overflow defect without predicting output

This program intentionally has undefined behavior when it evaluates the signed addition. There is no correct expected numeric output. A local undefined-behavior sanitizer run can diagnose the operation, but ordinary compilation does not make it valid.

Recognise the common families

An uninitialised automatic variable is not a source of useful arbitrary data. Initialise it before a path reads its value. A failed scanf can leave its destination unchanged or never assigned, so process input only after the required conversion count succeeds. An old value left after failure is not a newly read record.

String functions require their own boundaries. strlen and %s need an accessible terminator. strcpy needs enough writable destination space. A missing terminator can turn a small logical error into a read outside the object. Overlapping regions require an operation whose contract permits overlap, such as memmove rather than an unjustified memcpy.

Lifetime errors include using memory after free, freeing an allocation twice and freeing a pointer that was never returned as a suitable allocation base. Set and update ownership rules instead of scattering free calls until a crash disappears. Nulling one pointer does not repair other aliases that still point at released storage.

Library contracts matter too. A printf format must match the actual promoted argument types. A comparator passed to qsort must define a consistent ordering; subtracting arbitrary signed integers can overflow inside the comparator. Look for a valid operation at every layer, including helpers that appear too small to deserve review.

Use a diagnostic instrument with a stated scope

For local investigation, build with gcc -std=c17 -Wall -Wextra -Wpedantic -g -O1 -fsanitize=undefined -fno-sanitize-recover=undefined example.c -o example. Running the intentional overflow example under this instrumentation reports the invalid signed addition and stops. The exact diagnostic wording is compiler-specific; it is not a valid numeric answer for the undefined program.

Undefined-behavior instrumentation checks many arithmetic and related operations, but no single tool catches every possible defect. AddressSanitizer can help with many memory errors and is commonly enabled with a separate or combined address instrumentation option where supported. Neither tool replaces input validation, ownership reasoning or a correct library contract.

Dynamic instruments observe executed paths. A clean run on one index says little about an untested first-invalid index. Choose boundary inputs deliberately: empty input, zero sizes, maximum valid indices, one-past attempts and arithmetic limits. Keep intentional invalid examples separate from production code, and never assign them invented expected output.

Avoid reasoning from an accident

Using a debug result as a language rule

Unoptimised code may happen to preserve a value after an invalid access. Optimised code may expose the defect differently. Neither run decides what C guarantees. Remove the out-of-bounds access or invalid lifetime before comparing algorithm results.

Checking after the dangerous expression

A negative total is not a reliable signed-overflow detector. The operation may already be undefined. Establish the representable bounds first, as the safe-add example does, then compute only on the accepted path.

Calling every uncertain result unspecified

Unspecified behavior still has a permitted set of choices. Undefined behavior does not promise that a compiler will pick one of your proposed numeric options. In an exam, explain the violated rule rather than guessing the value seen in a lab session.

Suppressing the warning instead of repairing the cause

A cast or warning flag can hide a symptom while leaving the invalid access intact. Keep diagnostics enabled and repair the type, size, sequencing or ownership contract that the warning identifies.

A small review before an output trace

Consider a loop that visits indices zero through count minus one. First establish that count does not exceed the allocated element count. Next establish that every visited element was initialised. Then check that the sum of those elements fits the accumulator type. These are separate facts: a correct index bound does not prevent arithmetic overflow, and a wide accumulator does not initialise missing elements.

Only after those checks should you build a table of index, selected element and running total. If a row would require an invalid access, stop the trace and name the violated precondition. Continuing with a guessed value creates a misleading answer even when later arithmetic happens to look reasonable. A good explanation distinguishes the repaired program's valid trace from the original program's missing guarantee.

State the language version before a sequencing argument

This lesson reasons under C17 and uses GCC instrumentation as a development aid. Do not transfer a C++ sequencing rule into C because the expression looks similar. Language revisions can change particular rules or add checked facilities, but they do not make a general “compiled successfully” argument sufficient. Consult the selected standard and compiler documentation for the exact feature being used.
