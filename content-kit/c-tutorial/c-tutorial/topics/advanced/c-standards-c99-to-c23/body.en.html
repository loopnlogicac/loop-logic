Pick the language your tools actually speak

A classmate sends a short C program that works on their laptop but fails on yours at nullptr. The problem may be a language-version mismatch rather than a broken installation. C has developed through several standards, and compilers implement those standards over time. A source file's .c extension does not tell you which revision it requires.

Think of a standard as an agreed vocabulary and a compiler version as a speaker learning that vocabulary. Choosing a mode asks the compiler to use a particular language rule set. It does not prove that every newer word has been implemented. Good portability notes name both the intended baseline and the actual feature support.

This tutorial normally uses C17. The examples below select older or newer modes deliberately to show where useful features entered the language. Keep ordinary application code at the baseline you have chosen rather than adopting a new spelling accidentally and discovering the dependency on a different machine.

Select a standard and keep extensions visible

GCC accepts switches such as -std=c99, -std=c11 and -std=c17. GCC 14.2 uses -std=c2x for its developing C23 support. Keep -Wall, -Wextra and -Wpedantic enabled to expose suspicious code and extensions; -Werror makes warnings fail a strict build. A permissive default can accept extensions that an explicitly selected mode would diagnose.

The predefined macro __STDC_VERSION__ helps identify the selected standard's advertised version, but it is not a complete per-feature support test. Version-specific compiler documentation and a small compile test are useful when adopting a particular newer facility. Build every source file in a project with a consistent intended language mode.

Switching to an older mode does not translate newer syntax for you. If a project requires C99, replace or conditionally exclude later constructs and test the actual C99 build. A comment saying “portable C” is less useful than a reproducible command and a clear list of environmental assumptions.

Follow the main changes through the revisions

C99 made everyday code more expressive. You can declare a loop variable in the for initialiser, mix declarations with statements and use // comments. Designated initialisers assign named members, and compound literals create unnamed objects with an explicit type. These features reduce awkward temporary variables but still require correct lifetimes and bounds.

C99 also introduced facilities such as inline, restrict and variable-length arrays. Each has its own rules; do not treat them as automatic speed improvements. Later standards permit implementations to omit some optional facilities, so a feature's introduction date alone is not a universal availability guarantee. Use the subset your target tools actually support.

C11 added compile-time assertions with _Static_assert, anonymous structures and unions, and facilities for atomics and threads. Some library or language facilities have optional-support details. A static assertion checks a constant condition during translation; it cannot inspect a mark typed later by the user. Anonymous nested members can simplify access but should not hide an unnecessarily complicated layout.

C11 removed gets. That function cannot receive the destination size, so no caller can make it safe for unrestricted input. Replacing it requires a bounded-input design, not a warning-suppression flag. C17 then focused on corrections and clarifications to C11 rather than a broad set of new syntax.

C23 adds keyword bool, true and false, nullptr, typeof, binary integer literals and digit separators among many changes. Earlier C17 code normally obtains bool through stdbool.h. The new spellings can improve clarity, but only use them when the compiler and project baseline support them. Do not silently change the required language version of a shared module.

Compile representative features in their intended modes

Use C99 loop declarations and designated initialisers

C99 permits declaring i in the for initialiser and assigning structure members by name. Designated initialisers reduce dependence on member order. Compile this example in C99 mode rather than assuming an old default compiler mode.

Use a C11 assertion and an anonymous nested structure

The assertion checks a compile-time condition. The unnamed nested structure exposes x and y through point directly; it does not allocate a second dynamic object. C11 also removed gets from the standard library.

Try supported C23 spelling without changing the C17 baseline

GCC 14.2 accepts these C23 features in -std=c2x mode: keyword bool/true/false, nullptr, typeof, binary literals and digit separators. This does not imply that the same compiler implements every C23 facility, especially #embed.

Reject the removed unbounded gets interface

This intentionally invalid C17 program uses gets, which was removed in C11. It has no buffer-size argument and cannot be made safe by choosing a larger array. The strict compiler rejects its missing declaration; use bounded fgets and define an overlong-line policy.

Understand #embed without claiming unsupported execution

A supporting C23 compiler can use #embed to incorporate resource bytes during translation. A typical use is a byte-array initializer containing a small image or fixed lookup resource. Unlike fopen, this does not ask the running program to find a file later; the resource becomes part of the build inputs and generated program data.

The GCC 14.2 toolchain used for the examples does not implement #embed. Its acceptance of -std=c2x and the displayed C23 keywords is therefore not evidence that this directive works. Use a newer supporting implementation and a separate feature check when a project needs it. A generated reviewed byte-array initializer is one possible fallback, with its own build dependency.

Similarly, typeof can name an expression's type but does not make every expression safe to evaluate or every inferred interface readable. nullptr has a dedicated null-pointer role; it is not an allocation and cannot be dereferenced. New syntax removes some awkward spellings, not the need for pointer lifetime and access rules.

Do not confuse acceptance, support and safety

Relying on a compiler extension

A compiler may accept binary literals in an older mode as an extension. That does not move their standard introduction date backwards. A pedantic build helps reveal when source compatibility depends on implementation extensions rather than the selected standard.

Assuming C and C++ share every rule

Similar punctuation can hide different language rules and version histories. Use the C documentation for C code. In particular, do not import a C++ sequencing argument or declaration rule without checking the selected C standard.

Using version changes as input validation

C23 does not make an out-of-bounds array access safe. C11's removal of gets does not make an unbounded replacement safe. Keep ranges, ownership and error checks explicit in every version.

Advertising a feature that was never compiled

A compiler accepting one new keyword says nothing about another directive. Separate demonstrated working features from explanatory coverage and unsupported facilities. This makes another student's build failure understandable rather than mysterious.

Document the baseline and the exceptions

The package baseline remains C17. The first two examples explicitly select C99 and C11, while the third selects the supported subset of C23 in GCC 14.2. The intentional gets example is expected to fail under the strict C17 build. These are separate language-mode decisions, not a recommendation to mix incompatible declarations across one executable.

Make compatibility a checkable claim

Name the selected standard, know why each newer feature is needed and verify support on the target compiler. Keep unsupported facilities clearly marked. Next, coding style and best practices turns these technical choices into code that another student can read and maintain.
