Write for the next person who reads the code

A program can calculate the right answer and still be difficult to change safely. Imagine finding x, y and z in a marks report a month after writing it. Names such as mark_count and pass_count save you from reconstructing their meaning. Good style makes the intended behavior visible before a reader begins a detailed trace.

Style is not decoration added after correctness. Clear boundaries help you notice a missing validation branch, an accidental extra statement or a misleading rounding assumption. Consistency also reduces the effort needed to compare related functions. Use the team's agreed convention when working in an existing project rather than reformatting unrelated code to your personal taste.

Names, indentation and braces should reveal structure

Choose names for the job or value they represent: amount_due, pass_count and input_file are more useful than temp2. A short loop index such as i is reasonable in a small local loop. A long-lived value deserves a name that survives beyond the line where it is declared. Avoid abbreviations that force every reader to learn a private dictionary.

Use four-space indentation here and braces around every branch and loop body. Keep lines short enough to inspect without horizontal scrolling. A brace makes the controlled block explicit even when it currently contains one statement. When a second statement is added later, it is less likely to escape the condition by accident.

Name policy values such as PASS_MARK instead of repeating unexplained numbers. Do not replace every literal mechanically: zero as a loop start is usually clear. Name values whose meaning or future change affects the program's policy, and keep each name close to the scope where it belongs.

Give functions a coherent job

The grading example separates has_passed from display. A helper with a clear question can return a direct answer and be reused from a menu, a file report or a test. A helper that prompts, calculates, writes a file and terminates the program has several reasons to change and is harder to reuse safely.

Small does not mean one line at any cost. Keep operations together when they form one understandable step. Pass the required data explicitly and avoid hidden mutable globals when a parameter will do. Use const-qualified access for readers so that the function's type matches its role.

Validate input before passing accepted values into the calculation. Handle failure deliberately rather than burying it in a helper that quietly substitutes zero. The fee example documents a bounded nonnegative domain and whole-taka rounding. Those details matter more than whether the helper could be shortened by a few characters.

Explain the reason a reader cannot see in the expression

A comment saying “increment i” above ++i contributes little. A comment explaining why an amount is rounded down can prevent a future accidental change. Useful comments describe a contract, a domain assumption, a unit or a non-obvious algorithm choice. Prefer clear code over a long explanation of an avoidably confusing expression.

Comments are promises that need maintenance. If a policy changes, review the explanation and the examples that distinguish the policies. An inaccurate comment is worse than a missing one because it confidently directs the reader toward the wrong interpretation. Keep units such as taka, cents or milliseconds visible in names or nearby documentation.

Do not leave large commented-out blocks as a second unofficial implementation. Version control can retain earlier designs. Explain the active approach and remove dead alternatives when they no longer help the current reader. A focused function and one clear reason are easier to trust than several competing stories.

Modernise habits without hiding behavior

Copying an obsolete classroom environment

conio.h, clrscr and getch are not standard C interfaces. A hosted program should use an int-returning main and standard headers for ordinary console work. Run the program in a terminal that preserves its output instead of adding an unexplained pause to every exercise.

Suppressing warnings to obtain a clean screen

Compile with -std=c17 -Wall -Wextra -Wpedantic -Werror. Read the first useful diagnostic and repair its cause. A cast can sometimes express an intentional conversion, but it should follow range reasoning rather than conceal a mismatch. Keep all source files under the same warning policy.

Compressing unrelated decisions into one expression

A dense line can hide evaluation order, short-circuit effects and state changes. Give validation, calculation and reporting separate names or statements when that makes their relationship clearer. Short source is not automatically simple behavior.

Reformatting unrelated code during a small fix

A review should make the behavioral change easy to find. Follow local conventions in the lines you touch and keep broad style changes separate when needed. Consistency serves understanding; it should not overwhelm the actual reason for the edit.

Read the function from its caller’s point of view

Before considering a function finished, ask what a caller must know: accepted ranges, ownership, mutation, failure and units. The name and type should communicate as much as possible. Put the remaining assumptions in a short explanation near the interface. A caller should not have to inspect a private loop to discover that an empty list is forbidden.
