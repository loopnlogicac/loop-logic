Failure is a result the caller needs to understand

A mark parser can read a valid zero, encounter a word or receive a number above one hundred. Returning zero for all three outcomes forces the caller to guess. Error handling begins with a better interface: separate the useful result from the reason why no result was produced.

Picture a service desk returning either your requested document or a clear explanation of what is missing. A vague shrug makes you repeat the request without knowing what to change. A useful program similarly distinguishes invalid input, unavailable resources and ordinary absence. The distinction guides whether to correct, retry, skip or stop.

C provides return values, output parameters, enums, errno and process exit statuses, but no single universal exception mechanism for ordinary failures. You choose a convention for each interface and use it consistently. The goal is a caller that can decide the next step without reading private implementation details.

Give status and data separate meanings

A small status enum can name PARSE_OK, PARSE_SYNTAX and PARSE_RANGE. An output pointer carries the parsed mark only when status is PARSE_OK. State that the pointer must be valid and that failure leaves the pointed-to value unchanged. Those statements are part of the function contract, not incidental details of one implementation.

Some interfaces return a pointer and use null for failure. Others return a count, with a documented sentinel or partial-count meaning. Follow the interface's actual convention. Treating every zero as failure is wrong for functions that legitimately produce zero items or the number zero. Treating every nonnegative value as success is equally wrong when the result is an assignment count smaller than required.

For application-level operations, names are often clearer than scattered magic integers. A withdrawal can return WITHDRAW_OK, BAD_AMOUNT or INSUFFICIENT. Keep the meanings stable across callers. If a new failure category is added, review every decision point that interprets the enum rather than assuming an old default branch remains correct.

Validate, commit and then report

Begin by validating arguments that can be checked safely: a count is within its allowed range, a required pointer is not null when null is an allowed request to reject, and an amount is positive. A nonnull pointer alone does not prove valid storage or lifetime. Some assumptions remain caller obligations and should be documented explicitly.

Next perform the operation without exposing an unwanted partial state. The withdrawal example checks the amount before subtracting. On rejection, the balance remains unchanged. This is a small failure guarantee: a caller can inspect the old balance without reconstructing what a half-finished operation did.

For a compound operation, identify its commit point. Reading and validating a replacement record in temporary storage before assigning it can prevent partial updates. A file replacement requires more care because output can fail after bytes have been written. An in-memory rollback promise does not automatically extend to files, external services or concurrent readers.

Finally report a status that reflects every required stage. A successful calculation followed by a failed required write is not an entirely successful operation. Keep intermediate progress separate from the final result. Callers that need partial success must receive an explicit count or detailed result rather than a misleading all-or-nothing message.

Use errno only for a documented purpose

errno is a modifiable error-reporting value used by particular library interfaces. It is not a universal register containing the reason for the most recent unsuccessful idea. Check an operation's return value first, then consult errno when that interface documents its relevance. A successful call need not clear an older value.

strtol provides a concrete pattern. Set errno to zero before conversion, examine the end pointer and inspect ERANGE for a range failure. Save an error value promptly if reporting or cleanup must happen before the diagnostic is printed. An intervening function may change errno, so a later perror call can otherwise describe the wrong stage.

perror writes the supplied prefix and the message associated with current errno to standard error. Include the operation name in the prefix. The wording depends on the host and locale and is intended for people, not as a stable machine protocol. Return an enum or code when another program component needs to distinguish failure categories.

Do not use perror to explain an application rule unless a meaningful errno value actually belongs to that failure. An insufficient balance is not automatically an operating-system error. Give it the application's own status and explanation rather than printing a stale file-system message.

Keep responsibility visible on every path

A function that acquires a resource normally owns the duty to release it unless ownership is explicitly transferred. Initialise resource variables to safe empty states, then track which acquisitions succeeded. On failure, release only the resources that actually exist. Closing a null FILE pointer is not a harmless substitute for that reasoning.

Reverse acquisition order is often a convenient cleanup order, especially when later resources depend on earlier ones. Preserve the first meaningful failure before cleanup. Still record or report secondary failures when they affect the application's outcome. A close failure can matter for buffered output even if the earlier write calls appeared successful.

A single cleanup section reached by carefully structured branches can be clearer than duplicating releases in many places. A small function with early returns can also be clear when no resource is outstanding. Choose the control flow that makes ownership easy to verify; neither a blanket ban on early returns nor unrestricted jumps guarantees correctness.

Never combine required cleanup calls with short-circuit operators when one failure could skip another release. Attempt each owned close independently. Do not retry a close using the same FILE pointer after fclose has been called. The file-handling lessons show that stream lifetime and the close result must be considered separately.

Let the application boundary choose the policy

A reusable helper should usually return failure rather than end the process. Its caller may ask for another value, display a form error, log a problem or abort a larger workflow. Calling exit inside the helper removes those choices and makes isolated testing harder. Keep termination close to main unless the interface explicitly promises process termination.

Returning EXIT_SUCCESS or EXIT_FAILURE from main communicates the overall result to the environment. A printed error followed by a success status can mislead a script even if a person notices the text. Conversely, a normal not-found search may be ordinary application data rather than a fatal program error. Decide the policy at the level that understands the user's operation.

Retries need a reason to expect change and a limit. Repeating a malformed conversion without consuming input cannot repair it. Repeating a non-idempotent external action may duplicate its effects. Before retrying, state what was completed, what remains safe to repeat and how the caller learns that the retry limit was reached.

Errors should remain specific and actionable

Overwriting the first failure

A later cleanup problem can replace errno and hide the original read error. Save the first stage and its documented information promptly. Report secondary failures without pretending they were the initial cause.

Changing state before validation finishes

Subtracting first and adding back on rejection complicates reasoning and can itself overflow. Validate the withdrawal conditions before changing the balance. For larger operations, design temporary state and an explicit commit step.

Catching everything with one success-shaped default

A default branch that treats unknown statuses as success hides future failures. Handle the known categories deliberately and make unexpected states visible during development. Keep human messages and machine-readable statuses consistent.

Explicit conventions in C17

The examples use established C17 enums, errno reporting and standard process status macros. The huge conversion example is scoped to the documented GCC host's long range; its standard-error wording is host-dependent. More complex applications may adopt richer result structures, but their ownership and failure guarantees still need to be stated explicitly.

A good failure result preserves choices

Write the success and failure promises beside the function declaration. Separate status from data, validate before mutation, preserve useful diagnostics and release what you own.
