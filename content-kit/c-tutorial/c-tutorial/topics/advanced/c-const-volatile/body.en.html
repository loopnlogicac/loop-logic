A label describes how you may use a value

A marks report should read marks without changing them. A hardware status value, by contrast, may change even when your program has not assigned it. C has different qualifiers for these different promises. const limits modification through a qualified access path. volatile tells the implementation that certain accesses matter and must follow its volatile-access rules.

Imagine a notice board behind glass. You can read it but cannot write through your viewing window. Someone with a valid key may still update an ordinary board. That is a useful first picture for a const pointer to an originally mutable object. Do not stretch the picture into a claim that an actually const-defined object can be changed safely by removing the glass with a cast.

This distinction matters in function interfaces, pointer declarations and low-level systems code. The safest starting question is practical: who may write this object, through which access, and what can change it? Choose qualifiers to answer that question rather than adding keywords until a warning disappears.

Read the pointed-to type and pointer separately

In const int *view, the pointed-to int is const-qualified. The pointer variable can be reassigned, but an assignment through *view is not permitted. In int *const fixed, the pointer object is const-qualified. It must be initialised appropriately and cannot later point elsewhere, while *fixed remains writable if it names a mutable int.

The form const int *const fixed_view combines both restrictions. Read the declaration in two pieces: what access is allowed to the pointee, and may this pointer variable change? Writing small assignments on paper is often clearer than memorising a slogan about which side a keyword appears on.

An array parameter written const int marks[] adjusts to a pointer parameter whose elements cannot be modified through that parameter. It does not copy the array. The caller still supplies valid storage and a correct count. const neither checks bounds nor extends the lifetime of an array that has already ceased to exist.

The declaration volatile unsigned int status qualifies the object accesses in a different way. A pointer to a volatile register must preserve the appropriate pointee qualifier. A const volatile view can permit reading an externally changing status value while forbidding program writes through that view. Actual device addresses and valid access widths come from the target documentation.

Follow the access path rather than the spelling alone

The first example passes a mutable marks array to a read-only helper. Inside the helper, writing marks[0] would violate its parameter type. Back in main, assigning a new first mark is valid. The next call sees the update because the function reads the same array rather than a frozen copy.

The pointer example then separates two often-confused operations. Reassigning view changes which object it names. Writing *owner changes the object already named by a fixed pointer. Reassigning a pointer does not relocate either int object. These operations concern different objects: the pointer and the int. An object originally defined const is a stronger boundary. Modifying it through a cast-away qualifier has undefined behavior, even if the storage happens to be writable on one machine. The cast changes an expression's type; it does not change how the object was defined. A compiler accepting the cast is not permission to perform the later write.

Const correctness means preserving these promises through calls. A reader should accept a pointer to const data when it does not need to mutate it. That allows both mutable and const callers to use the operation. A writer should request writable access honestly. Avoid weakening a reader's interface because one internal helper was declared carelessly.

Read an array through a const-qualified parameter

The function promises not to change elements through its parameter. The original array remains mutable in main, which changes its first mark between calls. const restricts an access path; it does not make every alias to an originally mutable object read-only.

Separate pointer reassignment from pointee modification

view can point elsewhere but cannot modify an int through that pointer. owner cannot be reassigned, but it can modify first. const int *const would combine both access restrictions.

What volatile does and does not promise

A compiler may normally remove or combine ordinary accesses when no observable program behavior changes. A volatile-qualified access has special significance under the implementation's rules. This is useful when a memory location represents a device register whose reads or writes have externally visible meaning. The implementation must document what counts as an access.

volatile does not mean that the value changes randomly, that every expression is evaluated twice, or that an operation becomes indivisible. An increment still involves reading, computing and writing. If hardware or another execution agent can interfere between those stages, the qualifier does not automatically prevent that interference.

For threads, use the appropriate atomic operations or locks. A volatile flag does not establish the ordering needed to publish ordinary data safely to another thread. Conflicting unsynchronised accesses can still be a data race. Memory-mapped device ordering may also require target-specific barriers beyond the qualifier.

Signals have their own narrow rules. A suitable volatile sig_atomic_t flag is a common simple communication pattern with a signal handler, but that does not license arbitrary library calls or complex shared structures inside the handler. The hosted simulation here installs no handler and makes no concurrency claim. Its output is deterministic because one thread performs every assignment.

Read a status bit with unsigned arithmetic

The status example uses bit two as a ready flag. Bit positions count from zero, so its mask is 1U << 2, representing four. AND with the mask selects that bit. Comparing the selected result with zero turns it into a clear true-or-false answer without assuming the result itself equals one.

Use unsigned values for this kind of bit work and keep shift counts below the type's width. A negative shift count or one at least as large as the promoted left operand's width is invalid. Unsigned arithmetic avoids signed-shift surprises, but it does not make every shift count legal.

Setting a bit uses OR with its mask; clearing it uses AND with the complemented mask; toggling uses XOR. These operations preserve unrelated bits in an ordinary variable. A real device register may have special write-one-to-clear or read-side-effect behavior, so copying this read-modify-write pattern to hardware requires its manual. A software simulation teaches the arithmetic, not the device's protocol.

Keep each promise narrow and truthful

Casting away an inconvenient warning

If a function only reads data, repair its parameter type instead of casting the caller's const pointer. If it must write, the caller must supply writable storage. Casting a string literal to char * does not make modifying that literal valid.

Calling const an integer constant expression

In C17, a const int object is not automatically an integer constant expression. Some contexts require such an expression and cannot use that object merely because it is read-only. Use an appropriate enum constant or macro when the language requires a compile-time integer constant.

Treating volatile as a general safety switch

Adding volatile to every variable can obscure the actual access policy and restrict optimisation without solving bounds, lifetime or concurrency bugs. First identify the external effect that makes a particular access special. For ordinary shared-thread state, choose a real synchronisation design.

Dropping qualifiers through nested pointers

The safe-looking conversion from int * to const int * does not extend freely to every pointer depth. Nested-pointer qualification has additional compatibility rules. Do not force int ** into const int ** with a cast; redesign the interface or use the exact compatible type.

Established qualifiers with target-specific device rules

These examples use const and volatile under C17. They require no device mappings and no assumptions about the width of int beyond its standard minimum for the small masks used. Real embedded code must consult its compiler and hardware documentation. Later language facilities for atomic access serve a different purpose and should not be inferred from volatile alone.

Choose the qualifier that matches the operation

Use const for a truthful read-only interface, distinguish the pointer from its pointee, and reserve volatile for accesses whose external significance is documented.
