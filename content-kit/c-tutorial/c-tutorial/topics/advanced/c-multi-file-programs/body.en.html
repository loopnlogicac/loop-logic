Give each part of a growing program a clear home

A small marks program fits in one file. Add reports, validation and storage, and scrolling becomes harder than understanding the calculation. Splitting the program gives each part a clear job. A client asks how many students passed; a marks module knows how to count them. The client should not need to know the module's helper names.

Think of a header as a notice on a service desk. It tells callers which operations are available and what arguments they accept. The source file behind the desk performs the work. Changing the private method should not force callers to learn a new interface when the promised operation remains the same.

Multiple files do not create runtime processes or automatically isolate memory. They create separate compilation boundaries. You still build one executable, and its functions can share objects when the design permits. This lesson shows where declarations belong, how definitions reach the linker and how make rebuilds only the parts affected by a change.

Declare an interface once and implement it once

The project has main.c, marks.h and marks.c. marks.h declares passed_count with its argument and return types. main.c includes that declaration before calling the function. marks.c includes the same header before defining the function, allowing the compiler to detect disagreement between the advertised interface and its implementation.

Quotes in #include "marks.h" request a project header using the implementation's documented search rules. Angle brackets are conventional for standard headers such as stdio.h. The -I option adds a project include directory when files are compiled from elsewhere. Do not include marks.c in main.c to avoid learning the linker; compile both source files instead.

A guard uses #ifndef, #define and #endif around a header's content. The first inclusion defines a unique guard macro. Later inclusion in the same translation unit skips the body. Choose a project-specific name that does not collide with another header. The guard state starts independently for each separately compiled source file.

A declaration promises an entity and its type; a definition supplies the entity itself. An ordinary function prototype can appear consistently in several translation units through a header. An ordinary external function body should have one definition in the program. Shared global objects similarly need one definition, with extern declarations in the header if sharing is necessary.

From translation units to one executable

A translation unit is a source file after preprocessing has expanded its includes and conditional directives. The compiler checks main.c against the declarations visible there. It does not automatically open every other .c file to verify a matching body. Consistent headers are therefore part of the interface discipline, not optional decoration.

To compile without linking, run gcc -std=c17 -Wall -Wextra -Wpedantic -Werror -O2 -c main.c, then the corresponding command for marks.c. These produce main.o and marks.o. Link them with gcc main.o marks.o -o marks-demo. A one-command build may instead name both .c files and let the compiler driver perform the stages.

The linker resolves references between object files. A declaration without a linked definition can produce an undefined-reference error. Two competing external definitions can produce a multiple-definition error. Neither means that a runtime if statement chose the wrong branch; the executable has not successfully been built yet.

When a function is private to a source file, add static at file scope. The is_pass helper is then unavailable as a public external name to other translation units. Two files can use the same private helper name independently. Internal linkage is about which declarations identify an entity across files, not a promise that a function will be inlined or faster.

Build clients with small, explicit interfaces

Compile a client and marks module as separate sources

The header declares passed_count. marks.c defines it and keeps is_pass private with static. The four marks contain two passes. The project directory also contains a Makefile for separate compilation.

Include a guarded declaration twice without redefining it

The include guard makes the second inclusion harmless. Guarding a header does not make arbitrary function definitions safe across different source files; this header contains a declaration only.

Keep same-named helper functions private to their source files

Both source files define adjustment, but each definition has internal linkage. Their public wrappers call their own helper. Removing static from both helpers would create competing external definitions rather than a shared choice at runtime.

Let make remember prerequisites

The included Makefile describes an executable target and two object targets. A target is followed by a colon and its prerequisites. An indented recipe explains how to rebuild it. Make normally requires a tab at the start of each recipe line. Copying spaces into that position can produce a missing-separator error before any C compiler runs.

The executable depends on main.o and marks.o. Each object depends on its source and marks.h. When marks.c changes, make recompiles marks.o and then relinks. When the header changes, both objects rebuild because either caller or implementation may be affected. A second make with no newer prerequisite has no compile work to do.

CC and CFLAGS keep the compiler choice and warning options in one place. The clean target removes generated objects and the executable; declaring it .PHONY prevents a file named clean from suppressing the recipe. These introductory rules are explicit and small. Larger projects often generate header dependencies automatically, but the underlying question stays the same: which outputs depend on this input?

Incremental builds assume meaningful file modification times and complete dependency descriptions. If a rule forgets the header, an old object can survive an interface change. Cleaning and rebuilding may temporarily reveal the mistake, but adding the missing prerequisite is the lasting repair. Test a header edit as well as an ordinary source edit when checking your build rules.

Repair the boundary that actually failed

Including implementation files

Including a .c file pastes its definitions into the including translation unit. Compiling that .c file separately as well can create duplicate definitions. Put public declarations in a guarded header and compile each implementation once. This keeps the build graph and ownership of definitions understandable.

Putting mutable definitions in a header

A header guard cannot prevent two separately compiled files from each defining the same external object. Use one definition and extern declarations, or prefer explicit state passed through function arguments. A shared total is not automatically necessary because two modules both need to read marks.

Confusing two meanings of static

A block-scope static counter retains its value between calls. A file-scope static function has internal linkage. These uses share a keyword but answer different questions. The examples separate persistent state from private names so that you can explain each effect without guessing.

Guessing at linker failures

Changing a return statement cannot supply a missing object file. Read the missing symbol name, confirm the definition's spelling and inspect the link command. Keep compiler warnings enabled for every source, including modules that do not contain main. A clean client alone does not prove that the whole program has consistent declarations.

Choose an interface that callers can trust

The pass-count interface accepts a read-only array and a count. Its contract assumes a nonnegative count and that the caller supplies at least that many elements. The function does not own the array, so it does not free it or retain its address. Writing these assumptions beside the declaration helps a future caller use the module without reading its private loop.

A header should also compile when included on its own. If a declaration uses a standard type such as size_t, include the header that defines that type instead of relying on the client to include it first. This removes accidental include-order dependencies. Keep private structure layouts and helper declarations out of a public header unless callers actually need them.

A useful boundary is based on a coherent job rather than an arbitrary number of lines. Combining input prompts with a reusable calculation makes that calculation harder to test in another program. The counting module therefore performs no interactive input. The client chooses where marks come from, validates them and displays the result.

Before changing an interface, find all its callers and rebuild them together. Adding a parameter or changing a return type affects the agreement between translation units. A private helper can often change without any client edit, which is one practical benefit of keeping the public promise small.

C interfaces and a separate build tool

Header declarations, include guards and internal linkage are established C facilities used here under C17. make is a separate development tool rather than part of the C language. The supplied Makefile uses GCC-style command options and a shell removal command. On another system, adapt the tools while preserving the same source/header/object dependencies.

Keep the public promise small

A useful module exposes the operations its callers need and keeps the rest private. Compile each source with its own declarations, link every required object and rebuild dependants when a header changes.
