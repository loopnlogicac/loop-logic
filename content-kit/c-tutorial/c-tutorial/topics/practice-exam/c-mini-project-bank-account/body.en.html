Keep the story of a balance alongside the balance

A number saying 380 taka is less informative than the two actions that produced it: deposit 500, then withdraw 120. This project models one fictional account with an ordered transaction history. You can deposit, withdraw, inspect the balance and display accepted history.

The program is a local learning exercise, with no real payments, authentication or multi-user access. Use made-up amounts in a disposable directory. It stores whole taka only, limits each amount to 100000, limits balance to 1000000 and permits one hundred accepted transactions. These bounds make validation and memory ownership easy to inspect.

Start with an explicit empty history

Save the source as account.c, compile it in strict C17 mode and create an empty account.txt beside the running program. An existing file contains lines such as D 500 and W 120. The loader replays each entry from a zero balance and rejects any malformed, excessive or impossible history.

Commands are D amount for deposit, W amount for withdrawal, B for balance, H for history and Q to quit. Each command takes one bounded line. Extra tokens, huge numeric strings and nonpositive amounts are rejected. An overlong physical line is drained before the next command is read.

Follow accepted and rejected account changes

Preserve balance and history after rejected withdrawals

Deposit 500 and withdraw 120, leaving 380 taka. An attempted 400 withdrawal and a negative amount are rejected. Neither enters history. The saved file contains only the two accepted transactions, in order.

Replay a saved history before accepting another operation

The starting file records a 500 deposit and 120 withdrawal. Startup recomputes 380 from those entries. Withdrawing the exact balance is allowed and adds a third entry that brings the result to zero.

One structure holds the current state

Account contains a balance, a count and a fixed transaction array. Each transaction stores its type and amount. apply validates the request before changing either balance or history. It returns an explicit result so the caller can distinguish insufficient funds, a balance limit and a full history from a successful change.

A withdrawal may equal the current balance; it then leaves zero. A withdrawal above the balance fails. A deposit checks its upper bound before adding. Because amounts are positive and bounded, MAX_BALANCE minus amount is safe to compute. No signed overflow is used as a later detection mechanism.

History is the authoritative persisted representation. Startup reconstructs balance by applying each entry in sequence under the same rules. That catches a file that withdraws before funds exist, even if a later deposit would make its final arithmetic total nonnegative. Validity belongs to every prefix, not only the final sum.

Publish only a completely written history

After an accepted change, save writes the entire active history to account.tmp. It checks formatted writes and close, then attempts replacement of account.txt. The documented Linux environment supports this replacement behavior. A failure stops the process and is not followed by a saved-success message.

This approach keeps one complete representation instead of independently updating a balance file and a history file. It does not provide crash durability, multi-process locking or protection against hostile filesystem changes. Those require additional protocols. The fixed temporary name assumes one writer in the exercise directory.

History display replays the entries for a running balance beside each action. This is useful for checking the model: a rejected withdrawal must not create an entry, and a balance query must not change count. Restarting in the same directory should reconstruct exactly the accepted sequence.

Separate policy, storage and interaction

The apply helper knows account rules but does not print or terminate the program. load and save know file representation. The menu chooses human messages and the final process result. This division makes it possible to reuse the rule helper in a different interface without copying prompts into the calculation.

The project deliberately rejects new operations when history is full. Silently dropping the oldest entry would break replay from zero and lose the explanation of the balance. A larger design might archive a verified checkpoint and earlier history, but that is a new storage contract that must be designed and tested.

To add fractional amounts, use a documented integer minor unit and a strict decimal parser. Do not change the field to double and assume every decimal amount is represented exactly. The stored format must identify the scale so that an old 500-taka entry cannot be read as 500 paisa.

Challenge the invariant rather than only the menu

Try an empty history, exact-balance withdrawal, insufficient funds, zero and negative amounts, an amount above its maximum and a balance-limit deposit. Confirm that rejected requests leave both state components unchanged. Reach the history capacity and verify explicit rejection rather than an out-of-bounds write.

Then restart after successful changes. Corrupt a saved line and confirm startup stops without replacing the file. An unreadable existing file is not a reason to start an empty account silently. Keep human display separate from success status: a readable error must still produce a failed process outcome when persistence cannot be trusted.

A trustworthy total has a valid sequence behind it

Maintain balance and accepted history together, validate before mutation and save before announcing acceptance. The next project, tic-tac-toe, uses a different state machine built from arrays, functions and turn rules.
