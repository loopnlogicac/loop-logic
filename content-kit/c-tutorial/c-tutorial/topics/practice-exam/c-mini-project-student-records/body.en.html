Combine structures, validation and storage

Build a local notebook of fictional student rolls and marks. A menu lets you add, list, search, update and delete records. Each successful change is written to a text file so the next launch can load it. The project uses one bounded array of structures and deliberately keeps the data format small enough to inspect by hand.

This is a single-user learning program with fictional data. It has no authentication or access-control layer and is not a production student information system. Use a disposable working directory. The record limit is twenty, rolls range from one through 9999 and marks range from zero through one hundred.

Prepare a known starting file

Save the complete source as records.c and compile with gcc -std=c17 -Wall -Wextra -Wpedantic -Werror -O2 records.c -o records. Create an empty students.txt in the directory where you will run the program, or use the displayed starting records. The examples run locally because they need writable files.

Startup opens the existing file and validates every record. Missing, unreadable, duplicate, oversized or malformed data stops the program instead of silently creating an empty database. This prevents a bad load from becoming an accidental overwrite. The current format is one roll and mark pair per line, with no header or names.

Use a small command vocabulary

CommandMeaning
A roll markAdd a unique roll
LList the active records and count
S rollSearch one roll
U roll markUpdate an existing mark
D rollDelete an existing record
QQuit

Commands occupy one line. Numeric fields allow strtol's decimal sign syntax but must satisfy their application range. Extra trailing tokens are invalid. A command line that exceeds the buffer is drained as one rejected line, so its remaining fragment cannot become a second command. Blank or unknown commands are rejected without changing records.

Run complete record workflows

Add, search, update and delete fictional records

Start with an empty students.txt. Add two rolls, reject a duplicate, update roll 101, then delete roll 102. Each saved message follows a successful file replacement. Listing preserves insertion order and displays only active records.

Load existing records and reject malformed menu requests

The starting file contains two valid records. Out-of-range marks and trailing junk are rejected before mutation. A missing roll is a normal search result, and the final list confirms that rejected requests did not change the loaded records.

Give each helper one responsibility

number converts a bounded integer and advances a cursor only after a valid conversion. at_end permits only trailing whitespace. read_line distinguishes end of input, a complete line and an overlong physical line. These helpers keep text validation separate from record operations.

find_roll searches the active prefix and returns its first index or minus one. The unique-roll invariant means there is at most one target. Add requires absence and spare capacity; update and delete require presence. List and search read state without saving because they do not change it.

Deletion shifts later records left, then reduces count. Bytes beyond the active prefix are irrelevant and are not written. This is why a record's identity is its roll rather than its array position. After deleting the first record, all later indices change while their rolls remain the same.

The main loop controls the workflow. It validates a complete request, applies one accepted mutation, saves, then prints saved. On a save failure it terminates with failure rather than continuing to announce later results from a state whose disk representation is uncertain.

Write a complete replacement before publishing it

save opens students.tmp, writes every active record and checks fclose as well as each formatted write. Only then does it rename the temporary file to students.txt. The documented Linux host supports replacement of the existing destination. Other C environments may have different existing-destination behavior; the checked rename reports failure rather than pretending it succeeded.

This pattern avoids truncating the old file before the replacement content has been written. It is not a full crash-durable transaction: power loss, concurrent writers, malicious directory changes and storage-level guarantees need more work. The fixed temporary name also assumes this program is the only writer in its disposable directory.

To see persistence, add a record, quit and restart in the same directory. The loader should show the saved value. To test rejection, try a duplicate roll or mark 101 and list again. The file and active records should remain unchanged after those rejected requests.

Grow the design by changing one contract at a time

A natural extension stores names. Decide how spaces, separators and maximum length are encoded before changing the structure. Another extension separates parsing, storage and record operations into the source/header modules from the multi-file lesson. Keep the menu client dependent on public operations rather than private array layout where practical.

A larger database would need stronger storage, indexing and access controls. Those are separate engineering steps. First make the small project's invariants easy to explain: valid unique rolls, valid marks, a bounded active prefix and a successful save before acceptance is announced.
