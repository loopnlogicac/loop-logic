A room you rent while the program runs

Imagine arranging chairs for a programming lab. A fixed array is like reserving twenty chairs before anyone arrives. Dynamic memory lets you wait for the student count before choosing the space. You ask for storage while the program is running, use it, then return it when the task ends.

A dynamic allocation is a request for a block of memory whose lifetime you control. C provides the request functions in stdlib.h. You receive a pointer to the block, rather than a new array variable with a named size. You must keep enough information to use that pointer safely.

Dynamic storage helps when input determines the number of marks, records, or rows. It also lets a helper create data that survives the helper's return. You already know from pointer lifetimes why returning an automatic local variable's address fails. An allocated object has a different lifetime, so returning its pointer can be correct.

Allocation does add work. You must check failure, initialize the contents, respect the block's bounds, and release it. Choose a small fixed array when its capacity is sensible. Dynamic memory solves a storage need; it does not automatically make a program faster or simpler.

Read the C notation

An allocation request uses a byte count. The expression sizeof *mark asks for enough bytes for the pointed-to type. Although it contains a dereference symbol, this ordinary sizeof operand is not evaluated. No memory is read through an uninitialized pointer here.

A successful malloc result converts to the required object pointer type in C. A cast is unnecessary. Include stdlib.h so the compiler sees the correct declaration. Test the result before the first assignment through the pointer.

int *mark = malloc(sizeof *mark);
if (mark == NULL) {
    return 1;
}
*mark = 78;
free(mark);

Two lifetimes, one pointer

A local pointer variable and its allocated target are different objects. The pointer below belongs to main's block. The integer it selects belongs to an allocation. Ending the pointer variable's scope does not release that integer. Losing the last usable pointer would instead make the allocation unreachable.

People often say local variables live on the stack and dynamic objects live on the heap. These are useful implementation pictures. The C standard describes automatic and allocated storage duration without requiring a particular stack or heap design. A local array is not guaranteed to use a machine stack either.

Follow the single-mark example in time. Before malloc succeeds, main owns no allocated integer. After success, mark holds the block's base address. The assignment stores 78 into that integer. printf reads the initialized value. Finally, free ends the allocation's lifetime, even though the pointer variable still exists.

After free, do not read or compare the stale pointer value. Assigning NULL to the pointer is allowed and gives it a useful empty state. That assignment does not repair another pointer which copied the old address. Any such borrowed pointer must stop being used before release.

main block                  allocated storage
mark [address] ----------> [integer: 78]

after free(mark):
mark [stale value]           allocation lifetime ended
after mark = NULL:
mark [NULL]                  no owned block

Think of ownership as responsibility, rather than a C keyword. The owner decides when the allocation ends. A borrower may inspect the data while the owner keeps it alive. Write this agreement beside helpers that return or receive allocated storage. The compiler cannot infer the full agreement from int * alone.

Worked programs

Start with a single mark, then count several marks, then move allocation into a helper. Each program has one clear owner. Watch where ownership begins and which function eventually calls free. The printed values come from initialized integers, so their meaning does not depend on any numeric address.

One allocated mark

The single integer makes the allocation lifetime easy to see. sizeof measures an int through the pointer's type. malloc does not provide an initial mark, so the assignment is essential. The failure branch leaves before any dereference. A successful run prints Mark: 78, then releases the only allocation. No automatic local variable is passed to free.

Allocate room for three marks

The count variable describes three elements rather than three bytes. Multiplying by sizeof converts that element count to the allocation size. Each loop iteration writes one mark before adding it. The total starts at zero independently of the allocated contents. Releasing marks once releases the whole array; you do not free the address of each element.

A helper returns a live allocation

make_mark's result pointer is local, but the object created by malloc has allocated storage duration. Returning the address value lets main reach that object after the helper has finished. main prints Returned mark: 85 and becomes the function that must release it. This would fail if the helper instead returned the address of an automatic local integer.

Counts, failure, and useful limits

The count in a dynamic array must travel with the pointer. A pointer does not remember how many elements you requested. For three integers, indices zero through two are valid. Index three is outside the block even if nearby memory appears unused. Allocator bookkeeping never enlarges your permitted array bounds.

Validate a signed count before converting it to size_t. A negative int converted first can become a huge positive value. For a general count, check multiplication with count > SIZE_MAX / sizeof *items before requesting count times the element size. SIZE_MAX is available from stdint.h. Small classroom limits also make arithmetic and input handling easier to inspect.

An empty collection deserves an explicit policy. You can represent it with a NULL pointer and a count of zero, skipping allocation entirely. This avoids depending on whether a zero-byte request returns NULL or a pointer that still needs releasing. Never index an empty collection.

Allocation failure is an ordinary branch in your program. A tiny request usually succeeds, but success is not guaranteed by its size. A helper can return NULL and let its caller decide what to report. A longer operation must also release any earlier blocks before leaving on failure.

Mistakes and repairs

Losing the rented room

Assigning a second allocation to the only pointer to the first block loses the first address. Free the first block when its work is complete, or keep another owner until then. A pointer assignment copies an address; it never releases the old target for you.

Using automatic storage as an allocated object

Do not call free on the address of a local int or a fixed local array. Those objects follow their own storage duration. Only release an allocation base returned by an allocation function, and release it once. Passing a pointer into the middle of the block is also invalid.

Habits to use in your programs

Sketch the pointer and its target separately before writing an allocation helper. Name the owner in the helper's contract: for make_mark, the caller becomes responsible for the returned block. Keep a count beside every allocated sequence. Prefer sizeof *pointer over spelling the target type twice.

Place cleanup close enough to the work that you can review every exit. If input fails after allocation, release the block before returning. Use allocated storage only while its owner can guarantee that the lifetime continues. Later, memory tools will help check those paths.

C versions and portability

The malloc, calloc, realloc, and free interfaces are long-standing C features. These examples use C99 declarations and target C17. C11 adds aligned allocation for stronger alignment needs, which this lesson does not require. Ordinary int objects fit the alignment guarantee of malloc. The stack and heap drawing describes a common implementation, not a required machine layout.
