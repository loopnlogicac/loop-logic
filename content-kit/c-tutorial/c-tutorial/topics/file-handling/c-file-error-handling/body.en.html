A return value is the first piece of evidence

A file import can stop because the input ended, because a token was malformed, or because an actual read failed. Those outcomes need different responses. A class-mark importer should accept a complete last record without a final newline, reject a truncated mark, and report an unavailable device. Calling every stop “end of file” hides information that the caller needs to decide whether its result is trustworthy.

Think of a stream indicator as a note left by an earlier operation. It does not look ahead. Before the first read of an empty file, the end-of-file indicator can still be clear. The read discovers the end and sets the indicator. Therefore, the operation belongs in the loop condition: process a character after fgetc returns a character, an item after fread reports that item, or a converted integer after fscanf reports one assignment.

This lesson combines return-value checks, classification and cleanup. They form one contract: a function reports success only when every required stage succeeded, and it releases every resource that it owns even when an earlier stage failed. Diagnostics help explain failure; they do not replace those checks.

Read results and stream indicators

The expression fgetc(stream) returns either an unsigned-char value converted to int or EOF. Store the result in int so that the sentinel remains distinguishable. After EOF, inspect ferror to detect an input error; otherwise the read reached end-of-file. feof reports whether the stream's end indicator is set, while ferror reports its error indicator. Neither returns a portable error number or a description of the underlying cause.

For fscanf(stream, "%d", &value), a return value of one means that the requested assignment happened. Zero means matching failed before that assignment. EOF means an input failure occurred before the first conversion completed. A malformed word can cause zero while both stream indicators remain clear. Retrying the same conversion without consuming or rejecting that word makes no progress.

clearerr(stream) clears both indicators. It does not move the position, replace missing bytes, fix malformed input or repair a device. rewind also clears the indicators while returning to the beginning. A successful positioning call has its own specified effects; do not infer them from a convenient run alone. Keep the operation's return contract beside the indicator check when reasoning about recovery.

Classify the stop before choosing a response

Start with the smallest reliable fact: did this operation return the amount of usable data that its caller requested? If yes, validate and process that data. If not, identify the reason before touching a destination that may still contain an earlier value. In the integer example, the conversion loop prints only newly assigned integers; after it stops, an error indicator takes priority over treating the result as a clean end.

Matching failure is a data-format problem. A line-oriented importer can reject the complete physical line and continue at the next line boundary. A token-oriented importer needs an equally explicit recovery policy. Blindly calling clearerr cannot consume an invalid token because no stream error caused the mismatch. Choose rejection, termination, or a controlled skip according to the file format.

A short block read also needs two layers of interpretation. fread may return fewer items because a clean end was reached. If the format promises four bytes per record, receiving two final bytes still means a truncated record. “No I/O error” describes the transport; it does not certify the application's record structure. Count bytes when partial-record detection matters, then check the remainder against the record width.

Do not build a retry loop from hope. A transient failure may justify a bounded retry only when the environment and operation document that recovery. An unchanged malformed token, or an unchanged end position after clearerr, produces the same outcome again. Recovery must explain what changes and why the next attempt can make progress.

clearerr removes the indicator but does not move the stream position. The next read at the unchanged end reaches EOF again. Clearing state is not the same operation as rewinding.

Use errno without losing the original evidence

perror writes a prefix and the message associated with current errno to standard error. The wording is supplied by the host and may differ between systems and languages, so the example's captured standard output deliberately contains only a stable status line. Its nonzero process exit status tells a shell or caller that opening failed. The human diagnostic is additional information.

Check the interface documentation before treating errno as part of its contract. A failed fopen is portably indicated by a null pointer; common hosted systems also document useful errno values for that failure. ISO C does not promise that every library failure sets errno. A successful call need not clear an old value either. Testing errno after an otherwise successful operation can therefore report an unrelated earlier problem.

When a failing interface documents errno, copy it immediately, before reporting, allocating or cleaning up. Any intervening function may change it. If perror will report the original failure later, restore the saved value just before calling perror. Also preserve which operation failed: “copy input” and “close output” point to different stages even when their messages happen to match.

Close every owned stream and retain the first failure

The block-copy helper borrows two streams and leaves closing to its caller. That separation makes ownership visible. The caller owns the streams it opened, attempts both closes, and records their outcomes independently. An expression such as fclose(input) != 0 || fclose(output) != 0 is wrong for cleanup: short-circuit evaluation can skip closing output after the input close fails.

Buffered output makes close part of the success decision. A successful fwrite can mean that data entered the library buffer; fclose may discover a later delivery failure while flushing. A copy that ignores that failure can announce success for an incomplete destination. Once fclose has been called, do not retry using the same stream pointer, even when closing reported failure.

Preserve the earliest failed stage while still attempting later cleanup. Otherwise, a secondary close error can erase the more useful explanation of the original read or write failure. The example keeps both a stage description and its captured diagnostic value. Returning failure does not remove a partially written file automatically. Applications that need all-or-nothing replacement require a separately designed temporary-file and replacement protocol.

Mistakes that disguise invalid input

A while (!feof(stream)) loop asks about a previous read and can execute once after the last usable item. If it prints an unassigned destination on empty input, the problem is worse than one duplicate line. Put the read result in control of processing, then inspect why the read stopped. The written exercise asks you to trace both empty input and an invalid token because they expose different failures.

Another mistake treats each fgets fragment as a complete record. With a fixed buffer, an overlong physical line can occupy several reads. The practice solution accepts a line exactly at the stated limit, including an EOF-terminated final line, but drains the remainder of an overlong line before moving on. Otherwise, one invalid record can be silently split into several apparently valid records.

Finally, do not label a demonstration as a tested disk-full or device-disconnect case when it only exercised ordinary files. These examples execute successful transfers, a missing path, a malformed token and repeated reads at the end. Real delivery failures depend on the environment. Reliable stopping, reporting and cleanup

  • Process data only after the operation reports a successful assignment or transfer.
  • Distinguish matching failure, clean EOF, I/O failure and incomplete records.
  • Use stream indicators as evidence about earlier operations.
  • Save documented errno values before unrelated calls can replace them.
  • Attempt every owned close and include output-close failures in the final result.
  • Make any recovery policy consume input, change conditions or stop after a stated bound.
