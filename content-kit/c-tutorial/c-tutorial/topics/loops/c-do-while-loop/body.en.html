Introduction

A menu must appear before a student can choose an option. An input question must be asked before its answer can be checked. The do-while loop suits this act-then-check pattern. Its body comes first and its repeat condition comes at the end.

Picture taking one practice attempt, then deciding whether to try again. Reaching the loop normally means taking that first attempt. A while loop is different because its initial test may skip every attempt. Choose the post-test shape only when the first action is required even before you know the repeat decision.

Syntax and reading guide

do {
    /* first action and later repetitions */
} while (condition);
body --> condition? --false--> after loop
 ^            |
 |           true
 +------------+

The semicolon after the condition is required. It is different from a stray semicolon after a while header, which can create an empty body. Keep the closing brace and repeat condition visually connected.

Follow the values and decisions

Begin execution at the body, perform its statements, then evaluate the condition. Nonzero returns to the top of the body. Zero leaves the loop. A counter starting at zero can therefore run once even if its intended upper limit is also zero.

That is a feature for menus and a mistake for workloads that should be empty.

A menu iteration displays the options, reads one choice, processes it, and then asks whether the choice was the exit value. If zero means exit, zero still required the menu display and read that came before the test. You may want to suppress ordinary action messages for that exit choice inside the body.

For input validation, read a representable integer and repeat while it is outside the permitted range. A valid boundary ends the loop. A numeric conversion failure is different: the invalid token may remain unread. These examples stop on conversion failure instead of repeatedly trying the same token.

Later line-input techniques can offer more complete recovery.

Digit counting illustrates another post-test use. Zero has one decimal digit. A do-while can increment the count and divide the working number once before testing whether more digits remain. Positive numbers then repeat until division removes every digit.

This avoids a separate zero branch for the counting task.

Examples

A first action despite zero limit

Attempt prints once before count is compared with zero. The increment makes count one and the repeat condition fails. This is useful for a required first attempt, but would be wrong for a count-of-items task that expects zero work.

A menu including its exit choice

The input first requests balance, then exits. Menu appears twice because both choices are read after a display. Balance appears only for choice one. The zero choice ends repetition at the bottom condition without performing a normal menu action.

Repeat until a mark is in range

The numeric mark one hundred one is outside the allowed interval, so Retry prints and another read occurs. The next mark is one hundred, an inclusive boundary, which is accepted. Conversion success and academic range validation are handled separately.

Count the digits of zero

The first body counts zero as one digit. Dividing zero leaves zero, so repetition ends immediately. Positive values would keep losing their last digit until the same stop condition is reached.

Boundaries and alternatives

A do-while does not ignore control transfers. A return inside the body can leave the function immediately. A break can leave the loop before its bottom test, and a continue transfers to that bottom condition. Those details are covered in loop control.

The ordinary at-least-once claim concerns reaching the body, not a guarantee that every statement in it finishes.

The condition variable must be visible after the body's closing brace. A choice declared only inside the body block is out of scope in the trailing condition. Declare the variable in the enclosing block. Give it a value through a successful read or assignment before the condition uses it.

Bound a retry sequence when the task needs guaranteed termination. An interactive menu may legitimately wait for a user to choose exit; a finite input example needs either that choice or an explicit end-of-input response. A loop is not complete merely because its happy-path input eventually works.

Common mistakes

Forgetting the trailing semicolon

The syntax ends with while(condition);. A missing semicolon is a build error. Inspect the closing part of the construct rather than adding punctuation inside the body.

Using a post-test loop for an empty workload

If zero requested items must mean no work, use a pre-test for or while. A do-while would still process one item. Choose the loop from the task rather than making every repetition look alike.

Questions to ask while reading

QuestionRule and reason
Where is the do-while repeat condition?After the body. This makes it a post-test loop.
What punctuation ends the whole do-while construct?A semicolon. The trailing semicolon is required by its syntax.
Which workload can be wrong for do-while?A zero-item job that must do nothing. The body is entered before its repeat test.
What happens for a first valid validation input?One body and then exit. The first read succeeds and the repeat test is false.
Why not blindly retry a failed %d read?The bad token may remain unread. The same failure could repeat forever.
Where must choice be declared for a bottom test?In a scope visible at that test. A body-local name is no longer in scope after its closing brace.
Where does continue go in a do-while?To the bottom condition. The condition decides whether another iteration begins.

Version notes

Do-while and its trailing semicolon are part of C89 and remain in C17. The scope rule for a body-local declaration still applies: the trailing condition is outside that body block.
