Introduction

The structure of a C program is the way declarations and function definitions are arranged in a source file. A clear structure lets the compiler know each name before use and lets a reader find the purpose, shared data and main sequence of work.

Think of a lab report with a heading, assumptions, method and results. C does not require those exact report sections, but organizing the source serves a similar purpose. A student checking your marks calculation should not have to search the whole file to discover its maximum score.

This lesson introduces helper functions before their full module. A helper is a named function that performs one task and may return a result; see Functions in C. For now, read the declaration as a contract and the definition as the implementation of that contract.

Syntax and vocabulary

A typical teaching layout starts with documentation, then preprocessing directives, file-scope declarations, main and helper definitions. A prototype declares a function's name, result type and parameter types without supplying its body. A definition includes the body.

/* Purpose and important assumptions. */
#include <stdio.h>
int total_marks(int theory, int lab);
/* main definition follows; helper definition may come later. */

A statement expresses an action in a function body. A pair of braces forms a block, which groups statements and provides a region for local names. A declaration may also occur within that block before a name is used.

How it works

The compiler reads declarations according to their visibility in the source. When main calls total_marks, a preceding prototype supplies enough type information to check the call. The later helper definition must agree with that prototype and provide the actual work.

  1. The include directive makes printf's declaration available.
  2. The prototype declares the helper before main uses its name.
  3. main calls the helper with the two mark values.
  4. The helper adds its parameters and returns the result.
  5. printf writes the returned integer and main finishes.

A parameter is a local name used by a function to receive an argument value. In total_marks, theory and lab are parameters, while the 60 and 25 in the call are arguments. Parameters make the same calculation reusable without sharing every local variable between functions.

main --call with 60,25--> total_marks
main <--result 85------- total_marks

The annotated seats example shows all major regions in one complete source: a purpose comment, an include, a file-scope constant, a helper definition and main. Because the helper is defined before main, a separate prototype is unnecessary there. Both arrangements are valid when the name and type are known before the call.

The keyword const qualifies an object so it cannot be modified through that object after initialization; see Constants and Literals. The seats example uses this rule for its shared row capacity.

Details and comparisons

Scope explains where names work

A scope is the region where an identifier can be used to refer to its declaration. A name declared inside main normally belongs to that block. A helper cannot automatically use main's local marks variable merely because both functions appear in one file.

A declaration outside every function has file scope. Its name becomes available from its declaration onward, subject to the language's visibility rules. The shared seats-per-row constant is placed before the helper that uses it for that reason.

File-scope data is useful for a small shared constant, but making all variables global is not good organization. A parameter makes a helper's required input visible at the call. Keeping a temporary total local also prevents unrelated functions from changing it accidentally.

Statements, blocks and whitespace

Expression statements such as printf calls end with semicolons. A function definition ends with its closing brace and does not need a trailing semicolon as part of the definition. A prototype has no body and does end with a semicolon.

Several statements can be written on one source line, but that makes debugging locations harder to read. Blank lines and indentation separate ideas for people; braces and semicolons determine the grammar. Moving a brace changes structure, while adding an ordinary blank line normally does not.

Four-space indentation shows which statements belong to a function or nested block. This is a style rule for these files rather than a magic instruction to the compiler. The compiler does not treat indentation as a substitute for braces.

Read from contract to result

When reviewing a larger source, first read its purpose and input assumptions. Then inspect the function interfaces, follow main's sequence and check each helper against its stated task. This reading order keeps you from confusing source order with execution order: a helper written last can execute in the middle of main.

Common mistakes

The marked mistake example is supplied for compiler diagnostics. Repair the stated cause before running it; it has no expected stdout transcript.

Replacing a definition with a prototype

A prototype describes a helper but does not implement it. If the call is compiled and no matching definition is linked, the final build fails. Add the required body rather than assuming the declaration performs the calculation.

Using another function's local variable

A local variable belongs to its scope and is not automatically visible in a separate function. Pass the needed value as a parameter. Duplicating the same name in a different function creates a different local object.

Mistake: using a local name before declaration

The name marks is not declared at its first use; move its declaration before the printf call.

Best practices

  • Place declarations before their first use.
  • Keep main's overall sequence readable.
  • Use helper parameters to make data flow explicit.
  • Document units and limits rather than decorating every line.
  • Use braces and one clear indentation style throughout the file.

Version notes

C89 required declarations before statements within a block. C99 permits mixed declarations and statements, as used in the practice code. Modern C requires proper function declarations before calls; do not rely on old implicit-function conventions. The examples are built as C17.

Summary

A clear program separates interface declarations, shared constants and executable function bodies. Names must be visible before use, and a prototype cannot replace an implementation. Next, follow the build stages in How C Code Is Compiled.
