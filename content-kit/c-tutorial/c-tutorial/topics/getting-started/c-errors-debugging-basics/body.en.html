Introduction

Debugging is the process of finding why a program fails to meet its requirements and correcting the cause. Begin by separating build failures from runtime failures and wrong results. The same symptom, such as no expected output, can have several different causes.

Suppose a marks total should be 85 but the program reports 35. The source may be grammatically valid and the executable may exit successfully. You need to compare the calculation against the task rather than repeatedly changing build options.

A useful bug report states the exact source, command, input, expected result and actual result. This small record makes the failure reproducible on the next run. Without it, changing several things at once can hide the cause before you understand it.

Syntax and vocabulary

A compiler diagnostic commonly uses the form file:line:column followed by a severity and message. The location identifies where the compiler noticed the problem, which may be after its actual cause. Read the first meaningful error and inspect the preceding source line as well.

lab.c:8:5: error: expected ';' before ...

How it works

printf debugging adds temporary output to reveal intermediate values. Label each value so you can identify its role after reading several lines. A bare 35 gives less evidence than a trace naming theory, lab and wrong_total.

The first example deliberately uses a defined but incorrect formula. It prints the inputs and result, making the subtraction visible. The second example repairs the formula and produces 85; compare both runs to see why successful compilation was never enough.

  1. Write the required formula in words.
  2. Choose a small input whose result you can calculate by hand.
  3. Print the input values and each important intermediate result.
  4. Locate the first value that differs from your prediction.
  5. Repair that step and run the original failing case again.

A trace is a record of the program's changing state. The minutes example traces a unit conversion from 2 minutes to 120 seconds. Naming the unit prevents confusing the number of minutes with the number of seconds.

Remove temporary diagnostics from a solution whose exact output is graded, or make them part of an explicit debugging exercise. Extra trace lines can cause an otherwise correct algorithm to fail a judge's output comparison. Keep the failing input as a saved test after removing the temporary prints.

Details and comparisons

Pause and inspect with gdb

A debugger lets you pause an executing program and inspect its state. Build a debugging copy with symbols using -g and a low optimization level, so source steps and local values are easier to follow. This debugging build is separate from the optimized verification build.

gcc -std=c17 -Wall -Wextra -g -O0 lab.c -o lab-debug
gdb ./lab-debug
break main
run
next
print theory
next
print lab
next
print wrong_total
quit

A breakpoint requests a stop at a chosen source location or function. break main arranges a stop at the entry function, and run starts the process. next executes the next source-level step while stepping over a function call, so you can follow main without entering every library routine.

Use print with a variable only after execution has reached a point where that variable has an initialized value. The exact number of next commands depends on your saved source and debugger. Debug symbols do not make an uninitialized object safe to read.

A wrong-output checklist

First confirm you rebuilt the file you edited and launched the new executable. Next verify that stdin contains the values you intended and that input conversion succeeded. Then compare types, units, operand order, integer division and output formatting against the task.

Try zero where allowed, an ordinary case and the largest stated bound. Use unequal input values to reveal accidental swaps; equal values can hide subtraction-order mistakes. If a fix changes a formula, re-run both the original failure and a boundary case to check for regressions.

A regression is a failure reintroduced after a change. Saving a small failing case turns it into a repeatable guard against that mistake. The practice tests include boundaries for that reason rather than relying only on pleasant-looking ordinary values.

Some runtime faults are undefined behavior: C does not prescribe a result for the invalid operation. Do not invent a stable crash message or expected value for such code. Later sanitizer tools help expose some of these faults, but no tool replaces respecting object bounds and valid types.

Changing many things at once

A large random edit makes it harder to identify which assumption was wrong. Form one hypothesis, change the relevant line and repeat the saved test. Keep a clean baseline so a failed experiment can be reversed.

Ignoring a warning because the output looks right

One successful run does not make a format mismatch or uninitialized read safe. Read and fix the warning before trusting output. A wrong program may appear to work for one input or compiler configuration.

Mistake: a syntax error

The missing declaration semicolon can make the compiler point at the next statement; inspect the preceding line too.

Best practices

  • Make each bug reproducible with a small source and input.
  • Read compiler locations and messages before editing.
  • Label trace values with names and units.
  • Inspect initialized variables at the correct execution point in gdb.
  • Keep the original failure and boundary cases after the repair.

Version notes

The debugging method applies to C89 through C23. gdb is an external tool, not a language feature, and its interface depends on the installed version. These examples use C17 and avoid executing undefined behavior; a logical mistake is demonstrated with fully defined arithmetic.
