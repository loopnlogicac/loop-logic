Introduction

A printed booklet goes through preparation, printing and binding before you can use it. A C program also passes through several jobs before it runs. The compilation process usually means preprocessing, compiling, assembling and linking. Learning their outputs helps you choose the right repair when a build fails.

Imagine preparing a printed exam paper: you first expand shared instructions, arrange the content, produce a physical form and combine the required pages. The stages are different jobs, even when one command handles the whole workflow. GCC similarly acts as a driver for several tools.

The word compile is often used informally for the whole build. In the more precise stage description here, compilation turns preprocessed C into target assembly. A complete executable still needs assembly and linking after that step.

Syntax and vocabulary

The -E, -S and -c options stop the build at different points. Run each command on the first example source after saving it as lab.c. The .i, .s and .o files are intermediate build products rather than your original source.

gcc -std=c17 -E lab.c -o lab.i
gcc -std=c17 -S lab.c -o lab.s
gcc -std=c17 -c lab.c -o lab.o
gcc lab.o -o lab
./lab
What each stage produces

A target is the kind of machine and environment for which the toolchain generates code. Assembly syntax and object formats depend on that target. You do not need to understand every instruction to identify which stage produced a file.

How it works

Preprocessing handles directives such as includes and macro definitions. In the capacity example, ROWS is a macro, a name replaced by preprocessing tokens before ordinary compilation. See Macros. Inspect lab.i and find the output call with ROWS expanded to 3.

Compilation checks C syntax and constraints, determines expression types and translates functions into target instructions. With -S, you may see labels, registers, directives and a call to an output routine. Optimization can change those details without changing the required observable result of a well-defined program.

Assembly converts assembly text into machine-code bytes and records information needed later. An object file can contain function code, symbol information and unresolved references. A symbol identifies a function or object that other code may need to locate.

Linking combines object files and selected library code, resolves required symbols and produces an executable. Our small program calls printf, whose implementation comes from the standard library supplied with the environment. The source header supplies a declaration, while linking supplies the actual callable implementation.

lab.c --preprocess--> lab.i --compile--> lab.s
lab.s --assemble---> lab.o --link-----> lab

A normal command with lab.c and -o lab performs all these jobs without preserving every intermediate file. The intermediate commands are useful for learning and diagnosis. Keeping them separate does not make a wrong formula correct. Each stage has limited responsibilities.

Details and comparisons

Classify failures by evidence

A missing semicolon or an undeclared identifier is normally diagnosed while compiling the source. The compiler message names a source location and explains the grammar or constraint problem. Fix the earliest meaningful message before interpreting a long chain of later errors.

A declared function without a definition can pass compilation into an object file. The linker then reports an unresolved or undefined reference when trying to finish the executable. The deliberately broken example demonstrates this distinction: the declaration is known, but no implementation exists.

A runtime error happens after the program starts, for example an input failure handled with a nonzero exit status or an invalid memory operation in unsafe code. A logical error means the executed algorithm does not satisfy the task. Neither requires a syntax error, so a successful link is not the end of verification.

Debugging direction
SymptomFirst place to inspect
Expected semicolon diagnosticThe named source line and the preceding line
Undefined reference during final buildMissing definitions and linked object files
Program reports failed inputThe supplied stdin and conversion checks
Wrong total with a clean buildThe formula and task specification

When a build command fails, preserve its exact diagnostic and exit status before trying another command. Comparing a successful object-only build with a failed final link can isolate a missing definition without changing any C expression. Keep only source files as the authoritative input. Regenerate intermediate artifacts after every relevant edit.

Warnings are useful evidence

-Wall enables a useful group of warnings, despite not literally meaning every warning. -Wextra adds other diagnostics, and -Wpedantic requests diagnostics related to the selected ISO dialect. -Werror changes enabled warnings into build failures. It does not by itself enable every possible check.

Format mismatches, unused values and suspicious indentation often reveal real mistakes. Read the message and repair the cause rather than deleting a flag. A warning can also expose a design assumption that deserves an explicit comment or a different type.

-O2 requests optimization. It is not a proof tool and cannot tell whether a marks formula should add or subtract. Well-defined code should retain its required behavior under optimization. Undefined behavior can break that expectation, which is one reason later memory lessons use sanitizers.

A sanitizer is compiler-assisted runtime checking for selected problems, not a complete correctness guarantee. Its checks execute only along paths your tests run. Treat passing tests and clean diagnostics as complementary evidence rather than interchangeable certificates.

Its & argument names a storage address. A conditional block checks success, as described in if. Those runtime steps cannot happen until linking succeeds. If the final command fails, read its message before trying to run anything.

Common mistakes

Trying to run an object file

An object is an input to linking, not normally a finished program. Link lab.o into lab before launching it. Renaming lab.o to lab does not perform the missing linker work.

Editing generated assembly as a source repair

A fresh build will replace generated files, so ordinary C corrections belong in lab.c. Use intermediate outputs to understand a problem, then repair the original source and repeat the build.

Best practices

  • Keep source files separate from generated artifacts.
  • Use stage-specific commands when locating a build failure.
  • Compile with warnings enabled and investigate each message.
  • Record the compiler and selected standard for reproducible checks.
  • Run normal and edge inputs after a successful link.

Version notes

The four-stage toolchain model applies across the course editions, although actual compilers may merge internal phases. The selected -std option controls accepted language rules. It does not choose the target instruction set. These artifacts and diagnostics were verified with GCC on a 64-bit Linux system.

Summary

Preprocessing expands source, compilation translates it, assembly produces objects and linking finishes the executable. Identify the failing stage before changing code or commands. Next, learn how source explanations are handled in Comments in C.
