Introduction

Suppose a seat calculation multiplies the number of participants by two. The code shows the multiplication, but it may not explain the extra equipment space. A comment lets you leave that reason for the next reader. C does not execute the explanation.

You use comments to record useful assumptions, units and decisions.

Suppose a seat calculator multiplies participants by two because each participant brings a kit. The multiplication is visible in the code. The reason for two may not be. A short comment preserving that reason is more useful than a sentence saying that multiplication happens.

Comments are part of source maintenance. When a price or capacity changes, check any explanation that mentions it. An outdated comment can mislead a reader even when the executable calculation is correct.

Syntax and vocabulary

C17 supports line comments and block comments. A line comment begins with two slashes and covers the rest of its logical line. A block comment begins with slash-star and ends at the first star-slash marker.

// The room is shared, so keep two spare seats.
/* Units: the input duration is measured in minutes. */

/* text */First closing markerA short block or multi-line note

The extra star in a documentation-style comment does not create a new execution feature. Documentation tools may interpret tags and descriptions, but the C compiler still treats the whole thing as a block comment.

How it works

Comments are removed during translation before ordinary execution. Conceptually they become whitespace, preventing the surrounding tokens from being joined accidentally. A comment cannot print a label, create a variable or change the value stored in an object.

In the seats example, the explanation gives the equipment reason for two seats. The executable still performs an ordinary multiplication. In the capacity example, a comment occupies several source lines while the single initialized integer remains 30.

Comment markers inside quoted string literals are characters of the string, not comment delimiters. The practice label containing slash-star and star-slash therefore prints those characters. Before deciding that source text is commented out, check whether the marker occurs inside quotes.

Details and comparisons

Choose information the code cannot tell

A useful comment may explain why a boundary is inclusive, which unit a value uses or where a fixed price came from. A weak comment repeats the visible operation without adding meaning. Comments should reduce uncertainty for a future reader, including you during exam revision.

Improve a comment
Weak explanationBetter information
Add fiveThe lab task charges one fixed five-taka fee
Multiply by sixtyConvert input minutes to stored seconds
Return the answerThe returned amount is in whole taka

A function's documentation can state parameter meaning, output units, limits and failure behavior. Avoid promising validation that the function does not perform. If callers must supply counts from zero to one hundred, say that as a precondition rather than claiming all possible inputs are handled.

Commenting out code safely

A line comment can temporarily disable one source line. A block comment can disable several lines only when the selected region does not already contain a closing block marker. C block comments do not nest, so wrapping a commented function in another block comment is fragile.

For longer experiments, version control preserves the old code without leaving large inactive sections in the file. Another tool is a preprocessing condition such as #if 0 followed by #endif. It excludes a source region from ordinary compilation. This is a directive technique, developed in Conditional Compilation, rather than a form of nested comment.

Even excluded regions must obey relevant early translation rules, so do not use conditional exclusion as a place for unfinished string or comment delimiters. Keeping a clean saved revision is easier to reason about than layers of partly disabled source.

Try a small change

To judge a comment, temporarily hide it and read the expression below. Can you still explain why that number is used? A comment about minutes and seconds can settle a unit question that multiplication alone cannot answer. The exercises read values with scanf.

Its & argument gives a variable address, and an if checks the read. Describe the purpose of that check rather than translating each symbol into English. For a fixed-price exercise, state whether the amount is per ticket or per group. That distinction is worth preserving beside the calculation.

Common mistakes

Trying to nest block comments

The first closing marker ends the comment regardless of how many opening markers appeared inside. Remaining text can suddenly become active source and produce confusing diagnostics. Use line comments for a short experiment or remove the inactive region through version control.

Writing a comment for every obvious operation

Too many repeated descriptions hide the few assumptions that matter. Let a meaningful variable name explain its role, and keep the comment for units or constraints. Re-read comments when the surrounding code changes.

Mistake: an unfinished block comment

The opening /* has no matching */. Restore the delimiter rather than adding random braces.

Best practices

  • Explain why a rule exists rather than narrating punctuation.
  • Put unit and range information next to the relevant declaration or function.
  • Keep comments accurate when changing code.
  • Use one short style consistently instead of decorative banners.
  • Avoid large abandoned code blocks in a finished solution.

Version notes

Block comments are available in C89 and later. Line comments were standardized in C99, so strict C89 builds may reject them. The course uses C17 and therefore permits both forms. Documentation conventions do not change these delimiter rules.

Summary

Comments preserve reasons and contracts while leaving execution to the actual statements. Choose short, accurate explanations and remember that block comments cannot nest. Next, use source and runtime evidence in Errors and Debugging Basics.
