Introduction

Most decisions and repetitions are clearest with if, switch and loops. Sometimes a C function acquires several resources and must release them on several failure paths. A goto statement can transfer control to one shared cleanup location inside that function.

Think of returning borrowed lab equipment at a single desk before leaving through different doors. The shared desk prevents forgetting one item on an unusual route. This is a limited reason to use goto. Scattered backward and forward jumps can instead turn a simple route into a maze.

Syntax and reading guide

if (failed) {
    goto cleanup;
}
/* normal work */
cleanup:
    /* release resources before returning */
    return status;

A label is an identifier followed by a colon and attached to a statement. The goto target must be a label in the same function. A jump cannot enter another function or another running program.

Follow the values and decisions

When control executes goto, the next statement comes from its target label. Statements between the jump and target are skipped. A forward label is allowed: you do not need to place its spelling before the goto. Labels have function scope, although ordinary local-variable visibility still follows block rules.

For a simple input check, returning immediately is usually clearer than jumping to a label that only returns. Cleanup becomes useful when several earlier actions require matching release actions. Each error path can set an appropriate status and go to the same release section.

The resource example introduces dynamic memory, storage requested while a program runs. malloc returns a pointer to that storage or NULL on failure. A pointer refers to an object; the unary star accesses that object. free releases an allocation, and free(NULL) is safe. These ideas are developed in dynamic memory; here they illustrate why one cleanup path matters.

Initialize both resource pointers to NULL before attempting either allocation. If the first allocation fails, neither resource exists. If the second fails, the first still needs releasing. The cleanup section can safely free both pointer values in either case because a missing allocation remains NULL.

The normal path also falls through cleanup after finishing the useful work.

Examples

A forward exit label

The false readiness flag causes a forward jump to finished. Work is skipped, and End prints. An if-else would express this tiny choice more directly; the example isolates the meaning of the transfer.

A status reaches one reporting point

The condition does not jump because valid is one. Accepted prints, and ordinary fall-through reaches report. A label is not a barrier; normal execution can reach it just as a jump can.

Release two possible allocations

Successful allocations hold twelve and eight, producing total twenty. Both are then freed through cleanup. Either allocation failure instead reaches the same release section with status one. NULL initialization makes missing-resource cleanup safe.

The program never dereferences an allocation that failed.

Boundaries and alternatives

A cleanup label does not automatically run when any arbitrary return executes. Every path that owns resources must reach the release section before returning. Review the control flow rather than assuming the label's presence is enough. Release in a sensible reverse-acquisition order, especially when one resource depends on another.

Do not jump past initialization and then read a skipped local value. Ordinary fixed-size local variables do not receive automatic initialization merely because a jump enters their scope. C17 also forbids certain jumps into scopes containing variably modified types. Avoid jumping into nested blocks; keep cleanup in the same clear outer scope as its resource pointers.

A break cannot leave several nested loops at once. A flag often makes that search termination clear; a carefully placed goto can also leave them for a named exit. Compare those designs in loop control. Prefer the one that exposes the search intent and cleanup obligations with the fewest hidden paths.

The ownership table is more useful than hoping an allocation failure happens during a demonstration. Each incoming path has defined pointer values. No path reads through NULL, and no successful allocation is abandoned. When adding a third resource, extend the table before adding another failure exit.

This keeps the cleanup design reviewable as the function grows.

Common mistakes

Using goto to imitate every loop

A named loop already shows where repetition starts, what keeps it going, and how it advances. Replacing those parts with labels spreads the same reasoning across the function. Use a loop for ordinary counted or conditional repetition.

Jumping to cleanup before initializing resource pointers

An uninitialized pointer cannot safely be passed to free. Initialize ownership state before any possible failure jump. A shared cleanup path needs values that are valid on every incoming path.

Questions to ask while reading

QuestionRule and reason
Where must a goto target label belong?In the same function. The jump cannot transfer between functions.
Can ordinary execution reach a label without goto?Yes. Labels mark statements and do not block fall-through.
When is a cleanup goto useful?Several failure paths share resource releases. One release section can handle partial ownership consistently.
What should a resource pointer contain before acquisition?NULL. free(NULL) is safe on missing-resource paths.
Does a cleanup label run automatically before every return?No. Control must actually reach the cleanup section.
Why avoid jumping past initialization?A later read may use a value never assigned. Skipping initialization can invalidate the data flow.
What is usually clearer for ordinary repetition?A structured loop. A loop keeps the repetition condition and body together.

Give each resource one clear owner

Cleanup is easier when the function knows exactly which successful acquisitions it owns. A pointer copied elsewhere does not create a second allocation, so freeing both copies would be a double release. Keep one owning pointer for each allocation and treat other references as temporary views. Do not dereference a pointer after its allocation has been freed.

A later edit may add an early return for a new validation failure. If that return occurs after acquisition, it must also release the owned resources. Review exits again whenever the acquisition sequence changes. The shared label helps by offering one route, but it cannot prevent a programmer from introducing another route that skips it.

A status variable should describe success or failure independently of resource ownership. The first pointer may need freeing even when status reports an error. Conversely, a successful computation still needs cleanup before returning success. Do not tie release decisions only to the final status code.

For a short no-resource function, early returns can stay clearer than goto. The cleanup technique earns its place when it reduces duplicated release logic and makes partial acquisitions explicit. Choose it for the resource problem it solves, and keep ordinary calculations on a straightforward path.

Version notes

goto and function-scope labels exist in C89. C99 added VLA-related jump restrictions. In C17, a label must precede a statement; put a null statement after a label if a declaration must follow. C23 relaxes some label-placement rules.
