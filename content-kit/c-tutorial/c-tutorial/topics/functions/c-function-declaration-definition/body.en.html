Tell C the interface before using it

A declaration tells the compiler that a name exists and describes its type. For a function, a prototype states the result type and the types of its parameters. Think of a service counter with a notice saying what information to bring and what result you receive.

A definition also gives the function body. The prototype for triple promises an int result from one int input. The definition explains how to calculate that result. A semicolon ends the prototype; braces enclose the definition.

This separation lets you read main before reading every helper's implementation. main can show the overall plan near the top of a file. The compiler still needs the interface before each call, so it can check how that helper is used.

Prototype and definition side by side

int triple(int value);

int triple(int value)
{
    return value * 3;
}

Both lines describe the same function type. The prototype has no body and does not run any calculation. The definition contains an actual return expression. Do not put a semicolon between the definition's closing parenthesis and its opening brace.

Parameter names may be omitted from a prototype. int larger(int, int); still states two int inputs. Names become necessary in a definition when the body refers to those parameters. The names in a prototype need not match the definition's names; the types and order must agree.

A prototype can appear more than once if every declaration is compatible. A normal externally linked function should have one definition in the program. Repeating its full body in several source files causes multiple-definition problems during linking.

Compile a call using its declared type

When the compiler sees triple(9), the visible prototype says one int argument is expected. It checks the number of arguments and converts compatible argument values to parameter types. It also knows that the call expression produces an int.

The compiler does not infer the intended interface from a later function body. Put a matching declaration earlier, or move the whole definition before the call. These are two valid ways to make a declaration visible. Even a definition is also a declaration.

What each stage needs
StageNeeded information
Compile a callA visible declaration describing the function type
Compile the helperA compatible definition and a valid body
Link the programThe definition of each called external function

A missing body may therefore be a linker error even when the call compiles. A mismatched declaration can fail earlier, during compilation. Read which stage reports the problem before changing the code.

Share declarations through a header

A header is a file included where declarations are needed. The C preprocessor reads its contents into each including source file. Your own header uses quotes, such as #include "fees.h". Standard library headers normally use angle brackets.

A small fees.h can contain int fee(int hours);. Both the caller source and the fee implementation should include it. This gives the compiler a chance to compare the implementation with the same declaration the callers see. It reduces accidental disagreement between separately maintained files.

#ifndef FEES_H
#define FEES_H
int fee(int hours);
#endif

The guard prevents repeated processing of that header in one translation unit. A translation unit is one source file after its included text has been processed. These preprocessor lines are explained further in Header Files. A header normally shares declarations, while one source file supplies the function definition.

Including a header is not the same as linking an implementation. A declaration tells C how to call a helper; the linker still needs its compiled body. For standard library functions, the implementation comes from the toolchain's libraries.

Do not guess a function type

Calling without any earlier declaration

Old C allowed implicit function declarations in some situations. Modern C does not. In C99 and later, declare a function before using it. A compiler diagnostic about an implicit declaration is a reason to add the correct interface, not to suppress the warning.

Confusing empty parentheses with void

In C17, int f(); does not provide parameter-type information. Write int f(void); to explicitly declare no parameters. This also helps the compiler diagnose accidental extra arguments.

Changing only one declaration

Changing fee to return double requires updating its declaration and definition consistently. A caller compiled with an incompatible interface cannot safely rely on the function result. Put shared declarations in one header to reduce this risk.

Read signatures before bodies

For each prototype, say the result type and each input type aloud. Then compare those with the definition. Look especially for missing pointer stars, switched parameter order and inconsistent return types. These errors are easier to find at the signature than inside a long calculation.

Keep public interfaces small. A prototype should reveal the information a caller needs without exposing unrelated implementation details. Descriptive parameter names help readers even though they are optional in a declaration.

A changing empty parameter list

C99 removed implicit function declarations and implicit int. C17 still distinguishes f() from f(void) in declarations. C23 changes an empty parameter list to mean no parameters; explicit void remains clear in code shared with older standards.

One interface, one implementation

A prototype lets C check a call; a definition supplies the work. Keep them compatible and use headers when several source files need the same interface. Continue with Parameters and Return Values to design the information that crosses that boundary.
