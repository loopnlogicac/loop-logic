A flexible call needs a strict agreement

You have used printf with one value, several values and sometimes no converted values. Its parameter list cannot name a separate variable for every possible call. A variadic function accepts a variable number of arguments after its named parameters.

Flexibility removes information that ordinary prototypes provide. The function must learn the number and types of unnamed arguments through an agreement with its caller. A count can describe how many int values follow. A format string can describe both order and type.

Think of sealed envelopes accompanied by a packing list. The helper opens each envelope using the type written on that list. C does not attach a runtime type label to every variadic argument. A wrong packing list can therefore make the program read arguments incorrectly, causing undefined behavior.

Use an ordinary array interface when it describes your data more safely. Variadic helpers are useful for understanding formatted library calls and specialized interfaces. They are not a shortcut for accepting arbitrary unknown values.

Start, retrieve and finish a list

int sum_ints(int count, ...)
{
    va_list arguments;
    va_start(arguments, count);
    int total = 0;
    for (int i = 0; i < count; i++) {
        total += va_arg(arguments, int);
    }
    va_end(arguments);
    return total;
}

Include stdarg.h to obtain va_list and the argument-list macros. In C17, the ellipsis follows at least one named parameter. Here count is the last named parameter and tells the helper how many int arguments to retrieve.

va_list is an implementation-defined type for traversing unnamed arguments. Treat it as a special library-managed object, not as an ordinary int pointer. Its representation may contain more than one field or use an array type.

va_start prepares the traversal. va_arg retrieves the next argument using the specified type and advances the traversal. va_end finishes its use. Pair every successful start with an end in the same function before leaving that path.

In sum_ints(3, 12, 8, 5), count receives three normally. The ellipsis covers the three following values. The first va_arg reads 12, the second reads 8, and the third reads 5. The total progresses through 12, 20 and 25.

The count does not prove that three arguments actually exist. Calling sum_ints(3, 12, 8) breaks the agreement. The third retrieval has no corresponding argument and the behavior is undefined. There is no portable has_next operation that can repair an incorrect count.

Calling sum_ints(0) is valid for this helper because its loop reads nothing. A negative count would also skip this particular loop, but it lies outside the intended nonnegative count contract. A different helper, such as maximum, may require at least one value.

The caller must also respect arithmetic bounds. A valid count and correct types do not prevent the int total from overflowing. The examples use small integers, and the practice problems state bounds that keep both sums and products representable.

A tiny typed printing interface

The i, d and i tags select int, double and int. Unlike printf, this interface recognizes only those two tags.

The typed printing helper is a deliberately small analogue of a formatting interface. Its type string uses i for int and d for double. The helper follows those tags in order. It does not implement field widths, escaping, strings or the full printf conversion language.

The maximum practice has a stronger count requirement than sum. It retrieves the first value before entering its remaining loop. A count of zero would therefore violate its interface. Always read a variadic function's specific contract rather than assuming every counted list accepts an empty list.

Retrieve the promoted type

Default argument promotions apply to unnamed arguments. A float becomes double. Small integer types, including char and short, undergo integer promotion, usually to int. If int cannot represent every value of a small unsigned type, that type promotes to unsigned int instead.

The average helper retrieves double, even when the caller writes a float variable. Retrieving float with va_arg would use the wrong type. Conversely, passing the int literal 4 does not automatically turn it into double because the helper wants a floating reading.

Use 4.0, or an explicit conversion to double, when the agreement requires double. The ellipsis provides no fixed parameter type to trigger that conversion for an int. A normal declared double parameter behaves differently because its prototype describes the conversion destination.

How printf decides what to read

Conceptually, printf walks through its format string. Ordinary characters are printed directly. A conversion such as %d tells it to obtain an int; %f tells it to obtain a double. The conversion also describes how to format that retrieved value.

A format conversion and its corresponding argument must agree. Printing an int with %f is not a numeric conversion request; it tells printf to retrieve the wrong argument type. That mismatch can cause undefined behavior. Convert the value first, then use the matching conversion.

Compilers often recognize printf-like calls and diagnose literal format mismatches. This is valuable assistance, but it is not a general runtime type system for your own ellipsis interface. A format constructed during execution can also hide mistakes from a compile-time format check.

scanf is variadic too, but its conversion rules concern destination pointers. For example, %f expects float pointer and %lf expects double pointer there. Do not transfer printf's floating conversion rules to scanf without considering what each function receives.

Copy a traversal before reusing it

Reading a va_list advances its state. A second loop over the same already-consumed state does not automatically restart at the beginning. To perform two independent traversals, use va_copy before consuming the original list. End the copied list as well as the original.

The show_twice helper starts first, copies it into second, and computes a sum and product. Each va_arg advances only its own list. Ordinary assignment between va_list objects is not a portable replacement for va_copy because their representation varies.

Passing a va_list to another function has additional ownership rules. A called function that consumes the list can affect the caller's usable traversal state. Standard vprintf-family functions are designed around a va_list interface. When you need to retain an independent traversal, make and manage a separate copy.

Do not return a va_list that depends on arguments of a function call that has ended. Its traversal is tied to the active variadic call and its argument storage. Keep initialization, copying, consumption and cleanup within a clearly defined lifetime.

An ellipsis does not validate its contents

Using a count larger than the argument list

The helper cannot infer where the list really ends. A sentinel convention also requires the caller to provide the correct sentinel type. Prefer an array plus length for runtime-sized input collected in a loop.

Requesting a convenient type instead of the passed type

va_arg performs retrieval, not arbitrary numeric conversion. Retrieve the promoted type that was passed, then convert that retrieved value if the calculation needs another type.

Returning before va_end

An early return after va_start still needs cleanup. Structure the helper so every started list reaches its matching end. The average helper handles its empty-count decision before starting a list.

Assuming a list can be indexed backward

The macros provide forward traversal. They do not expose a portable array of all arguments or support decrementing a cursor. Store retrieved values in an ordinary array if later random access is required.

Prefer a small, documented type agreement

Write down the meaning of every named parameter and the exact sequence of unnamed types. Check that every call obeys the count and promotion rules. Keep a variadic interface narrow enough that readers can verify it without guessing.

If values originate in an array, keep them in that array and pass its length. You cannot turn an arbitrary runtime array length into a matching ellipsis call in standard C. For a reusable formatting wrapper, consider the existing vprintf family rather than inventing an incompatible list representation.

C17 and C23 differ at va_start

stdarg.h is available since C89, while va_copy was added in C99. C17 uses va_start(list, last_named_parameter) and requires a named parameter before the ellipsis. C23 relaxes these rules. These programs retain the C17 form for a clear older-standard baseline.

Flexible arguments require exact types

A variadic function traverses arguments according to a count or type description supplied by its caller. Promotions, list lifetime and va_end matter as much as the calculation. Continue with The math.h Library for ordinary typed functions that perform common numerical work.
