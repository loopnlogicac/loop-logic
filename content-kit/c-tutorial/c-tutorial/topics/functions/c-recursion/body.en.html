Solve one smaller version first

Imagine a row of students passing a question backward. Each student asks the next student about a shorter remaining row. The last student knows an immediate answer. Answers then travel forward, with each waiting student adding one small contribution.

Recursion is the same general idea in a function. A function calls itself to solve a smaller instance of its problem. A factorial helper asks for the factorial of a smaller number. It then multiplies that returned result by its own number.

Recursion is useful when a problem already describes itself through smaller parts. It also requires careful stopping rules. A call that keeps asking the same question never reaches an answer. Before writing recursive code, identify both the simplest case and a measure that decreases.

Base case before the smaller call

unsigned long long factorial(unsigned int n)
{
    if (n == 0) {
        return 1;
    }
    return n * factorial(n - 1);
}

The base case returns an answer without another recursive call. Here it is zero factorial, defined as one. The recursive case expresses the current answer using a smaller call. For positive n, factorial(n) equals n times factorial(n minus one).

The condition appears before subtracting from an unsigned zero. Otherwise n minus one would wrap to a very large value. Correct ordering protects both termination and arithmetic. The accepted input domain in the practice task is zero through twenty.

A function can also recurse indirectly, by calling another function that eventually calls it again. The same requirements apply to the complete call cycle. There must be a reachable stopping case and progress toward it.

The factorial loop and recursive helper calculate the same mathematical product. The difference lies in saved work. The loop updates one product repeatedly. The recursive version keeps enough information to complete each waiting multiplication later.

For Fibonacci, the base answers are F(0) = 0 and F(1) = 1. F(4) asks for F(3) and F(2). F(3) then asks for F(2) again. This duplicate work matters even though each individual call is short.

Compare time and extra storage

A factorial call on n performs roughly n multiplications. Both the loop and direct recursive version therefore take O(n) time. Big-O describes how work grows as the input size grows; constants and machine details are left out.

The direct recursive factorial has O(n) active call depth in its straightforward execution model. The iterative version uses O(1) extra working storage. For a long count, the loop often has a practical advantage because it does not need a growing chain of calls.

Naive recursive Fibonacci is much more expensive. Its call tree branches repeatedly, giving exponential time, commonly bounded by O(2^n). Its maximum active depth is O(n), not exponential, because branches are executed one after another rather than all remaining active together.

An iterative Fibonacci calculation keeps the previous two numbers and computes the next. It takes O(n) time and O(1) extra storage. Saving already computed answers is another way to avoid repeated work, introduced later with dynamic programming.

A tail call is a call whose result can be returned without further work. The factorial expression here is not tail-recursive because multiplication remains pending. Even a tail-recursive version has no guarantee of constant call storage in standard C.

Termination is necessary but not sufficient

A recursive function may terminate mathematically yet still fail for a large input. Real implementations have limited execution storage. Too many active calls can exhaust the call stack or another implementation resource. C does not promise a portable recursion-depth limit or a recoverable stack-overflow result.

Keep recursion depth bounded for classroom tasks. Do not demonstrate a missing base case by deliberately running until a crash. Instead, inspect the recursive argument and show why it fails to shrink. A debugger can display active calls for a small safe input.

Arithmetic limits are independent of depth limits. Twenty factorial fits in an unsigned long long on every conforming implementation with at least its standard minimum range. Larger factorials may exceed that type even when the call depth is still small. Unsigned wraparound is defined, but it is not the intended factorial answer.

The zero case deserves direct testing. A loop that starts its product at zero would return zero for every factorial. A recursive factorial returning zero at its base case makes the same mathematical mistake. Correct termination must also return the correct identity value.

Check progress and combine the returned result

Calling with the same argument

A positive factorial call that invokes factorial(n) has made no progress. Its base case stays unreachable. Use n minus one only after confirming that n is not already zero.

Ignoring the recursive result

Calling factorial(n minus one) as a statement throws away its value. The current call still needs to multiply by that value and return the product. Follow the data coming back as carefully as the calls going down.

Writing only one Fibonacci base case

The recurrence needs two starting values. Allowing the n equals one case to subtract two from an unsigned n creates a huge argument. Handle both values below two before branching.

Explain a recursive function in three claims

State the answer for the smallest input. State why every recursive call uses a smaller valid input. Finally, explain why combining a correct smaller answer produces the current answer. These three claims give a practical correctness argument.

Use small traces before larger numeric tests. For factorial, trace zero, one and four. For Fibonacci, draw F(4) with its repeated F(2). Choose iteration when the recursive form adds depth without making the reasoning clearer.

Recursion has no special keyword

C supports recursive function calls without an extra keyword. C17 does not require tail-call elimination or prescribe the available call-stack size. Compiler optimizations may alter resource use, so portable code cannot rely on a particular optimized call layout.

Shrink the question, then build the answer

Recursion needs a correct base case, a smaller recursive case and a way to use returned answers. Count both repeated work and maximum active depth. Continue with Recursion Problems to apply these ideas to digits, Hanoi and searching.
