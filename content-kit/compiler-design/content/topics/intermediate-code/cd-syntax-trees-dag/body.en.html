Introduction

Suppose a fee formula contains (base + tax) * (base + tax). Drawing the syntax literally gives two addition branches. If base and tax keep the same values, both branches calculate the same result. A directed acyclic graph, or DAG, can represent that shared calculation with one addition node and two uses.

An abstract syntax tree, or AST, keeps the meaningful operations of a program while dropping grammar scaffolding. A DAG goes further by allowing several parents to refer to one node. Both describe structure, but they answer different questions about identity and repeated work.

Sharing is a claim about values, not matching text alone. A repeated spelling after an assignment may refer to new data. A useful compiler representation therefore records which version of each variable a leaf means. This lesson uses pure scalar arithmetic inside one basic block, where execution order is explicit.

Worked trees and value numbers

From concrete tree to AST

For (a + b) * (a + b), a concrete parse tree includes E, T, F and punctuation nodes. The AST needs only multiplication, two additions, and their operand leaves. Parentheses disappear because the tree shape preserves their grouping.

An AST occurrence represents a particular use of an operator in source. In the DAG, the multiplication node has two edges to the same addition node. The graph has no directed cycle because a value cannot depend on itself through an unfinished arithmetic computation.

Value-number construction

A value number is an internal identity for a value known to be equivalent to another occurrence. Keep a map from leaf values or operator-and-operand keys to numbers. When a key already exists, reuse its number. Otherwise create a node and assign a new number.

The suffix 0 identifies the incoming version of each name. The resulting TAC needs t1 = a + b and t2 = t1 * t1. Generate nodes in dependency order so an operation appears after its operand nodes. Sharing the graph is not enough if your code emitter still recomputes a node for each incoming edge.

Assignments change value identities

Consider x = a + b; a = a + 1; y = a + b. The final addition is not the first addition. The new a value needs a fresh value number, while b can keep its incoming identity. Keep a current-name map and update the destination after computing each right-hand side.

The old value v1 remains a valid graph input for x even after a stops naming it. This is why value numbering separates a variable's current spelling from the value already captured by an earlier computation. An implementation that mutates leaf a in place would incorrectly change x's meaning.

Aliases and memory barriers

Scalar names are the easy case. Now imagine p and q can point to the same location. A store through q may change the next load through p. Even if the text *p appears twice, sharing those loads needs alias information or a conservative invalidation rule.

A classroom DAG can clear memory-expression entries after an unknown store or call. That loses some optimisation opportunities but preserves correctness. Better alias analysis can prove that particular locations are independent. Never turn an absence of information into a claim that two memory accesses are unrelated.

Equivalence rules and costs

Value-number keys must preserve operation and operand identities. For subtraction, (+,v1,v2) and (-,v1,v2) differ, and (-,v1,v2) differs from (-,v2,v1). For mathematical integer addition, you may normalise operand order because addition is commutative. Such normalisation is an extra rule that must match the language and target arithmetic semantics.

Floating-point reassociation needs special care. Although a+b and b+a often agree numerically, NaNs, signed zero, exceptions and language evaluation rules can matter. Replacing (a+b)+c with a+(b+c) can change rounding even for ordinary finite values. Our worked DAG does not apply floating-point algebraic identities.

With a hash map and fixed-size keys, numbering n tree occurrences takes expected O(n) time. The graph has no more nodes than the original tree. Its storage includes the key map and node records. Emitting each distinct operation once takes time proportional to the number of DAG nodes and edges used by the result.

To inspect a numbering result, list each distinct key once and check every use against its assigned node. A shared node must denote one unchanged value on every path represented by the graph. If two uses require different versions of an operand, keep separate nodes even when the source text is identical.

A shared node's value can have a longer lifetime than either original local computation. That can increase register pressure. Fewer arithmetic operations do not automatically guarantee faster machine code, because retaining the shared result may require extra loads or spills. Optimisation must eventually consider the target's storage costs as well as expression counts.

When a destination receives a DAG result, several variable names can label the same node. If only y is needed at block exit, code generation may omit a copy to an unused x. That additional decision requires liveness information. The DAG alone tells you equivalence, not which outputs remain observable.

Common mistakes

Merging by spelling after reassignment

The two a+b expressions around a write to a use different operand values. Update the current-name map after each assignment. Preserve the earlier node for users that still need the old value.

Sorting operands for every operator

Swapping subtraction operands changes its result. Only canonicalise an operator whose relevant semantics permit the swap. Include the operator identity and types in the key when those distinguish computations.

Forgetting to mark shared nodes as emitted

A recursive tree emitter visits every occurrence. A DAG emitter needs a visited set or an explicit topological schedule. Otherwise the graph looks shared on paper while the generated code repeats the work.

Summary

An AST records expression grouping; a DAG can also record equivalent values. Value numbers make sharing explicit, provided writes and effects do not invalidate the claim. Next, connect expression results to branch destinations in control-flow translation.
