Introduction

A function call needs more than a jump to another instruction. The called function must remember where to return, where its arguments are, and which local values belong to this call. A runtime environment is the organisation that gives those values and control information a home while the program executes.

Imagine recursion as opening a separate worksheet for each call. Every worksheet can contain a local variable called n without overwriting another call's n. An activation record, often called a stack frame, is the runtime record for one active function invocation. Recursive calls need separate records even when they execute the same function code.

The compiler plans storage and emits access instructions. The operating system and runtime also participate in creating and managing the actual memory. A language's abstract storage model does not require every value to occupy memory exactly as a classroom diagram shows; optimisations may keep values in registers or remove unused storage.

Frames and parameter effects

A teaching frame layout

Use a simplified machine with four-byte slots and a downward-growing stack. The frame pointer, FP, names a stable point inside the current frame. Positive and negative offsets below are our chosen convention. They are not a universal ABI layout or a statement about Python frames.

An ABI, or application binary interface, defines concrete calling conventions such as argument locations and saved registers. A real target may pass the first arguments in registers, omit a frame pointer, or align the stack more strictly. The teaching offsets explain the idea without prescribing those target choices.

Recursive calls without shared locals

Let sum(n) return 0 for n=0 and n+sum(n-1) otherwise. Calling sum(3) creates four active invocations at the deepest point. Each has its own argument. Returns unwind in reverse call order.

The return address identifies code in the caller, while the saved frame pointer helps recover its storage. These are different pieces of information. Returning must both transfer control and restore the caller's view of live data.

Stack, static storage and heap

A stack is convenient when activations finish in reverse order of creation. Heap allocation supports objects whose lifetimes do not follow that order. Static storage is suitable for values that exist for the program's whole execution. Allocation choice depends on lifetime and language semantics, not merely whether an object is large.

A heap object can still be referenced by a local variable in a stack frame. Destroying that local variable does not necessarily destroy the object. Conversely, a pointer value living in the heap does not extend the lifetime of a stack object it points at. Separate where the reference lives from where the referenced object lives.

Comparing parameter passing methods

Let caller variable a initially hold 5. Call change(a), whose body sets its parameter x to x+1. Under call by value, x receives a copy. Under call by reference, x refers to the caller's variable. Under value-result, x receives a copy on entry and is copied back on normal return.

Call by name substitutes a delayed access to the caller's expression, usually implemented with a thunk. It is different from passing the already computed argument value. Expressions containing an index or another changing variable can therefore behave differently on repeated uses. The simple argument a hides that difference, so do not generalise from that row alone.

Aliasing changes the result

Consider set2(x,y) with body x=1; y=2, called as set2(a,a). Reference parameters both name the same caller variable. Value-result parameters are separate local copies, so the copy-out order matters when they both return to a. If the language does not specify that order, you cannot claim a single final value.

Python passes object references by assignment, often described as object sharing. Rebinding a parameter does not rebind the caller's variable. Mutating a shared mutable object can still be visible. Avoid calling this ordinary call by reference, because assigning a new object to the local parameter does not assign the caller's name.

Following access links

A dynamic link usually leads to the caller's activation. A static link, in a runtime with nested lexical functions, leads to an activation of the lexically enclosing function. If one sibling nested function calls another, the caller and lexical parent are different. Access to an enclosing local follows lexical structure rather than arbitrary call history.

A closure pairs executable code with an environment that keeps required captured bindings available. If a nested function escapes its defining call, an ordinary pointer into a popped stack frame is not enough. The runtime must preserve the captured storage, often in a heap environment. The exact representation depends on language rules for capture and mutation.

Procedure entry code, called a prologue, reserves frame space and saves required state. Procedure exit code, called an epilogue, restores state and returns. The compiler can omit unnecessary saves only when the calling convention and liveness information permit it. Correctness comes from preserving observable caller behaviour, not from following one fixed drawing.

Common mistakes

Allocating one local set per function name

Recursion requires one local set per active invocation. A single shared n would be overwritten by deeper calls and produce wrong returns. Associate ordinary locals with an activation, not only with the function's declaration.

Returning the address of an expired stack local

A local's address may stop denoting a live object after the function returns. A successful-looking run does not extend its lifetime. Allocate storage with a suitable lifetime or return the value itself under the language's rules.

Equating a reference parameter with every pointer argument

A pointer can be passed by value. The callee may modify the pointed object while reassignment of the local pointer leaves the caller's pointer unchanged. Specify which object an operation changes before comparing passing methods.

Summary

Runtime organisation connects calls, values, storage and lifetimes. Keep each activation separate, follow the chosen calling convention, and trace parameter effects through actual aliases. Next, divide generated instructions into basic blocks for control-flow analysis.
