Introduction

A compiler can often perform work once that the original program performs repeatedly. If a fee expression contains 4*5, no input is needed to know its value. Code optimisation transforms a program while preserving its required observable behaviour. The aim may be faster execution, smaller code, or lower resource use.

Preserving behaviour is the first condition, not a detail added after finding a shorter expression. Arithmetic overflow, exceptions, input/output, memory aliases and floating-point rules can all make a tempting rewrite invalid. This lesson states the assumptions for each worked transformation instead of promising that every algebraic identity is always legal.

A local optimisation reasons within one basic block. A global optimisation may use information from several blocks. A loop optimisation focuses on repeated work. These categories describe the scope of evidence, not a fixed order that every compiler must follow.

Worked transformations

Folding and propagating constants

Constant folding evaluates an operation whose operands are known constants. Constant propagation substitutes a known constant for a variable use. They often help one another: propagation exposes another operation that can then be folded.

Assume mathematical integers and no observable assignment to the temporary names. Begin with x=3, y=4, t=x*y, z=t+2. The final z is observable. Move through the block in execution order, updating what is known after each assignment.

At a join, a name is a known constant only when all relevant incoming paths agree. If one predecessor gives x=3 and another gives x=7, replacing x by 3 in the join block is wrong. A reaching-definitions or constant-data-flow analysis supplies the evidence needed beyond a single path.

Common expressions and dead assignments

A common subexpression repeats an operation on unchanged operand values. A dead assignment computes a destination whose value is never used before replacement or exit. Removing dead work is valid only when evaluating that work has no required effect or exceptional behaviour that must remain.

Loop-invariant code motion

Loop-invariant code motion moves a calculation outside a loop when repeated executions would compute the same value and moving it is safe. Let p and q be unchanged scalar integers. In a loop over i=0 through n-1, computing p*q on every iteration is redundant.

The n=0 row exposes an extra safety condition. Hoisting executes the product even if the loop body never runs. For pure mathematical integer multiplication that has no observable failure, this may be harmless. Hoisting a division that could trap, an invalid load, or an effectful call can introduce behaviour absent from the original program.

You must also ensure that all operands remain invariant, that the moved destination does not interfere with live values, and that the result reaches every replaced use. A preheader, a block entered once before a loop, provides a natural home for a safely hoisted instruction.

Strength reduction with a trace

Strength reduction replaces an expensive recurring operation with a cheaper equivalent update. For i starting at 0 and increasing by 1, the expression 4*i follows 0,4,8,12. Maintain a separate address offset j and increase it by 4 after each use.

The invariant before each use is j=4*i. It holds initially because both are zero. If the loop increments i by 1 and j by 4, the relation remains true at the next iteration. Initialise j before entering the loop and update it at the corresponding point, not before its first use.

A real target may implement multiplication by four as a shift or fold the scaled index into an addressing mode. An extra maintained variable can increase register pressure. Strength reduction should therefore be evaluated with target costs; the mathematical recurrence proves equivalence but does not guarantee a speedup on every machine.

A case where elimination is unsafe

Take x=a+b; a=input(); y=a+b. The first and last sums use different versions of a. Even if input returns the old value in one run, the compiler cannot assume that for every execution. Similarly, two identical loads around a store may read different data when pointers alias.

Choosing and combining passes

Optimisation passes can expose opportunities for one another. Constant propagation may make a condition always false. Removing that branch can make a block unreachable. Removing the block can make more assignments dead. Compilers therefore organise passes with explicit invariants and may repeat selected passes until no useful changes remain.

More aggressive is not automatically more correct. A pass must respect the source language's treatment of overflow and floating-point evaluation. For example, replacing x*0 by zero can suppress a NaN result for floating-point x. Reassociating large finite sums can also alter rounding. State the arithmetic model before applying familiar school algebra.

When explaining an optimisation in an exam, give the original code, transformed code, and the condition that permits the change. A short before-and-after trace on a representative input can illustrate the effect. Then explain why the preserved relationship applies to every allowed execution, rather than treating the one trace as a proof.

Common mistakes

Carrying a constant past an unknown write

An indirect store or function call may modify memory used by a later expression. Keep scalar and memory facts separate. Invalidate facts that an unknown effect might change unless alias or effect analysis proves independence.

Removing an operation because its result is unused

An unused result can still come from observable work. Preserve calls, volatile accesses, and required failures according to the language semantics. Liveness of the destination answers only part of the question.

Moving an induction update before its use

Using j after incrementing it by 4 would produce 4 on the first iteration instead of 0. Establish the invariant at the exact program point where the original expression was used. Trace the first and last iterations before accepting the rewrite.

Summary

Optimisation reduces work by using proven facts about values, effects and control flow. Folding and propagation exploit constants; sharing and liveness remove redundancy; loop transformations exploit repetition. To calculate facts across branches, continue with data-flow analysis.
