Introduction

TAC says which values a program needs, but it does not say exactly how a particular processor will compute them. Code generation turns intermediate operations into target instructions while respecting types, storage, control flow and the calling convention. A correct generator must preserve the values and effects described by the intermediate program.

Think of TAC as a cooking plan and the target machine as a kitchen with limited tools. A plan may mention many temporary bowls, but the kitchen has only a few physical bowls. Register allocation decides which values can share the scarce fast storage, and when a value must be saved elsewhere.

This lesson uses a deliberately small two-register machine. Its instructions and costs are stated below. They illustrate the reasoning without pretending to describe a real processor's full instruction set. Real code generation also handles many data types, addressing modes, exceptions, alignment requirements and architectural constraints.

Target instructions and allocations

Define the machine before selecting code

The target has R0 and R1, integer memory locations, and mathematical integer arithmetic. LD and ST move values between a register and named memory. ADD, SUB and MUL update their first register operand. Their second operand may be a register or a memory location. Each instruction has unit cost for this teaching example.

The destructive two-address form matters: ADD R0,b uses and then replaces R0. You cannot overwrite a live value in R0 unless another valid copy remains or the value is saved. A three-address target could have different instruction choices and different register pressure.

Select instructions for an expression

Generate result = (a+b)*(c-d). First compute the left child in R0, then the right child in R1. Multiplication can combine the two register values without a spill because neither intermediate needs to survive separately afterwards.

Register and address descriptors

A register descriptor records which value currently occupies a register. An address descriptor records the valid locations holding a value, including memory and registers. If a new value is computed in R0, memory for its destination may still contain an older value until a store occurs.

Descriptors describe validity, not merely the last spelling printed in code. After ADD, R0 no longer holds the old a value. Memory[a] is still valid because the operation did not assign to a. If t is live after multiplication, overwriting its only copy would be wrong and the generator must preserve it first.

Live ranges and interference

Two values interfere when they must be available at the same time and cannot share one physical register in the chosen representation. An interference graph uses values as vertices and simultaneous-live requirements as edges. Assigning registers resembles colouring that graph with the available register colours.

The interference edges are t1—t2 and t2—t3. There is no t1—t3 edge in this example because t1 dies when t3 is produced. Two colours suffice: R0 can hold t1 and then t3, while R1 holds t2. A value's textual name is not itself a reason to allocate a new register forever.

A genuine two-register spill

Now keep three independent values live: t1=a+b; t2=c+d; t3=e+f; u=t1+t2; v=u+t3. After computing t3, all three t values are needed. Two registers cannot simultaneously retain all three without saving one value in memory or changing the calculation schedule.

A spill saves a live value to memory so its register can be reused. Reloading is unnecessary in step 5 because this teaching target allows a memory operand. On a load-store machine, an extra load would be required. Instruction-set details therefore change the cost of the same allocation decision.

The use of t2+t1 instead of t1+t2 in step 5 is valid under our mathematical integer addition model. For subtraction, that operand swap would change the result. For a target or language with additional arithmetic restrictions, the instruction selector must respect those restrictions rather than assuming all familiar rewrites apply.

Instruction selection can combine operations

For x = y + 1, a target with INC may replace a load-plus-add pattern with an increment form, depending on where y and x reside. A target with scaled addressing may compute an array location without a separate multiplication instruction. Pattern matching chooses a legal target sequence for an intermediate subtree or region.

A cheaper-looking pattern may set condition flags that another instruction uses. It may also change exception behaviour or memory access width. Include these effects in the target model before accepting a replacement. Counting only arithmetic symbols in TAC is not a complete instruction-selection cost model.

From local choices to function code

A local generator can inspect each basic block, prefer values already in registers, and use next-use information to choose a register to reuse. If a value is dead, its register can be overwritten without a store. If the value is live and its only valid copy is in that register, save it before replacement.

At a block boundary, several predecessors may carry different register contents. A simple generator stores required live-out values and starts successor blocks with a conservative memory-based state. More advanced allocation coordinates locations across edges and can avoid these stores. Either strategy needs a clear invariant about where each live value is valid.

Calls introduce calling-convention constraints. Some registers may be caller-saved and others callee-saved. A value live across a call cannot assume that a caller-saved register keeps its contents. Preserve it in an allowed location or emit the required save and restore. Call arguments and returned values may also occupy fixed registers.

Real register files have classes: integer, floating-point, vector or special-purpose registers may accept different instructions. Some instructions require a particular register or tied operands. Graph colouring is a helpful model, but a practical allocator must include these constraints and may split live ranges or rematerialise cheap values instead of spilling them.

To review generated code, trace value identities rather than only instruction mnemonics. After every overwrite, ask whether any future use still needs the displaced value. At every branch and join, check that live values reach the expected locations. At function entry and exit, check that the calling convention's promises are met.

Common mistakes

Overwriting a live operand too early

A destructive operation consumes the old first operand. If that value is still needed later and has no other copy, save it first or choose another register. The printed destination name alone does not prove the old value is dead.

Treating a stale memory slot as current

A register-only computation does not immediately update memory. The address descriptor must mark only valid copies. Loading a stale destination slot later can silently restore an obsolete value.

Allocating registers without liveness

Using a different register for every temporary wastes limited resources. Reusing one for simultaneously live values loses data. Build or approximate live ranges before choosing which values can share storage.

Applying an instruction from an unstated machine

A memory-operand ADD is legal in our model but not in every target. Define operand forms and side effects first. A selection trace is meaningful only relative to its stated machine.

Summary

Code generation combines semantic instruction selection with careful value placement. Descriptors track valid copies, liveness permits register reuse, and spills preserve values when capacity is insufficient. Next, inspect short target sequences with peephole optimisation.
