Introduction

A road segment between junctions has no decision point inside it. Once you enter, you continue to its end. A basic block is a similar straight-line instruction sequence: entry is at its first instruction, and control leaves only at its end. It is a convenient unit for analysing generated code.

A branch destination must begin a block, because control can enter there from somewhere else. An instruction after a branch must also begin a new block when it exists. Otherwise a supposedly straight-line region would contain a possible control transfer before its end.

A control-flow graph, or CFG, uses blocks as vertices and possible immediate transfers as edges. This CFG abbreviation means control-flow graph here, rather than context-free grammar. The graph describes possible paths; it does not itself tell you which conditions can be true for a particular input.

Indexed instruction model

The Python implementation uses four operation kinds: assign, if, goto and return. A conditional if has two possible successors, its target and the next instruction. A goto has only its target. A return has no successor inside this function. Other assign instructions fall through normally.

Targets are zero-based instruction indices within the same nonempty list. Text is retained for display but is not parsed to discover branches. Explicit operation kinds prevent a variable name containing the word goto from being mistaken for a control transfer. The empty list has no blocks and prints empty.

The edge B4→B1 is a back edge in this example's loop. B1's false condition path enters B2; its true path leaves for B5. A graph can contain a cycle without guaranteeing that execution terminates. Termination also depends on updates and conditions, such as whether i eventually reaches n.

The word exit in the program's printed display means that there is no successor block in the list. It is not a new numbered block. A later analysis can add a synthetic exit vertex if it needs one. Keep that convention consistent when presenting predecessor sets or data-flow boundaries.

An unreachable instruction after goto

Take 0: goto 2; 1: x=99; 2: return x. All three instructions are leaders: entry marks 0, the goto marks target 2, and the following instruction marks 1. The edge from B0 goes directly to B2, leaving B1 unreachable from entry.

Keeping B1 in the initial partition does not claim that it executes. It preserves a faithful view of the input code. Once reachability is known, an optimisation may remove B1 if the language's observable semantics allow that removal.

Targets equal to fallthrough

Suppose 0: if flag goto 1; 1: return x. Both outcomes lead to instruction 1. The block graph contains one successor edge B0→B1, rather than duplicate copies of the same edge. The implementation uses a set while collecting successors, then sorts it for stable presentation.

A self-targeting goto is also legal in the stated model. Its block has an edge to itself. A target outside 0 through n-1 is rejected, including a target equal to n. Use an explicit return instruction if you need an in-range exit destination in this representation.

Why the algorithm works

Every location where a new control path can enter is a leader: function entry and branch targets. Every instruction after a terminator begins a separate region. Between consecutive leaders, no branch target enters the middle and no earlier terminator exits before the last instruction. Therefore each region has the required straight-line property.

For a block's final instruction, enumerate every permitted successor from the operation kind. A goto contributes its target only. An if contributes target and fallthrough. A return contributes neither. An assign at the end of a nonfinal block contributes the next block. Mapping instruction indices to owner blocks turns these transfers into graph edges.

With n instructions and k leaders, collecting leaders and mapping owners takes O(n). Sorting leaders costs O(k log k) in this implementation. Building successors takes O(k), since each block has at most two. Storage is O(n) for membership lists and ownership, plus the graph's small successor lists.

Common mistakes

Adding fallthrough after an unconditional jump

A goto does not execute the physically next block unless that block is also its named target. Adding an extra edge invents a path and can make later analyses unnecessarily conservative or incorrect.

Combining a jump target with the preceding block

A target inside a block violates single entry. Mark targets before cutting the instruction list. Splitting only after branch instructions misses this second source of boundaries.

Confusing unreachable with nonexistent

An unreachable instruction still belongs to the original code and must appear somewhere in the initial partition. Reachability analysis can justify removal later. Block detection itself should not lose instructions.

Python implementation notes

The records use an int-or-None annotation, supported by Python 3.10 and later. Examples run with Python 3.12. Integer target validation excludes Boolean values even though Python treats bool as an int subclass. Return instructions terminate their block and have no internal successor.

Summary

Leader marking partitions every instruction into a straight-line region. Successor rules then describe exact transfers between regions. Keep partitioning, edge construction and reachability as separate questions before studying data-flow analysis.
