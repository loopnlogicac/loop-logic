Introduction

Think of a university building with a room list on every floor. Room 201 means something only when you know which floor you are using. Names in a program have a similar problem. A symbol table records declarations and lets the compiler find the declaration meant by each use of a name.

The table is more than a list of spellings. A lexer may recognise marks as an identifier, but semantic analysis needs its type and scope. Later phases may need its storage location. Keeping this information together prevents every compiler phase from inventing a separate, inconsistent account of the same declaration.

A scope is a region where a declaration can be found by name. Under lexical scoping, source nesting determines which declaration is visible. A function's caller does not change that source relationship. We use lexical block scopes here, with declarations visible after they are processed.

The runnable entry keeps name, type, depth and slot. These are enough to demonstrate lookup and shadowing without pretending to implement a machine stack frame. Slot 0 in two different scopes does not imply the same runtime address. Real frame layout also considers size, alignment and lifetime.

Use enter when a block opens and leave when it closes. Declare inserts into the current scope only. Lookup searches the current scope, then each enclosing scope, stopping at the first match. Rejecting a duplicate declaration and permitting shadowing are separate rules in our small language.

A failed declaration must not overwrite the first declaration. Keep its original type and source location so a diagnostic can mention both lines. Likewise, a failed lookup should not insert a placeholder normal variable. Such a placeholder can hide a genuine error in a later use.

Hash tables and lookup cost

A dictionary uses hashing to find a key without scanning all declarations. With a well-behaved hash table, insertion and lookup within one scope have expected constant cost. Hash collisions are handled by the dictionary implementation. They are different from a duplicate source name in the same scope.

If there are d active scopes, an unsuccessful lookup checks all d dictionaries. Its expected cost is O(d), not O(1) for the entire chain. A successful lookup near the current scope can finish sooner. Total entry storage is proportional to the declarations retained in those scopes, plus the stack of scope dictionaries.

Another design keeps one dictionary from each name to a stack of declarations. That can make lookup direct, but leaving a scope must undo each declaration introduced there. The stack-of-dictionaries design makes enter and leave easy to see, which is useful while learning the rules.

Lexical scope versus a caller chain

Imagine global x:int, function outer containing x:real, and a separately declared global function show that reads x. Calling show from outer does not make show see outer's local x under lexical scoping. Show was defined globally, so its enclosing source environment supplies the global declaration.

The small scope stack models traversal of nested source blocks. Do not use it as a complete runtime implementation for separately declared functions or closures. A real compiler associates each function with its defining environment and emits the necessary access mechanism later.

Examples with scope dictionaries

Hide and restore a name

The first program declares marks twice in different scopes. Lookup chooses the inner entry while its scope exists, then returns to the global entry. The two printed depths make the resolution visible.

This behaviour is called shadowing. The outer entry stays in its own dictionary throughout the inner block. Nothing has to copy its value back when the block closes.

Keep a duplicate from overwriting

The second program attempts a duplicate declaration. It catches the error and prints the surviving entry. You should still see the original int declaration, showing that validation happens before insertion.

Duplicate-name diagnostics can therefore be added without corrupting subsequent semantic analysis. Continue only when your compiler has a deliberate error-recovery policy, rather than silently replacing the declaration.

Reject invalid scope operations

The third program demonstrates an unknown name and an attempt to leave global scope. Both are rejected. Afterwards the global dictionary still accepts a new declaration, so a rejected operation has not broken the scope stack.

These examples represent source types as strings. They could instead store the type expressions from type checking. The dictionary organisation does not depend on the internal shape of the type object.

Common mistakes

Looking outside before looking inside

Searching the global table first makes an outer declaration win over a legal inner shadow. Reverse the order of the active scope stack during lookup. Stop immediately after finding the nearest declaration.

Clearing the global dictionary on block exit

Leaving an inner block should remove only its dictionary. Clearing every dictionary destroys declarations that remain visible. Keep a permanent global scope and reject an attempt to pop it.

Treating a hash collision as redeclaration

Two different names can have the same hash without denoting the same identifier. Dictionary key equality handles that case. A redeclaration error arises when the actual name already exists in the current source scope.

Python dictionary notes

Python 3.12 dictionaries support the operations used here without external packages. The examples print individual entries in deliberate order rather than depending on hash bucket layout. The slot counter assigns consecutive positions within each scope; it is an explanatory index, not a byte offset or a register number.

Summary

A symbol table connects identifier uses to declarations and their semantic information. Search the nearest lexical scope first, reject same-scope duplicates, and preserve outer entries when leaving a block. These entries will later help explain storage in runtime environments.
