Introduction

Suppose a marks formula adds a number to a truth value. The parentheses may be perfectly balanced, yet the calculation has no meaning in your intended language. Type checking asks whether each operation receives the kinds of values it accepts. It catches a different family of mistakes from parsing.

A type is a description of permitted values and operations. An integer can participate in arithmetic. A Boolean represents true or false. An array describes many indexed elements. The exact permissions belong to the source language, so a compiler must follow that language's rules rather than its implementation language's habits.

For this lesson, use a small language with int, real and bool. Addition accepts numeric operands. Comparing two numbers with less-than produces bool. Assignment permits an int value to enter a real destination, but rejects an implicit real-to-int conversion. These choices are explicit teaching rules; they are not a claim about every programming language.

Worked type derivations

Writing type expressions

A type expression builds a type from basic types and constructors. For arrays, include the index range or length and the element type. For functions, record the ordered parameter types and the return type. Merely writing function or array leaves out information needed to check a use.

Two independently written array(10, real) expressions can be structurally equal. A language using name equivalence may instead require the same declared type name. State which rule applies before deciding whether record or array assignments are legal. Our array examples use structural equality of length and element type.

A typing environment Γ maps names to declared types. The judgement Γ ⊢ e : T means that expression e has type T under those declarations. You do not need the expression's numeric result to derive its type. That is why a compiler can reject many errors without running the user's program.

Bool is excluded from every numeric cell. In Python, bool is a subclass of int. The implementation therefore tests the exact literal type before considering an integer. Otherwise True could accidentally become a source-language number, contradicting our rule even though the Python program runs successfully.

A coercion is an implicit conversion inserted by the compiler. An explicit cast is written by the programmer. A widening conversion often preserves a larger range of values, but machine floating-point cannot represent every large integer exactly. Our type rule permits int-to-real; it does not promise exact representation of every possible mathematical integer.

Arrays and function calls

Let scores have type array(3, int). Indexing scores[1] produces int because the index has type int. Indexing scores[True] is rejected in our language. Indexing scores[5] has a valid index type but an invalid constant bound; that is an additional check, not a reason to confuse type and value.

The executable type model checks the type of an array index, not its runtime bounds. A full compiler can separately reject a known bad constant index. When the index depends on input, a runtime bounds check may still be needed even after static type checking succeeds.

When checks happen

Static and dynamic checks

A static check happens before execution, using declarations and program structure. A dynamic check happens while an operation is executed, using actual values or runtime type information. A dynamically typed language can still detect syntax errors before running. A statically typed language can still need runtime checks.

The difference matters for diagnostics. A static error can point at an expression that would never execute. A dynamic error occurs only when execution reaches the operation. Neither style means that all incorrect programs can be recognised in advance.

Run the rule engine

The first program derives types from a small tuple-based expression representation. It prints successful results and catches deliberate invalid cases. An undeclared name receives a clear error instead of being assigned a convenient default type.

The second program prints all scalar assignment combinations. Each rejection follows the language's conversion table, including bool versus int. Notice that accepting an expression type and accepting an assignment are separate decisions.

A practical checker normally records the type on each AST node. During a second traversal, it can insert explicit conversion nodes such as int-to-real. Later code generation then sees the intended operation directly, instead of rediscovering conversion decisions from names or token spellings.

Common mistakes

Borrowing Python's arithmetic policy

Python permits True + 1. Our source language rejects the same operand pair. Keep a separate table of source-language rules even when the compiler is written in Python. Host behaviour is an implementation detail, not the language specification.

Treating a cast as proof of safety

An explicit real-to-int cast may discard a fractional part or fail for values outside a machine range. A cast expresses a requested conversion. Explain its value semantics and range rules before claiming the operation is safe.

Losing the original diagnostic

Once a child is invalid, avoid reporting many invented parent errors. A larger compiler often propagates an error type to suppress these cascades. The small implementation raises on the first invalid subtree, which keeps its examples easy to trace.

Summary

Type checking applies declared rules to expression structure and reports incompatible uses. Separate operand typing, assignment conversion, and value-dependent runtime checks. To supply the typing environment in nested programs, continue with symbol tables.
