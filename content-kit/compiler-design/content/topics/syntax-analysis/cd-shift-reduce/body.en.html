Introduction

Picture assembling a sentence from word cards on a desk. You place the next card on a pile, then replace a recognised phrase with its name. Shift-reduce parsing works upward in this way, from tokens toward the start symbol.

A shift moves the next input token onto the stack. A reduction replaces a recognised right side β with its production’s left side A. The parser does not expand the start symbol first. It recognises smaller phrases and combines them until the whole input forms a start phrase.

The key problem is deciding when a phrase is ready. A right side somewhere on the stack is not automatically safe to reduce. The correct reduction must fit a reverse rightmost derivation. LR states, introduced below and developed in the next topic, carry the context needed for that decision.

Grammar and representation

0. S' → S
1. S → C C
2. C → c C
3. C → d

This small grammar recognises two groups. Each C contains zero or more c tokens followed by one d. Thus d d, c d d, and c c d c d are valid. A single d is incomplete, and d d d has an extra group. The augmented rule S′ → S is used only to identify acceptance.

A handle is a production occurrence whose reduction reverses the next step of a rightmost derivation. Handle pruning repeatedly removes that occurrence. Brackets in the trace mark the correct handle on the stack; they are explanatory marks, not grammar symbols. The parser never changes the already unread suffix during a reduction.

The rightmost derivation is reconstructed backward
Forward derivationReverse reduction
S ⇒ C CC C → S
C C ⇒ C dC d → C C

Read the forward derivation downward and the reduction column upward. The first bottom-up reduction changes the first d to C, because the rightmost derivation produced that d last. The second d was produced earlier and remains unread at that moment. This is why bottom-up parsing reconstructs a rightmost derivation in reverse.

How the parser works

Store context using a state stack

The runnable recogniser uses a list of state numbers rather than keeping symbol and state pairs. The current state summarises the viable prefix already recognised. ACTION[state,lookahead] selects a shift, reduction, acceptance, or error. GOTO[state,nonterminal] supplies the state after a reduction has produced a phrase.

On a shift to state j, append j and advance one input token. On A → β, remove len(β) states, inspect the newly exposed state, and append its GOTO on A. For an empty right side, remove zero states. Do not use stack[:-0], because that slice is empty rather than unchanged.

The state-only trace and the symbol trace describe the same decisions. In the state trace, r3 means C → d, r2 means C → c C, and r1 means S → C C. The leading state 0 remains at the bottom. Acceptance uses the augmented start situation and lookahead $, rather than shifting a literal end token.

Separate the two conflict types

Conflicts are competing ACTION entries
GrammarSituationCompeting actions
E → E + E | idAfter E + E with lookahead +Shift +, or reduce E → E + E.
S → A | B; A → id; B → idAfter id with lookahead $Reduce A → id, or reduce B → id.

A shift/reduce conflict offers both reading another token and completing a phrase. For E → E + E | id, the choice after E + E on + decides whether an addition chain groups left or right. The grammar does not express that association. A layered grammar or a documented precedence rule can settle it.

A reduce/reduce conflict offers two different completed productions. For S → A | B with A → id and B → id, the single id has two parse trees. The parser cannot know which phrase name to create. Reordering production lines hides the choice but does not remove the grammar’s ambiguity.

A conflict does not always prove that a grammar is ambiguous. A weaker table method can combine contexts too broadly. For example, LR(0) may offer two reductions that SLR separates using FOLLOW sets. Keep grammar ambiguity separate from the power of the chosen table-construction method.

Why greedy suffix matching fails

Suppose E → E + E | E * E | id. After recognising E + E with lookahead *, an intended multiplication-first language needs to shift * and extend the right operand. Reducing every available E + E immediately would instead force the addition first. A stack suffix match alone has no knowledge of precedence.

An LR table turns this contextual decision into a lookup. The examples construct tables rather than encoding “reduce whenever possible.” They retain every competing action in a set. The recogniser refuses a conflicting table before reading input, so success does not depend on Python’s set iteration order.

A reduction consumes no new input. The next ACTION lookup uses the same lookahead in a different state. A shift always advances the input position. This distinction helps you check a trace: two consecutive reductions are possible, but two different unread suffixes require a shift between them.

For a fixed deterministic LR grammar, recognition normally takes linear time in the number of tokens. Each token is shifted once, and the number of reductions is linear for the small grammars used here. The stack can grow linearly with a long unfinished phrase. Generating the state collection can cost far more than recognition, so parser generators build tables before ordinary source files are parsed.

When tracing an exam problem, state the grammar numbers, stack orientation, initial state, input marker, and acceptance rule. Then write one row before each action. For a reduction, show both its production and resulting GOTO state. That evidence lets a reviewer distinguish a correct parse from a lucky final S.

Common mistakes

Reducing any visible right side

A handle includes context from a reverse rightmost derivation. Let the parser state and lookahead choose the action rather than scanning for an arbitrary matching suffix.

Moving input during reduction

A reduction replaces recognised stack content. The next unread token stays unchanged until a shift occurs.

Treating accept as an ordinary reduction

Acceptance recognises the completed augmented start with $. It does not consume another source token or count as a C or S reduction.

Python version notes

Frozen sets are hashable in Python 3.12 and represent item sets. State numbering follows sorted outgoing symbols, so runs use a stable numbering scheme.

Summary

Shifts read tokens; reductions build phrases by pruning handles. Context decides which reduction is valid. In LR(0) items and SLR, you will construct the states and ACTION/GOTO entries that drive these decisions.
