Introduction

Imagine a teacher handing a calculation to three assistants. One handles sums, one handles products, and one handles single numbers or brackets. Each assistant returns a completed value before the caller continues. Recursive descent organises parsing in this familiar way.

A recursive-descent parser uses functions that follow grammar rules. A function consumes the tokens belonging to its phrase and returns to its caller. Recursion handles nested phrases such as parentheses. Loops handle repeated operators without creating unnecessary recursive calls.

The parser here evaluates unsigned integer expressions using +, -, *, and parentheses. It also reads programs containing semicolon-terminated expressions. Unary signs, division, variables, and assignments are outside this language. Thus 9-2 is legal, while -2 is rejected because a factor cannot begin with minus.

Grammar and representation

program    → { expression ; } EOF
expression → term { (+ | -) term }
term       → factor { * factor }
factor     → NUM | ( expression )

Braces in this displayed notation mean zero or more repetitions; they are not source characters. The functions expression, term, and factor each implement one nonterminal. program implements the outer statement sequence. After an expression, the caller decides which following token is required.

Each token is a tuple containing its kind, value, and zero-based character position. NUM carries a Python integer; punctuation carries its own spelling. The scanner appends EOF once. Error messages add one to the character position so students see one-based columns. A tab counts as one character in this convention, not as a display-width tab stop.

The expression parser operates on source characters through its scanner. This differs from the preceding LL(1) recogniser, which receives token kinds such as id. Both designs separate lexical recognition from grammar decisions, but the recursive parser also carries numeric values.

How the parser works

expression first calls term. term first calls factor. When term sees *, it consumes the operator and obtains another factor before returning. Therefore expression receives the complete value 12 for 3*4. It cannot add the 3 early because its right-hand term has not yet finished.

A factor beginning with ( consumes that token, calls expression, and requires ). This recursive call starts a new expression level inside the parentheses. For (2+3)*4, the inner call returns 5 before the outer term multiplies by 4. The call stack remembers which closing parenthesis belongs to which opening one.

The expression loop updates value after each operator. This is a left fold: the result of the previous operation becomes the next left operand. Replacing the loop with value - expression() would recurse through the entire remaining tail. That alternative computes 9-(2-1), giving 8 and changing the language’s association rule.

Signal a failed expectation precisely

take(kind) checks the current token before advancing. If the kind differs, it raises ParseError with the column, expected kind, and actual kind. A failed take does not consume a token. The caller can therefore decide how to recover without losing the location of the error.

factor first accepts NUM. Otherwise it attempts the parenthesised branch and expects (. Consequently an operand error such as 8+; reports that ( was expected at the semicolon. That message names the remaining factor branch; a fuller diagnostic could say “expected a number or (”. The recogniser rejects the input correctly in either wording.

Unknown source characters are lexical failures. tokenize raises ParseError before returning its token list. The examples catch that exception around parser construction. Statement-level recovery cannot run if tokenisation never completed. This deliberate separation keeps the small parser’s syntax recovery from guessing what an unknown character meant.

Panic-mode recovery discards tokens until reaching a chosen boundary. Here the synchronising set is {;, EOF}. After a syntax exception, program advances to one of those tokens. If it finds ;, it consumes it and tries the following statement. If it finds EOF, the outer loop ends.

A statement value is saved only after its semicolon matches. Thus a partially computed 8+ result never enters the results list. A missing final semicolon also counts as an error even if expression returned a number. For input 7 without ;, the value 7 is discarded because the statement is incomplete.

Recovery must make progress. The scanning loop moves the token position unless it already sees a boundary. A boundary semicolon is then consumed. At EOF, parsing stops. Without one of these changes, the parser could report the same error forever at the same token. One recovery episode records one syntax error, even if several damaged tokens are skipped.

Semicolon recovery may discard more than the original mistake. For a missing ) inside a statement, everything through ; is abandoned. A production compiler can use context-specific synchronising sets or error productions to retain more structure. Recovery is a useful continuation strategy, not a proof that the skipped text has a unique correction.

Check complete consumption and resource limits

For the single-expression practice problem, call expression and then require EOF. Otherwise 2 3 might appear valid because the first call returns 2 and ignores the trailing number. For the program parser, require a semicolon after each expression and stop only at EOF. Empty programs are allowed; empty expressions are not.

Each successful token is normally consumed once, so syntax work is linear in token count. Nested parentheses use O(d) call-stack depth for nesting depth d. The scanner stores O(n) tokens and the program stores successful values. Python integers have arbitrary precision, so arithmetic cost also grows with the size of intermediate values.

Deeply nested source can exceed Python’s recursion limit. The practice tasks keep nesting below 100, which avoids this concern for ordinary classroom inputs. A parser for untrusted large documents should enforce a depth limit explicitly or use an iterative stack. Increasing the interpreter limit without controlling input depth is not a parsing strategy.

Examples

Multiply before adding

term consumes 3*4 before expression adds it to 2, giving 14.

Group and subtract from left to right

Parentheses produce 20. Repeated subtraction uses a loop and produces 6.

Recover after a malformed statement

Recovery discards the damaged statement through its semicolon, then keeps the later values.

Reject unknown source characters

The scanner reports @ before grammar functions run. No statement recovery is attempted here.

Common mistakes

Calling expression for the right side of every operator

That choice changes subtraction into a right-associated operation. Use term for additive operands and update the accumulator inside a loop.

Recording values before the statement ends

A returned expression value is not a completed statement. Match ; first so a damaged suffix cannot leave a false successful result.

Recovering without moving the token position

Consume a synchronising semicolon or stop at EOF. Re-entering the same failed phrase without progress repeats the error indefinitely.

Python version notes

The recursive parser uses standard Python 3.12 exceptions and integers. Python limits recursion depth, so very deeply nested expressions need an explicit stack.

Summary

Recursive descent mirrors grammar levels with functions. Loops preserve left association, calls handle nesting, and exceptions carry failures to recovery boundaries. Next, shift-reduce parsing builds phrases upward from recognised tokens.
