Introduction

In arithmetic, some operators should wait while a tighter operation finishes. An operator-precedence parser compares the nearest stack terminal with the next input terminal. Their relation says whether to read more tokens or reduce a completed phrase.

An operator grammar has no empty right sides and no two adjacent nonterminals on a right side. Terminals separate neighbouring phrases, giving visible boundaries for handle searches. An operator-precedence grammar additionally has at most one derived precedence relation for each ordered terminal pair.

These relations are written <·, =·, and ·>. They mean yields precedence, equal boundary precedence, and takes precedence. They are grammar-derived parsing relations, not numerical comparisons. In the tables and Python code, the shorter symbols <, =, and > represent those three relations.

Worked examples

Start with an operator grammar

E → E + T | T
T → T * F | F
F → ( E ) | id

Every right side is nonempty, and no right side places two nonterminals together. Unit productions such as E → T are permitted. The grammar already expresses multiplication precedence and left association. The relation table extracts enough terminal-boundary information to guide reductions for this expression language.

FIRSTVT(A) contains terminals that can occur first, or immediately after a leading nonterminal, in a form derived from A. Thus E → E + T puts + in FIRSTVT(E), even though a complete expression cannot begin with +. This set describes terminal boundaries near the left edge, not only first tokens of completed sentences.

LASTVT(A) is the corresponding right-edge set. A terminal can appear last or immediately before a trailing nonterminal. For T → T * F, * enters LASTVT(T) because it precedes the last F. Unit rules propagate the boundary sets from the inner nonterminal to the outer one.

Read a row as the closest terminal already on the stack and a column as the next input terminal. The + row under * contains <, so multiplication is shifted into the right operand. The * row under + contains >, so the product reduces before addition. The +/+ and */* entries contain >, giving left association at each level.

The = relation pairs the parenthesis boundaries; it does not claim that parentheses have the same arithmetic priority. The $/$ cell triggers a separate acceptance check. Accept only if the stack holds $ followed by exactly one completed start-expression marker. Empty input must not be accepted merely because both nearest terminals are $.

When the top terminal yields or has equal boundary precedence to the lookahead, shift. When it takes precedence, scan backward through stack terminals. Pass across = links until finding the nearest < boundary. The suffix after that boundary must match a permitted handle, including any N markers between its terminals.

Inside parentheses, + takes precedence over ), so the addition reduces. Then ( = ) permits shifting the closing parenthesis. The next comparison lets the whole (N) reduce. Only afterward can the outer multiplication proceed. The equality relation is therefore part of handle-boundary detection, while the reduction still checks a real production pattern.

The relation + < * shifts multiplication into the right operand before addition can reduce.

Reasoning and checks

Relation uniqueness is a necessary table property. If deriving a pair inserts both < and >, this construction cannot decide the action for that pair. Do not keep whichever relation was inserted last. A grammar with adjacent nonterminals also lacks the terminal separation assumed by the boundary algorithm. Use another parsing method or reshape the grammar instead of guessing a relation.

A non-error relation does not alone validate the input. For + id, the boundary table may allow the first shifts because FIRSTVT(E) contains +. Eventually the candidate suffix + N fails to match any allowed handle. The parser rejects it. Both relation checks and handle checks are required for correct recognition.

For id id, the id/id cell is an error immediately. For ( id, reductions reach a stack with an unmatched opening parenthesis, and the (/$ comparison is an error. For id +, the eventual N + handle is invalid because its right operand is missing. These examples show different ways the table and grammar cooperate to reject malformed phrases.

The demonstration recogniser scans backward through terminal indices when reducing. An efficient implementation can maintain boundary information directly on its stack. Operator precedence is useful for compact expression subparsers, but full programming languages include declarations, empty constructs, and adjacent phrases. LL or LR methods handle a much wider range of grammatical structures.

For an exam answer, show the grammar restrictions, FIRSTVT/LASTVT sets, relation-generation rules, and every terminal-pair cell. Then state whether your trace shows full nonterminal names or normalised N markers. During each reduction, identify the nearest terminal and the left handle boundary. That evidence explains why the product finishes before the surrounding addition.

Common mistakes

Using FIRST where FIRSTVT is needed

FIRST(E) excludes +, while FIRSTVT(E) includes it. Substituting ordinary FIRST loses operator-boundary relations such as + < *.

Comparing a nonterminal against lookahead

Skip N markers to find the nearest terminal. Relations are defined between terminal pairs, not between an expression marker and an operator.

Reducing a suffix without checking its shape

A > relation starts a handle search. It does not make every stack suffix valid. Reject an incomplete N + rather than inventing its missing operand.

Summary

Operator precedence combines terminal relations with handle recognition. FIRSTVT/LASTVT expose the boundaries needed to derive those relations. In Bison/Yacc, grammar rules and precedence declarations drive generated LR parsers.
