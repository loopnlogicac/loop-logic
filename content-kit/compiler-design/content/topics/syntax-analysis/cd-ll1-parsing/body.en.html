Introduction

Think of a route map whose rows name your current task and whose columns show the next sign. An LL(1) table plays that role for a parser. You look up one cell, apply its production, and continue without guessing.

The first L means reading input from left to right. The second L means constructing a leftmost derivation. The 1 means using one lookahead token to choose the next production. Lookahead is inspected without being consumed until a terminal match occurs.

An LL(1) grammar gives at most one applicable production in every predictive-table cell. An empty cell means syntax error for that nonterminal and lookahead. A cell containing two productions is a grammar conflict, even if a particular input never visits it. The implementation refuses to parse with any conflicting table.

How the parser works

Use the stack as a list of unfinished work

Place $ at the bottom of a stack and the start symbol above it. Append a separate $ to the input. The trace prints the stack from bottom to top, so its top is at the right. At every step, the stack describes what still needs to match the remaining input.

If the stack top is a terminal, it must equal the lookahead. Pop that terminal and advance one input token. If the top is a nonterminal A, consult M[A,lookahead]. Pop A and push the selected right side in reverse order. An ε rule pushes nothing and consumes no input.

The first expansion replaces E by T R. Reverse pushing leaves T on top and R below it. After F matches the first id, Q sees + and vanishes. R then selects + T R. The second T handles id * id before the final R vanishes at $.

Acceptance requires matching both end markers. An empty grammar-work stack without a consumed input marker is not enough. Likewise, reading all ordinary tokens does not permit ignoring unfinished nonterminals. For id +, T remains on top when lookahead is $, so the parser rejects the missing operand.

Test the grammar rather than trusting its shape

A FIRST/FOLLOW collision; slash retains both alternatives
Nonterminala$

For S → A a and A → a | ε, FIRST(a) contains a. Because A can disappear, its ε rule also selects FOLLOW(A), which contains a. One token of lookahead cannot choose whether the first a belongs to A or to the following terminal. The grammar is not LL(1), although the language itself has an LL(1) description S → a R, R → a | ε.

For alternatives α and β, their terminal FIRST sets must be disjoint. If α is nullable, FIRST(β) must also avoid FOLLOW(A). Apply the symmetric condition when β is nullable. If both are nullable and FOLLOW(A) is nonempty, their selection sets collide. Constructing the table checks these conditions directly.

Recognise errors at the current decision

For id + * id, the parser has already matched id and + when T sees *. M[T,*] is empty, so report an expected operand at that point. For ( id $, the parser eventually expects ) but sees $. These failures occur at different operations: a missing production versus a terminal mismatch.

The predictive recogniser stops at the first syntax error. A teaching tool can report the stack top, lookahead, and possible non-error columns in that row. A production parser may recover using synchronising tokens, such as ; or ). Recovery should never turn a damaged statement into a successful one without recording the error.

Table construction costs depend on the grammar and its FIRST/FOLLOW calculation. Once a fixed LL(1) grammar has a table, each stack operation is constant time apart from pushing a fixed-length right side. For ordinary reduced LL(1) grammars, parsing uses O(n) actions and O(n) worst-case stack space for n tokens. Nested parentheses demonstrate why the stack may grow with input depth.

The recogniser does not evaluate arithmetic or build an abstract syntax tree. Its job is to decide whether the token order fits the grammar. You can attach construction actions to productions later, but those actions must preserve the intended precedence and association. Keep recognition traces separate from numeric evaluation so a correct value cannot hide an invalid token sequence.

Common mistakes

Pushing a production in forward order

A Python list pops at its right end. Pushing T then R would expand R first. Use reversed(rhs) so the leftmost grammar symbol is handled next.

Overwriting a conflict

Assigning table[A,a] = rule can silently hide an earlier rule. Retain all candidates and reject a table with multiple choices.

Matching an epsilon token

The ε alternative removes unfinished work without advancing input. Its selection comes from FOLLOW, not from an epsilon column.

Accepting an early input prefix

The valid prefix id does not make id id valid. Require the stack and the complete token stream to reach their end markers together.

Python version notes

Python 3.12 lists support the stack operations used here. Dictionary insertion order does not decide a grammar choice; conflicting cells retain every alternative.

Summary

A predictive table turns grammar decisions into deterministic stack operations. A conflict exposes insufficient lookahead for that grammar. In recursive descent, ordinary Python functions carry out similar decisions and can compute expression values.
