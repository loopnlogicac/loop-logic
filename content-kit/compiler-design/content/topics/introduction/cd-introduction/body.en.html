Introduction

Imagine you write a marks calculator, but the processor understands only machine instructions. A compiler helps bridge that gap. You express the calculation using names and rules that people can read. The compiler translates that description into a form another system can use.

A translator changes a program from one language or representation into another. Its input is the source language. Its output is the target language. The target need not be machine code. It might be assembly, virtual-machine instructions, or another programming language.

A compiler is a translator that produces a target program while preserving the source program's defined meaning. For a correct marks calculation, the translated program must calculate the same result. Changing variable names internally is usually harmless. Changing the formula from an average into a sum is not.

You study compilers to understand more than executable files. The same ideas appear in formula editors, query processors, configuration readers, and code analysis tools. Whenever you read structured text and decide what it means, compiler techniques can help.

Worked examples

Four jobs around a small calculation

Take the expression total = marks + 5. A compiler might translate it into target instructions. An interpreter instead carries out the described operations using its own execution machinery. An assembler translates assembly notation into machine instructions and related object information.

The assembly names above describe an imaginary machine. They explain responsibilities rather than promise a particular processor's syntax. A linker connects separately translated pieces. A loader places a program in memory and prepares execution. Neither tool replaces the compiler's language analysis.

Compilation and interpretation can cooperate

Suppose a teaching system first translates an expression into a list of operations. A second component walks that list and performs each operation. The first component acts as a compiler. The second acts as an interpreter. Both descriptions are useful because they describe different stages of the same system.

Python offers a familiar example of this cooperation. In common CPython execution, source is compiled into code objects containing bytecode. The Python virtual machine then executes those instructions. Saying that Python never compiles would hide this useful distinction. Other Python implementations may use different strategies.

A just-in-time compiler, often called a JIT, translates selected code during execution. A runtime may interpret some operations and compile frequently used ones. This is why a strict claim about all compilers being faster than all interpreters is misleading. Program size, startup cost, optimisation, and runtime behaviour all matter.

Why compiler ideas are useful

A compiler course trains you to separate spelling, structure, and meaning. The characters in marks + 5 form meaningful pieces. Those pieces form an expression. The expression then needs rules about types and values. Keeping these questions separate makes both implementation and error messages clearer.

Consider a spreadsheet formula reader. It must recognise a cell name, decide where multiplication belongs, and reject an unknown function. A search tool may use a small pattern language. A database can translate a query into an execution plan. These applications use related ideas even when they never produce native machine code.

Compiler work also gives you practice with tables, graphs, and precise definitions. A state table can describe valid number spellings. A tree can describe which operations belong together. A symbol table can remember what each name represents. You will build these pieces gradually rather than inventing a complete language at once.

When choosing a translation strategy, first ask what result the next component needs. A learning tool may prefer a readable intermediate form. A small embedded device may need a native executable for a different processor. An interactive calculator may prefer immediate evaluation. The intended use guides the architecture.

Common mistakes

Treating a language as one execution method

A language specifies program meaning; an implementation chooses how to realise it. Describe the implementation you mean. Avoid claiming that a language can only be compiled or only be interpreted.

Expecting translation to reveal every error

A compiler can accept a program that later divides by a value supplied as zero. Some problems depend on runtime data. Distinguish a reported translation error from a failure during execution and from a logical mistake in an otherwise valid formula.

Confusing an assembler with a linker

An assembler encodes assembly instructions. A linker resolves connections between object files and libraries. If a library definition is missing, changing how the assembler encodes an addition will not supply that definition.

Summary

Translation produces another program representation; interpretation performs operations. A real system may combine both. Check which component receives source, which produces a target, and which executes instructions. Continue with Phases of a Compiler to follow one statement through the translator.
