Introduction

You can recognise one identifier with a pattern, but a program contains many different tokens together. A lexer must decide where each token ends, remember positions, and continue after spaces or comments. We will build that whole character-to-token loop for a small classroom language.

The language can express let marks=85; and print marks+5;. It also includes parentheses, multiplication, division, subtraction, and an equality operator. The lexer recognises these pieces without evaluating expressions or checking whether a variable has been declared.

A cursor is the current position in the source. Our scanner stores a zero-based string offset plus one-based line and column. Each emitted token records its category, original spelling, and starting line and column. This gives later analysis enough information for clear diagnostics.

This language has integers but no decimal literals, strings, block comments, or Unicode identifiers. A pair of slashes starts a line comment that runs to a newline or end of input. Space, tab, and carriage return are skipped. A newline updates the line and resets the column.

Each stored tab counts as one character column. This differs from a screen editor that expands a tab into several visual spaces. A real tool can support visual columns, but its convention must remain consistent. The source positions here count Python string characters, not encoded UTF-8 bytes.

A digit sequence followed immediately by a letter produces two tokens under these rules. Thus 12roll becomes INT(12) followed by ID(roll). Whether that sequence makes sense in a statement is a parser question. If your language instead bans this spelling lexically, add a deliberate rule and explain it.

Implement the advancing loop

The tokenize generator yields one record at a time. A generator lets the caller receive tokens as needed, although this demonstration reads the source text into memory first. It is not a streaming file-buffer implementation.

At each offset, handle whitespace and comments before ordinary tokens. Whitespace changes positions but yields no record. A comment consumes characters until newline; the next loop iteration handles that newline. This keeps line counting in one place.

For an identifier, remember its start and advance while allowed name characters remain. Then look up the complete spelling in the keyword table. For an integer, advance through ASCII digits. Neither loop advances beyond the string because its condition checks the offset first.

Check the two-character equality operator before the single-character operator dictionary. Otherwise == would become two assignment tokens. Comment recognition similarly happens before the single slash rule. These explicit choices implement longest matching for the overlapping spellings in this language.

When a token ends, its spelling is the slice from the remembered start to the current offset. Its column advances by that slice length. None of the ordinary tokens spans a newline, so this update is sufficient. Newlines and comments have their own position handling.

For an unsupported character, yield an ERROR record and advance by one character. Continuing lets you report more than one problem. The EOF record is emitted once after the outer loop finishes. It has empty spelling and the final line and column.

Progress, errors, and resource costs

A useful loop invariant is that every successful iteration either advances the offset or exits the scan. Whitespace, newline, comment, identifier, integer, operator, and error branches all advance. EOF is outside the loop. This structure prevents an error branch from becoming an infinite loop.

Another invariant is that line and column describe the character at the current offset. Each branch must preserve it. Identifier and integer branches move only within one line. Comment scanning stops before newline, and the newline branch resets the position. These facts make the recorded starts reliable.

Empty input produces only EOF at 1:1. A comment with no newline consumes through the last character and then produces EOF. A single slash is SLASH because it is not a comment opener. Three equals signs produce EQ followed by ASSIGN.

The hand-written scan advances over each character a bounded number of times, so its time is O(n) for source length n. Slicing a completed token copies its characters, but the total copied spelling length is still O(n). The loaded source uses O(n) memory. A caller that stores every token also uses O(n) additional storage.

The generator itself retains only the source and current scan state between yields. A different design could read chunks and preserve incomplete tokens, as discussed in the buffering lesson. Do not claim constant total memory for this implementation merely because it yields tokens lazily.

Tokenisation is only the front boundary of a compiler. The input print + ; has recognised tokens but lacks an operand. An undeclared name can also be a perfectly valid ID token. Send these records to the parser and later semantic checks rather than making the scanner guess missing structure.

Recovery is intentionally local here. Consuming one illegal character is easy to understand, but a richer language may need different handling for an unfinished quoted string or nested comment. Those features require their own rules before the error policy can be chosen.

Common mistakes

Checking a keyword prefix early

Do not stop after the letters print when the next character continues an identifier. Read printable in full, then compare with the keyword table. Exact matching keeps keyword boundaries predictable.

Moving the offset but not the column

A scanner can produce correct categories while every later error points to the wrong place. Check positions using small inputs with known character counts. Include comments and blank lines because they are easy to skip incorrectly.

Using Unicode predicates accidentally

Python's isalpha and isdigit accept more characters than our language. The letter helper adds an ASCII check, and the digit helper compares 0 through 9 explicitly. Wider source-language rules would need a different definition.

Handling an error without consuming it

Yielding an ERROR token does not move the cursor by itself. The branch must increment offset and column before the loop repeats. Test two adjacent invalid characters to verify both are reported exactly once.

Version notes

The lexer uses functions, dictionaries, generators, and f-strings from the Python standard environment. It runs on Python 3.10 or later without packages. The same scanner function appears in the demonstrations so each complete program can be read and tried independently.

Summary

A hand-written lexer combines explicit spelling rules, longest-match choices, position tracking, and a progress guarantee. Its tokens describe source pieces while leaving grammar and meaning for later stages. Next, compare this approach with rule-based generation in Lexer Generators: Flex.
