Introduction

When you read a classroom notice, you recognise words before deciding how the sentence fits together. A lexical analyser does similar early work for a program. It groups characters into meaningful pieces so the next stage does not need to inspect every letter.

A lexeme is the actual source spelling, such as marks or 85. A token describes the category of that spelling, such as identifier or integer. A pattern is a rule for which spellings belong to a category.

The lexical analyser is also called a lexer or scanner. Its output normally feeds a parser. The parser checks how tokens combine into expressions and statements. Recognising each token successfully does not prove that their sequence forms a legal program.

Token rules and attributes

For a small marks language, identifiers begin with an ASCII letter or underscore. Further characters may also be ASCII digits. Integers contain one or more digits. The words let and print are reserved. Operators and punctuation have their own token categories.

A token may carry a value, spelling, and source location. The integer lexeme 85 can carry the numeric value 85. The identifier token can carry its spelling for later declaration lookup. The token's category alone cannot distinguish marks from roll.

Characters, boundaries, and buffering

A scanner maintains a current position. It identifies a token start, advances through a matching spelling, emits a token, and continues. Spaces and comments often separate tokens without becoming parser tokens. Newlines can still update locations even when discarded.

Two common decisions are longest match and keyword recognition. If a name begins with the letters print but continues as printable, read the entire identifier. Then compare that complete spelling with the keyword table. The word printable remains one identifier rather than a keyword followed by another token.

Input buffering means reading characters in blocks rather than requesting each one separately from storage. A scanner may use a token-start pointer and a forward pointer. The forward pointer explores possible matches while token-start remembers where the current spelling began.

A buffer boundary is not a token boundary. If one block ends with mar and the next begins with ks, the name is marks. Preserve the unfinished spelling or keep access to its earlier characters. Token length can exceed a buffer's capacity, so a real design needs a growth or spill strategy.

A traditional two-buffer design alternates two regions. While scanning one region, the implementation can refill the other when safe. A sentinel can signal a region boundary, but it must not be confused with a source character or with true end of file. Never overwrite characters still needed by the current token.

Lexical errors and progress

A lexical error occurs when source text cannot form an allowed token under the language's rules. An unsupported character is a simple example. An unterminated string or comment can also be lexical, when the language includes those constructs.

Some malformed-looking text is still a valid sequence of tokens. A language that allows an integer immediately before an identifier may scan 2roll as INT(2), ID(roll). A whole-word classifier may reject 2roll as one word instead. State which interface you are using before claiming there is a lexical error.

Useful diagnostics retain the bad spelling and its position. A recovery policy might report one illegal character and advance past it. Another policy may stop immediately. Whichever policy you choose, scanning must make progress or terminate. Reporting the same character forever is not recovery.

Line and column conventions also need a rule. These lessons use one-based lines and columns. A newline moves to the next line and resets the column to one. Tabs can count as one stored character or expand to display columns; document the choice rather than mixing conventions.

Common mistakes

Calling the category the lexeme

ID is a category. The text marks is a lexeme. Keep both when explaining an example, because later name checking needs the particular spelling.

Emitting at every buffer refill

A refill only means more characters are needed. Wait for an actual token boundary or true end of input. Otherwise marks can become two incorrect identifiers.

Throwing away locations with whitespace

Skipping whitespace does not mean ignoring its effect on positions. Update line and column before recognising the next token. A correct token at the wrong location still produces a confusing diagnostic.

Version notes

The examples use Python's standard library and run on Python 3.10 or later. ASCII checks are explicit because Python character predicates also recognise many non-ASCII letters and digits. A different source language may deliberately allow those characters.

Summary

A scanner recognises spellings, returns categories and attributes, and retains positions. Buffering must not change token boundaries. Error handling must either advance or stop. Continue with Regular Expressions for Tokens to express spelling rules precisely.
