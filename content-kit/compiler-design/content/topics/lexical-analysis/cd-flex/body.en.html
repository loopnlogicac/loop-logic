Introduction

Writing every scanner branch yourself gives you control, but it can become repetitive as a language grows. A lexer generator lets you write token patterns and actions instead. Flex translates that rule description into a scanner implementation.

A lexer generator is a tool that builds a scanner from lexical rules. The generated scanner reads the student's program; the generator itself reads the language designer's rules. Keeping those two inputs separate helps explain what happens during construction and what happens during scanning.

Flex is commonly used to produce C scanner code from a file ending in .l. Its patterns resemble regular expressions, but their notation is not identical to Python re. This topic shows Flex descriptions for reading and tracing. The runnable scanner implementations in this course use Python.

The key ideas are the file's three sections, pattern-action rules, matched text, and deterministic recognition. You can understand these ideas before learning a full parser generator interface. A scanner can first print category names, then later return token codes to a parser.

Worked examples

Read the three-part rule file

A Flex file has a definitions section, a rules section, and an optional user-code section. Two separator lines containing %% divide them. Definitions contain options, named patterns, and C declarations. Rules pair patterns with C actions. User code supplies helper functions or a main function.

The section boundaries are part of the .l format

The compact description below prints categories for a restricted language. It recognises only let as a keyword, identifiers, integers, equality, and assignment. It skips whitespace and reports other characters. This rule set is intentionally narrower than the hand-written classroom scanner.

%option noyywrap
%{
#include <stdio.h>
%}
%%
[ \t\r\n]+ ;
"let" { printf("LET %s\n", yytext); }
[A-Za-z_][A-Za-z0-9_]* { printf("ID %s\n", yytext); }
[0-9]+ { printf("INT %s\n", yytext); }
"==" { printf("EQ %s\n", yytext); }
"=" { printf("ASSIGN %s\n", yytext); }
. { printf("ERROR %s\n", yytext); }
%%
int main(void) { yylex(); return 0; }

The option noyywrap removes the need to supply the usual yywrap end-of-input callback. The declaration block includes the printing header. The rule for whitespace uses an empty action, so matching whitespace performs no token action. The main function calls yylex, the scanner entry function.

The fallback dot catches one non-newline character. Newlines are already covered by the whitespace rule. Without a suitable fallback, Flex's default rule can echo unmatched input. An intentional catch-all makes unexpected source characters visible rather than silently treating them as valid tokens.

Apply longest match, then rule order

At the current input position, Flex selects the rule matching the most characters. When rules tie on length, the earlier rule wins. These are two separate decisions. Earlier placement does not let a short keyword prefix defeat a longer identifier.

For let, the keyword and identifier rules match the same three characters. The earlier keyword rule wins. For letter, the identifier rule matches six characters, while the keyword rule matches only three. Longest match chooses the whole identifier despite the keyword appearing first.

For ==, the equality rule matches two characters. Assignment and fallback can match only one. Equality wins even if the one-character assignment rule is written earlier. This differs from assuming that the first successful Python regex alternative automatically implements longest token matching.

Use yytext and yyleng in an action

yytext gives access to the spelling matched by the selected rule. yyleng gives its length. For integer 25, the text contains the two digit characters and the length is two. The action can convert those digits to a numeric attribute if needed.

A matched spelling and its converted value are different things. The text 0025 has length four even when its integer value is 25. Preserve the spelling when an error message or source display needs it. Use checked conversion routines when a real scanner must handle values outside the target type's range.

Do not assume yytext remains unchanged after the next scanner operation. Later scanning can reuse the underlying storage. If a parser or symbol table needs a name for longer, copy or intern it using an ownership rule. An action that returns a pointer without considering its lifetime can corrupt later name information.

From patterns to a scanner automaton

The conceptual generator pipeline begins with automata for token patterns. Epsilon edges combine them under one start. Accepting states remember which rule they belong to. Subset construction creates a deterministic machine whose states can include several candidate rule finals.

The scanner may pass through several accepting states while exploring a longer match. It remembers the most recent accepting point and the corresponding winning rule. When no transition can continue, it returns to that point, exposes the matched text, and performs the action.

This last-accepting-point rule explains why finding one accepted prefix is not enough to emit immediately. An identifier may grow with each new character. A one-character operator may become a two-character operator. The scanner must establish that no longer candidate wins before committing.

Rule labels matter during automaton optimisation. Ordinary yes/no DFA minimisation preserves only acceptance. A token scanner must also preserve which action wins. Two accepting states with different winning actions cannot be merged merely because both accept some word.

In a parser-based system, an action often returns an integer token code instead of printing a label. A parser may also need the token's semantic value and location. Flex and Bison integrations define interfaces for these details; the exact declarations depend on the chosen parser settings.

Skipping whitespace with an empty action makes yylex continue looking for a meaningful token. Returning a token pauses that call so a parser can process it. End of input is a separate condition; it should not be disguised as a bad source character.

Location tracking still requires a policy. Newline rules or scanner options can update a line counter. Columns need updates for all matched text, including skipped whitespace and comments. Generating the recogniser does not automatically settle whether a tab counts as one character or several display columns.

Common mistakes

Putting a general identifier rule before a keyword

Equal-length keyword matches then lose to the identifier rule. Place keyword rules earlier or classify complete identifiers in an action. Longest match still protects longer names such as letter.

Reusing Python pattern syntax without checking it

Flex definitions and escapes follow Flex's syntax. A Python raw-string prefix is not part of a .l pattern. Translate the intended spelling rule, rather than pasting host-language notation blindly.

Believing an empty action returns a token

The whitespace rule performs no return. Scanning continues. If a grammar requires newlines as tokens, the whitespace rule must not swallow them without an action that communicates them.

Losing the winning action during minimisation

Recognising a token spelling is only half the job. The scanner must also select its category and action. Preserve rule priority in accepting labels when combining or reducing states.

Summary

Flex separates definitions, rules, and supporting code. Its longest-match rule uses file order only for equal lengths. Actions read yytext and yyleng, then skip text, report errors, or deliver tokens. Continue toward Context-Free Grammars, where the parser organises those tokens into structure.
